## 一、Runway 连接器实际能调用什么

### 3. 工作流编辑工具（单独权限，同样每次审批）

`create_workflow`、`save_workflow_version`、`validate_workflow_graph`。

### 4. 运行机制（文档明文，写进方案当纪律）

- 生成是异步任务制：提交后用 `get_task` 查状态与产物，查到终态才许报结果。

- 工具的真实入参以 `list-tools` 返回的实时 schema 为准，不许猜工具名和必填字段。

## 二、为什么首测盯升频：与我方现状的对照

现行管线（管线文档 v2/v4 口径）：AI 生成源只有 **720×1280、24fps**，合成时由 ffmpeg（build-v2.py）**插值放大**到 1080×1920、30fps 输出。也就是说，用户 2026-11-16 立的短视频四条硬标准第②条「成片做高清修复收尾」，至今实际只有插值放大，**从没做过 AI 升频**——插值不产生新细节，这是已知短板（管线文档第四节第 3 条自认）。Runway 的 `upscale_video` 是现成对口工具，已连接、从没用过。

## 三、首测方案

### 样本

`~/workspace/social-ops/week3/assets/W3D4-video-final.mp4`（主片，约 36MB，1080×1920/30fps——即 720p 源经 ffmpeg 插值的现行成片）。选它的理由：已排期 2026-12-05 19:30 发布，是在排期成片里发布时间最晚的一条，测试与回滚时间最充裕；且内容为茶园题材，茶垄纹理、叶片、远山轮廓都有可比对的细节层次。
全程纪律：只在本地副本上测，**不动平台侧排期、不覆盖原文件**，产物另存 `~/workspace/social-ops/runway-test/`。

### 步骤

- **第 0 步（只读、零费用，先行）**：`status` 确认连接 → `list-tools` 取 `upscale_video` 的真实 schema（入参、输出档位、时长/大小限制）→ `show_plans_and_credits` 查套餐与余额，按 schema 估算本条成本。三项任一与本方案假设不符（无升频档位、余额不够、时长超限），停手回报，不硬上。
- **第 1 步（基线取证）**：对样本跑 ffprobe（时长/分辨率/帧率/音视频流/码率/大小），按管线自检同点位抽 5 帧存档（5/15/25/35/45 秒），作为升频前后对照基线。
- **第 2 步（上传＋提交）**：`init_upload`＋`complete_upload` 上传样本 → `call-tool upscale_video` 提交。此步是媒体调用：按连接器口径每次都要审批、且耗积分，执行时会有审批卡，属平台机制，先在此写明。
- **第 3 步（等终态）**：`get_task` 轮询至终态；失败/超时先查 `list_recent` 确认是否其实已产出，确认无产出才许第二次提交。
- **第 4 步（下载＋验收）**：产物下载到 `runway-test/`，按下面标准逐项验，结果记入本文件续篇或管线文档，不许只报「成功」。

### 验收标准（逐项可复核）

| 项 | 标准 | 验法 |
|---|---|---|
| 分辨率 | 达到第 0 步 schema 确认的最高输出档（预期 2160×3840） | ffprobe 实测读数，不许拿 ffmpeg 插值充数 |
| 帧率 | 与源一致（30fps），或变化被明确记录 | ffprobe |
| 时长 | 与源差 ≤0.1 秒 | ffprobe 前后对账 |
| 音画同步 | 产物保留 AAC 音轨；抽 3 个口播句首时点，字幕出现时刻与源偏移 ≤100ms | 抽帧＋试听比对 |
| 画质提升 | 同点位 5 帧与基线并排：茶垄纹理、叶片边缘、远山轮廓锐度提升肉眼可辨 | 抽帧并排目检，截图留证 |
| 文字完整性 | 烧录字幕与右上「AI 生成示意图」角标逐字核对，无错字、无变形、无重绘乱码 | 抽帧逐字核（AI 升频最容易在这里翻车） |
| 成本 | 实际扣减积分与第 0 步估算对账，记单条成本 | `show_plans_and_credits` 前后差 |

### 失败兜底

- **任务失败/超时**：不重跑，先 `get_task`/`list_recent` 定性；确认未产出才二次提交（防重复扣费）。
- **产物无音轨**：ffmpeg `-c:v copy` 把源音轨回 mux，再按音画同步标准复验。
- **字幕/角标被 AI 重绘变形**：整片升频路线判不通过 → 转衔接点 B（分段先升频、后烧字幕），结论照实记，不许把变形产物当成果。
- **画质无肉眼提升或单条成本过高**：如实报不达标、不入管线，现行 ffmpeg 链照常跑，Runway 升频降为备选登记。
- **余额不足**：停手回报差额，不许先斩后奏充值。

## 四、与现有 ffmpeg 管线的衔接点

现行链：AI 分段生成（720×1280/24fps）→ ffmpeg build-v2.py 分段渲染、插值放大、concat、配音混音、配乐（v4 口径已取消垫乐）、烧逐字字幕 → 主片 1080×1920/30fps ＋微信版 720×1280 → 发布时平台加 BGM。

- **衔接点 A（首测验证位）**：ffmpeg 合成之后、发布之前，对主片整片走 `upscale_video`。优点：改动最小，一条链验清工具可用性、效果与单条成本。缺点：字幕与角标已烧录，AI 重绘风险最高；整片约 50 秒计费。这是首测选 A 的原因——先验工具，不等于生产就走 A。
- **衔接点 B（推荐生产位）**：替换 build-v2.py 里「分段渲染→插值放大」一环——5 段 720p 源片段先逐段 `upscale_video` 到 1080×1920，再交 ffmpeg 做 concat、混音、烧字幕。优点：字幕在升频之后才烧，零重绘风险；片段短、单段失败重跑成本低；与现行「逐段抽帧检查」自检位天然对齐。缺点：每条 5 次媒体调用，审批与积分次数多，入管线前要把单条总成本算清。
- **衔接点 C（登记备选，非本次范围）**：`upscale_image` 给封面图升频、`remove_video_background` 备选抠像、`generate_speech` 与现行 TTS 线互为备选——只登记，等 A/B 有结论再议。

结论建议：首测走 A 验工具链与成本口径；生产入管线优先 B。A、B 共用第三节同一套验收标准。
