# 记账解析攻坚（课程台账专题 7）

研究日期：2026-11-26。范围：只做公开资料研究，未登录任何账号、未读取任何本地文件、未动任何数据。
背景卡点：六家银行（邮储/工行/建行/农行/柳州银行/广西农信）记账以 163 邮箱账单为准；Mac 上网易邮箱大师本地库 content.db 中，建行账单（LocalId=179/194）已定位，但 OrigBody 标准 zlib 解压只得 "Email Preview" 占位链接、非完整账单 HTML；mail.db 中无银行账单附件。

## 结论先行：三条路线排序

| 路线 | 定位 | 理由 |
|---|---|---|
| A. IMAP 授权码直连 163 拉原文 | **主线** | 拿到的是服务器上的完整 RFC822 原文（HTML 正文＋附件），不受本地客户端存了多少的影响；六家银行的账单识别锚点在开源界已有实证（见第一节）。本地库解码无论成败都不再是单点故障。 |
| B. content.db 解码攻坚 | 存量补救 | 只解决"本地已有、服务器拉取不便"的存量；且现有证据提示卡点可能不是编码而是"本地只存了预览"（见第二节），先做低成本证伪再投入。 |
| C. 客户端内触发全文下载 / App 申请导出 | 辅助 | 对只有预览的条目，在邮箱大师内打开邮件触发全文下载后重查；对借记卡类无周期邮件账单的银行，走银行 App"明细导出→发邮箱"通道（建行借记卡已有成熟模式，见第一节）。 |

## 一、六家银行电子账单邮件的版式与字段特点

### 1. 工商银行（ICBC）信用卡 —— 有开源实证
- **识别锚点**：对账单邮件标题通常为「中国工商银行客户对账单」；正文为 HTML 表格，交易明细表中含「商户名称」列，开源解析器即以此表为锚点逐行提取（依据：PyPI 项目 china_bean_importers 的 icbc_credit_card 说明；zsxsoft/my-beancount-scripts 的 ICBCCredit 实现，输入为 EML 原文）。
- **解析目标字段**：交易日、记账日、卡号后四位、商户名称、交易金额（人民币/外币分列）、摘要。
- 注意：china_bean_importers 将工行信用卡 importer 标注为"测试"，版式稳定性需以真实样本回归为准。

### 2. 建设银行（CCB）—— 信用卡与借记卡是两条完全不同的通道
- **信用卡**：邮件主题含「中国建设银行信用卡」；正文 HTML 中有「」分段表，开源解析器 CCBCredit 以此为锚点（依据：my-beancount-scripts 的 Bank Credit Card Importers 文档）。这与我方现象吻合：建行账单是正文 HTML 而非附件，所以 mail.db 里找不到账单附件是正常的。
- **借记卡**：未见周期性邮件账单的公开口径；成熟路径是手机银行 App 内「我的→银行卡→管理→明细导出→明细导出申请」，选发送方式后**邮箱收到带密码的 ZIP，解压密码在 App 的导出历史中查询**，ZIP 内为 XLS，转 CSV 后解析（依据：china_bean_importers 的 ccb_debit_card 说明）。
- 账单基础概念以建行官方《龙卡信用卡使用指南》为准：账单日、到期还款日、本期全部应还款额、最低还款额四项是每期账单的汇总锚点，对账时优先抓这四项与台账勾稽。

### 3. 农业银行（ABC）信用卡 —— 有开源实证
- **识别锚点**：邮件主题含「金穗信用卡」；正文 HTML 中以 `#reportPanel3` 区块内的 `#loopBand1` 循环表为明细锚点（依据：my-beancount-scripts 的 ABCCredit 实现）。

### 4. 邮储银行（PSBC）信用卡 —— 有官方口径
- **电邮账单**：账单日后**第 2 日**发送至预留电子邮箱；发件地址为 `creditcardcenter@cardmail.psbcltd.cn`（可作 IMAP 侧的发件人过滤锚点）；开通/变更方式：信用卡 App 账单寄送栏目，或短信「DZZDTX#卡号后4位#电子邮箱地址」发送至 95580（依据：邮储银行信用卡"账单知识"页，含电邮账单白名单指引）。
- **到期还款日**：账单日后第 20 日（同上）。
- 正文版式（HTML 还是 PDF 附件、字段排布）：**未确认**，公开渠道未见样本披露，须以邮箱中真实样本为准。

### 5. 柳州银行、6. 广西农信 —— 公开信息缺失，标未确认
- 本轮检索（含官网公告、百科、行业报道）**未找到两家有周期性电邮账单的公开说明**，其公开材料以手机银行/微信银行/网银渠道为主。
- 现实路径（与建行借记卡同构）：手机银行内申请交易明细导出（PDF/Excel）发送到邮箱，再走附件解析；若邮箱里从未出现这两家的账单，"邮箱里有账单再记账"对这两家天然不成立，需改以导出文件为输入源。此点须向用户点明，不能假设六家同构。

### 通用规律
- 五大行自 2014–2015 年起陆续取消纸质账单、全面电子化，信用卡账单以邮件推送为标准通道之一（依据：公开新闻报道汇总）。
- 信用卡账单主流形态是 **HTML 正文**（工行/建行/农行均然），借记卡明细主流形态是 **App 申请→邮箱加密 ZIP/PDF**；解析器应按这两类各备一条管线，而不是按银行逐个硬编码到底。

## 二、网易邮箱大师本地库：公开已知信息与 OrigBody 编码假设

### 已知事实（有公开来源）
1. **Mac 版数据目录**：沙盒容器 `~/Library/Containers/com.netease.macmail` 内含设置与本地邮件数据（依据：Mole 卸载指南对 mailmaster cask zap 清单的实测记录）。
2. **本地正文确为压缩存储、且可被第三方解出**：社区已有"网易邮箱大师本地读取"技能包（mailmaster-local-reader）在售卖/分发，功能描述明确包括"定位数据目录、按关键词/日期/账号/文件夹搜索本地邮件、**读取并解压（decompress）邮件正文**、查看元数据"（依据：砖块儿商品页 zhuankuai.com 与 yeyupiaoling 博客的技能介绍）。这证明 content.db 路线在原理上可行、且有人已跑通，但其具体解码方法未公开披露。
3. **同类客户端的通行做法**：Android Gmail 的 mailstore 库中，短正文存明文字段、长正文以 **zlib 压缩存入单独的 BLOB 字段**（body/bodyCompressed 双字段设计），SQLite 本身不提供解压函数、须在应用层 inflate（依据：Linux Sleuthing 取证博客对 Gmail mailstore 的实测分析）。邮箱大师采用"元数据一库、正文一库（content.db）"的拆分与此模式同构。

### 对当前卡点的判断（分析，非实证）
- 关键事实：OrigBody 用**标准 zlib 已经解压成功**，解出的内容是 "Email Preview" 占位链接。这说明该条记录的编码层没有问题——**本地存的本来就只有预览段**。邮箱大师存在省流量/按需下载类设计：未在客户端内打开过的邮件，本地可能只落了摘要预览，全文留在服务器。
- 因此攻坚顺序应先证伪"编码问题"、确认"存量不全"，再决定是否继续深挖编码；若属实，B 路线的价值只剩"批量判定哪些条目是预览占位"，全文一律走 A 路线（IMAP）补齐。
- 另一非官方来源（网易邮箱大师类 SEO 站点）有"本地邮件加密存储"的说法，若属实则部分字段可能另有加密层；该说法未经证实，列入未确认，不作为立论依据。

## 三、content.db 解码攻坚清单（按可行性排序，每条附依据）

1. **先验"预览占位"假设（零成本，先做）**
做法：在邮箱大师内打开 LocalId=179/194 对应邮件、等全文加载完，退出后重查同一 LocalId 的 OrigBody，对比长度与解压结果是否由占位变为完整 HTML。
依据：标准 zlib 已成功解出占位文本（背景事实）＋邮箱客户端按需下载的通行设计。若假设成立，本地库攻坚立即降级为存量盘点工具。

2. **对全部账单条目做占位签名盘点**
做法：批量解压已定位的账单类 OrigBody，统计"解出占位链接"与"解出完整 HTML"的比例和分界特征（如长度阈值、占位链接域名），形成"本地可用/须 IMAP 补拉"的清单。
依据：占位内容本身即签名；先把存量摸清，再决定 IMAP 补拉范围，避免全量重拉。

3. **BLOB 编码指纹全扫描（防漏检其他编码的条目）**
做法：对解压失败的 BLOB 逐一做 magic 检测——zlib（0x78 01/9C/DA）、gzip（0x1F 8B）、zstd（0x28 B5 2F FD）、LZ4 frame（0x04 22 4D 18）、snappy；再做 0–64 字节偏移扫描逐偏移试 inflate（raw deflate 用 wbits=-15 另试）。
依据：Gmail mailstore 先例证明同类客户端以 zlib 家族存长正文；偏移扫描覆盖"头部带长度/标志字节"的常见私有封装。

4. **查容器内的旁路正文与附件文件**
做法：在 `~/Library/Containers/com.netease.macmail` 容器内（只读）盘点 content.db 之外的 EML/HTML 缓存文件与附件目录，看已下载附件和全文缓存是否另存为文件。
依据：Mole 实测记录确认容器内含本地邮件数据；邮箱大师"文件中心"有附件本地管理功能，附件落盘成文件是常见实现。

5. **拿社区现成实现做对照样本**
做法：mailmaster-local-reader 技能包声称已实现本地正文解压读取，可购入/取其文档做对照，用同一封邮件比对输出，反推其解码路径（偏移、算法、字段映射）。
依据：砖块儿商品页与博客介绍均明确其"read and decompress message bodies"能力；有现成轮子时不重复造（开源/现成优先口径）。注意其为付费社区包，口径未经我方验证，购入前须评估。

6. **同封邮件三方逐字节比对（定规则）**
做法：同一封建行账单，分别取 IMAP 原文 HTML、OrigBody 解压结果、网页版导出，比对截断点与占位生成规则，固化"预览占位"的机器可判签名，供管线自动分流。
依据：第 1、2 条的自然延伸；没有比对基线，批量解析无法自动判废。

7. **（最低优先）私有加密/混淆层逆向**
做法：若某类 BLOB 呈高熵、无任何已知 magic、偏移扫描全灭，再考虑 XOR/AES＋应用内密钥等可能。
依据：仅有非官方"本地加密存储"说法支撑，未证实；且此类逆向成本高、随版本失效，性价比最低——若走到这一步，结论应是放弃该类字段、全量改走 IMAP，而不是硬解。

## 四、IMAP 授权码直连拉取：正规流程要点

1. **开服务、拿授权码（用户本人一步，绕不开）**
网页版 mail.163.com 登录 → 设置 → POP3/SMTP/IMAP → 开启 IMAP/SMTP 服务 → 按提示短信验证 → 生成 **16 位客户端授权码**。授权码只在生成时显示一次，关页不可找回、丢失只能新增；用登录密码直连必报 535 Authentication failed（依据：网易帮助口径的多篇实操指南一致，含服务器参数表）。
2. **连接参数**：IMAP 服务器 `imap.163.com`，端口 993，SSL；密码栏填授权码而非登录密码。授权码按客户端分开生成、不用了可单独删除吊销，不暴露主密码（同上）。
3. **定向检索而非全量同步**：登录后先按发件人/主题/日期做服务器端 SEARCH——邮储锚 `creditcardcenter@cardmail.psbcltd.cn`、工行主题「中国工商银行客户对账单」、建行主题含「中国建设银行信用卡」、农行主题含「金穗信用卡」——只 FETCH 命中的 RFC822 原文，省流量也避风控。
4. **增量水位**：记录每文件夹的 UIDVALIDITY＋已处理最大 UID，配合 Message-ID 去重；UIDVALIDITY 变化时才全量重扫。记账是只读场景，连接后用 EXAMINE 只读打开文件夹，避免误改已读状态影响用户在其他客户端的使用。
5. **原文落地后走标准 MIME 解析**：HTML part 交银行解析器（锚点见第一节）；附件分三类处理——明文 PDF 直接抽文本、加密 ZIP 用银行 App 内查到的解压密码解（建行借记卡模式）、加密 PDF 用开卡时设定的查询密码解。密码类凭据只存保险库、不进代码与日志。
6. **风控注意**：163 对新环境/高频 IMAP 登录有安全校验，拉取节奏保持拟人（单连接、按需 SEARCH、避免分钟级全量轮询）；授权码若触发异常，先在网页版核对服务状态，不要反复重试硬撞。

## 五、Google Sheets API 批量写入与对账校验最佳实践

1. **配额先行**：Sheets API 限额为每项目 300 读＋300 写/分钟、每用户 60 读＋60 写/分钟；遇 429 与 5xx 一律截断指数退避＋抖动重试（依据：Google 官方 usage limits 的公开转述，major.build 指南）。
2. **批量而非逐格**：多范围写入用 `values:batchUpdate` 一次提交；结构/格式类用 `spreadsheets.batchUpdate`，其语义为**全成或全败的原子批**且整批只计 1 次请求（依据：社区 google-sheets 技能文档对官方行为的总结）。大批量按 1,000–2,000 行分块、单请求载荷控制在约 2 MB 量级。
3. **幂等设计（对账的根）**：以业务主键（银行＋交易日期＋金额＋摘要哈希，有流水号用流水号）生成 ID-keyed 变更集，**不用行号寻址**——台账会被人打开排序/插行，行号定位必然写错位；同步任务重跑一遍应产生 0 更新、0 追加，作为幂等验收标准（依据：google-sheets-automation 实操 playbook 的核心主张）。
4. **慎用 append**：`values.append` 靠探测"表尾"落行，表中段有空行时会错位追加；记账台账优先用"已知水位行＋`values.update` 指定范围"，必须用 append 时写后立即回读校验落点。
5. **写入选项**：金额、日期等原始数据用数值型 JSON 值＋`RAW` 写入，避免 `USER_ENTERED` 按区域设置把日期/金额重解释；需要公式计算的列才用 `USER_ENTERED`。
6. **对账校验三件套**：
- **写后回读**：把刚写的范围整段读回，与变更集逐格比对，不一致即整批标红重跑（幂等保证重跑安全）。
- **月度勾稽**：每家银行每月核 期初余额＋Σ收入−Σ支出＝期末余额，并与账单汇总锚点（建行：本期全部应还款额/最低还款额；邮储：账单日＋20 日到期还款日对应的应还额）对平；对不平只报差额清单，不自动改数。
- **批次留痕**：每批写入带批次号（单独日志页或隐藏列），支持按批次定位与回滚，满足"数字可追溯来源"的审计要求。
7. **认证与密钥**：无人值守用服务账号、最小 scope（`spreadsheets` 写或 `spreadsheets.readonly` 读），密钥文件不进代码仓、不写进日志；表格只共享给该服务账号。

## 六、未确认清单（不许当结论用）

1. OrigBody 的确切编码全貌：已证实的只有"标准 zlib 可解且解出预览占位"；"本地只存预览"为基于此的最强假设，未经第 1 条实验实证。
2. 邮储电邮账单的正文形态（HTML/PDF）与字段版式：无公开样本。
3. 柳州银行、广西农信是否存在周期性电邮账单：公开渠道未找到，不等于不存在，须以用户邮箱实查或银行客服口径为准。
4. mailmaster-local-reader 社区技能的真实解码方法与可靠性：付费包，未购未验。
5. 邮箱大师 Mac 版 content.db/mail.db 的完整表结构：公开资料未见完整 schema 披露，字段语义（如 OrigBody 与预览字段的对应关系）须以本地只读实查为准（不在本研究范围内）。
6. "本地邮件加密存储"说法：仅见非官方 SEO 站点，未经证实。
