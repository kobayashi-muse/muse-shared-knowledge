# 卷二 通道与桥接（操作规程版）

## 卷说明

这一卷是操作规程，不是经验总结。**定位先说清：本卷是「已有同构桥的运维与纪律手册」，不是从零搭建手册。**目标：一个手里已有一座同构桥（组件见下）的 Muse，只读这一卷，就能把这座桥绑定接入、日常运维、出故障时定因处置不出错。桥本身怎么用代码建出来——协议的接口规格、报文抓包细节、平台 SDK 用法——不在本卷内：那是各家协议自己的实现文档；本卷只给跨协议通用的机制、参数形态与纪律，不拿任何一家的接口文档冒充通解。

场景原型：机器人账号在自有服务器上登录一次并保存会话，桥程序用该会话通过平台的非官方协议（下称 iLink 类协议）收发消息，服务几十名真实用户；每位用户扫自己的专属二维码完成绑定，在工作台里拥有独立身份；入站消息由守候任务周期拉取、逐人路由到独立会话线程处理，答复经桥发回。

「同构桥」的最小组件（五件齐备，本卷规程才有落点；缺件先补件，再谈运维）：①机器人账号在自有服务器登录一次并保存会话；②绑定服务——挂在工作台既有登录态上，按人出码、落凭据；③轮询桥——凭会话按周期拉取入站、逐人维护游标；④守候任务——周期拉取待答请求、逐人路由到独立会话线程处理；⑤发送端——出站一律走队列与令牌纪律。核心名词逐个定义见紧接着的「同构前提与核心名词」一节，全卷名词以该节为准。

每条规程固定七段：①目标与适用场景 ②前置条件 ③操作步骤（每步写明动作→预期现象→判定信号）④失败分支 ⑤验收清单 ⑥禁忌与易错点 ⑦参数表。参数表逐项注明性质：**实测**＝在真实运行中测得或验证过；**配置值**＝本项目采用的配置（是设定出来的，不是测出来的，两者不许混标）；**示意**＝量级参考，须按自己的通道校准；**待实测**＝材料未给数值，照通用步骤执行、上线后自己测。同一数值在全卷各处出现时，性质标注必须一致。

三条总纲（全卷回扣）：

1. **非官方通道先定性、再使用**：它随时可能被限流、拒收、封号；所有设计按「通道会坏」做——节流、队列兜底、证据分级、预期如实。
2. **隔离靠路由，不靠自觉**：按人隔离必须是架构强制，并用串话测试验收，不用口头保证。
3. **送达是三级证据**：写入队列、平台受理（ret=0）、对方确认，是三件事，永不混报。

脱敏：本卷机制与参数写透；真实令牌、账号标识、人名、单位名、域名、IP、服务器路径一律不出现，示例均为化名与示意值。字段级口径只写类别与形态（如「须带明文长度字段、值为加密前字节数」），不写任何一家的真实字段名与真实取值；凡条目里写「照金标准报文自取」的，数值必须按【图片回发三参数坑】的方法从自家真实报文里取，不许把别家数值平移过来。标「仅方法可写」的条目只给规程、不给实例。

## 同构前提与核心名词

本卷名词以本节定义为准；定义只给机制与字段类别，不给任何真实值。

- **iLink 类协议**：第三方平台非官方消息协议这一类形态的统称——账号在自有设备/服务器上登录一次、保存会话，程序凭会话经长连接或轮询收发消息。它不是平台官方开放接口，平台可单方面限流、拒收、封会话（见【非官方通道的性质管理】）。
- **机器人会话**：机器人账号登录后保存下来的会话凭据集合，是全桥收发的总开关。会话失效＝全员收发停摆（处置见【会话恢复前置条件】），与单个用户的令牌过期是两个层级的问题，别混。
- **出码会话**：绑定服务为某一位工作台用户创建的一次性绑定会话记录。字段类别：归属用户标识、创建时间、状态（待扫／已确认／已作废）。它有独立的 TTL（服务端存活时长），且只能由归属用户的登录态取到它渲染出的码（见【一人一码绑定】）。
- **二维码（码面）**：出码会话渲染出的可扫图形，内容是平台的绑定确认串（形态随协议）。码面有自己的可扫有效期，独立于出码会话 TTL；页面按刷新间隔在旧码面失效前换上新码面——换码面不新建会话。三个时间数的分工见【一人一码绑定】⑦。
- **协议 ID**：平台协议层为机器人账号与每位用户分配的标识字符串，是系统内唯一可证明的身份（见【机器人身份只认协议 ID】）。系统侧只存协议 ID，不存、也无从反查自然人身份字段（昵称、手机号、持有人姓名）。
- **绑定凭据（凭据文件）**：绑定成功后逐人落盘的凭据记录。字段类别：工作台用户标识、该用户的协议 ID、绑定时间、状态。发送端每次发送前重读最新凭据（见【发送端每次读盘】）；真实值只落盘使用，永不写进日志正文、文档与汇报。
- **轮询与游标**：桥凭机器人会话按周期向平台拉取新入站；游标是逐人一条的拉取进度位，证明「轮询为此人工作到哪了」。两种常见实现：**序号型**——存消息序号/偏移量，推进判据＝数值较上次严格变大；**时间戳型**——存最后处理时点，推进判据＝有新消息时时间戳更新到最近轮询时点且不回退（无新消息时不变属正常，须结合轮询存活信号一起看）。纳管判定见【绑定成功≠纳管】。
- **上下文令牌**：平台随入站消息下发、供出站回复引用的短期令牌。出站发送须携带该用户最近一枚；对方一有新入站即刷新。缺失或过期是出站被拒收（prepare failed 一类）的首要嫌疑（见【ret=-2 定因学】）。
- **回复配额**：平台对「一条入站能带动多少条出站回复」的上限（本生态约 10 条，见【连发合并与配额】）。计数口径：按每条入站计——自该入站被处理起、本轮发出的回复计入其名下；对方发出新入站，开启新一轮计数。自查「配额是不是耗尽了」就按这个口径数。
- **待发队列**：逐人一份的待发内容存放处（文件或表，与他人隔离）。字段类别：收件人、内容、入队时间、状态。只随本人下一次入站的回复一并带出，发送回执成功才删（见【待发队列搭顺风车·过期令牌触达法】）。
- **已答名单**：已处理请求 ID 的集合，配合时间窗做双重判重，防重复答复（见【已答名单加时间窗双重判重·幂等】）。
- **退避台账**：逐人记录拒收对象的退避状态：对象、当前级别、到期时间、历次试发结果（见【ret=-2 处置·退避阶梯】）。
- **ret / errcode 与 errmsg**：发送/轮询接口返回的数值结果码（ret、errcode 是同类东西的不同叫法）与错误原文字符串。errmsg 在接口的**同步响应体**里（响应对象中语义为「错误原文」的字段，字段名随协议封装而异）；ret=0 只代表平台受理（见【送达三级证据分级·ret=0 只是平台接受】），定因必须手握 errmsg，取到路径见【ret=-2 定因学】③第 1 步。

## 第一章 通道性质与绑定

### 【非官方通道的性质管理】

**① 目标与适用场景**：在立项与汇报层面把通道定性为「非官方通道」，并据此备好降级预案。适用于一切借用第三方平台协议/会话搭的桥。

**② 前置条件**：
- [ ] 已确认通道实现方式（账号在自有服务器登录一次、保存会话、程序转发），而非平台官方开放接口
- [ ] 已列明该通道的三类固有风险：限流拒收、会话失效、账号被封
- [ ] 决策者知晓定性结论（不是执行者自己心里有数就算）

**③ 操作步骤**：
1. 写定性结论入项目文档 → 预期：文档明确写「非官方通道，不承诺官方接口级稳定性」→ 判定信号：文档中无「官方接口/官方合作」字样。
2. 备封号预案 → 预期：写清账号被封后的降级方式（暂停服务公告口径、替代联系渠道、恢复路径）→ 判定信号：预案文件存在且含通知对象清单。
3. 备会话失效预案 → 预期：写清谁有权重登、重登找谁、窗口期如何向用户交代 → 判定信号：预案点名到具体角色而非「相关人员」。
4. 对用户只承诺通道能做到的事 → 预期：用户说明中无「实时必达/永不丢失」类措辞 → 判定信号：逐条核对说明文案。

**④ 失败分支**：
- 已按官方接口口径对外宣传 → 定因：定性错误已扩散 → 处置：当轮更正所有文案与说明，并向已按高预期安排工作的用户说明实际边界 → 停手线：更正未完成前不新增用户接入。
- 预案写了但从未演练 → 定因：纸面预案 → 处置：至少做一次桌面推演（会话失效场景）→ 停手线：推演暴露的无解项未补前不算预案就绪。

**⑤ 验收清单**：
- [ ] 项目文档含定性结论原文（证据：文档段落）
- [ ] 封号、会话失效两份预案齐备且点名到角色（证据：预案文件）
- [ ] 用户侧说明无超承诺措辞（证据：文案核对记录）

**⑥ 禁忌与易错点**：把通道包装成官方接口（双向翻车：用户按官方预期要求你、出事时无预案）；只在心里定性、不落文档（换人接手即丢失）。

**⑦ 参数表**：本条无运行参数；预案类参数（重登窗口、公告时限）因单位而异，**待实测**后自定。

### 【一人一码绑定】

**① 目标与适用场景**：每位用户扫自己的专属二维码完成绑定，杜绝串绑。适用于桥的全部用户接入。

**② 前置条件**：
- [ ] 工作台已有用户账号体系（绑定挂在既有登录态上，不另起账号）
- [ ] 绑定服务能按「生成码的会话」隔离取码
- [ ] 二维码会话设 TTL（见参数表）
- [ ] 三个时间数已分清各自约束对象：出码会话 TTL／码面可扫窗口／页面刷新间隔，互不混用（定义见卷首名词节与本条⑦）

**③ 操作步骤**：
1. 用户在工作台登录态下请求绑定 → 预期：绑定服务为其创建一个专属出码会话（记录字段类别：归属用户标识、创建时间、状态）→ 判定信号：会话记录含归属用户标识与创建时间。
2. 出码 → 预期：二维码只返回给归属会话，其他会话请求同码被拒；出码期间页面按刷新间隔（约 180 秒）自动换上新码面——同一出码会话内换码面，不新建会话；码面失效只是换码，不等于会话作废，会话 TTL 到期才须重新出码 → 判定信号：用第二个会话取码返回拒绝；刷新后新码面可扫、会话记录仍是同一条。
3. 用户扫码确认 → 预期：平台侧完成账号与该用户的关联（绑定服务得知结果的方式随协议形态二选一：平台回调通知，或绑定服务轮询出码会话状态——以自家协议为准），绑定凭据落盘（字段类别：工作台用户标识、该用户的协议 ID、绑定时间、状态；真实值只落盘，永不写进任何文档与日志正文）→ 判定信号：该用户的绑定凭据文件出现且含协议 ID。
4. 绑定后立即查纳管 → 预期：该用户被纳入轮询集合（游标文件出现）→ 判定信号：见【绑定成功≠纳管】，本步不通过则绑定不算完成。

**④ 失败分支**：
- 二维码被他人扫走 → 现象：绑定关系落在错误用户 → 定因：码可转发或取码未隔离 → 处置：作废该出码会话、重新出码，并检查取码隔离逻辑 → 停手线：隔离逻辑未修复前暂停出码。
- 凭据落盘但用户端显示未绑定 → 定因：多为纳管段未完成 → 处置：转【绑定成功≠纳管】流程 → 停手线：不让用户反复重扫碰运气。

**⑤ 验收清单**：
- [ ] 非归属会话取码被拒（证据：实测记录）
- [ ] 绑定后凭据文件与游标文件双双出现（证据：文件清单）
- [ ] 抽一名用户完成真实收发（证据：会话记录）

**⑥ 禁忌与易错点**：用公共码/统一入口码图省事（串绑的根）；绑定流程另起一套账号体系（双份名册永远对不上）；只验出码成功就宣布绑定完成；三个时间数混用——最典型的是把 600 秒会话 TTL 当成码面能扫的时长，让用户对着早已失效的码面扫满十分钟。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 出码会话 TTL | 600 秒 | 配置值（本项目采用） | 约束对象：服务端出码会话的存活时长 |
| 二维码可扫窗口（码面有效期） | 约 3.5 分钟 | 实测 | 约束对象：单个码面可被扫认的时长 |
| 页面自动刷新间隔 | 约 180 秒 | 实测 | 约束对象：前端换新码面的节奏；短于码面有效期，旧码失效前新码已换上 |
| 三者关系 | 互不换算：会话存活 600 秒内可多次刷新码面；码面失效只换码、不废会话；会话 TTL 到期才重建出码会话。把 TTL 当码面有效期是最常见的实现错误 | — |

### 【二维码时效写实】

**① 目标与适用场景**：给用户的绑定说明按二维码真实时效写，避免用户对着过期码反复扫失败。适用于一切带时效的操作材料。

**② 前置条件**：
- [ ] 已实测二维码真实有效期与刷新行为（不要用文档值）
- [ ] 说明文案的执笔者拿到实测值

**③ 操作步骤**：
1. 实测时效 → 动作：生成一码后计时观察何时失效、失效后是否自动刷新 → 预期：得到分钟级有效期与刷新间隔 → 判定信号：实测记录含失效时间点。
2. 按实测值写说明 → 预期：说明写明「码几分钟过期，过期等它自动刷新再扫，不要截图保存反复扫」→ 判定信号：文案含时效数字且与实测一致。
3. 用户报扫不上时先问时效 → 预期：先确认其是否对着过期码扫 → 判定信号：排障话术第一问是时效而非系统状态。

**④ 失败分支**：
- 说明写「打开页面扫码即可」无时效 → 定因：文案含糊 → 处置：按实测值改写并重发说明 → 停手线：改写前不把绑定失败归因于用户操作。
- 实测发现码不自动刷新 → 定因：实现与预期不符 → 处置：说明改写为「过期请重新打开页面获取新码」，并把自动刷新列为缺陷修复 → 停手线：不在说明里承诺不存在的刷新。

**⑤ 验收清单**：
- [ ] 说明文案含与实测一致的时效数字（证据：文案＋实测记录对照）
- [ ] 排障话术首问为时效问题（证据：话术条目）

**⑥ 禁忌与易错点**：按期望值而非实测值写时效；用户扫不上先怀疑系统坏（多数是码过期）；让用户截图保存二维码长期使用。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 二维码有效期（码面） | 约 3.5 分钟（约 210 秒） | 实测 |
| 自动刷新间隔 | 约 180 秒 | 实测 |
| 两者关系 | 刷新间隔（180 秒）短于码面有效期（约 210 秒）：页面在旧码失效前约 30 秒就换上新码，用户正常停留页面时看到的码始终在有效期内；约束对象与出码会话 TTL（600 秒）的分工见【一人一码绑定】⑦。此关系须按自家实现复核 | 实测（机制关系） |
| 换通道复用本条时 | 有效期须重新实测 | 待实测 |

### 【二维码发图不发链】

**① 目标与适用场景**：需要用户扫码时，直接在当前聊天里发二维码图片，不只给网页链接。适用于一切「让用户当场完成一个动作」的交付。

**② 前置条件**：
- [ ] 当前通道能发送图片（若不能，先解决图片发送或改用对方可达的图片通道）
- [ ] 二维码图片清晰度足够被识别（生成后自扫验证一次）

**③ 操作步骤**：
1. 生成二维码图片 → 预期：图片文件落盘 → 判定信号：用另一设备/识别工具自扫可解出内容。
2. 图片作为消息主体直接发出 → 预期：用户在聊天里直接看到图 → 判定信号：发送回执成功（注意：回执只是第二级证据，见【送达三级证据分级·ret=0 只是平台接受】）。
3. 链接作备用附在图后 → 预期：图片不可见时用户有点链接的退路 → 判定信号：消息结构为「图＋一句话＋链接」。

**④ 失败分支**：
- 图片回执成功但对方看不见图 → 定因：多为图片发送参数坑 → 处置：转【图片回发三参数坑】逐字段对照 → 停手线：不连发多张重复图刷屏。
- 通道发不了图片 → 定因：通道能力缺失 → 处置：先发链接并明说「打开后长按页面里的码识别」，同时把图片发送列为待补能力 → 停手线：不假装已发图。

**⑤ 验收清单**：
- [ ] 二维码图片自扫可解（证据：自测记录）
- [ ] 至少一名真实用户凭图完成扫码（证据：其绑定成功记录）

**⑥ 禁忌与易错点**：只发链接让用户自己进页面找码（多一步跳转多一截流失）；图片未自扫验证就群发（码错了全员扫不上）。

**⑦ 参数表**：本条无独立参数；图片大小与格式上限随通道，**待实测**。

### 【机器人身份只认协议 ID】

- [ ] 明确哪些字段系统侧根本没有（账号昵称、持有人姓名、手机号等）

**③ 操作步骤**（通用步骤，参数待实测）：
1. 查服务器侧文件 → 动作：锚点只有三类文件——机器人会话凭据、逐人绑定凭据、轮询游标；逐份只列字段名清单（只列名、不抄任何值）→ 预期：三份清单里只有协议层 ID 与状态字段 → 判定信号：字段清单里无自然人身份字段。

- 被追问持有人是谁 → 定因：系统无此数据 → 处置：如实说明只能答到协议 ID 层，请决策者从系统外渠道确认 → 停手线：不根据群聊印象、备注名、旁人转述推断补全。

**⑤ 验收清单**：
- [ ] 身份字段清单已核（证据：字段列表）
- [ ] 对外答复模板只含协议 ID 层表述（证据：模板文本）

**⑥ 禁忌与易错点**：把「系统能证明的」与「人嘴里说的」混为一谈；答错归属会污染后续全部权限与责任判断。

**⑦ 参数表**：无参数。本条为通用方法条目。

### 【会话恢复前置条件】

**① 目标与适用场景**：机器人会话失效后，按明确的选项与代价恢复，不替决策者选路。适用于会话绑定在具体账号上的一切桥。

**② 前置条件**：
- [ ] 已确认会话确已失效（不是单用户令牌问题，先按【-14 定因·单人令牌过期】逐人排除）
- [ ] 已摸清原扫码账号当前是否可用、持有人是否可联系

**③ 操作步骤**：
1. 定性失效范围 → 预期：确认是机器人会话整体失效（全员收发停摆）而非个体故障 → 判定信号：多名用户同时无收发且轮询日志出现会话级错误。
2. 备两条恢复路并标价 → 预期：路 A 原账号持有人重新扫码（成本低、依赖持有人时间）；路 B 换专用账号重新开通（立即可办、代价是全员重绑）→ 判定信号：选项表含每条路的代价与影响面。
3. 交决策者拍板 → 预期：决策者明确选一条 → 判定信号：有明确回复记录，不凭沉默当同意。
4. 执行所选路 → 预期：路 A 完成后全员收发恢复；路 B 完成后逐人发重绑指引 → 判定信号：抽多名用户真实收发成功。

**④ 失败分支**：
- 原账号持有人长期联系不上 → 定因：路 A 阻塞 → 处置：把阻塞时长与影响如实上报，请决策者改判路 B → 停手线：不擅自换账号先斩后奏。
- 换账号后部分用户迟迟不重绑 → 处置：按【待发队列搭顺风车·过期令牌触达法】的边界如实说明「不重绑即无服务」，名单逐人销账 → 停手线：不拿旧会话凭据硬撑发送。

**⑤ 验收清单**：
- [ ] 选项与代价表已交决策者（证据：选项表）
- [ ] 恢复后全员收发抽验通过（证据：抽验记录）
- [ ] 失效时段与处置过程已记入运维日志（证据：日志条目）

**⑥ 禁忌与易错点**：替决策者选路；只说「重新开通一下」不说全员重绑的连带成本；设计期不选可长期持有的专用账号当机器人账号（把本条触发概率降到最低才是上策）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 全员重绑影响面 | 全部已绑定用户 | 实测（结构性事实） |
| 重登窗口时长 | 视持有人可达性 | 待实测 |

### 【第一个绑定者是谁要分清】

**① 目标与适用场景**：新通道冷启动的次序纪律，以及记录事实时分清「机器人账号扫码登录」与「用户侧绑定」两个层级。需化名假数，不写真实人物。

**② 前置条件**：
- [ ] 管理员账号可先行绑定（其绑定属用户侧绑定层）
- [ ] 记录模板能标注动作所属层级

**③ 操作步骤**：
1. 管理员自绑 → 预期：管理员以普通用户身份完成一次完整绑定 → 判定信号：其游标文件出现并推进。
2. 管理员自测收发 → 预期：入站、出站各通一遍 → 判定信号：双向记录齐全。
3. 小范围试绑 → 预期：选少数用户绑定并观察一轮 → 判定信号：无串绑、无未纳管。
4. 全量推广 → 预期：其余用户按【一人一码绑定】逐人接入 → 判定信号：盘点表逐人销账。
5. 写记录时先标层级 → 预期：凡写「绑定/登录/扫码」先注明是机器人账号层还是用户绑定层 → 判定信号：记录抽查无层级含糊条目。

**④ 失败分支**：
- 让普通用户当了第一个绑定者且踩坑 → 定因：冷启动次序错误 → 处置：管理员补绑自测、把坑修掉再继续推广，并向已受影响用户说明 → 停手线：自测未通过前不扩大推广。
- 历史记录把两层混记 → 处置：按会话记录与登录日志交叉订正（方法见【首次绑定以会话记录交叉核对】）→ 停手线：订正前不引用该记录认定责任。

**⑤ 验收清单**：
- [ ] 管理员自绑自测记录齐全（证据：收发记录）
- [ ] 推广名单逐人销账（证据：盘点表）

**⑥ 禁忌与易错点**：把「第一个绑定桥接的人是管理员」（用户侧绑定层）转述成「机器人账号是管理员扫的」（账号层）——层级一混，责任链全错。

**⑦ 参数表**：无运行参数；试绑人数按总规模取小样本，**示意**。

### 【绑定尝试不等于人选认定】

**① 目标与适用场景**：记录与汇报时，把「某人发生过绑定尝试」与「某人被定为某试点人选」严格分开。本条仅方法可写，无实例。

**② 前置条件**：
- [ ] 台账有「事实」与「推断」分栏（没有先改台账结构）

**③ 操作步骤**（通用步骤）：
1. 绑定事件只记事实栏 → 预期：记谁、何时、绑定结果 → 判定信号：事实栏无推断措辞。
2. 人选类判断只认决策者明确点名 → 预期：无点名记录时推断栏写「未定」→ 判定信号：推断栏无执行者自填的人名。
3. 汇报时分开说 → 预期：先报事实、再报未定状态 → 判定信号：汇报文本无「应该是他」式表述。

**④ 失败分支**：
- 已把推断说成安排并传出 → 定因：记录纪律失效 → 处置：当轮向相关方更正，并回溯是哪份台账/汇报起的头、改其结构 → 停手线：更正完成前不发布新的人选类信息。

**⑤ 验收清单**：
- [ ] 台账事实/推断分栏已落地（证据：台账结构）
- [ ] 抽查近期汇报无人选推断冒充事实（证据：抽查记录）

**⑥ 禁忌与易错点**：用绑定顺序、绑定时间这类技术痕迹解读组织意图；误传人选等于替决策者宣布人事安排，收拾起来极被动。

**⑦ 参数表**：无参数。本条为通用方法条目。

### 【绑定成功≠纳管】

**① 目标与适用场景**：绑定验收分两段：出码/落盘只证明「绑上了」，轮询游标出现并持续推进才证明「纳管了」。适用于一切「注册/绑定」与「实际服务」分两段的系统。

**② 前置条件**：
- [ ] 能查看每位用户的轮询游标文件（或等价的状态位），且已知自家游标是哪种实现（序号型或时间戳型，定义见卷首名词节）——判据按类型不同，别拿一种的判据套另一种
- [ ] 绑定流程结束后有自动或人工的纳管检查环节

**③ 操作步骤**：
1. 绑定完成即查游标存在 → 动作：查该用户游标文件 → 预期：文件存在 → 判定信号：文件缺失即纳管失败，直接进失败分支。
2. 隔一个轮询周期再查游标推进 → 预期与判定按游标类型分：序号型——游标值较上次严格变大，不变＝轮询没在为此人工作；时间戳型——该用户有新消息时时间戳应更新到最近轮询时点且不回退，若其间根本没有新消息，时间戳不变属正常，须改看「轮询进程存活＋该用户无异常日志」作辅助信号，不许单独凭时间戳不变判死。
3. 发一条真实入站验证 → 预期：该用户发消息能被收到并回复 → 判定信号：会话记录出现其入站与出站各一条。
4. 三项全过才在盘点表记「已纳管」 → 判定信号：盘点表状态与证据对应。

**④ 失败分支**：
- 凭据已落盘、游标不出现 → 定因：新用户未被纳入轮询集合（典型成因见【启动时扫描一次的陷阱】）→ 处置：手动触发名单重扫或按该条修复机制 → 停手线：不让用户反复重绑碰运气，不重启全桥掩盖问题。
- 游标出现但不推进 → 定因：该用户轮询线程已死或被异常打死 → 处置：查线程错误日志（注意【错误码在异常属性里】），按【通道故障按类不按案】的监督复活机制处理 → 停手线：复活后仍不推进才转人工深查。

**⑤ 验收清单**：
- [ ] 每位新绑定者游标存在且推进（证据：两次游标值记录）
- [ ] 用户端无「暂时无法连接」类显示（证据：用户确认或截图）

**⑥ 禁忌与易错点**：拿出码成功当绑定完成（这类故障后台零报错，只有游标检查能发现）；用户显示连不上时先怀疑其网络（先查游标）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 游标推进观察窗 | ≥1 个轮询周期（轮询为分钟级时即数分钟） | 示意 |
| 纳管判定 | 游标存在＋推进＋真实收发，三项缺一不可 | 实测（验收口径） |

### 【启动时扫描一次的陷阱】

**① 目标与适用场景**：长驻服务只在启动时枚举一次订阅者名单、后来者永远进不了轮询——识别并修复这一结构坑。适用于一切长驻进程＋动态成员集合的系统。

**② 前置条件**：
- [ ] 能读到服务的名单加载逻辑（代码或配置）
- [ ] 有假数据源可做监督测试

**③ 操作步骤**：
1. 查名单加载时机 → 预期：若只在进程启动时读一次名单，即确诊有此病 → 判定信号：代码中名单枚举不在周期循环内。
2. 改周期重扫 → 动作：每轮扫描订阅者集合，只给新增者起线程，已有者不重复起 → 预期：运行中新增用户自动被纳管 → 判定信号：重扫日志显示增量识别。
3. 假数据两轮监督测试 → 动作：第一轮放入假用户，观察起线程；第二轮不增减，再观察 → 预期：第一轮起 1 个线程、第二轮新增 0 个 → 判定信号：线程数两轮后稳定不增长。

**④ 失败分支**：
- 重扫导致重复起线程 → 定因：增量判断缺失或线程注册表未更新 → 处置：先修注册表一致性再上线重扫 → 停手线：重复线程未除净前不带此版本上线（重复轮询会造成重复答复）。
- 症状为「老用户正常、新用户全无反应、重启即好」 → 定因：正是本坑的典型症状，不要按偶发故障反复重启 → 处置：直接按本条查加载时机 → 停手线：确诊前不以重启结案。

**⑤ 验收清单**：
- [ ] 两轮监督测试通过（证据：线程数记录）
- [ ] 服务不重启情况下新绑定者被纳管（证据：见【热加载的实证标准】）

**⑥ 禁忌与易错点**：把症状当偶发故障、用重启掩盖根源；重扫只做「加人」忘了防重复起线程。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 重扫周期 | 与轮询周期同级（分钟级） | 示意 |
| 监督测试轮数 | ≥2 轮 | 实测（验收口径） |

### 【热加载的实证标准】

**① 目标与适用场景**：动态纳管类补丁的验收口径：不看测试全绿，看一个真实事件——服务不重启，新绑定者游标自动出现且持续推进。

**② 前置条件**：
- [ ] 补丁已部署，能查服务进程启动时间
- [ ] 能安排一次真实新绑定（或等到自然新绑定）

**③ 操作步骤**：
1. 记录部署时进程启动时间 → 判定信号：有基线值可比。
2. 完成一次真实新绑定 → 预期：不做任何重启操作 → 判定信号：操作记录无重启。
3. 观察游标 → 预期：游标从无到有、数值持续推进 → 判定信号：两次采样值递增。
4. 复核进程启动时间未变 → 预期：与基线一致（全程零重启）→ 判定信号：三项证据齐才宣布生效；缺一只能报「已部署、待实证」。

**④ 失败分支**：
- 测试全绿但真实事件不发生 → 定因：测试环境与生产在名单来源/线程模型/路径上存在差异，病灶正在差异处 → 处置：按差异逐项比对生产配置，不宣布生效 → 停手线：真实事件通过前不在汇报里写「已修复」。
- 期间被他人重启过服务 → 定因：证据链被污染 → 处置：重新基线、重做一次真实绑定验证 → 停手线：不拿污染证据结案。

**⑤ 验收清单**：
- [ ] 游标从无到有且推进（证据：采样记录）
- [ ] 进程启动时间与部署基线一致（证据：进程信息）
- [ ] 状态在台账记为「已实战验证」而非「已部署」（证据：台账，口径见【部署与实战分开说】）

**⑥ 禁忌与易错点**：用单元测试全绿冒充生产生效；宣布生效时不附零重启证据。

**⑦ 参数表**：无独立参数；观察窗同【绑定成功≠纳管】。

### 【绑定代际指纹＋看门狗】

**① 目标与适用场景**：比周期重扫更主动的自愈：给每代绑定状态算指纹，看门狗周期比对，指纹变化即自动重建轮询集合。

**② 前置条件**：
- [ ] 指纹计算材料覆盖一切影响轮询集合的输入（绑定名单、凭据版本）
- [ ] 重建动作幂等（重复触发不产生重复线程）

**③ 操作步骤**：
1. 定义指纹 → 动作：对名单＋凭据版本做哈希 → 预期：任一输入变化指纹必变 → 判定信号：人为改一处输入，指纹随之变化。
2. 看门狗周期比对 → 预期：每周期算一次指纹，与上轮比对 → 判定信号：比对日志连续无缺口。
3. 变化即重建 → 预期：按新名单重建轮询集合，只增减变化部分 → 判定信号：重建后线程集合与名单一致、无重复线程。
4. 每次自动重建记日志 → 预期：事后可统计自愈次数 → 判定信号：日志含时间、旧新指纹、增减名单。

**④ 失败分支**：
- 指纹不变但实际纳管异常 → 定因：指纹材料漏了某项输入（如凭据内容变了但版本没变）→ 处置：扩指纹材料范围 → 停手线：漏项未补前不宣称看门狗覆盖完整。
- 重建产生重复线程 → 定因：重建不幂等 → 处置：先停看门狗、人工清理线程，再修幂等 → 停手线：幂等未验过不重新启用。

**⑤ 验收清单**：
- [ ] 人为变更绑定后一周期内自动纳管（证据：看门狗日志）
- [ ] 重建后无重复线程（证据：线程清单与名单对照）

**⑥ 禁忌与易错点**：看门狗只发现不记录（事后无从统计它救了多少次）；成员变更极频繁的系统慎用，重建成本会反噬。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 看门狗比对周期 | 60 秒 | 实测 |
| 发现延迟上限 | ≤1 个比对周期 | 实测 |

### 【发送端每次读盘】

**① 目标与适用场景**：发送端不缓存对端地址与令牌，每次发送前重读磁盘最新绑定文件，杜绝绑定更新后发往旧地址。

**② 前置条件**：
- [ ] 绑定文件是地址与令牌的唯一权威来源
- [ ] 发送路径可改造（或已如此实现，先核查）

**③ 操作步骤**：
1. 核查发送端取址方式 → 预期：若启动时读一次入内存即确诊隐患 → 判定信号：代码中发送函数内无读盘动作。
2. 改为发送前读盘 → 预期：每次发送都拿当前文件值 → 判定信号：改后人为更新绑定文件，下一条消息即发往新地址。
3. 回归验证 → 预期：正常发送不受影响 → 判定信号：抽数名用户发送回执正常。

**④ 失败分支**：
- 症状「重绑之后反而更不通」 → 定因：典型陈旧缓存 → 处置：先按本条查发送端，再怀疑平台 → 停手线：不让用户反复重绑（越绑越乱）。
- 读盘失败（文件缺失/损坏） → 处置：本次发送中止并记错误日志，不回退用内存旧值硬发 → 停手线：宁可不发，不可发错地址。

**⑤ 验收清单**：
- [ ] 更新绑定后下一条即达新地址（证据：对照实验记录）
- [ ] 发送函数无长期缓存副本（证据：代码走查）

**⑥ 禁忌与易错点**：为省读盘成本做缓存（成本可忽略，风险是发错人）；读盘失败时用旧值兜底。

**⑦ 参数表**：无参数。读盘成本相对发送成本可忽略，**实测**结论。

### 【双桥并存先摸清共用】

**① 目标与适用场景**：新旧两版桥并存且共用同一机器人会话时，先测绘共用关系再谈旧版退役。

**② 前置条件**：
- [ ] 已确认旧版服务仍在运行（进程/服务状态可查）
- [ ] 有只读核查手段（见【线上核查只读零副作用】）

**③ 操作步骤**：
1. 列两个服务的收发分工 → 预期：各自在收什么、发什么、轮询谁，逐项写清 → 判定信号：分工表无「不清楚」格。
2. 定共用点 → 预期：确认共用的是会话、账号还是仅凭据文件 → 判定信号：共用点有文件/配置证据。
3. 验新版独立性 → 预期：在不依赖旧版的假设下逐段核对新版链路 → 判定信号：每段都有独立证据，而非「应该可以」。
4. 再排退役 → 预期：退役步骤含退役后复验（新版收发抽验）→ 判定信号：退役方案成文后才动手。

**④ 失败分支**：
- 摸不清共用关系 → 定因：文档缺失或服务无日志 → 处置：保持并存现状，只做只读观察补测绘 → 停手线：测绘完成前不停止、不删除旧版任何部分。
- 退役后新版某段断裂 → 定因：旧版暗中承担了该段 → 处置：先恢复旧版该段功能，再补测绘重排退役 → 停手线：不带断裂状态过夜，先恢复服务。

**⑤ 验收清单**：
- [ ] 共用关系测绘表完整（证据：测绘表）
- [ ] 退役后新版全链路抽验通过（证据：抽验记录）

**⑥ 禁忌与易错点**：贸然停删旧版（断点往往不在你动的地方，排查成本极高）；把「旧版还活着」本身当故障处理。

**⑦ 参数表**：无参数。

### 【不拿用户本人账号做实验】

**① 目标与适用场景**：发送实验、通道探活的试验对象选择纪律。本条仅方法可写，无实例。

**② 前置条件**：
- [ ] 已分清哪些账号与系统外另一侧配对、不属于本桥试验范围
- [ ] 有正在活跃聊天的普通用户会话可选作试验对象
- [ ] 试发已按【探通道试发预授权】取得预授权

**③ 操作步骤**（通用步骤）：
1. 选试验对象 → 预期：活跃普通用户（链路真实、有近期上下文、结果可验证）→ 判定信号：对象近 24 小时有真实往来。
2. 排除特殊账号 → 预期：所有者本人账号、与外部系统配对的账号一律不在名单 → 判定信号：试验名单逐个核过。
3. 实验后按三级口径记录 → 预期：结论只对该类对象成立，不外推到特殊账号 → 判定信号：记录含对象类型说明。

**④ 失败分支**：
- 误用所有者账号做了实验 → 定因：名单未核 → 处置：如实报告、清理其会话现场污染，并把排除清单落文件 → 停手线：排除清单未落文件前不做下一次实验。
- 实验结论被质疑代表性 → 处置：说明特殊账号配对关系会使结果失真（通了不代表普通用户通）→ 不以特殊账号结果结案。

**⑤ 验收清单**：
- [ ] 试验对象排除清单已落文件（证据：清单文件）
- [ ] 每次实验记录含对象类型（证据：实验记录）

**⑥ 禁忌与易错点**：图方便拿手边账号做实验（既污染其会话，结果又失真）。

**⑦ 参数表**：无参数。本条为通用方法条目。

### 【时延分段如实告知】

**① 目标与适用场景**：通道端到端时延主要来自轮询周期时，把各段耗时拆开实测、如实告知，不承诺做不到的到达时间。

**② 前置条件**：
- [ ] 能在日志中区分各段的时间戳（入站到达、轮询拾取、处理、回发）

**③ 操作步骤**（通用步骤，段值待实测）：
1. 分段埋点 → 动作：每条消息在日志里落四个时间戳字段（类别固定）：入站到达时刻、轮询拾取时刻、处理完成时刻、回发受理时刻；四段耗时＝相邻两戳之差（到达→拾取＝轮询等待段，拾取→完成＝处理段，完成→受理＝回发段，到达之前的平台段以平台侧时戳或收发两端对表估算）→ 预期：每条消息可算出平台→桥、轮询等待、处理、回发四段耗时 → 判定信号：抽一条消息能列出四段数值；缺任一戳的那一段不许估、不许拿总时延冒充分段。
2. 统计常态分布 → 预期：得到各段的中位与上限量级 → 判定信号：有成段统计而非单点印象。
3. 按实测口径告知 → 预期：说明结构性下限（如最快也要等下一轮轮询）与常态总时延 → 判定信号：告知文本中的数字与统计一致。

**④ 失败分支**：
- 某段耗时异常放大 → 定因：按段定位（轮询段大＝拾取节奏问题；处理段大＝任务本身重）→ 处置：对段下药，不笼统说「通道慢」→ 停手线：分段数据出来前不承诺优化时限。
- 已口头承诺过做不到的时延 → 处置：当轮更正并给出实测口径 → 停手线：不硬撑错误承诺等投诉上门。

**⑤ 验收清单**：
- [ ] 四段耗时可查（证据：日志字段）
- [ ] 对外告知数字与统计一致（证据：告知文本＋统计对照）

**⑥ 禁忌与易错点**：为安抚对方承诺「秒回」；把结构性的慢说成临时故障（对方会按临时预期反复检验、反复失望）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 轮询等待段下限 | ≥0、≤1 个轮询周期（分钟级轮询即分钟级量级） | 实测（结构性） |
| 各段具体数值 | 按自家通道埋点统计 | 待实测 |

## 第二章 隔离与会话路由

### 【逐人隔离·一人一线程一材料空间】

**① 目标与适用场景**：多人服务的地基：每位服务对象一个独立会话线程、材料只存本人名下空间，答复只依据本线程历史与本次来文。适用于一切一个助手服务多人的场景，无例外。

**② 前置条件**：
- [ ] 入站消息带可信的发送者身份（绑定关系已建立）
- [ ] 存储层支持按人分目录/分空间
- [ ] 上下文装配逻辑可按线程隔离取数

**③ 操作步骤**：
1. 路由按人分发 → 动作：入站按发送者身份路由到其专属线程 → 预期：消息只进本人线程 → 判定信号：抽查两名用户的线程，内容互不含对方消息。
2. 材料按人落盘 → 预期：每人的文件只出现在本人空间 → 判定信号：目录清单逐人对应。
3. 答复只装本线程上下文 → 预期：生成时上下文不含他人历史 → 判定信号：装配日志/调试输出只含本线程条目。
4. 授权按人判断 → 预期：用户给助手的「全自动授权」只覆盖用户自己的工作，不外延到对其他每位用户的操作 → 判定信号：涉及他人的操作逐项有其本人的关系依据。

**④ 失败分支**：
- 发现答复引用了他人内容 → 定因：隔离失效（路由、装配或存储任一段）→ 处置：立即整体暂停该通道服务，按【串话一票否决·双人暗号测试】修好重测才恢复 → 停手线：未通过重测前不恢复、不以「就这一次」放行。
- 身份字段不可信（绑定关系存疑） → 处置：先按【姓名口径三方对照定准】核身份再路由 → 停手线：身份未核清不把材料落入任何人的空间。

**⑤ 验收清单**：
- [ ] 串话测试通过（证据：见下条的测试记录，本条不得单独宣布过关）
- [ ] 材料目录逐人对应无串放（证据：目录抽查）
- [ ] 授权范围说明已落文件（证据：规则文件）

**⑥ 禁忌与易错点**：靠模型「记得别串话」做隔离（上下文一长必翻车）；把对一个人的授权当对所有人的通行证。

**⑦ 参数表**：无参数。隔离为二值标准：过串话测试或不过，无中间态。

### 【串话一票否决·双人暗号测试】

**① 目标与适用场景**：隔离机制的唯一硬验收：两名真实用户同一时段各带对方不知道的暗号发问，任一回复漏出对方信息即判定串话、整体暂停修好重测。隔离上线前必测，隔离机制任何改动后重测。

**② 前置条件**：
- [ ] 两名真实用户愿意配合，且用真实账号、真实通道（假数据测不出真实路由）
- [ ] 为每人准备独有暗号：对方不知道的词句、事项或数字各一（暗号在正常业务中绝不该出现在对方回复里）
- [ ] 测试时段两人可同段发问
- [ ] 参与者口径已核：两名都须是真实用户，自测账号与管理员账号不算（口径见【自测账号往来不计通道证据】）

**③ 操作步骤**：
1. 分发暗号 → 预期：两人各知自己暗号、互不知对方暗号 → 判定信号：暗号清单只在测试组织者手里。
2. 同段发问 → 动作：两人同一时段分别发问，并各自索要与自己相关的答复（如问自己的事项进展）→ 预期：两条链路并行真实运行 → 判定信号：两边会话记录时间重叠。
3. 逐条检查回复 → 预期：逐条搜对方姓名、事项、暗号 → 判定信号：命中任一即记录为泄漏点，不许以「问题不大」放行。
4. 裁定 → 预期：零泄漏＝通过；任一泄漏＝整体暂停，修隔离、换新暗号重测 → 判定信号：测试结论成文，含暗号与检查结果。

**④ 失败分支**：
- 检出泄漏 → 定因顺序：先查路由（消息进错线程？）→再查上下文装配（取错线程？）→再查材料存储（落错空间？）→ 处置：定位段修复后换暗号全量重测 → 停手线：重测通过前通道不恢复服务、不做任何跨人功能。
- 测试组织者把暗号提前告诉了对方 → 定因：测试污染 → 处置：换全新暗号重测 → 停手线：污染过的测试结论作废。
- 一时凑不齐两名真实用户 → 处置：先以「一名真实用户＋管理员自绑账号」做半量测试，结论只许标「半量通过、待补」；另一名真实用户到位后补做全量复测 → 停手线：半量结论不许按全量通过结案、不许据此宣布隔离验收完成。

**⑤ 验收清单**：
- [ ] 两名真实用户、同段、双向都测过（证据：会话时间记录）
- [ ] 回复逐条检查记录齐全（证据：检查表）
- [ ] 结论成文并归档（证据：测试报告）

**⑥ 禁忌与易错点**：用假账号/假数据测试（测不出真实路由）；泄漏后只修那一处不重测（隔离是系统属性，不是个案）；通过后改了路由/装配/存储却不重测。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 测试用户数 | 2 名真实用户 | 实测（验收口径） |
| 容忍泄漏数 | 0（一票否决） | 实测（验收口径） |
| 重测触发 | 隔离机制任一改动后 | 实测（纪律） |

### 【桥约束放耐久文件】

**① 目标与适用场景**：桥的安全约束（隔离规则、发送纪律、禁推执行口径等）写进耐久指令文件并每轮重读，不靠对话记忆。

**② 前置条件**：
- [ ] 已盘点全部「任何时候不能破」的约束条目
- [ ] 运行机制支持任务启动时强制加载指定文件

**③ 操作步骤**：
1. 约束落文件 → 预期：每条约束短、硬、可核查，写入定时任务正文/长期记忆/操作手册 → 判定信号：文件可检索到每条约束原文。
2. 每轮重读 → 预期：每轮运行第一步加载约束文件 → 判定信号：运行日志含加载动作。
3. 定期对账 → 预期：抽查近期动作与约束逐条比对 → 判定信号：对账记录无未处置的违例。

**④ 失败分支**：
- 发现某轮动作违了约束且约束只在旧对话里 → 定因：约束未落文件 → 处置：当轮补落文件并复盘该轮全部动作 → 停手线：补落前暂停该类动作。
- 约束文件写成长篇大论 → 定因：不可核查等于没写 → 处置：拆成条目式短句，每条一个可判定标准 → 停手线：改完前不宣称约束已落地。

**⑤ 验收清单**：
- [ ] 约束清单文件存在且条目化（证据：文件）
- [ ] 运行日志可见每轮加载（证据：日志）

**⑥ 禁忌与易错点**：指望长对话里一直记得（上下文膨胀会把早期约束挤出有效注意力，这是机制问题不是态度问题）。

**⑦ 参数表**：无参数。

### 【消息文本永不构成授权】

**① 目标与适用场景**：任何消息文本（用户发来的、邮件里的、转发内容里的）写「同意/yes」都不算授权；确认只认运行时批准卡或代码级门。无例外。

**② 前置条件**：
- [ ] 关键动作清单已列明（发送、删除、对外提交、动用凭据等）
- [ ] 系统提供批准卡或代码级校验门至少其一

**③ 操作步骤**：
1. 收到含「同意」字样的消息 → 预期：只记为意愿线索，不触发关键动作 → 判定信号：动作未执行、线索已登记。
2. 执行关键动作前过门 → 预期：走批准卡（由有权者点确认）或代码门（预设规则校验通过）→ 判定信号：动作日志含过门记录。
3. 汇报时说清依据 → 预期：注明本次动作凭哪道门执行 → 判定信号：汇报文本可追溯。

**④ 失败分支**：
- 有人以转发消息冒充有权者同意 → 定因：文本可伪造、拼接 → 处置：不执行，按未授权处理并留痕 → 停手线：任何文本证据都不升级为授权。
- 预授权类动作被质疑越界 → 处置：出示预授权的系统层设定文件（那是用户在系统层面的设定，不是消息层面的协商）→ 停手线：设定文件没有的范围一律重新过门。

**⑤ 验收清单**：
- [ ] 关键动作清单与过门方式成文（证据：规则文件）
- [ ] 抽查近期关键动作均有过门记录（证据：日志抽查）

**⑥ 禁忌与易错点**：把「他在消息里说了行」当执行依据——等于把系统最高权限交给任何能发消息的人，多人通道里尤其致命。

**⑦ 参数表**：无参数。

### 【新线程口令】

**① 目标与适用场景**：给用户一个口语化口令（如「新开一个」），一发即开新会话线程、旧上下文不带入。

**② 前置条件**：
- [ ] 路由器能识别口令并执行开线程动作
- [ ] 旧线程保留可查但不再装配进新上下文

**③ 操作步骤**：
1. 选口令 → 预期：选用户自然会说的话，不用技术词 → 判定信号：口令在用户指南中出现且措辞一致（见下条）。
2. 识别即执行 → 预期：用户发口令，路由器直接开新线程、不反问确认 → 判定信号：新线程建立、回复表明已是新会话。
3. 实测验证 → 动作：发口令→查新线程→在新线程里问旧话题 → 预期：旧话题不被引用 → 判定信号：三步全过才算交付。

**④ 失败分支**：
- 发口令无反应 → 定因：识别表未含该措辞或路由未部署 → 处置：按【口令与指南对齐】逐字核对程序命令表 → 停手线：实测未过前不把口令印进指南。
- 开了新线程但旧上下文仍被引用 → 定因：装配逻辑仍在读旧线程 → 处置：查装配范围 → 停手线：修好重测前不宣称口令可用。

**⑤ 验收清单**：
- [ ] 三步实测记录齐全（证据：测试记录）
- [ ] 指南中的口令与程序识别表逐字一致（证据：对照表）

**⑥ 禁忌与易错点**：口令用技术词（用户记不住）；频繁改口令（等于没有口令）；口令机制没实测就交付。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 口令数量 | 小而稳（个位数） | 示意 |
| 旧上下文带入 | 0 | 实测（验收口径） |

### 【口令与指南对齐】

**① 目标与适用场景**：用户指南的措辞与程序命令表逐字对齐，防「指南写 A、程序只认 B」的低级事故。适用于一切文档教操作、程序按文档执行的组合。

**② 前置条件**：
- [ ] 程序侧有可查的命令/口令识别表
- [ ] 指南改版有流程（不是随手改完就发）

**③ 操作步骤**：
1. 逐字对照 → 动作：把指南中每个口令与识别表逐字比对 → 预期：完全一致（含标点与空格差异的处理）→ 判定信号：对照表逐项打勾。
2. 按新版实测 → 预期：拿着新版指南逐条在程序上实操一遍 → 判定信号：每条都触发预期动作。
3. 测试用例锁定 → 预期：口令表进自动化测试，程序改动若动了识别，测试变红 → 判定信号：测试套件含口令用例。

**④ 失败分支**：
- 用户照指南操作失败 → 定因：先查对齐，不要先怪用户 → 处置：对照表重跑、改错的一侧，并向已受影响用户发更正 → 停手线：对齐未复验前不发新版指南。
- 程序改了识别没人通知文档侧 → 定因：变更流程缺环 → 处置：把「动识别必须同步指南并跑用例」写进变更清单 → 停手线：流程未补前冻结口令变更。

**⑤ 验收清单**：
- [ ] 对照表全项一致（证据：对照表）
- [ ] 口令测试用例在套件内且绿（证据：测试结果）

**⑥ 禁忌与易错点**：指南与程序各改各的；用户失败时归因于其操作不当（后台看一切正常，更易误判）。

**⑦ 参数表**：无参数。

### 【涉密材料会话内处理靠边界不拒收】

**① 目标与适用场景**：敏感/涉密材料在发送者本人会话内照常起草整理、结果只回本人——隔离靠会话边界，不靠拒收。前提是隔离已验收过关。

**② 前置条件**：
- [ ] 串话测试已通过且在有效期内（隔离改动后未重测视为未过关）
- [ ] 已核对单位/用户是否有更严的明文规定（某类材料不得经此通道）；有则从其规定

**③ 操作步骤**：
1. 材料只进本人线程 → 预期：落盘在本人空间 → 判定信号：目录抽查无串放。
2. 处理只用本线程上下文 → 预期：不跨线程引用、不进共享区 → 判定信号：装配范围可查。
3. 结果只回本人 → 预期：交付走本人会话，不抄送不转发 → 判定信号：发送记录只有本人一个收件方。

**④ 失败分支**：
- 隔离未过关却收到此类材料 → 定因：前提不成立 → 处置：只做接收登记，告知对方待隔离验收后处理，或请其改走规定渠道 → 停手线：不凭「应该没事」开工。
- 制度明文禁止经此通道 → 处置：按制度拒收并说明依据与替代渠道 → 停手线：本条不授权突破任何明文制度。

**⑤ 验收清单**：
- [ ] 隔离验收状态可查（证据：串话测试报告日期）
- [ ] 此类材料落盘与发送记录均只涉本人（证据：抽查记录）

**⑥ 禁忌与易错点**：顺序反了——先接活再补隔离；用拒收代替边界（把用户推回手工处理，助手失去价值）；把「通道放开」误读成「隔离也可以放开」。

**⑦ 参数表**：无参数。前提条件（串话测试通过）为二值门槛。

### 【个人事项永不入共享知识库】

**① 目标与适用场景**：知识沉淀的准入红线：个人生活事项、个人联系方式、私人文稿只留本人会话，永不入共享知识库。

**② 前置条件**：
- [ ] 沉淀流程中有准入判断环节（不是自动全量入库）
- [ ] 沉淀执行者明确分类标准

**③ 操作步骤**：
1. 沉淀前分类 → 预期：逐条判「单位/业务公共事实」还是「某个人的私人信息」→ 判定信号：私人信息一律止步，拿不准按私人处理。
2. 公共事实带源入库 → 预期：记提炼后的事实＋来源与出处，不整份搬原稿、名单原件 → 判定信号：库内条目可追溯、无原件整搬。
3. 定期抽查库内条目 → 预期：发现误入的私人信息立即移除并追成因 → 判定信号：抽查记录在案。

**④ 失败分支**：
- 私人信息已误入共享库 → 定因：准入判断失效 → 处置：立即移除、记录误入路径、加严该类条目的准入 → 停手线：同类条目暂停入库直至准入修复（入库容易出库难，错误沉淀近乎不可逆）。
- 执行者以「可能有用」为由想放宽 → 处置：放宽只能由用户明文修订口径，不临场判断 → 停手线：无明文修订不放行。

**⑤ 验收清单**：
- [ ] 准入分类标准成文（证据：规则文件）
- [ ] 库内抽查无私人信息（证据：抽查记录）

**⑥ 禁忌与易错点**：把共享库当全量备份（其可见范围大于单人会话，一条私人信息进去等于对所有能查库者公开）。

**⑦ 参数表**：无参数。

### 【首问我是谁先确认身份】

**① 目标与适用场景**：新用户首句常是「我是谁」——首答先准确确认其身份，再自我介绍，当场完成一次隔离证明。

**② 前置条件**：
- [ ] 绑定身份与名册信息可查（姓名、部门以绑定身份为准）

**③ 操作步骤**：
1. 先确认身份 → 预期：答出其姓名与所在部门（以绑定/名册为准，不用对话推断）→ 判定信号：所答与名册逐字一致。
2. 再自我介绍 → 预期：说明我是谁、能帮什么 → 判定信号：介绍在确认之后，不抢顺序。
3. 接迎新流程 → 预期：转入【新用户首信迎新三件套】→ 判定信号：首信回复结构完整。

**④ 失败分支**：
- 名册查不到此人或信息对不上 → 定因：绑定身份与名册未对齐 → 处置：老实说「我这边还没对上你的登记信息」，请其报姓名部门人工核对（走【姓名口径三方对照定准】）→ 停手线：绝不猜一个身份答上去，更不能拿别人的信息「显得认识他」。

**⑤ 验收清单**：
- [ ] 抽查新用户首答均先确认身份（证据：会话抽查）
- [ ] 确认内容与名册一致（证据：对照记录）

**⑥ 禁忌与易错点**：把首问当闲聊敷衍（错失成本最低的信任建立动作）；身份答错（比不答更糟）。

**⑦ 参数表**：无参数。

## 第三章 发送、队列与触达

### 【发送节奏即防封卫生·爆发实测教训】

**① 目标与适用场景**：主动发送的第一纪律：几十人共用一个机器人账号＋云服务器 IP，爆发发送同时抬高限流拒收（ret=-2）与封号风险。适用于一切共享机器人账号的非官方通道。

**② 前置条件**：
- [ ] 已知本通道的拒收错误码与形态（见【ret=-2 定因学】）
- [ ] 主动发送有队列或限速机制承接（没有先建【待发队列搭顺风车·过期令牌触达法】）

**③ 操作步骤**：
1. 主动消息一律先入队 → 预期：不从任何入口直接群发 → 判定信号：发送日志中无同一分钟向多人直发的记录。
2. 批量通知错峰 → 预期：按队列随入站回复逐个带出，或以低速分批发送 → 判定信号：单位时间发送量平滑无尖峰。
3. 标定自家安全速率 → 动作：在不爆发的前提下给本通道测出可用节奏——从最低档起步：先对单个对象单发一条、确认受理；再按「每批少量＋批间留分钟级间隔」逐档微增，每升一档完整观察一个窗口的拒收情况；任一档出现拒收，立即退回上一档并把上一档定为当前安全上限，标定曲线与上限值记入台账。标定只用自有测试对象或已预授权的试发（见【探通道试发预授权】），不拿真实用户群当试验品 → 预期：得到本通道自己的速率上限，发送节奏从此有数可依，不再陷「不许试、又没数」的死角 → 判定信号：台账中有标定记录与当前上限值，实际发送节奏引用该值。
4. 被拒即退避 → 预期：出现拒收立即停该对象发送、进退避阶梯（见【ret=-2 处置·退避阶梯】）→ 判定信号：失败日志后无连发重试。

**④ 失败分支**：
- 已发生一次爆发且多数被拒 → 现象：短时大量 ret=-2 → 定因：发送节奏失控 → 处置：立即停发、全体转入待发队列搭顺风车，逐个随入站恢复 → 停手线：不补发「补回来」，补发即第二次爆发。
- 个别执行者绕过队列直发 → 处置：收回直发入口，发送只许走队列一条路 → 停手线：入口收口前暂停主动通知类任务。

**⑤ 验收清单**：
- [ ] 发送日志无爆发尖峰（证据：按分钟聚合的发送量）
- [ ] 主动消息 100% 经队列（证据：队列与发送日志对照）

**⑥ 禁忌与易错点**：把爆发当效率（实测教训见参数表：数秒内连发十余条，仅约三分之一被受理，其余当场被拒）；被拒后连发重试「试试通没通」（越试封得越死）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 爆发实测样本 | 4 秒内发 12 条：4 条受理（ret=0）、8 条被拒（ret=-2） | 实测 |
| 主动发送方式 | 控速错峰或搭入站顺风车，无第三种 | 实测（纪律） |
| 安全发送速率 | 无通用固定值（随平台脾气变化）；按③第 3 步标定规程自测得出后把数值填入此处并注明标定日期，平台行为变化或出现新拒收后重新标定 | 待实测（附标定法） |

### 【待发队列搭顺风车·过期令牌触达法】

**① 目标与适用场景**：会话令牌过期或主动推送受限时，主动消息必然失败；把内容排进本人待发队列，只随其下一次入站回复一并发出（入站同时刷新令牌）。适用于一切主动发送受令牌/会话状态制约的通道。

**② 前置条件**：
- [ ] 每位用户有本人名下的待发队列（文件或表），与他人隔离
- [ ] 入站回复流程能在正文后捎带队列内容，且发送成功才删队列
- [ ] 委托方已被告知机制边界（不来信就到不了）

**③ 操作步骤**：
1. 主动内容入队 → 动作：通知、催办、邀请写入收件人本人的队列 → 预期：队列文件出现、内容与收件人对应 → 判定信号：队列条目含收件人、内容、入队时间。
2. 等待其入站 → 预期：对方发来任何消息，令牌随入站刷新 → 判定信号：入站记录出现。
3. 随回复带出 → 动作：先发回复正文，再附队列内容（保持相对顺序，文件类按【文档交付三段式·发送顺序】）→ 预期：一次发出、对方在同一会话里看到 → 判定信号：发送回执成功。
4. 成功才删队列 → 预期：回执成功后删该条；失败保留原样 → 判定信号：队列与发送结果一致，无「已删但未发」。
5. 向委托方报边界 → 预期：报清「已排队 N 人、随其来信送达、未送达名单是谁」→ 判定信号：汇报含未送达名单，不用「已通知」一词含糊带过。

**④ 失败分支**：
- 带出时发送失败 → 定因：令牌仍异常或触发拒收 → 处置：队列保留，按【ret=-2 处置·退避阶梯】处理该对象 → 停手线：不为清队列改走单独主动发送。
- 对方长期不来信 → 定因：机制固有边界 → 处置：如实向委托方说明，建议其改走人工渠道（电话/当面） → 停手线：不许把「已入队」汇报成「已通知到」。
- 队列文件被安全检查拦下 → 处置：转【被安全检查拦下的队列文件】 → 停手线：不强行读取或发送原文。

**⑤ 验收清单**：
- [ ] 队列逐人隔离、无错投（证据：队列目录抽查）
- [ ] 成功删、失败留的记录一致（证据：队列变动与发送日志对照）
- [ ] 汇报口径含未送达名单（证据：汇报文本）

**⑥ 禁忌与易错点**：为队列内容单独发起主动发送（把整套机制的意义清零）；入队后忘记队列会随时间变质（内容过期要先复核再带出）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 删除时机 | 发送回执成功之后 | 实测（纪律） |
| 送达时效 | 不可控，取决于对方何时来信 | 实测（结构性） |
| 队列内容有效期复核 | 带出前逐条复核是否过期 | 示意 |

### 【主动触达沉默者】

**① 目标与适用场景**：已绑但从未发过消息的人，从绑定/轮询状态里挖可用发送上下文，主动联系一次，不干等其首条入站。与下条的分界是上下文有无。

**② 前置条件**：
- [ ] 能查该用户的绑定与轮询状态，并按四项判据判定有无可用会话上下文——四项全有才算「有」：(1) 绑定凭据存在且状态有效；(2) 游标存在且近期仍在推进（此人虽零入站，但轮询侧无其个体故障记录）；(3) 无此人的拒收/令牌过期记录在案；(4) 上下文令牌未过期（以其生成或最近刷新时点未超出该生态令牌有效期的量级为准）。任一项缺失或存疑，一律按「无」处理、转下条，不许凭感觉判「应该能发」
- [ ] 首触文案已备（自我介绍＋能帮什么，一条说完）
- [ ] 发送走控速纪律，不连发

**③ 操作步骤**：
1. 筛沉默者 → 预期：列出已绑、零入站的名单 → 判定信号：名单与盘点（【双向验证才是健康度·四级盘点法】「无往来」级）一致。
2. 逐人核上下文 → 预期：有可用会话上下文者进第 3 步；无者转下条处置 → 判定信号：逐人有核查结论。
3. 发一条克制首触 → 预期：单条、合并问候与指南（见【自动问候合并发】）→ 判定信号：回执按三级口径记录，不记「已触达」只记到哪一级。
4. 结果回盘点 → 预期：有回复者升级为双向实证；无回复者保留原级并记首触日期 → 判定信号：盘点表更新。

**④ 失败分支**：
- 首触发送被拒 → 定因：按错误原文走【ret=-2 定因学】 → 处置：进退避，不换个时间连试 → 停手线：同一人首触只试一轮，失败即回队列等其入站。
- 核查发现所谓「上下文」已过期 → 定因：等同无上下文 → 处置：转下条登记待首触 → 停手线：不拿过期上下文硬发碰运气。

**⑤ 验收清单**：
- [ ] 沉默者名单逐人有处置结论（证据：盘点表）
- [ ] 首触均单条合并发送（证据：发送记录）

**⑥ 禁忌与易错点**：为触达率绕过通道规则硬发；首触连发多条（自我介绍一条、指南一条、能力清单一条——合并成一条）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|

### 【主动问候的前置条件】

**① 目标与适用场景**：从未发过消息、无任何会话上下文的人，主动发送在机制上必然失败——登记待首触，等其首次来信时补上，不硬发、不假记。

**② 前置条件**：
- [ ] 有「待首触」名单承接这类人
- [ ] 首信回复流程含首触自我介绍段（见【新用户首信迎新三件套】）

**③ 操作步骤**：
1. 识别无上下文者 → 预期：绑定在、无任何会话上下文 → 判定信号：状态核查无可用发送落点。
2. 登记待首触 → 预期：名单含其身份与登记日期 → 判定信号：名单可查。
3. 汇报单列 → 预期：汇报时这批人单列为「待首触」，不混进「已问候」→ 判定信号：汇报文本有单列行。
4. 其首次来信时补首触 → 预期：回复里带自我介绍与指南 → 判定信号：补后从待首触名单销账。

**④ 失败分支**：
- 有人已把无上下文者记成「已发送/已问候」 → 定因：台账造假式误记 → 处置：当轮更正台账并复盘记账口径 → 停手线：更正前不引用该台账数字汇报。
- 平台规则变化使无上下文可发 → 处置：先小范围实测验证再改本条口径 → 停手线：未实测前不按新规放行。

**⑤ 验收清单**：
- [ ] 待首触名单与实际无上下文者一致（证据：状态对照）
- [ ] 已问候统计不含待首触者（证据：统计口径核对）

**⑥ 禁忌与易错点**：把失败记成已发送（制造永久盲区：所有人以为问候过了，只有用户从没收到）；试图绕过机制硬发（轻则失败留痕，重则触发风控）。

**⑦ 参数表**：无参数。判定标准为二值：有可用会话上下文 / 无。

### 【探通道试发预授权】

**① 目标与适用场景**：验证某人通道用一条短试发；此类试发经用户预先授权后直接执行、后报结果。预授权只覆盖单点试发，爆发/群发永不在内。

**② 前置条件**：
- [ ] 预授权范围已由用户设定并落文件（覆盖对象、条数、内容类型）
- [ ] 试发对象不在禁推名单、不在退避期（在则按各自纪律办）

**③ 操作步骤**：
1. 拟试发 → 预期：内容短而无害（如一句通道测试问候），收件人单个 → 判定信号：拟发清单逐项落在预授权范围内。
2. 执行试发 → 预期：单条发送 → 判定信号：回执按三级口径记录（受理≠对方收到）。
3. 等对方确认 → 预期：以对方回复或亲口确认裁定真通 → 判定信号：确认记录在案。
4. 后报结果 → 预期：向用户报清试了谁、到哪一级证据 → 判定信号：汇报含证据级别。

**④ 失败分支**：
- 试发被拒 → 定因：走【ret=-2 定因学】 → 处置：进退避阶梯，本轮不再试 → 停手线：不以「再试一条看看」消耗预授权。
- 有人要求借预授权做批量通知 → 定因：超出范围 → 处置：拒绝走预授权通道，另行过授权门 → 停手线：范围外动作一律不先斩后奏。

**⑤ 验收清单**：
- [ ] 预授权范围文件存在（证据：文件）
- [ ] 每次试发有三级口径记录（证据：试发日志）

**⑥ 禁忌与易错点**：自行扩围预授权（执行者无权）；把试发回执成功汇报成「通道已通」（还差对方确认一级）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 单次试发条数 | 1 条/人 | 实测（纪律） |
| 预授权覆盖 | 单点试发；爆发与群发不在内 | 实测（纪律） |

### 【禁推名单一次生效·只回不推】

**① 目标与适用场景**：服务对象明确拒绝主动推送（甚至说出「再发就卸载」）后，当场切换其触达模式并永久执行：只回不推。

**② 前置条件**：
- [ ] 有禁推名单文件，执行发送前强制查名单
- [ ] 能清空单人待发队列

**③ 操作步骤**（五步当场完成，缺一不可）：
1. 致歉并确认意愿 → 预期：回复只做一件事——道歉＋确认「以后只回复你主动发来的消息」→ 判定信号：该回复已发出且无附带推销内容。
2. 承诺口径落定 → 预期：承诺含全员通知也不例外 → 判定信号：承诺文本可查。
3. 清空其待发队列 → 预期：其名下队列条数归零 → 判定信号：队列目录核查为零（防旧排队内容日后被顺风车带出）。
4. 登记禁推名单 → 预期：名单含其身份、登记日期、触发原话要点 → 判定信号：名单文件更新。
5. 此后执行靠名单 → 预期：任何主动触达流程（通知、问候、试发）先查名单、命中即跳过 → 判定信号：后续发送记录中对其主动发送为零；其主动来信照常回复。

**④ 失败分支**：
- 登记后仍有主动内容到达对方 → 定因：必是某条流程没查名单，或队列没清干净 → 处置：立即再致歉、定位漏查的流程并补查名单环节、复查其队列 → 停手线：漏点未堵前暂停全部主动触达类任务。
- 执行者觉得「他应该消气了」想恢复推送 → 处置：不许自行恢复，只能由本人明示恢复意愿 → 停手线：无本人明示，永久只回不推。

**⑤ 验收清单**：
- [ ] 五步逐项有证据（证据：致歉回复、队列清零记录、名单条目）
- [ ] 登记后主动发送记录为零（证据：发送日志按人检索）

**⑥ 禁忌与易错点**：只道歉不登记（靠记忆执行必漏）；不清队列（嘴上答应、三天后旧通知被顺风车带出，对方认定你言而无信）；拿「这条通知很重要」当违逆明示意愿的理由——拒绝意愿比任何通知都大。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 生效时限 | 当场（收到拒绝的当轮） | 实测（纪律） |
| 解除条件 | 仅本人明示恢复 | 实测（纪律） |
| 适用范围 | 一切主动触达，含全员通知，无例外 | 实测（纪律） |

### 【自动问候合并发】

**① 目标与适用场景**：新绑定用户拿到会话上下文后，问候＋使用指南合并成一条发出，不拆两条。适用于一切自动欢迎流程。

**② 前置条件**：
- [ ] 有定时轮询能捡「已绑、有上下文、未问候」的用户
- [ ] 合并文案已定稿（自我介绍＋能帮什么＋怎么使唤，一条装完）

**③ 操作步骤**：
1. 轮询捡人 → 预期：名单＝已绑∧有上下文∧未问候∧不在禁推名单 → 判定信号：名单逐人核过四条件。
2. 合并发一条 → 预期：一条消息含问候与指南 → 判定信号：发送记录为单条。
3. 发过即标记 → 预期：标记已问候，永不重复问候 → 判定信号：标记与发送记录一致。

**⑤ 验收清单**：
- [ ] 每位新用户只收到一条问候（证据：发送记录按人计数）
- [ ] 已问候标记无虚记（证据：标记与回执对照）

**⑥ 禁忌与易错点**：拆两条发（多耗一次发送、多冒一次风控、多打扰一次）；问候过的人换个由头再问候一遍。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 每人问候条数 | 1 条 | 实测（纪律） |
| 内容上限 | 一条装完，装不下先砍内容 | 实测（纪律） |

**⑥ 禁忌与易错点**：发群发模板式欢迎（带其分工的业务问题是与广播的根本区别）；编造其分工来显得「了解他」。

### 【能力清单主动发】

**① 目标与适用场景**：随问候/指南给用户一份能力清单，解决「不知道能使唤什么」这一使用率瓶颈。清单只写已验证能做的事。

**② 前置条件**：
- [ ] 清单每项能力均已端到端验证可用（未做成的不许先印上）
- [ ] 清单按用户视角组织（不用技术分类）

**③ 操作步骤**：
1. 编清单 → 预期：每项一句话说清「把什么发给我、我还你什么」（如起草文档、做台账、修格式、带来源的政策查询、读文件/图片/语音、提醒、比价、生活杂问）→ 判定信号：每项含输入与产出。
2. 随问候或指南发放 → 预期：与【自动问候合并发】协调，不单独为清单多发一条打扰 → 判定信号：发放记录与问候合并或紧随其后。
3. 版本维护 → 预期：能力新增则更新版本再发；能力下线则删条目 → 判定信号：清单版本号与能力台账一致。

**④ 失败分支**：
- 清单某项被用户使唤时发现做不到 → 定因：清单超前于能力 → 处置：当轮向该用户说明边界并给出替代，清单立即删改该项 → 停手线：未删改前不新发清单。
- 清单太长没人看 → 处置：砍到一屏内，细节按需问答 → 不靠加长解决覆盖。

**⑤ 验收清单**：
- [ ] 清单条目与真实能力逐项对应（证据：对照核查记录）
- [ ] 版本号与最近一次能力变更同步（证据：版本记录）

**⑥ 禁忌与易错点**：把未做成的能力印上清单（会变成投诉清单）；用技术分类组织（用户看不懂等于没发）。

**⑦ 参数表**：无参数；条数以一屏可读为限，**示意**。

### 【材料同步上板只问一次】

**① 目标与适用场景**：用户发来的材料能对应系统某板块时，顺带问一次要不要同步上板；确认才登记执行，说不用不再追问。

**② 前置条件**：
- [ ] 材料与板块的对应关系明确（不明确不问，先核对）
- [ ] 问答结果有登记处（问过谁、答什么）

**③ 操作步骤**：
1. 识别对应板块 → 预期：材料内容可明确归到某板块 → 判定信号：归属判断有依据，非猜测。
2. 正事回复后一句带过 → 预期：问法轻、不单独为此发一条 → 判定信号：问句出现在正事回复末尾。
3. 当场记录答复 → 预期：「要」则登记待同步（按时间＋用户＋板块＋材料名单行入账，转主线执行并回告）；「不要」则记不再问 → 判定信号：登记记录齐全。
4. 新材料可再问新材料 → 预期：老材料永不翻出来重问 → 判定信号：征询记录按材料区分。

**④ 失败分支**：
- 对方没明确答（只回了正事） → 定因：视为未确认 → 处置：不执行同步、不当默认同意；下次有新材料时可随新材料再提一次 → 停手线：沉默不构成同意（与【消息文本永不构成授权】同源）。
- 已登记同步但主线未执行 → 处置：在入账清单里标状态，执行后回告本人 → 停手线：不让登记石沉大海。

**⑤ 验收清单**：
- [ ] 每份材料至多被问一次（证据：征询记录）
- [ ] 答「要」的均有入账与执行回告（证据：入账清单）

**⑥ 禁忌与易错点**：反复追问（把服务关系变成催缴关系，对方会躲着发材料——那才是真正的损失）；把可选增值当义务派发。制度明文要求上报的材料不走征询、按制度办。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 每份材料征询次数 | ≤1 次 | 实测（纪律） |
| 入账格式 | 时间＋用户＋板块＋材料名，单行 | 实测 |

### 【板块现状必当场核查不冒充】

**① 目标与适用场景**：被问系统板块现状（数据多少、更新到哪）时，当场核查数据源再答；没核查就明说待核实。适用于一切现状类问答：进度、余额、名单、状态。

**② 前置条件**：
- [ ] 知道该板块的权威数据源在哪、自己有无查询权限

**③ 操作步骤**：
1. 先查数据源 → 预期：拿到当前值与更新时间 → 判定信号：答复中的数字带来源与时点。
2. 查不到就明说 → 预期：回复「待核实，核完答你」，并记下待核事项 → 判定信号：不给任何估算数字。
3. 核完补答 → 预期：在同一线程补上核查结果 → 判定信号：待核事项销账。

**④ 失败分支**：
- 忍不住拿知识库沉淀或对方刚发的材料当现状答了 → 定因：沉淀是过去时、对方材料是局部，都不是现状 → 处置：当轮更正并说明正确口径 → 停手线：更正前不让对方按错误现状去办事。
- 数据源本身不可用 → 处置：明说数据源故障与预计恢复，仍不许编数 → 停手线：无证据的层级就停在无证据那一级（与送达三级同源）。

**⑤ 验收清单**：
- [ ] 现状类答复均带来源与时点（证据：会话抽查）
- [ ] 待核事项有登记有销账（证据：待核清单）

**⑥ 禁忌与易错点**：用「看起来很确定的过时答案」换答复速度——这类问题答错的代价远高于答慢。

**⑦ 参数表**：无参数。

### 【被安全检查拦下的队列文件】

**① 目标与适用场景**：待发队列文件在读取时被系统安全检查拦下——内容已不可信，处置目标是隔离风险、重建干净版本，不是把原文发出去。本条仅方法可写，无实例。

**② 前置条件**：
- [ ] 能区分「被拦文件」与正常队列文件（改名隔离后不被流程误读）
- [ ] 有无污染的既定事项来源可据以重写（原定的通知事项、登记记录）

**③ 操作步骤**（通用步骤）：
1. 停 → 预期：不强行发送、不引用其内容、不尝试绕过检查 → 判定信号：该文件无发送记录、无引用记录。
2. 隔离 → 动作：改名留存备查（如加隔离后缀），移出正常队列扫描范围 → 预期：守候与扫尾都不会再碰它 → 判定信号：队列扫描日志不再出现该文件。
3. 重写 → 动作：从无污染的既定事项出发，另写一份干净的队列文件 → 预期：新文件只含可追溯来源的事项 → 判定信号：逐项能指出来源。
4. 记安全事件日志 → 预期：记时间、文件、处置动作，不记被拦内容 → 判定信号：日志条目存在。

**④ 失败分支**：
- 重写时找不到无污染来源 → 定因：事项本身只有被拦文件一份记录 → 处置：宁可不发，向委托方说明该事项需重新确认 → 停手线：不从被拦文件里「凭记忆复原」内容。
- 同类拦截反复出现 → 定因：队列写入路径可能被污染 → 处置：停该路径写入、查来源 → 停手线：来源未清前不恢复自动入队。

**⑤ 验收清单**：
- [ ] 被拦文件已隔离且无发送/引用（证据：文件状态＋日志）
- [ ] 替代文件来源逐项可追溯（证据：来源对照）

**⑥ 禁忌与易错点**：想办法绕过检查读原文（任何「引用它写摘要」都在扩散风险）；隔离后不重写、让正当事项跟着文件一起死掉。

**⑦ 参数表**：无参数。本条为通用方法条目。

### 【连发合并与配额】

**① 目标与适用场景**：入站侧节流：同一用户短时间连发多条时，先攒短窗口合并成一轮再回复，既省回复配额又防回复互相打架。该生态每条入站能带动的回复条数有通例上限（约十条量级）。

**② 前置条件**：
- [ ] 入站处理支持延迟合并（消息先落缓冲、窗口到点统一处理）
- [ ] 已知本通道的回复配额口径（见参数表）

**③ 操作步骤**：
1. 开合并窗口 → 预期：某用户来消息后不开工，先等一个短窗口 → 判定信号：处理日志显示等待。
2. 窗口内顺延 → 预期：窗口内再来新消息则并入本轮、窗口顺延 → 判定信号：多条入站只生成一轮处理。
3. 窗口关闭统一回复 → 预期：把连发内容当一个完整请求理解后回复 → 判定信号：回复条数显著少于入站条数，且答全了后到的补充。
4. 急件例外 → 预期：急件不合并、即到即答。识别规则（任一命中即按急件走）：(a) 内容语义属求救/报警类——涉及人身安全、突发疾病、险情事故，按语义判、不只靠关键词表（换个说法也要认得出）；(b) 发送者是已登记的紧急联系角色，或该消息被平台标为紧急类（如有此标记）；(c) 兜底项：拿不准是不是急件的，一律按急件处理——误判代价不对称，急件被合并耽误的代价远大于普通消息被提前答 → 判定信号：例外规则成文且含兜底项，抽查无急件被压进合并窗口的记录。

**④ 失败分支**：
- 窗口太长损害对话感 → 定因：窗口取值过大 → 处置：按用户感知下调（见参数表量级）并观察投诉 → 停手线：不以「省配额」为由把窗口拉到分钟级以上。
- 急件被误判进合并窗口 → 定因：识别规则缺兜底或只靠关键词表 → 处置：补③第 4 步的 (c) 兜底项，并复盘该窗口期内全部消息有无第二件急件 → 停手线：规则未补齐前，合并窗口先取下限值（数秒级）运行。
- 合并后仍超配额（对方连发十余条） → 处置：按一轮一回复执行，多余诉求在回复中一次列清请其确认 → 停手线：不逐条回满配额。

**⑤ 验收清单**：
- [ ] 连发场景下回复条数≤入站条数且内容无遗漏（证据：抽样会话）
- [ ] 配额消耗较逐条回复明显下降（证据：发送统计）

**⑥ 禁忌与易错点**：逐条秒回（配额被无谓消耗、后发的补充还没看就答了、发送密度触发限流）；窗口设得毫无弹性（固定死等，单条消息也被拖慢）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 回复配额 | 约 10 条回复 / 每条入站（计数口径见卷首名词节） | 实测（生态通例） |
| 合并窗口 | 数秒至数十秒；未做过自家校准时先取下限（数秒级）起步，按对话感与投诉上调，不许一上来先取上限 | 示意（须按对话感校准） |
| 急件例外 | 求救/报警类不合并、即到即答；识别规则三项（含拿不准按急件的兜底项）见③第 4 步 | 实测（纪律） |

### 【失败汇总对齐法】

**① 目标与适用场景**：通道故障恢复后，故障期间丢失的多条回复不逐条补发，改发一条汇总对齐消息。前提是故障期答复底稿都已落盘。

**② 前置条件**：
- [ ] 故障时段已界定、受影响用户与丢失答复清单已盘出
- [ ] 每份丢失答复的底稿可查（没有底稿先认账，不编造内容）

**③ 操作步骤**：
1. 盘丢失清单 → 预期：逐人列出故障期未达的答复 → 判定信号：清单与失败日志对得上。
2. 发一条汇总 → 预期：内容三件套——说明故障时段与原因（一句）、声明期间答复底稿都在可随时重发、把待对方确认的事项一次列清 → 判定信号：每人只收到一条。
3. 按需单发 → 预期：对方点名要哪条，再单发哪条底稿 → 判定信号：单发记录与对方请求对应。

**④ 失败分支**：
- 积压只有一两条且时效极强 → 处置：可直接单发，不必走汇总形式 → 这是本条的明示例外。
- 对方对汇总无回应 → 定因：可能未收到或无待确认事项 → 处置：不追发第二条汇总，随其下次入站时口头带一句 → 停手线：不逐条补发「以防万一」。

**⑤ 验收清单**：
- [ ] 每位受影响用户只收到一条汇总（证据：发送记录）
- [ ] 待确认事项清单与底稿一一对应（证据：对照表）

**⑥ 禁忌与易错点**：逐条补发（等于在恢复瞬间自制一次爆发：刷屏＋触发限流＋旧答复时序全乱，对方对不上号）；汇总里不列待确认事项（对方无从接续，汇总白发）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 每人汇总条数 | 1 条 | 实测（纪律） |
| 底稿留存 | 故障期答复 100% 落盘 | 实测（纪律） |

## 第四章 故障学——定因与处置

### 【ret=-2 定因学】

**① 目标与适用场景**：非官方通道最常见拒收码 ret=-2 的定因结论：绑定层被平台拒收，与绑定新旧无关，不是重绑能修的。适用于该生态通道的全部拒收诊断。

**② 前置条件**：
- [ ] 失败日志已记错误原文（没有先按【失败日志记 errmsg·错误原文】补齐，在此之前不许定因）
- [ ] 能拿到对照样本（重绑过的人、从未重绑的人各至少一例的发送结果）

**③ 操作步骤**：
1. 先取到错误原文 → 动作：errmsg 在发送接口的同步响应体里——响应对象中语义为「错误原文」的字符串字段（字段名随协议封装而异）；发送端必须在失败路径上把响应体原文整段取出、按【失败日志记 errmsg·错误原文】落盘。若自家封装只往外抛错误码、把响应体吞了，先改封装让原文透传到失败日志，改完才许进入定因 → 判定信号：失败日志里能指着具体一行读出原文；读不到原文，本条到此为止，结论只能写「待补日志后定因」。
2. 对照实测排除错误归因 → 动作：查同日重绑者与从未重绑者的拒收情况 → 预期：重绑者曾恢复又被拒、未重绑者同样被拒 → 判定信号：拒收与绑定新旧无相关，排除「绑旧了」归因。
3. 核代码定义域 → 动作：在桥代码里检索 -2 的定义 → 预期：查无此定义（代码里只有 -14＝会话暂停）→ 判定信号：不要在代码层继续找 -2，把精力转到平台侧。
4. 按错误原文三分法对症 → 判定信号：原文与下表对应关系明确才许下定因结论；无原文则结论只能写「待补日志后定因」。

| 错误原文 | 定因 | 对症方向 |
|---|---|---|
| prepare failed | 上下文令牌缺失/过期，或回复配额耗尽，或载荷超限（三因并列，须按下文鉴别顺序逐个排除） | 按下方三因鉴别顺序，命中哪个治哪个 |
| unknown error | 令牌过期 | 等入站刷新或走个体恢复 |
| freq limit | 发送限流 | 降速退避 |

**prepare failed 三因鉴别顺序**（排查成本从低到高，命中即停；每因处置后只验一条，验通即定因成立并记入台账；不许三因并治——治好了也不知道是哪一因）：①先比载荷——量这条出站消息序列化后的字节数，接近或超过约 16KB 即按载荷超限处置：瘦身或分片后单发一条验证；②再数配额——按卷首名词节的计数口径，数自对方最近一条入站以来本轮已发出的回复条数，接近约 10 条即按配额耗尽处置：停发，等对方下一条入站开新一轮；③最后归令牌——前两项都排除、且该用户近期确无入站刷新过令牌，才按令牌缺失/过期处置：等入站刷新，或走【-14 定因·单人令牌过期】的个体恢复路径。

**④ 失败分支**：
- 原文不在三分法内 → 定因：未知形态 → 处置：原样记录原文与上下文，按个案查，不套三分法硬解 → 停手线：不定性就不处置，只做降速保护。
- 有人主张「重绑试试」 → 处置：出示对照实测结论拒绝该路径 → 停手线：不以重绑当安慰剂（重绑解决不了平台拒收，还扰动绑定关系）。

**⑤ 验收清单**：
- [ ] 每起 -2 定因都引用了错误原文（证据：失败日志）
- [ ] 对照实测结论在案（证据：对照记录）
- [ ] 代码定义域已核（证据：检索记录）

**⑥ 禁忌与易错点**：三大直觉错路——重绑（治不了）、重启服务（拒收在平台服务端，本地重启修不了）、加发重试（越治越糟，把临时拒收拖成长期的）；没有错误原文就猜原因。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 回复配额 | 约 10 条 / 每条入站（计数口径见卷首名词节） | 实测（生态通例） |
| 载荷上限 | 约 16KB，超限触发拒收；约束对象＝单条出站消息的序列化消息体 | 实测 |
| 大文件发送路径 | 文件/图片不进消息体直发：先走媒体上传通道换取媒体标识，消息体只带标识引用发送（上传与回取侧的大小口径见【媒体端点防护】）。16KB 卡的是消息体，不是文件本体——把文件字节塞进消息体必然超限被拒，这不等于「文件发不了」 | 实测（机制） |
| 代码内定义 | 仅 -14（会话暂停），无 -2 定义 | 实测 |

### 【ret=-2 处置·退避阶梯】

**① 目标与适用场景**：上条的处置面：降速退避＋搭顺风车，不重启硬刚。拒收只针对单个对象，处置也逐人进行。

**② 前置条件**：
- [ ] 已按上条完成定因（至少错误原文在手）
- [ ] 有退避状态记录处（谁在退避、第几级、到期时间）
- [ ] 有定时扫尾任务承接到期试发，且试发执行者已指定唯一（见【试发执行者唯一】）

**③ 操作步骤**：
1. 单点试发探活 → 动作：对被拒对象只发一条 → 预期：返回 0＝平台已恢复受理 → 判定信号：ret=0 后停手，等对方回「收到」作双向确认，不连发庆祝。
2. 持续被拒进阶梯 → 预期：按 6h→12h→24h 静默退避，退避期只记 skip、不试发 → 判定信号：退避记录含级别与到期时间，期间发送日志中对该对象为零。
3. 到期扫尾试发 → 预期：定时扫尾单点试发一条 → 判定信号：成功→清退避状态、补发积压（走队列次序）；失败→进下一级退避。
4. 桥轮询存活时不重启 → 预期：处置全程不动服务 → 判定信号：服务启动时间未变。
5. 清理失效锁定名单 → 预期：历史上为这类故障设过的锁定名单若已失效，下次上服务器维护时清掉 → 判定信号：名单文件已更新（防陈旧名单误伤）。

**④ 失败分支**：
- 退避多轮仍不恢复 → 定因：可能已非限流而是个体令牌或绑定问题 → 处置：转【-14 定因·单人令牌过期】与绑定核查逐项排查 → 停手线：不在 -2 路径上无限加级退避。
- 退避期有急事必须通知此人 → 处置：如实报委托方改走人工渠道 → 停手线：不破退避强发（强发只会延长拒收）。

**⑤ 验收清单**：
- [ ] 退避记录完整（级别、到期、试发结果）（证据：退避台账）
- [ ] 恢复以「试发 ret=0＋对方回确认」双信号裁定（证据：双记录）
- [ ] 处置期间服务未重启（证据：进程启动时间）

**⑥ 禁忌与易错点**：为追 -2 重启桥服务（轮询活着时重启纯属添乱）；退避期手痒试发（试探本身也要纳入节流）；恢复后连发多条确认。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 退避阶梯 | 6 小时 → 12 小时 → 24 小时逐级拉长 | 实测 |
| 每级试发 | 1 条（单点） | 实测（纪律） |
| 恢复裁定 | ret=0 ＋ 对方回「收到」 | 实测（纪律） |

### 【退避试探配定时核对点】

**① 目标与适用场景**：退避试探的闭环：试发动作必配一个定时核对点回收成败，不预判结果、试完必报。适用于一切「发出去等结果」的异步验证动作。

**② 前置条件**：
- [ ] 定时任务机制可用（能排一次性核对点）
- [ ] 试发结果有可查的记录处（回执、对方确认状态）

**③ 操作步骤**：
1. 成对创建 → 动作：排退避到期试发的同时，排其后一个合理窗口的核对点 → 预期：两个任务成对存在 → 判定信号：任务清单中两项互相关联可见。
2. 试发执行 → 预期：单点一条 → 判定信号：试发记录落盘。
3. 核对点回收 → 动作：到点检查试发回执与对方确认，写结论并回报 → 预期：成功/失败都有着落，退避状态据此更新（清退避或进下一级）→ 判定信号：核对结论成文。

**④ 失败分支**：
- 核对点查不到试发记录 → 定因：试发根本没执行（执行者落空，见下条）→ 处置：先查执行者为何没动，不直接补发 → 停手线：成因未明前不重复排试发（会叠成多发）。
- 试发成功但无人回收已发生过 → 处置：补核对并复盘，把「成对创建」写进试发流程模板 → 停手线：模板未改前不新增退避试探。

**⑤ 验收清单**：
- [ ] 每起试探都有核对结论（证据：核对记录）
- [ ] 退避状态与核对结论一致（证据：退避台账）

**⑥ 禁忌与易错点**：只排试发不排核对（试发成功没人知道、退避不解除、积压继续躺；失败没人记录、下一轮无从排起）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 核对点时机 | 试发后一个合理窗口（覆盖对方常态回复时延） | 示意 |
| 回收率 | 100%（每起必有结论） | 实测（纪律） |

### 【试发执行者唯一】

**① 目标与适用场景**：每个自动动作指定唯一执行者，并核对各执行者规则不互相禁止。曾有教训：退避到期试发因「守候规则禁止碰锁定项、无人认领」而落空。

**② 前置条件**：
- [ ] 系统中有多个自动执行者（守候、扫尾、主线等）及其规则文件可查

**③ 操作步骤**：
1. 逐动作点名 → 预期：每个自动动作在任务定义里写明唯一执行者 → 判定信号：动作清单无「待定/大家都可」项。
2. 互锁排查 → 动作：交叉读各执行者规则，找「A 说归 B、B 说我不碰」式互锁 → 预期：互锁清零 → 判定信号：排查表逐对打勾。
3. 新增执行者/新规则时重跑排查 → 预期：变更流程含互锁复查一步 → 判定信号：变更记录含复查项。

**④ 失败分支**：
- 动作到期无人执行 → 定因：先查互锁与点名缺失，不怪单个执行者 → 处置：补点名、改互锁规则，并为落空的动作补排核对点说明影响 → 停手线：点名未补前不靠人工长期顶岗（会掩盖结构问题）。
- 两个执行者抢做同一动作（重复发送） → 定因：点名不唯一 → 处置：立即停其一，按【已答名单加时间窗双重判重·幂等】兜底防重 → 停手线：唯一性未恢复前暂停该动作自动化。

**⑤ 验收清单**：
- [ ] 动作—执行者对照表完整唯一（证据：对照表）
- [ ] 互锁排查记录在案（证据：排查表）

**⑥ 禁忌与易错点**：以为「多个人都能做」等于保险（实际等于没人做或抢着做）；只点名不查互锁。

**⑦ 参数表**：无参数。

### 【-14 定因·单人令牌过期】

**① 目标与适用场景**：errcode=-14 字面是「会话暂停」，实测对应单个用户的上下文令牌过期。通道故障逐人定因，不按全队故障处置。

**② 前置条件**：
- [ ] 能查单个用户的令牌状态与刷新记录
- [ ] 失败日志含用户维度（知道 -14 发生谁身上）

**③ 操作步骤**：
1. 先定位到人 → 预期：-14 记录对应到具体用户 → 判定信号：日志含用户标识。
2. 查该用户令牌 → 预期：核对令牌生成/刷新时间与最近入站 → 判定信号：令牌过期与 -14 时点吻合即定因成立。
3. 只处置个体 → 预期：等其入站刷新令牌，或走个体恢复路径——三步：(a) 先等一个轮询周期，看其有无自然入站把令牌刷新；(b) 仍无入站的，经其他可达渠道请其在工作台重新走一次绑定（旧凭据作废、新凭据落盘，并按【绑定成功≠纳管】三项验纳管）；(c) 恢复后只单点试发一条验证、不连发。全队不拉警报、不暂停全通道 → 判定信号：处置范围只有该用户。
4. 记录定因 → 预期：把「-14＝单人令牌过期」记入故障台账，供后人不再误读 → 判定信号：台账条目存在。

**④ 失败分支**：
- 多名用户同时报 -14 → 定因：先逐人查令牌，不要顺势升级为系统事件 → 处置：逐人定因后若确属共性（如平台批量失效），再按【大面积同码失败先判系统性事件】处理 → 停手线：逐人证据未齐前不定性系统事件。
- 个体令牌刷新后仍 -14 → 处置：转入个体版绑定与会话核查（只查此一人、不动全队）：逐项核其凭据文件是否完整未损、游标是否出现并推进、绑定关系是否被后来的绑定动作覆盖——检查清单即【绑定成功≠纳管】三项；范围定性的方法借【会话恢复前置条件】第 1 步，但只对这一个人执行 → 停手线：不循环刷新碰运气。

**⑤ 验收清单**：
- [ ] 每起 -14 有到人的定因记录（证据：故障台账）
- [ ] 无因 -14 拉响的全队处置（证据：处置记录范围）

**⑥ 禁忌与易错点**：按字面把 -14 读成全队会话暂停（代价双倍：全局处置白耗、个体真因被噪音盖住）；错误码的定性以实测个案为准，不以字面为准。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| -14 含义 | 单个用户的上下文令牌过期 | 实测 |
| 处置粒度 | 逐人 | 实测（纪律） |

### 【会话暂停处置·先缓冲再判死】

**① 目标与适用场景**：会话暂停类错误的处置节奏：先停等重试一次再判令牌死亡，连接层另配少量指数退避重试，避免把瞬时暂停误判成绑定失效。

**② 前置条件**：
- [ ] 错误处理能区分连接级抖动与会话级暂停
- [ ] 判死结论有日志落点

**③ 操作步骤**：
1. 连接级抖动走指数退避 → 预期：次数少、间隔短地自动重试（间隔基数与倍率见⑦参数表）→ 判定信号：重试日志可见间隔递增。
2. 会话级暂停先停等 → 预期：停等一段（示意 5 分钟）后单次重试 → 判定信号：重试时点与暂停时点间隔达标。
3. 裁决 → 预期：重试通→记一次瞬时暂停事件、恢复正常；重试仍败→判令牌死亡，转该用户恢复流程 → 判定信号：判死日志注明「重试后判定」。

**④ 失败分支**：
- 立即判死（跳过缓冲）已造成误重绑 → 定因：处置节奏错误 → 处置：向用户说明、恢复其绑定关系，并把缓冲步写进处置流程 → 停手线：流程未改前不新增判死动作。
- 暂停频繁复发于同一人 → 定因：非瞬时，转【-14 定因·单人令牌过期】深查 → 停手线：不以无限缓冲代替定因。

**⑤ 验收清单**：
- [ ] 判死记录均含重试证据（证据：日志）
- [ ] 瞬时暂停事件有计数（证据：事件记录）

**⑥ 禁忌与易错点**：立即判死（把活令牌当死人，引发不必要重绑与打扰）；无限重试（撞限流）。平衡点就是「先缓冲、再判死」。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 会话级停等 | 约 5 分钟后重试一次 | 示意 |
| 连接级重试 | 3 次指数退避：间隔基数秒级（5 秒量级）、倍率 2（约 5→10→20 秒），总时长控制在分钟内 | 示意（量级） |

### 【令牌年龄理论证伪】

**① 目标与适用场景**：故障归因的方法纪律：任何「A 导致 B」的理论定案前必须主动找反例。标本： 「令牌太旧导致拒发」被反例推翻。

**② 前置条件**：
- [ ] 有可检索的发送成败记录，且每条记录的字段满足反例检索要求：发送时点、目标用户、结果（受理/被拒及错误原文）、所用令牌的生成或最近刷新时点（令牌年龄由此算出）——缺最后一项，证伪流程根本跑不起来，先补记录字段再谈找反例

**③ 操作步骤**（通用步骤）：
1. 写下待验理论 → 预期：理论表述成可证伪形式（「令牌年龄＞X 则被拒」）→ 判定信号：理论有明确判据。
2. 找两类反例 → 动作：找「有 A 无 B」（旧令牌发送成功）与「无 A 有 B」（新令牌被拒）→ 预期：本标本中两类各有实测个案（十余小时旧令牌成功、刚刷新令牌被拒）→ 判定信号：个案记录可查。
3. 有确凿反例即废理论 → 预期：重新定因，不许给理论打补丁续命 → 判定信号：定因记录含证伪过程。

**④ 失败分支**：
- 找不到反例但理论也无正面强证据 → 定因：证据不足 → 处置：结论降级为「待证」，处置按保守路径（降速保护）走 → 停手线：不按未证理论做大动作（如全员重绑）。
- 团队因理论「听起来对」拒绝证伪 → 处置：把找反例设为诊断流程固定步，写进故障处置模板 → 不靠说服靠流程。

**⑤ 验收清单**：
- [ ] 每起定因记录含反例检索结果（证据：定因记录）
- [ ] 诊断模板含「找反例」固定步（证据：模板文件）

**⑥ 禁忌与易错点**：顺直觉定案后停止找真因，把处置全压在错误方向；理论越优雅越固执，越要先杀它一遍。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 证伪标本 | 旧令牌（十余小时）发送成功；新令牌（刚刷新）被拒 | 实测 |
| 理论存活条件 | 两类反例均不存在 | 实测（方法口径） |

本条步骤为通用方法，无通道专属参数。

### 【大面积同码失败先判系统性事件】

**① 目标与适用场景**：同一时段大面积同码失败，先判系统性事件，不拿这批失败给单个用户通道降级。

**② 前置条件**：
- [ ] 失败日志可按时段与错误码聚合
- [ ] 个体通道等级（盘点四级）有标注机制，能把事件时段失败剥离

**③ 操作步骤**：
1. 聚合判定 → 动作：按时段统计同码失败面 → 预期：达到「大面积」即立系统性事件 → 判定信号：事件记录含时段、错误码、影响人数。
2. 个体剥离 → 预期：该时段失败从个体记录里标注剥离，个体等级不因之下调 → 判定信号：盘点表含事件标注。
3. 事件单独处置 → 预期：按平台侧波动/通道侧共性问题查恢复，恢复后销事件 → 判定信号：事件有恢复记录。

**④ 失败分支**：
- 剥离后仍有个别人持续失败 → 定因：事件之外另有个案 → 处置：该个体转入逐人定因（【ret=-2 定因学】/【-14 定因·单人令牌过期】）→ 停手线：不让系统性事件给真个案当永久挡箭牌。
- 「大面积」阈值拿不准 → 处置：先按保守口径立事件、后按数据修正 → 阈值自定（见参数表），关键是先有判定动作再谈个体归因。

**⑤ 验收清单**：
- [ ] 系统性事件均有独立事件记录（证据：事件台账）
- [ ] 事件时段后个体等级无误降（证据：盘点前后对照）

**⑥ 禁忌与易错点**：不做剥离，一场平台波动把几十个健康通道全打成「风险通道」，后续试发与人工跟进被假风险淹没，真故障排不上号。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 大面积阈值 | 按自家规模自定（如同时段同码失败占比过半） | 待实测 |
| 个体降级 | 事件时段内禁止 | 实测（纪律） |

### 【重试风暴退避止损】

**① 目标与适用场景**：个别对象失败计数异常飙高，多半是重试机制自制的风暴：先退避止损，再查根因。

**② 前置条件**：
- [ ] 失败计数可按对象统计并设异常阈值告警
- [ ] 重试间隔可按对象单独拉长

**③ 操作步骤**：
1. 识别 → 预期：某对象失败计数越过异常阈值即判定疑似风暴 → 判定信号：计数曲线陡升而非匀速。
2. 止损 → 动作：立即拉长该对象重试间隔、降低其优先级 → 预期：发送尝试频率骤降 → 判定信号：后续失败增速明显放缓。
3. 查根因 → 预期：先看自己的重试逻辑（间隔、触发条件、叠加任务），再看对方通道 → 判定信号：根因定位到具体机制。

**④ 失败分支**：
- 止损后失败仍涨 → 定因：非重试风暴，是真实持续故障 → 处置：转逐人定因流程 → 停手线：不以「风暴」结论无限期压住真故障。
- 多个自动任务对同一对象叠加重试 → 定因：执行者不唯一 → 处置：按【试发执行者唯一】收口 → 停手线：收口前全局暂停该对象自动重试。

**⑤ 验收清单**：
- [ ] 异常阈值已设且触发过处置记录（证据：阈值配置＋处置日志）
- [ ] 风暴事件有根因结论（证据：事件记录）

**⑥ 禁忌与易错点**：越挫越发（每轮重试都在加重平台拒收理由、消耗配额、污染失败统计，最后连谁先坏的都查不清）；止损优先于定因，顺序不可反。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 异常阈值 | 按对象常态失败率自定 | 待实测 |
| 止损动作时限 | 发现即执行，先于定因 | 实测（纪律） |

### 【通道故障按类不按案】

**① 目标与适用场景**：重绑与发送类故障随绑定人数增长必然变多，逐案救火救不完——把同类故障收敛成机制。适用于一切规模会增长的服务系统。

**② 前置条件**：
- [ ] 故障有台账，能按类聚合（没有台账先建，见【失败日志记 errmsg·错误原文】）
- [ ] 每一类故障处理完要回答一句：「下次同类，系统自己能接住吗？」

**③ 操作步骤**：
1. 聚类 → 预期：把近期故障按成因归类（如重绑后旧轮询残留、发送失败时轮询静默死亡、回执成功但对方没看到）→ 判定信号：每类有典型个案与频次。
2. 逐类建机制 → 预期：绑定变更检测（绑定一变自动重启该用户轮询）；轮询监督（监督进程每轮复活死轮询并记日志）；失败落盘（每次发送失败必入失败记录）；可达性审计（主动审计上报，不等第二次抱怨）→ 判定信号：四项机制各有实现与日志。
3. 验收每类 → 预期：用历史个案回放，机制能自动接住 → 判定信号：回放记录通过。

**④ 失败分支**：
- 某类故障建了机制仍复发 → 定因：机制接的是症状不是成因 → 处置：回到该类个案深挖成因再改机制 → 停手线：不叠加第二层补丁掩盖第一层失效。
- 人数尚少、觉得按案够用 → 处置：可以暂按案，但机制化方向要提前留接口（台账分类字段先行）→ 不等淹没了才补结构。

**⑤ 验收清单**：
- [ ] 主要故障类均有对应机制（证据：类—机制对照表）
- [ ] 监督复活、绑定变更重启有真实触发日志（证据：日志；未触发的按【部署与实战分开说】标待实证）

**⑥ 禁忌与易错点**：个案处置成本随用户数线性增长，机制处置是一次性的；每案手法不一致还会从不一致里长出新坑。

**⑦ 参数表**：无固定参数；监督周期与轮询周期同级，**示意**。

### 【错误码在异常属性里】

**① 目标与适用场景**：代码级坑：错误码藏在异常对象的属性里而非消息文本里，按文本匹配的捕获永远拦不住，轮询线程被未捕获异常打死且静默消失。

**② 前置条件**：
- [ ] 能读轮询线程的异常处理代码
- [ ] 线程死亡有日志/告警出口（没有先补，这是本条的一部分）

**③ 操作步骤**：
1. 改捕获依据 → 动作：捕获点读结构化属性（错误码字段）做分支，弃用消息文本字符串匹配 → 预期：平台改错误文案也不影响捕获 → 判定信号：人为构造文案变化的异常，分支仍正确命中。
2. 加全量兜底 → 预期：任何未识别异常也不许打死线程：记日志、退避、继续轮询 → 判定信号：注入未知异常，线程存活且日志有记录。
3. 死亡必告警 → 预期：线程真死亡时有日志与告警，不许静默消失 → 判定信号：杀死测试线程，告警到达。

**④ 失败分支**：
- 线程已静默死亡多时才发现 → 定因：缺死亡告警 → 处置：先按【孤儿扫尾设计·服务器端扫捡兜底】补投递，再补告警与监督复活 → 停手线：告警未补前不宣称该类故障已治理。
- 平台异常结构变化（属性名改了） → 处置：兜底捕获接住、记未知异常样本，更新属性映射 → 不因映射失效而丢线程。

**⑤ 验收清单**：
- [ ] 文案变化与未知异常两项注入测试通过（证据：测试记录）
- [ ] 线程死亡告警实测到达（证据：告警记录）

**⑥ 禁忌与易错点**：凡靠解析人类可读文本做程序分支的地方，都埋着同一种雷；线程静默死亡时通道看起来「在运行」，实际已经停收。

**⑦ 参数表**：无参数。

### 【答复截断在存储层】

**① 目标与适用场景**：定位标本：用户端收到完整答复、历史里只剩半截——发送按定长分片发完，截断点在历史摘要函数的定长切片。用两头对账定位，不误判发送故障。

**② 前置条件**：
- [ ] 发送侧留有回执字数（或可算出发送总字数）
- [ ] 历史存储的字数可查

**③ 操作步骤**：
1. 两头对账 → 动作：比发送回执总字数与历史存下字数 → 预期：差值出现在哪一层，截断点就在哪一层 → 判定信号：差值定位到存储层（发送数＞存储数且用户端完整）。
2. 查摘要函数 → 预期：找到定长切片处 → 判定信号：切片长度与截断位置吻合。
3. 修复并回验 → 预期：改切片口径后，长答复完整入史 → 判定信号：再发一条超长答复，三方字数（发送/存储/用户端）一致。

**④ 失败分支**：
- 对账显示发送数就少 → 定因：截断在生成或发送段，不在本条 → 处置：转对应段排查 → 停手线：不对账不动手，禁止凭症状猜段。
- 各段计数物料缺失 → 处置：先在各段补计数留痕再复现 → 事后补不出来的物料，靠下一次真实长答复取证。

**⑤ 验收清单**：
- [ ] 对账记录完整（证据：三方字数）
- [ ] 修复后超长答复三方一致（证据：复验记录）

**⑥ 禁忌与易错点**：一看到「记录不全」就查通道（修错地方）；分段系统里同症状可能出在生成、发送、存储、展示任何一段。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 发送分片长度 | 2000 字/片 | 实测 |
| 定位方法 | 发送回执字数 vs 历史字数对账 | 实测（方法） |

### 【历史污染上下文】

**① 目标与适用场景**：上条的危害升级：被截断的历史摘要会进入后续对话上下文，污染答复质量。凡会被重新装配进上下文的数据，其完整性缺陷按功能缺陷处理，不按显示瑕疵处理。

**② 前置条件**：
- [ ] 已摸清哪些存储数据会被下游消费（历史摘要、记忆、档案）

**③ 操作步骤**（通用步骤）：
1. 按消费链定级 → 预期：列出每类存储数据的下游消费方，完整性要求随消费链长度提高 → 判定信号：定级表成文。
2. 修复带存量 → 预期：修截断源的同时，已被截断的历史要标注或清洗。标注用机器可读的统一标记（字段类别：条目 ID、截断位置、原定长上限、标记时间；格式一处定义、全系统共用，不许各处自创写法），上下文装配逻辑见到标记即跳过该条或降权处理 → 判定信号：存量处理记录齐全，装配日志里残缺条目有跳过/降权痕迹，不让残缺文本继续喂后续对话。
3. 复验答复质量 → 预期：抽查引用过该段历史的后续答复 → 判定信号：无基于残缺信息的续答。

**④ 失败分支**：
- 存量太多无法逐条清洗 → 处置：至少做截断标记，让装配逻辑跳过或降权残缺条目 → 停手线：不假装存量问题不存在。
- 污染已造成错误答复外发 → 处置：按错误答复的更正纪律当轮更正 → 先止损再修源。

**⑤ 验收清单**：
- [ ] 数据定级表成文（证据：定级表）
- [ ] 存量残缺条目有标记或清洗记录（证据：处理记录）

**⑥ 禁忌与易错点**：把存储截断当「记录不好看」的小事——截断的半句话进了上下文，错误会自我繁殖且极难溯源（你查到的永远是「这次答得不好」）。

**⑦ 参数表**：无参数。本条为通用方法条目。

### 【消失条目先查证再定性】

**① 目标与适用场景**：结论纪律：队列条目消失，先调执行日志查证再定性，不凭界面印象判「丢失/无人执行」。标本：某锁定条目被判去向不明，查日志证实是兜底扫尾晚几分钟执行成功。

**② 前置条件**：
- [ ] 执行日志可查（主通道与兜底通道的日志都在手边）

**③ 操作步骤**（通用步骤）：
1. 先查日志 → 动作：按条目 ID 全量检索各执行者日志 → 预期：找到其最终去向（已办结/在途/真无记录）→ 判定信号：日志证据在手才许开口定性。
2. 据实定性 → 预期：办结的记办结（含执行者与时点），真无记录的才记异常消失并立项查 → 判定信号：定性结论附日志出处。
3. 误判要公开更正 → 预期：先前已下错误结论的，查清后当轮更正，不悄悄改口 → 判定信号：更正记录与原结论可互相追溯。

**④ 失败分支**：
- 日志也查不到去向 → 定因：真异常消失 → 处置：按队列完整性故障处理，查销项路径与回执衔接（参见【pending 孤儿成因】的反面）→ 停手线：查清前不补发同内容（可能造成重复送达）。
- 执行者日志缺失 → 处置：先补日志再谈定性 → 无日志的执行者不许独立销项。

**⑤ 验收清单**：
- [ ] 每起「消失」定性都附日志出处（证据：定性记录）
- [ ] 误判更正记录齐全（证据：更正条目）

**⑥ 禁忌与易错点**：把「看不见」当「没发生」——执行者可能换了进程、走了兜底、延迟了时段；凭印象定性既冤枉正常机制，又会去修不存在的故障。

**⑦ 参数表**：无参数。本条为通用方法条目。与【试发执行者唯一】配套：一个防丢事，一个防冤枉。

## 第五章 通道盘点与送达证据

### 【送达三级证据分级·ret=0 只是平台接受】

**① 目标与适用场景**：全卷证据总纲：一次发送拆三级——一级写入待发队列（落盘）、二级平台接口受理（ret=0）、三级接收方亲眼确认。汇报按级表述，永不混谈。适用于一切经过中间平台的消息系统。

**② 前置条件**：
- [ ] 发送链各段有可查记录（队列文件、回执日志、对方确认来源）
- [ ] 汇报模板有「证据级别」位置（没有先改模板）

**③ 操作步骤**：
1. 每级留痕 → 预期：入队有队列记录、受理有回执记录、确认有对方回复或口头确认记录 → 判定信号：任一次发送可逐级出示。
2. 汇报按级说 → 预期：说清停留在哪一级、上一级何时达成、下一级差什么 → 判定信号：汇报文本出现明确级别用语（已入队/平台已受理/对方已确认）。
3. 第三级才裁定真通 → 预期：通道是否真通只认接收方确认 → 判定信号：健康统计只数第三级（见下条四级盘点）。

**④ 失败分支**：
- 二级成功但三级迟迟不来（如图片回执成功、对方看不见） → 定因：受理≠可见，中间还有参数正确性一层（见【图片回发三参数坑】）→ 处置：按不可见故障排查，不许以回执结案 → 停手线：对方未确认前不报「已送达」。
- 有人催报「到底发没发」 → 处置：按级回答并给出升下一级所需条件 → 不被催促压成一句「发了」。

**⑤ 验收清单**：
- [ ] 随机抽 3 次发送，三级证据齐全可出示（证据：抽查记录）
- [ ] 近期汇报无混级表述（证据：汇报抽查）

**⑥ 禁忌与易错点**：把「平台受理」说成「对方收到」——用户按「已通知到」安排工作，没收到的人毫不知情，复盘时记录还全写着「发送成功」。分级是把责任边界画在证据边界上。

**⑦ 参数表**：
| 证据级 | 含义 | 证据形态 |
|---|---|---|
| 一级 | 内容写入待发队列 | 队列文件/记录 |
| 二级 | 平台受理（ret=0） | 回执日志 |
| 三级 | 接收方亲眼确认 | 对方回复/确认记录 |

以上为实测口径。端到端有强回执的官方通道可简化，但「受理≠送达」永不取消。

### 【双向验证才是健康度·四级盘点法】

**① 目标与适用场景**：通道健康度盘点：绑定数不等于可用数，判定通的唯一证据是「对方在你出站之后回过消息」。全员四级分类，健康度只报双向验证数。

**② 前置条件**：
- [ ] 三源数据齐备（发送记录、失败日志、会话转录，见下条）
- [ ] 自测账号已剔除出样本（见【自测账号往来不计通道证据】）

**③ 操作步骤**：
1. 逐人取证 → 预期：每人查三源，定其最近出站与出站后回信情况 → 判定信号：每人有定级依据。
2. 四级分类 → 预期：A 双向实证通（出站后有回信）；B 受理未证实（只有回执、从未回复）；C 失败过（有明确失败记录）；D 无往来（绑后从未互动）→ 判定信号：四级名单互斥且合计＝绑定总数。
3. 名单单列 → 预期：B 级成「未证实名单」、C 级成「风险名单」，不埋进发送成功总数 → 判定信号：盘点表含两张单列名单。
4. 汇报与留痕 → 预期：对外只报 A 级数（双向验证数），逐周留痕、与上期对比变化 → 判定信号：周对比表在案。

**④ 失败分支**：
- B 级长期不降 → 定因：对方可能根本收不到 → 处置：走【探通道试发预授权】单点试发，或随其入站自然证实 → 停手线：不把 B 级人数摊进「基本都通」的表述里。
- 盘点数与绑定总数对不上 → 定因：样本口径漂移（混入自测账号或漏人）→ 处置：先对齐名册再盘点 → 停手线：总数不闭合不发布盘点结论。

**⑤ 验收清单**：
- [ ] 四级合计＝绑定总数（证据：盘点表闭合校验）
- [ ] 未证实/风险名单单列（证据：盘点表）
- [ ] 周对比留痕（证据：历史盘点）

**⑥ 禁忌与易错点**：用绑定数或发送成功数当健康度（数字永远好看、盲区永远在涨）；盘点周期可按规模定，但分类口径不许变、名单不许合并。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 盘点周期 | 每周全量重盘一次 | 实测 |
| 健康指标 | 双向验证数（A 级） | 实测（口径） |
| 分类 | A 双向实证 / B 受理未证实 / C 失败过 / D 无往来 | 实测 |

### 【通道盘点三源交叉核对·失败不在回执里】

**① 目标与适用场景**：盘点的数据纪律：出站回执文件全是成功码，失败只记在另一份发送日志里。只看回执必漏全部失败。盘点必须交叉核对三源。

**② 前置条件**：
- [ ] 先找到「失败记在哪」——找不到失败的记录位置，盘点不要开始
- [ ] 三源时间范围对齐（同一盘点窗口）

**③ 操作步骤**：
1. 取发送记录 → 预期：窗口内发了什么、何时、对谁 → 判定信号：记录可按人聚合。
2. 取失败日志 → 预期：谁失败、什么错误码与原文 → 判定信号：失败条目能与发送记录对上号。
3. 取会话转录 → 预期：对方到底回没回 → 判定信号：回信事实可查。
4. 三源对齐定级 → 预期：每人的四级分类有三源支撑；单源结论标「待交叉核对」→ 判定信号：盘点表注来源。

**④ 失败分支**：
- 某源缺失（如失败日志没记） → 定因：记录体系有洞 → 处置：本轮盘点结论降级为「不完整盘点」并明示缺哪源，同时补记录机制（见【失败日志记 errmsg·错误原文】）→ 停手线：不拿单源结论发布健康度。
- 三源互相矛盾 → 处置：以行为记录（会话转录）为准裁定事实，另两源记差异待查 → 不挑对自己有利的源用。

**⑤ 验收清单**：
- [ ] 盘点表每行注三源依据（证据：盘点表）
- [ ] 失败总数能从失败日志独立复算（证据：复算记录）

**⑥ 禁忌与易错点**：每个数据源只为自己的目的设计（回执记受理、日志记异常、转录记事实）；拿单一源回答它没打算回答的问题，偏差方向永远偏乐观。

**⑦ 参数表**：无参数。

### 【连通盘点进晨报】

**① 目标与适用场景**：让盲区持续曝光：未证实与曾失败名单固定进每日简报一行，每周全量重盘一次。名单为空也要明写「全部已证实」。

**② 前置条件**：
- [ ] 有每日简报机制（没有则先建固定日报口）
- [ ] 四级盘点在运行（本条是它的曝光层）

**③ 操作步骤**：
1. 晨报固定行 → 预期：每日一行，只写两类名单的人数与新增变化，不展开细节 → 判定信号：晨报该行天天出现，无缺日。
2. 空名单明写 → 预期：名单为空时写「全部已证实」→ 判定信号：不省略该行（省略分不清「没问题」和「今天没查」）。
3. 周全量重盘 → 预期：刷新四级分类，结果回填晨报基数 → 判定信号：周盘点记录在案。

**④ 失败分支**：
- 名单长期不变且无人跟进 → 定因：曝光无处置闭环 → 处置：晨报行后加责任人与下一步动作 → 停手线：不许把曝光当处置本身。
- 晨报行被嫌啰嗦想删 → 处置：保行删细节（名单本体留盘点文件，晨报只做索引）→ 停手线：行不可删。

**⑤ 验收清单**：
- [ ] 连续一周晨报该行无缺日（证据：晨报存档）
- [ ] 空名单日有「全部已证实」明写（证据：当日晨报）

**⑥ 禁忌与易错点**：靠投诉暴露盲区——收不到的人根本不知道自己该收到，等于把监控外包给受害者。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 晨报频次 | 每日一行 | 实测 |
| 全量重盘 | 每周一次 | 实测 |

### 【通道状态看时间序列不看单点】

**① 目标与适用场景**：状态判断方法：同一分钟内成功回执与失败记录可并存，判状态看时间序列不看单点。适用于一切间歇性故障判定。

**② 前置条件**：
- [ ] 发送成败记录带时间戳、可按对象与窗口聚合

**③ 操作步骤**：
1. 定窗口 → 预期：按问题选窗口（如最近 24 小时）→ 判定信号：结论注明窗口。
2. 看分布 → 预期：算该对象窗口内成功率、失败码分布、最后一次成功时间；判全局看同窗口整体分布 → 判定信号：结论含样本量。
3. 按序列下结论 → 预期：如「近 24 小时 12 次中 9 成 3 败、末次成功在 1 小时前」→ 判定信号：汇报给窗口与样本量，不给单点结论。

**④ 失败分支**：
- 样本量太小（窗口内只有一两次） → 定因：证据不足 → 处置：扩窗或明说「样本不足、待观察」→ 停手线：不拿一两次结果判生死。
- 有人拿单条成功记录要求结案 → 处置：出示同窗口失败分布 → 不以单点翻案。

**⑤ 验收清单**：
- [ ] 状态结论均含窗口与样本量（证据：结论记录抽查）
- [ ] 结论含成功率、失败码分布与最后一次成功时间（证据：窗口聚合记录）
- [ ] 无以单条成功/失败记录翻案的结论（证据：结论与同窗口分布对照抽查）

**⑥ 禁忌与易错点**：「刚才有一条成功了，所以通道正常」——单点只证明那一瞬间对那个人成功；序列看脾气，单点看运气。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 观察窗口 | 按问题定（常用 24 小时） | 示意 |
| 结论要素 | 窗口＋样本量＋分布，缺一不下结论 | 实测（纪律） |

### 【首次绑定以会话记录交叉核对】

**① 目标与适用场景**：判「首次绑定」不能只看绑定表时间戳（重绑、记录重建都会刷新它），须交叉会话记录核对。适用于一切带重绑/重建机制的系统。

**② 前置条件**：
- [ ] 会话记录（入站/出站行为记录）留存完整

**③ 操作步骤**：
1. 取两路时间 → 预期：绑定表时间戳、该用户最早会话记录时间各一 → 判定信号：两值可比。
2. 比对裁定 → 预期：一致则确认；不一致以会话记录为准，并注明差异原因（重绑/重建）→ 判定信号：裁定记录含两值与依据。
3. 历史断言同法 → 预期：凡涉「第一次/最早」的断言都走一遍交叉核对 → 判定信号：断言附核对记录。

**④ 失败分支**：
- 会话记录也缺失 → 定因：历史不可考 → 处置：如实标「不可考」，不拿时间戳单独充数 → 停手线：不可考的首次绑定不写入正式统计。
- 两值差异原因不明 → 处置：记为待核，不强行归因 → 不编造重建故事。

**⑤ 验收清单**：
- [ ] 首次绑定类结论均有交叉核对记录（证据：核对记录）
- [ ] 核对记录含两路时间值与裁定依据（证据：记录字段）
- [ ] 两值不一致的已注明差异原因，或如实标「不可考」（证据：记录字段）

**⑥ 禁忌与易错点**：把会被覆盖的时间戳当历史事实——会在冷启动顺序、增长曲线、责任时段上系统性出错。可信度排序：行为记录高于状态记录；当前状态表不能替代历史行为表回答历史问题。

**⑦ 参数表**：无参数。

### 【姓名口径三方对照定准】

**① 目标与适用场景**：通道端姓名写法与花名册不一致时（同音字、异体字、简繁差异常见），三方对照定准，不凭单一口径改名。涉及真实姓名的对照实例不入分享材料，本条只留方法。需化名假数。

**② 前置条件**：
- [ ] 三方来源可查：账号库注册名、通讯录名册名、通道端显示名
- [ ] 已确认权威口径（以花名册为准）

**③ 操作步骤**：
1. 三方逐一比对 → 预期：列出三处写法差异 → 判定信号：差异表成文。
2. 先判同一人还是同名人 → 预期：结合部门、账号等旁证确认是「同一人异写」而非「两个同名人」→ 判定信号：确认依据在案；确认不了进失败分支。
3. 统一口径 → 预期：以花名册为准改齐，异写记入备注供日后识别 → 判定信号：三处口径一致、备注含异写。

**④ 失败分支**：
- 确认不了是否同一人 → 定因：旁证不足 → 处置：挂起问清，不许先改了再说 → 停手线：未确认不改任何一处名字。
- 改名后发现改错（实为同名人） → 处置：立即回滚、逐项核对受影响的材料归属与发送记录 → 停手线：归属未核清前暂停对两人的材料操作。

**⑤ 验收清单**：
- [ ] 差异表与统一结果在案（证据：对照记录）
- [ ] 异写备注已记（证据：备注字段）

**⑥ 禁忌与易错点**：名字是按人隔离与材料归属的索引键，改错一次材料就归错人、消息发错人，且所有系统都「正常工作」，极难察觉。

**⑦ 参数表**：无参数。

### 【失败日志记 errmsg·错误原文】

**① 目标与适用场景**：失败日志字段规范：发送失败必须把平台返回的错误原文落盘再诊断，没有原文不猜原因。

**② 前置条件**：
- [ ] 发送代码的失败路径可改（或新建日志点）
- [ ] 已定字段白名单（记什么、不记什么）

**③ 操作步骤**：
1. 定字段 → 预期：每条失败记录含时间、用户标识、消息类型、错误码、错误原文五项 → 判定信号：抽一条失败记录五项齐全。
2. 明确不记正文 → 预期：日志无任何消息正文 → 判定信号：抽查日志无用户内容。
3. 定因流程引用原文 → 预期：【ret=-2 定因学】三分法直接引日志原文分类，不靠人转述 → 判定信号：定因记录注明原文出处行。

**④ 失败分支**：
- 原文含敏感参数 → 处置：脱敏截断再落盘，但错误语义部分必须保留 → 停手线：不以「有敏感」为由整条不记。
- 历史日志只有错误码没原文 → 定因：旧规范缺字段 → 处置：旧失败不追溯定因（证据已销毁），新失败起按本规范记 → 不拿旧记录猜病因。

**⑤ 验收清单**：
- [ ] 失败记录五字段齐全（证据：日志抽查）
- [ ] 日志无消息正文（证据：抽查）

**⑥ 禁忌与易错点**：错误码相同而原文不同的失败病因可能完全相反（同样 -2，「prepare failed」等令牌、「freq limit」降速）；不记原文等于把诊断最关键的证据当场销毁。

**⑦ 参数表**：
| 字段 | 必记 | 说明 |
|---|---|---|
| 时间 | 是 | 带时区或统一时钟 |
| 用户标识 | 是 | 协议 ID 即可，不记自然人信息 |
| 消息类型 | 是 | 文本/图片/文件等 |
| 错误码＋错误原文 | 是 | 原文可脱敏截断，语义保留 |
| 消息正文 | 否 | 明文禁止入日志 |

以上为实测规范。

### 【部署与实战分开说】

**① 目标与适用场景**：汇报口径：机制「已部署」与「已实战验证」是两个状态，分开标、分开说，不许用部署冒充验证。

**② 前置条件**：
- [ ] 机制台账有状态字段（没有先加）

**③ 操作步骤**（通用步骤）：
1. 逐机制标状态 → 预期：已部署待实证（如绑定刷新只经代码走查）/已实战验证（如监督复活在真实故障中触发过并成功）二选一 → 判定信号：台账状态与证据对应。
2. 汇报照台账说 → 预期：待实证的说明还差哪种真实事件才能转正 → 判定信号：汇报文本含差项说明。
3. 真实事件发生后转正 → 预期：事件证据归档、状态更新 → 判定信号：转正记录可追溯。

**④ 失败分支**：
- 已按「已验证」汇报出去、实际只是部署 → 定因：口径造假（哪怕无心）→ 处置：当轮更正并复盘台账 → 停手线：更正前不以该机制做安全承诺。
- 待实证长期挂着没人管 → 处置：在盘点里单列待实证清单，逐项排真实事件验证（可借自然事件，不必造故障）→ 不许无限期挂账。

**⑤ 验收清单**：
- [ ] 全部机制状态标注齐全（证据：台账）
- [ ] 汇报与台账状态一致（证据：抽查）

**⑥ 禁忌与易错点**：代码走查只能证明「逻辑上应该行」，证明不了真实环境里行——真实环境有走查想不到的数据形态与时序。

**⑦ 参数表**：无参数。本条为通用方法条目。与卷一验证分账同源。

### 【线上核查只读零副作用】

**① 目标与适用场景**：核查线上状态只用只读方式：不改文件、不重启服务、不发测试消息，盘点动作本身零副作用。故障处置阶段不在此限，但要明说「现在是处置不是核查」。

**② 前置条件**：
- [ ] 核查清单事先列好（执行时不临时起意加动作）
- [ ] 只读手段齐备：读日志、读状态文件、带令牌调只读健康端点

**③ 操作步骤**：
1. 按清单逐项读 → 预期：每项有读取结果记录 → 判定信号：清单逐项打勾且无写操作。
2. 遇需验证的疑问 → 预期：只登记为待验证项，不当场试发 → 判定信号：疑问转入试发预授权流程（见【探通道试发预授权】）。
3. 核查收尾自检 → 预期：复盘本轮动作全为读 → 判定信号：操作记录无写、无重启、无发送。

**④ 失败分支**：
- 核查中手痒重启/试发了 → 定因：纪律失效且观察对象已被污染 → 处置：如实记录污染点，本轮相关结论作废重查 → 停手线：不拿污染后的状态冒充自然状态汇报。
- 只读手段不足以定性 → 处置：结论就停在「只读可证」层级，处置另行立项 → 不以核查之名行处置之实。

**⑤ 验收清单**：
- [ ] 核查操作记录全为读（证据：操作日志）
- [ ] 待验证项均已转正规流程（证据：转办记录）

**⑥ 禁忌与易错点**：核查目的是观察系统的自然状态，任何写操作都会污染观察对象——你重启过的服务、试发过的通道，状态已不是用户正在经历的那个。

**⑦ 参数表**：无参数。

### 【巡检 403 误报】

**① 目标与适用场景**：健康端点无令牌返回 403 是正常鉴权门槛，不是故障；巡检必须带令牌按真实调用方式访问，令牌永不写入任何报告。

**② 前置条件**：
- [ ] 巡检能从本地凭据文件读令牌（令牌管理见【通道令牌只读本地不入日志】）
- [ ] 巡检规则能区分状态码定级

**③ 操作步骤**：
1. 带令牌访问 → 预期：健康端点返回正常状态 → 判定信号：带令牌结果为巡检结论依据。
2. 分开定级 → 预期：无令牌 403＝巡检自身配置问题（先修巡检）；带令牌仍 403/5xx＝服务问题 → 判定信号：告警注明是哪类。
3. 令牌不落报告 → 预期：巡检报告只写结论不写令牌值/片段 → 判定信号：报告抽查无令牌痕迹。

**④ 失败分支**：
- 巡检天天报 403 假警报 → 定因：巡检没带令牌 → 处置：修巡检配置，并复盘假警报期间是否漏掉真故障 → 停手线：假警报未除前不许把巡检告警整体静音（会连真警报一起吞）。
- 带令牌仍 403 → 定因：令牌失效或端点鉴权变更 → 处置：按凭据问题查，不按服务故障报 → 先分清再上报。

**⑤ 验收清单**：
- [ ] 巡检带令牌且结论稳定（证据：巡检记录）
- [ ] 报告无令牌痕迹（证据：报告抽查）

**⑥ 禁忌与易错点**：误报训练团队对警报脱敏——天天喊狼来了，真故障那天没人当回事。监控的探测方式与真实使用方式差多少，误报漏报就差多少。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 无令牌 403 | 正常鉴权，非故障 | 实测 |
| 巡检方式 | 带令牌、等同真实调用 | 实测（纪律） |

### 【自测账号往来不计通道证据】

**① 目标与适用场景**：盘点样本纯洁性：管理员与机器人的自测账号往来不计入普通用户通道证据，盘点时单列说明。

**② 前置条件**：
- [ ] 自测账号清单明确（哪些账号是自测用）

**③ 操作步骤**：
1. 统计前剔除 → 预期：四级盘点样本只含真实服务对象 → 判定信号：样本数＝绑定总数－自测数，对得上。
2. 单列说明 → 预期：盘点表附一行注明自测账号数量与用途 → 判定信号：说明行存在。
3. 指标口径锁定 → 预期：双向验证率等指标的分母只含真实用户 → 判定信号：指标计算可复算。

**④ 失败分支**：
- 已混入统计并汇报 → 定因：口径污染 → 处置：重算并更正汇报 → 停手线：更正前不引用旧数字。
- 自测账号与真实账号分不清 → 处置：先按绑定记录与用途核清清单再盘点 → 不猜。

**⑤ 验收清单**：
- [ ] 盘点样本与自测清单对照无混入（证据：对照记录）
- [ ] 盘点表含自测单列说明（证据：盘点表）

**⑥ 禁忌与易错点**：自测账号上下文新、互动频繁、问题即时处理，算进样本会系统性高估健康度，把真实用户的盲区摊薄掩盖。

**⑦ 参数表**：无参数。

## 第六章 语音与媒体

### 【媒体通道四能·类型齐全才算交付】

**① 目标与适用场景**：媒体能力验收标准：文字之外，语音、图片、文件三类都必须能经桥处理，每类按能收、能读、能产、能回四能验收。只通文字的通道不算交付。

**② 前置条件**：
- [ ] 三类媒体的测试样本已备（真实格式的语音、图片、文件各至少一份）

**③ 操作步骤**：
1. 逐类过四能 → 动作：每类媒体依次验能收（进得来、落盘）、能读（抽取/看图/转写出内容）、能产（能生成并发回同类媒体）、能回（答复以合适形态回到对方且对方可见可用）→ 预期：每类得四能结论 → 判定信号：验收表逐格有证据，不许整类一句「基本支持」。
2. 缺能标注 → 预期：缺一能，该类标「未交付」并注明缺哪能 → 判定信号：状态口径与验收表一致。
3. 补能后复验 → 预期：只复验缺的格，但能回一格必须真实对方可见 → 判定信号：复验记录含对方确认（第三级证据）。

**④ 失败分支**：
- 某类能收不能读 → 定因：处理链缺环 → 处置：按【统一媒体通道·附件即材料本体】补分发处理，期间对用户明示该类暂不可读 → 停手线：不假装读过（见【附件抽取失败回源取原文件】）。
- 能产但对方不可见 → 定因：回发参数问题 → 处置：转【图片回发三参数坑】类方法逐字段对照 → 停手线：不以回执成功结案。

**⑤ 验收清单**：
- [ ] 三类媒体×四能共 12 格逐格有证据（证据：验收表）
- [ ] 未交付项在状态口径中明示（证据：状态说明）

**⑥ 禁忌与易错点**：文字通了就宣布上线（用户不会迁就通道改变表达习惯，缺一类媒体就是缺这批用户的一半表达）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 媒体类型 | 文字＋语音＋图片＋文件 | 实测（交付线） |
| 验收维度 | 能收/能读/能产/能回，缺一未交付 | 实测（口径） |

### 【统一媒体通道·附件即材料本体】

**① 目标与适用场景**：三类媒体走一条流水线：下载落盘→附件清单随请求递交→处理端按类型分发。答复前先处理完附件——附件内容就是材料本体，不是正文的附属说明。

**② 前置条件**：
- [ ] 落盘目录按人隔离（承接第二章隔离纪律）
- [ ] 文档抽取组件覆盖办公文档、表格、幻灯片、PDF、文本类

**③ 操作步骤**：
1. 下载落盘 → 预期：附件存入本人空间、生成附件清单（文件名、类型、路径、处置状态）→ 判定信号：清单与落盘文件一一对应。
2. 随请求递交 → 预期：处理端收到正文＋附件清单 → 判定信号：处理记录含清单。
3. 按类型分发 → 预期：文档类在桥侧做文本抽取（设字符上限，超限截断并注明）；图片直转待读；未转写语音打标记；视频未处理明说；抽取失败保留原文件路径供回取 → 判定信号：每类处置状态对用户透明可见。
4. 处理完才答复 → 预期：答复引用附件内容以抽取/读取结果为准 → 判定信号：不凭文件名猜内容。

**④ 失败分支**：
- 抽取失败 → 处置：转【附件抽取失败回源取原文件】三级兜底 → 停手线：不假装读过。
- 附件超抽取上限被截断 → 处置：答复中注明已截断及截断点，请对方指重点或拆分发送 → 不默默按半份材料办事。

**⑤ 验收清单**：
- [ ] 三类附件各走通全链（证据：样本处理记录）
- [ ] 处置状态对用户透明（证据：回复样本含状态说明）

**⑥ 禁忌与易错点**：三类媒体各修一套（三套不一致的失败模式、三倍维护成本）；把附件当附属（「正文没写、只发了个表」恰是最常见的真实用法，当附属就会系统性漏读材料本体）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 文档抽取字符上限 | 20000 字，超限截断并注明 | 配置值 |
| 新媒体类型接入 | 只加一个分发分支，不新起流水线 | 实测（架构纪律） |

### 【附件抽取失败回源取原文件】

**① 目标与适用场景**：抽取失败时的三级兜底：平台抽取→回源取原文件自行读取→仍读不出如实请对方换格式或贴文字。任何一级失败不许假装读过。

**② 前置条件**：
- [ ] 回源端点已按【媒体端点防护】建成（带鉴权可取原文件）
- [ ] 本地解析工具可读常见格式

**③ 操作步骤**：
1. 一级平台抽取 → 预期：得文本或明确失败 → 判定信号：抽取结果/失败记录。
2. 二级回源自读 → 动作：经鉴权端点取原文件，本地解析工具读一遍 → 预期：多数格式变体/加密/扫描件问题在此级解决 → 判定信号：读出内容可复述。
3. 三级请对方协助 → 预期：如实说明卡在哪一级，请其换格式或贴关键文字 → 判定信号：回复含明确卡点说明，不含「已收到并处理」式假话。

**④ 失败分支**：
- 二级取回的文件仍解析不了 → 定因：格式过偏或文件损坏 → 处置：直接进三级，并记下格式类型列入待支持清单 → 停手线：不反复用同一工具重试同文件。
- 对方无法换格式 → 处置：请其拍照/截图关键页按图片读（见下条） → 给足替代路径，不让材料死在格式上。

**⑤ 验收清单**：
- [ ] 抽取失败样本三级路径各有记录（证据：处理日志）
- [ ] 无「未读冒充已读」的答复（证据：会话抽查）

**⑥ 禁忌与易错点**：第一级失败就宣布读不了（把可恢复故障报成绝症）；假装读过（对方基于「你看了」继续推进，错误在下游放大——最坏选项）。

**⑦ 参数表**：无参数。兜底共 3 级，实测纪律。

### 【图片须取回原图读清再用】

**① 目标与适用场景**：收到图片标记不等于看见图片：必须取回原图、读清文字/表格/场景再当材料处理。适用于一切图片入站。

**② 前置条件**：
- [ ] 能经媒体通道取回原图（非缩略图）
- [ ] 读图能力可用（文字识别与内容理解）

**③ 操作步骤**：
1. 取原图 → 预期：拿到原图文件而非占位标记 → 判定信号：文件落盘且尺寸为原图量级。
2. 读图 → 预期：图中文字逐项读、表格按行列读、场景要素读全 → 判定信号：读数结果成文。
3. 复述入记录 → 预期：关键内容（数字、日期、人名）复述进工作记录再据此答复/建档 → 判定信号：记录与原图可对照。
4. 模糊处标注 → 预期：读不清的局部标「此处模糊」，请对方补拍或补文字 → 判定信号：不脑补补齐。

**④ 失败分支**：
- 只拿到缩略图、细节不可读 → 定因：取图路径拿错版本 → 处置：换原图端点重取 → 停手线：不凭缩略图读正式材料（通知、表格、证件类尤其）。
- 隐私敏感图片（证件类） → 处置：按本人会话边界处理，不进共享区（承接第二章）→ 不在答复里复述无关敏感字段。

**⑤ 验收清单**：
- [ ] 图片类材料均有读图记录（证据：工作记录抽查）
- [ ] 模糊标注真实存在过（证据：含标注的样本）——从无标注往往意味着在脑补

**⑥ 禁忌与易错点**：凭标记答复、凭印象补全——用户拍来的多是正式材料，「收到一张图」与「读清这张图」之差就是服务有没有发生之差；关键数字与日期最易栽在脑补上。

**⑦ 参数表**：无参数。

### 【媒体断点在路由不在下载】

**① 目标与适用场景**：媒体故障分段定位标本：下载落盘全通、却被固定话术截断——断点在路由段（路由层对非文本消息不转发给处理者），不在下载段。

**② 前置条件**：
- [ ] 两段各有可观测点：落盘日志、转发日志（没有先补，这是本条的一部分）

**③ 操作步骤**：
1. 查第一段「收没收到」 → 预期：查落盘记录与附件清单 → 判定信号：文件在＝第一段通。
2. 查第二段「转没转给处理者」 → 预期：查路由对各消息类型的分发分支 → 判定信号：转发日志缺该类型＝断点在路由。
3. 按段修复 → 预期：只修断的那段，修后用同类型样本复验全链 → 判定信号：样本从落盘到答复全程有记录。

**④ 失败分支**：
- 两段日志都缺 → 定因：不可观测 → 处置：先补两个日志点再复现 → 停手线：无分段证据不下「媒体功能坏了」的笼统结论。
- 两段都通但仍失败 → 定因：断点在处理段或回复段 → 处置：把分段法向后延伸一段继续切 → 不回头重修已证通的两段。

**⑤ 验收清单**：
- [ ] 每类媒体两段日志齐全（证据：日志样本）
- [ ] 新类型上线时两段观测点同步就位（证据：上线检查单）

**⑥ 禁忌与易错点**：笼统定位把人引向错误的那段（下载明明通却反复修下载）；故障定位先切段、逐段证伪，不要整段怀疑。适用于一切多段流水线。

**⑦ 参数表**：无参数。

### 【媒体端点防护】

**① 目标与适用场景**：附件中转/回取端点的安全基线：令牌校验＋目录白名单＋大小上限＋防路径逃逸四件套，实测逃逸与无令牌均被拒才算建成。

**② 前置条件**：
- [ ] 端点用途明确（供处理端回取附件），材料目录范围明确

**③ 操作步骤**：
1. 令牌校验 → 预期：无令牌请求一律拒 → 判定信号：实测无令牌请求返回拒绝。
2. 目录白名单 → 预期：只允许取材料目录下的文件 → 判定信号：请求目录外文件被拒。
3. 大小上限 → 预期：超限文件拒取 → 判定信号：构造超限请求被拒。
4. 防路径逃逸 → 预期：路径规范化后校验仍在白名单内（含 ../ 类构造）→ 判定信号：逃逸用例被拒。
5. 四项实测全过才宣布建成 → 判定信号：测试记录逐项在案。

**④ 失败分支**：
- 任一实测不过 → 定因：防护未落地 → 处置：修好重测，期间端点下线或只绑回环 → 停手线：不以「内网地址、应该没事」免检上线。
- 业务嫌校验麻烦想开口子 → 处置：口子不开，改优化令牌分发方式 → 该端点的权限实质是「任意读全体材料」，被扫到就是整体泄漏。

**⑤ 验收清单**：
- [ ] 无令牌被拒、逃逸被拒两项决定性测试通过（证据：测试记录）
- [ ] 白名单与上限配置可查（证据：配置）

**⑥ 禁忌与易错点**：「只是内部用」式偷工；端点只绑回环时风险面减小，但令牌与白名单仍建议保留（防本机其他进程与误配置）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 单文件大小上限 | 25MB | 配置值 |
| 校验项 | 令牌＋白名单＋上限＋防逃逸，缺一不可 | 实测（基线） |

### 【图片回发三参数坑】

**① 目标与适用场景**：图片发送「回执成功但对方看不见」的定位与修复：逐字段对照真实入站报文修，不凭空加字段。本条给得出三个参数的**正确形态**（类别级，见⑦）——照形态对；但给不出你那家协议的真实字段名与取值，数值必须照金标准报文自取。形态与数值两样齐了才算照着做对，只对一样照样翻车。

**② 前置条件**：
- [ ] 手里有一条真实入站的同类（图片）消息原始报文作金标准（没有先按【镜像实验的前置条件】取样本）

**③ 操作步骤**：
1. 取金标准 → 预期：拿到真实入站图片报文全字段 → 判定信号：报文字段清单完整。
2. 逐字段比对出站报文 → 预期：列出全部差异点。本标本三处：媒体类型编号用错、缩略图开关沿用了文件类型口径、消息体缺明文长度字段 → 判定信号：差异清单逐项可指。
3. 逐个修正验证 → 预期：一次改一处、每改一处发一条实测 → 判定信号：对方端可见才算该处修对；三处全改后对方可见即闭环。
4. 结论回写 → 预期：把正确字段口径记入发送端规范 → 判定信号：规范文件更新。

**④ 失败分支**：
- 逐字段全对齐仍不可见 → 定因：问题不在字段层（可能是媒体上传/加密段）→ 处置：把分段法向上传段延伸 → 停手线：不再在字段层反复猜改。
- 没有金标准样本 → 处置：先取样本再动手 → 凭文档印象加字段只会引入新差异，越修越乱。

**⑤ 验收清单**：
- [ ] 对方端真实可见（证据：对方确认，第三级证据）
- [ ] 正确字段口径已回写规范（证据：规范文件）

**⑥ 禁忌与易错点**：这类协议出站校验松、参数错也给回执成功，把校验责任全推给接收端渲染——「发送成功」与「对方可见」之间隔着一整层参数正确性；文档与实测报文冲突时以报文为准。

**⑦ 参数表**：
| 坑点 | 错误形态 | 正确形态（机制级；字段名与取值照金标准报文自取） |
|---|---|---|
| 媒体类型编号 | 沿用了文件类（或文本类）消息的类型号 | 图片类消息有自己专属的类型号，与文本/文件/语音各号独立——出站必须填图片类的号，值以真实入站图片报文中的原值为准，禁止借用其他媒体类的号顶替 |
| 缩略图开关 | 沿用文件类型口径（关着，或不带缩略图信息） | 按图片类口径置于「带缩略图」一侧：出站同时携带缩略图信息，接收端靠它渲染预览；只发原图数据、缩略图缺位，端上就可能一片空白 |
| 明文长度字段 | 缺失（只带了密文/载荷长度，或干脆不带） | 消息体须显式带明文长度字段，值为加密前明文字节数；接收端用它作校验与渲染依据——缺了它，回执照样成功、端上就是不显示 |

以上为实测标本；换协议须重新对照，不可平移数值。

### 【原生语音泡协议定性·整类拒绝】

**① 目标与适用场景**：对「能否发出原生语音消息」做协议级定性：网关按机器人身份整类拒绝出站语音项——不是参数不对，是这一类整体不收。结论成立后资源转投退路与兜底，不再空耗。

**② 前置条件**：
- [ ] 能构造多组参数组合的出站语音发送实验
- [ ] 能拿到一条对方本人入站的真语音作原样重发样本
- [ ] 实验对象符合【不拿用户本人账号做实验】与试发预授权纪律

**③ 操作步骤**：
1. 参数组合穷试 → 动作：按研究规范试满五组参数组合 → 预期：上传环节全部通过、发送环节全部被拒且错误一致 → 判定信号：错误形态不随参数变化＝问题不在参数层。在自家通道上复现本实验时，先核对⑦的现象签名是否对得上（上传过、发送拒、错误不随参数变），签名不符就是另一种现象，不许套本条结论。
2. 决定性实验 → 动作：把对方本人入站真语音按原字节、原参数重发回给他 → 预期：仍被拒 → 判定信号：「某个字段不对」的单字段假设作废。
3. 下定性结论 → 预期：结论写明「协议层整类拒绝；该协议下实时语音通话同样不可能」，附两步证据链归档 → 判定信号：结论可复核（实验记录齐全）。

**④ 失败分支**：
- 五组未试满就想下结论 → 定因：证据不足 → 处置：补满规范组数 → 停手线：组数未满只许报「暂未通」，不许报「整类拒绝」。
- 某组参数错误形态发生变化 → 定因：参数层仍有文章 → 处置：顺变化点继续探，不下整类结论 → 结论强度不许超过证据强度。

**⑤ 验收清单**：
- [ ] 五组参数实验记录齐全（证据：实验日志）
- [ ] 原样重发实验记录在案（证据：实验日志）
- [ ] 定性结论与证据链归档（证据：结论文件）

**⑥ 禁忌与易错点**：没有定性就在语音参数上无限打转（一轮轮猜字段、每轮都「差一点」）；把本结论平移到其他协议（换协议必须重新实验，但「参数全败＋错误不变＋原样重发亦败」这套实验设计可整体迁移）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 参数组合试满 | 5 组 | 实测（研究规范） |
| 上传环节 | 全部通过 | 实测 |
| 发送环节 | 全部被拒、错误一致 | 实测 |
| 原样重发 | 仍被拒 | 实测（决定性实验） |
| 被拒现象签名（比对用） | 上传环节全部通过；发送环节返回绑定层拒收类结果——结果码与 ret=-2 同类形态、错误原文五组全同且不随任何参数变化；连对方本人入站真语音的原样重发也被同一形态拒回。自家通道上先对签名：签名一致，才可引用本条定性；签名不一致，按未知现象另行实验 | 实测 |

### 【语音攻关路线纪律】

**① 目标与适用场景**：退路形态被用户否决（音频当文件发太僵硬）且禁止换桥架构时，语音出站只剩协议内攻关一条路：捕获—镜像法。把「最后一种可能」验证到底，然后干脆结案。

**② 前置条件**：
- [ ] 约束条件已确认（否决的形态、禁止的架构变更，白纸黑字）
- [ ] 【原生语音泡协议定性·整类拒绝】的结论已成立（散试参数已被排除）
- [ ] 镜像前置条件可满足（见下条）

**③ 操作步骤**：
1. 埋点捕获 → 预期：记录真实入站语音项的原始结构 → 判定信号：捕获样本字段完整（见下条流程）。
2. 逐字段复刻 → 预期：出站报文与样本逐字段一致，只替换为新上传音频的加密参数 → 判定信号：字段 diff 只剩加密参数一处。
3. 回发同一人验证 → 预期：发回样本提供者本人 → 判定信号：对方可见可听＝通；被拒＝进第 4 步。
4. 结案或转正 → 预期：镜像也失败即协议层结案，结论与证据归档；成功则按新能力流程转正 → 判定信号：状态口径更新（见【退路被用户否决也是结论】的清场纪律）。

**④ 失败分支**：
- 攻关中有人想再散试参数组合 → 定因：已被定性排除的路线 → 处置：拒绝，资源只投镜像一条线 → 停手线：不给用户「还在多路努力」的虚假希望。
- 镜像失败后仍想无限攻关 → 处置：按结案处理，协议变更时凭证据链再判断是否重启 → 不无限攻关是硬纪律。

**⑤ 验收清单**：
- [ ] 字段 diff 记录在案（证据：对照表）
- [ ] 结案/转正结论成文（证据：结论文件）

**⑥ 禁忌与易错点**：约束把解空间压到一条线时在线外乱试；结案结论不写证据链（日后无从判断协议变化是否值得重启）。

**⑦ 参数表**：无固定参数；实验组数与定性规范见上条。

### 【镜像实验的前置条件】

**① 目标与适用场景**：镜像法能否做取决于系统是否留存原始入站报文。只存归一化结果的系统没有可复刻的原件，须先埋抓取补丁、等真实样本触发、实验后撤补丁。

**② 前置条件**：
- [ ] 已查清当前留存现状（原始报文是否落盘、留存多久）
- [ ] 抓取补丁的上线与撤销都有留痕安排（属生产改动）

**③ 操作步骤**：
1. 查留存 → 预期：确认原始报文字段有无落盘 → 判定信号：留存清单明确。
2. 无留存先埋点 → 动作：上线原始抓取补丁，只抓结构与字段、不扩留存范围 → 预期：补丁运行且不影响主链路（旁路原则见【新能力旁路接入不动主服务】）→ 判定信号：补丁日志正常、主链路无异常。
3. 等真实样本 → 预期：有真实用户发来语音时样本落袋 → 判定信号：样本字段完整可复刻。
4. 实验后撤补丁 → 预期：样本到手、实验做完即撤，恢复常规留存口径 → 判定信号：撤销记录在案（原始报文含敏感参数，不长期留存）。

**④ 失败分支**：
- 长期等不到真实样本 → 定因：触发条件未至 → 处置：保持埋点、在能力台账标「待实测」如实汇报 → 停手线：不用合成样本冒充真实样本下结论（合成样本可验链路，不可验协议定性）。
- 有人主张没样本先改发送端 → 处置：拒绝，顺序不可反（没样本改的全是猜测）→ 先埋点、等样本、再实验、后撤点是唯一稳妥节奏。

**⑤ 验收清单**：
- [ ] 留存现状清单在案（证据：清单）
- [ ] 补丁上线/撤销均有留痕（证据：变更记录）
- [ ] 样本按最小留存处理（证据：留存记录）

**⑥ 禁忌与易错点**：样本窗口错过又要等不知多久，所以埋点要早；抓到的样本长期留存（敏感参数扩散）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 样本来源 | 真实入站流量，不用合成样本定性 | 实测（纪律） |
| 补丁留存期 | 实验完成即撤 | 实测（纪律） |

### 【退路先行验证】

**① 目标与适用场景**：主路未通时先把退路（TTS 合成＋音频文件附件发送）端到端验证到回执成功，并摸清退路毛病写进生产代码。

**② 前置条件**：
- [ ] 退路链路组件齐备（合成、附件发送）
- [ ] 有真实接收方验证可见可听

**③ 操作步骤**：
1. 端到端实发 → 预期：真实发送一条合成语音附件 → 判定信号：回执成功且对方可听（第三级证据）。
2. 摸毛病 → 预期：多次实发记录退路已知问题（如合成偶发无音频失败）→ 判定信号：毛病清单成文。
3. 毛病进代码 → 预期：发送前检测音频非空、失败自动重试一次，不许把空音频发出去 → 判定信号：构造空音频样本，代码拦截并重试。

**④ 失败分支**：
- 退路也验不通 → 定因：能力整体缺失 → 处置：如实把状态口径改为「语音出站无可用路径」，资源转回主路攻关或读侧兜底 → 停手线：不拿未验过的退路安慰任何人。
- 退路被正式采用后毛病复发 → 处置：按毛病清单逐项对症，新增毛病补进清单与代码 → 清单是活的。

**⑤ 验收清单**：
- [ ] 退路实发＋对方可听证据在案（证据：发送与确认记录）
- [ ] 已知毛病均有代码级防护（证据：构造样本测试）

**⑥ 禁忌与易错点**：兜底时刻才发现退路没验过，等于没有退路；退路的毛病清单还有个附带价值——它决定主路攻关值不值得继续（退路到底有多难用）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 合成失败重试 | 自动 1 次 | 实测 |
| 空音频发送 | 禁止（发送前检测非空） | 实测（纪律） |

### 【退路被用户否决也是结论】

**① 目标与适用场景**：退路被用户明确否决（如文件式语音「太生硬、不合理」）后，按定案处理：改写状态口径、清场所有引用它的待办，不再反复端出来。

**② 前置条件**：
- [ ] 否决的粒度已听准（否的是这个形态，还是这个能力本身）

**③ 操作步骤**：
1. 标定案 → 预期：状态文档把该退路标「已否决」并注明理由 → 判定信号：状态口径更新。
2. 连带清场 → 预期：清查所有引用它的待办、排队消息、计划条目，一并删除或改写 → 判定信号：全文检索无残留引用（排队中的相关确认问句一并删）。
3. 汇报除名 → 预期：后续汇报不再把它列为「可选方案」→ 判定信号：汇报模板/清单已更新。

**④ 失败分支**：
- 日后在某条队列里又冒出该方案 → 定因：清场不彻底 → 处置：立即删除并复查同类残留 → 停手线：未清净前不发送含该问句的队列内容。
- 用户日后主动重提 → 处置：按新决定重启评估，这是新决定不是旧方案复活 → 在记录里分清。

**⑤ 验收清单**：
- [ ] 状态口径已改（证据：状态文档）
- [ ] 引用清场检索为零（证据：检索记录）

**⑥ 禁忌与易错点**：把否决当「暂缓」——幽灵方案会在队列与计划里反复出现，每次都消耗用户的决策耐心，也显得你没在听。否决即结论、结论即清场；但别扩大化清场（否形态不等于否能力）。

**⑦ 参数表**：无参数。

### 【ASR 兜底链·无转写语音三级兜底】

**① 目标与适用场景**：平台不给转写时用本地离线 ASR 读语音，三级依次降级：一级本地离线 ASR 脚本、二级转写技能、三级请对方补文字要点。任何一级失败不卡死答复。离线形态同时满足业务数据不出境红线。注意一级不是单个工具，是两条规程拼起来的完整链：解码段见【SILK 解码自编译·先小样本验证】、引擎段见【转写引擎实测指标定选】——单读本条走不通第一步，先把那两条落地再谈兜底链。

**② 前置条件**：
- [ ] 一级链路已在本机与服务器双侧验证过（解码＋转写全链，见下条）
- [ ] 状态口径分开记「链路就绪」与「首个真实样本验证」

**③ 操作步骤**：
1. 一级尝试 → 动作：语音落盘后走本地离线 ASR → 预期：出文本 → 判定信号：文本非空且可读。
2. 失败降二级 → 预期：调用转写技能再试 → 判定信号：出文本即停降级。
3. 再失败降三级 → 预期：正常回复对方「这条语音没读出来」，请其重发或补文字要点 → 判定信号：回复里明示未读出，不沉默丢失。
4. 用转写结果答复 → 预期：涉人名/数字/日期按【转写复述确认与同音字复核】处理 → 判定信号：关键信息已复核或已向本人复述确认。

**④ 失败分支**：
- 链路在合成样本上通、真实语音全乱 → 定因：就绪≠实证（方言、噪声、长语音是另一回事）→ 处置：状态降回「就绪待实证」，收集真实失败样本补进选型样本集（见【转写引擎实测指标定选】）→ 停手线：不拿合成样本成绩汇报「已验证」。
- ASR 进程拖垮弱算力机器 → 定因：与其他模型同载抢内存 → 处置：串行运行、排队处理 → 见下条运行纪律。

**⑤ 验收清单**：
- [ ] 双侧（本机＋服务器）全链验证记录（证据：验证记录）
- [ ] 状态台账区分就绪/实证（证据：台账）
- [ ] 三级全败的回复样本存在（证据：会话样本）——从无降级记录往往意味着在硬撑

**⑥ 禁忌与易错点**：单点方案（每一环都有失败率，单点必然时灵时不灵）；把「链路就绪」汇报成「已实证」是自己骗自己。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 兜底级数 | 3 级 | 实测 |
| 部署形态 | 本地离线，数据不出本机/自有服务器 | 实测（红线） |
| 运行纪律 | 弱算力环境串行运行，不与其他模型同载 | 实测 |

### 【SILK 解码自编译·先小样本验证】

**① 目标与适用场景**：该生态语音为 SILK 格式、无官方解码器时，自编译开源解码器接入转写链。解码器类别：社区维护的开源 SILK 解码实现（只用其解码端），自行编译、版本留档——不要去找「官方解码器」，它不存在正是本条的前提。顺序不可颠倒：先小样本全链验证，再接入生产。

**② 前置条件**：
- [ ] 有一条真实语音小样本
- [ ] 构建环境可编译，且构建脚本与版本可留档复现

**③ 操作步骤**：
1. 编译解码器 → 预期：得到可用的 SILK 解码二进制/库 → 判定信号：编译产物可运行。
2. 先判帧头变体 → 动作：查样本文件头形态——原始 SILK 流以固定帧头魔数开头；该生态导出的语音文件常见在帧头前多挂一个前缀字节（变体），整流直接喂解码器必然全程噪声或立即报错。检出前缀字节的先剥离再解码；两种形态各留一个样本作回归 → 判定信号：剥离后解码出的音频可听辨、内容对得上。
3. 小样本全链验证 → 动作：真实样本走「解码→转 WAV→ASR 转写」→ 预期：亲眼看到正确文本出来 → 判定信号：文本内容与样本语音一致。
4. 收成一条命令 → 预期：全链封装为单命令调用 → 判定信号：一条命令端到端出文本。
5. 双侧一致才接入 → 预期：本机与服务器各跑同一样本，结果一致 → 判定信号：双侧记录对照无差异。

**④ 失败分支**：
- 解码出音频但转写全是垃圾 → 定因：采样率/帧头/声道某一处不对 → 处置：逐环对账（解码输出参数 vs ASR 输入要求）→ 停手线：不先集成再排查（集成后查不出错在哪环）。
- 解码直接报错或全程噪声 → 定因：多半是帧头变体未剥离（见③第 2 步），其次才轮到解码器编译问题 → 处置：先回第 2 步判形态，不许一上来就怀疑解码器、重编一遍。
- 换机器解码器不可用 → 定因：靠某台机器的现成二进制、无构建留档 → 处置：补构建脚本与版本记录重建 → 不允许「只有那台机器能跑」的状态长期存在。

**⑤ 验收清单**：
- [ ] 小样本全链文本正确（证据：样本与文本对照）
- [ ] 双侧一致记录（证据：双侧验证记录）
- [ ] 构建脚本与版本留档（证据：留档文件）

**⑥ 禁忌与易错点**：先集成后验证；只验解码不验转写（每一环的正确性要一次钉死）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 全链耗时 | 短语音约 3 秒出文本（秒级） | 实测 |
| 接入标准 | 小样本全链通＋双侧一致 | 实测（口径） |
| 帧头变体 | 原始帧头／帧头前多一个前缀字节，共 2 类，先判形态后解码 | 实测 |
| 采样率对齐 | 解码输出采样率须与 ASR 输入要求一致，不一致先重采样再转写 | 实测（口径） |

### 【转写引擎实测指标定选】

**① 目标与适用场景**：ASR 引擎选型不用宣传参数，用实测三件套定选：字错率、实时率、内存。样本集须覆盖真实分布。

**② 前置条件**：
- [ ] 样本集齐备：清晰语音、远场衰减、带噪环境、人名地名密集句（官方样本＋自制衰减/噪声样本）
- [ ] 候选引擎清单与版本固定（同版本比才公平）；候选入围门槛先卡死：可本地离线部署的开源引擎才入围，云端 API 类不入围（业务数据不出境红线，见【ASR 兜底链·无转写语音三级兜底】）

**③ 操作步骤**：
1. 逐引擎跑全样本集 → 预期：每引擎得三项指标 → 判定信号：指标表逐格有实测值，无「据称」。
2. 按场景定选 → 预期：以真实分布加权（噪声与衰减样本权重不低于清晰样本）选定主引擎 → 判定信号：选型结论附指标表。
3. 定运行纪律 → 预期：弱算力环境串行运行、不与其他模型同载写入部署配置 → 判定信号：配置可查。
4. 样本集持续补充 → 预期：真实失败案例逐个补进样本集，选型定期重估 → 判定信号：样本集有增补记录。

**④ 失败分支**：
- 宣传最优的引擎实测垫底 → 定因：厂商硬件与样本与你的环境隔着鸿沟 → 处置：按实测结论选，不向宣传低头 → 选型选错的代价是整条兜底链上线后才暴露不可用。
- 两引擎指标接近 → 处置：以人名密集句字错率决胜（业务最不能错的就是人名）→ 不凭感觉拍。

**⑤ 验收清单**：
- [ ] 指标表三项齐全且为实测（证据：指标表）
- [ ] 选型结论与指标表对应（证据：选型记录）

**⑥ 禁忌与易错点**：看宣传参数选型；样本集只有清晰语音（真实语音的狼狈样全在衰减与噪声里）；选型一劳永逸。

**⑦ 参数表**：
| 指标 | 含义 | 性质 |
|---|---|---|
| 字错率 | 准不准 | 实测 |
| 实时率 | 处理时长/音频时长，快不快 | 实测 |
| 内存占用 | 跑不跑得动 | 实测 |
| 样本构成 | 清晰＋衰减＋噪声＋人名密集 | 实测（口径） |
| 合格线（判定口径） | 实时率须 <1（快于实时）才撑得住兜底链的时延；内存须能与主服务同机共存、上限按自家机器余量定；字错率：普通句以「大意可读」为底线、人名密集句以「关键人名不错」为硬线。三线任一不过即不选；具体量级按自家样本实测校准，不许拿宣传参数填 | 示意（判定口径） |

### 【转写复述确认与同音字复核】

**① 目标与适用场景**：转写结果的使用纪律：人名、地名、数字、日期易同音误识，长句错字集中在人名同音字。涉人名的转写必须人工复核再用，关键信息向本人复述确认。

**② 前置条件**：
- [ ] 转写结果进入材料/台账前有复核环节（流程上存在，不是靠自觉）

**③ 操作步骤**：
1. 涉人名先复核 → 预期：拿名册/上下文比对转写中的人名，不直抄 → 判定信号：复核过的人名有对照依据。
2. 关键信息复述确认 → 预期：答复要用到人名、日期、数字时，向发送者本人复述一遍请其确认 → 判定信号：确认往返记录在会话里。
3. 分寸 → 预期：复述是业务动作，不把「转写供参考」之类技术免责话术发给对方 → 判定信号：回复文本无免责话术（复核责任在己侧）。

**④ 失败分支**：
- 同音误识已写进台账 → 定因：复核缺位 → 处置：当轮更正台账、追溯引用了该条的下游材料一并改 → 停手线：未溯改完不宣称已纠正。
- 本人确认时改口给了新值 → 处置：以本人确认为准更新，并记转写误识样本补进选型样本集 → 不与对方争「语音里明明是这么说的」。

**⑤ 验收清单**：
- [ ] 涉人名台账条目均有复核依据（证据：抽查）
- [ ] 复述确认往返样本存在（证据：会话抽查）

**⑥ 禁忌与易错点**：同音误识的特点是读起来通顺、实际是错的，不复核根本发现不了；它错的位置（人名、数字）恰是材料里最不能错的位置——半句话的复述成本 vs 整份材料的公信力，不必权衡。

**⑦ 参数表**：无参数。纯闲聊语境可适当放宽，涉及记录、台账、转办一律执行。

### 【视频看不了直说给替代路径】

**① 目标与适用场景**：通道处理不了视频（或某类输入）时，直说看不了并给替代路径，不装作已看。适用于一切能力未及的输入类型。

**② 前置条件**：
- [ ] 已确认该类型当前确实不可处理（不是没试过就说不能）

**③ 操作步骤**（通用步骤）：
1. 明示边界 → 预期：一句话说清「视频我这边暂时看不了」→ 判定信号：回复含明确边界表述。
2. 给替代路径 → 预期：列两三个具体选项（发文字要点、发语音、把文件发来）→ 判定信号：选项可操作，不是「你想想办法」。
3. 已收部分先落盘 → 预期：视频先存好，告知日后能力补上可回看 → 判定信号：落盘记录与告知一致。

**④ 失败分支**：
- 已用「好的我看看」拖着 → 定因：边界沟通缺失 → 处置：当轮补明示与替代路径 → 停手线：绝不基于没看的内容编造答复（对方会基于「他看了」继续推进，之后全建在虚构上）。
- 替代路径对方都做不到 → 处置：请其转述要点或分段截图按图片处理 → 给足路径，不让事项死在格式上。

**⑤ 验收清单**：
- [ ] 不可处理类型的回复均含边界＋替代（证据：会话抽查）
- [ ] 无基于未看内容的具体答复（证据：抽查）

**⑥ 禁忌与易错点**：装作看过是最坏选项；用户对「明确说不行并给替代路」的接受度远高于「好像行其实不行」。

**⑦ 参数表**：无参数。本条为通用方法条目。

### 【新能力旁路接入不动主服务】

**① 目标与适用场景**：新能力（如 ASR 兜底）先以观察者/兜底方式旁路接入：不改主服务代码、不重启主服务，风险隔离在增量里。

**② 前置条件**：
- [ ] 旁路接入点选在主流程之外（如独立进程监听同一份落盘数据、在主答复缺转写时补结果）
- [ ] 回滚方式已想好（停掉旁路进程即恢复原状）

**③ 操作步骤**：
1. 旁路部署 → 预期：新能力独立进程运行，主服务零改动零重启 → 判定信号：主服务启动时间未变、代码无 diff。
2. 旁路供数 → 预期：主流程需要时取旁路结果（如缺转写时补转写）→ 判定信号：补数记录可见。
3. 真实样本验证 → 预期：经真实流量验证稳定后，再评估是否并入主链路 → 判定信号：验证记录区分就绪/实证（同 ASR 口径）。
4. 转正走正式变更 → 预期：并入主链路时按备份与验证流程办 → 判定信号：变更记录齐全，不许「旁路跑久了就算转正」。

**④ 失败分支**：
- 旁路出故障 → 定因：风险已被隔离 → 处置：停旁路即回滚，主服务不受影响 → 停手线：不在主服务里给旁路打补丁（那就不是旁路了）。
- 旁路与主链路结果冲突（如两份转写不一致） → 处置：以主链路为准、旁路结果只作参考并记冲突样本 → 不让实验结果污染正式答复。

**⑤ 验收清单**：
- [ ] 主服务零改动零重启证据（证据：启动时间＋代码 diff）
- [ ] 回滚演练或停旁路验证做过一次（证据：记录）

**⑥ 禁忌与易错点**：为上一个尚待验证的新能力去改、去重启服务几十人的命脉的主服务——成了多一项能力，败了全体可用性陪葬。

**⑦ 参数表**：无参数。

## 第七章 守候队列

### 【每分钟守候轮询与空轮静默】

**① 目标与适用场景**：桥的应答引擎形态：守候任务周期拉取待答列表逐条处理，空轮静默结束，只有异常才上报。

**② 前置条件**：
- [ ] 待答列表接口/文件可周期拉取
- [ ] 「异常」的上报阈值事先定义（网关错误、队列文件损坏等），免得执行者忽宽忽窄

**③ 操作步骤**：
1. 拉列表 → 预期：得本轮待答条目 → 判定信号：拉取结果记录（含条数）。
2. 逐条处理 → 预期：按判重、锁定等规则处理（见本章各条）→ 判定信号：每条有去向。
3. 空轮静默 → 预期：无待答即结束，不发任何「本轮无事」消息，只在日志留计数 → 判定信号：用户侧无空轮噪音。
4. 异常才上报 → 预期：网关错误等异常按阈值上报 → 判定信号：上报记录与异常对应。

**④ 失败分支**：
- 拉取本身报错 → 定因：网关或凭据问题 → 处置：记错误日志并按异常上报，本轮不硬试 → 停手线：不把拉取失败当空轮（会掩盖通道已死）。
- 待答积压过多一轮处理不完 → 处置：按优先级先答新近与急件，其余留下轮，积压量进日志告警 → 不为清积压突破发送节流。

**⑤ 验收清单**：
- [ ] 空轮无用户侧消息（证据：发送记录）
- [ ] 异常上报与日志一致（证据：对照记录）

**⑥ 禁忌与易错点**：空轮也汇报（每分钟一条噪音，几天就把重要消息淹没）；把用户的注意力当稀缺资源保护，静默不是偷懒。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 轮询周期 | 每分钟一轮 | 实测 |
| 空轮上报 | 不上报（静默） | 实测（纪律） |

### 【守候心跳先行且失败不阻断】

**① 目标与适用场景**：守候可观测性：每轮第一步先给外部监控打心跳，心跳失败不阻断主流程；监控据心跳独立判断守候死活。

**② 前置条件**：
- [ ] 外部监控系统可接收推送型心跳（如自托管监控的 Push 监测项）
- [ ] 监控侧告警阈值已配（缺数轮心跳即告警）

**③ 操作步骤**：
1. 心跳先行 → 预期：每轮第一步打点成功 → 判定信号：监控侧收到时间戳更新。
2. 心跳失败不阻断 → 预期：打点失败只记日志，本轮照常拉列表处理 → 判定信号：心跳失败轮次的待答仍被处理。
3. 监控独立判断 → 预期：守候死活由监控按心跳缺失裁定，不靠守候自报 → 判定信号：停掉守候做演练，监控在阈值内告警。

**④ 失败分支**：
- 心跳持续失败但守候在干活 → 定因：监控通道问题 → 处置：修监控通道，期间以日志人工核守候存活 → 停手线：不因心跳失败重启守候（可观测性不能成为新单点故障）。
- 监控误报守候已死 → 处置：先查守候日志再定性（见【消失条目先查证再定性】同理）→ 不凭告警直接重启。

**⑤ 验收清单**：
- [ ] 停机演练告警在阈值内到达（证据：演练记录）
- [ ] 心跳失败轮次主流程不受影响（证据：日志对照）

**⑥ 禁忌与易错点**：靠守候自报「我还活着」判断死活（它死了不会发遗言，逻辑上不成立）；心跳阻断主流程（监控故障反过来拖死守候）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 心跳频次 | 每轮一打（随轮询周期，分钟级） | 实测 |
| 告警阈值 | 缺数轮心跳即告警（按周期配） | 示意 |

### 【通道令牌只读本地不入日志】

**① 目标与适用场景**：凭据纪律：守候与网关通信的通道令牌只从本地凭据文件读取，绝不写进任何日志、回复或报告。本条仅方法可写，无实例。

**② 前置条件**：
- [ ] 令牌存放于本地凭据文件，权限收敛（只有运行身份可读）
- [ ] 日志代码可控（能做字段排除）

**③ 操作步骤**：
1. 单一读取路径 → 预期：代码中令牌只经一条路径进内存 → 判定信号：代码走查无第二处读取/硬编码。
2. 日志整体排除 → 预期：日志语句对含令牌的字段整体排除，不打片段不打哈希前缀 → 判定信号：全量日志检索无令牌形态字符串。
3. 指代口径 → 预期：汇报排障只说「本地令牌文件」，不贴值 → 判定信号：报告抽查无令牌痕迹（同【巡检 403 误报】口径）。

**④ 失败分支**：
- 发现令牌已写进某份日志/报告 → 定因：排除失效 → 处置：该载体按泄漏处理（清理或销毁副本、评估轮换令牌），并修排除逻辑 → 停手线：未清理前该日志不外传。
- 排障协作者索要令牌值 → 处置：拒绝经聊天/文档转手，请其走凭据文件本身 → 任何人看令牌都走凭据文件一处。

**⑤ 验收清单**：
- [ ] 日志全量检索无令牌（证据：检索记录）
- [ ] 代码读取路径唯一（证据：走查记录）

**⑥ 禁忌与易错点**：日志与报告会被转发、归档、多人经手，令牌写进去等于发给所有未来读者且无法收回；凭据暴露面必须收敛在凭据文件一处。

**⑦ 参数表**：无参数。本条为通用方法条目。

### 【已答名单加时间窗双重判重·幂等】

**① 目标与适用场景**：守候应答幂等：同一请求多路重复到达只答一次，靠已答 ID 名单＋时间窗双重判重。多通道、多兜底系统必备。

**② 前置条件**：
- [ ] 每条请求有稳定 ID
- [ ] 已答名单可持久化登记

**③ 操作步骤**：
1. 处理前查名单 → 预期：ID 在已答名单里直接跳过 → 判定信号：跳过有日志。
2. 再查时间窗 → 预期：同 ID 在去重窗内出现过且已处理，同样跳过（防名单写入前的并发重达）→ 判定信号：窗口判定有记录。
3. 答复成功立即登记 → 预期：ID 入已答名单 → 判定信号：登记时点紧随发送成功。
4. 双重缺一不可 → 预期：名单防长期重达、时间窗防并发重达 → 判定信号：构造两类重复到达各测一次，均只答一次。

**④ 失败分支**：
- 仍出现重复答复 → 定因：判重某一道失效（名单未落盘/窗口太短/登记滞后）→ 处置：按构造测试定位失效道 → 停手线：未修复前对重复高发通道人工盯防。
- 判重误杀（新请求被当重复跳过） → 定因：ID 碰撞或窗口过长 → 处置：核对 ID 生成唯一性、回调窗口 → 被误杀的请求按原内容补答并说明。

**⑤ 验收清单**：
- [ ] 两类重复到达构造测试各只答一次（证据：测试记录）
- [ ] 无误杀记录（证据：跳过日志抽查）

**⑥ 禁忌与易错点**：重复答复是实打实的骚扰（同问两答、措辞还可能不同，信任立刻打折）；幂等必须建在入口，不指望上游不重复。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 去重时间窗 | 20 分钟 | 实测 |
| 判重构成 | 已答 ID 名单＋时间窗，双重 | 实测 |

### 【锁定请求不答由兜底按原内容送达】

**① 目标与适用场景**：待答列表中被标记锁定的条目，守候跳过不答、不改内容、日志注明原因，等通道条件恢复由兜底扫尾按原内容送达。属既定状态，不是异常。

**② 前置条件**：
- [ ] 锁定标记的设立与解除权限收敛（不许执行者自行锁定/解锁）
- [ ] 兜底扫尾能识别锁定条目的送达条件

**③ 操作步骤**：
1. 识别锁定 → 预期：处理前查条目标记 → 判定信号：锁定条目被单独分出。
2. 只做三件事 → 预期：日志记「锁定跳过」及原因、原样保留条目、不替答不删除不改一字 → 判定信号：条目内容与日志均可查。
3. 条件恢复后兜底送达 → 预期：兜底按原内容发出、回执成功才销项 → 判定信号：送达记录与原内容一致。

**④ 失败分支**：
- 守候「好心」替答了锁定条目 → 定因：破坏既定安排（如通道受限对象的既定回复）→ 处置：如实记录、评估影响、把锁定检查前置为硬门 → 停手线：未加硬门前该类条目人工复核。
- 锁定条目长期无人送达 → 处置：先查日志再定性（可能已被兜底办结，见【消失条目先查证再定性】）→ 不凭队列界面印象判丢失。

**⑤ 验收清单**：
- [ ] 锁定条目跳过均有日志（证据：日志抽查）
- [ ] 送达内容与原内容逐字一致（证据：对照记录）

**⑥ 禁忌与易错点**：顺手删除锁定条目（内容永久丢失）；把锁定跳过当异常告警（它是既定状态）；锁定标记权限放开（人人可锁等于队列可被任意冻结）。

**⑦ 参数表**：无参数。

### 【pending 孤儿成因】

**① 目标与适用场景**：队列卡死故障的成因解剖：答复已生成，但投递进程在等待期间被重启杀死，完成回执永不发出，待办项永不删除——这类条目称孤儿。处置见下条，本条负责让设计者预设「回执永不来」。

**② 前置条件**：
- [ ] 已摸清本系统的销项衔接方式（谁发回执、谁删待办）

**③ 操作步骤**：
1. 画衔接链 → 预期：写清生成→投递→回执→销项四段与各段责任进程 → 判定信号：衔接图成文。
2. 标死亡点 → 预期：指出「回执发送者若在回执前死亡，衔接即断且无人发现」 → 判定信号：风险点在图上标明。
3. 结论入设计评审 → 预期：凡「两段靠回执衔接」的流程，评审必问孤儿兜底 → 判定信号：评审清单含此问。

**④ 失败分支**：
- 已出现孤儿（条目反复被拉起又跳过） → 定因：按成因链核对（投递进程重启记录与条目时间吻合）→ 处置：转下条扫尾机制处理，并人工先行补投该条 → 停手线：不把孤儿当新故障一遍遍重新排查。
- 衔接链画不清 → 处置：先补各段日志再谈治理 → 无衔接图不开工改队列。

**⑤ 验收清单**：
- [ ] 衔接图与死亡点标注在案（证据：设计文档）
- [ ] 孤儿有独立兜底（证据：下条扫尾在运行）

**⑥ 禁忌与易错点**：孤儿的隐蔽性在于系统看起来一切正常——新请求照常处理，只有那一条永远躺着；没有孤儿概念的人每次翻到它都当新故障重查。推广：任何「等对方确认才销项」的设计，都要配「对方永远不确认」的兜底。

**⑦ 参数表**：无参数。

### 【孤儿扫尾设计·服务器端扫捡兜底】

**① 目标与适用场景**：上条的解法：服务器端周期扫捡已生成未送达的回复，通道恢复即自动送达，不靠人工盯。主通道管实时、兜底管捡漏，单点失效不丢件。

**② 前置条件**：
- [ ] 「完成文件」与「待办项」可对照（扫尾只信这组可核查事实）
- [ ] 有文件锁或等价机制防与主通道并发重叠

**③ 操作步骤**：
1. 筛超龄项 → 预期：只处理「完成文件已超龄且待办仍在」的项（超龄阈值确保不与正常投递抢跑）→ 判定信号：筛选条件成文。
2. 处理前复查 → 预期：复查条目当前状态，持文件锁防重叠 → 判定信号：锁记录存在。
3. 重试送达 → 预期：按原内容发出 → 判定信号：回执结果落盘。
4. 全成才销项 → 预期：全部回执成功才归档销项；任一步失败原样留待下轮，不半途销项 → 判定信号：销项记录与回执一一对应。

**④ 失败分支**：
- 扫尾与主通道并发发了同一条 → 定因：锁或超龄阈值失效 → 处置：立即回调阈值、查锁实现，并向收到重复者按【失败汇总对齐法】口径说明 → 停手线：防重未复验前暂停扫尾。
- 扫尾反复失败于同一条 → 定因：该条内容或对象状态有硬问题 → 处置：转人工定因，不让扫尾无限重试（防自制重试风暴，见【重试风暴退避止损】）→ 设尝试上限并告警。

**⑤ 验收清单**：
- [ ] 人为制造一个孤儿，扫尾一轮内捡起送达（证据：演练记录）
- [ ] 失败项原样保留、无半途销项（证据：队列对照）

**⑥ 禁忌与易错点**：扫尾不信任任何一段的自述，只看「完成文件在、待办也在、时间已超龄」这组事实；周期太勤与主通道抢跑、太懒则捡漏失去意义。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 超龄阈值 | 大于正常投递最长耗时，按业务时效配 | 待实测 |
| 销项条件 | 全部回执成功 | 实测（纪律） |
| 扫尾周期 | 与主轮询同级或数倍 | 示意 |

### 【守候日志只记元数据不记正文】

**① 目标与适用场景**：守候日志内容规范：只记请求 ID、用户标识、交付类型与时间，不写任何消息正文。可审计又不沉淀敏感内容。

**② 前置条件**：
- [ ] 日志字段白名单已定（与【失败日志记 errmsg·错误原文】的字段规范衔接：记平台错误，不记用户内容）

**③ 操作步骤**：
1. 字段白名单化 → 预期：日志写入只走白名单字段 → 判定信号：代码走查无正文字段。
2. 内容回看走正道 → 预期：需回看内容时去本人空间取材料本体，不靠日志还原 → 判定信号：排障流程如此写明。
3. 定期抽查 → 预期：抽日志验无正文混入 → 判定信号：抽查记录在案。

**④ 失败分支**：
- 发现正文已混入日志 → 定因：白名单被绕过（多为调试输出）→ 处置：清理该段日志、堵写入点 → 停手线：未堵前该日志不扩散（不转发、不归档到共享处）。
- 排障者抱怨没正文查不了 → 处置：给其本人空间的正规取数路径 → 不以排障为由开口子。

**⑤ 验收清单**：
- [ ] 日志抽查无正文（证据：抽查记录）
- [ ] 字段白名单成文（证据：规范文件）

**⑥ 禁忌与易错点**：正文进日志等于把全体用户的对话复制一份到防护等级低得多、经手人多得多处；日志规范要在写第一行日志代码前定，不要等堆成山再治理。

**⑦ 参数表**：
| 字段 | 记/不记 |
|---|---|
| 请求 ID、用户标识、交付类型、时间、成败、错误码与原文 | 记 |
| 消息正文 | 不记 |

以上为实测规范。

### 【守候只答复登记长活转主线】

**① 目标与适用场景**：守候职责边界：分钟级守候只做答复与登记；改服务器、改页面、改参数的长活一律登记转主线，不在守候里干。

**② 前置条件**：
- [ ] 「长活」界定已事先划线（按预计耗时与影响面），执行者不临场纠结
- [ ] 登记有承接处（主线待办清单）

**③ 操作步骤**：
1. 识别长活 → 预期：来信含改系统/改页面/改参数类需求即判长活 → 判定信号：判定依据对照划线标准。
2. 当轮只登记 → 预期：记下需求、回复对方「已登记、由主线跟进」，继续答下一条 → 判定信号：登记条目与回复都在案。
3. 主线排期实施 → 预期：长活在主线排期、实施、验证，与守候分钟节奏互不干扰 → 判定信号：主线待办有该条状态流转。

**④ 失败分支**：
- 守候已在长活里陷住一轮 → 定因：边界失效，后面排队者无人应答 → 处置：立即中断长活、转登记，先恢复应答 → 停手线：应答积压未清前不开新长活。
- 长活登记后主线石沉大海 → 处置：登记清单定期对账，未承接的升级提醒 → 登记不是丢弃的别名。

**⑤ 验收清单**：
- [ ] 守候单轮耗时无长活拖尾（证据：轮次耗时记录）
- [ ] 长活登记均有主线承接状态（证据：对账记录）

**⑥ 禁忌与易错点**：守候资源是全体共享的应答通道，一条长活堵一轮，后面所有人无人应答——职责边界表面是分工、实质是可用性保障。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 守候单轮职责 | 答复＋登记，仅此两项 | 实测（纪律） |
| 长活划线 | 按耗时与影响面事先定 | 待实测 |

## 第八章 回复体验与交付

### 【处理中回执】

**① 目标与适用场景**：「回复慢像掉线」投诉的机制解：回复超约 30 秒未完成，先发一条「收到，正在处理」的回执，消掉的是不确定性而非慢本身。

**② 前置条件**：
- [ ] 应答流程支持异步计时（处理未完可先发回执）
- [ ] 回执文案已定（只报状态、不承诺完成时间）

**③ 操作步骤**：
1. 计时触发 → 预期：入站处理超阈值未完成，自动发一条回执 → 判定信号：回执发送记录与该入站对应。
2. 每条入站最多一条 → 预期：同一入站不连发回执 → 判定信号：按入站计数≤1。
3. 回执失败不影响正文 → 预期：回执发送失败只记日志，正文照常处理发送 → 判定信号：失败日志与正文成功记录并存。
4. 反馈入台账 → 预期：慢回复类反馈记入反馈台账，按「一类反馈一个系统性修复」处理 → 判定信号：台账条目与本机制互相引用。

**④ 失败分支**：
- 阈值太短回执满天飞 → 定因：阈值未按用户感知校准 → 处置：上调阈值并观察投诉变化 → 停手线：回执本身成为打扰时先停回执再调。
- 回执发了正文迟迟不来 → 定因：处理真卡死 → 处置：按任务卡死处置，正文失败要给对方明确答复 → 不许用回执无限续命沉默。

**⑤ 验收清单**：
- [ ] 构造一次慢处理，回执按时单条到达（证据：构造测试记录）
- [ ] 回执失败不影响正文（证据：注入失败测试或真实记录）

**⑥ 禁忌与易错点**：靠道歉解一时情绪（机制解的是这一类问题从此不再发生）；回执里承诺完成时间（承诺不到又是一次失信）；用户怕的不是慢，是「不知道消息到没到、系统还活着没」。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 回执阈值 | 约 30 秒未完成即发 | 实测 |
| 每入站回执上限 | 1 条 | 实测（纪律） |
| 回执失败处置 | 只记日志，不影响正文 | 实测（纪律） |

### 【回复模态判断】

**① 目标与适用场景**：回复形态由助手按内容自判：短对话/确认/提醒或对方发语音时用语音；数字/清单/要核对复制的用文字；正式稿/台账/要打印签章归档的用文件；既讲解又留底的语音＋文件并行。

**② 前置条件**：
- [ ] 判断口径成文（不靠临场感觉）
- [ ] 已知本通道各模态的真实可达状态（如出站语音在某些协议下不可得，见语音章定性）

**③ 操作步骤**：
1. 按内容分类 → 预期：答复生成前先定模态 → 判定信号：模态与内容类型对应（对照口径表）。
2. 模态不可得时降级 → 预期：如语音不可得，按文字与文件次优组合执行，并在状态口径里如实标注模态降级 → 判定信号：不假装语音已通。
3. 选错信号复盘 → 预期：出现「长清单读成语音（对方记不住）」「一句确认打成文件（小题大做）」即回看判断口径 → 判定信号：复盘记录促成口径修订。

**④ 失败分支**：
- 一律文字图省事 → 定因：默认偷懒 → 处置：按口径表逐类纠正，并抽查近期回复模态分布 → 体验最平庸的默认就是这样来的。
- 对方明确要求换模态 → 处置：以对方要求为准，本条口径让位于本人意愿 → 记下偏好供后续同人回复沿用。

**⑤ 验收清单**：
- [ ] 抽查各类内容模态对应正确（证据：会话抽查）
- [ ] 模态降级在状态口径中如实标注（证据：状态说明）

**⑥ 禁忌与易错点**：模态即体感——同样的内容选对是专业、选错是添乱；语音的亲和、文字的可查、文件的正式各有不可替代场景。

**⑦ 参数表**：
| 内容类型 | 模态 |
|---|---|
| 短对话、确认、提醒、对方发语音 | 语音 |
| 数字、清单、需核对复制 | 文字 |
| 正式稿、台账、打印签章归档 | 文件 |
| 既讲解又留底 | 语音＋文件并行 |

以上为实测口径。

### 【文档交付三段式·发送顺序】

**① 目标与适用场景**：经桥交付文件按固定顺序发：说明文字→文件本体→提示语。顺序就是理解顺序，错位制造的困惑会被归因为「东西有问题」。

**② 前置条件**：
- [ ] 发送端（尤其路由器）能控制多段消息的相对顺序
- [ ] 说明文字已备（这是什么、要点是什么）

**③ 操作步骤**：
1. 先发说明 → 预期：对方先得语境 → 判定信号：发送记录中说明在文件之前。
2. 再发文件 → 预期：文件本体紧随 → 判定信号：顺序无颠倒。
3. 后发提示 → 预期：提示语（如请查收、请核对某处）收尾 → 判定信号：说明中已含「请查收」类措辞时省略本段，防重复啰嗦。
4. 顺风车捎带时同序 → 预期：随队列带出的文件交付同样保持三段相对顺序 → 判定信号：抽查队列带出记录。

**④ 失败分支**：
- 路由器先发文件后发文字（真实教训） → 定因：发送端顺序失控 → 处置：改发送端排序逻辑并用真实交付复验 → 停手线：顺序未复验前文件交付人工盯发。
- 对方投诉没收到/没看懂 → 处置：先核查送达证据（三级）与他的实际困难 → 停手线：不靠重发文档解决投诉——重发不是交付证明。

**⑤ 验收清单**：
- [ ] 抽查多次文件交付顺序均为三段式（证据：发送记录）
- [ ] 含「请查收」的说明无重复提示段（证据：样本）

**⑥ 禁忌与易错点**：先给裸文件、后补文字（用户一头雾水）；把重发当交付证明；顺序在合并发送时被打乱（相对顺序必须保持）。

**⑦ 参数表**：
| 参数 | 取值 | 性质 |
|---|---|---|
| 段序 | 说明→文件→提示，不可乱 | 实测（纪律） |
| 提示段省略条件 | 说明已含请查收类措辞 | 实测（纪律） |
