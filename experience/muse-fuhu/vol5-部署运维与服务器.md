# 卷五 部署、运维与服务器（操作规程版）

## 卷说明与通用工具箱

本卷是操作规程版：每条经验改写为可照做的规程，固定七段——①目标与适用场景 ②前置条件 ③操作步骤（每步写明：动作 → 预期现象 → 判定信号）④失败分支（停线怎么停、报告什么）⑤验收清单（可打勾）⑥禁忌与易错点 ⑦参数表。只读本卷，应能独立完成部署、巡检、回滚而不闯祸——前提是先按下面的环境参数卡把本机参数填实；卡上每一项都是执行前必须落到实处的值，不许留空上场。

全卷总纲只有一句：**线上才是真相，本地只是候选。** 本地源码树与线上会因服务器端单改、线上独有文件、多份副本而悄悄分叉；任何「本地打包→整页覆盖」的默认动作，迟早冲掉别人的修复或漏掉一份副本。

**环境参数卡（执行前逐项填实，缺项不开工）**：主机身份（哪台机、哪个服务、站点根目录）；线上拉取通道；部署通道；备份区位置与备份集命名；部署报告库位置；通道占用登记处；冲突裁决人；服务重载方式；巡检对象表位置。卡随环境变更当轮更新，写在各执行者自己的工具笔记里，不写进本卷（本卷只给方法）。

规程中反复出现的标准动作，先在工具箱里定义一次，各条引用：

- **拉线上版**：从线上运行环境取目标文件的现行内容到本地临时区（不覆盖本地源树），作为比对基线。判定信号：取到的文件大小/修改时间与线上目录列表一致。
- **diff 比对**：用文本 diff 工具逐行比对「线上版 vs 待部署版」，输出分三类：仅线上有（线上改动）、仅包里有（本地改动）、同段双方都改（冲突）。
- **三方合并**：以线上版为底，逐段叠加本地改动；线上独有段落原样保留；冲突段不猜，停线（见【整页部署三方合并】④）。
- **整目录备份**：把将被改动的整个目录复制到备份区，目录名带日期与轮次标识（如 `备份目录/事项名-YYYYMMDD/`，具体命名按本单位既有惯例，无惯例时用此格式，属通用步骤）；复制须保权限、属主、符号链接与空目录，复制前让源目录停写或用快照（见【改线上先整目录备份】）。判定信号：逐文件哈希清单与源目录一致——只数文件数不算备份成立。
- **md5 核对**：对同一文件在各处（包内/线上每份副本）计算 md5，逐一相同才算一致。
- **落位验收五项**：任何文件落位后统一验五项——路径（落点与清单一致）、类型（普通文件/目录/符号链接与清单一致）、哈希（回读哈希与包内一致）、权限（mode/属主与同目录正常文件一致）、渲染（受影响页面实查正常）。各落位条目的验收清单从严不从宽，缺项不算落位完成。
- **渲染实查**：用真实请求打开线上页面，看渲染结果（关键内容在否、资源加载否、控制台报错否），不看源码下结论。
- **停线（分两种状态）**：写前停线——尚未动线上时立即停止部署动作，保持线上现状不动，把冲突点、双方版本、已执行到哪一步写成报告上交裁决；裁决未到，不继续。写后围堵——已经写坏/写了一半时线上现状已变，「保持不动」不成立，按对应条目的围堵流程处置（如【线上多副本全覆盖】④的三选一），先控制影响面再报告。解除停线必须绑定裁决记录与待部署稿哈希，口头放行不算。

脱敏说明：实例中的地址、标识、真实路径一律通用表述；材料未给出具体数值/命令的步骤，标注「（通用步骤）」；材料给出的数值（如权限 640/664）原样保留并注明出处条目。参数表中的实测值注明来源类型与适用对象；凡标「（通用步骤）」的数值口径，须在自己的环境参数卡中测得后填入，不许直接照抄他方数值上生产。

## 第一章 部署防分歧与合并停线

### 【整页部署三方合并】

**① 目标与适用场景**：任何整页、整文件覆盖线上文件之前，先消除本地树与线上的分叉，保证部署不回滚线上已有改动。适用于页面文件、整份脚本、整份配置的覆盖式部署。

**② 前置条件**：
- 整目录备份已完成且备份集 ID 已记录并验活（见【改线上先整目录备份】）——硬门槛，未过不许进入第 1 步；
- 待部署文件已在本地定稿，且知道它要覆盖线上哪个文件；
- 有拉取线上现行版的通道；
- 本轮部署有明确的任务下达方（冲突时裁决人）。

**③ 操作步骤**：
1. 拉线上版：拉取前先记录目标身份（主机、服务、站点根目录），防拉错环境；拉到临时区后立即算线上原件哈希，连同大小、修改时间、权限、属主、符号链接目标写入基线清单 → 预期：临时区得到线上现行文件 → 判定信号：哈希已入基线清单且文件大小与线上目录列表一致，拉取过程无报错。
2. diff 比对线上版与待部署版 → 预期：差异被分成「仅线上有 / 仅包里有 / 双方同段都改」三类 → 判定信号：diff 输出非空且每处差异都能归入一类；若 diff 为空，说明两版一致，本轮无需部署，跳到第 6 步记录。
3. 无冲突时做三方合并：以线上版为底，逐段叠加本地改动 → 预期：合并稿同时包含线上独有段落与本地新改动 → 判定信号：对合并稿再 diff 线上版，差异应只剩本地预定改动，不多不少。
4. 把合并稿作为最终部署文件，替换原待部署版 → 预期：部署对象唯一 → 判定信号：部署清单上该文件只出现一次，指向合并稿。
5. 执行部署（按第二章各条规程）：替换走「先写临时文件→校验哈希→原子改名落位」，不直接覆盖写；落位后保留原文件的权限、属主与符号链接形态（见工具箱「落位验收五项」）→ 预期：线上文件被合并稿替换 → 判定信号：线上文件 md5 与合并稿一致。注：二进制、压缩或生成文件不走逐行 diff，改走哈希＋来源版本＋生成命令比对；整文件仅换行符（CRLF）差异时先规范化再判实质冲突（通用步骤）。
6. 在部署报告中记录本条执行情况（比对文件数、分叉数、处理方式），格式见【部署报告可审计】。

**④ 失败分支**：第 2 步出现「双方同段都改」且无法判断取舍 → 立即停线：不部署该文件，已部署的其他文件保持现状并在报告中标注「本轮部分完成」；报告内容＝冲突文件、冲突段落位置、线上版该段内容摘要、本地版该段内容摘要、各自的改动时间线索；等裁决后按裁决重走第 3 步。裁决必须落成裁决单：冲突段、采用版本、理由、裁决人、批准的合并稿哈希，五项齐全才算裁决到达；执行者只能部署裁决单批准的那个哈希，口头「按线上为准」不算裁决。

**⑤ 验收清单**：
- [ ] 备份集 ID 已记录并验活
- [ ] 线上版已拉取且与线上目录信息一致
- [ ] diff 三类差异已逐项归类，无未归类差异
- [ ] 合并稿对线上版的 diff 只含预定改动
- [ ] 线上文件 md5 与合并稿一致
- [ ] 部署报告已记录本轮 diff 与合并决定

**⑥ 禁忌与易错点**：
- 禁止不 diff 直接整页覆盖（本卷头号事故源）；
- 禁止以本地版为底合并——底必须是线上版；
- 易错：只比对主文件、漏比对它引用的整份子文件，子文件同样适用本条。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 合并基底 | 线上现行版 | 材料原值 |
| 冲突处置 | 停线报告，不现场裁决 | 材料原值 |
| 比对粒度 | 逐行 diff，全文件 | 材料原值 |

### 【停线救回线上修复】

**① 目标与适用场景**：把「发现冲突就停」从个人警觉变成每个部署任务的常设机制。适用于一切部署任务的流程设计；本条是制度条，不是单次操作条。

**② 前置条件**：
- 部署任务有标准流程文档或任务模板；
- 有明确的报告接收人（任务下达方）。

**③ 操作步骤**：
1. 在部署任务模板中写入停线条款：比对出现包里解释不了的冲突 → 停 → 报告 → 等裁决 → 判定信号：模板中存在该条款且每个新任务自动带上（通用步骤：写入任务下达的固定字段）。
2. 执行者每轮部署在 diff 环节逐项自问：这处线上改动，我知道是谁、为何改的吗？→ 预期：每处线上独有改动都有出处或被标为「出处不明」→ 判定信号：出现「出处不明」即触发停线，不许默认保留或默认删除。
3. 停线范围默认三条：冲突文件停、同批未开始文件全停、已完成文件冻结不再追加改动；同时取消未完成的传输/落位、记录在途文件状态、先核对已触及目标的当前哈希再报告。只有裁决单明确放行某些文件时，才可按放行范围继续。停线后按【整页部署三方合并】④的格式出报告，解除停线必须绑定裁决记录与待部署稿哈希 → 判定信号：报告含冲突位置、双方内容摘要与各目标当前哈希。
4. 若停线暴露出「上一轮部署已经冲掉过线上改动」的迹象（线上某已知修复不见了）→ 预期动作：立即扩大报告范围，写明疑似被冲掉的改动与时间线索 → 判定信号：报告中单列「疑似历史事故」一节（通用步骤）。

**④ 失败分支**：裁决迟迟不到 → 部署保持停止状态，线上不动；在晨报/待办中滚动挂账并注明报告接收人与首次送达时间，超时未裁决按未结项升级给用户，不许因「等太久」自行合并。紧急故障例外：可先行处置止损，但备份硬门槛不许跳，事后必须补裁决并在报告中标「紧急例外」。

**⑤ 验收清单**：
- [ ] 部署任务模板含停线条款
- [ ] 本轮 diff 中每处线上独有改动均有出处或已触发停线
- [ ] 停线报告要素齐全（冲突点、双方版本、已执行步数）

**⑥ 禁忌与易错点**：
- 禁止把停线当「部署失败」而绕过它赶进度；
- 易错：停线只停当前文件，却继续部署同批其他文件又不标注——必须在报告中写明本轮完成范围。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 停线触发条件 | 出现包里解释不了的冲突 / 线上改动出处不明 | 材料原值 |
| 停线后状态 | 线上保持不动，等裁决 | 材料原值 |

### 【服务器端改动当轮回并】

**① 目标与适用场景**：在服务器上直接做的一次性编辑（紧急修复等），必须在同一轮工作内合并回本地源树，消除「改动只活在线上」的分叉。

**② 前置条件**：
- 刚完成一处服务器端直接编辑，且线上已验证生效；
- 本地源树可写。

**③ 操作步骤**：
1. 记录本次服务器端改动点：文件、段落、改前改后内容 → 判定信号：改动点清单与实际编辑一一对应，无凭记忆补记。
2. 把改动逐点同步进本地源树对应文件 → 预期：本地文件包含该改动 → 判定信号：在本地文件中检索改动特征串，命中。
3. 拉线上版与本地版做 diff → 预期：该文件两版一致 → 判定信号：diff 输出为空；不为空则逐处判断是漏并还是本地另有未部署改动，后者要在记录中写明。
4. 在当轮工作记录中写一行：已回并，文件 X，第 N 处 → 判定信号：记录存在且可被下轮打包者检索到（通用步骤：记录位置用本单位既有台账/日志）。

**④ 失败分支**：diff 不为空且差异无法解释 → 按停线处理：暂停一切从本地树打包的部署，先报告差异，等查清再打包。

**⑤ 验收清单**：
- [ ] 改动点清单完整
- [ ] 本地源树含全部改动点
- [ ] 该文件线上/本地 diff 为空，或差异已逐项写明
- [ ] 当轮记录已留痕

**⑥ 禁忌与易错点**：
- 禁止「先上线，回头再并」——拖过当轮即视为未并；
- 易错：临时排障改动（如临时开调试）撤销后忘了在记录中注明「已撤销、无需回并」，导致后人把残留当正式改动。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 回并时限 | 当轮（同一工作轮次内） | 材料原值 |
| 一致性判定 | 该文件 diff 为空 | 材料原值 |

### 【只部署变更段落】

**① 目标与适用场景**：线上页面含有与本轮无关的热修复、且本轮改动局部时，不整页替换，只部署变更段落，把冲突面缩到最小。

**② 前置条件**：
- 整目录备份已完成且备份集 ID 已记录并验活（见【改线上先整目录备份】）——硬门槛；
- 改动段落边界清晰（能明确指出起止位置）；
- 已拉线上版并完成 diff，确认无关热修的位置不在本轮段落内。

**③ 操作步骤**：
1. diff 定位本轮改动的确切段落范围 → 判定信号：段落起止能在文件内唯一指出。
2. 用带上下文的补丁或唯一锚点定位段落（相同文本多处出现时靠锚点区分），仅把该段落替换为新版，其余段落保持线上原样；禁止凭行号手工粘贴。应用补丁前后核对文件编码与换行风格不变；工具若自动格式化全文件，立即放弃段落部署 → 预期：生成「线上版仅动一段」的部署稿 → 判定信号：部署稿与线上版 diff 只含该段落。
3. 部署该文件 → 判定信号：线上 md5 与部署稿一致。
4. 验证两件事：变更段落已生效；无关热修段落未被触碰 → 判定信号：渲染实查变更点正确；且对线上新版再 diff 本地源树时二选一成立——热修尚未回并时应表现为「线上独有差异」仍在，热修已回并时应表现为该段无差异。两种形态都算通过，其他形态即异常。

**④ 失败分支**：第 1 步发现段落边界不清、或改动散布全页 → 放弃段落部署，退回【整页部署三方合并】全流程，不许硬切。

**⑤ 验收清单**：
- [ ] 备份集 ID 已记录并验活
- [ ] 部署稿与线上版 diff 仅含目标段落
- [ ] 变更段落线上生效（渲染实查）
- [ ] 无关热修段落复检仍在

**⑥ 禁忌与易错点**：
- 禁止为了省事把段落部署扩大成整页替换；
- 易错：段落切分错位一行，把相邻段落的首尾带坏——切分后必须看 diff 全文再部署。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 适用条件 | 段落边界清晰、改动局部 | 材料原值 |
| 不适用时 | 退回三方合并 | 材料原值 |

### 【部署报告可审计】

**① 目标与适用场景**：每轮部署结束时产出一份可审计的报告，让事后任何人能还原「比对了什么、发现什么分叉、怎么决定的」。

**② 前置条件**：本轮部署已完成（含停线终止的轮次，同样要出报告）。

**③ 操作步骤**：
1. 按固定栏目写报告：部署对象清单（文件→线上路径→部署后 md5）；diff 结果（比对文件数、分叉处数）；每个分叉的处理决定（保留线上/采用本地/三方合并）及依据；备份位置与回滚办法（见【备份与回滚写进报告】）；未完成项与缺口（见【测试证据未采到如实记缺口】）→ 判定信号：五栏目齐全，无空栏。
2. 完整 diff 原文不进报告正文，归档在部署包旁，报告中给出归档位置 → 判定信号：按报告索引能找到 diff 原文（通用步骤：归档路径按本单位既有惯例）。
3. 报告随当轮工作记录留存 → 判定信号：以日期+事项名可检索到（通用步骤）。

**④ 失败分支**：部署中途停线/失败 → 报告照写，把状态写为「停线终止/部分完成」，并写明线上当前实际状态（哪些文件已换、哪些未动）；禁止只报成功轮次、不报失败轮次。

**⑤ 验收清单**：
- [ ] 五栏目齐全
- [ ] 每个分叉都有处理决定与依据
- [ ] diff 原文有归档索引
- [ ] 失败/停线轮次同样有报告

**⑥ 禁忌与易错点**：
- 禁止报告只写「已上线」三个字；
- 易错：md5 清单抄的是包内文件的，不是部署后从线上回读的——必须回读线上文件再算。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 报告栏目 | 对象清单/diff 结果/合并决定/备份与回滚/未完成项 | 材料原值（栏目构成综合本卷各条） |
| diff 原文 | 归档不入正文，报告给索引 | 材料原值 |

## 第二章 部署包制作、落位与上线验证

### 【部署文件首call带齐】

**① 目标与适用场景**：通过「调用即携带文件」语义的部署通道（如浏览器类部署工具）执行部署时，第一次调用就把本轮全部文件带齐，避免漏带导致整轮问答返工。材料实测：漏带一天犯过 3 次，每次多耗一整轮。

**② 前置条件**：
- 部署包已按【包逐文件 cmp】检验合格；
- 已有本轮文件总清单（文件名+目标路径）。

**③ 操作步骤**：
1. 发起调用前，把总清单逐项与待传文件逐一勾对 → 预期：清单项数＝待传文件数 → 判定信号：两数相等且文件名逐一对应。
2. 在第一次调用的文件参数里放入全部文件 → 判定信号：调用受理后回读文件列表，与总清单一致。
3. 再开始部署正文动作（解压、落位等）→ 判定信号：执行方不出现「缺文件」类回问。

**④ 失败分支**：第 2 步回读发现漏带 → 不要在原轮里零碎补传后继续部署（状态易乱）；停下，在报告中记「本轮因漏带作废」，备齐后重新发起完整一轮。

**⑤ 验收清单**：
- [ ] 首调前清单与文件已勾对
- [ ] 首调回读文件列表与清单一致
- [ ] 本轮无「缺文件」回问

**⑥ 禁忌与易错点**：
- 禁止「先发一部分、正文里再补」；
- 易错：清单是上一轮的旧清单——每轮按当轮部署包重新生成。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 文件携带时机 | 第一次调用 | 材料原值 |
| 漏带代价 | 多耗一整轮问答（实测一天 3 次） | 材料原值 |

### 【线上多副本全覆盖】

**① 目标与适用场景**：同一客户端文件在线上存在多份副本（如站点大厅目录一份、联机服务静态根目录一份，都被真实用户加载）时，部署必须逐份覆盖、逐份核对，漏一份等于没部署。

**② 前置条件**：
- 已按「副本发现顺序」查清全部线上副本：端口图登记 → 服务配置 → 监听进程的工作目录 → 反向代理目标 → 目录内符号链接/硬链接 → 各入口实际响应哈希；任一环节发现图外副本，先补图再部署；
- 部署文件已定稿（经三方合并，见第一章），且已选定一个稳定版本标记（版本号或特征内容）随部署稿一同确定，验收时逐份核对；
- 全副本旧版已纳入本轮备份集（见【改线上先整目录备份】），整批回退路径可用。

**③ 操作步骤**：
1. 列出副本清单：每份副本的目录、加载入口、当前哈希 → 判定信号：清单份数与端口图登记一致；图外新发现的副本当轮补进图。
2. 按依赖顺序逐份覆盖：先写非入口副本与被依赖文件，最后写入口直接加载的副本，缩短新旧混杂窗口；把部署文件逐一写入每个副本位置 → 判定信号：每份写入无报错。
3. 逐份回读并算 md5 → 预期：全部副本 md5 相同且与部署文件一致 → 判定信号：md5 列表全等；任一不等即该份未部署成功。
4. 从每个副本对应的入口各打开一次页面做渲染实查 → 判定信号：各入口加载到的都是新版（可用版本号/特征内容辨认，通用步骤）。

**④ 失败分支（写后围堵，三选一，必须执行其一，不许只停写报告）**：某份副本写入失败或 md5 不一致 → 先冻结：停止继续写入，逐入口记录当前版本（哈希＋版本标记），然后按序裁决并执行——
- 选项 A 整批回退（默认首选）：用备份集把全部副本恢复到部署前状态，逐份回读哈希验活，恢复后各入口渲染实查为旧版且功能正常；
- 选项 B 摘入口维持：异常入口先下线/摘除（保留其余已验活入口对外服务），异常副本单独修复，修好验活后才恢复入口；
- 选项 C 裁决后维持混合：仅当各入口新旧版本均可独立正常工作、且无跨副本数据/协议不一致时，由裁决人在报告中批准短时维持混合，并写明每个入口当前版本与恢复全覆盖的下一步动作；批准前不得以混合状态结项。
判定信号：报告中含逐入口版本表与所选围堵选项的执行结果；未执行任一选项、只写「部分完成」不算处置。

**⑤ 验收清单**：
- [ ] 副本清单与端口图一致，新副本已补图
- [ ] 全部副本 md5 与部署文件一致，版本标记逐份命中
- [ ] 每个入口渲染实查为新版
- [ ] 失败时已执行围堵三选一并留逐入口版本表（未失败则免）

**⑥ 禁忌与易错点**：
- 禁止只覆盖「最眼熟」的那一份就收工；
- 易错：副本清单凭印象列——必须以端口图加实查为准。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 一致性判定 | 全部副本 md5 全等 | 材料原值 |
| 副本来源 | 端口图登记＋实查 | 材料原值 |

### 【线上独有文件清单】

**① 目标与适用场景**：登记只存在于线上、本地源树没有的文件（如语音合成脚本、语音包、排行榜页、大厅头图与标志图），防止删除式同步把它们抹掉，并逐步回捞补齐本地树。

**② 前置条件**：能列出线上目录与本地源树的完整文件集。

**③ 操作步骤**：
1. 生成线上文件集与本地文件集，做集合差：线上有、本地无 → 逐项登记进「线上独有文件清单」（文件名、所在目录、用途若知）→ 判定信号：差集每项都在清单内。
2. 此后一切部署遵守派生硬规矩：增量包只覆盖不删除；禁用任何带删除语义的同步方式 → 判定信号：部署方案中无删除式同步工具/选项。
3. 单开一轮回捞：把清单文件逐个从线上取回本地源树对应位置 → 预期：本地树补齐 → 判定信号：回捞后重做第 1 步差集，该项消失；回捞文件在本地仅作存档，不改变「部署前仍须 diff 线上」的规矩。

**④ 失败分支**：差集中出现无法判断用途的文件 → 只登记、不动它，并在报告中标「用途待查」；禁止以「不知道是什么」为由删除或不登记。

**⑤ 验收清单**：
- [ ] 差集已生成且逐项登记
- [ ] 本轮部署方案无删除式同步
- [ ] 回捞计划已排期或已执行，差集随之缩小

**⑥ 禁忌与易错点**：
- 头号禁忌：对含线上独有文件的目录做删除同步——一次可抹掉无可再生的资产（如录制生成的语音包）；
- 易错：清单建完不维护——每轮部署后有新增线上文件（如服务端单改产生）要补登记。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 同步方式 | 只增量覆盖，禁删除同步 | 材料原值 |
| 清单字段 | 文件名/目录/用途 | 材料原值（字段为通用补全） |

### 【本地 404≠线上故障】

**① 目标与适用场景**：看到资源 404 时先分清观察点再定性：本地预览缺失多半是本地源树不完整，线上实查才是故障判据。防止把树缺失误报成线上故障、去线上「修」不存在的问题。

**② 前置条件**：能分别访问本地预览与线上真实地址。

**③ 操作步骤**：
1. 记录现象的观察点：本地还是线上 → 判定信号：报告中写明观察点，不写裸结论「某图 404」。
2. 到线上真实地址请求同一资源：逐字复用原始 URL（路径大小写、编码、查询参数、尾斜杠都照原样；若另做规范化请求，两组结果都留）；除状态码外核对 Content-Type、响应大小与内容哈希，排除站点回退页/默认图类软 404；必要时用缓存绕过请求并换一个观察点复测，登录资源注明身份状态 → 预期两种结果：线上 200 → 定性为本地树缺口，转第 3 步；线上同样 404 → 定性为线上故障，按故障流程处理 → 判定信号：以线上实查（状态码＋内容判据）为准。
3. 本地树缺口处理：把该资源登记进【线上独有文件清单】并纳入回捞计划 → 判定信号：清单新增该项。
4. 定性结论写入当轮记录：观察点＋线上实查结果＋定性 → 判定信号：三要素齐全。

**④ 失败分支**：线上状态间歇性不一致（时 200 时 404）→ 间隔多次复测并记录时间—结果序列（通用步骤），仍无规律才不下定性结论，报告「状态不稳定」并附采样序列，升级排查。

**⑤ 验收清单**：
- [ ] 现象已注明观察点
- [ ] 已有线上实查状态码
- [ ] 定性与后续动作匹配（缺口登记 / 故障处理）

**⑥ 禁忌与易错点**：
- 禁止只凭本地预览下「线上故障」结论；
- 易错：反向错误同样禁止——线上真 404 不许用「可能本地树问题」搪塞。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 故障判据 | 线上实查 HTTP 状态 | 材料原值 |
| 本地缺口去向 | 登记线上独有文件清单 | 材料原值 |

### 【删除靠清单执行】

**① 目标与适用场景**：需要删除线上死代码/死资源时——增量包覆盖永不删文件，删除必须靠包内删除清单在服务端逐项执行。防止「以为发包即删了」与「口头交代删错」。

**② 前置条件**：
- 四道闸门齐全才许执行（缺一即停）：闸门一·删除前归档已生成并验活（见第 1 步）；闸门二·引用检查已按第 2 步做完并逐项留证；闸门三·高风险项已过隔离观察期（见第 3 步）；闸门四·恢复方案已写明（见④）；
- 已对照【线上独有文件清单】：清单内文件默认不在删除范围。

**③ 操作步骤**：
1. 删除前归档：把待删文件连同相对路径、哈希、权限、属主打包成只读归档，验哈希通过后才继续；归档位置与保留期写进部署报告 → 判定信号：归档包可回读、逐项哈希与线上原件一致。
2. 引用检查（逐项留证）：静态——全库扫描代码、页面、配置与模板拼接字符串中的文件名/路径引用；动态——查数据库配置引用、定时任务、路由表，并查近周期访问日志是否仍有请求命中。每项在清单旁记录检查范围与结果 → 判定信号：每项都有「静态＋动态」两类证据，无证据的项不许删。
3. 隔离观察（高风险项必走）：先改名隔离（移入隔离目录），观察期内有引用报错或访问命中即恢复原名并撤销删除；观察时长由任务下达方指定或按既有惯例（通用步骤），期满无命中才进第 4 步。低风险项（自产临时文件等）可经下达方确认后免隔离，理由写入清单。
4. 试运行预览：输出将删路径、文件大小、最后修改/访问时间与引用检查结果，交任务下达方确认 → 判定信号：确认记录在案。
5. 编制删除清单文件（材料惯例名 DELETIONS.txt）：逐行写待删文件的线上路径 → 判定信号：行数＝确认待删数，每行可定位。
6. 把清单放进部署包，部署说明中单列「本轮含删除动作」→ 判定信号：执行方能一眼看到删除环节。
7. 执行方在服务端按清单逐项删除：只用精确路径，禁止通配符与目录递归删除；每删一项前再核对路径与清单行，删后回读确认不存在，并做一次页面与服务健康检查 → 判定信号：逐项验证「文件不存在」且健康检查通过。
8. 执行结果写回部署报告：删了哪些、逐项验证结果、归档位置 → 判定信号：报告删除清单与包内清单逐行对应。

**④ 失败分支**：某项删除前复查发现仍有引用 → 该项从清单划掉并报告原因，其余项继续；禁止「顺手一起删」清单外任何文件。删错/误删恢复：立即从第 1 步的归档包按原路径、原权限恢复该文件，回读哈希与归档一致、页面与服务健康检查通过后才算恢复完成，并把误删记入报告。归档缺失或哈希不符 → 按事故上报，不许用同名文件凑数恢复。

**⑤ 验收清单**：
- [ ] 四道闸门齐全（归档验活/引用双查/隔离观察/恢复方案）
- [ ] 删除清单与确认待删数一致
- [ ] 清单外文件零删除
- [ ] 逐项「不存在」已验证、健康检查通过并写入报告

**⑥ 禁忌与易错点**：
- 禁止口头交代删除；
- 禁止把删除寄托于同步工具的自动行为（与【线上独有文件清单】的禁删除同步不冲突：本条是人工清单删除，那条禁的是工具自动删除）。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 清单文件名 | DELETIONS.txt（材料惯例） | 材料原值 |
| 删除验证 | 逐项回读确认不存在 | 材料原值 |

### 【包逐文件 cmp】

**① 目标与适用场景**：部署包交付前的出厂检验：把包解压后与源码树逐文件字节比对，拦住打错包（混入旧版、漏文件、错目录）。

**② 前置条件**：部署包已打好；源码树为定稿状态（已完成三方合并/回并）。

**③ 操作步骤**：
1. 打包前先生成并冻结「应打包文件集」清单：逐项列包含项、剔除项（按【测试桩剔除清单】）与理由；验包开始时记录源码树清单哈希 → 判定信号：清单已冻结，【部署包逐文件落位清单】从同一清单派生。
2. 把包解压到干净临时区（解压方式须保留权限与符号链接形态，具体工具选项按本单位既有惯例，通用步骤）→ 判定信号：解压无错误，文件数与文件集清单一致。
3. 逐文件比对临时区与源码树：普通文件做 cmp 字节比对，并逐项核对清单字段——相对路径、类型、大小、哈希、权限（mode）、符号链接目标、空目录 → 预期：全部一致 → 判定信号：差异项数为 0；不抽查，全量比。
4. 验包结束时复核源码树清单哈希未变 → 判定信号：与第 1 步记录一致；变了则本轮验包结论作废。

**④ 失败分支**：任一文件有差异或文件集对不上 → 整包作废，查清打包环节后重新打包重验；禁止只替换差异文件后沿用旧包（包的整体性已不可信）。

**⑤ 验收清单**：
- [ ] 全量 cmp 差异为 0
- [ ] 清单字段（路径/类型/大小/哈希/权限/链接目标/空目录）逐项一致
- [ ] 文件集多/缺为 0
- [ ] 检验结论写入部署报告

**⑥ 禁忌与易错点**：
- 禁止抽查代替全量；
- 易错：cmp 只证明包与源码树一致，不证明源码树该上线——上线判断仍靠 diff 线上（第一章）。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 比对方式 | 逐文件字节级 cmp | 材料原值 |
| 比对范围 | 包内全部文件，不抽查 | 材料原值 |
| 不合格处置 | 整包作废重打 | 材料原值 |

### 【服务端改动分开标注】

**① 目标与适用场景**：一次上线同时含客户端文件与服务端改动（如 MIME 类型、缓存规则写在服务端代码里）时，两部分分开写明、分开执行、分开验证，防止只上了客户端包导致功能不生效。

**② 前置条件**：已识别本轮全部改动点，并能判断每点属客户端还是服务端。

**③ 操作步骤**：
1. 部署说明分两节写：客户端节（文件清单、落位、生效方式）；服务端节（改什么、落在哪个服务端文件/配置、生效条件如是否需重启）→ 判定信号：每个改动点恰好出现在一节中，无遗漏、无重复。
2. 两路分别执行：客户端按部署包流程；服务端改动若是整文件覆盖，走【整页部署三方合并】→ 判定信号：两路各有执行记录。
3. 两路分别验证：客户端查渲染页与 md5；服务端查其生效证据（如响应头里的 MIME/缓存字段符合预期，通用步骤）→ 判定信号：两路验证结论都写入报告。

**④ 失败分支**：任一路未落地 → 整体不宣布上线完成，报告写明哪一路卡住与线上当前状态；禁止用「客户端已上线」掩盖服务端缺失。

**⑤ 验收清单**：
- [ ] 部署说明双节齐全，改动点无遗漏
- [ ] 两路执行记录齐全
- [ ] 两路验证结论齐全

**⑥ 禁忌与易错点**：
- 禁止把服务端改动塞进客户端包里「顺带」；
- 易错：服务端改动生效需重启服务却没写明——生效条件必须显式写出。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 标注方式 | 客户端/服务端分开写明 | 材料原值 |
| 完成判据 | 两路均落地并验证 | 材料原值 |

### 【新文件权限坑】

**① 目标与适用场景**：部署新增文件落地后权限过严导致 Web 进程读不了、线上 403 的固定排查与预防。材料实测：新文件权限 640 → 线上 403；改 664 后复验 200 且 md5 一致。

**② 前置条件**：本轮有新增文件落到线上 Web 目录。

**③ 操作步骤**：
1. 新文件落地后，查其权限并与同目录既有正常文件对照；同时从站点根到目标文件逐级查父目录的执行（x）权限、属主/组与 ACL——文件可读但目录不可穿越照样 403 → 预期：新文件权限不严于既有文件、路径链可穿越 → 判定信号：权限位一致或已按第 2 步调整，目录链逐级可穿越。
2. 权限过严（如 640）时，不套固定值：复制同目录已验证正常文件的权限组合（mode、owner、group 及 ACL）到新文件 → 判定信号：新文件权限组合与正常文件逐项一致。（材料案例中该组合恰为 664，仅作历史案例，不是通用修复值。）
3. 复验三项：该文件 URL 返回 200（并核对响应体哈希、Content-Type、Content-Length，排除缓存、默认页与软 404，必要时用缓存绕过方式复核）；线上回读 md5 与包内一致 → 判定信号：全过。另把部署工具为何产出过严权限记入当轮记录（查打包/传输环节的 umask 与属性保留设置，通用步骤），防每轮靠上线后补权限。
4. 把「新文件权限检查」作为固定项执行于此后每轮含新增文件的部署（本条即该清单项的来源）。

**④ 失败分支**：权限已放开仍 403 → 停下排查其他原因（路径、反代、文件属主，通用步骤），并在报告中写明「权限已排除」；禁止反复盲目放宽权限（如给 777）。

**⑤ 验收清单**：
- [ ] 新文件权限已对照既有文件
- [ ] URL 返回 200
- [ ] md5 与包内一致

**⑥ 禁忌与易错点**：
- 禁止用 777 图省事——只放到「Web 进程可读」为止；
- 易错：既有文件的权限不在本轮调整范围，不要顺手批量改权限。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 故障权限值 | 640（导致 403） | 材料原值 |
| 修复方法 | 复制同目录正常文件的 mode/owner/group/ACL | 本卷规程 |
| 历史案例 | 某轮新文件 640→664 后复验通过 | 材料原值（仅案例，不作通用值） |
| 复验项 | HTTP 200 ＋ md5 一致 | 材料原值 |

### 【测试环境变量不带上生产】

**① 目标与适用场景**：为软件渲染等测试环境临时放宽的超时类变量（如判死阈值 10s→90s），只许存在于验证轮；生产部署逐项确认不携带。

**② 前置条件**：验证轮用过环境变量覆盖；验证记录中已登记用过的变量与值。

**③ 操作步骤**：
1. 整理验证轮变量登记：变量名、测试值、默认值 → 判定信号：登记与验证记录一致。验证时漏登记的，部署前按序反查补齐：服务定义 → 启动脚本 → 部署配置 → 进程环境 → 历史命令记录，逐处查覆盖变量并留证据（通用步骤）。
2. 生产部署前逐项核对部署配置：每个曾被覆盖的变量在生产侧应为默认或未设置 → 判定信号：逐项打勾，无测试值残留，每项核对留可回读证据（配置原文或进程环境摘录）。
3. 部署后抽查一个与该变量相关的行为（如判死触发时限符合默认量级）→ 判定信号：行为与默认值相符（通用步骤：以可观测行为为准）。

**④ 失败分支**：发现测试值已混入生产 → 按独立配置变更处理：报告混入项与影响，评估后改回默认并验证；禁止「先这样跑着」。

**⑤ 验收清单**：
- [ ] 验证轮变量已登记
- [ ] 生产配置逐项核对无测试值
- [ ] 相关行为抽查符合默认

**⑥ 禁忌与易错点**：
- 禁止以「测试时用过」为由把放宽值带进生产；
- 易错：某个放宽值在生产确有必要时，它是独立配置变更，走评估与部署流程，不许混带。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 示例变量 | 判死阈值 测试 90s / 默认 10s | 材料原值 |
| 生产侧取值 | 默认值（真实硬件帧率下余量充足） | 材料原值 |

### 【向后兼容即灰度】

**① 目标与适用场景**：联机功能升级时用兼容性换灰度：服务端先行部署且向后兼容，旧客户端忽略新字段照常运行，客户端随正式版发布后新功能才激活。

**② 前置条件**：协议改动属于加字段式变更（旧端可忽略新字段）；若必须做不兼容变更，本条不适用（见④）。

**③ 操作步骤**：
1. 设计期确认兼容性：新服务端对旧客户端的全部既有请求行为不变 → 判定信号：逐项列出旧端用到的接口/字段，新版行为对照无变化（通用步骤：以接口清单对照）。
2. 先部署服务端 → 判定信号：服务端上线且旧客户端实测可正常进入与游玩。
3. 观察期：先列旧端版本清单与关键链路样本（登录、进入、对局），观察期内逐项监测；确认无旧端异常报告后再发布客户端正式版 → 判定信号：观察期内旧端关键链路无新增故障（观察时长与异常率红线材料未给，须在部署说明中先写明再执行，通用步骤）。
4. 客户端发布后验证新功能激活 → 判定信号：新端实测新功能可用，旧端仍可正常运行。

**④ 失败分支**：第 1 步发现必须做不兼容变更 → 本条停用，另行设计强制升级或分服方案并报告；第 2 步后旧端出现异常 → 回滚服务端一处即可（本方法回滚面小是其设计目的），按第三章回滚规程执行；回滚后实测旧端关键链路恢复正常才算回滚完成。

**⑤ 验收清单**：
- [ ] 兼容性对照清单无行为变化项
- [ ] 服务端上线后旧端实测正常
- [ ] 客户端发布后新功能激活、旧端仍正常

**⑥ 禁忌与易错点**：
- 禁止客户端先行、服务端滞后（新端会打到不懂新字段的旧服务端）；
- 易错：「忽略新字段」必须实测——某些旧端对未知字段是报错而非忽略。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 部署顺序 | 服务端先行 → 客户端正式版 | 材料原值 |
| 兼容形态 | 加字段，旧端忽略 | 材料原值 |
| 回滚面 | 仅服务端一处 | 材料原值 |

### 【原目录不动原则】

**① 目标与适用场景**：合并与实验一律在副本目录做，原目录保持不动，作为最后的已知良好状态；合并正确性靠 diff 实测（如「有且仅有 N 处挂接」）证明，不整文件覆盖。

**② 前置条件**：有可复制的原目录；知道本轮实验/合并的预期改动点数量级。

**③ 操作步骤**：
1. 记录原目录指纹：生成逐文件哈希清单（含相对路径、大小、权限、符号链接目标）→ 判定信号：哈希清单已留存。
2. 用保留属性的方式复制出工作副本（保 mode、属主、符号链接与时间戳，具体工具选项按既有惯例，通用步骤），复制后先验副本哈希清单与原目录一致，防复制过程污染 → 判定信号：全部写操作发生在副本路径下，副本初始状态与原目录逐项一致。
3. 对副本与原目录做 diff → 预期：差异应恰好等于预定挂接点 → 判定信号：差异处数＝预定 N 处，且逐处可解释；多一处即停查。
4. 结论成立后，副本成果按正常部署流程上线（第一、二章）；原目录指纹复检未变 → 判定信号：逐文件哈希清单与第 1 步全等。

**④ 失败分支**：第 3 步差异处数多于预定 → 副本作废，查清多出差异的来源后重做；禁止在副本里「修一修」继续用（差异来源不明，修补不可信）。

**⑤ 验收清单**：
- [ ] 原目录指纹已记录且收尾复检未变
- [ ] 全部作业在副本内完成
- [ ] diff 差异处数与预定一致且逐处可解释

**⑥ 禁忌与易错点**：
- 禁止直接在原目录上试改「改完再说」；
- 易错：副本长期堆积冒充存档——副本是作业区，上线后按备份规矩处置（见第三章）。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 合并证明方式 | diff 实测差异处数＝预定挂接数 | 材料原值 |
| 原目录未动证据 | 逐文件哈希清单全等（时间戳/大小为辅助） | 本卷规程（材料原值为时间戳/大小，本卷升级为哈希） |

### 【测试桩剔除清单】

**① 目标与适用场景**：本地测试用的桩与脚手架（临时最小服务、测试依赖目录等）不属于产品，打包时按清单剔除并在报告中明示，防止测试代码混进生产、也防止「包里没 X」被误判漏包。

**③ 操作步骤**：

**⑤ 验收清单**：

**⑦ 参数表**：

|---|---|---|

### 【部署后查渲染页】

**① 目标与适用场景**：部署验收的最后一关：线上实查渲染后的页面，而不是以文件一致收尾。文件全对而页面坏掉的路径很多（权限、缓存规则、服务端配套缺失、副本漏覆盖），只有渲染层是用户真正接触的层。

**② 前置条件**：部署已落地；受影响页面清单已按引用关系反推生成：从变更文件出发，沿页面引用、路由与副本入口推出直接页面，再加首页与一个关键业务入口作烟雾检查（公共脚本/样式变更时，受影响面按全部引用页计）。

**③ 操作步骤**：
1. 逐页用线上真实地址打开受影响页面（用硬刷新或缓存绕过，逐页记录 URL、登录身份状态、视口、状态码、关键元素、资源失败数、控制台错误，并留截图或 DOM 关键元素结果作证据）→ 预期：页面正常渲染 → 判定信号：关键内容出现、图片/脚本等资源加载成功、控制台无报错。
2. 对含交互的页面执行最小交互：只做预先列明的只读交互；会改数据的交互（提交、删除、确认类）只许用测试数据与测试对象，没有测试对象时该交互标「未验」→ 判定信号：交互有响应、无白屏。
3. 把渲染结论与文件侧证据（md5 等）合并写入部署报告 → 判定信号：报告同时含「文件一致」与「页面正常」两项结论，缺一不算验收完成。

**④ 失败分支**：文件一致但页面异常 → 按现象分流：403 先查权限（【新文件权限坑】）；内容旧查副本（【线上多副本全覆盖】）与缓存；功能不生效查服务端配套（【服务端改动分开标注】）；查不清则报告现象与已排除项，必要时回滚（第三章）。回滚红线：关键入口白屏、登录不可用、核心资源 404、阻断性控制台错误持续出现——任一命中即进入回滚评估，由任务下达方（或授权范围内的维护者）当场裁决，不许带病观望。

**⑤ 验收清单**：
- [ ] 受影响页面逐页渲染实查通过
- [ ] 最小交互验证通过（适用时）
- [ ] 报告含文件与渲染双结论

**⑥ 禁忌与易错点**：
- 禁止以 md5 一致代替页面验收；
- 易错：渲染检查证明不了帧率、手感、真实设备表现——这部分如实标「未验，待真机」，不许写进「正常」（卷一总规矩）。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 验收层 | 渲染后的页面 | 材料原值 |
| 未验项标注 | 真机表现标未验 | 材料原值 |

### 【部署包逐文件落位清单】

**① 目标与适用场景**：部署包附逐文件落位清单（每个文件→线上目标路径），落位后按清单核对线上实际文件集。来源教训：曾有包内测试文件随包落进线上目录——无害但属落位失控。

**② 前置条件**：部署包已通过【包逐文件 cmp】；已知道每个文件的目标路径；目标目录已纳入本轮备份集（见【改线上先整目录备份】）。

**③ 操作步骤**：
1. 编制落位清单：逐行「包内文件 → 线上目标路径」→ 判定信号：行数＝包内文件数。
2. 审查清单：非运行时文件（测试、构建脚本）原则上不进线上目录；确需带入的单独标注理由 → 判定信号：无未标注理由的非运行时文件。
3. 落位前先给目标目录做文件集＋哈希基线快照，并逐行核对目标现状类型（普通文件/目录/符号链接）：类型与清单不一致立即停线，不许覆盖穿透到链接目标。按清单逐项落位，每行落位后回读线上文件算哈希，与包内哈希逐行比对 → 判定信号：每行路径、类型、哈希三项一致。
4. 落位后用前后快照差集核对线上实际文件集：本轮新增/变更文件与清单逐行对应 → 判定信号：多 0、少 0；多出的文件必须当轮解释。

**④ 失败分支**：核对发现多出文件 → 按序定位来源：落位前后快照差集 → 文件时间 → 并行任务记录（见【并行部署防同名覆盖】）→ 文件哈希比对；不许直接删；查清后按【删除靠清单执行】处理或登记保留；无法定位来源时默认保留并上报。

**⑤ 验收清单**：
- [ ] 落位清单行数与包内文件数一致
- [ ] 非运行时文件均有标注理由或已被剔除
- [ ] 逐行回读哈希与包内一致，目标类型无异常
- [ ] 线上文件集核对多/少为 0

**⑥ 禁忌与易错点**：
- 禁止「解压了事」不核对落位；
- 易错：清单只列新增不列覆盖——覆盖文件同样占行。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 清单粒度 | 逐文件→逐路径 | 材料原值 |
| 非运行时文件 | 原则不进线上，进则标注理由 | 材料原值 |

### 【并行部署防同名覆盖】

**① 目标与适用场景**：两个部署任务并行、共用同一中转盘时，同名文件会互相覆盖且静默成功。材料案例：执行方核对字节数发现不对、当场停工，保住现网。

**② 前置条件**：存在并行部署可能；各任务有自己的文件清单与字节数记录。

**③ 操作步骤**：
1. 并行前隔离中转：各任务用任务 ID 独立中转目录（文件名前缀只作辅助），不共用裸文件名；前缀只许出现在中转区，线上目标名一律以【部署包逐文件落位清单】为准。同时以目标路径为粒度做占用登记：同一目标已有任务未释放，后到任务排队 → 判定信号：两任务中转目录互不重叠，目标占用无冲突。
2. 文件先传到本任务暂存区并验哈希，验过才在目标占用内原子落位；每一步传输/落位后核对文件大小（字节数）与本任务清单（字节数只是快速异常信号，不是安全证明）→ 预期：逐项相等 → 判定信号：任一不等立即停工（第 4 步）。
3. 完工后对关键文件再算 md5 与包内比对 → 判定信号：一致（通用步骤：字节数是快速熔断，md5 是终检）。
4. 停工处置：先保现网（不再写任何文件），报告哪个文件、期望字节数、实际字节数、怀疑的覆盖来源，等裁决。

**④ 失败分支**：已确认发生同名覆盖且错误内容已上线 → 按事故处理：用本任务合格包重新部署受影响文件并全量复验，同时报告另一任务可能受的影响范围。

**⑤ 验收清单**：
- [ ] 并行任务文件名已错开
- [ ] 每步字节数核对无异常
- [ ] 关键文件 md5 终检一致

**⑥ 禁忌与易错点**：
- 禁止共用中转盘裸文件名并行；
- 易错：字节数相同不等于内容相同——字节数只作熔断信号，终检仍靠 md5/cmp；本条不替代【包逐文件 cmp】。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 熔断信号 | 字节数与清单不符 | 材料原值 |
| 熔断动作 | 立即停工、先保现网 | 材料原值 |

### 【共用通道部署排队】

**① 目标与适用场景**：多个任务共用同一条服务器控制台通道时，并发写操作会互相干扰（会话、终端、传输互踩）；部署方主动排队，不抢通道。

**② 前置条件**：知道当前还有谁在用同一通道做写操作。

**③ 操作步骤**：
1. 部署开始前查通道占用登记（登记处按环境参数卡）：登记含占用者、开始时间、预计完成、释放信号；无登记机制时以通道侧会话状态/对方任务报告为准 → 判定信号：明确「通道空闲」或「某任务进行中、预计何时释放」。
2. 有任务进行中 → 排队等待其完成/释放信号，再开始自己的；占用超时未释放 → 只上报下达方裁决是否接管，不许自行抢占 → 判定信号：自己的第一个写操作发生在对方释放信号之后，本任务占用与释放均已登记。
3. 紧急修复需要插队时，由任务下达方调整顺序并知会双方 → 判定信号：双方都确认知悉新顺序（通用步骤）。

**④ 失败分支**：等待期间发现对方任务长时间无进展 → 只询问/报告，不许强行接管通道开始写操作；由下达方裁决是否中止对方任务。

**⑤ 验收清单**：
- [ ] 开始前已确认通道状态
- [ ] 无与他人写操作重叠的时间段
- [ ] 插队（如有）已经下达方调整并知会双方

**⑥ 禁忌与易错点**：
- 禁止抢通道并发写；
- 易错：只读巡检、状态查询不占写通道，不必排队——不要把排队扩大到只读动作而拖慢巡检。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 排队范围 | 同一通道的写操作 | 材料原值 |
| 默认顺序 | 先就绪者先上 | 材料原值 |

## 第三章 备份与回滚

### 【改线上先整目录备份】

**① 目标与适用场景**：动线上系统前先整目录备份，保证任何改动都有一个自洽的已知状态可整目录回滚。适用于一切线上改动（部署、巡检维修、工作台改造）的前置动作。

**② 前置条件**：已明确本轮要改动的目录范围；已列依赖清单——目录外状态（数据库、配置文件、服务单元、定时任务、外部上传目录）凡与本目录功能相关者都在清单内；备份区空间已实测（源目录大小、备份区可用空间与安全余量均有数，空间不足直接停线，不许边复制边删旧备份腾挪）。

**③ 操作步骤**：
1. 定备份集：本轮全部备份（整目录＋依赖清单中的目录外状态）共用一个备份集 ID；数据库导出、配置与服务定义分别生成可恢复备份，与目录备份互相引用 → 判定信号：备份集清单列齐每一项及其恢复方式。
2. 让源目录进入静止状态：停写、停相关服务或用文件系统快照；无法停写时须有证据证明复制窗口内目录无变化（如复制前后哈希清单一致）→ 判定信号：静止状态成立方式已写入本轮记录。
3. 整目录复制到备份区（目录名带日期与轮次标识），复制保留权限、属主、符号链接与空目录 → 判定信号：复制完成无报错。
4. 生成逐文件哈希清单并验活：对备份逐文件算哈希，与源目录哈希清单全量比对（文件量过大时按风险分级：可执行与配置文件全量、静态资源抽验，分级规则写入记录）；同时做可恢复性验证——备份可读性检查通过，并做过一次回滚演练或等价证据（改名式干跑：把备份改名到临时位置验证可独立成目录）→ 判定信号：哈希清单一致＋演练/等价证据在案。只数文件数不算验活。
5. 把备份集 ID 与备份路径写进本轮记录（先于改动落字）→ 判定信号：记录中备份集可定位。
6. 执行改动 → 判定信号：改动按各自规程完成。
7. 改后用页面实测（渲染实查）验证 → 判定信号：受影响页面正常；异常则走④。

**④ 失败分支**：改后验证不过 → 按影响等级定回滚决策：关键入口不可用时立即决策回滚，不等普通修复窗口；其余情形的决策时限与裁决人在本轮记录中先写明。整目录回滚顺序：停相关服务/停写 → 把故障目录改名封存（保留现场，不直接删）→ 把备份恢复到正式位置并恢复权限/属主 → 按备份集清单处理数据库与目录外状态 → 启动服务 → 渲染实查确认恢复到改前状态 → 故障目录留待裁决后处置。回滚动作与原因写入报告。禁止逐文件找补式回滚（易漏连带变更，滚成半新半旧）；文件级恢复的唯一例外见【备份与回滚写进报告】③。

**⑤ 验收清单**：
- [ ] 备份集 ID 已生成，目录与目录外状态同属一个备份集
- [ ] 源目录已静止（停写/快照/无变化证据三选一）
- [ ] 逐文件哈希清单一致，可恢复性已演练或有等价证据
- [ ] 备份路径已记入本轮记录
- [ ] 改后页面实测通过（或已整目录回滚并复验）

**⑥ 禁忌与易错点**：
- 禁止只备份「要改的几个文件」——回滚点必须整目录自洽；
- 易错：有备份不等于可跳过 diff/三方合并；备份是保险，不是许可；
- 易错：备份无限堆积占满磁盘——保留周期按目录重要性定（具体周期材料未给，按本单位既有惯例，通用步骤）。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 备份粒度 | 整目录 | 材料原值 |
| 备份命名 | 带日期与轮次标识 | 材料原值 |
| 回滚方式 | 整目录替换 | 材料原值 |
| 验收线 | 哈希清单一致＋回滚演练或等价证据 | 本卷规程 |
| 回滚顺序 | 停服→改名封存→恢复→验活 | 本卷规程 |

### 【备份与回滚写进报告】

**① 目标与适用场景**：每轮部署报告固定写明备份位置与可照做的回滚办法——回滚发生在事故压力下，报告就是当时的操作手册，不能靠翻聊天记录找路径。

**② 前置条件**：本轮已有备份（见【改线上先整目录备份】）；知道本轮新增文件清单与涉及的服务。

**③ 操作步骤**：
1. 报告中写备份位置（完整路径/标识）→ 判定信号：按报告能直接定位备份。
2. 写回滚步骤：默认整目录回滚（与【改线上先整目录备份】同一口径）——写明备份集 ID、整目录恢复顺序与服务停启；文件清单只用于说明影响范围，不等于按文件回滚。文件级恢复仅在同时满足四条时才许写入报告：本轮无新增、无删除、无配置与状态变更；每个待恢复文件有对应快照或哈希证据；经裁决人批准（四条缺一即整目录回滚）→ 判定信号：报告中的回滚粒度与上述口径一致，无含糊的「恢复某几个文件」。
3. 写新增文件处置：逐个判断——留置结论必须附引用检查范围（静态扫描＋路由/插件发现/配置通配/定时任务动态排查）与观察期结论；无法证明无引用时默认随回滚隔离，不直接留置。被配置或路由引用的必须一并处置并写明 → 判定信号：每个新增文件都有带证据的处置结论。
4. 若涉及服务端：写明恢复后要重启哪个服务 → 判定信号：服务名明确。
5. 写回滚验证与触发：回滚步骤须有验证证据——备份可读性检查结果、最近一次回滚演练/干跑的时间与结果；写明回滚触发红线、裁决人、执行人。涉及数据库、数据写入、定时任务、缓存等状态变更的，单列「数据与状态变更」栏；不可逆的数据操作写补偿方案，不许笼统称「恢复备份」→ 判定信号：各项齐全。

**④ 失败分支**：写报告时发现备份实际不存在或不完整 → 如实写明「本轮无有效备份」，并立即补做当前状态备份，同时把该轮标记为高风险轮次上报；禁止在报告中虚构备份路径。

**⑤ 验收清单**：
- [ ] 备份位置可按报告定位
- [ ] 回滚粒度符合统一口径（默认整目录；文件级例外四条件齐全）
- [ ] 每个新增文件有带证据的处置结论
- [ ] 涉及服务时重启对象明确
- [ ] 回滚验证证据、触发红线、裁决人与执行人已写明

**⑥ 禁忌与易错点**：
- 禁止回滚说明写「恢复备份即可」这类空话；
- 易错：「新增文件可留置」只适用于确认无引用者，未确认的一律按「需处置」写。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 报告必含 | 备份位置/回滚步骤（整目录默认）/新增文件处置/重启服务/回滚验证证据 | 材料原值＋本卷规程 |
| 留置条件 | 旧代码不引用且无副作用 | 材料原值 |

## 第四章 巡检、工作台改造与故障定性

### 【工作台维护独任制】

**① 目标与适用场景**：（组织规程，材料只给原则，具体动作为通用步骤。）整个服务器与工作台由一个智能体单独维护，避免多头改动互相不知情；巡检职责含主动发现「不合理/可改进」并修，不限于报故障。

**② 前置条件**：维护责任已明确归属单一维护者；其他智能体知悉不插手同一系统（通用步骤）。

**③ 操作步骤**：
1. 一切线上改动（巡检修复、部署、改造）统一经维护者执行或登记：登记写入本单位既有工作台账/工作记录（位置按环境参数卡），逐项写对象、动作、时间、执行者 → 判定信号：每轮改动都有维护者记录可检索。授权范围＝用户授予的维护范围（巡检修复、部署、经批准的改造）；超出范围的改动只登记上报。维护归属冲突（他方声称同一系统维护权）→ 不抢改，报告用户仲裁（通用步骤）。
2. 巡检中发现「不合理/可改进」项：在授权范围内当轮修（先备份、后验证，按【改线上先整目录备份】）；超出范围的只记录上报 → 判定信号：每项都有「已修并验证」或「已上报」结论（通用步骤）。
3. 发现他方在同一服务器的工作痕迹 → 不动，按【发现他方架子不动】报告（通用步骤）。

**④ 失败分支**：出现非维护者改动且已造成分叉 → 按第一章 diff/停线流程查清分叉范围并报告用户，不许以「恢复独任」为名擅自回滚对方改动。

**⑤ 验收清单**：
- [ ] 本轮全部改动有维护者记录
- [ ] 巡检发现项逐项有处置结论
- [ ] 他方痕迹未擅动、已报告

**⑥ 禁忌与易错点**：
- 禁止多头并行改同一系统；
- 易错：独任≠擅专——用户明示决定（【用户明示保留的故障不修】）高于维护者判断。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 维护主体 | 单一智能体 | 材料原值 |
| 巡检范围 | 故障＋不合理/可改进 | 材料原值 |
| 本条性质 | 原则条，步骤为通用步骤 | 本卷标注 |

### 【每日外部巡检】

**① 目标与适用场景**：每日定时从外部视角巡检首页与各子页/子应用，把「静悄悄坏掉」的故障（入口消失、子页报错、资源 404）在用户投诉前发现。

**② 前置条件**：有巡检对象表并逐项写明：地址、身份状态（匿名/普通登录/维护身份）、预期状态码、关键元素、允许的异常、负责人；未覆盖的身份态在表上标「未验」，不许用匿名正常代替。知道保留项清单（见【用户明示保留的故障不修】）。

**③ 操作步骤**：
1. 按对象表逐项外部请求：记录 HTTP 状态 → 判定信号：每项有状态码记录；保留项状态与保留预期一致（如应为 502 的仍是 502）即为正常。单次请求失败先复测（间隔复测并换一个观察点，通用步骤），复测仍异常才定性故障，防网络抖动制造无谓变更。
2. 对状态正常项做渲染检查（见【巡检看渲染不看源码】）→ 判定信号：关键入口与内容在渲染页可见。
3. 发现明确故障先分级：甲类·可当轮自修（故障明确、不涉结构与保留项、影响面小）；乙类·必须停线报告（成因不明、影响面大、涉共用通道或他人维护范围）；丙类·必须用户裁决（结构变更、保留项、口径问题）。甲类修复前依次过四道门——整目录备份已验活、通道未被占用、属本维护者范围、改动不超本轮范围——然后修复 → 改后验证（状态＋渲染双过；数据类页面另加数据新鲜度/关键总数抽查，渲染正常与数据正确分开下结论）→ 判定信号：修复项复检通过且分级与过门记录在案。
4. 出巡检记录：范围、发现、处置、验证结果；无问题也留记录 → 判定信号：记录可按日期检索（通用步骤）。

**④ 失败分支**：故障涉及结构变更或需用户决策 → 只记录上报，不在巡检轮擅自大动；故障一时修不好 → 报告现象与影响范围，挂入晨报未结项滚动（见【晨报制度】）。

**⑤ 验收清单**：
- [ ] 清单逐项有状态记录
- [ ] 正常项已做渲染检查
- [ ] 修复项已备份、已复验
- [ ] 本轮巡检记录已留存

**⑥ 禁忌与易错点**：
- 禁止巡检顺手「修好」保留项；
- 易错：只查首页不查子应用——静默故障多在子页。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 频率 | 每日定时 | 材料原值 |
| 检查项 | HTTP 状态＋渲染 | 材料原值 |
| 修复顺序 | 先备份→改→验证→报告 | 材料原值 |

### 【巡检看渲染不看源码】

**① 目标与适用场景**：巡检与验收的观察层纪律：以渲染后的页面下结论，源码只作辅助定位。来源教训：曾有入口在源码里消失多日，靠渲染检查才发现。

**② 前置条件**：能以真实请求访问页面并看到渲染结果。

**③ 操作步骤**：
1. 按巡检对象表的标准观察环境做真实请求并看渲染形态（每类页面定浏览器/视口，移动端关键页加一个移动视口结论；必须可见的元素与必须加载的资源以对象表为准）：关键入口在否、内容出否、资源加载否 → 判定信号：逐项可见性结论，而不是「源码里有这段代码」。
2. 渲染异常时再回源码/模板/数据定位原因 → 判定信号：定位结论能解释渲染现象。
3. 巡检记录写渲染结论并附证据：每页留截图或 DOM 关键元素结果、资源状态与控制台错误摘要，证据位置写进记录；结论以稳定后的渲染为准——按等待条件等异步加载完成、用硬刷新或缓存绕过排除旧缓存，闪烁/延迟项复测后再下结论 → 判定信号：记录用语是「页面上看到什么」且证据可回查。

**④ 失败分支**：渲染环境本身受限（如软件渲染查不了动画/帧率）→ 如实标注该部分未验，不许以「源码正确」补位下结论。

**⑤ 验收清单**：
- [ ] 每页有渲染层结论
- [ ] 异常已定位或已标注未验部分
- [ ] 记录未以源码检查冒充验收

**⑥ 禁忌与易错点**：
- 禁止看源码说「页面正常」；
- 易错：渲染正常≠数据正确——数字口径类页面还要按数据对账纪律核数（卷四），两层都过才算验完。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 验收对象 | 渲染后的页面 | 材料原值 |
| 源码角色 | 仅辅助定位 | 材料原值 |

### 【用户明示保留的故障不修】

**① 目标与适用场景**：用户明示决定保持下线的入口（如某些路径保持 502）是「决定」不是「故障」；巡检只核对它们仍在保留状态，不修复、不反复提议。

**② 前置条件**：有用户明示保留的清单（含入口与预期状态）。

**③ 操作步骤**：
1. 把保留项登记成清单：入口、预期状态、决定来源 → 判定信号：每项有用户明示依据（通用步骤：无依据的不得自封保留项）。
2. 每轮巡检逐项核对实际状态与预期一致 → 判定信号：一致即通过，不触发修复流程。
3. 用户主动改口时，将该项移出清单、转入正常修复流程并留痕 → 判定信号：清单变更有记录（通用步骤）。

**④ 失败分支**：保留项状态发生变化（如 502 变 404、或开始影响其他页面）→ 报告变化，不自行恢复也不自行「修好」；保留的是决定，状态变化仍须上报。

**⑤ 验收清单**：
- [ ] 保留清单每项有明示依据
- [ ] 本轮逐项核对状态一致
- [ ] 状态变化（如有）已报告

**⑥ 禁忌与易错点**：
- 头号禁忌：把保留项「顺手修好」——这是越权，不是勤快；
- 易错：拿保留当免检——状态漂移照样要报。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 保留项预期状态 | 以下线状态为准（如 502） | 材料原值（路径已化名） |
| 处置 | 只核对、不修复 | 材料原值 |

### 【侧边栏只动条目】

**① 目标与适用场景**：工作台导航侧边栏的变更边界（用户亲定）：只增删条目，不动结构。条目级改动可直接执行；分组、层级、布局类调整需先经用户确认。

**② 前置条件**：明确本轮改动属于条目级还是结构级；条目目标页面存在且可达。

**③ 操作步骤**：
1. 判断改动级别：新增/移除/改名单个条目＝条目级，可执行；涉及分组结构、层级、样式＝结构级，停，转第④ → 判定信号：级别判断写入当轮记录（通用步骤）。
2. 条目级执行：先确认目标页面存在且能打开 → 再增删条目 → 判定信号：导航点击直达目标页，无空指向。
3. 改后渲染实查侧边栏 → 判定信号：条目出现/消失符合预期，其余条目未受影响。

**④ 失败分支**：发现「改个条目」实际需要动结构（如新条目无组可归）→ 停下报告，不许顺势改结构；人员变动引起的组名问题同样冻结，等分工文件（见【分工未定不落结构】）。

**⑤ 验收清单**：
- [ ] 改动级别已判断并记录
- [ ] 目标页面先验可达
- [ ] 渲染实查条目状态正确、其余未受影响

**⑥ 禁忌与易错点**：
- 禁止条目改动夹带结构调整；
- 易错：先删条目后发现目标页只是临时下线——删改名前先验目标状态。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 可直接执行 | 条目增删改名 | 材料原值 |
| 需用户确认 | 分组/层级/布局结构 | 材料原值 |

### 【新结构先测保存路径】

**① 目标与适用场景**：给工作台新建板块/结构时，验收拆两段：结构段与保存段。保存路径未端到端测过，不许宣称可用。

**② 前置条件**：新结构已建成；备有可识别的测试数据（与真实业务数据可区分）。

**③ 操作步骤**：
1. 结构段验收：页面出得来、字段与设计一致 → 判定信号：渲染实查通过。
2. 保存段验收：用测试数据真实写入一条 → 重新读出 → 逐字段比对 → 预期：读出值与写入值一致 → 判定信号：比对全等；任一字段不一致即保存段不过。
3. 清理或标注测试数据 → 判定信号：测试数据不与真实数据混杂（通用步骤：删除或显式标注，二选一并留痕）。
4. 汇报分段报结论：两段都过才报「可用」；只过结构段报「结构已建、保存未验」→ 判定信号：报告用语与实测段位一致。

**④ 失败分支**：保存段失败 → 报告失败点（接口/权限/字段映射逐项排查结果，通用步骤），板块标「未可用」，不许先上线再修。

**⑤ 验收清单**：
- [ ] 结构段渲染通过
- [ ] 保存段写入→读出逐字段一致
- [ ] 测试数据已清理或标注
- [ ] 汇报用语与实测段位一致

**⑥ 禁忌与易错点**：
- 禁止「演示能打开」冒充「功能可用」；
- 易错：测试数据用真实业务数据——污染底账，必须用可识别测试数据。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 验收段位 | 结构段＋保存段，缺一不可 | 材料原值 |
| 保存判定 | 写入→读出逐字段一致 | 材料原值 |

### 【财务监控全零是真状态】

**① 目标与适用场景**：监控页数字全零/全空时先定性再处置：区分「曾有数据而今消失」（丢数据，走恢复）与「数据表从未录入」（空表，解法是推动录入）。来源案例：实查发现底层表从未录入，全零即真状态。

**② 前置条件**：能查底层数据表的记录数与录入历史。

**③ 操作步骤**：
1. 查数据表当前记录数 → 判定信号：得到确切数字，不凭页面观感。
2. 查录入史/变更日志：该表历史上是否有过非零记录（表定位方法：从页面数据源反查接口与表名，通用步骤）；无录入史可查时按序找替代证据——历史备份、审计日志、页面历史版本 → 预期两种定性：从未有记录 → 空表；曾有而今无 → 丢数据 → 判定信号：定性有实查证据（记录数＋历史或替代证据）支撑；证据不足时禁止启动恢复（见④）。
3. 按定性分流：空表 → 报告「未录入」并推动录入，不做恢复；丢数据 → 按备份恢复流程走（第三章）并报告丢失范围 → 判定信号：动作与定性匹配。

**④ 失败分支**：录入史查不到、定性证据不足 → 报告「定性未定」与已查项，不许默认按丢数据做恢复（对空表恢复只会恢复出空表，还可能误伤）。

**⑤ 验收清单**：
- [ ] 已查记录数与录入史
- [ ] 定性结论有实查证据
- [ ] 处置动作与定性匹配

**⑥ 禁忌与易错点**：
- 禁止见全零就启动恢复；
- 易错：凭「感觉像没录过」下结论——定性必须有表级证据。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 定性两分 | 空表（从未录入）/ 丢数据（曾有而无） | 材料原值 |
| 空表处置 | 推动录入，不恢复 | 材料原值 |

### 【加载三态分明】

**① 目标与适用场景**：（界面实现条，材料只给状态规则，具体实现为通用步骤。）数据页面必须让「加载中 / 已加载有数据 / 已加载为空」三态视觉可辨，防止加载完成前闪现「台账（0 条）」被误读为数据丢失。

**② 前置条件**：页面有异步加载的数据区；能控制加载前占位形态。

**③ 操作步骤**：
1. 加载开始即显示明确的加载中状态，结论性元素（条数、金额等数字）不出终局形态 → 判定信号：加载期内页面无「0 条」类文案（通用步骤：以占位/骨架/加载提示实现）。
2. 加载成功有数据 → 显示数据与真实条数 → 判定信号：条数与接口返回一致（通用步骤）。
3. 加载成功为空 → 显示明确的空结果文案，与加载中形态明显不同 → 判定信号：空文案出现且加载指示已消失（通用步骤）。
4. 加载失败 → 显示失败状态并可重试，不得停在「0 条」形态 → 判定信号：失败文案与空结果文案可区分（通用步骤）。
5. 竞态处理：每次请求带序号，后发请求的结果才许落屏；先发请求的迟到响应直接丢弃，不许覆盖新状态；新请求发出时取消或忽略未完成的旧请求 → 判定信号：快速连续刷新时页面最终停在最后一次请求的结果上（通用步骤）。
6. 三态测试法：分别模拟慢加载（限速/延迟响应）、空结果与失败响应三种条件逐一验形态 → 判定信号：三种条件下形态与第 1–4 步定义逐一对上（通用步骤：用测试环境或拦截工具模拟，不动生产数据）。

**④ 失败分支**：现有组件无法区分三态 → 先以文案区分兜底（加载中明确写「加载中…」），并把组件改造记入待办；不许带着「闪 0 条」上线。

**⑤ 验收清单**：
- [ ] 加载期无结论性数字闪现
- [ ] 有数据/空/失败三态文案两两可辨
- [ ] 条数与返回数据一致

**⑥ 禁忌与易错点**：
- 禁止先渲染「0 条」再跳变；
- 易错：只给数据区做三态却让标题里的总数先行出数——结论性元素全域适用。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 状态集合 | 加载中/有数据/为空（三态必备，失败态为通用补全） | 材料原值 |
| 本条性质 | 规则条，实现为通用步骤 | 本卷标注 |

### 【工作台按真实业务改造】

**① 目标与适用场景**：（方法论条，材料只给原则，具体动作为通用步骤。）逐板块按各部门真实工作重构工作台，而不是按模板套壳；没有真实数据的板块宁可空着标注，不编数据。

- [ ] 汇报只含拍板项与卡住项

**⑥ 禁忌与易错点**：
- 禁止套壳式改造（字段对不上业务，板块必死）；

### 【晨报制度】

**① 目标与适用场景**：每日晨报给用户日常心跳感：短简报一份，含通道/服务状态与未结事项；安静的日子也发；未结项跨日滚动直到销项。

**② 前置条件**：有当轮实测的状态来源（巡检结果等）；有未结事项清单。

**③ 操作步骤**：
1. 备简报：只放实测状态与待办，写短 → 判定信号：每条状态可溯源到当轮实测，无凭印象写的「正常」（通用步骤）。
2. 未结事项全量带入：昨天未销项的逐条滚入今天 → 判定信号：与昨日清单比对，无无故消失项。
3. 需用户拍板的事项单独标出，不淹没在状态列表里 → 判定信号：拍板项有显式标记（材料原值）。

**④ 失败分支**：某状态当轮无法实测 → 写「未测」及原因，不许沿用昨日状态冒充今日实测。

**⑤ 验收清单**：
- [ ] 状态均为当轮实测
- [ ] 未结项无无故消失
- [ ] 拍板项单独标出
- [ ] 安静日同样发出

**⑥ 禁忌与易错点**：
- 禁止晨报写成流水账；

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|

### 【测试证据未采到如实记缺口】

**① 目标与适用场景**：测试汇报中，某项证据因故未采到（如浏览器硬超时被拆场，没来得及读计分板与服务端日志）时，明记缺口，不拿整体通过盖住单项缺口；复测优先补采。

**② 前置条件**：测试有预定的证据项清单（每项证据采或未采应可判定）。

**③ 操作步骤**：
1. 测试结束时逐项核对证据清单：每项标「已采/未采到」及未采原因 → 判定信号：清单无空白项。
2. 结论分两层写：已被其他独立信号闭环证明的部分照常下结论（如击杀链路由四路信号闭环）；未采项单列为缺口 → 判定信号：报告中缺口一节与结论一节分开（材料原值）。
3. 把缺口项排进复测计划并标优先补采 → 判定信号：复测清单含缺口项（通用步骤：写入待办）。

**④ 失败分支**：缺口项恰是某结论的唯一证据 → 该结论降级为「未证」，不许用其他部分的通过替它背书。

**⑤ 验收清单**：
- [ ] 证据清单逐项有采/未采标记
- [ ] 结论与缺口分层书写
- [ ] 缺口已排入复测并标优先

**⑥ 禁忌与易错点**：
- 禁止用「整体通过」覆盖单项缺口；
- 易错：记缺口不等于否定已证部分——两层分开，互不牵连。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 缺口处置 | 明记＋复测优先补采 | 材料原值 |
| 结论口径 | 已证与未采分层 | 材料原值 |

## 第五章 监控、证书与调度机制

### 【监控自托管选型】

**① 目标与适用场景**：给自有服务上可用性监控时的选型与安装：容器镜像不通时改走包管理器安装自托管监控工具；安装全程不许装出事故。

**② 前置条件**：有自有服务器可部署；知道要监控的目标清单。

**③ 操作步骤**：
1. 按可达性选安装渠道：镜像仓库可达用镜像；不通则改包管理器（如 npm）渠道安装 → 判定信号：安装包能完整获取，不在死渠道上反复重试。
2. 安装中若需修该工具自身的数据库补丁问题：先备份它的数据库再动手修 → 判定信号：备份文件存在且可读，之后才改库。
3. 选监听端口前先查占用：列出候选端口的现有占用者 → 预期：新端口无占用，或占用者是可动对象 → 判定信号：端口确定且不与他人既有服务冲突；被既有服务占用的端口不可动，另选。
4. 把本次验证过的安装基线记入工具笔记：工具名与锁定版本、安装命令、服务注册方式、数据目录、升级与卸载方法 → 判定信号：笔记可照着复现安装；换工具时另立基线，不共用含糊步骤（通用步骤）。
5. 装完自检：监控界面可达、能添加监控项 → 判定信号：实测打开成功（通用步骤）。

**④ 失败分支**：所选渠道也装不通 → 换渠道或换同类工具并报告，不许为装监控去动既有服务的端口/配置腾地方。

**⑤ 验收清单**：
- [ ] 安装渠道可达且安装完成
- [ ] 改库前已有数据库备份
- [ ] 监听端口无冲突、未动他人服务
- [ ] 监控界面实测可达

**⑥ 禁忌与易错点**：
- 禁止抢占他人既有服务端口；
- 易错：监控本身成为无人看管的盲区——其可用性纳入每日巡检（见【监控告警自托管】）。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 渠道优先级 | 镜像可达用镜像，否则包管理器 | 材料原值 |
| 改库前置 | 先备份数据库 | 材料原值 |
| 端口原则 | 先查占用，不动他人服务 | 材料原值 |

### 【子路径不行就回滚】

**① 目标与适用场景**：部署形态试错纪律：工具不支持目标形态（如某监控不支持挂子路径部署）时，干净回滚该形态，改走工具官方支持的形态（子域名＋独立证书）。

**② 前置条件**：试错前改动可逆、配置留底（回滚路先留好）。

**③ 操作步骤**：
1. 小步试形态：只做验证该形态是否可行的最小改动 → 判定信号：得到「可行/不可行」的明确证据，不靠猜（通用步骤）。
2. 判定不可行 → 立即回滚该形态的全部改动 → 判定信号：回滚后站点/服务恢复试错前状态，实测正常。
3. 改走受支持形态上线（子域名＋独立证书）→ 判定信号：新形态下功能实测可用。
4. 记录试错结论：该工具不支持何种形态、证据是什么 → 判定信号：记录留痕，后人不重试（通用步骤：记入工具笔记）。

**④ 失败分支**：回滚后状态未恢复 → 按事故处理：用留底配置逐项还原并报告；禁止在坏状态上叠加新形态改动。

**⑤ 验收清单**：
- [ ] 形态可行性有明确证据
- [ ] 不可行形态已干净回滚并复验
- [ ] 受支持形态上线可用
- [ ] 试错结论已留痕

**⑥ 禁忌与易错点**：
- 禁止与不支持的形态死磕打补丁；
- 易错：把「形态不行」误判成「工具不行」——回滚的是形态，不是选型。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 不支持形态处置 | 回滚 | 材料原值 |
| 替代形态 | 子域名＋独立证书 | 材料原值 |

### 【监控心跳打进业务轮次】

**① 目标与适用场景**：探活方式选择：把 Push 型心跳接入既有业务守望任务的每一轮第 0 步，监控「业务轮次真的在跑」，而不是只探端口存活。

**② 前置条件**：有周期性运行的业务守望任务；监控端支持 Push 型心跳（以「心跳按时到达」判活）。

**③ 操作步骤**：
1. 在守望任务的执行序最前面（第 0 步）加心跳打点：轮次一启动先发心跳，再干业务 → 判定信号：代码/任务定义中打点位于业务动作之前。
2. 监控端设置预期到达间隔、迟到宽限与缺失判定（宽限须小于一个轮次周期，具体值按守望任务实际周期与既有惯例设置，通用步骤）→ 判定信号：正常轮次下心跳按期到达、无误报（间隔数值材料未给）。
3. 做一次停轮验证：人为停一轮守望任务 → 预期：监控端报心跳缺失 → 判定信号：告警实际触发（通用步骤：验证后恢复轮次）。

**④ 失败分支**：心跳缺失告警响起 → 只说明轮次没跑起来；定因按【目标完成会暂停定时任务】的排查序查调度与服务，监控负责发现、不负责定性。

**⑤ 验收清单**：
- [ ] 打点位于每轮第 0 步
- [ ] 正常轮次无误报
- [ ] 停轮验证告警可触发

**⑥ 禁忌与易错点**：
- 禁止用独立探活脚本探端口冒充业务存活（进程僵死时端口可能还开着）；
- 易错：把打点放在业务动作之后——业务卡死时心跳照发，监控失明。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 打点位置 | 每轮第 0 步 | 材料原值 |
| 判活依据 | 心跳按时到达 | 材料原值 |

### 【监控告警自托管】

**① 目标与适用场景**：监控告警体系的归属原则：自托管开源工具落在自有服务器（子域名、独立证书、心跳接入巡检/业务轮次），业务运行状态数据不出门。

**② 前置条件**：有自有服务器；已按【监控自托管选型】完成工具安装。

**③ 操作步骤**：
1. 接入形态按工具支持情况选（见【子路径不行就回滚】）→ 判定信号：形态为子域名＋独立证书或工具官方支持形态。
2. 监控项覆盖自有业务系统：站点可用性＋业务轮次心跳（见【监控心跳打进业务轮次】）；每个监控项按模板登记：目标、检查间隔、预期状态/关键字，心跳类另加迟到宽限 → 判定信号：监控清单与业务清单对照无遗漏，模板字段齐全（数值按各业务实际周期填，通用步骤）。
3. 告警链配置齐：通知渠道与接收人、静默规则、升级顺序逐项写明，并做告警演练（人为触发一次，确认接收人实际收到）；演练按既有惯例定期重复（通用步骤）→ 判定信号：演练记录在案，告警记录可回查。
4. 监控工具自身纳入每日巡检范围 → 判定信号：巡检清单含监控工具可用性一项（材料原值）。
5. 历史数据与告警记录只存自有基础设施 → 判定信号：无第三方平台托管业务状态数据。

**④ 失败分支**：自托管工具长期不可用且修不好 → 报告并重新选型（仍限自托管开源），不许图省事改用第三方托管监控承载业务状态。

**⑤ 验收清单**：
- [ ] 接入形态为受支持形态
- [ ] 监控项覆盖业务系统与轮次心跳
- [ ] 监控自身在每日巡检内
- [ ] 状态数据未出自有设施

**⑥ 禁忌与易错点**：
- 禁止把业务系统状态（在线率、故障时段、服务清单）交给第三方平台；
- 易错：范围只限自有业务系统——与业务无关的公开服务状态不在此列。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 部署归属 | 自有服务器自托管 | 材料原值 |
| 接入形态 | 子域名＋独立证书＋心跳打点 | 材料原值 |

### 【证书日期以实查为准】

**① 目标与适用场景**：证书到期日以线上正在生效的证书实查为准；文档与提醒里的旧日期（旧证日期）一律作废，续期提醒跟着实查日期迁移。

**② 前置条件**：能查询线上生效证书（不是证书目录里躺着的文件）。

**③ 操作步骤**：
1. 查线上生效证书的签发日与到期日 → 判定信号：读到的是当前 serving 证书的日期（通用步骤：以 TLS 握手返回的证书为准）。
2. 与现有记录（提醒、台账）比对 → 预期：不一致时以实查为准，旧日期标作废 → 判定信号：记录只剩一个有效日期口径。
3. 迁移续期提醒：改提醒触发日期时，把提醒正文里写的证书事实（签发/到期）一并更新 → 判定信号：提醒的日期与正文事实一致，无「新日期＋旧正文」的半截更新。
4. 此类更正经用户一句批准即可执行 → 判定信号：不长篇请示（材料原值）。

**④ 失败分支**：线上证书与目录文件日期不一致 → 以线上为准，并报告目录里存在未启用证书的情况；不许拿文件日期当生效日期。

**⑤ 验收清单**：
- [ ] 到期日来自线上实查
- [ ] 旧日期已标作废
- [ ] 提醒日期与正文事实同步更新

**⑥ 禁忌与易错点**：
- 禁止引用转述或旧记录里的证书日期（转述出过误差，见分片【转述说法默认未验证】）；
- 易错：只改提醒时间不改正文——到期前按旧正文从容准备、新证先到期，是真实风险路径。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 事实源 | 线上生效证书实查 | 材料原值 |
| 提醒迁移 | 日期＋正文事实一起改 | 材料原值 |

### 【目标完成会暂停定时任务】

**① 目标与适用场景**：平台机制陷阱入册：把目标标记为完成会自动暂停其名下定时任务。守望任务静默（该跑没跑、无报错）时，先查调度与目标状态，再怀疑服务本身。

**② 前置条件**：有可查的调度器/目标状态；本条机制已入册可查。

**③ 操作步骤**：
1. 发现任务静默 → 第一步查调度器：任务是否被暂停、其所属目标状态是否被标完成 → 判定信号：得到「暂停/未暂停」明确状态。
2. 若因目标完成被暂停：确认该目标是否真的应完成 → 应完成则重新安排任务归属或恢复方式并报告；误标则恢复目标状态并验证任务复跑 → 判定信号：下一周期任务实际执行（通用步骤：以执行记录为准）。
3. 调度无异常再查服务本身（进程、日志）→ 判定信号：按序排查，不跳步（材料原值：先调度后服务）。
4. 新发现的平台机制坑当轮入册：机制、触发条件、排查序 → 判定信号：册子新增一条且可检索。

**④ 失败分支**：调度与服务都正常但任务仍不跑 → 报告已查项与现象，升级处理；不许反复重启服务碰运气。

**⑤ 验收清单**：
- [ ] 静默时先查调度/目标状态
- [ ] 恢复后有实际执行证据
- [ ] 新机制坑已入册

**⑥ 禁忌与易错点**：
- 禁止静默故障一上来就查服务代码；
- 易错：机制行为后续变更时要更新册子并标日期，旧结论不保留。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 机制 | 目标完成→自动暂停其定时任务 | 材料原值 |
| 排查序 | 调度器/目标状态 → 服务本身 | 材料原值 |

## 第六章 服务器接入、共机与服务退役拓扑

### 【服务器接入事实入册】

**① 目标与适用场景**：（本条仅写方法，实例细节禁入。）把服务器的正确接入方式记成入册事实：该机走云控制台免密登录（TAT 类通道），从来没有 SSH 密码。防的是后人（或未来的自己）反复用错方式试登录。

**② 前置条件**：接入方式已经用户确认或实测证实；有本地工具笔记可记。

**③ 操作步骤**：
1. 接入一律走控制台免密登录：界面路径为——云厂商控制台 → 实例列表 → 按工具笔记登记的实例名/标识选中目标实例 → 点「登录/远程登录」→ 免密终端打开（实例识别只凭名称与标识，不凭任何凭据）→ 判定信号：免密通道直接进终端，无密码环节；常见失败信号：控制台会话过期（重新登录控制台）、免密通道不可用（报告通道故障，不改走密码方式，见④）。
2. 两件不许做：不切 SSH 密码验证；不拿云平台账号密码试 SSH → 背景：都试过、都被拒、且被用户亲自纠正（材料原值）。
3. 把接入方式写进本地工具笔记：通道类型、登录入口、明确禁试的方式 → 判定信号：笔记可检索，接手者照记即可接入（通用步骤：笔记位置用本单位既有工具笔记文件）。

**④ 失败分支**：免密通道一时不可用 → 报告通道故障，等恢复或经用户指示换路；不许因为通道故障就回头试 SSH 密码。

**⑤ 验收清单**：
- [ ] 接入走免密通道
- [ ] 未尝试任何密码方式登录
- [ ] 接入事实已入工具笔记

**⑥ 禁忌与易错点**：
- 头号禁忌：拿平台账号密码试 SSH——既浪费轮次，也可能触发平台安全锁定；
- 易错：笔记只记方法与通道类型，绝不记任何凭据本身；凭据只走保险库。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 接入方式 | 控制台免密登录（TAT 类） | 材料原值（仅方法） |
| SSH 密码 | 不存在，禁试 | 材料原值 |

### 【发现他方架子不动】

**① 目标与适用场景**：多智能体共用一台服务器时，发现另一智能体先搭的架子（文件带对方指令署名）：原样不动、报告用户、由用户决定是否清理；本方部署绕开对方目录。

**② 前置条件**：能在部署/巡检中识别文件归属（署名、路径、时间线索）。

**③ 操作步骤**：
1. 发现疑似他方文件 → 先停对该目录的一切写操作 → 判定信号：本方动作绕开该目录进行。
2. 记录发现：位置、署名信息、文件概况（只读查看）→ 判定信号：记录足以让用户判断归属（通用步骤：只读不改）。
3. 当轮报告用户，附位置与署名 → 判定信号：报告已发出，是否清理由用户裁决。
4. 本方如需同名项目部署，另起独立目录 → 判定信号：本方目录与对方目录无重叠。

**④ 失败分支**：对方文件与本方部署硬冲突（如端口被占）→ 只报告冲突点，不先行动手；等用户裁决后再动。

**⑤ 验收清单**：
- [ ] 对方文件零改动
- [ ] 发现已当轮报告（含位置与署名）
- [ ] 本方部署已绕开

**⑥ 禁忌与易错点**：
- 禁止覆盖、清理或「顺手整合」对方文件；
- 易错：不动≠不报——不报等于让用户在不知情下长期共机。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 处置原则 | 不动＋报告＋等裁决 | 材料原值 |
| 本方部署 | 另起独立位置 | 材料原值 |

### 【旧服务退役删净验净且不误伤同端口服务】

**① 目标与适用场景**：按用户停用令退役旧服务：服务管理单元与程序目录一并删净、逐项验证不存在；动手前先查清其端口实际归属，防止误伤同端口的在用服务。材料案例：待退役服务的原端口当时已属另一在用转发服务，退役全程未误伤。

**② 前置条件**：有用户明确的停用决定；能查服务单元、程序目录与端口归属。

**③ 操作步骤**：
1. 动手前查端口归属：待退役服务记录中的端口，现在实际由哪个进程在用（以实际监听进程为证）→ 判定信号：归属明确；在用服务与退役对象不是同一个时，把该端口排除出退役动作范围。
2. 退役前归档与依赖检查：把服务单元定义与程序目录打包归档并验哈希（恢复方案即从此归档还原）；查依赖——活跃进程、定时器、套接字、其他服务对该目录的引用 → 判定信号：归档验活、依赖清单无未处置项。
3. 先停用服务并观察：停服后观察一段（时长按既有惯例，通用步骤），确认无业务报错、无他方调用，再进入删除 → 判定信号：观察期内无异常记录。
4. 删除服务管理单元，逐项确认后再删 → 判定信号：单元查询无此服务。
5. 删除程序目录，逐项确认 → 判定信号：目录不存在。
6. 逐项验证：单元不存在、目录不存在、原端口的在用服务（如有）仍正常 → 判定信号：三项实测结论齐全。
7. 退役结果写入当轮记录 → 判定信号：含删除范围、归档位置与验证结论（通用步骤）。

**④ 失败分支**：端口归属查不清 → 不动手，先报告；删除中发现目录里有不明新文件（疑似他方在用）→ 停，按【发现他方架子不动】报告。误删/误判恢复：从第 2 步归档还原单元定义与程序目录，恢复后验证服务可启动、端口归属正确，并写入记录。

**⑤ 验收清单**：
- [ ] 端口归属已查清，在用服务已排除
- [ ] 单元与目录均验证不存在
- [ ] 同端口在用服务复验正常

**⑥ 禁忌与易错点**：
- 禁止按旧记录对端口下手不查现状；
- 禁止自行扩大退役范围到「看起来没人用」的其他服务——那类只上报（维护者只负责执行质量，不决定退役范围）。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 删除范围 | 服务单元＋程序目录 | 材料原值 |
| 验证标准 | 删后逐项验证不存在 | 材料原值 |
| 前置检查 | 端口实际归属 | 材料原值 |

### 【联机反代剥前缀与服务端口图】

**① 目标与适用场景**：维护两件拓扑基础设施：联机服务经反向代理接入时路径前缀要剥净；每个内部服务的端口、静态根、线上副本位置记成一张端口图，部署排障按图走。

**② 前置条件**：能查看反向代理配置与各服务实际监听状态。

**③ 操作步骤**：
1. 反代接入新联机服务时配置前缀重写：每条规则登记四项——适用服务、匹配的外部前缀、重写后的目标路径、多条规则的执行顺序（材料教训：曾用一条剥不净、加到两条才干净；两条各自匹配什么必须逐条写明，不许只记条数）。改配置前留底旧配置；改后先做配置语法校验，校验通过才重载；重载失败立即用留底配置回滚。逐条验证剥离效果：用带前缀的外部路径请求接口 → 预期：请求落到服务根路径、接口正常返回 → 判定信号：接口非 404 且响应正确；剥不净的典型表现是接口 404 而服务本身正常。
2. 建/更新端口图，逐服务登记：服务名、内部端口、静态根目录、对外路径前缀、哪份客户端文件是线上副本 → 判定信号：图上每项与实查一致（通用步骤：以实际监听与配置为准核对）。端口图每次变更留变更记录（日期、变更人、差异），图本身按版本留存。
3. 此后部署按图找副本（配套【线上多副本全覆盖】）、排障按图找目录 → 判定信号：不再靠记忆报端口/路径。

**④ 失败分支**：图与实查不一致 → 以实查修正图，并报告差异（图错比没图更危险）；禁止以图压实查。

**⑤ 验收清单**：
- [ ] 新接入服务前缀剥离已实测
- [ ] 端口图字段齐全且与实查一致
- [ ] 副本信息已登记供部署引用

**⑥ 禁忌与易错点**：
- 禁止端口图记凭据——只记拓扑；
- 易错：一条 rewrite「看起来对了」就收工——必须用真实请求验剥离结果。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 前缀剥离 | rewrite 剥净（实测曾需两条） | 材料原值 |
| 剥不净表现 | 接口 404 而服务正常 | 材料原值 |
| 端口图字段 | 端口/静态根/前缀/线上副本 | 材料原值 |

## 第七章 名册与账号管理

### 【名册维护纪律】

**① 目标与适用场景**：人员进出当轮同步名册：离任移除、退二线标注、新人建号并登录验证；总人数以最新核定为准，旧数在所有引用处标作废。（本条人数为化名假数，方法为准。）

**② 前置条件**：人事变动消息来自正式渠道——指用户直接通知、正式人事文件或单位正式渠道发布，三者之外（口头风声）只登记待核，不先改册（见④）。总人数的全部引用位置已列清单，改数时逐处同步。

**③ 操作步骤**：
1. 离任者：当轮从名册移除 → 判定信号：名册检索无此人。其账号按处置矩阵当轮办结并在记录中写明方式（停用/删除/保留观察，三选一，依本单位既有规矩；规矩未覆盖的情形先报告确认，不许悬空）。
2. 退二线者：标注状态，不删除 → 判定信号：名册中状态字段已更新。
3. 新到任者：当轮建号（按【账号命名约定】）并实际登录验证 → 判定信号：登录成功才算建成。
4. 总人数更新：以最新核定数为准；旧总数在所有引用处标作废 → 判定信号：检索旧数，出现处均有作废标注（历史叙述除外）。

**④ 失败分支**：变动消息来源不正式（风声、未确认调动）→ 只登记待核，不改名册；新人登录验证失败 → 标「未建成」继续处理，不许报建成。

**⑤ 验收清单**：
- [ ] 离任/退二线/新人三类变动均当轮处置
- [ ] 新人已登录验证
- [ ] 总数单一口径，旧数已标作废

**⑥ 禁忌与易错点**：
- 禁止攒批同步——名册是权限与联络底账，滞后即出事（已离任者仍能登录、新任者无号可用）；
- 易错：两套总数并行流通——引用数字的材料会互相矛盾。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 同步时限 | 当轮 | 材料原值 |
| 退二线处置 | 标注不删除 | 材料原值 |
| 人数口径 | 最新核定数为准，旧数标作废 | 材料原值（数字已化名） |

### 【双名册对账】

**① 目标与适用场景**：同一批人有两份名册（账号表与联系人表）时定期对账：人数一致、姓名集合一致，差额逐个定位当轮修平。

**② 前置条件**：能同时读取两份名册。

**③ 操作步骤**：
1. 比人数：两份总数 → 判定信号：相等或差额明确。
2. 比姓名集：做集合差（甲有乙无、乙有甲无）→ 判定信号：差集逐人列出。
3. 逐个定位差额原因（漏建、未删、改名未同步）→ 当轮修平 → 判定信号：修后重跑第 1、2 步，差为 0。
4. 留对账记录：日期、差额、原因、处置 → 判定信号：记录可检索（通用步骤）。

**④ 失败分支**：某差额原因查不清（不知此人应否在册）→ 标待核并报告，不许为凑平数字擅自增删。

**⑤ 验收清单**：
- [ ] 人数与姓名集双一致
- [ ] 差额逐个有原因与处置
- [ ] 对账记录已留存

**⑥ 禁忌与易错点**：
- 禁止只比人数不比姓名集——人数相等也可能一进一出错位；
- 易错：对账只核存在性与一致性；职务、电话等字段对错按各自来源核，不在对账轮顺手改。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 对账项 | 人数＋姓名集合 | 材料原值 |
| 差额处置 | 当轮修平并留痕 | 材料原值 |

### 【分工未定不落结构】

**① 目标与适用场景**：人事接任时「新人全部顶前任工作」只是口径层结论；具体分管、工作组归属、界面组名在正式分工文件到达前一律不动、不猜。

**② 前置条件**：已收到接任口径；分工文件未到。

**③ 操作步骤**：
1. 记录层记下接任口径（谁接谁、口径来源）→ 判定信号：记录存在且标「具体分工待文件」（通用步骤）。
2. 系统侧结构冻结：分组、侧边栏组名、权限归属保持原状 → 判定信号：无任何结构变更发生（与【侧边栏只动条目】联动）。
3. 被问到具体分工时如实答「未定、待文件」→ 判定信号：不输出猜测性归属。
4. 分工文件到达后，按文件一次性落结构，并逐项与文件核对 → 判定信号：结构与文件逐项一致。

**④ 失败分支**：等待期间业务急需明确归属 → 报告用户裁决个案，不许以个案裁决为由推测性改全套结构。

**⑤ 验收清单**：
- [ ] 接任口径已记录待文件
- [ ] 文件到达前结构零变更
- [ ] 文件到达后按文件落结构并核对

**⑥ 禁忌与易错点**：
- 禁止按猜测落结构——返工之外，猜测期的错误归属可能已影响真实流转（材料派错组、权限给错人）；
- 易错：不落结构≠不服务——新人账号照建、个人工作照常支持，冻结的只是组织归属层。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 冻结范围 | 分管/工作组/组名/权限归属 | 材料原值 |
| 解冻条件 | 正式分工文件到达 | 材料原值 |

### 【名字纠正全库同步】

**① 目标与适用场景**：用户纠正人名同音错字后（如某姓被误写为同音另一姓、某名末字误写同音字，均已化名），同步改遍全部名册文件并留痕，不许只改被指出的那一处。（实例字形已化名，方法为准。）

**② 前置条件**：已确认正确写法与对象（同名异人时先按证件/上下文区分）。

**③ 操作步骤**：
1. 全库检索错写法的全部出现点（名册、联系人表、历史材料）→ 判定信号：出现点清单完整。
2. 逐份改对 → 判定信号：逐份回读，正确写法命中、错写法零残留（历史叙述中作为「曾经错过」的记载除外）。
3. 纠正记入长期记忆作为该人标准写法 → 判定信号：记忆中有该条（通用步骤：按本单位记忆机制）。
4. 服务器上的两份名册文件同步改并留痕 → 判定信号：两份文件均已改（材料原值）。

**④ 失败分支**：检索发现同名异人共用同一错写法风险 → 逐人区分后再改，禁止全局替换误伤他人。

**⑤ 验收清单**：
- [ ] 出现点清单完整
- [ ] 逐份改对且回读零残留
- [ ] 标准写法已入长期记忆

**⑥ 禁忌与易错点**：
- 禁止只改被当场指出的那一处——其他文件里的错字会继续繁殖到新材料；
- 易错：再犯同一个错＝没记住，这是被用户明确点过的账。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 同步范围 | 全部名册与引用文件（材料为服务器两份文件） | 材料原值 |
| 判定 | 错写法零残留（历史记载除外） | 材料原值 |

### 【口径纠正全域追改】

**① 目标与适用场景**：用户纠正任何口径（人名、数字、日期）后，追改所有引用旧口径的记录与待办状态，不只改被指出的那处。

**② 前置条件**：新口径已明确（值＋生效范围）。

**③ 操作步骤**：
1. 在全部档案（记忆、台账、待办、草稿）检索旧口径出现点 → 判定信号：出现点清单完整。
2. 逐处改为新口径，或标注作废 → 判定信号：逐处有处置。
3. 复查检索：旧口径零残留 → 判定信号：复查结果为 0（历史记录原文除外，见⑥）。
4. 待办状态联动：依赖旧口径的待办按新口径更新状态 → 判定信号：待办无按旧数准备的残留（通用步骤）。

**④ 失败分支**：某出现点改与不改有争议（如已发出的材料）→ 标待裁并报告，不许默默改或默默留。

**⑤ 验收清单**：
- [ ] 出现点清单完整且逐处处置
- [ ] 复查零残留
- [ ] 关联待办已联动更新

**⑥ 禁忌与易错点**：
- 禁止篡改历史：当日日志等历史记录保留原文，其后补记纠正，不回头改写已发生的记录；
- 易错：旧口径残留在待办里最危险——会按旧数备料、旧日期行事。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 追改范围 | 全部引用记录＋待办状态 | 材料原值 |
| 历史记录 | 保留原文、补记纠正 | 材料原值 |

### 【账号命名约定】

**① 目标与适用场景**：工作台账号建号规矩：用户名＝姓名全拼（小写拼音），全员统一；建成以实际登录验证为准；密码变更类问题以系统字段实查回答。

**② 前置条件**：新人姓名已确认（写法以名册为准）。

**③ 操作步骤**：
1. 按约定生成用户名：姓名全拼小写 → 判定信号：与名册姓名拼音一致（通用步骤：多音字以本人确认或既有惯例为准）。
2. 在系统管理后台建号（入口按环境参数卡）；初始凭据按系统规则生成，只经既有安全渠道交付本人，不写进任何名册或记录 → 判定信号：系统记录创建成功（这只是中间状态）。
3. 实际登录验证一次 → 预期：登录成功进入系统 → 判定信号：登录成功才算建成；失败则标未建成继续处理。
4. 被问「谁改过密码」类问题时，查系统字段（如密码变更时间戳）再回答 → 判定信号：回答带字段实查结果，不凭印象。

**④ 失败分支**：用户名与既有账号冲突（同名同拼）→ 报告并按用户裁决加区分方式，不许自创命名规则全库扩散。

**⑤ 验收清单**：
- [ ] 用户名符合全拼约定
- [ ] 登录验证通过
- [ ] 账号问题均以字段实查回答

**⑥ 禁忌与易错点**：
- 禁止以「记录创建成功」冒充建成；
- 易错：历史账号不符合约定的不强制改名（影响登录习惯与引用），在名册标注对应关系即可。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 用户名规则 | 姓名全拼（小写拼音） | 材料原值 |
| 建成判据 | 实际登录验证成功 | 材料原值 |
| 密码状态判据 | 系统字段实查（字段名以系统实际为准；定位方法：查账号记录中的密码变更时间字段） | 材料原值（字段名为示例） |

### 【不推改密】

**① 目标与适用场景**：（纪律条，材料只给原则，具体动作为通用步骤。）系统无强制改密机制、且用户明确不推动时，服务对象初始密码现状留置，不自发组织改密催促。注意：本条是纪律条，没有配套的系统操作流程，不要据此寻找「改密处置入口」；唯一的动作通道是安全事件上报（见④）。

**② 前置条件**：用户已就此事明示表态；无强制改密机制（两个条件同时成立才适用本条）。

**③ 操作步骤**：
1. 不把改密塞进日常通知、不发改密催促 → 判定信号：通知清单无改密类条目（通用步骤）。
2. 有人主动问改密方法时，正常指导 → 判定信号：个案咨询照常服务（材料原值）。
3. 用户表态或机制变化时，本条适用性重估并留痕 → 判定信号：记录有更新（通用步骤）。

**④ 失败分支**：出现明确账号被盗用迹象 → 不适用「不推」：按安全事件立即上报用户，由他决定处置。

**⑤ 验收清单**：
- [ ] 无自发改密催促发出
- [ ] 个案咨询正常指导
- [ ] 盗用迹象（如有）已按安全事件上报

**⑥ 禁忌与易错点**：
- 禁止以安全洁癖自发搞「安全运动」——无机制支撑的推动只制造无效沟通、消耗一线信任；
- 易错：留置≠无视风险，安全事件通道独立于本条。

**⑦ 参数表**：
| 参数 | 取值 | 出处 |
|---|---|---|
| 默认动作 | 留置不推 | 材料原值 |
