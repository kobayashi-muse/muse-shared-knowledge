# 卷三后半 · 操作规程版（联机与各游戏具体坑，156 条）

本卷是总结稿的操作级升级版：每条都改成可直接执行的规程，固定七段——①目标与适用场景 ②前置条件 ③操作步骤（每步：动作→预期现象→判定信号）④失败分支（现象→根因→处置）⑤验收清单（注明测试怎么组织才算真验）⑥禁忌与易错点 ⑦参数表（原值保留）。参数与手法只取自原始记录；原记录未给出细参数的条目已在节内标注「通用步骤」，执行时按该节验收清单实测标定，严禁凭经验编造数值。本轮修订中补入的规程性数值一律标注「示意值/示意规程」，与原记录原值分开，不许混引。

**读法**：第九章是前八章的验收工具箱（校验和、整场模拟、协议级测试、木偶收敛等方法都被前八章当作既定工具引用），建议先通读第九章再按章执行。少数条目引用了其他卷的方法（卷一验证分账、卷三前半性能章、卷五部署纪律），已在条内附最小自洽说明，只持有本卷也可执行。

**术语·三种 ping 先分清**：本卷「ping」有三义，严禁混用——（a）**RTT 探针 ping**：服务器每 2s 发、兼测 RTT 供迁移排序（见【候选人按 RTT 排序】），不作判死依据；（b）**协议保活 ping**：协议层 25s 周期保活，防静默掐断（见【静默掐断要有保活】）；（c）**应用层 ping/pong**：应用消息层的心跳对，与（b）双保活并行，周期见【静默掐断要有保活】⑦。【预发延迟分档】开局测 RTT 用的是与（a）同机制的开局加密采样，不是新的一种。

## 第一章 联机架构与同步（18 条）

### 【协议层可脱离画面验】

**①目标与适用场景**：在自动化浏览器/软件渲染环境跑不动画面（rAF 不推进、帧率极低）时，仍然把联机协议验完：连接、快照收敛、移动同步、击杀一致。适用于一切「环境证明不了画面、但必须给联机结论」的场合。

**②前置条件**：联机服务已启动且端口可达；至少两个可编程客户端（脚本客户端或无头页面）；服务端日志可读；被测构建的版本号/文件校验值已记录。

**③操作步骤**：
1. 两端脚本客户端连接服务器并加入同一房间→预期：服务器日志出现两条连接与入房记录→判定信号：日志中房间成员数=2。
2. 房主端开局→预期：两端均收到开局快照→判定信号：两端快照的实体列表长度一致。
3. 在一端把某实体传送到已知坐标，等待至少 3 个快照广播周期（20Hz 即 ≥150ms）再采样→预期：另一端该实体坐标收敛到设定点→判定信号：两端坐标逐值相等（不是「差不多」）；采样早于 3 个周期读到的未收敛值不作数。
4. 一端脚本驱动角色直线移动固定时长后停下→预期：另一端复现相同位移→判定信号：最终坐标逐值一致；位移差容差定义＝一个快照周期内的最大位移量（移动速度×50ms），位移差≤该容差且最终坐标一致才算过——不许自创其他容差数值。
5. 一端击杀另一端目标→预期：击杀播报、击杀数、阵亡数三处同步变化→判定信号：击杀方击杀数+1、被杀方阵亡数+1、播报文本一致。
6. 把本轮未能验的画面项（渲染、帧率、手感）逐条写进报告「未验证」栏→判定信号：报告里协议结论与环境局限分开陈述。

**④失败分支**：
- 现象：快照不收敛→根因：快照广播未启动或房主权威未确立→处置：查服务器广播定时器与房主标识，先修开局流程再重测。
- 现象：击杀数不一致→根因：击杀记账只在客户端本地加、服务器未记账→处置：击杀事件改为上报服务器记账后广播。
- 现象：脚本客户端连不上→根因：把画面环境问题误判为协议问题→处置：先用裸 WebSocket 客户端直连验证端口与握手，再谈页面。

**⑤验收清单**：
- [ ] 两轮独立执行（关掉重来），五项信号（入房/快照/收敛/移动/击杀）两轮全过才算通过；
- [ ] 验收组织：协议级脚本测试，不以截图或「看见对方」为证据；
- [ ] 报告明确标注环境局限与未验证项。

**⑥禁忌与易错点**：不许用「页面打开了、能看见人」冒充协议验收；不许把软件渲染环境的低帧率写成产品缺陷；不许只跑一轮就下结论。

**⑦参数表**：快照广播 20Hz（见【房主权威+服务器记账】）；收敛判定=等≥3 个广播周期后坐标逐值相等；位移容差=速度×单周期时长；轮次=2。

### 【容量档位单独排轮】

**①目标与适用场景**：多人容量测试（如 5v5、10 个客户端）耗时量级远超普通回归，必须单独排一轮、给足墙钟预算，不能塞进普通回归顺带跑。适用于一切客户端数≥4 的联机验证。

**②前置条件**：普通双人回归已通过；机器算力现状已知（核数、是否软件渲染）；容量测试脚本具备分阶段日志输出（不是只在结尾输出一行）。

**③操作步骤**：
1. 先估算单客户端在当前环境的启动与跑满时长→预期：得到每阶段耗时量级→判定信号：估算值写进排轮单，总预算≥各阶段之和×1.5。
2. 单独创建一轮任务，只跑容量档位，不与其它回归混跑→判定信号：任务说明中明确客户端数与目标时长。
3. 脚本按阶段打日志（连接→入房→开局→同步→击杀）→预期：任一阶段卡住能定位→判定信号：日志时间戳间隔可见。
4. 跑完后逐阶段核对耗时与结果→判定信号：每阶段都有起止时间与通过/未判定结论。
5. 未跑到的阶段写「未判定」，不写通过也不写失败→判定信号：报告中容量结论与双人结论分开。

**④失败分支**：
- 现象：几十分钟零输出被误判卡死→根因：脚本只在结尾输出一行＋本机算力饱和→处置：改分阶段日志后重跑，先查 CPU 占用再怀疑产品。
- 现象：容量轮挤占普通回归时间导致两边都超时→根因：排轮合并→处置：拆轮，容量单独成轮。

**⑤验收清单**：
- [ ] 排轮单存在且预算按量级放大；
- [ ] 分阶段日志齐全；
- [ ] 未跑阶段如实标「未判定」。

**⑥禁忌与易错点**：不许把容量未验写成「应该没问题」；不许在饱和机器上用双人回归的时长经验推断容量轮时长。

**⑦参数表**：参考量级：本环境双客户端 3D 联机**全程回归**约 45 分钟（软件渲染、1.5 核，多机制全跑）；5v5 **容量单项**一轮预算约 40 分钟起（只验容量链路、阶段少于全程回归，故预算下限可低于双人全程——两数口径不同，不可直接比大小）；均按环境标定。

### 【内容追加只许末尾】

**①目标与适用场景**：给已上线联机游戏新增角色/场景/武器时，保证旧客户端与新客户端索引不串位。适用于一切「联机只传索引、不传全量定义」的系统。

**②前置条件**：已摸清哪些数组是联机索引源（角色表、场景表、武器表）；有旧版本客户端可做对照。

**③操作步骤**：
1. 列出全部联机索引数组并冻结现有顺序→判定信号：清单与代码逐一对应。
2. 新内容只 append 到数组末尾，既有元素不移动、不改名、不删除→预期：旧索引含义不变→判定信号：diff 显示只有尾部新增行。
3. 新旧两端各选一个旧索引实体进同一局→预期：两端显示同一实体→判定信号：截图/快照实体 id 与名称一致。
4. 新端选新增索引、旧端旁观→预期：旧端至少不崩溃（降级表现可接受）→判定信号：旧端无 pageerror。

**④失败分支**：
- 现象：两端同一索引显示不同角色→根因：有人在数组中间插入或重排→处置：回滚顺序，改为末尾追加并全员更新构建。
- 现象：删除下架内容导致后续索引整体前移→根因：把「下架」做成物理删除→处置：保留占位、只在选择界面隐藏。

**⑤验收清单**：
- [ ] 索引数组 diff 只有尾部追加；
- [ ] 新旧端同索引实体一致实测通过；
- [ ] 下架走隐藏不走删除，有登记。

**⑥禁忌与易错点**：不许顺手「整理」数组顺序；不许在联机索引数组里做删除。

**⑦参数表**：无数值参数；规则=append-only。

### 【LOD 预留钩子】

**①目标与适用场景**：联机实体未来要按距离/性能切换高低模时，提前在协议与渲染层留好钩子，避免日后改协议。适用于模型面数高、远端实体多的联机场景。

**②前置条件**：实体快照结构可扩展字段；渲染层创建网格的入口唯一或可收口。

**③操作步骤**：
1. 在实体协议结构中预留 quality 字段，服务器只原样透传、不解释→判定信号：抓包可见字段往返不变。
2. 渲染层只留一个 applyQualityMesh(entity, quality) 切换点，所有换模走此函数→判定信号：全仓搜索换模调用只此一处。
3. 在切换点加 mpLockMesh 守卫：联机模式下单机侧的「自动升级画质」逻辑不得把已降档网格顶回高模→预期：联机中切档后网格保持→判定信号：联机对局内抓取实体网格面数不回升。
4. 单机模式回归一遍自动画质→判定信号：单机升降档行为与改前一致。

**④失败分支**：
- 现象：联机中远端角色模型被自动升回高模导致卡顿→根因：守卫缺失、单机自动画质逻辑在联机也跑→处置：切换点加联机守卫并回归。
- 现象：多处代码各自换模→根因：切换点未收口→处置：收口到单一函数再加守卫。

**⑤验收清单**：
- [ ] quality 字段透传抓包验证；
- [ ] 换模调用点全仓唯一；
- [ ] 联机/单机各回归一轮。

**⑥禁忌与易错点**：服务器不许解释 quality 字段（保持零逻辑透传）；不许为省事把守卫写在调用方各处。

**⑦参数表**：字段名 quality；守卫名 mpLockMesh；切换点 applyQualityMesh（命名供参考，实现以本节语义为准）。

### 【房主权威+服务器记账】

**①目标与适用场景**：联机分工定版：Bot AI 只在房主客户端跑；服务器只记账（血量/击杀/比分/复活计时）并以 20Hz 广播快照，服务器保持零依赖极简。适用于小规模娱乐局联机原型。

**②前置条件**：服务器只依赖标准库/极简依赖可独立启动；客户端具备完整地图/寻路/弹道数据；房间与房主标识机制已定。

**③操作步骤**：
1. 服务器实现房间管理＋记账字段（hp/kills/score/respawnTimer）→判定信号：单元级协议测试可读写记账。
2. 房主客户端跑全部 Bot AI 并上行 Bot 位姿→预期：非房主端能看到 Bot 移动→判定信号：木偶坐标收敛（见【协议层可脱离画面验】）。
3. 任一客户端上报命中→服务器校验后改账并广播→判定信号：两端血量/比分一致。
4. 服务器以 20Hz 广播全量快照→判定信号：抓包测得广播间隔约 50ms。
5. 断开房主→预期：对局按已知代价结束或走迁移（见迁移章）→判定信号：行为与设计声明一致，不假装无感。

**④失败分支**：
- 现象：两端比分不一致→根因：客户端本地改账未走服务器→处置：所有记账收口服务器，客户端只显示。
- 现象：服务器 CPU 打满→根因：把模拟逻辑放进了服务器→处置：迁回房主端，服务器恢复只记账。

**⑤验收清单**：
- [ ] 记账字段四项两端一致实测；
- [ ] 广播频率抓包≈20Hz；
- [ ] 服务器依赖清单为零/极简，有据可查。

**⑥禁忌与易错点**：不许在服务器里写第二套游戏逻辑；不许客户端本地记账后再「同步」给服务器。

**⑦参数表**：快照广播 20Hz（间隔 50ms）；记账字段：血量、击杀、比分、复活计时。

### 【Bot 不放服务器的理由】

**①目标与适用场景**：立项评审时决定 Bot 模拟放客户端还是服务器，给出可复核的决策依据与代价声明。⚠ 本条原记录为决策论证，具体阈值须按本节验收清单在评审时标定（通用步骤）。

**②前置条件**：已盘点 Bot 依赖的数据（地图/寻路/弹道）在客户端与服务器的分布；已估算服务器重写成本。

**③操作步骤**：
1. 列 Bot 依赖清单：地图几何、寻路图、弹道表、感知规则→判定信号：每项标注现存位置（客户端/服务器/两处）。
2. 估算服务器重写工作量与双份逻辑维护成本→判定信号：给出人日量级与「双份逻辑必漂移」的风险说明。
3. 写明选择客户端方案的代价：房主负载高、房主退出即解散（或需迁移机制）→判定信号：代价条目进入设计文档「已知代价」节。
4. 给出反转条件：何时必须改服务器权威（如对外公开运营、反作弊要求）→判定信号：触发条件可判定。

**④失败分支**：
- 现象：评审只谈好处不谈代价→根因：决策记录缺代价栏→处置：补齐代价与反转条件再评审。
- 现象：后期被迫服务器跑 Bot 时发现数据只在客户端→根因：立项未盘点数据分布→处置：回到第 1 步补盘点，评估数据下发方案。

**⑤验收清单**：
- [ ] 决策文档含依赖清单、成本估算、代价、反转条件四项；
- [ ] 代价已如实写入对外说明（如适用）。

**⑥禁忌与易错点**：不许把原型期取舍包装成长期架构；不许隐瞒「房主走即解散」。

**⑦参数表**：无原值参数；成本与阈值按项目标定。

### 【延迟型同步的取舍】

**①目标与适用场景**：格斗类强实时联机在「延迟型输入同步」与「回滚同步」之间选型。结论：选延迟型；回滚要求引擎完全确定性＋全状态可序列化，改造量约为延迟型的 3–5 倍；同城/局域网 RTT 多 <50ms 时，3 帧输入延迟可接受。两条判据分工：P95 ≤100ms 是**选型成立线**（超过则延迟型不成立、按反转条件重评）；RTT 多 <50ms 是**体验舒适线**（在成立线以内、舒适线以外能玩但输入感变钝）——两条不是一回事，不许并读成一条。

**②前置条件**：已测目标用户群 RTT 分布；引擎确定性现状已知（随机源、浮点用法已盘点，见【随机调用逐行盘点】【浮点确定性风险】）。

**③操作步骤**：
1. 实测 RTT 分布→判定信号：P50/P95 有数，若 P95 ≤100ms 延迟型成立。
2. 按【预发延迟分档】实现输入预发与配对消费→判定信号：协议级测试两端输入序列对齐。
3. 用【校验和同步验证】长跑一局→判定信号：mismatch=0。
4. 把取舍与代价（高延迟下输入感变钝）写进设计文档→判定信号：文档含改造量对比 3–5 倍与适用 RTT 上限。

**④失败分支**：
- 现象：跨城对局输入延迟不可接受→根因：超出延迟型适用域→处置：按文档反转条件重评回滚或缩减对局半径，不硬撑。
- 现象：两端偶发脱同步→根因：确定性缺口而非同步模型问题→处置：先查随机源与浮点，再谈换模型。

**⑤验收清单**：
- [ ] RTT 实测数据在档；
- [ ] 校验和长跑 mismatch=0；
- [ ] 取舍文档含代价与反转条件。

**⑥禁忌与易错点**：不许未测 RTT 就选型；不许把回滚的改造量低估成「加个环形缓冲」。

**⑦参数表**：回滚改造量≈延迟型 3–5 倍；延迟型成立线：P95 ≤100ms；体验舒适线：RTT 多 <50ms（同城/局域网）；可接受预发延迟 3 帧（60fps 约 50ms）。

### 【输入序号与帧号解耦】

**①目标与适用场景**：延迟型同步中，两端对齐的基准是「引擎成对 poll 的消费序号」，不是游戏帧号。顿帧（hitstop）tick 不消费输入，双方按消费顺序对齐即可，不必帧帧对齐。适用于一切带顿帧/慢镜的格斗同步。

**②前置条件**：引擎输入接口为 poll 式成对消费；每对输入带自增序号。

**③操作步骤**：
1. 给每对已消费输入打自增序号 seq→判定信号：日志中 seq 严格递增、无跳号。
2. 同步层按 seq 配对两端输入再喂引擎→预期：顿帧期间 seq 不增长、恢复后继续→判定信号：顿帧前后两端 seq 序列一致。
3. 校验和按 seq 节点计算而非帧号（见【校验和同步验证】）→判定信号：长局 mismatch=0。
4. 构造顿帧密集场景（连续命中）跑一局→判定信号：无脱同步、无输入丢失。

**④失败分支**：
- 现象：顿帧后两端动作错位→根因：按帧号对齐、顿帧帧被一端计入→处置：改按消费序号对齐并回归。
- 现象：某端 seq 跳号→根因：poll 在异常路径重复消费或丢弃→处置：消费点收口为唯一入口。

**⑤验收清单**：
- [ ] seq 日志递增无跳号；
- [ ] 顿帧场景长局 mismatch=0；
- [ ] 校验和锚点为 seq 而非帧号（代码可查）。

**⑥禁忌与易错点**：不许用渲染帧号当同步锚；不许在多个地方消费输入队列。

**⑦参数表**：锚点=成对 poll 消费序号；校验和节拍见【校验和同步验证】（每 30 对输入一次）。

### 【预发延迟分档】

**①目标与适用场景**：延迟型同步中每端预发 delay 个输入，delay 按开局实测 RTT 定档；对局中自适应只改采样提前量、不动已配对序列。适用于 RTT 波动的局域网/同城对局。

**②前置条件**：开局有 RTT 测量通道（RTT 探针 ping 的开局加密采样，见卷首术语）；输入队列支持预发与提前量调整。

**③操作步骤**：
1. 开局测 RTT：连采 10 次取中位数（采样规程，防单次尖峰定档）→判定信号：RTT 中位数落档。
2. 按档设 delay：≤40ms→2；≤100ms→3；>100ms→4（delay 上限即 4，不再加档；中位数 >300ms 时本局已超出延迟型适用域，按【延迟型同步的取舍】反转条件提示重评）→判定信号：两端 delay 一致（由服务器下发或房主广播）。
3. 对局中持续采样 RTT，只调整「采样提前量」→预期：已配对输入序列不回改→判定信号：seq 序列连续、校验和不 mismatch。
4. 跨档抖动时加迟滞再调档：须连续 3 个采样窗（每窗取中位数）的中位数都落在新档才调档，单窗跨档不调（迟滞规则为标定规程，窗长按采样节奏登记）→判定信号：调档次数有限、不来回横跳。

**④失败分支**：
- 现象：调档后立即脱同步→根因：改动了已配对序列→处置：回滚为只改提前量。
- 现象：高 RTT 端总慢半拍→根因：两端 delay 不一致→处置：delay 由权威方统一下发。

**⑤验收清单**：
- [ ] 三档边界各测一局（人为注入延迟）；
- [ ] 对局中调档不产生 mismatch；
- [ ] delay 两端一致可查。

**⑥禁忌与易错点**：不许按单次 ping 尖峰定档；不许两端各自定档。

**⑦参数表**：RTT ≤40ms→delay 2；≤100ms→delay 3；>100ms→delay 4（上限）；采样=开局连采 10 次取中位数；调档迟滞=连续 3 窗同档才调。

### 【快照校正与重连共用重演】

**①目标与适用场景**：校验和不一致的快照校正、断线重连、页面刷新恢复，三者共用同一套「按 pair 日志重演」机制：服务端保留完整输入日志，回归者从零重演追赶（自动加速步进并静音）。

**②前置条件**：服务器保存全场 pair 输入日志；引擎可无渲染步进（逻辑与渲染可分离调用）；重演可加速且静音。

**③操作步骤**：
1. 服务器按 seq 顺序落盘/缓存全部 pair 输入→判定信号：日志长度=当前 seq。
2. 触发任一恢复路径（mismatch 校正/断线重连/刷新）→客户端从 seq=0 以加速步进重演→预期：重演期间静音、无输入接受→判定信号：重演速度>实时且声音关。
3. 追赶到最新 seq 后做校验和比对→判定信号：与权威端一致才切回实时。
4. 切回实时并恢复声音/输入→判定信号：后续 seq 继续递增、再无 mismatch。

**④失败分支**：
- 现象：重演追不上（对局还在跑）→根因：加速倍率不足或日志太长→处置：提高步进倍率；超长局考虑中途快照点（须另立项，不临时发明）。
- 现象：重演后仍 mismatch→根因：日志本身缺失或引擎非确定性→处置：先查日志完整性，再查随机源盘点。

**⑤验收清单**：
- [ ] 三条路径（校正/重连/刷新）各实测一次并通过；
- [ ] 重演期静音与禁输入可验；
- [ ] 追赶后校验和一致。

**⑥禁忌与易错点**：不许为三条路径各写一套恢复逻辑；不许重演期出声或接受本地输入。

**⑦参数表**：日志=全场 pair 输入；重演=从零、加速、静音。

### 【种子化 RNG 兜底】

**①目标与适用场景**：联机开局把 Math.random 替换为服务器下发种子驱动的 mulberry32，离开对局恢复，保证现存与未来所有随机消费两端同序列。

**②前置条件**：可替换全局随机入口；种子由服务器下发并随开局消息到达。

**③操作步骤**：
1. 开局消息携带种子→客户端保存原始 Math.random 并替换为 mulberry32(seed)→判定信号：同种子两端连续取数序列逐值相等（脚本断言，取数个数取前 1,000 个逐值比对）。
2. 对局内全部随机消费走替换后入口→判定信号：全仓 grep 无绕过入口的直调残留（如自带随机 API 的库调用须登记）。
3. 离开对局恢复原始 Math.random→判定信号：单机模式随机行为正常。
4. 与【校验和同步验证】联跑长局→判定信号：mismatch=0。

**④失败分支**：
- 现象：中期开始 mismatch→根因：某库内部自带随机源未替换→处置：登记该调用点，改走统一入口或将其移出逻辑层。
- 现象：单机模式随机「不随机」→根因：离开未恢复→处置：恢复逻辑挂到所有退出路径（含异常退出）。

**⑤验收清单**：
- [ ] 同种子序列逐值相等断言通过；
- [ ] 进入/退出各回归一次；
- [ ] 长局 mismatch=0。

**⑥禁忌与易错点**：不许只替换「已知的」随机调用而不做全仓盘点；种子不许客户端自选。

**⑦参数表**：算法 mulberry32；种子来源=服务器下发。

### 【随机调用逐行盘点】

**①目标与适用场景**：下「同步可成立」结论之前，逐行盘点全代码随机调用，确认逻辑层不消费随机数（随机只在环境粒子/震屏/音效速率等视觉听觉量）。适用于任何确定性同步立项。

**②前置条件**：可全仓搜索；已区分逻辑层与表现层边界。

**③操作步骤**：
1. 全仓搜随机 API（Math.random、shuffle、随机区间函数等）→判定信号：命中清单全量导出。
2. 逐行标注每个调用点：逻辑/表现→判定信号：清单每行有归类与依据。
3. 逻辑层若有命中→先改走种子化入口（见【种子化 RNG 兜底】）或移除随机→判定信号：逻辑层命中清零。
4. 盘点表随设计文档存档→判定信号：结论「同步可成立/不可成立」有盘点表支撑。

**④失败分支**：
- 现象：盘点清零后仍偶发脱同步→根因：第三方库内部随机未被搜索命中→处置：按库名补查其文档与源码。
- 现象：表现层随机被误改成种子化导致两端特效「整齐划一」怪异→根因：归类过头→处置：表现层恢复自由随机（不影响校验和，前提是校验和不覆盖表现字段，见【确定性表现层隔离】）。

**⑤验收清单**：
- [ ] 盘点表全量且逐行归类；
- [ ] 逻辑层随机命中=0；
- [ ] 结论与盘点表互相引用。

**⑥禁忌与易错点**：不许凭「应该没几处」跳过盘点；不许把音效速率这类表现随机当逻辑问题处理。

**⑦参数表**：无数值参数；产出物=逐行盘点表。

### 【浮点确定性风险】

**①目标与适用场景**：JS 加减乘除逐位一致，但 Math.pow/Math.sin 等超越函数跨引擎可能差 1 ulp；同引擎逐位一致，跨引擎长局极小概率漂移靠校验和＋房主快照校正兜底，不静默分叉。

**②前置条件**：已启用【校验和同步验证】与【快照校正与重连共用重演】；已知各端浏览器引擎分布。

**③操作步骤**：
1. 盘点逻辑层超越函数调用（pow/sin/cos/exp/log 等）→判定信号：清单在档，能改整数/查表法的优先改。
2. 同引擎两端长跑→预期：mismatch=0→判定信号：校验和日志。
3. 跨引擎两端长跑→预期：偶发 mismatch 时自动走快照校正并恢复→判定信号：校正次数与恢复结果有日志、不出现双边各自继续的分叉。
4. 把风险与兜底写进设计文档→判定信号：文档含「1 ulp」「跨引擎」字样与处置路径。

**④失败分支**：
- 现象：跨引擎局频繁 mismatch→根因：逻辑层重度依赖超越函数→处置：逐项替换为确定性实现（定点/查表），再长跑。
- 现象：mismatch 后两端继续各玩各的→根因：校正通路未接→处置：先接校正再谈精度。

**⑤验收清单**：
- [ ] 超越函数盘点表在档；
- [ ] 同引擎、跨引擎各一轮长跑记录；
- [ ] mismatch→校正→恢复链路实测触发过一次。

**⑥禁忌与易错点**：不许宣称「JS 浮点全平台一致」；不许关掉校验和来「解决」mismatch 报警。

**⑦参数表**：风险量级=1 ulp 级；兜底=校验和（每 30 对输入）＋快照校正重演。

### 【同步面最小化】

**①目标与适用场景**：联机原型先用团队死斗验证「连接—同步—击杀」主链路；爆破模式的回合/炸弹/经济状态机同步复杂度高一个量级，列入后续路线，不一口吃下。注：本条讲**原型期**的接入顺序；【敌人不见人的五因】【经济滚雪球与样本量】【整场模拟自测】所述安包/拆包/回合经济，是同一产品**后续阶段模式已落地后**的故障与验收对象——是阶段先后，不是口径冲突；读到安包类条目时，默认其产品阶段已过本条的原型期。

**②前置条件**：模式清单已按同步复杂度分级；主链路验收标准已定（见【协议层可脱离画面验】）。

**③操作步骤**：
1. 列全部模式并标同步面（实体数、状态机、经济系统）→判定信号：分级表在档。
2. 只实现最低复杂度模式并跑通主链路五项信号→判定信号：见协议层验收清单全过。
3. 其余模式写入路线图并标明前置条件（主链路稳定）→判定信号：路线图有顺序与依赖。
4. 主链路稳定后按路线逐个接入，每接一个回归主链路→判定信号：回归记录齐全。

**④失败分支**：
- 现象：原型期同时开工爆破导致全线不稳→根因：同步面贪大→处置：冻结新模式，先稳主链路。
- 现象：为赶进度跳过主链路验收直接加模式→根因：验收纪律缺失→处置：补验主链路再继续。

**⑤验收清单**：
- [ ] 分级表与路线图在档；
- [ ] 主链路五项信号通过后才有新模式代码；
- [ ] 每加一个模式有主链路回归记录。

**⑥禁忌与易错点**：不许用「模式多」冒充联机完成度；不许在主链路未稳时并行开新模式。

**⑦参数表**：复杂度标尺：爆破（回合+炸弹+经济）≈团队死斗的下一个量级。

### 【服务器校验基线】

**①目标与适用场景**：客户端报告命中、服务器记账时，服务器按基线校验报告合法性，防误报与初级作弊。

**②前置条件**：服务器持有房间实体表、存活状态、队伍、位置（快照）数据。

**③操作步骤**：
1. 收到命中报告后依次校验：报告者与目标同房、均为实体、均存活、不同队→任一不符即拒并记日志→判定信号：非法报告有拒绝日志。
2. 校验单次伤害≤400 上限→超限截断/拒绝→判定信号：记账值不超上限。
3. 校验同报告者命中报告间隔≥50ms→过密丢弃→判定信号：高频脚本报告被限。
4. 校验双方已知距离≤150m→超距拒绝→判定信号：隔图命中报告不入账。
5. 全部通过才改账广播（见【房主权威+服务器记账】）→判定信号：合法命中两端一致。

**④失败分支**：
- 现象：合法近战命中被拒→根因：距离用的是过期快照→处置：校验用最近一帧快照并放宽到基线内，记录误拒样本。
- 现象：脚本刷命中→根因：间隔校验缺失→处置：补 50ms 间隔与伤害上限。

**⑤验收清单**：
- [ ] 七类非法报告（异房/非实体/死亡/同队/超伤/过密/超距）各构造一次，均被拒；
- [ ] 合法命中不误拒（正常对局一轮零误拒）；
- [ ] 拒绝日志可查。

**⑥禁忌与易错点**：不许客户端报多少记多少；不许把校验失败静默吞掉不记日志。

**⑦参数表**：单次伤害上限 400、命中报告最小间隔 50ms、最大合法距离 150m——三值均为**本项目案例值**（娱乐局基线原值，不是通用标准），换项目按自家武器伤害量级与地图尺度重新标定；队伍关系=必须不同队；状态=双方存活；校验类数=7（同房/实体/存活/队伍/伤害/间隔/距离），与③步骤一一对应。

### 【作弊面如实列】

**①目标与适用场景**：原型定位同事内网娱乐局：作弊面逐项列明（位姿自报可瞬移、命中事件可虚报、房主可操纵 Bot），不假装有商业级反作弊，并给出权威化三步路线。

**②前置条件**：系统信任模型已定（客户端自报哪些、服务器校验哪些，见【服务器校验基线】）。

**③操作步骤**：
1. 逐项列作弊面：位姿自报、命中虚报、房主操纵 Bot、改客户端内存等→判定信号：每项标注「可为/不可为/部分可防」。
2. 每项写影响范围（娱乐局可接受/不可接受）→判定信号：有明确判定。
3. 给出权威化三步路线：服务器复核弹道→服务器权威模拟→爆破模式同步→判定信号：路线有顺序与触发条件（对外运营前必做）。
4. 文档随产品说明发布→判定信号：使用者能查到本清单。

**④失败分支**：
- 现象：对外开放了却没升级权威化→根因：触发条件没人盯→处置：把三步路线列入上线检查单。
- 现象：宣传口径称「防作弊」→根因：口径与实现不符→处置：按本清单改口径。

**⑤验收清单**：
- [ ] 作弊面清单逐项有判定；
- [ ] 三步路线在档且与上线检查单挂钩；
- [ ] 对外口径与清单一致。

**⑥禁忌与易错点**：不许把基线校验（上限/间隔）宣传成「反作弊系统」；不许藏已知作弊面。

**⑦参数表**：已知作弊面 3 项（位姿瞬移/命中虚报/房主操纵 Bot）；权威化路线 3 步。

### 【名字牌无遮挡】

**①目标与适用场景**：名字牌是 Canvas 贴图精灵、隔墙可见，无遮挡处理。娱乐局可接受，列为已知问题，权威化阶段再改。⚠ 本条为已知问题登记规程，改法细节须在权威化阶段另行标定（通用步骤）。

### 【上行节拍受帧率钳制】

**①目标与适用场景**：位姿上行写在渲染循环里且 dt 钳到 0.05：低帧率机器实际上行低于 20Hz、远端木偶收敛变慢。环境现象与代码账分开记；后续应改独立定时器。

**②前置条件**：可测实际上行频率（服务器收包计数）；有高/低帧率两类客户端。

**③操作步骤**：
1. 服务器侧统计各客户端位姿上行实际 Hz→判定信号：低帧率端 Hz 明显低于 20。
2. 确认上行调用点在渲染循环且 dt 被钳制 0.05→判定信号：代码定位到行。
3. 评估影响：木偶收敛变慢但不脱同步（快照校正兜底）→判定信号：结论分「环境现象/代码账」两栏记录。
4. 排期改独立定时器上行；改后复测→判定信号：低帧率端上行恢复 20Hz。

**④失败分支**：
- 现象：把低帧率端的木偶迟钝误判为网络丢包→根因：没分环境与代码账→处置：先测实际上行 Hz 再定性。
- 现象：改定时器后上行与渲染状态不一致→根因：定时器读到半更新状态→处置：在逻辑步进后取快照上行。

**⑤验收清单**：
- [ ] 高/低帧率端上行 Hz 实测在档；
- [ ] 定性结论分栏记录；
- [ ] 若已改定时器：低帧率端 20Hz 复测通过。

**⑥禁忌与易错点**：不许把 dt 钳制调大来「修复」（会连带改逻辑步长）；不许只测高帧率机器。

**⑦参数表**：目标上行 20Hz；现状 dt 钳制上限 0.05s。

## 第二章 联机主机迁移与恢复（12 条）

### 【主机迁移：租赁+纪元栅栏】

**①目标与适用场景**：房主掉线时把「Bot 模拟权」移交他人而不乱账：借鉴开源实现把模拟权做成服务器租赁，迁移时 epoch+1、先栅栏掉旧权威再移交，带错纪元的迟到上行直接丢弃；记账从未离开服务器，所以计分不回滚。

**②前置条件**：服务器持有记账与 epoch；客户端上行消息带 epoch 字段；持有者有持续 state 上行（见【心跳复用上行】）。

**③操作步骤**：
1. 服务器检测持有者失联（判死口径与阈值 T 见【心跳复用上行】③的标定规程，本条与该条共用同一 T）→启动迁移→判定信号：迁移日志含旧 epoch 与判死依据（lastBeatAt、T）。
2. epoch+1 并栅栏旧权威：此后旧 epoch 的一切上行直接丢弃→判定信号：构造旧纪元迟到包，服务器不入账且有丢弃日志。
3. 按【候选人按 RTT 排序】选新持有者并下发新 epoch→预期：新持有者开始驱动 Bot→判定信号：Bot 位姿上行恢复、木偶重新收敛。
4. 核对记账连续性→判定信号：迁移前后血量/击杀/比分无回跳。
5. 新持有者以快照位姿初始化 Bot AI（见【AI 内部状态不搬运】）→判定信号：Bot 短暂顿挫后恢复行动。

**④失败分支**：
- 现象：双权威同时驱动 Bot→根因：栅栏未先行、旧持有者假活→处置：确保 epoch+1 与栅栏在移交之前原子完成——原子性实现：单线程事件循环里把「epoch+1＋置栅栏＋下发移交」写在同一同步代码段内，天然原子；多线程/异步实现必须把三步放进同一把锁或同一条串行队列任务，禁止拆成多个异步步骤。
- 现象：迁移后比分回滚→根因：记账曾放客户端→处置：记账收口服务器（见【房主权威+服务器记账】）。
- 现象：无合格候选人→处置：如实解散并写明原因（见【迁移失败情形表】）。

**⑤验收清单**：
- [ ] 协议级测试覆盖迁移主链路（断言清单结构见【协议级测试免渲染】⑦，共 26 条；原记录 26/26 全过为参考基线）；
- [ ] 旧纪元迟到包丢弃实测；
- [ ] 计分不回滚实测；
- [ ] 链式迁移（epoch 2→3）实测。

**⑥禁忌与易错点**：不许先移交再栅栏；不许接受错纪元上行「补记」。

**⑦参数表**：纪元递增 +1/次；记账归属=服务器全程；原子性=单同步段/单锁/单串行队列（三选一，落码可查）；判死阈值与【心跳复用上行】共用同一 T。

### 【接管资格能力协商】

**①目标与适用场景**：客户端在 create/join/rejoin 时带 auth:1 声明「我能接管权威」，才有资格被选为接管方；旧客户端照常玩与当首任房主，但不能接管——强行移交只会让 Bot 无人驱动。

**②前置条件**：客户端版本能力位已定义；服务器在入房时记录每连接的 auth 声明。

**③操作步骤**：
1. 客户端在 create/join/rejoin 消息中带 auth:1（具备接管能力时）→判定信号：服务器会话记录含该字段。
2. 服务器候选池只纳入 auth:1 的连接→判定信号：构造无 auth 的在线连接，迁移时候选名单不含它。
3. 无 auth 客户端正常参战与当首任房主各测一轮→判定信号：功能不受影响。
4. 迁移触发时若候选池为空→走如实解散（见【迁移失败情形表】）→判定信号：解散原因写明「无合格候选人」。

**④失败分支**：
- 现象：Bot 在迁移后无人驱动→根因：移交给了无能力客户端→处置：候选池过滤 auth 并回归。
- 现象：新客户端忘了带 auth 被误判旧版→根因：发版漏字段→处置：入房日志打印 auth 值，发版检查单加此项。

**⑤验收清单**：
- [ ] 带/不带 auth 两种连接候选资格实测；
- [ ] 无 auth 当首任房主可玩实测；
- [ ] 候选池为空时解散路径实测。

**⑥禁忌与易错点**：不许默认所有在线者都有接管能力；不许用版本号猜能力（以声明为准）。

**⑦参数表**：能力字段 auth:1（声明式）。

### 【候选人按 RTT 排序】

**①目标与适用场景**：接管候选人=在线＋有接管能力＋非现持有者的真人，按 RTT 最低优先、同档按入房序号；服务器每 2 秒发 **RTT 探针 ping** 兼作 RTT 测量（与【静默掐断要有保活】的 25s 协议保活 ping 是两个机制：探针管排序、保活管判活，见卷首术语）。

**②前置条件**：候选资格过滤已实现（见【接管资格能力协商】）；服务器有周期 RTT 探针 ping 与 RTT 记录。

**③操作步骤**：
1. 服务器每 2s 对各连接发 RTT 探针 ping 并记录 RTT→判定信号：RTT 表持续更新。
2. 迁移触发时生成候选集：在线∧auth:1∧非现持有者∧真人→判定信号：名单可打印核查。
3. 按 RTT 升序、同档按入房序号排序，取第一名下发移交→判定信号：选中者与排序表一致。
4. 被选者无响应/拒绝→按【迁移失败情形表】走超时换人取下一名→判定信号：换人有日志。

**④失败分支**：
- 现象：选中高 RTT 者导致接管后卡顿→根因：RTT 表过期→处置：迁移前强制刷新一轮 RTT 探针 ping。
- 现象：Bot 账号被选为候选→根因：未过滤真人→处置：候选集加真人条件。

**⑤验收清单**：
- [ ] 人为注入不同 RTT 后选中结果符合排序；
- [ ] 同 RTT 时入房序号决胜实测；
- [ ] 换人路径实测。

**⑥禁忌与易错点**：不许随机选候选人；不许把现持有者自己列入候选。

**⑦参数表**：RTT 探针 ping 周期 2s（仅测 RTT，不判死）；排序键：RTT 升序→入房序号升序。

### 【心跳复用上行】

**①目标与适用场景**：不新增心跳消息类型：持有者 20Hz 的 state 上行本身就是心跳（每次刷新 lastBeatAt），假活判死靠 1s 看门狗查超时。判死阈值原记录未给原值，按③的标定规程取值，不凭经验拍数。

**②前置条件**：持有者有固定频率 state 上行；服务器记录每持有者 lastBeatAt。

**③操作步骤**：
1. 每次收到持有者 state 上行刷新 lastBeatAt→判定信号：日志/计数可见刷新。
2. 看门狗每 1s 扫：now-lastBeatAt 超过判死阈值 T 判失联→触发迁移（见【主机迁移：租赁+纪元栅栏】）。**阈值标定规程**（原记录未给原值，按此规程标定并登记）：T 必须是上行周期的整数倍，T＝N×50ms（上行 20Hz、周期 50ms）；选 N 的决策依据是两类代价的权衡——N 太小，一次网络抖动或一帧卡顿就误判失联，误迁移会打断整局对局（误判代价高）；N 太大，真失联后 Bot 长时间无人驱动（迁移迟滞代价随 N 线性增长）。**示意起点（示意值，非原记录原值）**：N=20，即 T=1s——含义是容忍连续丢 19 个上行、约 1s 无上行才判死；上线后按误判次数与迟滞体感在 N=10–40 间调整并登记终值。**触发延迟口径**：从真失联到迁移触发的延迟＝T＋0~1s（看门狗扫描间隔），示意起点下约 1–2s；不许写「约 1s 触发」这类把阈值与扫描间隔混在一起的表述→判定信号：杀掉持有者进程后在 T＋1s 内触发迁移，日志含 lastBeatAt 与 T。
3. 非持有者连接不走此判死：其连接死活由**协议保活 ping**（25s，见【静默掐断要有保活】）负责；**RTT 探针 ping**（2s，见【候选人按 RTT 排序】）只供迁移排序、不作任何连接的判死依据→判定信号：普通成员静默不触发迁移。

**④失败分支**：
- 现象：持有者假活（进程在、上行停）长时不迁移→根因：只看连接存活不看上行时间→处置：判死依据改为 lastBeatAt。
- 现象：网络抖动误杀持有者→根因：阈值太紧（N 太小）→处置：按③标定规程调大 N，记录取值依据与误判样本；不许改回只看连接存活。

**⑤验收清单**：
- [ ] 杀进程、停上行两种失联都能触发迁移；
- [ ] 正常对局无误触发；
- [ ] 判死阈值 T（＝N×上行周期）与选 N 的依据在档；触发延迟按 T＋扫描间隔实测并记录。

**⑥禁忌与易错点**：不许再叠一套独立心跳消息（双轨必漂移）；不许用 TCP 连接状态代替上行判活。

**⑦参数表**：state 上行 20Hz（周期 50ms）；看门狗扫描周期 1s；判死阈值 T＝N×50ms（标定规程见③，原记录未给原值）；示意起点 N=20、T=1s（**示意值**）；触发延迟＝T＋0~1s。

### 【迁移失败情形表】

**①目标与适用场景**：迁移设计先列失败情形表再写代码：二次掉线链式移交、无合格候选人、ack 纪元错误、终局/大厅期迁移，每种情形有既定处置。

**②前置条件**：迁移主链路已实现（见【主机迁移：租赁+纪元栅栏】）；协议级测试可构造各情形。

**③操作步骤**：
1. 链式移交：接管后再杀新持有者→预期：epoch 2→3 继续移交→判定信号：实测通过、记账不回滚。
2. 无合格候选人：让唯一候选掉线后触发迁移→预期：如实解散并写明原因→判定信号：解散消息含原因、客户端回大厅。
3. ack 纪元错误：构造旧 epoch 的 ack→预期：不生效，走超时换人→判定信号：未误认接管成功。
4. 终局/大厅期房主掉线→预期：只移交房主身份、不迁 Bot 权威→判定信号：新房主可开局，无 Bot 驱动冲突。

**④失败分支**：
- 现象：情形表外的新失败→根因：枚举不全→处置：先登记新情形与临时处置，补进表后再发版。
- 现象：解散不写原因→根因：解散路径没带 reason→处置：所有解散出口强制带原因。

**⑤验收清单**：
- [ ] 四种情形逐一构造实测并留记录；
- [ ] 每种情形的客户端表现（提示/回大厅）符合表内定义；
- [ ] 情形表与测试用例一一对应。

**⑥禁忌与易错点**：不许只测「一次迁移成功」的主路径；不许解散无原因。

**⑦参数表**：情形 4 类；链式移交验证 epoch 2→3。

### 【AI 内部状态不搬运】

**①目标与适用场景**：Bot 的 AI 内部状态（目标/路径点/计时）在旧房主内存里无服务器副本，接管方按快照位姿全新初始化 AI；玩家侧表现为 Bot 顿 0.5–1 秒——可接受降级，如实标注。

**②前置条件**：快照含 Bot 位姿；接管方 AI 可由位姿冷启动。

**③操作步骤**：
1. 接管方收到移交后，用最新快照位姿初始化全部 Bot→判定信号：Bot 位置与快照一致、不回出生点。
2. AI 目标/路径/计时全部新建→预期：Bot 短暂静止后重新索敌移动→判定信号：顿挫时长在 0.5–1s 量级。
3. 把该降级写进已知问题与用户说明→判定信号：文档可查。
4. 回归：迁移后 Bot 能继续完成击杀/被击杀记账→判定信号：记账连续（见【击杀四方一致】）。

**④失败分支**：
- 现象：接管后 Bot 瞬移回出生点→根因：初始化用了出生点而非快照→处置：改用快照位姿。
- 现象：Bot 永久不动→根因：AI 冷启动漏了索敌初始化→处置：初始化序列补索敌并回归。

**⑤验收清单**：
- [ ] 迁移后 Bot 位姿与快照一致；
- [ ] 顿挫时长实测量级 0.5–1s 并登记；
- [ ] 降级说明在档。

**⑥禁忌与易错点**：不许为搬运 AI 状态给服务器加一套 Bot 状态同步（违背极简记账原则）；不许把顿挫说成「无感迁移」。

**⑦参数表**：预期顿挫 0.5–1s；初始化数据源=最新快照位姿。

### 【构建时机竞态】

**①目标与适用场景**：联机消息可能先于 window load 到达，此时 scene 未创建、buildMatch 抛 TypeError 使消息处理当场死掉（大厅不消失、无 HUD、状态文案永不收敛）。解法：就绪门控排队，200ms 轮询、上限 120s，等 init 完成再构建。

**②前置条件**：有明确的 init 完成标志；消息处理入口可前置门控队列。

**③操作步骤**：
1. 在消息处理入口加就绪门控：init 未完成时消息入队不处理→判定信号：人为延迟 init 时消息不丢不报错。
2. 门控以 200ms 轮询 init 标志，上限 120s→预期：init 完成后按序放行队列→判定信号：大厅正常消失、HUD 出现、状态文案收敛。
3. 超过上限仍未就绪→走错误上报路径（见【构建错误不静默死】）→判定信号：状态栏明示错误而非假死。
4. 正常时序回归→判定信号：消息在 init 后到达时行为不变。

**④失败分支**：
- 现象：「有人名血条、没人物、文案不收敛」→根因：先查控制台首条报错，多半是 buildMatch 时机→处置：按本节加门控（排查顺序见【异常位置决定症状】）。
- 现象：门控队列乱序→根因：放行时未按到达顺序→处置：队列 FIFO 并加序号断言。

**⑤验收清单**：
- [ ] 人为延迟 init 构造竞态，消息不丢、对局正常建成；
- [ ] 超时未就绪时错误明示；
- [ ] 正常时序无回归。

**⑥禁忌与易错点**：不许靠「让服务器晚点发」绕竞态（客户端必须自守）；不许把轮询间隔写成 0 死转。

**⑦参数表**：门控轮询 200ms；等待上限 120s。

### 【构建错误不静默死】

**①目标与适用场景**：buildMatch 调用包 try/catch：失败重试 2 次（可重入清理），仍失败把错误明示在状态栏或交回恢复流程，不让一个异常杀死整条消息链。

**②前置条件**：buildMatch 可重入（重复调用前能清理半成品）；状态栏可显示错误；恢复流程存在（见【统一恢复状态机】）。

**③操作步骤**：
1. buildMatch 外包 try/catch→判定信号：注入一次构建异常，消息链后续消息仍被处理。
2. 失败时先清理半成品再重试，共 2 次→判定信号：日志含重试计数。
3. 仍失败→状态栏明示错误并交恢复流程→判定信号：用户可见错误、恢复入口可用。
4. 成功路径回归→判定信号：正常构建无多余清理副作用。

**④失败分支**：
- 现象：重试时残留半个场景→根因：清理不可重入→处置：先修清理幂等再谈重试。
- 现象：异常被 catch 后无声无息→根因：catch 里没上报→处置：catch 强制写状态栏＋日志。

**⑤验收清单**：
- [ ] 注入异常实测：重试 2 次、消息链不断；
- [ ] 最终失败时状态栏明示；
- [ ] 正常路径回归通过。

**⑥禁忌与易错点**：不许空 catch；不许无限重试。

**⑦参数表**：重试次数 2（初次失败后）；清理要求=可重入。

### 【统一恢复状态机】

**①目标与适用场景**：页面加载与意外断线共用一个恢复状态机：rejoin 接管（3 次、间隔 800ms）→重新 join→放弃回主菜单并显示原因；'closed' 置位阻止恢复、防双页互踢死循环。

**②前置条件**：rejoin 凭据可用（见【席位接管凭据】）；主菜单有原因展示位。

**③操作步骤**：
1. 断线/加载触发恢复→先走 rejoin，最多 3 次、间隔 800ms→判定信号：日志含尝试计数与间隔。
2. rejoin 全败→降级为重新 join（新席位）→判定信号：能入房但席位变更有提示。
3. 再败→回主菜单并显示原因→判定信号：原因文本优先用服务器/网络错误原文，不写笼统「失败」；拿不到原文时（如纯超时、无错误对象）用占位格式「错误码＋阶段名」（如 timeout@rejoin第2次），不许留空、不许编造原文。
4. 收到 'closed'（被新连接接管）→置位阻止本页再恢复→判定信号：双开页面时旧页不再抢连、无互踢循环。

**④失败分支**：
- 现象：双页互踢死循环→根因：closed 未置位或置位后仍重试→处置：置位检查放在恢复入口第一行。
- 现象：rejoin 无限重试耗住用户→根因：没上限→处置：严格 3 次后降级。

**⑤验收清单**：
- [ ] 断线、刷新、双开三场景各实测；
- [ ] 重试次数与间隔符合参数；
- [ ] 放弃时原因明示。

**⑥禁忌与易错点**：不许加载与断线各写一套恢复；不许吞掉失败原因。

**⑦参数表**：rejoin 尝试 3 次；间隔 800ms；降级序：rejoin→join→主菜单。

### 【席位接管凭据】

**①目标与适用场景**：rejoin 凭据齐全即接管席位：旧连接先收 closed 通知再被关，其迟到的 onclose 用「conn 易主」守卫忽略；服务端对已在房间连接再发的 create/join 必须回明确 error，不能静默 return（否则客户端等满 6 秒误报超时）。

**②前置条件**：席位凭据在连接建立时保存，字段清单固定四项：会话标识（连接建立时下发、核对主键）、席位 id、房间 id、名字（名字回填见【会话名字回填】）；核对以会话标识＋席位 id 为准、名字为辅。服务器可按连接查房间归属。

**③操作步骤**：
1. 新连接带凭据 rejoin→服务器核对通过→先向旧连接发 closed 再关闭它→判定信号：旧端收到 closed 且不再恢复（见【统一恢复状态机】）。
2. 新连接接管席位与记账→判定信号：比分/身份延续。
3. 旧连接迟到的 onclose 到达→用「conn 已易主」守卫忽略→判定信号：不触发误恢复、不踢新连接。
4. 已在房间的连接再发 create/join→服务器回明确 error→判定信号：客户端立即收到错误而非等 6s 超时。

**④失败分支**：
- 现象：rejoin 后旧连接把新连接踢掉→根因：onclose 未守卫→处置：加易主守卫。
- 现象：客户端误报「连接超时」→根因：服务器静默 return→处置：所有拒绝路径回明确 error 并加日志。

**⑤验收清单**：
- [ ] 接管全链路实测（通知→关闭→接管→守卫）；
- [ ] 重复 create/join 立即收到 error；
- [ ] 名字核对依赖【会话名字回填】已修。

**⑥禁忌与易错点**：不许静默 return 任何请求；不许先关旧连接再通知（顺序反了旧端会误恢复）。

**⑦参数表**：客户端等待超时参考 6s——口径是**单次请求**的等待超时（服务器必须在此之前明确回 error），不是整轮恢复预算；【统一恢复状态机】的整轮预算＝每次 rejoin 尝试各自受 6s 单次超时约束、尝试间隔 800ms、共 3 次后降级。凭据字段：会话标识/席位 id/房间 id/名字。

### 【静默掐断要有保活】

**①目标与适用场景**：大厅阶段连接双向静默会被代理/网络静默掐断而客户端毫无感知：加**协议保活 ping**（25s）＋**应用层 ping/pong** 双保活（与【候选人按 RTT 排序】的 2s RTT 探针 ping 分工不同，见卷首术语）。

**②前置条件**：协议层支持 ping/pong；应用层有消息通道可承载心跳对。

**③操作步骤**：
1. 启用协议保活 ping，周期 25s→判定信号：抓包可见周期 ping/pong。
2. 应用层再加 ping/pong 对（带序号）：周期须短于所经代理/网络的静默掐断阈值——标定法：先实测静默掐断阈值（挂一条静默连接计时到被掐），应用层周期取该阈值的 1/3 以下并登记；示意起点 10s（**示意值**，须以自家实测阈值复核）；连续 3 个周期无 pong 判连接已死（示意规程）→判定信号：长时间挂大厅（≥10 分钟）后发消息即达、不需重连。
3. pong 超时→主动走恢复状态机→判定信号：断线提示与恢复入口出现，不假装还连着。

**④失败分支**：
- 现象：大厅挂久后点开局无反应→根因：连接已被静默掐断→处置：先查保活是否两层都在跑。
- 现象：只有协议保活 ping 没有应用 pong→根因：代理放行协议帧但连接已半死→处置：双保活缺一不可。

**⑤验收清单**：
- [ ] 大厅静置≥10 分钟后操作即达；
- [ ] 抓包见 25s 协议保活 ping 与应用层 ping/pong 两层都在跑；
- [ ] 人为断网后 pong 超时触发恢复。

**⑥禁忌与易错点**：不许只开一层保活；不许把保活周期设到分钟级以上。

**⑦参数表**：协议保活 ping 25s；应用层 ping/pong：周期≤实测静默掐断阈值的 1/3（示意起点 10s，示意值）、连续 3 周期无 pong 判死（示意规程）；实测阈值与最终周期登记在档。

### 【会话名字回填】

**①目标与适用场景**：会话存档的名字只靠 UI 赋值、非 UI 路径加入会存空名，导致 rejoin 名字核对必失败：发送前统一回填 _myName。

**②前置条件**：会话存档结构含名字字段；存在非 UI 加入路径（自动重连、深链等）。

**③操作步骤**：
1. 全仓查名字赋值点→判定信号：确认只有 UI 一处赋值即为隐患。
2. 在所有出站消息发送前统一回填：名字为空时从会话存档/上次会话补 _myName→判定信号：抓包见非 UI 路径消息也带名。
3. 非 UI 路径加入并断线 rejoin→预期：名字核对通过→判定信号：接管成功（见【席位接管凭据】）。

**④失败分支**：
- 现象：rejoin 总报名字不符→根因：存档空名→处置：先查回填点是否覆盖全部出站路径。
- 现象：回填了错名→根因：多账号共用存档→处置：回填来源限定为本会话存档。

**⑤验收清单**：
- [ ] UI 与非 UI 两条路径各测一次 rejoin；
- [ ] 出站消息抓包名字非空；
- [ ] 回填点唯一且在发送前。

**⑥禁忌与易错点**：不许在每个调用点各自补名（必漏）；不许拿设备名/随机名冒充会话名。

**⑦参数表**：字段 _myName；回填时机=发送前统一处理。

## 第三章 格斗玩法工程（12 条）

### 【技能存在≠玩家可用】

**①目标与适用场景**：角色本有成套必杀/超必杀/连段取消（每名 4–5 个必杀＋超必杀），但只能搓招触发且全游戏无一处招式表，玩家感知就是「技能不酷炫、动作太少」。可玩性排查要查「发现路径」：一键释放＋招式表三处可见。

**②前置条件**：已盘点每名角色的技能清单与原触发方式；有真人（或模拟新手）可做发现路径测试。

**③操作步骤**：
1. 列每名角色技能表：名称/原触发/耗气→判定信号：每人 4–5 必杀＋1 超必杀齐全。
2. 给每个技能加一键释放通道（见【一键技能等效通道】）→判定信号：新手不知搓招也能放出全部技能。
3. 招式表三处上线（见【招式表三处可见】）→判定信号：选人/暂停/对局中都能查到。
4. 找没玩过的人试玩 5 分钟→预期：能自主放出≥1 个必杀与大招→判定信号：观察记录达标。

**④失败分支**：
- 现象：用户仍说「技能少」→根因：先查发现路径而非技能数量→处置：按本节三步补齐再复测，不先加新技能。
- 现象：一键释放与搓招效果不一致→根因：没走同一通道→处置：见【一键技能等效通道】收口。

**⑤验收清单**：
- [ ] 技能清单与游戏内实际逐个对上；
- [ ] 新手试玩达标记录在档；
- [ ] 招式表三处齐全（逐处截图/实测）。

**⑥禁忌与易错点**：不许用「引擎里有」反驳玩家「用不了」；不许只加技能不补发现路径。

**⑦参数表**：每名角色必杀 4–5 个＋超必杀 1 个；招式表露出点 3 处。

### 【连招衔接接通既有系统】

**①目标与适用场景**：轻/重击命中取消接技能、爆气中必杀取消接大招：把已有取消系统接通，比新造系统便宜且稳。

**②前置条件**：引擎已有取消（cancel）机制与状态标记；技能通道已收口（见【一键技能等效通道】）。

**③操作步骤**：
1. 盘点现有取消点：哪些动作、哪个时间窗可取消→判定信号：清单与代码对应。
2. 在轻/重击命中判定帧开放取消窗口，接技能输入→预期：命中后立即出技能无空档→判定信号：录像/帧日志可见衔接。
3. 爆气状态下开放必杀→大招取消→判定信号：爆气连段可完整打出。
4. AI 同步可用（见【AI 同步会用新招】）→判定信号：AI 能打出同等连段。

**④失败分支**：
- 现象：取消窗口开了但接不上→根因：输入缓冲不在窗口内采样→处置：查输入缓冲与窗口时序。
- 现象：取消导致无限连→根因：窗口覆盖了技能收招→处置：窗口只开在命中帧段并加同招限制（按项目规则标定）。

**⑤验收清单**：
- [ ] 轻/重击→技能、爆气必杀→大招两条链各实测；
- [ ] 无无限连（构造测试）；
- [ ] AI 可复现同连段。

**⑥禁忌与易错点**：不许为连招新造第二套技能系统；不许只给玩家开取消不给 AI。

**⑦参数表**：取消链 2 条（轻/重击→技能；爆气必杀→大招）；窗口参数按引擎现值登记。

### 【酷炫可拆成特效清单】

**①目标与适用场景**：把「技能不酷炫」拆成可逐个落地的特效条目：武器轨迹、突进残影、招式名飘字、大招全屏闪光＋慢镜、必杀命中震屏，逐项实现逐项验收。

**②前置条件**：特效走纯表现通道（见【确定性表现层隔离】）；素材/粒子已备或可用程序化生成。

**③操作步骤**：
1. 把主观评价拆成清单五项并逐项定验收标准（如飘字须含招式名、慢镜须有明确时长感）→判定信号：清单可勾选。
2. 逐项实现，每项完成即在实机录像中核对→判定信号：录像中该项可见。
3. 全部完成后跑联机校验和→判定信号：mismatch=0（特效不入逻辑）。
4. 找用户复验观感→判定信号：以真机反馈为准（自动化画面不算数）。

**④失败分支**：
- 现象：特效加了但校验和 mismatch→根因：特效碰了逻辑字段→处置：按【确定性表现层隔离】剥离。
- 现象：全屏闪光/慢镜影响操作判定→根因：慢镜改了逻辑步进→处置：慢镜只改表现节奏或走引擎既有顿帧机制并回归同步。

**⑤验收清单**：
- [ ] 五项特效逐项录像可见；
- [ ] 联机 mismatch=0；
- [ ] 真机观感复验记录。

**⑥禁忌与易错点**：不许用「加了粒子」笼统交差；不许特效进逻辑层。

**⑦参数表**：特效清单 5 项：武器轨迹/突进残影/招式名飘字/大招全屏闪光＋慢镜/必杀命中震屏。

### 【AI 同步会用新招】

**①目标与适用场景**：给玩家加的新招必须同步教给 AI 对手：AI 优先走一键技能通道触发招牌技与大招、与搓招结果完全等价；原难度分档/难度参数不变。否则单机没可玩性、玩家也看不见 AI 放大招。

**②前置条件**：一键技能通道已收口（见【一键技能等效通道】）；AI 决策入口可调用该通道。

**③操作步骤**：
1. 把 AI 出招调用改走一键技能通道→判定信号：AI 放招与玩家一键放招走同一函数（代码可查）。
2. 设定 AI 使用招牌技/大招的触发概率（原记录原值：AI 走一键通道触发招牌技概率 55%、大招概率 50%，在决策点掷签判定）→判定信号：多局观察 AI 能放出必杀与大招，且长局统计触发率与 55%/50% 同量级。
3. 难度分档回归→判定信号：各档胜率/压迫感与改前同量级（大样本对照，见【经济滚雪球与样本量】的样本量纪律）。
4. 玩家侧回归→判定信号：一键与搓招结果等价（伤害/耗气/帧数据一致）。

**④失败分支**：
- 现象：AI 永不放大招→根因：AI 决策没接新通道→处置：按第 1 步收口。
- 现象：AI 新招过强/过弱→根因：触发倾向未按难度分档→处置：倾向参数分档标定，不改玩家侧规则。

**⑤验收清单**：
- [ ] AI 放必杀与大招多局可观察；
- [ ] 同通道代码证据；
- [ ] 难度分档回归记录。

**⑥禁忌与易错点**：不许给 AI 单独写一套出招逻辑；不许借机改难度参数不登记。

**⑦参数表**：通道=一键技能通道（与搓招等价）；触发概率（原值）：招牌技 55%、大招 50%；难度分档/参数保持原值。

### 【输入源误配死锁】

**①目标与适用场景**：单人模式给 AI 侧/2P 误配只读合并源（只有 poll），AI 控制器按可编程源调写接口（setDir）第一帧抛 TypeError、主循环死锁、双方都不渲染。修复：工厂函数对 vsai/arcade 也返回可编程源，AI 与人类走完全相同输入接口；多模式下逐个核输入源接口契约。

**②前置条件**：输入源有工厂函数按模式创建；AI 控制器依赖写接口。若项目没有工厂函数（各模式直接 new 输入源），先把创建点收口成一个工厂函数再套用本条，否则第 3 步无处落。

**③操作步骤**：
1. 列全部模式（vsai/arcade/双人/联机等）与每模式两侧输入源类型→判定信号：矩阵成表。
2. 逐格核契约：该侧消费者需要哪些接口（poll/setDir 等），源是否全提供→判定信号：缺口格标红。
3. 工厂函数对缺口模式改返可编程源→预期：AI 与人类同接口→判定信号：改后矩阵无缺口。
4. 逐模式进 UI 实跑（见【回归测试打在故障模式上】【模式覆盖矩阵】）→判定信号：每模式首帧无 pageerror、双方渲染。

**④失败分支**：
- 现象：「有人名血条没人物」→根因：先查控制台首条报错，多半是 setDir 死锁→处置：按本节核矩阵（见【异常位置决定症状】）。
- 现象：只修了 vsai、arcade 又犯→根因：逐个打补丁→处置：矩阵全量核完再发版。

**⑤验收清单**：
- [ ] 模式×侧别接口矩阵在档且无缺口；
- [ ] 每模式 UI 实跑首帧零 pageerror；
- [ ] 专门回归测试覆盖本故障模式。

**⑥禁忌与易错点**：不许给 AI 侧加 try/catch 吞掉 setDir 错误冒充修复；不许只测双人模式就下结论。

**⑦参数表**：故障签名：第一帧 TypeError（setDir 非函数）；修复点=输入源工厂函数。

### 【异常位置决定症状】

**①目标与适用场景**：步进函数抛错会让渲染永不执行、但 DOM 层 HUD 照常显示，形成「有人名、血条、按键提示，就是没有人物」的误导症状。排查先看控制台首条报错，而不是先查素材加载。

**②前置条件**：可抓 pageerror/控制台日志；知道渲染与 HUD 的分工（画布 vs DOM）。

**③操作步骤**：
1. 复现症状后先抓控制台第一条报错→判定信号：报错堆栈指向步进/逻辑函数即定性为逻辑抛错。
2. 按堆栈定位抛错行→预期：多为接口误配/空引用→判定信号：与【输入源误配死锁】等已知模式比对。
3. 修复后回归：首帧零 pageerror 且人物渲染→判定信号：pageerror 计数=0（见【pageerror 计数取证】）。
4. 若首条报错与素材相关，再转素材加载线排查→判定信号：排查路径有记录。

**④失败分支**：
- 现象：先去查素材加载查了半天→根因：症状误导→处置：立规矩——画面类故障第一步永远是控制台首条报错。
- 现象：报错被每帧重复淹没找不到首条→根因：死锁后每帧抛错→处置：按时间取第一条同签名错误。

**⑤验收清单**：
- [ ] 排查记录含首条报错原文；
- [ ] 修复后 pageerror=0；
- [ ] 症状—根因对应关系回写故障库。

**⑥禁忌与易错点**：不许在没看控制台前动素材；不许只看最后一屏日志。

**⑦参数表**：取证顺序：控制台首条报错→堆栈→已知故障模式比对。

### 【一键技能等效通道】

**①目标与适用场景**：一键技能键与搓招走同一条 buildSpecial 通道（同耗气、同取消规则、同联机输入位），老玩家打法不失效；新键位选空闲键、暂停键改 Esc 避冲突。

**②前置条件**：技能构建函数唯一（buildSpecial）；键位表可查冲突。

**③操作步骤**：
1. 一键键的按下事件直接构造与搓招成功相同的输入序列喂 buildSpecial→判定信号：两路调用栈汇合到同一函数。
2. 核对同耗气、同取消规则→判定信号：两路放招后气槽扣减逐值相等。
3. 联机输入位共用→判定信号：联机局一键放招两端一致、校验和 mismatch=0。
4. 键位冲突排查：新键选空闲键，原占用的暂停功能改 Esc→判定信号：全键位表无重复绑定。

**④失败分支**：
- 现象：一键版伤害/耗气与搓招版不同→根因：另写了一套技能逻辑→处置：删旁路、收口 buildSpecial。
- 现象：新键与既有功能冲突→根因：没查键位表→处置：按第 4 步全表排查。

**⑤验收清单**：
- [ ] 两路等价性逐项（伤害/耗气/取消/联机）实测；
- [ ] 键位表无冲突；
- [ ] 联机 mismatch=0。

**⑥禁忌与易错点**：不许为一键技能复制技能数据；不许改搓招判定迁就一键。

**⑦参数表**：通道=buildSpecial 单一入口；暂停键=Esc。

### 【招式表三处可见】

**①目标与适用场景**：招式表在三处共用一份数据生成：选人详情面板、暂停菜单双方全表、对局角落常驻图例（含「搓招同效」注脚），玩家在任何阶段都查得到。

**②前置条件**：招式数据单源（与 buildSpecial 同源数据，见【一键技能等效通道】）。

**③操作步骤**：
1. 招式表数据结构化：角色→技能（名称/按键/耗气/一句话效果）→判定信号：数据与技能清单逐项对上（见【技能存在≠玩家可用】）。
2. 三处 UI 各从同一数据渲染：选人详情、暂停全表、对局图例→判定信号：改一处数据三处同步变（改名测试）。
3. 图例加「搓招同效」注脚→判定信号：图例可见该注脚。
4. 逐处实机核对可达性→判定信号：选人时、暂停时、对局中三场景都能打开/看到。

**④失败分支**：
- 现象：三处内容不一致→根因：各写一份文案→处置：收口单源数据。
- 现象：图例遮挡对局→根因：常驻图例尺寸失控→处置：图例只放本方技能速查、全表留暂停菜单。

**⑤验收清单**：
- [ ] 单源改名测试通过；
- [ ] 三场景可达性实测；
- [ ] 注脚存在。

**⑥禁忌与易错点**：不许三处各维护一份招式文案；不许图例挡关键画面区域。

**⑦参数表**：露出点 3 处；数据源=1 份。

### 【重复方向指令坑】

**①目标与适用场景**：脚本搓招通道里 motionSteps 对「22/66」这类重复方向只产出一次方向事件，永远放不出该必杀（真人连点两次可出）。解法：两压之间插入 2 帧回中——此「帧」指**消费序号帧**（引擎成对 poll 的逻辑步，见【输入序号与帧号解耦】），不是渲染帧；顿帧期间逻辑步不推进、回中按逻辑步计，不会被顿帧吞掉。两端同步改、联机不受影响。

**②前置条件**：搓招由脚本通道生成方向事件序列；必杀表含重复方向指令。

**③操作步骤**：
1. 枚举必杀指令表，标出含重复方向（22/66/44 等）的招式→判定信号：清单与放不出的招式对应。
2. 在脚本通道生成时，两次同向之间插入 2 帧回中（中立）→预期：产生两次独立方向事件→判定信号：事件日志可见「下、中立、下」。
3. 脚本放招回归：清单内招式逐个可放出→判定信号：以角色进入必杀状态＋气槽按招式表扣减为放招成功信号（不以特效出现为准）；全清单通过。
4. 联机两端同改后跑校验和→判定信号：mismatch=0。

**④失败分支**：
- 现象：真人能放、脚本放不出→根因：先怀疑事件合并而非判定窗口→处置：打印方向事件序列核对。
- 现象：插回中后别的招式误触→根因：回中帧影响其他指令匹配→处置：只对重复方向指令启用插入。

**⑤验收清单**：
- [ ] 重复方向招式清单全量回归；
- [ ] 事件序列日志留证；
- [ ] 联机 mismatch=0。

**⑥禁忌与易错点**：不许放宽判定窗口来「兼容」（会误触其他招）；不许只改一端。

**⑦参数表**：回中插入 2 帧（逻辑步/消费序号口径）；受影响指令形如 22/66（同向重复）；放招成功信号=进入必杀态＋耗气扣减。

### 【确定性表现层隔离】

**①目标与适用场景**：武器轨迹/残影/飘字等特效必须走纯表现通道（fxAnims/fxVar），并逐行核对校验和只覆盖逻辑字段（权威清单见【校验和同步验证】①：帧号/阶段/位置/血量/气槽/投射物），特效加得再多联机也不脱同步。注意：帧表名不在清单内——它是表现层选帧结果、由逻辑状态派生，混入校验和会让纯表现差异误报脱同步。

**②前置条件**：校验和字段清单可查；表现层有独立数据通道。

**③操作步骤**：
1. 列校验和覆盖字段并逐行核对计算代码→判定信号：字段集与【校验和同步验证】①的权威清单逐项一致（帧号/阶段/位置/血量/气槽/投射物），无表现字段（帧表名、特效状态）混入。
2. 全部特效状态只写 fxAnims/fxVar→判定信号：全仓查特效变量无逻辑层写入。
3. 加满特效跑联机长局→判定信号：mismatch=0。
4. 新增特效时重复第 2 步检查→判定信号：检查记录随特效 PR 留档。

**④失败分支**：
- 现象：加特效后 mismatch→根因：特效改了位置/状态或用了逻辑随机→处置：定位字段并剥离到表现通道。
- 现象：为过校验和把必要逻辑字段移出校验和→根因：因噎废食→处置：恢复字段、修特效侧。

**⑤验收清单**：
- [ ] 校验和字段清单与代码逐行对上；
- [ ] 特效全开长局 mismatch=0；
- [ ] 新增特效有隔离检查记录。

**⑥禁忌与易错点**：不许特效回调里改逻辑状态；不许缩减校验和范围掩盖问题。

**⑦参数表**：校验和覆盖字段以【校验和同步验证】①权威清单为准（6 项逻辑字段，本条不另立清单）；表现通道=fxAnims/fxVar。

### 【双人同键盘鬼键】

**①目标与适用场景**：双人同键盘默认键位要避开常见鬼键冲突区；手柄混搭（P1 键盘＋P2 手柄）才是推荐玩法，写进说明。

**②前置条件**：目标键盘的鬼键冲突区已知（常见三键同按无响应组合）；键位可配置。

**③操作步骤**：
1. 列双人默认键位，逐组测三键同按（移动＋攻击＋跳跃等常用组合）→判定信号：无响应组合清单在档。
2. 把冲突组合涉及的键位移出冲突区→预期：常用组合全响应→判定信号：复测清单清零。
3. 说明文档写明推荐玩法：P1 键盘＋P2 手柄混搭→判定信号：说明在游戏内/随附文档可见。
4. 手柄路径回归→判定信号：P2 手柄全键位可用。

**④失败分支**：
- 现象：对局中某方按键偶发失灵→根因：先查鬼键组合而非程序→处置：复现组合并对照清单。
- 现象：改键位后与系统快捷键冲突→根因：未查系统保留键→处置：避开系统组合键。

**⑤验收清单**：
- [ ] 常用三键组合全响应实测表；
- [ ] 推荐混搭说明已上线；
- [ ] 手柄路径回归通过。

**⑥禁忌与易错点**：不许把鬼键失灵当程序 bug 改逻辑；不许默认键位扎堆在同一键盘矩阵区。

**⑦参数表**：推荐配置=P1 键盘＋P2 手柄；验收组合=各方常用三键同按。

### 【换引擎量化评估】

**①目标与适用场景**：是否迁移成熟格斗引擎，用工时量化表决策：单角色全量重制 1.5–3 个工作日、10 人约 3–6 人周，且现有素材/存档/自研测试资产全部作废——结论不换，并写明重评触发条件（角色扩到 20+ 且要立回/投技/空中战时再评估）。（本条仅方法可写：只给评估方法，不举实例细节。）

**②前置条件**：现引擎资产清单（素材/存档/测试）齐全；候选引擎能力边界已查。

**③操作步骤**：
1. 按角色数×单角色重制工时估迁移总工时→判定信号：给出区间而非单点数。
2. 列作废资产清单与重建成本→判定信号：素材/存档/测试三类齐全。
3. 列候选引擎带来的新能力与当前需求的差距→判定信号：需求—能力对照表。
4. 给结论＋重评触发条件（可判定事件，如角色数阈值、新机制立项）→判定信号：触发条件写进立项文档。

**④失败分支**：
- 现象：评估只算开发工时不算资产作废→根因：口径不全→处置：补作废清单再评。
- 现象：结论无触发条件、每次都重吵→根因：决策未沉淀→处置：触发条件入档。

**⑤验收清单**：
- [ ] 量化表四项（工时/作废/能力对照/触发条件）齐全；
- [ ] 结论与依据可复核。

**⑥禁忌与易错点**：不许凭「成熟引擎更好」直觉决策；不许低估测试资产重建成本。

**⑦参数表**：参考量级：单角色全量重制 1.5–3 工作日；10 人约 3–6 人周；重评触发示例：角色 20+ 且立回/投技/空中战立项。

## 第四章 射击玩法工程（36 条）

### 【敌人不见人的五因】

**①目标与适用场景**：「敌人不出来」是五因叠加不是单一 bug：安包读 ai=null 每帧崩溃、拆包手跟过期守位站死、寻路边图穿墙两点振荡、感知太弱目标丢失宽限 0、安包成功后不去猎杀拆包者。逐因修＋整场模拟验收。**产品/模式现状**：本条属爆破模式已落地的产品阶段（原型期先死斗、后爆破的接入顺序见【同步面最小化】，两者是阶段先后）；构建里没有安包模式就跑不了本条，先确认构建含爆破模式再执行。

**②前置条件**：可跑整场模拟（见【整场模拟自测】）；控制台/pageerror 可抓；五因清单在手。复现设置统一为：爆破模式、Bot 对 Bot 整场模拟至少 1 场全程（含安包与拆包回合）——崩溃因在安包回合触发，站死/猎杀两因在安包后阶段观察，振荡/感知两因全程观察；某一因复现不出时不许在验收里打勾，须注明未复现并保留观察。

**③操作步骤**：
1. 先抓崩溃：按②复现设置跑安包回合看 pageerror→预期：安包读 ai=null 每帧崩溃若在，首条报错指向它→判定信号：修空引用后该签名错误消失。**顺序纪律**：崩溃会掩盖其余四因的表现，修完崩溃必须整局重跑再看下一因；五因逐因串行确认，不许并行观察一轮就下结论。
2. 查站死：观察拆包手 Bot 是否跟过期守位→判定信号：守位失效后应重新索敌而非原地站死，修守位更新。
3. 查振荡：Bot 在墙边两点来回→判定信号：边图穿墙导致目标点不可达，修边图连通（见【寻路卡死三件套】）。
4. 查感知：目标短暂遮挡即丢失→根因：丢失宽限 0→处置：加宽限（见【目标丢失宽限】0.5s）。
5. 查猎杀：安包成功后 Bot 应转猎杀拆包者→判定信号：模拟中安包后 Bot 有进攻行为。
6. 五因全修后跑整场模拟→判定信号：全场无崩溃、Bot 全程有行为。

**④失败分支**：
- 现象：只修崩溃就宣布解决→根因：五因当一因→处置：五因逐项打勾再验收。
- 现象：模拟里敌人出来了、真人局仍不出→根因：模拟未覆盖安包/拆包分支→处置：模拟脚本覆盖全流程分支。

**⑤验收清单**：
- [ ] 五因逐项有修复与复测记录；
- [ ] 整场模拟全程无 pageerror；
- [ ] 安包/拆包/猎杀三分支在模拟中都被走到。

**⑥禁忌与易错点**：不许单因归因；不许用「出生点能看见 Bot」代替整场验收。

**⑦参数表**：因数 5；目标丢失宽限 0.5s（见本章【目标丢失宽限】）。

### 【寻路卡死三件套】

**①目标与适用场景**：墙角卡死用三件套：卡死检测＋连续脱困＋吸附选点，另加绕行点段中点法线搜索。适用于网格/边图寻路的 Bot。

**②前置条件**：Bot 有位移采样；地图有可达点集与直线可达判定——LOS 实现二选一并在档注明：边图直连（两点在边图中直接连通，成本低，适合已有边图的地图）或射线检测（逐段采样查碰撞，通用但成本高）；两种实现的验收口径相同（不穿墙）。

**③操作步骤**：
1. 卡死检测：0.35s 内位移<0.05m 判卡死→判定信号：日志出现卡死事件且位置在墙角类地点。
2. 连续脱困：向侧方以 0.3m 递增侧移、每侧 3 步，脱困动作带 2.5s 冷却→预期：Bot 离开卡点→判定信号：位移恢复。
3. 吸附选点：取最近 6 个候选点中直线可达者为新目标→判定信号：不再选穿墙点。
4. 绕行点：对阻挡段中点做法线搜索，步进 0.5m，结果带 1.2s 缓存→判定信号：绕行路径不穿墙。
5. 整场模拟回归→判定信号：无 Bot 长时卡死（统计口径见⑤；分层取证见【Bots 卡顿是结构性叠加】）。

**④失败分支**：
- 现象：脱困后立即又卡回→根因：目标点仍不可达→处置：先吸附换点再脱困，顺序不能反。
- 现象：脱困动作频繁触发像抽搐→根因：冷却缺失或检测阈值太松→处置：核 2.5s 冷却与 0.35s/0.05m 阈值。

**⑤验收清单**：
- [ ] 人为把 Bot 逼入墙角，脱困链完整触发并离开；
- [ ] 整场模拟无 >5s 卡死个体——口径：单个 Bot 的一次卡死事件，从卡死检测触发起、到脱困链使其恢复有效位移止，持续时长 >5s 才计一个（不是同一位置累计停留时长）；
- [ ] 参数与表内原值一致（代码可查）。

**⑥禁忌与易错点**：不许用随机传送脱困（破坏可复现性）；不许只加检测不加脱困。

**⑦参数表**：卡死判定 0.35s 位移<0.05m；侧移递增 0.3m、每侧 3 步；脱困冷却 2.5s；吸附候选最近 6 点；法线搜索步进 0.5m；绕行缓存 1.2s。

### 【到达半径大于转弯半径】

**①目标与适用场景**：Bot 绕目标点画圆的根源是到达半径（0.6）恰好在转弯半径（0.63）内侧：到达判定统一放宽到 1.0m、1.5m 内按距减速、绕行点到达 0.9m。

**⑤验收清单**：

**⑥禁忌与易错点**：不许靠加大转向速率硬压画圆（会抖）；不许各处到达判定各写一个半径。

**⑦参数表**：原到达半径 0.6m；转弯半径 0.63m；新到达半径 1.0m；减速起始距 1.5m；绕行点到达 0.9m。

### 【碰撞两遍解算】

**①目标与适用场景**：贴墙锯齿靠两遍碰撞解算：推出后把剩余位移沿墙面切向滑动、再解算一次；玩家与 Bot 共用同一 resolve 函数保一致。

3. 第二遍：剩余位移投影到墙面切向滑动后再解算一次→预期：贴墙移动顺滑无锯齿→判定信号：贴墙斜走轨迹平滑、速度不骤降。

**⑤验收清单**：

### 【速度包络防抽搐】

3. 蹲下加 0.8s 最小保持→判定信号：无起蹲闪烁（录像逐帧看）。
4. 整场模拟回归→判定信号：无抽搐类观感问题、寻路指标不恶化。

**⑤验收清单**：
- [ ] 速度曲线采样无阶跃；
- [ ] 蹲伏保持≥0.8s 实测；
- [ ] 模拟回归通过。

**⑥禁忌与易错点**：不许直接把 AI 目标速度赋给实际速度；不许为治抽搐关掉 AI 变向能力。

**⑦参数表**：加速 12/s；减速 16/s；横移趋近 17/s；蹲下最小保持 0.8s。

### 【动画选档迟滞】

**①目标与适用场景**：移动动画切档抖动根源在估速：估速做低通平滑（τ≈0.12s）＋全档位进/出双阈值迟滞（进 0.15/0.85/2.5/5.2、出更低），治「站立帧与行走帧横跳」。

**②前置条件**：动画按速度分档（站/走/跑等）；估速来源可平滑。

**③操作步骤**：

**④失败分支**：
- 现象：平滑后切档明显滞后→根因：τ 过大→处置：核 τ≈0.12s 原值。

**⑤验收清单**：
- [ ] 临界徘徊场景无横跳；
- [ ] 双阈值参数与原值一致；
- [ ] 变速响应无明显滞后。

**⑥禁忌与易错点**：不许用单阈值切档；不许把估速毛刺当动画资源问题去换资源。

**⑦参数表**：估速平滑 τ≈0.12s；进档阈值 0.15/0.85/2.5/5.2（m/s 量级，原值）；出档阈值＝进档×(1−带宽)，带宽示意 20%→示意出档 0.12/0.68/2.0/4.2（示意值，落码后登记实测终值）。

### 【行走帧与帧率解耦】

**①目标与适用场景**：行走帧推进按实际位移累计（每 13 单位一步、帧率解耦），慢设备不会倍速播帧、快设备不会慢动作。此「单位」是地图世界坐标单位（与角色坐标、塔射程同系，非像素、非米）；原记录未给与角色尺寸的换算——落码时先量自家角色身位（碰撞直径），确认 13 单位与身位的比例合理（一步约跨一个身位量级）再定版登记。

**②前置条件**：角色有实际位移量可累计；动画帧序列步长已定。

**③操作步骤**：
1. 帧推进量改由位移驱动：累计位移每满 13 单位推进一步→判定信号：代码无按时间/帧数推进的残留。
2. 高帧率端实测→预期：步频与速度成比例→判定信号：同速下步频一致。
3. 低帧率端实测→判定信号：步频仍与位移成比例、无倍速/慢动作。

**④失败分支**：
- 现象：慢设备步频翻倍→根因：仍按帧推进→处置：查推进量来源。
- 现象：原地踏步（位移为 0 还播帧）→根因：位移累计含抖动噪声→处置：静止时不累计（与到达判定联查）。

**⑤验收清单**：
- [ ] 高/低帧率两端步频—速度比例一致；
- [ ] 静止不播行走帧；
- [ ] 参数 13 单位/步落码。

**⑥禁忌与易错点**：不许按渲染帧推进动画；不许用时间近似位移。

**⑦参数表**：步长=每 13 世界坐标单位一步；驱动量=实际位移累计；落码前按角色碰撞直径复核比例并登记。

### 【朝向量化实测】

**①目标与适用场景**：朝向按最近四向取帧，用探针实测 face 量化值精确（0/1.57/3.14/−1.57），不靠目测「差不多朝下」。

**②前置条件**：可读角色 face 量化值（探针/日志）；四向帧齐全。

**③操作步骤**：
1. 角色分别朝四向静止→探针读 face 值→判定信号：四值=0/1.57/3.14/−1.57（π 量化）。
2. 斜向移动→预期：取最近四向→判定信号：量化值只在四值内跳变。
3. 帧与朝向对照→判定信号：所取帧方向与量化值一致。

**④失败分支**：
- 现象：目测朝下但帧是侧向→根因：量化边界或帧映射错→处置：以探针值为准查映射表。
- 现象：朝向在两值间高频跳→根因：输入方向抖动→处置：与动画迟滞同法加防抖（按实现标定）。

**⑤验收清单**：
- [ ] 四向探针值在档；
- [ ] 帧映射一致；
- [ ] 斜向取最近向实测。

**⑥禁忌与易错点**：不许目测验收朝向；不许四向帧映射凭序号猜。

**⑦参数表**：四向量化值：0 / 1.57 / 3.14 / −1.57（弧度）。

### 【减速挂统一口径】

**①目标与适用场景**：地形减速乘在统一速度出口（effSpd 末尾）覆盖英雄/小兵/野怪无一遗漏，冲刺与闪现不走此路不受影响；判定半宽与渲染水面半宽严格一致、相邻沙地按半径排除防误伤。

**②前置条件**：全场速度计算有统一出口 effSpd；地形判定与渲染共用半宽数据。

**③操作步骤**：
1. 减速系数只乘在 effSpd 末尾一处→判定信号：全仓减速应用点唯一。
2. 英雄/小兵/野怪各入水测速→判定信号：三者均为原速×0.8（涉水口径见【地形指控先核设计意图·河道】）。
3. 冲刺/闪现过水→判定信号：不受减速。
4. 判定半宽与渲染水面半宽逐值核对→判定信号：两值相等；相邻沙地按半径排除、不误减速。

**④失败分支**：
- 现象：某种单位不减速→根因：它没走 effSpd→处置：收口速度出口。
- 现象：岸边沙地被减速→根因：判定范围大于渲染范围→处置：半宽对齐＋半径排除。

**⑤验收清单**：
- [ ] 三类单位减速实测；
- [ ] 位移技能不受影响实测；
- [ ] 半宽两值一致证据。

**⑥禁忌与易错点**：不许在各单位速度公式里分别乘系数；不许判定与渲染各用一份地形数据。

**⑦参数表**：涉水系数 ×0.8（挂 effSpd 末尾）；判定半宽=渲染水面半宽。

### 【拖动转向挂 window】

**①目标与适用场景**：拖动转向的 mousemove 挂在画布上、指针滑过 HUD 就断档：改挂 window 并按画布 rect 换算坐标。

**②前置条件**：拖动转向逻辑在画布监听；可取画布 getBoundingClientRect。

**③操作步骤**：
1. mousemove 监听从画布改挂 window→判定信号：代码落点变更。
2. 坐标按画布 rect 换算→判定信号：画布内坐标与改前一致。
3. 拖动滑过 HUD 区域→预期：转向不断档→判定信号：连续拖动轨迹无中断。
4. 拖出窗口再回来→判定信号：状态不残留（mouseup 在窗外也能收尾，与窗口级 mouseup 联查）。

**④失败分支**：
- 现象：改挂后坐标偏移→根因：没按 rect 换算→处置：补换算并与【视角缩放坐标自检】的往返法自检。
- 现象：HUD 上拖动误转→根因：window 监听无区域判定→处置：按业务规则决定 HUD 区是否响应并登记。

**⑤验收清单**：
- [ ] 滑过 HUD 不断档实测；
- [ ] 坐标换算往返自检；
- [ ] 窗外松手收尾正常。

**⑥禁忌与易错点**：不许只挂画布再加一层 HUD 转发（易漏）；不许坐标不换算。

**⑦参数表**：监听对象=window；坐标=按画布 rect 换算。

### 【信号键不受键位互换影响】

**①目标与适用场景**：左右键移动互换选项开启时，Alt＋左键信号仍按物理键位判定，不被互换逻辑带偏。

**②前置条件**：互换开关已实现（见【输入偏好给开关不改习惯】）；信号键判定入口独立可查。

**③操作步骤**：
1. 开启互换→按 Alt＋物理左键→预期：发出信号而非移动→判定信号：信号标记出现、无移动指令。
2. 关闭互换→同操作→判定信号：结果一致。
3. 互换状态下普通左键→判定信号：按互换规则执行移动/攻击（与信号路径分开）。

**④失败分支**：
- 现象：互换后信号变移动→根因：信号判定走了互换后的逻辑键→处置：信号判定改读物理键位。
- 现象：修信号带偏普通键→根因：两路共用判定→处置：两路分离，信号独读物理键。

**⑤验收清单**：
- [ ] 互换开/关两态信号实测；
- [ ] 普通键互换行为不受影响；
- [ ] 判定入口代码可查。

**⑥禁忌与易错点**：不许信号键跟随逻辑键位；不许为修信号关掉互换功能。

**⑦参数表**：信号组合=Alt＋左键（物理键位）。

### 【Bot 决策限速】

**①目标与适用场景**：机器人感的一大来源是同帧同步决策：决策周期随机抽取＋初始相位按 id 错开，9 个 Bot 不再同 tick 齐动。

**②前置条件**：Bot 决策有周期计时；Bot 有稳定 id。

**③操作步骤**：
1. 每 Bot 决策周期在区间内随机抽取（种子化随机，联机可复现）：原记录未给区间原值——标定规程：下限不低于感知/反应窗的下限量级、上限不高于玩家可察觉的迟钝线；先以示意区间 0.2–0.5s（**示意值**）起步，观察同 tick 齐动消失且无明显迟钝后登记终值→判定信号：周期分布不整齐划一。
2. 初始相位按 id 错开→判定信号：开局首轮决策时刻互不相同。
3. 观察多 Bot 同屏行为→预期：动作起始时刻参差→判定信号：录像/日志无同 tick 齐动。

**④失败分支**：
- 现象：随机周期用了未播种随机、联机两端不一致→根因：随机源不统一→处置：走种子化 RNG（见【种子化 RNG 兜底】）。
- 现象：错开后个别 Bot 反应明显慢→根因：周期上限过大→处置：按③标定规程收窄区间上限并登记终值。

**⑤验收清单**：
- [ ] 决策时刻分布采样在档；
- [ ] 9 Bot 无同 tick 齐动；
- [ ] 随机源为种子化。

**⑥禁忌与易错点**：不许全 Bot 同周期同时相；不许用 Math.random 错相（联机必分叉）。

**⑦参数表**：对象量级：9 个 Bot；相位=按 id 错开；周期=区间随机抽取（原记录无原值，示意起点 0.2–0.5s，标定后登记终值）。

### 【Bot 反应窗】

**①目标与适用场景**：感知要有人类反应窗：目标进视野先登记、按难度采样反应延迟（简单 300–480ms/普通 180–300ms/困难 120–220ms）后才算「看见」，离开 580ms 注销带迟滞。

**②前置条件**：感知系统有登记/注销两段状态；难度分档参数表。

**③操作步骤**：
1. 目标进视野→先登记不反应→判定信号：登记时刻与反应时刻分离可测。
2. 按难度在区间内采样延迟→到期才置「看见」→判定信号：三档实测延迟落在各自区间。
3. 目标离开→580ms 后注销（迟滞）→判定信号：短暂出视野不立即失忆（与【目标丢失宽限】口径区分：此为 MOBA 感知窗）。
4. 难度切换回归→判定信号：延迟区间随档变。

**④失败分支**：
- 现象：Bot 零延迟描头→根因：登记即反应→处置：补反应窗。
- 现象：延迟采样用了未播种随机→根因：同【Bot 决策限速】→处置：种子化。

**⑤验收清单**：
- [ ] 三档延迟采样分布在档；
- [ ] 注销迟滞 580ms 实测；
- [ ] 录像观感无「秒锁」。

**⑥禁忌与易错点**：不许进视野即反应；不许注销无迟滞（会闪烁式失忆）。

**⑦参数表**：反应延迟：简单 300–480ms、普通 180–300ms、困难 120–220ms；注销迟滞 580ms。

### 【APM 令牌桶】

**①目标与适用场景**：Bot 操作限速用令牌桶（容量 3、回充按难度 90/150/210 APM），保命动作与玩家信号订单豁免不排队，治「瞬间全技能齐发」。

**②前置条件**：Bot 动作出口唯一可挂桶；动作可分类（普通/保命/订单）。

**③操作步骤**：
1. 动作出口挂令牌桶：容量 3，回充速率按难度 90/150/210 APM→判定信号：参数落码。
2. 普通动作无令牌时排队/丢弃（按设计口径）→判定信号：连发场景下技能间隔被拉开。
3. 保命动作与信号订单动作豁免直行→判定信号：桶空时保命仍可放。
4. 三档各跑一局统计实际 APM→判定信号：不超各档上限。

**④失败分支**：
- 现象：Bot 仍瞬间齐发→根因：有动作绕过出口→处置：出口收口盘点。
- 现象：保命被桶卡死→根因：豁免分类漏标→处置：补分类并回归。

**⑤验收清单**：
- [ ] 三档 APM 实测不超限；
- [ ] 豁免动作桶空可放；
- [ ] 齐发场景复测改善。

**⑥禁忌与易错点**：不许用固定冷却代替令牌桶（突发手感不同）；不许豁免口开太大（全标保命）。

**⑦参数表**：桶容量 3；回充：简单 90、普通 150、困难 210 APM；豁免：保命动作、玩家信号订单。

### 【信号订单机制】

**①目标与适用场景**：玩家信号转成有时限的队伍订单：进攻信号最多 3 人响应、近者优先，半径/时长/冷却分档，订单把决策计时压到 ≤0.05s 保证下一 tick 就被消费（实测 0.06s 内转向集结）。

**②前置条件**：信号系统可生成订单；Bot 决策可消费订单（见【Bot 决策限速】）；订单有时限与冷却。

**③操作步骤**：
1. 玩家发进攻信号→生成订单：响应上限 3 人、近者优先→判定信号：订单对象含半径/时长/冷却三参数——原记录未给分档原值，按信号类型分档标定（示意分档，**示意值**：进攻——半径 30 单位/时长 8s/冷却 15s；防守——半径 20 单位/时长 10s/冷却 20s；撤退——半径全图/时长 5s/冷却 20s），落码后以实测手感调整并登记终值表。
2. 订单注入响应者决策：决策计时压到 ≤0.05→预期：下一 tick 即被消费→判定信号：实测 0.06s 内 Bot 转向集结。
3. 订单到期/完成自动撤销→判定信号：Bot 不长时滞留旧订单。
4. 冷却内重复信号→判定信号：不叠加新订单。

**④失败分支**：
- 现象：全队 9 人齐涌信号点→根因：没上限→处置：核 3 人上限与近者优先。
- 现象：Bot 半天不理信号→根因：决策计时没被订单压低→处置：查订单注入路径。

**⑤验收清单**：
- [ ] 响应人数≤3 且近者优先实测；
- [ ] 消费延迟实测（0.06s 量级）；
- [ ] 到期撤销与冷却实测。

**⑥禁忌与易错点**：不许订单无时限；不许信号直改 Bot 目标（必须走订单机制以便限速与撤销）。

**⑦参数表**：响应上限 3 人；决策计时 ≤0.05s（单位：秒）；实测消费 0.06s 内；半径/时长/冷却=按信号类型分档（原记录无原值，示意分档见③第 1 步，标定后登记终值）。

### 【视野口径统一】

**①目标与适用场景**：世界渲染与小地图共用同一个 visibleTo 判定（含眼位/扫描/草丛贴身规则），两处口径不一致会出现「小地图看得见、世界里没有」的灵异现象。

**②前置条件**：视野判定可收口为单一函数 visibleTo；眼位/扫描/草丛规则在该函数内。

**③操作步骤**：
1. 盘点世界渲染与小地图各自的可见判定→判定信号：两处调用同一 visibleTo（代码证据）。
2. 构造对照场景：草丛贴身、眼位覆盖、扫描扫过→预期：两处可见性一致→判定信号：逐景截图对照（世界＋小地图同屏）。
3. 规则变更只改 visibleTo 一处→判定信号：改后两处同步变。

**④失败分支**：
- 现象：小地图有、世界无→根因：两套判定→处置：收口并逐景回归。
- 现象：收口后性能掉→根因：小地图高频全量调用→处置：缓存判定结果（按 tick 缓存，口径不变）。

**⑤验收清单**：
- [ ] 单一函数代码证据；
- [ ] 三类场景两处一致；
- [ ] 规则变更单点生效。

**⑥禁忌与易错点**：不许小地图自己算一套简化视野；不许用「小地图仅供参考」开脱不一致。

**⑦参数表**：判定函数=visibleTo（单一）；规则含：眼位/扫描/草丛贴身。

## 第六章 棋牌玩法工程（8 条）

### 【记账语义先确诊】

**①目标与适用场景**：「炸金花底池不涨」先做引擎数值实验确诊：实为累计贡献目标模型（跟注 need 常为 0、底池当然慢涨）而非显示 bug——先确诊语义再决定动不动引擎。

**②前置条件**：可直跑引擎做数值实验（无 UI）；可记录每动作底池与各家贡献。

**③操作步骤**：
1. 直跑引擎多局，逐动作记录底池与贡献→判定信号：数据表在档。
2. 对照守恒口径（见【守恒断言口径】）验算→判定信号：底池=贡献和、无凭空增减。
3. 分析涨速：跟注 need 常为 0→底池慢涨是模型结果→判定信号：定性「语义非 bug」并成文。
4. 把定性交用户/产品拍板：改模型还是改预期→判定信号：拍板记录在档，未拍板不动引擎。

**④失败分支**：
- 现象：直接改显示层「让底池涨快点」→根因：未确诊→处置：回滚，先做数值实验。
- 现象：实验数据与线上不一致→根因：实验未用现行引擎版本→处置：核版本再跑（见【引擎记账模型先于显示层】）。

**⑤验收清单**：
- [ ] 数值实验数据在档；
- [ ] 守恒验算通过；
- [ ] 定性结论与拍板记录齐全。

**⑥禁忌与易错点**：不许没确诊就动引擎或显示层；不许把模型语义当 bug 修。

**⑦参数表**：判据：跟注 need 常为 0→底池慢涨属累计贡献目标模型。

### 【引擎红线例外流程】

**①目标与适用场景**：改对局引擎是红线，例外须走流程：用户拍板＋只动单文件＋diff 留档＋改后跑大样本数值实验（360 把）＋守恒断言全过。

**①目标与适用场景**：全库 AI 都走 this.rng 种子源、独有一家用 Math.random 时，digest 确定性测试会间歇失败（10 跑 7 败、败局都出自该家）——随机源必须全库统一。

3. 全部改走 this.rng 种子源→判定信号：清单清零。
4. 复跑 digest≥10 次→判定信号：全过。

**④失败分支**：
- 现象：间歇失败被当 flaky 跳过→根因：没统计败局来源→处置：按来源归因再修。

**⑤验收清单**：

- [ ] digest 10 跑全过；
- [ ] 败局归因记录在档。

**⑥禁忌与易错点**：不许给确定性测试加重试掩盖；不许只改出事的一家不查全库。

**⑦参数表**：案例：10 跑 7 败（败局同源）；目标：随机源全库统一 this.rng。

## 第七章 跨游戏静态与交互基线（11 条）

### 【静态资源基线体检与出口收口】

**①目标与适用场景**：多款游戏共性硬伤先查传输层：无 gzip、无缓存头、缓存规则写了旧路径从未生效、大 HTML 裸传。治理法：静态出口收口到单一函数统一处理 gzip（按 mtime+size 缓存压缩结果、上限 64 条）、Content-Length、按路径分档缓存（素材/音频长缓存、HTML 不缓存、其余短缓存）与 mime。

**②前置条件**：静态服务代码可改；可抓响应头（curl -I 级别）。

**③操作步骤**：
1. 体检：逐款抓响应头→判定信号：gzip/缓存/Content-Length/mime 四项现状表在档。
2. 出口收口：全部静态响应走单一函数→判定信号：代码调用点唯一。
3. 函数内实现：gzip 按 mtime+size 缓存（上限 64 条）、带 Content-Length、按路径分档缓存、mime 表完整→判定信号：逐项抓头验证。
4. 大 HTML（如 259KB 级 play 页）复测传输量→判定信号：gzip 后约 −64% 量级（案例口径）。
5. 逐款回归→判定信号：每款页面 200 且功能正常。

**④失败分支**：
- 现象：改了缓存没生效→根因：规则指旧路径→处置：见【缓存规则路径漂移】。
- 现象：gzip 缓存爆内存→根因：无上限→处置：缓存上限 64 条并按 mtime+size 失效。

**⑤验收清单**：
- [ ] 四项体检表齐全；
- [ ] 出口函数唯一；
- [ ] 逐款抓头复验通过。

**⑥禁忌与易错点**：不许逐款各写一套静态逻辑；不许 HTML 长缓存（会掩盖新版）。

**⑦参数表**：gzip 缓存上限 64 条（键=mtime+size）；缓存分档：素材/音频长缓存、HTML 不缓存、其余短缓存；案例：259KB 页 gzip −64%。

### 【缓存规则路径漂移】

**①目标与适用场景**：资源迁了新路径（/assets/cards/）而缓存规则还指旧路径（/img/cards/），规则静默失效、从未生效；改资源路径时连带改缓存/引用规则并验真生效。

**②前置条件**：可查现行资源落点与缓存规则配置。

**③操作步骤**：
1. 列现行资源路径清单→与缓存规则逐条对→判定信号：不对齐条目即隐患。
2. 改规则指现行路径→判定信号：配置 diff 在档。
3. 验真生效：抓该路径响应头看缓存头→判定信号：出现预期的长缓存头。
4. 把「改路径连带改规则」写进变更清单→判定信号：清单含此项。

**④失败分支**：
- 现象：规则改了仍不生效→根因：还有一层代理/CDN 规则→处置：逐层抓头定位。
- 现象：资源路径再次迁移又漂移→根因：无连带清单→处置：补清单并全量对一遍。

**⑤验收清单**：
- [ ] 路径—规则对照表无漂移；
- [ ] 抓头验证生效；
- [ ] 变更清单含连带项。

**⑥禁忌与易错点**：不许只改资源不改规则；不许以「配置写了」代替「抓头生效」。

**⑦参数表**：案例路径：旧 /img/cards/ → 现行 /assets/cards/。

### 【跨游戏交互基线扫查】

**①目标与适用场景**：同发行方多款产品先一次修齐共性层再逐款验玩法：游戏页全域屏蔽右键（输入框除外）、按钮热区基础类补 min-height:44px 兜底、在座玩家给「回大厅」入口（离开先 confirm、语义与关页面一致即 AI 代打、不新增服务端消息类型）、头像/牌图加载失败 onerror 兜底——图片失败要看得见地降级。

**③操作步骤**：

3. 回大厅：在座玩家入口，离开先 confirm，语义=关页面（AI 代打），不新增服务端消息→判定信号：点离开后 AI 接管、服务端无新消息类型。
4. 图片兜底：头像失败隐藏图保留昵称、牌图失败露 CSS 兜底样式→判定信号：断网图/坏链接构造下仍可辨认。
5. 逐款打勾成表→判定信号：每款四项全过才算修齐。

**④失败分支**：
- 现象：某款改了基线玩法坏了→根因：共性改动碰了该款专用规则→处置：逐款验玩法（基线与玩法分两步）。
- 现象：兜底图仍白屏→根因：onerror 未挂或挂了又报错→处置：构造坏图实测。

**⑤验收清单**：
- [ ] 逐款四项验收表齐全；
- [ ] 热区实测≥44px；
- [ ] 坏图降级实测；
- [ ] 离开语义与关页面一致（AI 代打）实测。

**⑥禁忌与易错点**：不许只修一款就宣布基线齐；不许为回大厅新造服务端协议。

**⑦参数表**：按钮热区 min-height:44px；回大厅语义=AI 代打（同关页面）；兜底：头像隐藏图留昵称、牌图露 CSS 样式。

### 【部署文件权限坑】

**⑥禁忌与易错点**：不许只验页面不验资源；不许用 777 图省事。

**⑦参数表**：问题权限 640→对齐 664；验收=逐文件 HTTP 200。

### 【MIME 补全】

**①目标与适用场景**：woff2/webp 缺 MIME 会被当 application/octet-stream 下发、部分浏览器拒载字体：补全 MIME 表是静态服务的必查项。

**②前置条件**：静态服务 mime 表可改（与【静态资源基线体检与出口收口】同函数）。

**③操作步骤**：
1. 列站点实际文件扩展名→与 mime 表对→判定信号：缺失清单（woff2/webp 等）。
2. 补全缺失映射→判定信号：配置落码。
3. 逐类抓响应头验 Content-Type→判定信号：字体/图片类型正确、非 octet-stream。
4. 浏览器实载→判定信号：字体生效、无拒载报错。

**④失败分支**：
- 现象：补了 woff2 漏了 webp→根因：清单不全→处置：按扩展名全量对表。
- 现象：响应头对了浏览器仍拒→根因：缓存旧响应→处置：强刷/换 URL 复测（注意缓存分档）。

**⑤验收清单**：
- [ ] 扩展名—mime 对照无缺失；
- [ ] 逐类响应头正确；
- [ ] 实载无报错。

**⑥禁忌与易错点**：不许只补出事的那一个扩展名；不许以服务器「能下」代替浏览器「肯载」。

**⑦参数表**：必查扩展：woff2、webp（及全站实际扩展名全量）。

### 【死代码双口径删除】

**①目标与适用场景**：同名两套段位实现（死代码 rank_system.js 与现行口径）并存会误导后续开发：删前全仓核查无 require、且其自带测试本身 11/13 已坏，删除并在清单登记。

**②前置条件**：可全仓搜引用；有删除登记清单。

**③操作步骤**：
1. 全仓搜该文件/模块的 require/import→判定信号：0 引用才可进下一步。
2. 跑其自带测试→判定信号：如 11/13 已坏，佐证其非现行口径。
3. 确认现行口径文件是哪一份→判定信号：线上实际加载路径可指。
4. 删除并登记（文件名、删除依据、日期）→判定信号：登记在档。
5. 删除后全量回归→判定信号：测试全绿、线上功能正常。

**④失败分支**：
- 现象：删后某处报错找不到模块→根因：动态引用没被搜到→处置：恢复并改走下线流程（先断引用再删）。
- 现象：两份都在被引用→根因：真双口径并行→处置：先合并口径再删，不许直接删。

**⑤验收清单**：
- [ ] 0 引用证据；
- [ ] 现行口径指认明确；
- [ ] 删除登记与回归通过。

**⑥禁忌与易错点**：不许凭文件名新旧删；不许删了不登记。

**⑦参数表**：案例：死代码自带测试 11/13 已坏；判据=require 0 命中。

### 【死文件识别】

**①目标与适用场景**：图标文件因所有卡片都有照片图而永不被引用、1.5MB 的 click.mp3 无任何引用：识别「只占磁盘不占流量」的死文件，删除排清理轮次不混进功能包。

**②前置条件**：可全仓搜引用（含代码、样式、配置）；有清理轮次安排。

**③操作步骤**：
1. 按大小列可疑文件→逐个搜引用→判定信号：0 引用清单。
2. 复核引用形式：字符串拼路径、动态加载、清单文件→判定信号：排除假阴性。
3. 死文件排进专门清理轮次删→判定信号：不与功能部署同包。
4. 删后回归→判定信号：页面无 404、无缺图。

**④失败分支**：
- 现象：删后发现运行时拼路径引用→根因：复核不全→处置：从备份恢复并把拼法登记。
- 现象：把死文件混进功能包删除、出问题难回滚→根因：轮次混杂→处置：清理独立成包。

**⑤验收清单**：
- [ ] 0 引用复核含动态形式；
- [ ] 清理独立成包；
- [ ] 删后无 404。

**⑥禁忌与易错点**：不许只搜文件名全串（拼路径会漏）；不许清理混包。

**⑦参数表**：案例：无引用 click.mp3 1.5MB；判据=全形式 0 引用。

### 【CSS 类名相撞】

**①目标与适用场景**：新增横幅类名与既有轮播的 .banner 相撞被压成 112px 高：新类名上线前先查全站冲突，改名解决。

**②前置条件**：可全站搜类名定义与使用。

**③操作步骤**：
1. 新增类名前全站搜同名→判定信号：有同名定义即改名。
2. 上线后量测关键尺寸→判定信号：高度等与设计一致（如横幅不应是 112px）。
3. 若已相撞→给新类改专属名→判定信号：复测尺寸恢复、轮播不受影响。

**④失败分支**：
- 现象：用 !important 硬压回去→根因：治标→处置：改名根治。
- 现象：改名漏改 JS 里的类名引用→根因：只改 CSS→处置：类名全仓（CSS/JS/HTML）同改。

**⑤验收清单**：
- [ ] 新类名冲突检查记录；
- [ ] 上线尺寸量测达标；
- [ ] 既有组件回归。

**⑥禁忌与易错点**：不许用通用词（banner/box/list）作新类名不查重；不许 !important 叠罗汉。

**⑦参数表**：案例：.banner 相撞、横幅被压 112px 高。

### 【已下架条目防带回】

**①目标与适用场景**：本地基线大厅里还留着已下架游戏的条目，整页部署会把它带回线上：部署前与线上逐项对齐、同步删条目。

**②前置条件**：有线上现行版本可拉取对比（部署防分歧纪律）；下架清单在档。

**③操作步骤**：
1. 部署前拉线上大厅页与本地包逐项对条目→判定信号：差异清单（多/少/改）。
2. 本地多出的已下架条目→先在本地删条目再打包→判定信号：包内条目集=线上现行集＋本轮新增。
3. 部署后线上复核条目集→判定信号：下架游戏未复活。
4. 若线上条目比本地新（线上有一方改动）→按三方合并处理，不整页覆盖→判定信号：走合并流程（跨卷引用，见卷五部署纪律；本卷内口径：以线上为底三方合并、不整页盲覆盖）。

**④失败分支**：
- 现象：整页覆盖把下架游戏带回→根因：没对齐→处置：立即回滚并按本节重做。
- 现象：把线上独有条目误删→根因：单向对齐→处置：双向对齐、差异逐项定性。

**⑤验收清单**：
- [ ] 部署前差异清单在档；
- [ ] 部署后条目集复核；
- [ ] 下架清单与包内条目无交集。

**⑥禁忌与易错点**：不许整页盲覆盖；不许默认本地比线上新。

**⑦参数表**：对齐维度：条目多/少/改三类；原则=以线上为底。

### 【大厅卡图真实流程】

**①目标与适用场景**：大厅游戏卡图不用摆拍注入：走真实流程（建房→AI 补满→开托管推进→多个时点各截候选帧→人工挑信息量最大的一张定版），结算类卡图（如梭哈结算亮骰帧）要在报告里注明是结算时刻、不冒充对局中帧。

**②前置条件**：游戏可建房、AI 可补满、有托管推进；可截图。

**③操作步骤**：
1. 真实建房、AI 补满、开托管推进对局→判定信号：对局真实进行（非注入状态）。
2. 多个时点各截候选帧→判定信号：候选≥数张、覆盖不同阶段。
3. 人工挑信息量最大的一张定版→判定信号：定版理由可述。
4. 若定版是结算时刻帧→报告注明「结算时刻」→判定信号：注明在档。

**④失败分支**：
- 现象：用脚本注入摆拍状态截图→根因：省事→处置：按真实流程重截。
- 现象：结算帧冒充对局帧→根因：未注明→处置：补注明或换帧。

**⑤验收清单**：
- [ ] 候选帧多时点齐全；
- [ ] 定版为真实流程产物；
- [ ] 结算帧有注明。

**⑥禁忌与易错点**：不许注入状态摆拍；不许结算帧冒充对局中。

**⑦参数表**：流程 4 步（建房/AI 补满/托管推进/多时点截图）；定版=人工挑信息量最大。

### 【兜底 URL 拼法坑】

**①目标与适用场景**：语音兜底链里 .wav 实文件其实是 mp3、URL 拼法写错必然 404：一行拼法修复即可，但绝不能顺手改动线上独有的语音逻辑本体。

**②前置条件**：可查实文件格式与 URL 拼法；知道哪些文件是线上独有、不可整覆。

**③操作步骤**：
1. 404 取证：请求该 URL→判定信号：404 且实文件存在→定性拼法问题。
2. 查实文件真实格式（.wav 名实为 mp3）→判定信号：文件头证据。
3. 只改 URL 拼法一行→判定信号：diff=1 行。
4. 复请求→判定信号：200 且可播。
5. 确认未触碰语音逻辑本体→判定信号：diff 无其他行。

**④失败分支**：
- 现象：顺手重构语音链把线上独有逻辑冲掉→根因：改动面失控→处置：回滚、只留一行修复（部署防分歧纪律）。
- 现象：改拼法仍 404→根因：还有一层路径前缀问题→处置：按实际落点逐段核 URL。

**⑤验收清单**：
- [ ] diff 仅一行；
- [ ] URL 200 可播；
- [ ] 线上独有逻辑零改动。

**⑥禁忌与易错点**：不许借小修做大重构；不许整文件覆盖线上独有文件。

**⑦参数表**：修复面=1 行 URL 拼法；实文件格式 mp3（名为 .wav）。

## 第八章 玩法工程方法与立项（22 条）

### 【游戏问题自查前置】

**①目标与适用场景**：游戏线要自己想全面、主动发现问题，不等用户提了才补。适用于全部游戏产品的日常巡检与版本规划。

**②前置条件**：有自查清单与台账（见【夜间自审制度】）；有对标基线（见【极致标准对标】）。

**③操作步骤**：
1. 按七维（操作/可玩性/画面/声音/特效/渲染/模型）逐款自查→判定信号：每款有差距清单。
2. 差距按「用户会不会第一眼发现」排序→判定信号：高优先项有排期。
3. 每轮落地至少一件改进并留痕→判定信号：台账可查。
4. 用户反馈的问题先对照自查清单→判定信号：若清单没覆盖，补清单项（流程缺口）。

**④失败分支**：
- 现象：用户提的问题自查从没发现→根因：自查维度缺项→处置：补维度并复盘。
- 现象：自查只列不改→根因：无落地纪律→处置：每轮强制落地一件。

**⑤验收清单**：
- [ ] 逐款差距清单在档；
- [ ] 每轮落地记录；
- [ ] 用户新反馈能反哺清单。

**⑥禁忌与易错点**：不许等用户点名才查；不许自查报告全是优点。

**⑦参数表**：自查维度 7（操作/可玩性/画面/声音/特效/渲染/模型）。

### 【极致标准对标】

**①目标与适用场景**：全线产品按同品类优秀作品的公开标准打分立基线记分卡，不许「网页游戏差不多就行」的自我宽容；最弱维度优先补。

**②前置条件**：每品类有公开标杆作品与可比维度；评分口径成文。

**③操作步骤**：
1. 逐款按维度打分（5 分制）建记分卡→判定信号：基线记分卡在档（如最高 3.7、最低 2.9 的案例量级）。
2. 标出每款最弱维度→判定信号：改进排期按最弱优先。
3. 每轮改进后复评同维度→判定信号：分数变化有据（同口径，见【量测口径一致】）。
4. 记分卡定期刷新→判定信号：版本与日期在档。

**④失败分支**：
- 现象：自评普遍 4+→根因：标准注水→处置：按标杆公开标准重评。
- 现象：只补强项维度→根因：避难→处置：按最弱优先排期。

**⑤验收清单**：
- [ ] 记分卡全款覆盖；
- [ ] 最弱维度有排期；
- [ ] 复评同口径。

**⑥禁忌与易错点**：不许「网页游戏差不多就行」；不许换口径让分数变好看。

**⑦参数表**：评分 5 分制；案例基线：最高 3.7、最低 2.9、无一过 4。

### 【夜间自审制度】

**①目标与适用场景**：每日凌晨七维自审（操作/可玩性/画面/声音/特效/渲染/模型），逐维列差距、每晚只落地一件改进（只动表现/体验层），台账留痕，部署包备好待复核、有成果才汇报。

**②前置条件**：有定时任务与台账文件；部署需人工复核的约定在位。

**③操作步骤**：
1. 凌晨自动跑七维自审→判定信号：当日台账有条目。
2. 逐维列差距并选一件表现/体验层改进落地→判定信号：当晚有一件已落地或明确记录为何未落地。
3. 部署包备好待复核，不直发→判定信号：包在待复核区。
4. 有成果才汇报，无成果静默→判定信号：汇报记录与成果对应。

**④失败分支**：
- 现象：自审变成流水账（全是「正常」）→根因：标准注水→处置：按【极致标准对标】重校。
- 现象：自审改动直发线上出事→根因：跳过复核→处置：恢复备包待复核纪律。

**⑤验收清单**：
- [ ] 台账逐日连续；
- [ ] 每晚落地一件（或有未落地原因）；
- [ ] 部署包均经复核。

**⑥禁忌与易错点**：不许自审动逻辑层/引擎（只动表现体验层）；不许无成果硬汇报。

**⑦参数表**：频率=每日凌晨；维度 7；每晚落地 1 件；范围=表现/体验层。

### 【玩法名实核查】

**①目标与适用场景**：名字与玩法不符（如名为梭哈实为骰子、无下注结构）要上报用户拍板正名或重做，不默默将就。

**②前置条件**：已核玩法构成（是否有该品类的核心结构，如梭哈的下注结构）。

**③操作步骤**：
1. 按品类核心结构逐项核→判定信号：缺失项清单（如「无下注结构」）。
2. 定性名实不符→成文上报：现状、两条路（正名/重做）与各自成本→判定信号：上报记录在档。
3. 等用户拍板后执行→判定信号：拍板前不擅自改名或重做。

**④失败分支**：
- 现象：默默将就上线→根因：怕麻烦→处置：补上报并登记为流程缺口。
- 现象：擅自正名→根因：越权→处置：恢复并走拍板。

**⑤验收清单**：
- [ ] 核查清单在档；
- [ ] 上报含两条路与成本；
- [ ] 执行有拍板依据。

**⑥禁忌与易错点**：不许名实不符默默将就；不许未拍板先改。

**⑦参数表**：案例：名为梭哈、实为骰子玩法、无下注结构→待拍板（正名或重做）。

### 【回归测试打在故障模式上】

**①目标与适用场景**：修完死锁要新增专门回归测试（该模式进 UI 实跑一遍），防同类回退，不许只修不测。

**②前置条件**：故障模式可复现/可构造；测试框架可加用例。

**③操作步骤**：
1. 把故障模式写成测试：走真实 UI 路径进该模式→判定信号：旧代码上此测试必失败（先验）。
2. 修复后跑→判定信号：测试通过。
3. 测试入回归套件→判定信号：套件清单含此用例。
4. 后续每轮发版跑套件→判定信号：记录连续。

**④失败分支**：
- 现象：测试走 debug 后门全绿但真实路径仍死→根因：测试路径≠真实路径→处置：改走真实 UI（见【测试必须走真实路径】同理，补遗【pageerror 计数取证】可作信号）。
- 现象：只修不测、下轮回退→根因：无回归→处置：补测试再发版。

**⑤验收清单**：
- [ ] 测试在旧代码上失败、在新代码上通过（双向验证）；
- [ ] 走真实 UI 路径；
- [ ] 入套件。

**⑥禁忌与易错点**：不许用单元级 mock 代替模式实跑；不许测试只验「不报错」不验渲染结果。

**⑦参数表**：案例：vsai/arcade 死锁→新增该模式 UI 实跑回归。

### 【复现与所见不一致照实记】

**①目标与适用场景**：本地复现比用户所见更重（双边黑屏 vs 只见敌方）、代码无专属绘制分支、差异未完全解释——就写「未完全解释」，不编解释圆场。

**②前置条件**：有用户所见记录与本地复现记录可对照。

**③操作步骤**：
1. 逐项对照用户所见与本地复现→判定信号：差异点清单。
2. 能解释的写依据（代码分支/日志），不能的写「未完全解释」→判定信号：报告措辞与证据等级匹配。
3. 修复按已确诊根因走，差异项单独跟踪→判定信号：不因差异未解而停修，也不假装已解。

**④失败分支**：
- 现象：编一个解释圆场→根因：怕显得没搞清→处置：改回「未完全解释」并登记。
- 现象：因差异未解拒绝修复已确诊部分→根因：因噎废食→处置：分开处置。

**⑤验收清单**：
- [ ] 差异清单在档；
- [ ] 未解项措辞如实；
- [ ] 已确诊项照常修复。

### 【测试零输出≠卡死】

**⑤验收清单**：

- [ ] 脚本已加分阶段输出；
- [ ] 结论分栏。

**⑦参数表**：案例量级：双客户端联机全程约 45 分钟（本环境）；中途零输出属脚本设计。

2. 命中层逐层修：到达（【到达半径大于转弯半径】）、碰撞（【碰撞两遍解算】）、动画（【切档相位对齐】）、寻路（【寻路卡死三件套】）、同步（【木偶收敛证据】/上行节拍）→判定信号：逐层复测。
3. 全层修完跑整场→判定信号：「来回卡」整体消失而非单点改善。

**④失败分支**：
- 现象：修了一层就宣布不卡了→根因：叠加当单因→处置：五层全查完再下结论。
- 现象：某层查不出→根因：证据不足→处置：该层标待证，不硬说无问题。

**⑤验收清单**：
- [ ] 五层排查表齐全；
- [ ] 每层修复有专条对应；
- [ ] 整场复测整体通过。

**⑥禁忌与易错点**：不许单点归因；不许用「优化了寻路」代表全修。

**⑦参数表**：分层 5：转向/到达/碰撞/动画/同步。

### 【联机回归慢先查环境】

**①目标与适用场景**：联机回归脚本长时间零输出，先查脚本是否只在结尾输出一行＋本机算力饱和，再怀疑产品缺陷；容量档位未跑就写未判定，不写通过也不写失败。

**②前置条件**：可查脚本输出结构与机器占用；有分阶段日志改造方案（见【容量档位单独排轮】）。

**③操作步骤**：
1. 零输出超时→先读脚本输出设计→判定信号：是否只在结尾输出一行。
2. 查本机算力饱和证据（CPU/软件渲染）→判定信号：数据在档。
3. 定性后给脚本加分阶段日志、按环境标定预算重跑→判定信号：阶段日志可见。
4. 未跑到的档位写「未判定」→判定信号：报告措辞准确（见【诚实清单文化】）。

**④失败分支**：
- 现象：把环境慢写成产品失败→根因：没查环境→处置：改判并留痕。
- 现象：把未跑写成通过→根因：图交差→处置：改「未判定」并补排轮。

**⑤验收清单**：
- [ ] 环境定性有两项证据；
- [ ] 脚本已分阶段输出；
- [ ] 未跑项措辞为未判定。

**⑥禁忌与易错点**：不许零输出即判产品卡死；不许未跑写通过/失败。

**⑦参数表**：案例量级：本环境双客户端全程约 45 分钟；容量档位单独排轮约 40 分钟起。
