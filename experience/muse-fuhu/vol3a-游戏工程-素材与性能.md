## 素材收割与许可（26 条）

#### 【素材全量收割】

**① 目标与适用场景**：为一个游戏项目一次性把合法素材收全，避免开发中途缺素材回头找源。适用于立项或大版本开工前的素材准备轮。

**② 前置条件**：已明确目标游戏的品类与题材范围；已备好素材库目录与总目录（CATALOG）账本；已知本项目的许可白名单（见【许可白名单与付费拒收】）。

**③ 操作步骤**：
1. 按品类列收割清单做成需求矩阵（字段：品类 / 具体对象 / 动作或内容 / 尺寸 / 格式 / 数量，覆盖角色、场景、UI、音效、特效、字体）→ 预期现象：矩阵无空行 → 判定信号：「无空项」的判定 = 每个品类至少有一行细到可直接去找源的规格，清单与游戏设计文档的素材需求逐项对得上。
2. 只从三类源收割：开源仓库、CC0 素材站、明确标注免费可商用的素材站 → 注意：来源类别只是发现渠道、不是许可结论——公开可见的仓库没有 LICENSE 时按「许可无法确认」处理，不许因为「是开源仓库」就默认可用 → 预期现象：每个包在下载前逐个过许可闸门（见【许可白名单与付费拒收】）且许可类型可指认 → 判定信号：源页面或包内 LICENSE 能截图/存档（见【许可证据存档】）。
3. 逐包下载并立即跑文件头校验（见【文件头校验法】）→ 预期现象：坏文件当场被检出 → 判定信号：全量校验日志里坏文件数可计数，目标为 0（单波可达万级文件，实测一波 12,582 个文件、坏文件 0）。
4. 遇到需登录或人机验证的站点 → 预期现象：不尝试绕过 → 判定信号：该源登记进卡住清单（源名、卡因、所缺内容），并给出终态结论——已由替代源补齐同一需求，或已转入缺口表（两种都是合法终态，与失败分支口径一致，见【卡住清单不硬闯】）。
5. 每包入总目录登记（见【CATALOG 逐包登记】）→ 判定信号：库内文件数与账本登记数按同一计数口径全量一致（计数口径 = 解压后普通文件数，不含目录、原压缩包、evidence/、隐藏文件；符号链接跟随目标计一次——全库统一，口径定义见【CATALOG 逐包登记】）。

**④ 失败分支**：
- 现象：某品类素材怎么都找不到合规源 → 原因：该品类免费合规供给确实稀缺 → 处置：登记进缺口表（见【缺口如实登记】），走自制补齐路线（见【版权缺口自制补齐】），严禁用版权素材充数。
- 现象：下载量巨大、校验跑不完 → 原因：单波文件数过万 → 处置：按包分批校验、分批入账，不许跳过校验直接入库。

**⑤ 验收清单**：
- [ ] 收割清单各品类无空项，或空项已转入缺口表
- [ ] 全量文件头校验跑完，坏文件数 = 0
- [ ] 卡住站点全部登记且各有替代源结论
- [ ] 每包已入总目录，账本数与磁盘文件数一致

**⑥ 禁忌与易错点**：不许以「够用就好」收个子集交差——缺口总在最赶工时暴露；不许先下载后补许可判断；不许把无关题材素材凑数入库（见【题材不合不凑数】）。

**⑦ 参数表**：单波文件量级：万级（实测 12,582 个/波）；坏文件验收线：0；许可来源类别：开源 / CC0 / 明确免费可商用，共 3 类。

#### 【商业原作素材永不使用】

**① 目标与适用场景**：守住版权红线——商业游戏原作的角色精灵、音效、音乐及同人资源站扒图素材，永不进入项目。适用于任何有人提议「直接用原作素材」的时刻，包括需求方明确施压时。

**② 前置条件**：无技术前置；需要先明确一条事实并在沟通中摆明：产物部署在实名备案的公开域名上、公网可达，不存在「内部使用」的豁免空间。

**③ 操作步骤**：
1. 收到使用原作素材的提议 → 动作：明确拒绝，不执行、不下载、不留「临时试用」副本 → 判定信号：素材库与部署包内不存在任何原作文件。
2. 同步给出替代路径 → 动作：指出缺口对应的合法收割源或自制补齐方案（见【版权缺口自制补齐】）→ 判定信号：缺口表里该项的处置写的是合法源或自制，不是空白。
3. 若提议方以质量为由坚持（「原作素材最对口」）→ 动作：说明质量对口不改变侵权定性，替代方案按同规格（尺寸、帧数、风格）对齐原作规格来做 → 判定信号：自制规格清单与原作规格逐项对应。

**④ 失败分支**：
- 现象：已误收原作素材进库 → 原因：收割环节许可闸门失守 → 处置：立即删除该包全部文件、在拒收清单补登记（见【拒收清单留痕】）、全库按文件名与 MD5 复扫一遍确认无残留。
- 现象：替代素材观感差距大被质疑 → 处置：差距登记为缺口或顶替并明说等级（见【素材顶替明说等级】），不以差距为由回头用原作素材。

**⑤ 验收清单**：
- [ ] 素材库与部署包内无任何商业原作文件（按来源清单逐项核对）
- [ ] 每个被拒绝的需求都有对应的合法替代或自制条目
- [ ] 误收事件（如发生）已删除、已登记、已复扫

**⑥ 禁忌与易错点**：禁的是资产本身；玩法结构、招式结构可以学习（见【对标只学结构】），不要把红线扩大成「什么都不能参考」；也不要把「这次破例」当通融——口子一开，后续每包都要重新扯皮。

**⑦ 参数表**：实测参数：无——本条为红线纪律类，步骤为通用规程。

#### 【游戏托管红线】

**① 目标与适用场景**：自建游戏大厅的收录原则：所有游戏必须托管在自有服务器、点开即在本地玩，不挂官方下载链接跳转。适用于大厅收录/下架决策。

**② 前置条件**：大厅部署在自有服务器；对候选游戏已确认其客户端能否完整本地镜像。

**③ 操作步骤**：
1. 候选游戏先判体量与授权：大型商业游戏 → 结论：不收录 → 判定信号：候选清单上标注「不收录」及原因。
2. 客户端可完整镜像到本地的 → 动作：整包镜像、入口指向本地路径 → 判定信号：断网（或屏蔽外网）环境下点开入口能进游戏。
3. 全入口运行时审计：逐个入口实际打开并进入游戏，在网络请求记录（浏览器网络面板或代理日志）里核对首屏与进游戏全程的请求域名 → 判定信号：每个入口的外部域名请求数 = 0（入口地址是本地路径不算数，运行时偷偷请求外站同样算违规）。
3. 客户端无法本地镜像的非核心游戏 → 动作：删除该入口，宁缺毋滥 → 判定信号：大厅内不存在任何跳转外站的游戏入口。

**④ 失败分支**：
- 现象：某游戏本地镜像后缺资源、跑不起来 → 原因：镜像不完整或依赖外部服务 → 处置：补齐镜像再上线；补不齐则按非核心游戏删除，不留半成品入口。

**⑤ 验收清单**：
- [ ] 大厅每个入口的实际加载地址均为本地路径，且全入口运行时审计外部请求 = 0
- [ ] 断网环境抽测至少一款游戏可正常进入
- [ ] 被删入口在收录清单上有删除记录与原因

**⑥ 禁忌与易错点**：不要为了「游戏数量好看」留外链空壳入口；外链游戏不可控、无法纳入自有运维与验收。

**⑦ 参数表**：实测参数：无——本条为收录纪律类，步骤为通用规程。

#### 【文件头校验法】

**① 目标与适用场景**：批量下载后验证每个文件的真实格式与完整可解码性，剔除「扩展名对、内容错」与「头对、身坏」的坏文件（下载中断、站点返回 HTML 错误页冒充文件、CDN 给错内容、尾部截断）。适用于一切批量收割落盘后。本条分两级：**一级魔数初筛**只回答「像不像这个格式」，**二级完整解码终验**才回答「内容完整且可解码」——只有二级通过才许写「校验通过」，一级通过永远不许单独作为验收结论。

**② 前置条件**：本机有 Python + PIL，并按格式备齐二级解析手段（图片 PIL、音频解码器、GLB 结构解析、字体 fontTools、ZIP 标准库等，见步骤 3 对照表）；待验文件已全部落盘；已约定逐文件结果表的落盘位置；遍历规则先定死：递归全部子目录，符号链接跟随目标计一次，隐藏文件计入。

**③ 操作步骤**：
1. 枚举与分类：递归枚举全部文件，按文件头魔数判定真实类型（不信扩展名）→ 判定信号：每个文件有一行待验记录（路径、扩展名、魔数判定类型）；魔数不认识的类型直接标「未验（无分类规则）」，不许猜类型硬验。
2. 一级魔数初筛（只筛不验）：PNG 比对 8 字节签名 89 50 4E 47 0D 0A 1A 0A；JPG 比对 FF D8 FF；OGG 比对 "OggS"；WAV 须同时比对第 0–3 字节 "RIFF" 与第 8–11 字节 "WAVE"（只有 RIFF 不是 WAV）；GLB 比对 "glTF" 且版本号字段 = 2；HDR 比对 "#?RADIANCE" 或 "#?RGBE"（"#?" 只是前缀、单独不算命中）；ZIP 比对 "PK\x03\x04" → 判定信号：一级不符即判坏文件、移入隔离区，不再进二级。
3. 二级完整解码终验（按格式执行，缺一不可）：
   - 图片（PNG/JPG/WebP）：PIL 打开先 verify() 验结构——注意 verify() 后该文件对象即不可再用，必须**重新打开**再 load() 做完整像素解码；两步都过才算终验通过（verify 只验结构不验全部像素，load 才验像素数据）。
   - OGG：用解码器把整段音频解到文件尾（如解码到 null 输出），页 CRC 错误、流中途断裂即判坏——只看 "OggS" 头发现不了截断。
   - WAV：解析 RIFF 块结构，核对 fmt 块存在、data 块声明长度不超过文件实际剩余字节，再把全部采样帧读完；块长越界即判坏。
   - GLB：解析 12 字节头（魔数、版本 = 2、声明总长须等于文件实际字节数），再解析 JSON 块并逐项核对 accessor/bufferView 的偏移+长度不越出 BIN 块；任一越界即判坏。
   - HDR：核对头内 FORMAT 行与分辨率行存在，再完整解码全部扫描行；头对但扫描行不全即判坏。
   - ZIP：testzip() 逐条目验 CRC 之外，还要把每个条目实际读到尾（testzip 本身即读全条目验 CRC，返回非 None 指出首个损坏条目即判坏包）。
   - 字体（TTF/OTF/WOFF2）：用 fontTools 打开并读出 cmap，能打开且 cmap 非空才算通过。
   - JSON/文本类：全文解析（如 JSON 整体 parse），解析报错即判坏。
   - MP3/MP4 等媒体：用解码器完整解码到尾（解码到 null 输出），中途报错即判坏。
   - FBX 等无现成解析器的格式：有官方/第三方解析工具才许进二级；没有解析器的一律标「未验（无解析器）」，**不许计入已验总数**。
4. 逐文件结果表落盘：每文件一行，字段 = 路径 / 魔数判定类型 / 一级结果 / 二级结果 / 终态 / 错误详情 → 终态只许四种：通过、坏文件（已隔离）、永久失败（重下复验仍坏、已登记换源）、未验（无分类规则或无解析器，含原因）→ 判定信号：结果表行数 = 枚举文件总数，未验数被单独统计、明示在汇总里。
5. 坏文件处置：逐个重下并从一级重新复验（重下重试上限按源站情况在本轮开始前写明，示意 2 次）；复验仍坏 → 终态改「永久失败」，登记卡住并换源（见【卡住清单不硬闯】），不许无限重试、也不许带着坏文件入库。

**④ 失败分支**：
- 现象：一级通过、二级失败 → 原因：尾部截断或后半损坏（魔数只验开头，天然查不出）→ 处置：按坏文件走第 5 步，这正是设二级的原因，不许以「头是对的」放行。
- 现象：整批文件一级都不符 → 原因：站点返回了统一的错误页/拦截页 → 处置：整批作废，先解决下载通道（查 UA、查签名链），不要逐个重下。
- 现象：某类文件全批「未验」→ 原因：该格式没有解析手段 → 处置：如实保留未验终态并在汇总中置顶提示，补齐解析器后单独补验，不许把未验混进通过数。

**⑤ 验收清单**：
- [ ] 逐文件结果表齐全：行数 = 文件总数，每行有终态
- [ ] 通过数只含二级终验通过的文件；未验数单独列示且不为「已验」口径的一部分
- [ ] 坏文件 = 0（已重下复验通过）或已转永久失败并登记换源
- [ ] 结果表与校验日志留存，可按路径复查任一文件的判定依据

**⑥ 禁忌与易错点**：绝不按扩展名或文件大小判断真伪；绝不把魔数初筛说成「解码校验」——那是本条旧版的原罪；verify() 后不重新打开就 load 是常见代码错误；ZIP 只验「能打开」不够，必须验到条目级 CRC。

**⑦ 参数表**：校验分级：2 级（魔数初筛 / 完整解码终验）；魔数签名：PNG = 89 50 4E 47 0D 0A 1A 0A、JPG = FF D8 FF、OGG = "OggS"、WAV = "RIFF"+"WAVE"（双段）、GLB = "glTF"＋版本 2＋声明总长 = 实际字节数、HDR = "#?RADIANCE"/"#?RGBE"、ZIP = "PK\x03\x04"；终态集合：通过 / 坏文件 / 永久失败 / 未验，共 4 种；验收线：坏文件 = 0（或已转永久失败登记），未验数必须明示。
#### 【Kenney 官网下载流程】

**① 目标与适用场景**：从 Kenney 官网下载素材包时遇到 403，先按本流程走官网自家下载链路，不要直接下「下载被拦」的结论。适用于该站及同类有 UA 门控的素材站。

**② 前置条件**：有可编程的 HTTP 客户端；知道目标素材包的页面地址。

**③ 操作步骤**：
1. 带浏览器 User-Agent 访问素材页 → 预期现象：返回 200 页面 HTML → 判定信号：状态码 200；若仍 403，先换标准浏览器 UA 再试，不要改判为封禁。
2. 在页面 HTML 中提取 data-download-id（定位法：在页面源码中检索 download 按钮元素的 data-download-id 属性，取其属性值；记录时连同所在页面 URL 与提取位置一并写入链路记录）→ 判定信号：提取到非空 id；提取不到说明页面结构变了，转失败分支。
3. 用该 id 换取 download-link 的签名下载链接 → 预期现象：拿到带签名参数的直链 → 判定信号：直链下载返回的字节数与页面标注量级一致。
4. 下载后立即跑【文件头校验法】→ 判定信号：校验通过才算落盘成功。

**④ 失败分支**：
- 现象：素材页本身返回 404 → 原因：slug 不存在，不是通道问题 → 处置：转【slug 不存在≠下载失败】处置，找替代包。
- 现象：页面 200 但无 data-download-id → 原因：站点改版 → 处置：人工用浏览器打开页面走一遍点击下载，并按固定格式记录新链路（页面 URL / 点击路径 / 新字段名与位置 / 换链请求的方法与参数名）后再脚本化，不许只记一句「手动下过」。

**⑤ 验收清单**：
- [ ] 下载文件通过文件头校验
- [ ] 该包许可证据已存档（见【许可证据存档】）
- [ ] 下载链路（UA、id 提取方式）记录在案，下次可复现

**⑥ 禁忌与易错点**：403 的第一嫌疑永远是 UA 反爬，不是封禁；不要在没查 UA、请求头、官方接口之前向任何人报告「下载被拦」。

**⑦ 参数表**：关键字段：data-download-id；判定顺序：状态码 → UA → 签名链 → 文件头校验。实测参数：无专用数值——本条为流程类，步骤为通用规程（判定信号取自原始记录）。

#### 【itch 匿名免费下载流程】

**① 目标与适用场景**：下载 itch.io 上标价免费/自愿付费且开放下载的素材包，走官方匿名下载链路，与网页端点击「No thanks, just take me to the downloads」等价。无破解、无绕付费。

**② 前置条件**：目标包页面可公开访问；确认该包为免费开放下载（付费包不在此列）。

**③ 操作步骤**：
1. 向游戏页的 download_url 接口发 POST → 预期现象：返回下载页地址/内容 → 判定信号：响应中能找到目标文件的 upload 标识。
2. 向 file/<upload_id> 接口发 POST → 预期现象：返回签名直链 → 判定信号：直链有效期短（约 60 秒为一次实测的观察值、不是平台常数，各包可能不同），拿到后立即进入下一步，不许囤链。
3. 立即用直链下载文件本体 → 判定信号：字节数与下载页/响应给出的预期文件大小一致（页面未给大小时以「能完整解压＋文件头二级终验通过」为完整性判据，见【文件头校验法】），随后跑文件头校验。
4. 解压并保存包内 LICENSE 到 evidence/（见【许可证据存档】）；包内无 LICENSE 的按该条失败分支走页面标注路径，页面亦无标注的按许可无法确认处理、不许入库。

**④ 失败分支**：
- 现象：直链下载到一半失效 → 原因：60 秒签名过期 → 处置：从第 2 步重走换新链，不要反复重试旧链。
- 现象：download_url 不返回下载页 → 原因：该包未开放匿名下载或需登录 → 处置：登记卡住清单（见【卡住清单不硬闯】），找替代源。

**⑤ 验收清单**：
- [ ] 文件完整落盘且文件头校验通过
- [ ] 许可原文已存档
- [ ] 该包已登记进总目录

**⑥ 禁忌与易错点**：不要把这条流程用在付费包上——付费包按【许可白名单与付费拒收】拒收；签名链过期是平台设计，不是故障，不要据此报「下载失败」。

**⑦ 参数表**：签名直链有效期：约 60 秒（单次实测观察值，非平台常数）；多 upload 选择键：文件名 / 目标平台 / 文件大小（响应含预期大小时以大小核对目标文件）；接口顺序：download_url → file/<upload_id> → 直链下载，共 3 步。

#### 【官方 API 校验下载】

**① 目标与适用场景**：从提供官方 API 与校验和的素材站（Poly Haven、ambientCG 类）下载大文件（HDR、4K 贴图），下载后与官方 MD5 逐个比对，一致才算落盘成功。

**② 前置条件**：该站提供官方 API 且文件清单含 MD5；本地可计算 MD5。

**③ 操作步骤**：
1. 调官方 API 拿文件清单与 CDN 地址 → 判定信号：清单中每个文件带官方 MD5 值。
2. 逐个下载 → 预期现象：文件落盘。
3. 逐个计算本地 MD5 并与官方值比对 → 判定信号：全部一致 = 落盘成功；任一不一致进入失败分支。
4. 一致的文件再跑文件头校验（见【文件头校验法】）双保险 → 判定信号：双验通过才入总目录。

**④ 失败分支**：
- 现象：MD5 不一致 → 原因：传输损坏或 CDN 给错内容 → 处置：删除本地文件重下，重下仍不一致则换 CDN 节点或登记卡住，不要带着不一致入库。
- 现象：API 清单无 MD5 → 处置：退回【文件头校验法】单验，并在目录里注明该源无校验和。

**⑤ 验收清单**：
- [ ] 清单内每个文件 MD5 比对结果有记录
- [ ] 不一致文件已重下至一致或已登记处置
- [ ] 双验（MD5＋文件头）通过后才入账

**⑥ 禁忌与易错点**：文件头校验只能验格式、验不了内容完整——大文件只验文件头就入库是典型假验收；MD5 比对必须逐个做，不许抽查代替全量（官方给了全量清单）。

**⑦ 参数表**：校验算法：MD5（官方提供值）；验收线：清单文件 100% 一致。实测参数：无专用数值——本条为流程类，步骤为通用规程（判定口径取自原始记录）。

#### 【许可证据存档】

**① 目标与适用场景**：让每个素材包的许可结论日后可回查、可举证。适用于全部外部素材，无一例外（包括 CC0——「它是 CC0」本身就是需要证明的结论）。**证据口径全卷统一：每包必须两件齐全——许可原文＋来源页面存档，缺一即「证据未完成」，不许入库**（本条的步骤、验收、参数三处口径一致，无二选一）。

**② 前置条件**：素材包已下载；素材库内已约定 evidence/ 存档位置（与素材本体同包存放）。

**③ 操作步骤**：
1. 递归收集许可原文 → 动作：把包内**全部** LICENSE/License.txt/ COPYING 等许可文件（不限根目录，子目录与第三方子许可一并收）按相对路径原样复制进该包 evidence/，不改一字 → 判定信号：evidence/ 内许可文件数 = 包内许可文件总数。
2. 保存来源页面存档 → 动作：把素材页 HTML 存档到同一 evidence/（动态页面脚本抓取拿不到许可字段时，改用浏览器另存的完整页面或页面打印件，并注明获取方式）→ 判定信号：存档内能定位到许可标注原文。
3. 写证据记录行 → 字段固定：来源 URL、抓取时间、HTTP 状态、页面标题、各证据文件的 SHA-256、许可结论、判定依据（按哪条白名单规则判定，见【许可白名单与付费拒收】）→ 判定信号：日后审计凭记录行能对应到具体版本、复算哈希能对上。
4. 在总目录该包条目中注明许可类型与证据位置 → 判定信号：审计按目录能直接打开证据原文与记录行。

**④ 失败分支**：
- 现象：包内无任何许可文件 → 处置：只剩页面存档一件，按「证据未完成」处理：页面标注含完整条款或指向明确许可文本的，才可凭页面判定并在记录行写明「包内无许可文件、凭页面标注」；页面只有一句「Free for commercial use」式口号、无条款无指向的，不足以支撑结论，按许可无法确认处理（见【拒收清单留痕】）。
- 现象：来源页面已下线/改版 → 处置：已存档的页面即为当时证据，不因页面变化推翻既有结论，但要在目录标注页面现状。

**⑤ 验收清单**：
- [ ] 每包 evidence/ 两件齐全（许可原文＋页面存档），缺一的包未入库且已标注去向
- [ ] 每包有证据记录行（URL/抓取时间/状态/标题/SHA-256/结论/判定依据七项齐全）
- [ ] 包内多许可/子许可已递归收全
- [ ] 无「凭记忆认定许可」的包存在

**⑥ 禁忌与易错点**：素材站会改版、改条款，事后争议时「我当时看过」没有效力——没有存档等于没有证据；CC0 也要留原文；只存一件（只有原文没有页面、或只有页面没有原文）是半份证据，审计时同样站不住。

**⑦ 参数表**：每包存档件：许可原文（全量递归）＋来源页面存档，共 2 件，缺一不可；证据记录行字段：来源 URL / 抓取时间 / HTTP 状态 / 页面标题 / SHA-256 / 许可结论 / 判定依据，共 7 项。实测参数：无专用数值——本条为流程类，步骤为通用规程。
#### 【许可白名单与付费拒收】

**① 目标与适用场景**：收割环节的许可闸门：在下载之前就拦下不合规素材。适用于每个候选素材包的准入判定。

**② 前置条件**：候选包的许可类型可查（包内 LICENSE 或来源页标注）；拿不到许可信息的先按无法确认处理。

**③ 操作步骤**：
1. 判许可类型 → 放行类：CC0、MIT、Apache、OFL、明确标注免费可商用 → 判定信号：许可名称能在白名单中逐字对上。
2. CC-BY → 动作：先登记署名凭据（作者、来源、署名文本）再收 → 判定信号：署名登记完成才允许下载入库；署名落法见【CC-BY 署名位置】。
3. 付费包 → 结论：拒收 → 动作：只作质量标杆记录（记规格、价格、拒收结论，如某对标最佳格斗素材包实测标价 $4.54、拒收归档）→ 判定信号：库内无该包文件、标杆记录在册。
4. CC-BY-SA → 结论：拒收（传染性与项目分发方式冲突）→ 动作：登记拒收清单（见【拒收清单留痕】）。
5. 自定义许可 → 转【自定义许可细读】逐字读完再判。

**④ 失败分支**：
- 现象：免费 CC0 同类包足量、有人提议为单个付费包破例 → 处置：不破例，理由记录在案；破例口子一开，闸门即失效。
- 现象：许可标注含糊（只写「free」无条款）→ 处置：按许可无法确认处理，拒收并登记。

**⑤ 验收清单**：
- [ ] 入库每包许可类型都在白名单内或已登记 CC-BY 署名
- [ ] 付费/CC-BY-SA 拒收项全部在拒收清单有记录
- [ ] 无「先下下来再说」的包

**⑥ 禁忌与易错点**：许可问题在收割环节拦截成本最低，下完再判是浪费带宽还埋雷；不要用「非商业使用」自我安慰——产物是公网上线品，按最严口径判。

**⑦ 参数表**：白名单许可：CC0 / MIT / Apache / OFL / 明确免费可商用；条件放行：CC-BY（须先登记署名）；拒收：付费、CC-BY-SA、许可无法确认；标杆记录实例：付费格斗包 $4.54（实测标价，仅作记录、未购未用）。

#### 【拒收清单留痕】

**① 目标与适用场景**：把拒收变成可复用的情报资产，防止下一轮收割重复评估、重复踩坑。适用于所有被拒素材的登记。

**② 前置条件**：已备拒收清单文件（与缺口表一起维护）；拒收判定口径见【许可白名单与付费拒收】。

**③ 操作步骤**：
1. 每拒一包，逐项登记：包名、来源、许可类型、拒收原因 → 判定信号：清单条目四要素齐全。
2. 拒收原因按三类归口写明：CC-BY-SA / 自定义授权禁再分发 / 许可无法确认（UNKNOWN）→ 判定信号：原因字段能归入三类之一，不写含糊的「不合适」。
3. 下一轮收割开始前先读拒收清单 → 判定信号：本轮候选与清单比对过，重复候选直接跳过并注明「已拒收过」。

**④ 失败分支**：
- 现象：某包许可后来被作者澄清/变更为合规 → 处置：在清单该条目下追加复核记录（日期、新许可证据），按新结论重新准入，不删旧记录。

**⑤ 验收清单**：
- [ ] 每个拒收包在清单有条目且原因归类明确
- [ ] 收割轮启动前有读清单的比对记录
- [ ] 许可变更的复核以追加方式留痕，未覆盖旧记录

**⑥ 禁忌与易错点**：「无法确认」按拒收处理——许可举证责任在使用者一方；拒收不留痕等于没拒，下一轮必然重踩。

**⑦ 参数表**：拒收原因分类：3 类（CC-BY-SA / 禁再分发 / UNKNOWN）。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【Mixamo 许可边界】

**① 目标与适用场景**：使用 Mixamo 类「可内嵌使用、不可再分发原始文件」的动画素材时，部署形态不越界。适用于一切同类许可素材。

**② 前置条件**：原始文件（FBX）存放在内部素材区，不在 Web 可达目录内；项目有 FBX→GLB 转换环节。

**③ 操作步骤**：
1. 原始 FBX 只作内部素材源 → 判定信号：部署目录与静态资源目录内不存在 FBX 原文件（按扩展名全盘扫描确认）。
2. 转换后再部署 → 动作：FBX 转 GLB 后只把 GLB 放进部署包 → 判定信号：线上资源清单只有 GLB、无 FBX。
3. 入台账时标注该素材的许可类型与「原始文件不部署」处置 → 判定信号：台账条目含此标注。

**④ 失败分支**：
- 现象：部署包里混入 FBX 原文件 → 原因：打包脚本把素材源目录整包带入 → 处置：立即下线该文件、修打包脚本的包含规则、全包复扫同类文件。

**⑤ 验收清单**：
- [ ] 部署包/线上目录 FBX 扫描结果 = 0
- [ ] 每个此类素材台账条目含许可与部署形态标注

**⑥ 禁忌与易错点**：把原始文件放到可公开下载的服务器上等于再分发，这是本条唯一的红线动作；「转换后内嵌」属于用进作品，在许可内，不要混淆两者而因噎废食。

**⑦ 参数表**：部署允许格式：转换后 GLB；禁止部署：原始 FBX。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【自定义许可细读】

**① 目标与适用场景**：处理独立作者自拟许可的素材包（nanasha、rvros 类）：标签写「免费可商用」不够，必须逐字读 LICENSE 原文再定收不收、怎么部署。

**② 前置条件**：已拿到包内 LICENSE 原文（拿不到原文的按许可无法确认处理）。

**③ 操作步骤**：
1. 逐字读 LICENSE，逐项摘出四要素：能否商用、能否改编、能否转售素材本身、能否再分发素材本身 → 判定信号：四要素各有原文出处句。
2. 按最常见形态判定：可改编、可用进游戏，但禁转售、禁再分发素材本身 → 结论：「用进游戏可以，打包分发素材不行」→ 部署动作：只随游戏发布渲染结果与打包图集，不提供素材原包下载 → 判定信号：部署物内无原包文件、无原包下载入口。
3. 四要素任一与项目分发方式冲突 → 结论：拒收并登记（见【拒收清单留痕】）。
4. 判定结论与四要素摘录写入台账并存档证据（见【许可证据存档】）。

**④ 失败分支**：
- 现象：LICENSE 是外文/表述含糊，关键要素读不准 → 处置：按无法确认处理、拒收；不要凭机翻印象放行。
- 现象：已按「可商用」入库、细读后发现禁再分发 → 处置：素材可保留在游戏内使用，但立即撤下任何原包分发形态，并在台账更正部署形态。

**⑤ 验收清单**：
- [ ] 每个自定义许可包有四要素摘录与结论
- [ ] 部署物不含被禁分发的原包
- [ ] 证据原文已存档

**⑥ 禁忌与易错点**：这类许可与 CC0 的差别就在再分发一条上，凭标签印象行事最容易在这里翻车；「免费可商用」五个字永远不构成放行依据。

**⑦ 参数表**：必查四要素：商用 / 改编 / 转售素材 / 再分发素材。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【CC-BY 署名位置】

**① 目标与适用场景**：逐个素材按其 CC-BY 许可原文履行署名义务，署名载体必须**随作品一起到达接收者**。适用于确需使用 CC-BY 素材的情形；默认策略是选材优先免署名许可，从源头减少署名负担。

**② 前置条件**：该 CC-BY 素材已按【许可白名单与付费拒收】完成署名凭据登记（作者、来源、许可版本）；已拿到该素材所附的具体许可文本（不同版本、不同来源的署名要求不完全相同，不许凭「CC-BY 都一样」套用）。

**③ 操作步骤**：
1. 选材阶段先过滤：同功能有 CC0/MIT 替代的 → 动作：用免署名替代，不收 CC-BY → 判定信号：台账中 CC-BY 条目只剩无替代者。
2. 逐许可核对履约要素 → 动作：按该素材许可原文逐项摘出要求，通常包括：作者名、作品名、来源链接、许可名称与版本及许可链接、是否改动及改动说明；许可另有特别位置/形式要求的（如要求出现在特定位置）单独标出 → 判定信号：每个在用 CC-BY 素材有一张要素核对表，缺项 = 未履约。
3. 署名落到随作品分发的载体 → 动作：署名写进随产品一同交付的致谢/署名文件（如随包发布的 CREDITS/署名页），**只存在于内部开发文档、接收者拿不到的，不算履约**；内部开发文档可另存一份作台账备份，但不能替代分发载体 → 判定信号：从发布产物内能直接打开署名载体并逐项对上核对表。
4. 界面口径：默认不把署名塞进游戏界面（界面内署名易在改版中被误删、且破坏体验）；但某许可明文要求界面内或特定位置署名的，按其条款执行并在台账特别标注 → 判定信号：特殊要求项有对应的界面/位置证据。

**④ 失败分支**：
- 现象：改版时署名条目被误删 → 处置：以台账登记为准恢复，并把署名文件纳入发布前检查清单（见验收），防再次单点丢失。
- 现象：许可原文找不到或版本不明 → 处置：按许可无法确认处理，不凭印象补署名要素。

**⑤ 验收清单**：
- [ ] 每个在用 CC-BY 素材有逐许可要素核对表且无缺项
- [ ] 署名载体随发布产物分发、能从产物内打开（不是只在内部文档里）
- [ ] 台账登记数与署名载体条目数一致
- [ ] 有特殊位置/形式要求的已单独标注并执行

**⑥ 禁忌与易错点**：署名是法定义务必须履约，省的是位置不是义务；验收时只查「文档里写了」是假履约——查的是接收者拿到的产物里有没有；各版本 CC-BY 的要素要求有差异，逐个核对，不许一张表套全部。

**⑦ 参数表**：署名要素（逐许可核对，通常五项）：作者 / 作品名 / 来源链接 / 许可名称与版本（含许可链接）/ 改动说明；载体要求：随作品分发，内部文档不算。实测参数：无专用数值——本条为流程类，步骤为通用规程。
#### 【卡住清单不硬闯】

**① 目标与适用场景**：拿不到的素材源（需登录、人机验证、脚本 403）登记卡点并换源补齐需求，绝不硬闯验证、不代注册账号。适用于收割中任何受阻的源。

**② 前置条件**：已备卡住清单（字段：源、卡因、所缺内容、替代结论）；手头有 CC0 替代源渠道。

**③ 操作步骤**：
1. 遇阻即停 → 动作：不尝试破解验证、不代注册、不伪造身份 → 判定信号：无任何绕验证的尝试记录。

**④ 失败分支**：

**⑤ 验收清单**：
- [ ] 每个受阻源在卡住清单有条目
- [ ] 每条卡点有替代结论（已补齐/转缺口）
- [ ] 无绕验证、无代注册行为

**⑥ 禁忌与易错点**：与【Pexels 直链绕行】严格区分——站点自身有公开页面路径可走的是正道绕行；需要伪造身份或破解验证的是硬闯，禁止。硬闯的代价不止当次失败，还可能触发账号与 IP 层连带封禁。

**⑦ 参数表**：清单字段：源 / 卡因 / 所缺内容 / 替代结论，共 4 项。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【Pexels 直链绕行】

**① 目标与适用场景**：素材站（Pexels 类）网页对脚本直连返回 403 时，顺站点页面既有公开路径取图。仅适用于素材本身免费授权且页面公开可达的情形。

1. 脚本直连搜索接口 → 预期现象：返回 403 → 判定信号：不要据此判「图不可用」，进入下一步。
2. 走页面路径：先搜索、进照片页 → 动作：先记下该照片页的图片 ID，再在照片页 HTML 中提取与该 ID 对应的图片 CDN（images.pexels.com）直链（页面内常有多图直链，须按目标图的 ID/标识定位，不许取第一条）→ 判定信号：提取到的直链与目标图 ID 对应。

- 现象：照片页也需登录才可见 → 处置：超出本条适用范围，转【卡住清单不硬闯】登记，不找其他旁门。
- 现象：直链下载到的不是目标图 → 原因：页面内有多图、提取错位 → 处置：按页面中目标图的标识重新定位直链，下载后目检确认。

**⑤ 验收清单**：
- [ ] 下载文件与目标图一致（目检）
- [ ] 文件头校验通过、许可已存档
- [ ] 全程未登录、未破解、未伪造请求身份

**⑥ 禁忌与易错点**：绕行的正当性来自「走页面公开路径」——网页自己加载图片用的地址；任何需要伪造身份的「绕行」都是硬闯，不在此列。

**⑦ 参数表**：路径顺序：搜索 → 照片页 → CDN 直链，共 3 步。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【slug 不存在≠下载失败】

**① 目标与适用场景**：按 slug/ID 取资源失败时，先分清「资源不存在」与「下载通道失败」，避免排障方向错误。适用于一切按标识取资源的场景。

**② 前置条件**：已知目标 slug；能区分站点返回的状态码（404 与其他错误）。

**③ 操作步骤**：
1. 取资源失败 → 第一步查状态：用浏览器（或带浏览器 UA）直接访问该 slug 的官方页面 → 判定信号：官网页面本身 404 = 资源不存在（如某素材站的 weapon-pack、medieval-kit 两个 slug 官网直接 404）。
2. 结论为不存在 → 动作：停止一切重试，登记「包不存在」并找替代包 → 判定信号：下载失败入册记录写明不存在与替代方案（见【下载失败入册】）。
3. 官网页面存在但下载失败 → 才进入通道排障：查 UA、查签名链、查官方接口（见【Kenney 官网下载流程】）。

**④ 失败分支**：
- 现象：官网页面存在、脚本 404 → 原因：slug 拼写或路径规则错误 → 处置：从官网索引页反查正确 slug，不要对错误 slug 反复重试。

**⑤ 验收清单**：
- [ ] 每个失败项有「不存在 / 通道失败」二分结论
- [ ] 不存在的已登记并有替代结论
- [ ] 无对不存在资源超过一轮的无谓重试

**⑥ 禁忌与易错点**：把不存在误报成「下载失败」会引向查网络、查 UA、反复重试的整轮浪费；顺序永远是先验存在性、再谈通道。

**⑦ 参数表**：判定分叉：官网页面状态码（404 = 不存在）。实测参数：无专用数值——本条为流程类，步骤为通用规程（实例 slug 取自原始记录）。

#### 【题材不合不凑数】

**① 目标与适用场景**：全量收割的边界管理——目标范围外题材的素材，即使官网存在且可下载，也跳过并留痕。适用于收割清单执行中遇到题材外包时。

**⑤ 验收清单**：
- [ ] 题材外包零入库
- [ ] 每个跳过包有留痕记录
- [ ] 「全量」的口径在账本中写明为「目标范围内收全」

**⑥ 禁忌与易错点**：全量口径针对目标范围，无关素材只会膨胀库容、污染台账、增加接线审计成本；但跳过不留痕与乱收同样错误——收与不收都要有记录（见【缺口如实登记】）。

**⑦ 参数表**：实测参数：无——本条为纪律类，步骤为通用规程。

**② 前置条件**：已备缺口表（字段：缺口名、需求规格、已试过的源、处置状态）；缺口表与总目录、接线台账并行维护（三本账，见【素材库总量管理】）。

#### 【调研数字实测纠正】

**① 目标与适用场景**：外部调研给出的数量类数字（动画段数、帧数、体积等）在用作规划依据前，先实测纠正。适用于一切要拿来排期、做动作设计、定接入规划的二手数字。

**② 前置条件**：有可导入实测的工具（如 Blender 批量导入脚本）；调研数字及其出处已记录。

**③ 操作步骤**：
1. 拿到调研数字 → 动作：先标注「未实测」，不直接写入规划 → 判定信号：规划文档中该数字带未验标记。
2. 逐个导入实测并按统一口径计数（去重：同名变体、根运动变体不重复计）→ 实测案例：某动画库调研称约 250 段，Blender 逐个导入实测不重复只有 84 段 → 判定信号：实测计数过程可复现（导入清单留存）。
3. 查虚高来源 → 结论示例：调研把付费 Pro 版内容与根运动变体重复计入 → 动作：把虚高原因写进纠正记录。
4. 以实测值入档，调研值标注「已纠正」→ 判定信号：后续规划只引用实测值。

**④ 失败分支**：
- 现象：实测条件不具备（工具缺失、文件格式无法批量导入）→ 处置：该数字在规划中降级为「背景参考」，不作排期依据，并注明未实测。

**⑤ 验收清单**：
- [ ] 规划依据类数字全部有实测值与计数口径
- [ ] 被纠正的调研值有虚高原因记录
- [ ] 未实测数字未被用作排期依据

**⑥ 禁忌与易错点**：二手数字的计数口径（是否含变体、是否含付费版）默认不可信；虚高三倍的段数会让排期与动作设计整体落空——这类错误在做到一半时才暴露，代价最大。

**⑦ 参数表**：实测案例：调研值约 250 段 → 实测 84 段（不重复口径）；虚高来源：Pro 版内容 + 根运动变体重复计数。

#### 【免费版内容边界】

**① 目标与适用场景**：分级授权素材（Free/Pro、Standard/Full）的接入规划，只按免费版的实际内容清单走，不按产品页全量宣传走。

- [ ] 无按宣传清单排进计划的不存在内容

**⑥ 禁忌与易错点**：产品页展示的是全版本能力总和；免费版清单必须来自解包实查，截图和宣传页都不能替代。

**⑦ 参数表**：实测案例：免费 Standard 版动画组 = 手枪组（有）/ 步枪组（无）。其余参数：无——本条以清单核对为主，步骤为通用规程。

#### 【素材先验货再动手】

**① 目标与适用场景**：素材接入排工之前，先解析验货，把「以为有什么」换成「确实有什么」。3D 素材必验；2D 精灵表走【帧数实测对齐】。

**② 前置条件**：素材已落盘；有 GLB 解析与 FBX 头检查手段。

**③ 操作步骤**：
1. GLB：解析 JSON chunk，按验货字段表逐项查：meshes / skins / animations 计数、骨骼名清单、每段动画时长、材质与贴图清单、单位与坐标系 → 判定信号：字段表无空项并写入目录（只数三项不足以排工——骨骼名对不上、时长不对，接入照样返工）。

3. 验货结论入目录后再排接入工 → 判定信号：接入计划引用的模型数、骨骼、动画段与验货结论一致。

**④ 失败分支**：
- 现象：解析失败或结构异常 → 处置：先按【文件头校验法】判文件真伪；文件完好但结构与宣传不符的，以实查为准更正目录，不按包名排工。
- 现象：包内混有多个模型/多套骨骼 → 处置：逐个拆分登记，不许整包当一个素材排工。

**⑤ 验收清单**：
- [ ] 每个待接入 3D 包有验货结论入目录
- [ ] 接入计划数字与验货结论一致
- [ ] 异常包有单独处置记录

**⑥ 禁忌与易错点**：包名与宣传图经常与实际内容对不上（参见【调研数字实测纠正】【免费版内容边界】）；跳过验货直接排工，等于把不确定性排进工期。

**⑦ 参数表**：GLB 必查项：meshes / skins / animations 计数、骨骼名、动画时长、材质与贴图清单、单位与坐标系；FBX 必查项：Kaydara 文件头、动画栈清单、骨骼名清单。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【同文件 cmp 校验】

**① 目标与适用场景**：怀疑两个角色包同源时，先用字节比对给出「文件级等同」的确定性结论，再按骨架判定表决定动画能否共用。适用于同源嫌疑的模型文件。**结论边界先说死：cmp 无差异只能推出「两个文件逐字节相同、含其全部内嵌内容」，推不出任何超出这两个文件范围的结论。**

**② 前置条件**：两个待比文件均已落盘；有 cmp（或等效哈希比对）工具；已知该包的贴图/材质是内嵌在模型文件内还是外部文件（决定还要比什么）。

**③ 操作步骤**：
1. 对两个同名模型文件执行 cmp 字节比对 → 实测案例：两个角色包的 characterMedium.fbx 经 cmp 验证字节完全一致 → 判定信号：cmp 无差异输出（退出码 0）。
2. 字节一致时结论只写到这一层：「两文件字节等同，内嵌骨骼、内嵌动画、内嵌材质数据相同」→ 注意：文件真全等，则内嵌皮肤（贴图/材质）也相同，**不许写「只有皮肤不同」**——皮肤若不同，差异只可能在外部文件里，而外部文件不在本次比对范围内 → 动作：贴图/材质为外部文件的，把外部文件清单逐个另行 cmp 或哈希比对，差异结论只来自那次比对。
3. 动画共用的判定另走骨架判定表（不许由 cmp 单独推出）：逐项比对——骨骼名集合相同、父子层级相同、绑定姿势（bind pose）一致、动画轨道的目标骨骼名与目标文件骨骼名对得上 → 四项全过才许在目录标注「同骨架、动画可共用」；字节一致的文件四项天然全过（内嵌数据同一份），字节不一致时必须逐项实测后才许下此结论。

**④ 失败分支**：
- 现象：字节不同 → 原因：可能只是元数据差异，不等于骨骼不同 → 处置：退回【素材先验货再动手】，按第 3 步骨架判定表逐项比对再判，不许凭字节不同就判骨骼不合。

**⑤ 验收清单**：
- [ ] 比对结果（一致/不一致）与命令输出留存
- [ ] 结论表述未超出比对范围（无「只有皮肤不同」式外推）
- [ ] 外部贴图/材质文件已另行比对（如该包为外部形态）
- [ ] 「同骨架、动画可共用」结论有骨架判定表四项记录支撑

**⑥ 禁忌与易错点**：靠「看起来像」判断骨骼一致性不可靠；字节一致是免费且决定性的证据，先用它；但决定性只限于「这两个文件相同」这一句话——反过来，字节不同什么都证明不了，不要误判。

**⑦ 参数表**：判定工具：cmp（字节级）；一致判据：零差异；骨架判定表：骨骼名集合 / 父子层级 / 绑定姿势 / 动画轨道目标，共 4 项。实测参数：无专用数值——本条为流程类，步骤为通用规程。
#### 【帧数实测对齐】

**① 目标与适用场景**：精灵表帧数写入目录（作为后续所有切割代码的依据）之前，先定布局模型、再算帧数、最后逐帧预览裁定。适用于全部精灵表素材。**禁止只拿一个公式套所有表**——单行无间距只是布局的一种。

**② 前置条件**：精灵表图片可读取宽高；先把布局模型定下来并写进目录条目：行数 × 列数、边距 margin（上下左右）、帧间距 spacing、帧宽/帧高是等宽还是异宽；作者标注（帧数、帧宽、帧高）可查（包内说明或页面），查不到的按失败分支处理。

**③ 操作步骤**：
1. 定帧宽来源（按优先级取，取到哪级写明哪级）：(a) 作者标注帧宽/帧高；(b) 作者只给帧数时按布局反推——单行无边距无间距：帧宽 = 图宽 ÷ 帧数；带边距与间距：帧宽 = (图宽 − 左边距 − 右边距 − (列数−1)×间距) ÷ 列数，帧高同理按行数算；(c) 无任何作者标注时走第 2 步 alpha 扫描定界 → 判定信号：帧宽有明确来源与计算过程，不是猜的。
2. alpha 扫描定界（来源 (c) 或公式不能整除时用）：逐列统计 alpha 不为 0 的像素数得列投影，连续全透明列段即帧间空白候选界；阈值跑两档对照（alpha>0 与 alpha≥128，均为标定档位、非实测常数）——半透明辉光/阴影会撑大低阈值结果，两档结论不一致时以逐帧预览裁定 → 判定信号：帧界位置有列投影数据支撑。
3. 算帧数并比对：按布局模型算出帧数，与作者标注逐项比对 → 判定信号：一致直接进入第 4 步；不一致不许直接「以实测为准」——计算依赖假定帧宽、本身不是独立证据，必须走第 4 步裁定。
4. 逐帧预览裁定（冲突时的最高裁定方）：按候选帧界切出逐帧拼图（contact sheet），逐帧看主体是否完整、有无错位/残影/半帧 → 判定信号：拼图逐帧完整才定案；裁决顺序固定：逐帧预览 > alpha 界线 > 计算值 > 作者标注，定案值与裁定依据写入目录。

**④ 失败分支**：
- 现象：图宽不能被帧宽整除 → 原因不止帧宽取错，也可能是图外留白、最后一帧被裁、行列方向判反 → 处置：逐项排查布局模型（边距/间距/行列），再用 alpha 扫描重定帧宽；帧界异常的表升级到【帧表三方交叉核定】。
- 现象：作者标注缺失 → 处置：第 1 步走来源 (c)，定案后标注「无作者标注、经 alpha 扫描＋逐帧预览定案」，切割后逐帧目检复核（第 4 步不得跳过）。

**⑤ 验收清单**：
- [ ] 每张入目录的表有布局模型记录（行列/margin/spacing/帧宽来源）
- [ ] 帧数有定案值与裁定依据（冲突项有逐帧拼图留存）
- [ ] 切割代码引用的帧数与目录一致，且切割后抽查帧无错位

**⑥ 禁忌与易错点**：帧宽取错一位，整张表每一帧都切错位，动画接入后全是残影；用假定帧宽算出的「实测」去推翻作者标注是循环论证——独立证据只有 alpha 界线与逐帧预览；目录里的帧数错一处错全表，这是全卷最不许凭印象填的数字。

**⑦ 参数表**：帧数公式：帧宽 = (图宽 − 左右边距 − (列数−1)×间距) ÷ 列数（单行无边距无间距时退化为图宽 ÷ 帧数）；alpha 阈值对照档：>0 与 ≥128（标定档位，结果不一致以逐帧预览裁定）；裁决顺序：逐帧预览 > alpha 界线 > 计算值 > 作者标注；对齐方：计算 vs 作者标注，共 2 方（异常表升 3 方，见【帧表三方交叉核定】）。
#### 【对标只学结构】

**① 目标与适用场景**：向标杆作品学习时，只学玩法系统、招式结构、操作方式等结构层，角色名、招式名、形象全部原创。适用于立项对标与玩法设计阶段。

**② 前置条件**：已明确红线：资产层（形象、名称、音画素材）不可抄，见【商业原作素材永不使用】。

**③ 操作步骤**：
1. 拆解标杆的结构层 → 动作：记录玩法系统构成、招式判定帧、取消窗口等可量化结构；量化值的测法写明：判定帧/取消窗口从标杆的帧数据或逐帧录像计数测得，笔记中每个数值注明来源（帧数据/录像帧计数/官方资料）→ 判定信号：拆解笔记只含结构参数且数值有来源，不含资产文件。
2. 命名与形象原创化 → 动作：角色名、招式名逐个新造，形象按自有美术规格另行制作；核查法：把成品全部名称与标杆名称逐一比对（含同音、谐音与直译名）→ 判定信号：比对记录留存，成品中无相同或近似到可混淆的名称与形象。
3. 学到可验证程度 → 判定信号：结构参数（如判定帧、取消窗口）有具体数值并进入设计文档，不是「感觉差不多」的换皮模仿。

**④ 失败分支**：
- 现象：某招式名/形象与标杆撞车 → 处置：立即改名/改形象并全表复查同类撞车，不以「致敬」为由保留。

**⑤ 验收清单**：
- [ ] 设计文档含结构参数且可量化验证
- [ ] 名称与形象全表原创核查通过
- [ ] 项目内无标杆资产文件

**⑥ 禁忌与易错点**：结构是方法、不受版权保护；抄资产则直接回到红线。学结构也要学到可验证的程度，只学画面感的「对标」是换皮，不是学习。

**⑦ 参数表**：实测参数：无——本条为方法纪律类，步骤为通用规程。

#### 【生态优势用不上就不换引擎】

**① 目标与适用场景**：「生态型引擎/平台 vs 继续自研」的选型决策，按红线内可用存量算账，不按生态总量算账。适用于一切同类选型。

**② 前置条件**：已列清本项目的红线（版权素材不可用等）；能估算生态内容中合规可用的比例。

**③ 操作步骤**：
1. 先算生态的红线内可用量 → 实测案例：某格斗引擎的强大在二十年内容生态，但生态角色 99% 是版权扒图、自研只能用自制的 10 名角色 → 判定信号：可用量有具体数字（10 名），不是「生态很丰富」的印象。
2. 可用量 ≈ 0 时 → 结论：生态优势计价为零，选型只比引擎本体能力与改造成本 → 判定信号：决策记录中生态项的计价依据是可用量而非总量。
3. 把结论与账目留痕 → 判定信号：日后有人再提换引擎，先看这本账，不重新吵一遍。

**④ 失败分支**：
- 现象：生态中合规可用部分其实可观 → 处置：按可用量重新计价再比，不套「≈0」的旧结论——本条的方法是算账，不是预设答案。

**⑤ 验收清单**：
- [ ] 选型文档含生态可用量的具体估算
- [ ] 决策结论与账目一致且留痕
- [ ] 未用生态总量作为决策依据

**⑥ 禁忌与易错点**：引擎选型最常见的误判是把生态总量当成自己的可用量；与项目红线冲突的生态，账面再大也是零。

**⑦ 参数表**：实测案例：生态角色版权扒图占比约 99%；红线内可用 = 自制 10 名角色。

#### 【无合规人声不用仿冒】

**① 目标与适用场景**：没有合规人声音源时，角色语音直接不做，用打击音效分层代替；绝不用 AI 仿冒真人（原作声优）的声音。适用于角色配音决策。

**② 前置条件**：已盘点手头人声音源的授权状态（自有录制/明确授权/无）。

**③ 操作步骤**：
1. 无合规人声 → 结论：不做角色语音 → 动作：用打击音效分层支撑打击反馈，分层清单固定为：轻命中 / 重击 / 武器材质声（如金属）/ 破空 / 受击反馈，共 5 层（按游戏武器构成增删材质层，增删理由入台账）→ 判定信号：成品中角色无配音、无仿冒语音，5 层逐层有音可查；试听验收 = 无配音打完一段实战，逐层确认反馈不缺位。
2. 有自有录制或明确授权的人声出现时 → 动作：按正常素材流程入库（许可存档、台账登记）后再启用配音。
3. 合成的中性系统播报音 → 判定：不在禁列，但不得指向、模仿任何具体真人 → 判定信号（可操作口径）：播报音不使用任何真人录音样本作克隆/变声源、不以真人姓名或艺名标注、音色为通用合成音，三项全过才算无指向性。

**④ 失败分支**：
- 现象：有人提议用 AI 克隆原作声优补配音 → 处置：拒绝，理由是人格权与侵权观感风险与收益完全不成比例，记录在案。

**⑤ 验收清单**：
- [ ] 成品无仿冒真人语音
- [ ] 打击音效分层能独立支撑反馈（无配音不露馅）
- [ ] 启用的人声素材全部有授权存档

**⑥ 禁忌与易错点**：不要把「音效分层代替」做成敷衍——分层要做到玩家不觉得缺配音；仿冒真人声音是红线，不因「内部使用」豁免（同【商业原作素材永不使用】逻辑）。

**⑦ 参数表**：实测参数：无——本条为红线纪律类，步骤为通用规程。

## 素材台账与接线处置（10 条）

#### 【素材能用尽用·台账面】

**① 目标与适用场景**：保证每个已收素材包都有处置结论，杜绝「收了不用还没人说得清」。适用于每波收割后的接线审计。

**② 前置条件**：素材总目录（CATALOG）为唯一账本（见【CATALOG 逐包登记】）；接线台账已建立。

**③ 操作步骤**：
1. 以总目录为账本逐包过 → 每包给处置状态（五分，不许只分已接/未接）：正式使用 / 部分使用（写明已用文件数÷包内文件总数）/ 回退使用（只在回退层）/ 测试使用（只被测试引用）/ 未使用 → 判定信号：账本内无无结论的包；「正式使用」的证据字段固定 = 代码文件路径＋符号名或资源路径＋运行时加载点，功能开关关闭的按回退/未启用如实降级标注，不许按「有引用」就算正式使用。
2. 发现「收了不用且无理由」的包 → 判定：记为缺陷 → 动作：当轮补处置（接线或写理由），不许带缺陷结项。
3. 未使用理由只许用受控词表：风格不合 / 规格不符 / 题材不对 / 许可限制 / 已被替代 / 待触发条件（须写明具体触发条件，如「待天气系统上线后激活」）；写「以后可能用」的 → 不合格，退回按词表重写。

**④ 失败分支**：
- 现象：台账结论与代码现状对不上（台账说已接、代码无引用）→ 处置：以代码为准更正台账，并按【音效变体池接法】的「真实调用点」标准复查同批条目。

**⑤ 验收清单**：
- [ ] 逐包处置结论覆盖率 100%（五分状态）
- [ ] 正式使用项全部能按证据字段指出代码落点；部分使用项有覆盖比
- [ ] 未使用项理由出自受控词表，无「以后可能用」式空话

**⑥ 禁忌与易错点**：收割花的是真实时间成本，收了不用等于白收；更危险的是没人说得清库里有什么、用了什么，缺口判断全凭印象。

**⑦ 参数表**：处置状态：5 类（正式使用/部分使用/回退使用/测试使用/未使用）；未使用理由词表：6 类；缺陷判据：无理由未使用 = 缺陷。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【素材顶替明说等级】

**① 目标与适用场景**：库里确无成套目标素材时用最接近的成套素材顶替，但必须明说等级，不许冒充达标。适用于画质/规格有明确要求而库内无正解素材时。

**② 前置条件**：已确认库内无成套目标素材（查过总目录与缺口表）；已知正解的自绘规格要素（尺寸、帧数、题材、统一色板）。

**③ 操作步骤**：
1. 选最接近的成套素材顶上 → 判定信号：顶替素材已接入可运行。
2. 在报告与台账中明确标注等级（全手册统一三档命名：近规格顶替＝尺寸/帧数达标、仅风格或来源降级；降规格顶替＝尺寸或帧数低于正解；占位顶替＝仅保功能不保观感），如「顶替、非高清」须同时落到三档之一 → 判定信号：验收人签字时能看到等级标注，且正解的目标值（尺寸、帧数）在清单中写的是具体数值、不是「高清」式形容词。
3. 同时把正解写成可执行清单：尺寸、帧数、题材、统一色板四要素齐全，挂起待拍板 → 判定信号：清单可直接交给美术/生成环节执行，不需要再补规格。

**④ 失败分支**：
- 现象：验收方把顶替当达标通过 → 处置：以台账标注为准当场纠正；顶替解决「有没有」，不解决「好不好」。

**⑤ 验收清单**：
- [ ] 顶替项在报告与台账均有等级标注
- [ ] 正解规格清单四要素齐全并挂起
- [ ] 有画质硬标准的场景（见【人物形象硬标准】）未用顶替过关

**⑥ 禁忌与易错点**：顶替是进度妥协，冒充达标是欺骗——后者会在真机验收时以「画质太差」的形式爆回来，且爆回时已无人记得当初是顶替。

**⑦ 参数表**：自绘规格清单四要素：尺寸 / 帧数 / 题材 / 统一色板。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【CATALOG 逐包登记】

**① 目标与适用场景**：素材总目录（CATALOG）作为全库唯一账本，支撑接线核对与许可审计。适用于素材量达到无法靠文件夹考古的规模（万级文件）。

**② 前置条件**：素材已落盘并通过文件头校验（见【文件头校验法】）；许可证据已存档（见【许可证据存档】）。

**③ 操作步骤**：
1. 每包按固定 schema 登记：来源（站点＋来源 URL）、许可、落盘路径、文件数、字节数、校验结果、预定用途、下载日期、包版本（如有）、许可证据指针（evidence/ 位置）、内容哈希（包内文件清单哈希）、登记更新时间 → 判定信号：条目字段无空缺。
2. 校验结果如实写：写明校验方法（全量二级终验/抽查）——抽查的必须写抽样口径（抽几个、抽哪类、随机还是风险导向），全量验过的写「全量」→ 判定信号：后人能分辨哪包全验、哪包抽查、哪包还没验。
3. 文件数口径全库统一：解压后普通文件数，不含目录、原压缩包、evidence/、隐藏文件；符号链接跟随目标计一次 → 判定信号：任意两包的文件数可按同一口径复算。
4. 接线核对与许可审计只认此账本；预定用途与实际用途不一致时回写账本并保留变更记录（改前用途、改后用途、日期）→ 判定信号：其他文档与账本口径冲突时以账本为准并更正他处。

**④ 失败分支**：
- 现象：账本文件数与磁盘实际数对不上 → 处置：以磁盘为准重新清点该包并更正账本，差异原因（漏登记/误删）写进条目备注。

**⑤ 验收清单**：
- [ ] 每包 schema 字段登记齐全
- [ ] 账本文件数与磁盘按统一口径全量清点一致（不是抽查一致）
- [ ] 无第二套口径的素材清单在流通

**⑥ 禁忌与易错点**：账本记结论、evidence/ 存证据原文，两者配套（见【许可证据存档】），只记结论不存证据的账本经不起审计。

**⑦ 参数表**：登记字段：来源（站点＋URL）/ 许可 / 路径 / 文件数 / 字节数 / 校验结果（含方法与抽样口径）/ 用途 / 下载日期 / 版本 / 证据指针 / 内容哈希 / 更新时间，共 12 项；文件计数口径：解压后普通文件、不含目录/原包/evidence/隐藏文件、符号链接计一次。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【下载失败入册】

**① 目标与适用场景**：下载失败与资源不存在同样入册，让失败变成可复用情报，避免下一轮原样重试。适用于所有收割失败项。

**② 前置条件**：失败项已有定性结论（不存在/通道问题，见【slug 不存在≠下载失败】）。

**③ 操作步骤**：
1. 登记失败项：原需求是什么、失败定性、最终用什么替代补上 → 判定信号：条目三要素齐全。实测形态：两个查无此包的角色包 slug 连同替代方案一起入册。
2. 需求最终无缺口也要有记录 → 判定信号：入册不以「是否造成缺口」为条件。
3. 因站点卡住造成的失败 → 动作：同时进卡住清单（见【卡住清单不硬闯】），两处口径一致，不重复记账。

**④ 失败分支**：
- 现象：替代方案后来被换掉 → 处置：在原条目下追加更新，不删旧记录，保持情报链完整。

**⑤ 验收清单**：
- [ ] 本轮全部失败项已入册
- [ ] 每条有定性与替代结论
- [ ] 与卡住清单交叉项口径一致

**⑥ 禁忌与易错点**：不入册的失败会在下一轮被原样重试一遍；入册的失败是情报，不入册的失败是学费白交。

**⑦ 参数表**：条目三要素：原需求 / 失败定性 / 替代方案。实测参数：无专用数值——本条为流程类，步骤为通用规程。

#### 【接线优先于新开发】

**① 目标与适用场景**：素材利用的排期排序：第一轮只清「加引用、改路径、补映射」就能落地的接线项；需要渲染管线或状态机改造的项单独排期。适用于收割后第一轮利用工作。

**② 前置条件**：已收素材包处置结论齐全（见【素材能用尽用·台账面】）；能区分「纯接线」与「需改造」两类工作量。

**③ 操作步骤**：
1. 逐项分类（按决策树判，不许凭感觉）：只改引用/路径/映射、不动渲染管线与状态机 → 纯接线，归第一轮；凡要改渲染管线、状态机、加载机制任一 → 需改造，写明卡点（缺什么改造）单独排期 → 判定信号：两类清单分明，每项分类能指出命中的是哪条判据，需改造项每项有卡点说明。
2. 第一轮清完纯接线项 → 判定信号：第一轮交付不依赖任何未完成的改造。
3. 排期项进入后续轮次时以卡点说明为开工依据 → 判定信号：开工时不需要重新调研卡点。

**④ 失败分支**：
- 现象：某「纯接线」项动手后发现需要改造 → 处置：立即转入排期清单并写明新发现的卡点，不在第一轮里硬啃拖住整轮交付。

**⑤ 验收清单**：
- [ ] 第一轮清单全部为纯接线项且已清完
- [ ] 排期项每项有具体卡点，无「后续处理」式空话
- [ ] 两类未混排

**⑥ 禁忌与易错点**：混排的典型结果是易事被难事堵住、整轮零交付；接线项单价低、见效快，先清完能立刻抬升成品完成度。

**⑦ 参数表**：分类：纯接线 / 需改造，共 2 类。实测参数：无——本条为排期纪律类，步骤为通用规程。

#### 【音效变体池接法】

**① 目标与适用场景**：同类高频音效（点击、落子、命中）不单接一条，建成变体池随机抽播，用存量素材换听感。适用于高频重复音效；剧情性、唯一性声音不入池。

**② 前置条件**：同类音效文件成组存在；每个事件位已有明确触发点（无事件位的不接，见【无事件语义不接】）。

**③ 操作步骤**：
1. 盘点同类文件全量 → 实测案例：某赌场音效包 54 个文件 → 判定信号：文件清单与磁盘一致。
2. 逐个建映射键 → 目标：54/54 全映射，无一遗漏 → 判定信号：映射表键数 = 文件数。
3. 逐键核对真实调用点 → 动作：在代码中确认每个新键都有实际触发它的事件代码 → 判定信号：无「接了但没人调」的死键（逐键 grep 调用点核对）。
4. 运行时随机抽播 → 判定信号：同一事件连续触发时声音有可辨变化。

**④ 失败分支**：
- 现象：某文件无合适事件位 → 处置：不硬塞，按【同质素材不堆量】或【无事件语义不接】留痕，不为凑满映射数造假触发。

**⑤ 验收清单**：
- [ ] 映射数 = 文件数（全映射）
- [ ] 每键有真实调用点（代码可查）
- [ ] 连续触发同事件可听出变体差异（或波形抽查不一致）

**⑥ 禁忌与易错点**：同一声效反复播放是廉价感的头号来源；但「台账全映射、代码无人调」是假接线，比不接更坏——全映射必须以真实调用点为验收口径。

**⑦ 参数表**：实测案例：音效包 54 个文件 → 54/54 全映射；验收线：死键 = 0。

#### 【同质素材不堆量】

**① 目标与适用场景**：同家族同质变体无新可辨识功能点时，停止接入并留痕，防止台账被灌水成数字政绩。适用于成组变体素材的接入决策。

**② 前置条件**：该家族已有若干条接入；能说清「新功能点」的判据（覆盖新事件或新情绪）。

**③ 操作步骤**：
1. 对候选变体逐条比已接项：有无新可辨识功能点 → 判定法：盲测——两名测试者不知编号地听/看候选与已接项，两人都说不出功能差异（覆盖新事件或新情绪才算差异）才算「无可辨识差异」；一人能指出差异即不停接 → 实测案例：某界面音效包已接 5 条、其余约 95 条点击/铃声变体与已接的无可辨识差异 → 结论：停接 → 判定信号：停接结论连同盲测记录写入台账。
2. 有新功能点的（如胜利与失败两种铃声分属不同情绪）→ 正常接入，不受本条限制。

**④ 失败分支**：
- 现象：停接后发现某变体其实覆盖新事件 → 处置：在台账追加复核记录后单独接入，不推翻整组停接结论。

**⑤ 验收清单**：
- [ ] 停接结论有台账记录与判据
- [ ] 已接条目每条能指出其功能点
- [ ] 台账条目数未被无功能变体灌水

**⑥ 禁忌与易错点**：判据是「无新可辨识功能点」，不是「数量够了」；拿数量当判据会误杀真正的新功能变体。

**⑦ 参数表**：实测案例：界面音效包已接 5 条 / 停接约 95 条同质变体。

#### 【无事件语义不接】

**① 目标与适用场景**：素材没有对应的事件位就不接，逐项核对、逐项留痕。适用于音效与一切事件驱动型素材的接入决策。

**② 前置条件**：已盘点游戏内实际存在的事件/场景清单（地图结构、系统清单）。

**③ 操作步骤**：
1. 逐项核对事件是否存在 → 实测三例：门声对应地图门，但地图门不可开合 → 不接；水声对应水面，地图无水面 → 不接；雷声对应天气系统，无天气系统 → 不接 → 判定信号：每项结论有「无事件位：××不存在」的具体依据。
2. 不接项逐项留痕 → 判定信号：台账中不接项与接入项同样可审计。

**④ 失败分支**：
- 现象：对应系统后来上线（如天气系统落地）→ 处置：留痕项重新激活评估，按正常流程接入——留痕就是为复活备的索引。

**⑤ 验收清单**：
- [ ] 每个候选素材有事件位核对结论
- [ ] 不接项全部留痕且依据具体
- [ ] 无靠假触发凑播放的接入

**⑥ 禁忌与易错点**：硬塞无事件素材只能靠假触发，效果违和；与【环境音按场景开】互补——先有场景事件位，再谈接入，顺序不可反。

**⑦ 参数表**：实测不接三例：门声（门不可开合）/ 水声（无水面）/ 雷声（无天气系统）。其余参数：无——本条以事件核对为主，步骤为通用规程。

#### 【被否决素材降级回退】

**① 目标与适用场景**：被用户否决的素材不删除，降级为回退层：玩家正常不可见，但回退链与测试覆盖保留。适用于素材本身合规可用、只是观感被否的情形；违规（许可问题）素材必须真删，不适用本条。

**② 前置条件**：回退链机制存在（见【四级回退链】）；被否素材的加载路径可配置优先级。

**③ 操作步骤**：
1. 把被否素材的优先级降到回退层 → 实测形态：被否决的像素帧改为「新图集未就绪时的回退」→ 判定信号：正常加载路径下玩家看不到该素材（截图核查）。
2. 保留其测试覆盖 → 判定信号：回退链的拦截对照测试仍包含该层且通过（见【四级回退链】的对照遍）。
3. 在台账标注降级状态与原因 → 判定信号：后人不会误以为该素材仍是正式素材、也不会误删。

**④ 失败分支**：
- 现象：回退层素材被误删导致回退链断裂 → 处置：从素材库恢复该层并补拦截测试；删除动作必须过台账核对。

**⑤ 验收清单**：
- [ ] 正常路径下被否素材不可见（截图证）
- [ ] 回退触发时该素材可正常顶上（拦截测试证）
- [ ] 台账状态标注为「降级回退」

**⑥ 禁忌与易错点**：直接删除的代价是加载失败时无图可退；保留的成本只是少量体积——这笔账要算给提议删除的人听。

**⑦ 参数表**：实测参数：无——本条为处置流程类，步骤为通用规程。

#### 【素材库总量管理】

**① 目标与适用场景**：素材库按波次登记总量并设上限，总目录、接线台账、缺口表三本账持续对齐。适用于长期多波收割的素材库治理。

**② 前置条件**：三本账已建立（总目录见【CATALOG 逐包登记】、缺口表见【缺口如实登记】）；存储上限已按项目条件设定。

**③ 操作步骤**：
1. 每波收割前核对当前总量与上限 → 上限的定法：按可用磁盘、备份份数与部署包体积推导并写明推导过程（本项目定为约 2GB，是项目口径、不是通用常数；换环境必须重推导，不许照搬 2GB）→ 实测口径：总量上限约 2GB，单波约 492MB 量级 → 判定信号：本波预算在上限内。
2. 每波收割后逐波登记增量 → 判定信号：总量 = 上波总量 + 本波增量，账实一致。
3. 三本账同步更新：新收的进总目录、接了的进接线台账、仍缺的留在缺口表；固定对账节奏：每波收割后做一次三账对齐并产出差异表（条目/三账各自状态/差异处置），差异未销账不许开下一波 → 判定信号：对账差异表在案，抽查任一素材三本账状态互不矛盾。

**④ 失败分支**：
- 现象：三本账脱节（缺口表里有已收未接的素材重复申报缺口）→ 处置：以总目录为账本做一轮三账对齐，差异逐项销账后再继续收割。

**⑤ 验收清单**：
- [ ] 总量在上限内且逐波登记完整
- [ ] 三本账抽查无矛盾
- [ ] 无超上限囤积

**⑥ 禁忌与易错点**：无上限的收割会把库撑成无法审计的垃圾场；「全量」指目标范围收全，不是无限囤积（见【题材不合不凑数】）。

**⑦ 参数表**：总量上限：约 2GB（本项目口径，按存储条件可调）；单波量级：约 492MB；账本数：3（总目录/接线台账/缺口表）。

#### 【版权缺口自制补齐】

**① 目标与适用场景**：合法素材的缺口用自制/自生成同规格补齐，关闭缺口。适用于缺口表中有明确规格条目的情形。

**② 前置条件**：缺口规格明确（见【缺口如实登记】）；自制素材的许可归属清楚（自制成品与源模型同许可）。

**③ 操作步骤**：
1. 按缺口规格制作 → 实测实例法：某道具只有 OBJ 模型源、无成品图 → 用无头渲染产出 768×768 透明底 PNG → 判定信号：成品尺寸、底色（透明）与规格逐项一致。
2. 与同批素材混用复核 → 动作：把自制成品与同场景既有素材同框截图，由第二人按三项逐项复核——构图比例、光照方向、色调——三项全过才算可混用（复核人签字，不许制作者自审自过）→ 判定信号：同框截图与三项复核记录在案；达不到同规格的自制等于新缺口，如实登记回去。
3. 入台账标注「自制」并关闭缺口条目 → 判定信号：缺口表状态更新、三本账同步。

**④ 失败分支**：
- 现象：自制成品规格达标但风格不合 → 处置：不关闭缺口，标注「已试自制、风格未过」，调整制作参数重做或等合法源。

**⑤ 验收清单**：
- [ ] 成品规格与缺口规格逐项一致
- [ ] 同框混用截图复核通过
- [ ] 台账标注自制、缺口正式关闭

**⑥ 禁忌与易错点**：缺口是工程问题，自制是工程解法；因缺口去扒版权物是把工程问题换成法律问题，与【商业原作素材永不使用】直接冲突。

**⑦ 参数表**：实测实例：OBJ 源 → 无头渲染 768×768 透明底 PNG；许可：与源模型同许可。

#### 【字体子集化】

**① 目标与适用场景**：整套中文字体过大（实测 8.0MB），按全站实际用字子集化并转 woff2 上线。适用于 Web 项目的中文字体瘦身。

**② 前置条件**：有 fontTools（含 subset 工具）；能汇总全站全部页面的文本字符集。

**③ 操作步骤**：
1. 汇总字符集：抓取全站全部页面文本与脚本内固定字符串（含动态拼接的固定词表）取并集（不是单页用字）；预留生僻字余量的来源写明：通用常用汉字表＋项目专名用字（地名、人名类固定词）→ 判定信号：字符集覆盖全部页面文本，并含标点、数字与预留字表。
2. 执行子集化：fontTools.subset 按字符集切子集并转 woff2 → 实测结果：8.0MB → 193KB → 判定信号：产出体积量级与实测一致（百 KB 级）。
3. 上线后按【cmap 与异体字校验】验 cmap → 判定信号：关键文案全字在子集内。

**④ 失败分支**：
- 现象：某页出现缺字方框 → 原因：字符集漏收该页文本或文案后来新增 → 处置：把缺字页文本并入字符集重切子集，并把「文案变更同步更新字符集」写进流程。

**⑤ 验收清单**：
- [ ] 子集体积为百 KB 量级（对照实测 193KB）
- [ ] 全站各页抽查无缺字
- [ ] cmap 校验通过（见下条）

**⑥ 禁忌与易错点**：按单页切子集会在页面间互相缺字；并集是兼顾体积与安全的唯一口径。动态文本不要用子集字体，见【字体只上标题】。

**⑦ 参数表**：原字体 8.0MB → 子集 woff2 193KB（实测）；字符集口径：全站全文并集。

#### 【字体只上标题】

**① 目标与适用场景**：子集字体的使用范围控制：只用于固定文案，动态文本保持系统字体。适用于已做字体子集化的项目（见【字体子集化】）。

**② 前置条件**：能区分页面上的固定文案与动态文本（玩家昵称、结算行等用户生成或动态拼接内容）。

**③ 操作步骤**：
1. 固定文案（主标、标题、按钮等写死文本）→ 用子集字体 → 判定信号：这些文案的字符集可枚举、可校验。
2. 动态文本 → 一律系统字体 → 判定信号：样式表中动态文本元素未挂子集字体。
3. 例外判定：动态文本若来自可枚举的固定词表（如固定结算用语）→ 可把词表并入子集字符集后使用子集字体 → 判定信号：词表已并入且 cmap 校验覆盖。

**④ 失败分支**：
- 现象：动态文本出现同词两体或缺字方框 → 原因：动态元素误挂子集字体 → 处置：摘除该元素的子集字体，回系统字体，并全页复查同类元素。

**⑤ 验收清单**：
- [ ] 固定文案用子集字体、动态文本用系统字体，逐元素核对无误挂
- [ ] 用生僻字昵称做一遍显示测试，无方框、无混排

**⑥ 禁忌与易错点**：动态文本随时可能出现子集外生僻字，混排会同词两体；固定文案才可控，不要图省事全局挂子集字体。

**⑦ 参数表**：实测参数：无——本条为使用范围纪律类，步骤为通用规程。

#### 【cmap 与异体字校验】

**① 目标与适用场景**：字体子集化后的验收：验 cmap 含关键文案全字，并专门核对异体码点，不凭截图肉眼下结论。适用于所有子集化/裁剪字体的验收。

**② 前置条件**：有可读字体 cmap 的工具（fontTools）；关键文案清单已备（随文案变更同步更新）。

**③ 操作步骤**：
1. 读子集字体 cmap → 逐字核对关键文案的全部字都在 cmap 内 → 判定信号：缺字数 = 0。
2. 专门核对异体码点 → 实测案例：「锄」实为 U+9504，须确认该码点在子集内 → 判定信号：清单中每个异体字按码点（不是按字形）核对通过。
3. 截图上笔画疑似粘连时 → 先查码点再定性：码点在 = 渲染问题，码点不在 = 缺字 → 判定信号：定性结论有码点证据。

**④ 失败分支**：
- 现象：关键码点不在子集 → 处置：把该码点补入字符集重切子集（见【字体子集化】），并把该字加入关键文案清单防再漏。

**⑤ 验收清单**：
- [ ] 关键文案全字 cmap 核对缺字 = 0
- [ ] 异体字逐个按码点核对通过
- [ ] 关键文案清单与当前文案版本一致

**⑥ 禁忌与易错点**：缺字与渲染粘连在截图上长得像，误判会引向错误修复（重切子集或白换字体）；码点级校验是唯一能定性的办法，不许用「看着差不多」代替。

**⑦ 参数表**：实测异体码点：「锄」= U+9504；验收线：关键文案缺字 = 0。

#### 【特效图压缩策略】

**① 目标与适用场景**：特效图 PNG 转 WebP 时按内容定策略：有损与无损逐图判定，不一刀切。适用于光晕、烟尘等带 alpha 边缘的特效图批量压缩。

**② 前置条件**：有 PNG→WebP 转换与 PSNR 计算工具；已备原图备份（压缩不可逆，验收不过要能回退）。

**③ 操作步骤**：
1. 每张先试有损 q90 转 WebP → 判定信号：产出有损版。
2. 计算有损版与原图的 PSNR，口径固定：先对全部像素逐通道（含 alpha）算合并 MSE，再由 PSNR = 10·log10(255²/MSE) 得单一数值（不许逐通道各算 PSNR 再平均——两种算法结果不同，混用会让阈值失真）；记录所用编码器与版本（q90 指该编码器的质量参数 90，不同编码器的 q90 不等价）→ 判定：≥38dB 用有损版；<38dB 改无损转换 → 判定信号：每张图有按统一公式算出的 PSNR 数值与策略结论记录。
3. 汇总验收 → 实测总量：7.14MB → 3.71MB，零画质事故 → 判定信号：总量下降且抽查图 alpha 边缘无糊化。

**④ 失败分支**：
- 现象：PSNR 达标但目检 alpha 边缘仍糊 → 处置：该图改无损并下调同类图的判定信任，必要时对同类图全改无损——指标与目检冲突时以目检为准并记录。

**⑤ 验收清单**：
- [ ] 每张图有 PSNR 数值与有损/无损结论
- [ ] alpha 边缘抽查目检无糊化
- [ ] 总量有压缩前后对照数字

**⑥ 禁忌与易错点**：只算 RGB 通道 PSNR 会放过「RGB 达标、边缘已糊」的假达标——alpha 边缘是有损压缩最先烂的地方，必须全通道计算。

**⑦ 参数表**：有损试探质量：q90；PSNR 阈值：≥38dB（RGBA 全通道，本项目特效图口径）；实测总量：7.14MB → 3.71MB。

#### 【GLB 几何瘦身】

**① 目标与适用场景**：角色 GLB 体积过大（实测 59.87MB）时的组合瘦身，目标量级 −84%（实测至 9.57MB）。适用于 Web 加载的 3D 角色模型；动画片段不在此列（见【动画 GLB 不压缩】）。

**② 前置条件**：有 GLB 处理工具链（贴图重编码、几何去重、属性改写）；原文件已备份；骨骼数已确认 ≤256（JOINTS 降 u8 的前提）。

**③ 操作步骤**：
1. 贴图按语义分流重编码：不带 alpha 的 baseColor 转 JPEG q88；带 alpha 的 baseColor 改走 WebP/PNG（JPEG 无 alpha，一转即丢透明）；normal 转 WebP（记录有损/无损与质量值）；金属度/粗糙度等打包通道图不走彩色有损重编码（通道错位比体积更贵）→ 判定信号：每张贴图有分流结论，体积下降且目检无可见劣化。
2. 几何精确去重索引化 → 相等键先定死：顶点的全部属性（position / normal / UV / JOINTS / WEIGHTS / tangent / 顶点色）逐项全等才许合并，任一属性不同即不同顶点 → 实测：唯一顶点 609,366 → 125,235 → 判定信号：顶点计数与实测量级一致。
3. 属性降宽：JOINTS u16→u8；WEIGHTS/UV 归一化指转 normalized 整数存储，改后逐顶点校验 WEIGHTS 四分量之和 ≈ 1（容差按存储位宽取 1 个量化步长量级，超差顶点数须 = 0）→ 前置判定：骨骼数 ≤256 才许降 u8。
4. 压后逐角色渲染复核 → 动作：每个角色渲染一遍查接缝、孔洞、变形 → 判定信号：无渲染异常（重点防【删属性通道的 accessor 坑】类问题）。
5. 等价性验收（硬验收）：同机位同姿势、同背景同光照压前/压后对比图＋像素差量化；报告必须同时给平均绝对差与最大差（或 99 分位差）——平均值会掩盖小面积严重错位；通过阈值由本项目在首个角色上标定后全批统一（实测 0.07–1.26/255 是逐角色的历史样本范围，不是统一阈值，不许直接拿来当线）→ 判定信号：对比图与双指标（平均＋最大/分位）记录留存。

**④ 失败分支**：
- 现象：压后出现颈部接缝孔洞 → 原因：删属性通道未重映射 accessor（见下条）→ 处置：回退该文件，按「重建时不写该通道」的方式重做。
- 现象：骨骼数 >256 → 处置：JOINTS 保持 u16，只做其余两步，不许强降 u8。

**⑤ 验收清单**：
- [ ] 体积达到目标量级（对照实测 −84%）
- [ ] 逐角色渲染复核无异常
- [ ] A/B 像素差量化在可接受量级且记录留存
- [ ] 骨骼数 ≤256 的确认记录在案（或已注明保持 u16）

**⑥ 禁忌与易错点**：瘦身三步必须全做完再渲染复核，不要压一步看一步凭感觉停；删除任何属性通道必须走下条的纪律。

**⑦ 参数表**：总体积 59.87MB → 9.57MB（−84%）；唯一顶点 609,366 → 125,235；baseColor：JPEG q88；normal：WebP；JOINTS：u16→u8（前提骨骼 ≤256）；A/B 像素差参考量级：平均绝对差 0.07–1.26/255（实测）。

#### 【删属性通道的 accessor 坑】

**① 目标与适用场景**：删除 GLB 未使用属性通道（如 TEXCOORD_1）时的防污染规程。适用于一切手工修改二进制容器（GLB 及同类格式）的操作。

**② 前置条件**：明确要删的通道确实未被任何材质/着色器使用；有可整体重建 GLB 的工具链。

**③ 操作步骤**：
1. 删通道只许走一条路：在重建 GLB 时直接不写该通道，不留悬空引用 → 前置核查先做：逐处确认该通道未被引用——material 的各 texture index、KHR 扩展、自定义 shader、运行时动态材质四处都要查（只看 material 基础字段会漏扩展与动态材质）→ 判定信号：重建后跑引用完整性自动检查：遍历全部 mesh attribute、material 纹理索引、skin、animation sampler 的 accessor 引用，悬空引用数 = 0（检查输出留存）；重建前后 JSON 摘要 diff 只允许目标通道相关差异，另有差异即回退。
2. 严禁用「只删数据、不重映射 accessor 索引」的改法 → 原理：GLB 的 accessor 是全局编号，删一段不重排，后面所有引用整体错位，且不报错、只出怪图。
3. 改后逐角色渲染复核 → 实测症状样本：索引错位表现为颈部接缝孔洞 → 判定信号：无接缝、无孔洞、无错位贴图。

**④ 失败分支**：
- 现象：改后渲染出现局部孔洞/接缝但加载不报错 → 原因：几乎必是 accessor 索引错位 → 处置：回退文件，用二分对照定位（纯贴图版正常、纯去重版正常、逐项排除锁定删通道一步），按第 1 步重做。

**⑤ 验收清单**：
- [ ] 重建后无悬空 accessor 引用（自动检查输出留存，悬空数 = 0）
- [ ] 逐角色渲染复核无孔洞/接缝，且动画、蒙皮、材质回归无异常
- [ ] 修改方式为整体重建，非手工删段

**⑥ 禁忌与易错点**：这类坑的症状（怪图）与病因（索引错位）相距极远，且不报错——没有本条纪律时能耗掉数天；要么整体重建，要么同步重排索引，不许只删不理。

**⑦ 参数表**：实测症状：颈部接缝孔洞；典型未用通道：TEXCOORD_1。其余参数：无——本条以结构检查为主，步骤为通用规程。

#### 【动画 GLB 不压缩】

**① 目标与适用场景**：动画片段 GLB 不做轨道量化压缩，与角色本体瘦身区别对待。适用于角色动画资产的管理决策。

**② 前置条件**：已知单段动画体积量级（实测单段仅 100–240KB）。

**③ 操作步骤**：
1. 角色本体按【GLB 几何瘦身】处理，动画片段保持原样入库 → 判定信号：动画文件未经过量化工具。
2. 账目上算清这笔账：量化收益 = 单段百 KB 级；风险 = 骨骼轨道量化误差污染全部共用该动画的角色动作 → 结论：不压 → 判定信号：决策与账目记录在案。

**④ 失败分支**：
- 现象：动画总量涨到 MB 级且段数多 → 处置：重新评估分级方案（高频动画不压、低频动画轻压），不直接全压；评估结论留痕。

**⑤ 验收清单**：
- [ ] 动画片段文件均为未量化原件
- [ ] 不压的决策账目（收益 vs 风险）在册

**⑥ 禁忌与易错点**：不要为了「全库统一压缩口径」把动画一起压了——省几百 KB、赌所有角色的动作精度，这笔账不划算。

**⑦ 参数表**：单段动画体积：100–240KB（实测）；判定：收益小、污染面 = 全部共用角色。

#### 【过采样按显示尺寸回收】

**① 目标与适用场景**：素材尺寸按实际最大显示尺寸定，过采样的降档回收。适用于图片类素材的规格治理（牌面、桌布、主视觉等）。

**② 前置条件**：能测得素材在界面中的实际最大显示尺寸；最大显示尺寸在目标设备的 CSS 尺寸断点矩阵上逐断点测（手机/平板/桌面各取代表断点）；降档要按最大显示尺寸 × DPR 上限留余量，DPR 上限 = 2（与【DPR 渲染管线】口径一致），不是按当前截图尺寸一刀切。

**③ 操作步骤**：
1. 逐类素材量实际显示尺寸 → 实测案例：牌面原图 486×757，实际显示最大约 110px 宽 → 判定：严重过采样。
2. 按显示尺寸降档：牌面降到 300 宽 + 256 色量化；桌布 2048² → 1024²、q82 → 判定信号：降档后在最大显示尺寸下目检无可见劣化。
3. 量化后截图复核（见【量化才是关键步】）→ 判定信号：人像与花色仍锐利。
4. 汇总收益 → 实测：素材包 −54%、大厅首屏 −72% → 判定信号：收益用实际传输字节/首屏实测量，不用静态文件大小推算。

**④ 失败分支**：
- 现象：降档后高清屏上发糊 → 原因：余量留不足 → 处置：按 DPR 上限重新估尺寸回档一档，并把该类素材的余量口径写进规格表。

**⑤ 验收清单**：
- [ ] 每类素材有「原尺寸 / 显示尺寸 / 降档后尺寸」三联记录
- [ ] 最大显示尺寸下目检无劣化
- [ ] 收益以实测字节计

**⑥ 禁忌与易错点**：超出显示尺寸的像素纯属带宽与解码浪费，玩家看不见、设备全买单；但降过头会在高清屏露馅——余量按 DPR 上限留，不按当前设备留。

**⑦ 参数表**：牌面 486×757 → 300 宽 + 256 色量化（显示最大约 110px）；桌布 2048² → 1024² q82；实测收益：素材包 −54%、大厅首屏 −72%。

#### 【量化才是关键步】

**① 目标与适用场景**：扁平插画类 PNG（插画、图标、牌面等有限色素材）的体积治理：关键在 256 色量化，不在换格式。渐变丰富的照片类素材不适用（量化会出色带）。

**② 前置条件**：素材确属有限色类型；有量化工具（PIL 量化路径）；备好原图以便复核回退。

**③ 操作步骤**：
1. 先试 PIL 直存 RGBA → 预期现象：体积反而变大或基本不变 → 判定信号：不要在换容器上继续耗，直接进量化。
2. 执行 256 色量化（工具与参数定版记录：量化工具、调色板生成方式、抖动开/关逐项写进加工记录——抖动开关会改变颗粒感，不记录就不可复现）→ 判定信号：体积真正降下来（与【过采样按显示尺寸回收】的降档叠加执行）。
3. 量化后截图复核 → 动作：逐张看人像与花色是否仍锐利 → 判定：糊了就回退色数或改分区处理，不许带糊上线。

**④ 失败分支**：
- 现象：量化后出现色带 → 原因：素材实为渐变丰富型、被误判为有限色 → 处置：该素材退出量化路径，改走格式压缩（如 WebP，见【特效图压缩策略】的判定法）。

**⑤ 验收清单**：
- [ ] 量化前后体积有对照数字
- [ ] 逐张截图复核锐利度通过
- [ ] 照片类素材未被误量化

**⑥ 禁忌与易错点**：插画色数本就有限，量化几乎无损地砍掉冗余色彩信息；直存只是换容器，不解决信息量——把时间花在换格式上是走错关键步。

**⑦ 参数表**：量化色数：256 色；验收方式：截图复核（人像/花色锐利）。实测参数：无专用数值——本条以流程与复核为主，步骤为通用规程。

#### 【BGM 解析期零创建】

**① 目标与适用场景**：BGM 不在脚本解析期预加载，避免与首屏资源抢带宽。适用于 Web 游戏的音频加载设计。

**② 前置条件**：已盘点 BGM 总量（实测 4 首约 3.18MB）；理解浏览器自动播放策略（无用户手势不能播，解析期预加载纯属白抢带宽）。

**③ 操作步骤**：
1. 解析期零创建：脚本解析阶段不创建 Audio 元素、不 preload 任何 BGM → 判定信号：首屏网络请求列表中无 BGM 文件。
2. 首次用户手势后按当前界面创建：标题/选人界面建标题/选人曲 → 判定信号：只拉当前界面用得上的曲目。
3. 首次进对战才建对战曲目单 → 判定信号：未进对战的会话从未请求对战 BGM。

**④ 失败分支**：
- 现象：首击触发的时机与体积产生新问题（点卡进游戏时后台拉大文件）→ 处置：转【BGM 首击触发的代价】的方案流程，不在本条内擅自改触发点。

**⑤ 验收清单**：
- [ ] 首屏请求列表无 BGM
- [ ] 各界面只创建本界面曲目
- [ ] 未访问的界面曲目从未被请求

**⑥ 禁忌与易错点**：预加载的「提前准备好」是错觉——自动播放策略决定了手势前播不了，预加载只是提前浪费；按需创建要按界面粒度，不要手势后一次性全拉。

**⑦ 参数表**：实测 BGM 总量：4 首约 3.18MB；创建时机：首次手势后按界面 / 首次进对战。

#### 【环境音按场景开】

**① 目标与适用场景**：环境循环音只在对应场景开启、离开自动停。适用于有明确场景对应的循环环境音。

**② 前置条件**：场景与环境音的对应关系已盘点（判据与【无事件语义不接】同源：先有场景事件位，再谈接入）。

**③ 操作步骤**：
1. 进场景时按对应关系开启 → 实测案例：瀑布舞台开流水声 → 判定信号：只有当前场景对应的环境音在播。
2. 音量设为从属级：主音量 ×0.35 → 判定信号：环境音不抢打击音效与 BGM 的注意力（试听核对）。
3. 离开对战/场景自动停 → 判定信号：退出后无环境音残留播放。
4. 无对应场景的循环音（雨声、机械声）→ 不接，留痕（见【无事件语义不接】）。

**④ 失败分支**：
- 现象：切场景后旧环境音不停 → 原因：停止逻辑未挂在场景退出点 → 处置：把停止动作绑到统一的场景退出路径，不逐场景补。

**⑤ 验收清单**：
- [ ] 每场景只播对应环境音
- [ ] 音量比 = 主音量 ×0.35 已落实
- [ ] 离开场景自动停且无残留

**⑥ 禁忌与易错点**：环境音的价值是场景沉浸，错场景播放是噪音；音量从属关系是硬参数，不要凭手感随手调高。

**⑦ 参数表**：环境音音量：主音量 ×0.35（实测口径）；启停：进场景开 / 离场景停。

#### 【音效语义靠数值证据】

**① 目标与适用场景**：无名/乱名采样接不接，用时长与包络实测判定，不靠听感猜。适用于无语义命名采样的大批量筛选；命名明确的音效可直接按名接入。

**② 前置条件**：有音频分析手段（时长、包络/dB 曲线可测）；判定数值要写入台账供他人复测。

**③ 操作步骤**：
1. 逐个测候选采样的特征（口径固定：总时长、峰值电平（dBFS，相对满刻度）、起音时间（峰值前上升段时间）、包络衰减形态）→ 判定信号：每个候选有按同一口径测的数值记录；分类阈值须先用已知样本标定并登记，未标定的数值只作个案判据、不许推广成全库阈值。
2. 按声型判据判定 → 实测样本：air_03 实测 0.28s、快起快落（−16.8dB → −24.4dB），符合挥砍声型 → 接；air_01 长达 2.64s、气流嗡鸣型 → 不接 → 判定信号：判定结论与数值一并入台账。
3. 接入后在真实事件上试听复核一次 → 判定信号：声型与事件语义不冲突（数值判定为主、试听为兜底）。

**④ 失败分支**：
- 现象：数值符合但试听明显不对 → 处置：以事件语义为准撤下，并在台账标注该样本的数值特征为何误导，丰富后续判据。

**⑤ 验收清单**：
- [ ] 每个接入/拒接采样有数值判定记录
- [ ] 台账数值可被他人复测复现
- [ ] 无凭听感印象接入的无名采样

**⑥ 禁忌与易错点**：听感判断因人而异、不可复核；时长与包络是可写进台账的硬证据——本条的核心是把「我觉得像」换成「数据是这样」。

**⑦ 参数表**：实测样本：air_03 = 0.28s、包络 −16.8dB → −24.4dB（接）；air_01 = 2.64s 气流嗡鸣型（不接）。

#### 【构建脚本留痕】

**① 目标与适用场景**：新素材的拷贝/加工步骤必须写进构建脚本，保证任何人重跑构建得到同一产物。适用于一切经构建产出的资源（图集、字体、打包文件）。

**② 前置条件**：项目有构建脚本（如 build_atlas.py）；新素材已通过验货与许可闸门。

**③ 操作步骤**：
1. 接入新素材时同步改构建脚本 → 实测形态：build_atlas.py 增加对应 copy 行 → 判定信号：脚本 diff 中有该素材的处理行。
2. 重跑构建验证 → 动作：清空产物后完整重跑一次 → 判定信号：新素材出现在产物中，与手工接入时一致。
3. 只手工拷过、脚本里没有的 → 判定：不算接好，当轮补进脚本再验收。

**④ 失败分支**：
- 现象：重跑构建后某素材丢失 → 原因：该素材从未进脚本 → 处置：按第 1 步补脚本行，并全表复查还有哪些素材只存在于手工产物中。

**⑤ 验收清单**：
- [ ] 每项已接素材在构建脚本中有对应处理行
- [ ] 清空重跑构建后产物与预期一致
- [ ] 无「手工接好、脚本没有」的素材

**⑥ 禁忌与易错点**：「我拷过了」不是工程状态，脚本才是；手工产物一律要回写构建脚本，否则下一次重跑构建就是一次无声的素材丢失事故。

**⑦ 参数表**：实测参数：无——本条为工程纪律类，步骤为通用规程。

#### 【图集尺寸随脚本发布】

**① 目标与适用场景**：图集真实尺寸由打包脚本随元数据（atlas.js）一起发布，运行时直接读，消除「图片未加载完先按回退尺寸采样」的图标错位竞态。适用于一切资源尺寸参与布局/采样计算的场景；纯展示图不需要。

**② 前置条件**：打包脚本产出图集图片与元数据文件；运行时采样代码可读元数据。

**③ 操作步骤**：
1. 打包脚本把图集信息写进元数据（字段固定：图集宽 / 高 / 帧定义 / 元数据版本 / 图集内容哈希）→ 判定信号：元数据中宽高与图集实际像素尺寸一致（脚本断言核对）。
2. 运行时尺寸一律读元数据 → 动作：删除/禁用「等图片加载完成事件回填尺寸」的路径；元数据缺失或与内容哈希对不上时，运行时报错并停用该图集（不许回退到猜测尺寸凑合跑）→ 判定信号：代码中采样计算不依赖图片 onload 时序。
3. 竞态复现测试 → 动作：人为延迟图集图片加载，观察图标采样 → 判定信号：延迟下图标仍不错位。

**④ 失败分支**：
- 现象：元数据尺寸与图集实际尺寸不一致 → 原因：图集重打包后元数据未同步生成 → 处置：把尺寸写入做成打包脚本的强制步骤（同一次运行产出图与元数据），禁止分开维护。

**⑤ 验收清单**：
- [ ] 元数据尺寸与图集实际尺寸断言一致
- [ ] 运行时无依赖 onload 回填尺寸的代码路径
- [ ] 延迟加载复现测试下图标不错位

**⑥ 禁忌与易错点**：这类竞态时有时无、最难复现——不要试图靠「多等一会儿」掩盖，必须从数据源头（尺寸随脚本发布）消除。

**⑦ 参数表**：实测参数：无专用数值——本条以时序消除为主，步骤为通用规程。

#### 【BGM 首击触发的代价】

**① 目标与适用场景**：BGM 懒加载触发点本身的代价被发现后，列方案排期、不擅自改产品预期。适用于工程侧发现体验决策有量化代价时的处置流程；与【BGM 解析期零创建】是同一问题的两面。

**② 前置条件**：代价已量化（拉取体积、触发时机可测）；可选改法可枚举。

**③ 操作步骤**：
1. 量化记录代价 → 实测案例：大厅 BGM「任意首击触发」后，用户第一次点击（包括点卡进游戏）就会后台拉 1.15MB → 判定信号：代价有具体数字（体积＋触发点）入档。
2. 列可选改法成方案：低码率重编码 / 仅开关显式触发 / 短循环版 → 判定信号：每种改法写明预期收益与体验影响。
3. 方案排期上报决策 → 动作：在决策前不擅自改变触发行为 → 判定信号：线上行为与产品预期一致，方案在待决清单中。

**④ 失败分支**：
- 现象：工程侧已「顺手」改了触发点 → 处置：回滚到原行为，再走方案流程——触发点是产品体验决策（音乐何时响起），不是工程自由度。

**⑤ 验收清单**：
- [ ] 代价有量化记录
- [ ] 改法方案成文且各有收益/影响说明
- [ ] 未经决策未改线上行为

**⑥ 禁忌与易错点**：发现代价后装不知道是失职，偷偷改掉行为是越权；唯一正确姿势是量化＋列方案＋待决策。

**⑦ 参数表**：实测代价：首击触发后台拉取 1.15MB；候选改法：3 种（低码率重编码/开关显式触发/短循环版）。

## 素材加载与回退（6 条）

#### 【四级回退链】

**① 目标与适用场景**：角色模型加载做多级回退，任一层失败整体让位、永不白屏。适用于 3D 角色等大体积、失败模式多的资源加载。

**② 前置条件**：各回退层资源齐备（写实模型、次级模型、简模、程序化兜底）；加载器能逐级尝试并上报结果。

**③ 操作步骤**：
1. 定义回退链顺序 → 实测链：写实 GLB → 真人 FBX → 方块 GLB → 程序化人形，共四级 → 判定信号：链定义在代码中明确成列。
2. 逐级尝试：上层失败（报错/超时，超时机制见【回退链防挂死】）自动降下一层 → 判定信号：任一层成功即渲染该层，全链失败才落到程序化人形（程序化层不依赖外部资源，必成功）。
3. 对照遍实证（硬验收）→ 动作：按测试矩阵逐格跑：拦截层级（只拦一级 / 拦一二级 / 拦前三级）× 故障类型（404 / 文件损坏 / 超时），拦截一律带破缓存参数防缓存冒充下层接住；每格断言画面来自目标回退层（用该层来源标识/加载日志断言，不许只看截图猜）→ 预期现象：下层真的接住并渲染 → 判定信号：before（拦截走回退）与 after（正常加载）同机位对照截图留存，朝向/配色/脚底逐张核对。程序化兜底层另加存活探针：渲染后采样画面像素，非全透明/非单一色才算「必成功」被证实——程序化层也可能因代码异常或着色器失败而死，断言不是验收。

**④ 失败分支**：
- 现象：上层失败但回退不触发 → 原因：加载器挂死（既不成功也不失败）→ 处置：先修【回退链防挂死】的看门狗，回退逻辑本身不要乱改。
- 现象：回退层画质落差被验收误判为缺陷 → 处置：出示拦截对照记录，说明当前处于回退层，并按【素材顶替明说等级】如实告知落差。

**⑤ 验收清单**：
- [ ] 四级链定义明确且逐级可达
- [ ] 拦截对照遍通过（每一级都被实证接得住）
- [ ] 全链最底层（程序化）零外部依赖、必成功
- [ ] 任一单点资源损坏不白屏

**⑥ 禁忌与易错点**：回退链的画质落差要如实告知验收；没有拦截实证的回退链只是「写了回退代码」，不算成立。

**⑦ 参数表**：回退层级：4 级（写实 GLB / 真人 FBX / 方块 GLB / 程序化人形）；验收法：资源拦截对照遍 + 同机位对照截图。

#### 【回退链防挂死】

**① 目标与适用场景**：给基于回调计数的加载器加看门狗超时，防「不成功也不失败」的挂死让回退永不触发。适用于一切回调式加载器。

**② 前置条件**：已确认加载器的失败模式：某些加载器在贴图 404 时既不回调成功也不回调失败，pending 永不归零。

**③ 操作步骤**：
1. 给每级加载加看门狗：超过超时值未归零 → 强制判定该级失败、让位下一级 → 判定信号：人为制造贴图 404 时，回退在超时值内触发。
2. 超时值按模型定并随体积复核 → 模型：超时 ≥ 本级总体积 ÷ 最低保障带宽 × 安全系数（安全系数为标定值、示意 2，须按目标设备实测标定后登记）；慢设备的定义同时写明（目标设备清单中的最低档机型＋限速网络条件）→ 实测教训：素材涨到约 61MB 时，原 45s 超时会误杀慢设备，放宽到 120s（这是上式的项目个案，不是通用值）→ 判定信号：超时值有按模型算出的记录，体积大涨后复核过。
3. 慢设备验证 → 动作：在慢速网络/低端设备条件下跑一遍完整加载 → 判定信号：不误杀（能成功的加载不被超时砍掉）。

**④ 失败分支**：
- 现象：超时后回退触发了，但原加载随后又成功回调 → 处置：让位后到达的回调一律忽略（以看门狗裁定为准），防双重渲染/状态错乱。

**⑤ 验收清单**：
- [ ] 贴图 404 注入测试下回退按时触发
- [ ] 超时值与总体积对应关系有记录且为现行值
- [ ] 慢设备完整加载不误杀
- [ ] 迟到回调有忽略处理

**⑥ 禁忌与易错点**：回退逻辑写得再全，触发不了等于没有；超时太短又会在慢设备上把本可成功的加载误判失败——两个方向都是真机才暴露的坑，超时值不是一次定死的。

**⑦ 参数表**：看门狗超时：45s → 120s（素材总量约 61MB 时的实测口径，随体积复核）。

#### 【加载两级门控】

**① 目标与适用场景**：资源加载分两级放行：玩法必需的先行就绪即可进场，表现增强的后台续载。杜绝全量一票门控导致角色未就绪进场隐形。适用于资源总量明显大于首屏必需量的游戏。

**② 前置条件**：资源已按「玩法必需 / 表现增强」分级；进场门控可按级放行。

**③ 操作步骤**：
1. 一级（先行）：角色精灵先行加载 → 实测规模：90 张、约 0.39MB → 判定信号：一级就绪即放行进场。
2. 二级（后置）：其余约 6.7MB 资源后台续载 → 判定信号：续载不阻塞已进场玩家的游玩。
3. 后置资源加载中的占位与失败处理走【占位图顶替】【加载失败不静默】→ 判定信号：后置未到齐时界面呈现占位而非空白/隐形。

**④ 失败分支**：
- 现象：一级资源里混进了大文件导致先行变慢 → 处置：按体积复查一级清单，把非必需大文件降到二级；分级原则是「玩法必需先行」，不是按文件类型分。

**⑤ 验收清单**：
- [ ] 一级就绪即可进场且角色可见
- [ ] 二级续载不阻塞游玩
- [ ] 一级清单体积与实测量级一致（约 0.39MB）

**⑥ 禁忌与易错点**：全量 Promise 一票门控下，任何大资源慢一点，玩家看到的就是「人没出来」；分级放行把「能玩」与「全量到齐」解耦，这是本条的全部要义。

**⑦ 参数表**：一级：角色精灵 90 张约 0.39MB；二级：其余约 6.7MB 后台续载（实测口径）。

#### 【加载失败不静默】

**① 目标与适用场景**：图片加载禁止静默吞错，失败必须重试、留痕、可见。适用于全部资源加载路径。

**② 前置条件**：加载封装可统一改造（重试、记录、角标）；占位图机制可用（见【占位图顶替】）。

**③ 操作步骤**：
1. 全局清查并禁止 .catch(()=>{}) 式静默吞错 → 判定信号：代码扫描无此模式。
2. 失败自动重试 2 次：间隔 250ms / 500ms 递增，且带破缓存参数 → 判定信号：重试请求 URL 带破缓存参数（否则只是把同一份坏缓存再取一遍）。
3. 仍失败 → 三件套：记入 failed[] 留痕、console.error 输出、占位图顶替，并点亮页面角标明示有资源失败 → 判定信号：注入一次必失败的资源后，failed[] 有记录、控制台有错误、页面角标亮起、画面有占位图，四者齐现。

**④ 失败分支**：
- 现象：重试后成功但 failed[] 已有记录 → 处置：记录标注「重试后成功」再销账，不直接删记录，保持失败史可查。

**⑤ 验收清单**：
- [ ] 代码无静默吞错模式
- [ ] 注入失败测试四信号齐现（failed[]/console.error/占位/角标）
- [ ] 重试带破缓存参数且间隔递增

**⑥ 禁忌与易错点**：静默吞错是假验证的温床——素材永久隐形、测试却全绿，因为没人断言过「它真的显示出来了」；让失败可见是一切排查的起点。

**⑦ 参数表**：重试次数：2 次；重试间隔：250ms / 500ms 递增；失败处置：failed[] 留痕 + console.error + 占位 + 角标，共 4 件。

#### 【占位图顶替】

**① 目标与适用场景**：加载失败的角色用占位图顶替，让失败一眼可见且可被自动化断言。适用于角色精灵等关键资源的失败降级。

**② 前置条件**：加载失败路径已接通（见【加载失败不静默】）；canvas 可动态生成占位图。

**③ 操作步骤**：
1. 失败时生成占位图：灰色人物剪影 + 角色名，canvas 绘制 → 判定信号：失败位置显示占位图而非空白。
2. 占位图带 __placeholder 标记 → 判定信号：代码与测试可按标记识别「当前是占位状态」并断言。
3. 占位只作降级呈现 → 动作：failed[] 中的记录仍逐项清（修源、重下）→ 判定信号：占位数量随修复递减至 0。

**④ 失败分支**：
- 现象：正式验收时画面里有占位图 → 判定：不许以占位状态过关，先清 failed[] 再验收。

**⑤ 验收清单**：
- [ ] 注入失败时占位图正确显示且带标记
- [ ] 自动化能按标记断言占位状态
- [ ] 验收环境占位数 = 0

**⑥ 禁忌与易错点**：角色凭空消失时玩家与测试者都无从判断是没刷出来还是逻辑没生成；占位是降级不是修复，不要把「有占位兜底」当成可以不清失败记录的理由。

**⑦ 参数表**：占位图构成：灰色人物剪影 + 角色名（canvas 生成）；识别标记：__placeholder。实测参数：无专用数值——本条以机制为主，步骤为通用规程。

#### 【加载计数对齐】

**① 目标与适用场景**：异步贴图加载的就绪判定与进度呈现严格对齐，防就绪门控提前或永不触发。适用于回调计数式加载管理。**本条已废弃「发起数＝回调数＝分母」的总数相等判据**——总数相等只证明总量守恒，证明不了逐项对应：一项重复回调、另一项永不回调，总数照样相等，门控照样放过漏项。现行判据是**逐 ID 终态模型**。

**② 前置条件**：加载管理能给每次加载尝试分配唯一 ID 并记录其状态迁移；进度呈现能按 ID 集合算，而不是只维护一个自增计数器。

**③ 操作步骤**：
1. 发起即发 ID：每次加载尝试生成唯一 ID（构成 = 资源键 + 尝试序号；同一资源重试是新 ID，并回指原 ID），逐 ID 建一行状态记录：initiated → 终态 → 判定信号：发起清单是一张逐 ID 表，不是三个总数。
2. 终态集合封闭：每个 ID 只能进入且只进入一次终态，终态只许三种——成功 / 失败 / 超时（看门狗强制终结，见【回退链防挂死】）；终态后到达的迟到回调只记「迟到回调」计数并忽略，**不许改写终态、不许二次计数**；加载被取消的按超时同路处理（由看门狗或取消点强制落终态），不许留无终态 ID → 判定信号：任意时刻可查每个 ID 的当前状态，无 ID 停在 initiated 超过超时值。
3. 进度分母 = ID 集合本身：进度 = 已终态 ID 数 ÷ ID 总数；动态追加资源时新 ID 追加进集合并记录追加时点，门控判定时点冻结当时的 ID 集合快照（冻结后新追加的归下一批门控，不回头改已放行结论）→ 判定信号：进度条每个百分比都能对应到具体 ID 的终态变化。
4. 失败呈现与计数分离：失败 ID 由 failed[] 逐 ID 呈现（见【加载失败不静默】），进度到 100% 只表示「全部有终态」，不表示「全部成功」→ 判定信号：注入失败项后进度可达 100%，且成功/失败在呈现层分得开。

**④ 失败分支**：
- 现象：进度卡在不满 → 原因：有 ID 无终态（回调丢失或加载挂死）→ 处置：直接在逐 ID 表里点名无终态 ID 修其加载路径，看门狗负责给它落超时终态防门控永挂；不许靠加大超时掩盖计数 bug，更不许把计数器人工拨满。
- 现象：重复终态 ID 出现 → 原因：回调路径重复触发或重试未发新 ID → 处置：按 ID 定位重复来源修回调幂等，修前该批加载验收不通过。

**⑤ 验收清单**：
- [ ] 未终结 ID 数 = 0
- [ ] 重复终态 ID 数 = 0
- [ ] 逐 ID 集合相等：已终态 ID 集合 = 发起 ID 集合（总数相等仅作辅助核对，不作判据）
- [ ] 注入失败项后进度可达 100% 且失败另有呈现；注入「永不回调」项后看门狗落超时终态、门控不永挂
- [ ] 迟到回调有计数且未改写终态

**⑥ 禁忌与易错点**：计数错位产生的故障是间歇性的、最难复现；总数相等是最会骗人的判据——它对「一个重复、一个丢失」完全无感；对齐必须逐 ID，不许「大概齐」。

**⑦ 参数表**：实测对齐规模：40 项（项目样本）；ID 构成：资源键 + 尝试序号；终态集合：成功 / 失败 / 超时，共 3 种，每 ID 恰进入 1 次；验收量：未终结 ID 数、重复终态 ID 数（均须 = 0）。
## 角色与场景美术处理（22 条）

#### 【人物形象硬标准】

**① 目标与适用场景**：选包前先过形象硬线：角色必须像真人，拒绝方块/Minecraft 式与低多边形玩具风人物。适用于美术选包的第一道筛。注意：这是本项目的产品定调，不是普适真理——像素风、方块风本身可以是合格路线，但须在立项时定死、不许中途混用。**「像真人」不许只凭一句感觉判定**，必须走样本板对照＋特征清单＋双人裁定（见步骤），让结论可复现。

**② 前置条件**：立项时已定形象路线；候选包有可看的实机/精灵图样；已建形象样本板：合格样本与不合格样本各若干（取自已定版的历史结论：已入选的人物包样图入合格侧、已被淘汰的方块风/玩具风样图入不合格侧），新立项无历史样本时由定调人先标定第一批样本再开筛。

**③ 操作步骤**：
1. 对照样本板初判 → 动作：候选样图与样本板两侧逐个对照，归入「近合格侧 / 近不合格侧 / 两边都不像」→ 判定信号：每个候选有对照结论。
2. 按可观察特征清单逐项核：有无可辨的面部五官与人体比例、肢体是否为方块拼接、表面是否为大块低多边形平面、轮廓是否玩具化圆角 → 判定信号：结论能指认到具体特征，而不是只写「不像真人」。
3. 双人独立裁定：两名裁定人背靠背各给结论 → 一致才定案；不一致的由定调人（产品负责人）终裁，终裁理由写入选包表 → 判定信号：选包表每行有两人结论（或终裁记录），无单人一句定生死。
4. 过形象关的包再谈动作覆盖与规格（见【素材规格门】）→ 判定信号：评估顺序为形象 → 规格，无倒置；淘汰与入选结论连同特征依据在选包表留痕，并把典型样图补进样本板供下一轮用。

**④ 失败分支**：
- 现象：全候选包都不过形象关 → 处置：不降格凑数，按缺口登记并走自制/顶替明说流程（见【缺口如实登记】【素材顶替明说等级】）。
- 现象：双人裁定长期大量不一致 → 原因：样本板样本不足或特征清单不够细 → 处置：先扩样本板、细化特征清单再继续筛，不许靠多投几票糊弄过去。

**⑤ 验收清单**：
- [ ] 入选人物包全部过形象关：选包表有对照结论、特征依据与双人裁定记录
- [ ] 样本板已随本轮结论更新
- [ ] 无中途混入异风格人物

**⑥ 禁忌与易错点**：人物是玩家第一眼的观感锚点，形象路线定错，后续所有打磨都在错的地基上；硬标准前置能省掉整轮返工；只留痕不给判据等于没有标准——留痕是记录结论，样本板与特征清单才是标准本身。

**⑦ 参数表**：裁定方式：样本板对照 + 特征清单（4 项可观察特征）+ 双人独立裁定（不一致由定调人终裁）。实测参数：无专用数值——本条为选型纪律类，步骤为通用规程。
#### 【精灵发糊真因与限度】

**① 目标与适用场景**：人物发糊时先定位真因（采样方式）再动手，并如实交代修复限度。适用于小尺寸像素精灵被放大显示的项目。

**② 前置条件**：已知精灵原始尺寸（实测样本 126–250px）与实际显示放大倍数（约 2.2 倍）。

**③ 操作步骤**：
1. 先算放大倍数：显示尺寸 ÷ 精灵原始尺寸 → 实测约 2.2 倍且素材为像素图 → 判定：糊的真因是双线性平滑放大，不是素材低清。
2. 处置：角色本体改最近邻采样锐化；背景与特效保持平滑（通路分开，见【平滑口径分材质】）→ 判定信号：角色边缘锐利、背景无锯齿。
3. 如实交代限度 → 动作：在验收材料中明说「锐化后只是清晰的像素风、不是高清；高清重绘是独立美术工程」→ 判定信号：无任何「已高清」式表述。

**④ 失败分支**：
- 现象：误判为素材低清去换素材 → 后果：换什么都糊（倍数不变）→ 处置：回到第 1 步先算倍数再定性。

**⑤ 验收清单**：
- [ ] 发糊结论有放大倍数数据支撑
- [ ] 角色最近邻、背景平滑分别生效（截图核对）
- [ ] 限度说明在验收材料中明示

**⑥ 禁忌与易错点**：把锐化冒充高清是验收口径上的欺骗，真机一看就穿；采样分材质的通路不要用全局开关一刀切。

**⑦ 参数表**：精灵原始尺寸：126–250px（实测样本）；放大倍数：约 2.2 倍；角色采样：最近邻；背景/特效采样：平滑（双线性）。

#### 【立绘包围盒裁切】

**① 目标与适用场景**：选人头像按 alpha 内容包围盒裁切，把有效像素用满，杜绝「整帧缩进小框、人物只剩一点点」。适用于精灵帧含大量透明留白的头像/立绘展示。

**② 前置条件**：精灵帧带 alpha 通道；已知 idle 首帧可作裁切基准。

**③ 操作步骤**：
1. 量整帧缩进的现状作对照 → 实测：整帧缩进时人物只剩约 26px 高、高度占比约 31% → 判定信号：有现状数字。
2. 取 idle 首帧算 alpha 内容包围盒：内容判定阈值 = alpha ≥ 128（标定值——半透明辉光、投影不计入内容；改阈值须在记录中写明并全批统一）→ 按包围盒裁切、等比放大、底对齐填满头像框；占比公式写死：人物高度占比 = 裁切缩放后人物包围盒高 ÷ 头像框高；宽高双约束：宽或高任一维先触界即按该维定缩放倍数，不许只顾高度把宽度撑出框，四边留安全边距（示意 ≥2px，标定后登记）→ 判定信号：裁切后人物高度占比升到 83–94%（实测区间）。
3. 逐角色核对 → 判定信号：每名角色头像占比落在目标区间，无出框。

**④ 失败分支**：
- 现象：某角色动画中出框 → 原因：各帧包围盒差异大、只按首帧裁 → 处置：该角色裁切框改取各帧包围盒并集；切换判据量化：各帧包围盒与首帧包围盒任一维差异 >10%（标定值）即自动改用并集，不靠目测「差异大」。

**⑤ 验收清单（硬验收）**：
- [ ] 逐角色量头像人物高度占比，全部 ≥80% 量级（对照实测 83–94%）
- [ ] 无动画出框
- [ ] 裁切基准（首帧/并集）在角色数据中有记录

**⑥ 禁忌与易错点**：精灵帧的透明留白也是「帧的一部分」，整帧缩放等于把留白一起缩进框；占比要用像素量测验收，不许目测「差不多大了」。

**⑦ 参数表**：整帧缩进：人物约 26px 高、占比约 31%；包围盒裁切后占比：83–94%（实测）；内容阈值：alpha ≥ 128（标定值）；裁切基准：idle 首帧（各帧差异 >10% 取各帧并集）；逐角色记录字段：bbox / scale / offset。

#### 【footPad 锚点标定】

**① 目标与适用场景**：精灵帧内脚底透明留白逐角色标定（footPad），绘制时下移补偿，消除角色悬空。适用于帧底留白不一致的精灵素材接入。

**② 前置条件**：能逐帧扫描 alpha 得出底部透明行数；绘制层支持按角色偏移。

**③ 操作步骤**：
1. 逐角色实测脚底留白行数：自帧底向上逐行扫描，alpha ≥ 128（标定值，与【立绘包围盒裁切】同口径）的首行即内容底行，其下透明行数 = footPad；地面线 = 绘制锚点行（角色逻辑脚底应落到的那一行）→ 实测范围：44–83 行 → 判定信号：每名角色有 footPad 数值与所用代表帧（idle 首帧）入台账。
2. 绘制时整帧下移 footPad 行 → 预期现象：脚底与地面线齐平 → 判定信号：截图量测悬空量 ≈ 0（原悬空约百余 px）。
3. 严守分离：footPad 只进绘制层 → 判定信号：逻辑坐标与联机校验和代码中不出现 footPad（grep 核对）。

**④ 失败分支**：
- 现象：补偿后角色陷地/仍悬空 → 原因：标定取的帧不是代表帧 → 处置：按各动作帧重测取统一基准帧重标，不逐帧乱补。

**⑤ 验收清单**：
- [ ] 每名角色 footPad 有实测值入账
- [ ] 截图悬空量 ≈ 0
- [ ] 逻辑与校验和代码零 footPad 引用

**⑥ 禁忌与易错点**：把表现修正写进逻辑坐标，联机两端校验和会因表现差异对不上——表现量与逻辑量分离是底线，没有例外。

**⑦ 参数表**：footPad 实测范围：44–83 行（逐角色）；原悬空量：约百余 px；补偿后目标：≈0。

#### 【重着色造独立角色】

**① 目标与适用场景**：两名角色素材完全同源（同场无法分敌我）时，用 HSV 重着色造独立配色应急，并如实标注过渡属性。适用于同源角色必须同场出现的情形。

**② 前置条件**：已证同源（文件级比对）；有 HSV 色彩映射工具。

**③ 操作步骤**：
1. 先证同源 → 实测判据：两名角色精灵 10/10 文件 MD5 完全相同 → 判定信号：MD5 比对记录在案（无此证据不要启动重着色）。
2. HSV 色彩映射重着色 → 实测：改色像素比例 99.9% → 判定信号：新配色与原型同框截图可一眼区分。
3. 如实标注 → 动作：台账与汇报注明「动作与原型同源、属过渡方案」，正解（换独立角色包）挂入待办 → 判定信号：标注存在且待办未关。

**④ 失败分支**：
- 现象：重着色后仍易混淆（色相太近）→ 处置：拉大色相距离重染，并以同框截图复核为准，不许将就。

**⑤ 验收清单**：
- [ ] 同源证据（MD5 全同）留存
- [ ] 改色像素比例有数值（对照实测 99.9%）
- [ ] 同框区分度截图通过
- [ ] 「过渡方案」标注与正解待办都在

**⑥ 禁忌与易错点**：同源角色同场是必须解决的问题，但把换色冒充新角色是另一种欺骗；标注过渡属性才能让它进待办而不是被遗忘。

**⑦ 参数表**：同源判据：10/10 文件 MD5 全同；改色像素比例：99.9%（实测）；方法：HSV 色彩映射。

#### 【染色变体法】

**① 目标与适用场景**：敌方变体无原生素材时，用队色染色生成；有原生变体时优先原生。适用于阵营辨识刚需而素材不足时。

**② 前置条件**：已确认该角色无原生敌方变体（如骑士金甲版这类原生变体存在则直接用）；队色已定。

**③ 操作步骤**：
1. 先查原生变体 → 有则用原生，染色只作兜底 → 判定信号：选用结论在台账有记录。
2. 染色生成：以 35% 队色混合染生成红方版 → 混合口径写明：对选定色区像素在 RGB 空间按 输出 = 原色×(1−0.35)＋队色×0.35 混合（如实现改用 HSV 空间混合，须在台账注明空间与参数，两者结果不等价、不许混记）；辨识验收：同框截图由第二人在不知编号时盲辨阵营，辨对才算可辨 → 判定信号：产物与原版同框可辨阵营且盲辨记录在案。
3. 截图复核定版 → 判定信号：辨识度与原图质感平衡可接受；题材色差大的素材重新试混合比例再定版。

**④ 失败分支**：
- 现象：35% 染后辨识仍不足或质感崩坏 → 处置：在 35% 上下试值并逐档截图比对，定版值与截图一并入账；仍不行则转缺口/自制流程。

**⑤ 验收清单**：
- [ ] 原生变体优先的核查记录在案
- [ ] 染色比例与定版截图留存
- [ ] 同框阵营辨识通过

**⑥ 禁忌与易错点**：染色质感逊于原生变体，有原生的不用染色的是观感排序问题，不要图省事全员染色；混合比例是本项目平衡点（35%），不是普适常数。

**⑦ 参数表**：队色混合比例：35%（实测口径，按题材复核）；优先序：原生变体 > 染色兜底。

#### 【离线描边打包】

**① 目标与适用场景**：矢量人物图无描边、在高频背景上边缘发飘时，描边在离线打包阶段统一做。适用于矢量风人物与图标；像素素材不走此路（走采样路线，见【精灵发糊真因与限度】）。

**② 前置条件**：打包脚本可插入图像处理步骤；原图为矢量渲染的位图。

**③ 操作步骤**：
1. 打包阶段统一加描边：在放大前的源图上加 2px 深色描边（这是处理阶段宽度）→ 判定信号：产物边缘有均匀描边。
2. 描边后再放大：×3 Lanczos 放大进图集（顺序不可反——先放大后描边边缘更脏）→ 注意成品描边宽度 = 处理阶段宽度 × 放大倍数 ≈ 6px，规格对的是成品宽度；目标成品宽度不同时按 目标成品宽度 ÷ 放大倍数 反推处理阶段宽度 → 判定信号：图集内成品尺寸与成品描边宽度符合规格。
3. 运行时零处理 → 判定信号：运行时代码无描边逻辑，各端显示一致。

**④ 失败分支**：
- 现象：描边后与背景对比仍发飘 → 处置：先查背景频率与描边色深浅关系，调描边色而不是加粗到失真；调整值入打包脚本（见【构建脚本留痕】）。

**⑤ 验收清单**：
- [ ] 描边在打包产物中均匀一致
- [ ] 描边→放大的顺序在脚本中固定
- [ ] 运行时无描边处理代码

**⑥ 禁忌与易错点**：描边是确定性加工，离线做一次即可；运行时做既费性能又难保各端一致。

**⑦ 参数表**：处理阶段描边：2px（深色，放大前源图口径）；放大：×3 Lanczos（描边后执行）；成品描边：约 6px（= 2px × 3，验收按成品口径量）。

#### 【素材调色救观感】

**① 目标与适用场景**：成品素材质量合格只是色调不合题材时，先调色再用。适用于造型、帧数达标、仅色调违和的素材。

**② 前置条件**：有 HSV 调色工具；调色参数定版前必须与游戏内实际背景同框截图复核。

**③ 操作步骤**：
1. 定位色调问题并定调法 → 实测两例：植被素材青蓝玩具色 → 按模板乘橄榄绿调；等距树图 → HSV 色相 −0.085、饱和 ×0.92、明度 ×0.88 回自然绿 → 判定信号：每类素材有自己的参数组，不全库套同一组值。
2. 调后与实际背景同框截图复核 → 复核由第二人执行并签字（制作者自看自过不算数），逐项看：色调与背景光照是否同向、饱和度是否同量级 → 判定信号：实验图好看不够，同框不违和且有第二人复核记录才定版。
3. 参数写入构建/加工脚本留痕（见【构建脚本留痕】）→ 判定信号：重跑可复现同色调。

**④ 失败分支**：
- 现象：调色后同框仍违和 → 原因：问题不在色调而在造型/光影 → 处置：退出调色路径，按缺口或换素材处理，不无限调参。

**⑤ 验收清单**：
- [ ] 每类调色素材有参数组记录
- [ ] 同框截图复核通过后才定版
- [ ] 参数已回写脚本

**⑥ 禁忌与易错点**：只在实验室背景里看调色效果是典型自欺——必须与游戏内实际背景同框看；参数逐类试定，不许全库一刀切。

**⑦ 参数表**：实测参数组：等距树 HSV 色相 −0.085 / 饱和 ×0.92 / 明度 ×0.88；植被：模板乘橄榄绿调。

#### 【实例化渲染】

**① 目标与适用场景**：场景同类道具用实例化渲染降 draw call，同时逐件登记碰撞防「看得见挡不住」。适用于同模板重复出现的静态道具；数量少或每件需独立动画的道具不值得实例化。

**② 前置条件**：道具按模板归类完成；碰撞登记流程明确（含子弹碰撞、包围盒近似）。

**③ 操作步骤**：
1. 按模板建 InstancedMesh：每模板一个 → 实测规模：23 个 GLB 模板 → 判定信号：同模板道具不再逐件成网（渲染统计可查）。
2. 新增掩体逐件登记碰撞 → 动作：登记含子弹碰撞、包围盒近似 → 测试口径：逐件全检（掩体数量有限，不抽样）——每件做正面射击 1 次＋正面通行 1 次，两项都挡住才算过 → 判定信号：逐件测试记录齐全（实测验证，不凭登记表自证）；draw call 收益的基线 = 实例化前同场景同机位计数，无基线不许报收益。
3. 与合并类优化分工：实例化管同模板重复件，静态合并管异类静态物（见【装饰合并降 draw call】）→ 判定信号：同一道具不被两套机制重复处理。

**④ 失败分支**：
- 现象：实例化后某件道具需要单独隐藏/动画 → 处置：该件从实例化中拆出独立成网，其余保留；不要为一件拆全组。

**⑤ 验收清单**：
- [ ] 每模板一个 InstancedMesh（对照实测 23 个模板）
- [ ] 新增掩体逐件碰撞实测通过
- [ ] draw call 有下降数据

**⑥ 禁忌与易错点**：碰撞登记不能只写表不实测——「看得见挡不住」是表现/逻辑脱节的典型症状，验收必须打一枪、走一遍。

**⑦ 参数表**：实测规模：23 个 GLB 模板（每模板一个 InstancedMesh）；碰撞近似：包围盒（含子弹碰撞）。

#### 【素材规格门】

**① 目标与适用场景**：选角色包先定规格门，不合规格在选包环节淘汰，避免接入后才发现动作缺项。适用于各品类角色包选型（规格门按品类定，格斗与 MOBA 的动作清单不同）。

**② 前置条件**：规格门已按品类写明（本项目格斗口径：方帧 + Idle/Run/Atk/Jump/Fall/Hit/Death 齐全）。

**③ 操作步骤**：
1. 逐包实测三项：帧宽、帧数、动作覆盖 → 判定信号：每包有实测记录表（帧数测法见【帧数实测对齐】）。
2. 对照规格门判定：异尺寸帧、只有攻击表、缺受击或死亡 → 直接淘汰并记录理由 → 判定信号：淘汰包有理由留痕，不默默丢弃。
3. 入选包进入验货与接入流程（见【素材先验货再动手】）。

**④ 失败分支**：
- 现象：某包只缺一项但其余极优 → 处置：仍按门淘汰或登记为缺口候补，不破格入选——破格一次，规格门即失效；单攻击表是否算缺项另有判例（见下条）。

**⑤ 验收清单**：
- [ ] 每包有帧宽/帧数/动作覆盖实测表
- [ ] 淘汰包全部有理由留痕
- [ ] 入选包全过规格门

**⑥ 禁忌与易错点**：动作缺项在接入后才发现，补法要么阉割玩法要么重找素材，都是整轮返工；规格门把淘汰提前到成本最低的环节。

**⑦ 参数表**：规格门（格斗口径）：方帧 + 动作齐全（Idle/Run/Atk/Jump/Fall/Hit/Death）；实测三项：帧宽 / 帧数 / 动作覆盖。

#### 【单攻击表不构成缺陷】

**① 目标与适用场景**：只有一张攻击表的角色不按规格缺陷处理——前提是引擎能以参数做出动作区分。适用于规格门判定时的例外裁定（见【素材规格门】）。

**② 前置条件**：引擎支持以参数（位移、判定、特效）区分重击与必杀；已有现役同类角色可玩为证。

**③ 操作步骤**：
1. 遇单攻击表角色 → 先查现役判例 → 实测事实：现役多名角色同样只有一张 atk 表且可玩 → 判定信号：有现役可玩实例则不按缺陷处理。
2. 在选包表标注「单攻击表、引擎参数区分」→ 判定信号：标注与裁定依据（现役实例）齐全。
3. 例外情形复核：某招式必须有专属起手帧（如投技）→ 该角色仍需补帧或换包 → 判定信号：招式清单逐招核对过起手帧需求。

**④ 失败分支**：
- 现象：引擎参数区分做不出可感差异 → 处置：该角色按缺项处理，补帧或换包，不硬套本条。

**⑤ 验收清单**：
- [ ] 单攻击表角色有裁定记录与现役依据
- [ ] 招式起手帧需求逐招核对无遗漏
- [ ] 参数区分的可感差异经实测：第二人看实战画面能逐招区分重击与必杀（说不出区别 = 参数区分不成立，按缺项处理）

**⑥ 禁忌与易错点**：真正的规格缺项是缺受击、缺死亡这类无引擎代偿的动作；把「攻击表数量」当规格门会误杀可用素材。

**⑦ 参数表**：实测参数：无专用数值——本条为裁定规则类，步骤为通用规程（现役实例取自原始记录）。

#### 【场景出画修复法】

**① 目标与适用场景**：追加舞台的主体被缩放出画时，用环绕平移把主体移回画内，不重做场景图。适用于分层背景类舞台；主体出画若因原始素材构图残缺，平移救不回，要换素材并留痕。

**② 前置条件**：场景为分层结构、地表平铺可独立保持；场景索引机制为只追加（保联机兼容）。

**③ 操作步骤**：
1. 定位出画层 → 判定信号：明确是哪一层、被缩放推出多少。
2. 对该层做环绕平移把主体移回画内 → 出画量与平移量（px）逐项记入台账；约束：不破坏地表平铺 → 判定信号：平移后在环绕接缝处单独截图核对无错位、主体完整在画内。
3. 场景索引只追加新配置，不改既有编号 → 判定信号：旧房间/旧回放的场景编号仍可复现。

**④ 失败分支**：
- 现象：平移后主体回来但构图仍残缺 → 原因：原始素材构图本身残缺 → 处置：换素材并在台账留痕，不继续平移硬凑。

**⑤ 验收清单**：
- [ ] 主体完整在画内（截图证）
- [ ] 地表平铺无接缝错位
- [ ] 既有场景索引未被改动

**⑥ 禁忌与易错点**：重做场景图成本远高于平移修复，但平移只治「位置出画」、不治「构图残缺」，两种病因不要混。

**⑦ 参数表**：实测参数：无专用数值——本条以截图核对为主，步骤为通用规程。

#### 【SFF 调色板坑】

**① 目标与适用场景**：索引图打包为 SFF 类按固定步进读调色板的格式时，强制补齐调色板，防第二张精灵起整体错位。适用于一切按固定步进读调色板的索引图格式。

**② 前置条件**：打包工具为 PIL 保存索引图；已知目标格式的调色板步进（SFF 为 768 字节）。

**③ 操作步骤**：
1. 打包前检查每张索引图的调色板长度 → 判定信号：长度 <768 字节的即为风险图。
2. 强制补齐调色板到 768 字节再打包 → 判定信号：打包脚本中有补齐步骤且对全部图生效。
3. 打包后逐帧目检 → 判定信号：第二张起精灵无错位（本坑的标志症状就是第二张起全错位）。

**④ 失败分支**：
- 现象：已打包文件出现第二张起错位 → 原因：调色板未补齐 → 处置：按第 2 步补齐后整包重打，不逐图修补（错位是整包步进问题）。

**⑤ 验收清单**：
- [ ] 全部索引图调色板长度 = 768 字节
- [ ] 打包后逐帧目检无错位
- [ ] 补齐步骤固化在打包脚本中

**⑥ 禁忌与易错点**：症状（第二张起全错位）与病因（调色板长度）相距极远，无人点破时能耗掉数天；补齐是零副作用的一行修复，不要去逐图对位。

**⑦ 参数表**：调色板步进/补齐目标：768 字节；症状起点：第二张精灵。

#### 【转换逐帧人工标定】

**① 目标与适用场景**：精灵表转帧动画时，打击帧与判定帧必须人工标定，不可全自动。适用于攻击表混有蓄势帧与特效帧的转换。

**② 前置条件**：转换器能先自动标一版；标定结论要入角色数据表供联机校验共用。

**③ 操作步骤**：
1. 转换器自动标出候选打击帧/判定帧 → 判定信号：有初版标定表。
2. 人眼逐帧复核打击帧与判定帧位置 → 动作：逐帧看攻击表，确认哪帧是打击生效帧；标定表字段固定：动作名 / 打击帧 / 判定帧起止 / 标定人 / 复核人（标定与复核不得同一人）→ 判定信号：关键帧标定经人工确认且标定表字段齐全。
3. 其余帧信自动结果 → 判定信号：人工只动关键帧，不全表重标。
4. 标定结论入角色数据表 → 判定信号：联机校验使用同一份标定数据。

**④ 失败分支**：
- 现象：实战手感/命中公平性异常 → 原因：判定帧错一帧 → 处置：回查标定表逐帧复核该动作，不先怀疑网络或数值。

**⑤ 验收清单**：
- [ ] 每个攻击动作的打击/判定帧有人工复核记录
- [ ] 标定数据已入角色数据表且联机共用
- [ ] 无全自动标定直接上线的动作

**⑥ 禁忌与易错点**：「哪帧是打击帧」是语义判断，自动转换器依据 alpha 或位移猜不准；判定帧错一帧，手感与命中公平性全错。

**⑦ 参数表**：实测参数：无专用数值——本条以人工复核流程为主，步骤为通用规程。

#### 【帧表三方交叉核定】

**① 目标与适用场景**：帧界异常的精灵表，帧数结论必须三方互证才可作切割代码依据。常规表两方对齐即可（见【帧数实测对齐】），异常表必须升三方。

**② 前置条件**：三方材料齐备：Preview.gif、帧界 alpha 扫描工具、逐帧拼图目检条件。

**③ 操作步骤**：
1. 第一方：数 Preview.gif 帧数 → 注意先按 GIF 合成规则（透明合成与 disposal 方式）重建视觉帧再计数，文件里的 image descriptor 数不等于视觉帧数（局部帧会多数）→ 记录重建后的视觉帧数。
2. 第二方：帧界 alpha 扫描定帧界 → 方法：逐列统计 alpha ≥ 阈值（与【帧数实测对齐】同档位口径）的像素数得列投影，连续零列段为帧间空白、非零段为帧内容，界线由投影定，不依赖任何初步切割；目检材料用整表原始像素条带图（未切割原图），不许用初切拼图当独立证据 → 记录。
3. 第三方：逐帧拼图目检 → 记录。
4. 三方一致 → 结论成立写入目录；不一致 → 以目检拼图为锚逐项查差异来源 → 实测判例：曾有「中段帧变宽」的早期结论，经三方核定实为把帧尾空白误读，结论被推翻并留痕 → 判定信号：被推翻的旧结论有留痕，不静默改数。

**④ 失败分支**：
- 现象：三方两方一致、一方差一帧 → 处置：差的那一帧单独放大目检定界，不许投票表决定案。

**⑤ 验收清单**：
- [ ] 异常表有三方各自结论记录
- [ ] 最终帧数三方一致或有差异定界记录
- [ ] 被推翻的旧结论留痕

**⑥ 禁忌与易错点**：每种方法都有盲区（gif 可能抽帧、alpha 扫描会被空白误导、目检会看花）；单方结论作切割依据，错一帧全表错位。

**⑦ 参数表**：核定三方：Preview.gif 帧数 / 帧界 alpha 扫描 / 逐帧拼图目检；实测判例：「中段帧变宽」为帧尾空白误读（已推翻留痕）。

#### 【选角数据与身份双判】

**① 目标与适用场景**：选角/换角分配要过数据与身份两判：量化数据是参考，题材身份是硬线。适用于素材与角色身份的匹配决策；数值平衡（强度、帧数）仍按数据定，两者不互相越界。

**② 前置条件**：有可量化的步态/动作数据（如帧间差）；角色题材身份定义明确。

**③ 操作步骤**：
1. 先看数据：量候选素材的量化指标 → 实测样本：某角色步态帧间差最大（144）→ 数据面它最优。
2. 再过身份判：造型不合法师身份 → 结论：仍不换给法师；法师现役角色帧间差 27、最弱也不换 → 判定信号：决策记录中数据结论与身份结论分开写明。
3. 决策与理由都留痕 → 判定信号：后人能查到「为什么没按数据最优分配」。

**④ 失败分支**：
- 现象：身份与数据双优的素材后来出现 → 处置：按正常流程替换，旧决策留痕不删——旧决策在当时信息下成立。

**⑤ 验收清单**：
- [ ] 分配决策有数据面与身份面双记录
- [ ] 身份否决项有具体造型依据
- [ ] 数值平衡决策未被身份判越界干预

**⑥ 禁忌与易错点**：纯按数据最优分配，会得到「拿着法杖抡步态的战士」，玩家一眼出戏；观感问题不能用数据达标来驳回。

**⑦ 参数表**：帧间差定义：同尺寸、同对齐下相邻两帧逐像素绝对差的均值（全序列取平均）；实测样本：步态帧间差最大 144（数据最优、身份否决）vs 法师现役 27（数据最弱、身份保留）——均为该口径下的项目样本，换口径不可直接比。

#### 【平滑口径分材质】

**① 目标与适用场景**：平滑采样按材质分开设置：矢量开平滑、像素关平滑（最近邻）。适用于图集/渲染管线中矢量与像素素材混装的项目。

**② 前置条件**：能按精灵（而非按图集）设置采样模式；已分清每张素材属矢量还是像素。

**③ 操作步骤**：
1. 逐精灵设采样：矢量人物图 → 平滑采样开；像素图 → 关平滑（最近邻）→ 判定信号：配置按精灵粒度，不是全局一个开关。
2. 双向截图核对 → 判定信号：矢量图无锯齿、像素图不糊（对照【精灵发糊真因与限度】）。

**④ 失败分支**：
- 现象：一边糊一边锯齿 → 原因：用了全局统一采样 → 处置：拆回按精灵配置，混装图集尤其要逐个核对。

**⑤ 验收清单**：
- [ ] 每张精灵采样模式与其材质类型一致
- [ ] 截图双向核对通过

**⑥ 禁忌与易错点**：混用必然一边糊一边锯齿——这是采样常识，但在统一渲染管线里最容易被一刀切掉。

**⑦ 参数表**：采样口径：矢量 = 平滑开 / 像素 = 平滑关（最近邻）；设置粒度：逐精灵。实测参数：无专用数值——本条以配置核对为主，步骤为通用规程。

#### 【DPR 渲染管线】

**① 目标与适用场景**：高清屏发糊要整条管线一起改：画布物理像素、坐标换算、UI 补偿三处同步。适用于 Canvas/WebGL 项目的 DPR 适配。

**② 前置条件**：能改画布尺寸、世界/输入/小地图三处坐标换算、UI 缩放补偿四处代码点。

**③ 操作步骤**：
1. 画布物理像素 = CSS 尺寸 × min(DPR, 2) → 判定信号：高清屏下画面锐利度提升。
2. 三处坐标同步换算：世界、输入、小地图 → 硬验收：坐标往返换算误差 = 0.00——口径写明：测试点集取画面中心、四角与小地图四角，各点做 世界→屏幕→世界 往返后取整像素误差为 0（浮点中间值容差 <0.5px），不是「浮点数恰好相等」→ 判定信号：测试点集逐点误差记录在案，点击位置与显示位置无错位。
3. 屏幕 UI 按缩放反向补偿 → 判定信号：UI 元素在高清屏上保持恒定大小，不成比例放大。

**④ 失败分支**：
- 现象：画面清了但点击错位 → 原因：只改画布、漏改某处坐标换算 → 处置：按三处清单逐处排查，漏哪补哪，不许靠偏移量硬凑。

**⑤ 验收清单**：
- [ ] DPR 封顶 = 2 已落实
- [ ] 三处坐标往返误差 = 0.00（量测记录）
- [ ] UI 恒定大小核对通过

**⑥ 禁忌与易错点**：只改画布尺寸是半套工程，必然生出点击错位的新故障；小地图是最容易漏的第四处——清单里必须显式列它。

**⑦ 参数表**：DPR 封顶：min(DPR, 2)；坐标换算验收误差：0.00；换算覆盖：世界 / 输入 / 小地图，共 3 处。

#### 【小地图真实缩略图】

**① 目标与适用场景**：小地图底图用预渲染的真实地图缩略图替换手画示意图，保证河流、道路、野区与实际地形一致。适用于地形对导航有实际意义的游戏。

**② 前置条件**：地图地形已定型；有离线预渲染手段。

**③ 操作步骤**：
1. 以背板尺寸预渲染真实地形缩略图 → 实测口径：380px 背板 → 叠图核对量化：把缩略图与大地形图叠合，关键地标（河道拐点、道路交叉点）偏移 ≤ 2px（该背板口径下的标定值，背板尺寸变了按比例重标定）才算对得上 → 判定信号：地标偏移量测记录在案。
2. 替换手画示意图 → 判定信号：小地图底图来源为预渲染产物。
3. 动态元素（单位、视野）仍走实时绘制层 → 判定信号：底图静态、动态层独立，不互相污染。
4. 地形变更时同步重渲染缩略图（见【图集重建时机】）→ 判定信号：地形改版记录中有缩略图重渲染项。

**④ 失败分支**：
- 现象：玩家按小地图找路被误导 → 原因：缩略图过期（地形改了图没重渲）→ 处置：立即重渲染并把「地形变更→重渲染」写进改版流程。

**⑤ 验收清单**：
- [ ] 缩略图与实际地形叠图核对一致
- [ ] 底图为预渲染产物、动态层独立
- [ ] 地形变更流程含重渲染项

**⑥ 禁忌与易错点**：手画示意图与真实地形必然有出入，差一处就误导一次；真实缩略图是「渲染一次、永久一致」，前提是变更时记得重渲。

**⑦ 参数表**：实测背板尺寸：380px；一致性验收：叠图核对（河流/道路/野区）。

#### 【装饰零逻辑】

**① 目标与适用场景**：纯装饰只落表现层，永不进逻辑与碰撞；落点有断言约束。适用于茶树、茶花、石灯类纯装饰物。带玩法功能的物件（掩体、草丛）不是装饰，走【实例化渲染】逐件登记碰撞。

**② 前置条件**：地图有兵线、河面等功能区定义；装饰落点生成环节可加断言。

**③ 操作步骤**：
1. 装饰只进预渲染层与绘制层 → 判定信号：逻辑与碰撞数据中无装饰条目（数据核查）。
2. 落点断言：距兵线 ≥92 单位（距离定义 = 装饰落点到兵线路径包络边缘的最短距离，不是到中心线）、河面零落点 → 判定信号：生成时断言全过，违规落点被拦截并重落。
3. 上线前抽查 → 动作：随机抽装饰点核对与兵线距离与河面关系，样本量 = 不少于 30 点或全量的 10%（取大者，规程量级、按地图规模标定）→ 判定信号：抽查全合规。

**④ 失败分支**：
- 现象：玩家反馈「看不见的墙」 → 原因：装饰误入碰撞 → 处置：按坐标定位该装饰，从碰撞数据中剔除并全表复查同类误入。

**⑤ 验收清单**：
- [ ] 碰撞/逻辑数据零装饰条目
- [ ] 落点断言在生成环节生效且有拦截记录机制
- [ ] 抽查落点全合规

**⑥ 禁忌与易错点**：装饰进碰撞会以「看不见的墙」污染玩法；落点压住兵线、河道会毁地图可读性——两条都是断言要拦的。

**⑦ 参数表**：落点断言：距兵线 ≥92 单位；河面落点 = 0（实测口径）。

#### 【图集重建时机】

**① 目标与适用场景**：预渲染底图在素材任一后到时重建一次，防半成品底图被定格使用。适用于重建成本低的预渲染层；成本高的（整图集重打包）改为批次节点重建并留痕。

**② 前置条件**：底图由构建函数生成（如 buildMapCanvas）；素材到达有登记（总目录更新）。

**③ 操作步骤**：
1. 每有新素材落盘 → 重跑底图构建函数重建底图 → 判定以内容指纹为准：底图产物记录其构建时的素材清单哈希，上线前核对该哈希与当前素材清单哈希一致（时间戳只作辅助——文件被触摸、时区变化都会让时间戳说谎）→ 判定信号：哈希一致且底图产物时间戳晚于最新素材落盘时间。
2. 上线前核对 → 动作：比对底图内元素与当前素材清单 → 判定信号：无缺失元素（后到素材都在图里）。

**④ 失败分支**：
- 现象：线上底图缺半套装饰 → 原因：先渲染的版本被定格、后到素材没触发重建 → 处置：立即重建并把「素材落盘→触发重建」挂进收割流程，不靠人记。

**⑤ 验收清单**：
- [ ] 底图时间戳 ≥ 最新素材落盘时间
- [ ] 底图元素与素材清单核对无缺失

**⑥ 禁忌与易错点**：预渲染产物不会自动包含后到素材；不定下重建时机，线上跑的就可能是缺了半套装饰的旧底图，而且无人察觉。

**⑦ 参数表**：实测参数：无专用数值——本条以时机纪律为主，步骤为通用规程。

#### 【小兵变体取模】

**① 目标与适用场景**：小兵造型变体按 ID 取模分配，零逻辑风险换观感丰富度。仅适用于小兵；英雄单位不适用（英雄造型必须唯一可辨，见【重着色造独立角色】）。

**② 前置条件**：有 ≥2 种小兵造型素材；单位有稳定 ID。

**③ 操作步骤**：
1. 生成时按 u.id % 3 在三种造型间取模分配 → 判定信号：同 ID 在各端分配结果一致（取模天然确定性，无需额外同步）。
2. 生成逻辑与数值零改动 → 判定信号：变体只影响造型字段，数值表未动（diff 核对）。

**④ 失败分支**：
- 现象：变体分布明显不均 → 原因：ID 分配本身偏斜 → 处置：先查 ID 生成规律，不急着改取模基数。

**⑤ 验收清单**：
- [ ] 取模分配各端一致
- [ ] 数值与生成逻辑 diff 为零改动
- [ ] 英雄单位未被取模变体

**⑥ 禁忌与易错点**：变体数与取模基数随素材量调整；把英雄也取模换造型会毁掉辨识度，是本条的红线误用。

**⑦ 参数表**：取模基数：3（u.id % 3，三种造型，实测口径）。

## 性能剖析与渲染优化（13 条）

#### 【不猜设备、全设备最低档起步】

**① 目标与适用场景**：画质档位不靠设备指纹猜测，全设备最低档起步、按实测帧率自适应升降。适用于 Web 游戏的画质策略总纲。

**② 前置条件**：画质档位表已定义最低档参数；自动升降档规则就位（见【自动画质迟滞重写】）；起步档受创建期参数约束（见【MSAA 是创建期参数】）。

**③ 操作步骤**：
1. 废弃设备猜测逻辑 → 依据：靠 UA/deviceMemory/线程数猜弱设备会大面积误判——Firefox/Safari 不暴露 deviceMemory（默认按高值）、老核显多线程设备全被判「非弱」，照样高档起步卡死 → 判定信号：代码中无按设备指纹定起步档的路径。
2. 全设备一律最低档起步 → 参数：像素比 0.7、无阴影、MSAA 关（创建时 false）→ 判定信号：任意设备首进游戏均为最低档（用帧率仪表核对，见【给用户留报数仪表】）。
3. 按实测帧率升降档 → 判定信号：强设备在数秒内逐步升档、弱设备稳在低档不卡死。

**④ 失败分支**：
- 现象：强设备迟迟不升档 → 原因：升档阈值不可达 → 处置：转【自动画质迟滞重写】核查阈值物理可达性，不回头恢复设备猜测。

**⑤ 验收清单**：
- [ ] 无设备指纹定档代码路径
- [ ] 多种浏览器（含不暴露 deviceMemory 的）首进均为最低档
- [ ] 升降档按帧率规则工作（仪表可见档位变化）

**⑥ 禁忌与易错点**：设备指纹是启发式猜测，帧率是事实；用事实驱动档位，误判率归零，代价只是强设备晚几秒升到高档——这笔账永远划算。

**⑦ 参数表**：起步档：像素比 0.7 / 阴影 关 / MSAA 关；误判样本：Firefox、Safari 不暴露 deviceMemory。

#### 【性能根因·渲染三件套】

**① 目标与适用场景**：射击类 Web 游戏渲染卡顿的三个元凶成套处置：阴影每帧全量重绘、贴图总量数百 MB、画质起步过高。适用于渲染侧卡顿的首轮攻坚（先按【先剖析后动手】量过指标再动）。

**② 前置条件**：perf_probe 指标已量到三件套的量级（见【先剖析后动手】）；场景光源与地图基本静止（阴影隔帧的前提）。

**③ 操作步骤**：
1. 阴影：太阳与地图静止时设 shadowMap.autoUpdate=false，按档隔帧刷新 → 实测（本项目档位样本）：1024 档 30Hz 刷新肉眼无差；参数变更时强制刷一次 → 判定信号：静止场景阴影无闪烁、帧耗时下降。
2. 贴图：总量先量后压 → 实测（统计范围：本射击项目全量贴图、解码后口径）：95–98 张贴图解码后约 304MB（其中 9 套 PBR 三通道 1024²、单张含 mipmap 约 5.36MB——算法：1024×1024×4 字节 = 4MiB，加完整 mipmap 链 ×4/3 ≈ 5.33MiB，即约 5.36MB 量级，记录时须注明 MiB/MB 单位口径）；按档封顶，弱设备地表贴图降最长边（实测降至 512 量级）→ 地表贴图可由约 190MB 压到约 13MB 量级，整包（统计范围：本项目部署整包）318.6MB → 112.9MB → 判定信号：贴图内存估算与整包体积有前后对照数字且各带统计范围。
3. 起步档：全设备最低档起步（见上条）→ 判定信号：同上条验收。

**④ 失败分支**：
- 现象：隔帧阴影在动态光源场景闪烁 → 原因：前提不成立（光源/遮挡物在动）→ 处置：该场景退出隔帧策略，回到每帧刷新，不许硬扛。

**⑤ 验收清单**：
- [ ] 阴影刷新策略按档生效且静止场景无闪烁
- [ ] 贴图内存有前后对照（对照实测 304MB 总量、整包 318.6→112.9MB）
- [ ] 起步档全设备一致为最低档

**⑥ 禁忌与易错点**：渲染卡顿很少是单一原因，只治一件套往往看不到效果就误判方向；贴图「文件不大」不等于「显存不大」——解码后体积才是账。

**⑦ 参数表**：贴图总量：95–98 张、解码后约 304MB（本项目全量贴图口径）；单张 PBR 贴图（1024² 三通道含 mipmap）约 5.36MB（= 4MiB × 4/3 ≈ 5.33MiB 量级，单位口径见正文）；弱设备地表贴图：约 190MB → 约 13MB（降最长边至 512 量级）；整包：318.6MB → 112.9MB；阴影：1024 档隔帧 30Hz 刷新。

#### 【装饰合并降 draw call】

**① 目标与适用场景**：同类装饰物逐件成网的 draw call 治理：按类合并，只动渲染不动碰撞。适用于静态装饰密集的场景；会被单独隐藏/替换的装饰先排除（见【合并排除动态对象】）。

**② 前置条件**：装饰已按类清点；碰撞数据与渲染数据分离存储（合并后碰撞按原位置一一对应保留）。

**③ 操作步骤**：
1. 逐类清点件数 → 实测样本：茶垄 52 个网格、墙外远景树 78、远山 11，合计 141。
2. 逐类合并 → 分组键写明：按「材质 × 空间分区」分组，合并后组数由材质数与分区数决定（52→2 等是本项目的材质/分区构成结果，不是目标数，换场景按分组键重算、不许照搬数字）→ 实测结果：52→2、78→3、11→2，合计 141→7 → 判定信号：网格计数与合并记录一致。
3. 全场核账（两个三角形口径分栏记，不许混）：**全场三角形总量**——合并只减调用不减几何，前后应基本不变，大变说明合错了；**单视角三角形**（如出生点机位视锥内）——合并改变剔除粒度后可以明显变化，实测出生点 −28% 属于此口径，与全场总量不矛盾 → 实测：场景总网格 517→383；draw call −18%（测量条件：出生点固定机位、稳态帧统计，换机位数字不可比，记录时必须带机位）；出生点视角三角形 −28%（视角口径）→ 判定信号：两栏各有数字且口径标注齐全；等价性另查：合并前后同机位截图差分无可见差异、逐组顶点数与包围盒（AABB）对得上——只看三角形总数会放过几何错位。
4. 碰撞复验 → 动作：按原位置逐类抽验碰撞仍在，每类至少抽 3 个位置（规程量级）做通行/遮挡实测 → 判定信号：抽验位置与结果有记录，行为与合并前一致。

**④ 失败分支**：
- 现象：合并后某装饰需要单独隐藏 → 原因：该件本属动态对象被误并 → 处置：把该类拆回并补进排除清单（见【合并排除动态对象】）。

**⑤ 验收清单**：
- [ ] 逐类合并前后网格数有记录（对照实测 141→7）
- [ ] 全场 draw call 有下降数据（对照实测 −18%）
- [ ] 碰撞按原位置保留且抽验通过
- [ ] 三角形双口径分栏核对：全场总量无异常变化、视角口径变化有记录

**⑥ 禁忌与易错点**：每件装饰一个 draw call 时，几百件装饰的提交开销比它们的像素还贵；合并前逐类清点、动态对象另行处理，顺序不可反。

**⑦ 参数表**：实测：茶垄 52→2 / 远景树 78→3 / 远山 11→2（合计 141→7，分组键 = 材质 × 空间分区）；场景网格 517→383；draw call −18%（出生点机位口径）；三角形：全场总量基本不变 / 出生点视角 −28%（两口径分栏）。

#### 【特效池化】

**① 目标与适用场景**：粒子与曳光用定长缓冲对象池复用，消除高频特效的新建/销毁 GC 尖峰。适用于射击类高频特效；低频一次性大特效（爆炸主特效）不入池。

**② 前置条件**：特效上限已定（见【特效封顶】，池容量按上限设定）；能改特效的创建/回收路径。

**③ 操作步骤**：
1. 定位分配热点 → 判据：每次开火/命中新建 BufferGeometry + 材质、死亡即 dispose → 判定信号：帧率曲线上有与开火节奏同步的周期性尖峰。
2. 粒子改定长缓冲 + 速度池 → 实测形态：160 点定长缓冲 → 判定信号：开火路径无新建几何/材质（代码核查 + 分配探针）。
3. 曳光预分配线段回池复用 → 判定信号：曳光创建路径同样零新建。
4. 池化对象关 frustumCulled → 原因：防粒子扩散超出初始包围球被整组误裁 → 判定信号：大范围扩散的特效不整组消失。

**④ 失败分支**：
- 现象：池化后特效偶发整组消失 → 原因：frustumCulled 未关、包围球误裁 → 处置：先查此项，不要怀疑池逻辑。

**⑤ 验收清单**：
- [ ] 开火/命中热路径零新建几何与材质
- [ ] 池化对象 frustumCulled 已关
- [ ] 帧率曲线周期性尖峰消失或明显收敛

**⑥ 禁忌与易错点**：池化只治分配抖动，不改特效上限（上限归【特效封顶】管）；把低频大特效也入池是浪费内存。

**⑦ 参数表**：粒子池：160 点定长缓冲 + 速度池（速度池容量与粒子池同容量）；池满语义：粒子池满时环形覆盖最旧点、曳光池满时丢最旧（与【特效封顶】的超限策略一致），不许池满后静默丢新特效而不留痕——覆盖/丢弃计数可查；池化对象 frustumCulled = 关。

#### 【先剖析后动手】

**① 目标与适用场景**：性能轮的标准开局：先建探针量指标，再动手优化，前后 JSON 对照。适用于一切性能攻坚轮次。

**② 前置条件**：有可重复进入的同机同场景测试路径；探针代码与正式包隔离（探针不进正式包）。

**③ 操作步骤**：
1. 建 perf_probe 量六项指标：draw call、三角形、纹理、阴影、逻辑耗时、加载 → 每项同时记平均值与 P95/最大值（只记平均会漏尖峰）；JSON 须带元信息：场景名、采样时长、设备/浏览器 → 判定信号：六项都有双口径数值与元信息输出。
2. 优化前跑一份 JSON 存档 → 判定信号：基线文件在案。
3. 优化后同机同场景再跑一份 → 判定信号：两份 JSON 可逐项对照，差异即本轮收益。
4. 指标口径中途不换 → 判定信号：前后两份的量法一致（换口径等于作废对照）。

**④ 失败分支**：
- 现象：优化后指标变好但体感没变 → 处置：先查量错了指标（量的是平均值、卡的是尖峰），补尖峰/分位指标再判，不许拿 JSON 数字压体感反馈。

**⑤ 验收清单**：
- [ ] 六项指标前后两份 JSON 齐全
- [ ] 每项优化的收益能在对照中指认
- [ ] 探针未进入正式包

**⑥ 禁忌与易错点**：凭感觉砍性能，砍掉的常是无辜项、真凶纹丝不动；函数级定位同理——先用计时探针找到头号耗时（如逐点碰撞检测的累计耗时占比）再动手。

**⑦ 参数表**：探针指标：draw call / 三角形 / 纹理 / 阴影 / 逻辑耗时 / 加载，共 6 项；对照方式：同机同场景前后 JSON。

#### 【静态 Box 几何合并】

**① 目标与适用场景**：数百个独立 Box 网格的 draw call 治理：按组烘焙合并且保留视锥剔除粒度。适用于静态 Box 密集的场景。

**② 前置条件**：排除清单已列（见【合并排除动态对象】）；碰撞体与雷达矩形是独立数据，不受合并影响——确认方法：代码中检索碰撞/雷达数据的来源，确认其不引用被合并网格的几何（检索记录留存），确认完再动手。

**③ 操作步骤**：
1. 分组：按「材质 × 16×16 米扇区 × 阴影标志」分组 → 判定信号：每组键三要素齐全。
2. 把世界矩阵烘焙进几何后逐组合并 → 实测：185 个 Box → 76 个网格 → 判定信号：网格计数达标。
3. 核账 → 硬验收是逐组对照表，不是只看三角形总数（丢一个 Box 又重复另一个，总数照样相等）：逐组核对顶点数 / 索引数 / AABB / 材质键，分组键须覆盖材质、透明度、renderOrder、castShadow 与 receiveShadow（阴影是两个独立标志，不是一个布尔）五维；三角形总数相等只是其中一项 → 实测：出生点 draw call 376→293 → 判定信号：逐组对照全等、三角形差 = 0；另加合并前后同机位截图差分无可见差异。烘焙规则同时写明：法线用正规矩阵（模型矩阵的逆转置）变换、不许直接乘模型矩阵；负缩放镜像须翻转面绕序；索引超 16 位上限的组用 32 位索引。
4. 视锥剔除验证 → 动作：在固定测试机位（出生点、朝向场景一角、固定 FOV，机位参数写进记录）量 draw call，并与全景机位对照 → 判定信号：局部机位 draw call 明显低于全景且落在按扇区数估算的预期区间内（区间与实测都记录）；全场合一网格则此项必挂。

**④ 失败分支**：
- 现象：合并后看一角仍画全场 → 原因：分组太粗/合成了单网格 → 处置：按扇区重新分组，不许以「合并了」交差。

**⑤ 验收清单**：
- [ ] 网格数有前后对照（对照实测 185→76）
- [ ] 三角形总数差 = 0
- [ ] draw call 有下降（对照实测 376→293）
- [ ] 视锥剔除粒度保留（局部视角 draw call 随视角下降）

**⑥ 禁忌与易错点**：全场合成一个网格会让视锥剔除失效——分组（扇区）是本条的灵魂，省了分组，合并就是负优化。

**⑦ 参数表**：分组键：材质 × 16×16m 扇区 × 阴影标志；实测：185 Box → 76 网格；出生点 draw call 376 → 293；三角形差：0。

#### 【合并排除动态对象】

**① 目标与适用场景**：静态合并前先列排除清单，保护动态对象的单独显隐与变换能力。适用于一切静态几何合并（与【静态 Box 几何合并】【装饰合并降 draw call】配套，顺序是先排除、再合并）。

**② 前置条件**：能盘点场景中全部对象的动态属性。

**③ 操作步骤**：
1. 逐类过排除判据 → 排除四类：会被异步隐藏/替换的装饰、相机子级（视图模型）、蒙皮网格、实例化网格 → 判定信号：排除清单成文。
2. 合并范围 = 全集 − 排除清单 → 判定信号：合并脚本/流程按清单取范围，不靠记忆。
3. 确认独立数据不受影响：碰撞体与雷达矩形是独立数据 → 判定信号：合并后碰撞与雷达行为复验通过。

**④ 失败分支**：
- 现象：合并后某对象显隐失效或变换异常 → 原因：该对象本属排除类被误并 → 处置：将其拆出恢复独立网格，并补进排除清单防再犯。

**⑤ 验收清单**：
- [ ] 排除清单成文且四类齐全
- [ ] 合并范围严格按清单
- [ ] 合并后动态对象行为复验通过

**⑥ 禁忌与易错点**：并入静态几何的对象就失去单独显隐与替换能力，异步逻辑再操作它只会出错或无效；视图模型与蒙皮网格的变换方式与静态烘焙根本不兼容。

**⑦ 参数表**：排除类别：异步显隐装饰 / 相机子级 / 蒙皮网格 / 实例化网格，共 4 类。实测参数：无专用数值——本条以清单核对为主，步骤为通用规程。

#### 【阴影滤波分档】

**① 目标与适用场景**：阴影滤波质量按档位分，只在最高档买软阴影。适用于多档画质体系。

**② 前置条件**：画质档位表已定义各档阴影分辨率（本条 2048 最高档为本项目档位表口径；【性能根因·渲染三件套】的 1024 档刷新样本出自另一项目的档位体系，两者是不同项目的样本、不互为矛盾，引用时须带项目口径）；与阴影刷新策略配套（见【性能根因·渲染三件套】）；目检用固定测试场景（出生点＋阴影密集区，截图留存后逐档比）。

**③ 操作步骤**：
1. 档位映射：最高档（2048）用 PCFSoft，其余档用 PCF → 判定信号：档位表中滤波类型逐档写明。
2. 材质刷新只在切换档位时做 → 判定信号：逐帧路径中无滤波切换动作（代码核查）。
3. 档位切换点防抖 → 与升降档迟滞规则配套（见【自动画质迟滞重写】）→ 判定信号：临界帧率下滤波类型不反复横跳。

**④ 失败分支**：
- 现象：中低档阴影边缘明显劣化被投诉 → 处置：先查分辨率档是否过低，不直接给中低档开 PCFSoft（那是把每帧成本买回来）。

**⑤ 验收清单**：
- [ ] 滤波类型逐档与映射表一致
- [ ] 滤波切换只发生在切档时
- [ ] 各档阴影在固定测试场景目检可接受（截图留存）

**⑥ 禁忌与易错点**：软阴影的滤波成本每帧都在付，而中低档分辨率下 PCFSoft 与 PCF 肉眼难分——在低档买软阴影是纯浪费。

**⑦ 参数表**：滤波映射：2048 档 = PCFSoft；其余档 = PCF；刷新时机：仅切档时。

#### 【投射体瘦身】

**① 目标与适用场景**：关掉影子不可见的小物件的 castShadow，降阴影图渲染成本，保留接收阴影。适用于场景中有大量低矮小物件时。

**② 前置条件**：能逐类盘点投射体并按「影子可见性」判判据；角色、大型掩体等观感主体的投射不可关（先划出保护名单）。

**③ 操作步骤**：
1. 逐类判：影子不可见或不重要的 → 关 castShadow、保留 receiveShadow → 「不可见」的判定要过视角矩阵：正午与低角度光照两个时段 × 常用观察视角逐类各查一遍（低角度时影子拉长，低矮物的影子也可能变得重要），全矩阵都不可见/不重要才许关 → 实测样本：52 丛 0.78m 高的低矮色块丛（0.78m 是本项目样本值、不是普适高度阈值）。
2. 核账 → 实测：castShadow 网格 276→224（−19%）→ 判定信号：关闭数与清单一致。
3. 目检复核 → 判定信号：画面中被关物件的受影效果仍在（receiveShadow 保留），无明显观感损失。

**④ 失败分支**：
- 现象：关后某物件在画面里「浮」起来 → 原因：其影子其实承担落地感 → 处置：单独恢复该类 castShadow 并移出关闭清单，记录判据修正。

**⑤ 验收清单**：
- [ ] 关闭清单与判据成文（对照实测 52 丛样本）
- [ ] castShadow 网格数有前后对照（对照实测 276→224）
- [ ] receiveShadow 全部保留、目检无感损失

**⑥ 禁忌与易错点**：阴影图成本按投射体数量走；判据是「影子不可见或不重要」，不是「物件小」——小而醒目的物件影子照样重要。

**⑦ 参数表**：实测：castShadow 网格 276 → 224（−19%）；样本：52 丛 0.78m 高低矮丛状物；receiveShadow：保留不动。

#### 【自动画质迟滞重写】

**① 目标与适用场景**：自动画质升降档规则的设计：降档要快、升档要慢，且阈值必须物理可达。适用于帧率自适应画质系统。

**② 前置条件**：有 1s 窗口的帧耗时统计；帧耗时口径先定死：本条用 **rAF 回调间隔（呈现间隔）**——它与渲染工作耗时是两个量，阈值只对本口径成立，改测工作耗时必须整套换阈值；已知目标显示器刷新率（阈值按刷新率重算，公式见参数表）。窗口状态机：不重叠的连续 1s 窗口，切档后当前窗口统计清零、升档连续计数重置。

**③ 操作步骤**：
1. 降档规则：1s 窗口均帧 >40ms 立即降档；>66ms 降两档；取消降档冷却 → 判定信号：人为制造卡顿后一窗内档位下降。
2. 升档规则：连续 5 个窗口均帧 <20ms 才升一档 → 判定信号：帧率恢复后约 5 秒量级才升一档，无横跳。
3. 阈值可达性自检（硬验收）：逐个阈值对照刷新间隔验算 → 订正表述：16.7ms 是 60Hz 下 rAF 呈现间隔的下限（不是渲染工作耗时的下限——工作耗时可以小于它）；在本条的 rAF 间隔口径下，升档阈值必须大于刷新间隔才可达 → 实测反例：旧规则要求 3 窗口 <11.5ms 才升档，而 60Hz 呈现间隔下限 16.7ms，该阈值物理不可达 = 永不升档 → 判定信号：每个阈值都大于刷新间隔且留有余量。另补长尾约束：均值会掩盖尖峰，窗口内 P95 帧间隔超降档阈值时同样触发降档判定（均值与 P95 双轨，P95 为方法补注、阈值同降档线）。

**④ 失败分支**：
- 现象：档位在临界点反复横跳 → 原因：升档太快或窗口太短 → 处置：拉长升档连续窗口数，不动降档规则（降档慢了玩家正在卡）。

**⑤ 验收清单**：
- [ ] 降档/升档规则与参数表逐项一致
- [ ] 全部阈值通过物理可达性验算
- [ ] 卡顿注入测试下降档及时、恢复后升档平稳无横跳

**⑥ 禁忌与易错点**：阈值不可达的规则比没有规则更坏——它让所有人以为自适应在工作；写规则时先算单帧下限，再写数字。

**⑦ 参数表**：帧指标：rAF 回调间隔（呈现间隔口径）；窗口：1s 不重叠，切档清零；降档：均帧 >40ms 降一档、>66ms 降两档、无冷却（P95 同线触发）；升档：连续 5 窗口 <20ms 升一档；高刷换算（由 60Hz 实测值反推的比例公式，示意）：降档阈值 ≈ 2.4 × 刷新间隔、升档阈值 ≈ 1.2 × 刷新间隔，换屏后按公式重算再实测标定；反例阈值：11.5ms（60Hz 呈现间隔口径下不可达，下限 16.7ms）。

#### 【MSAA 是创建期参数】

**① 目标与适用场景**：识别渲染器创建期参数（antialias 等），不把它们写进运行时档位表做假开关。适用于画质档位表设计。

**② 前置条件**：能区分创建期参数与运行时可改参数（antialias、powerPreference 等属创建期）。

**③ 操作步骤**：
1. 「起步即关 MSAA」的唯一实现：创建渲染器时对全设备设 antialias=false → 判定信号：创建代码中该参数为 false，无运行时切换路径。
2. 代价明示：手动调到高档也无 MSAA，清晰度靠升像素比找回 → 判定信号：档位表说明中写明此代价，验收不以「高档没抗锯齿」报缺陷。
3. 档位表只放真正运行时可改的项；创建期项单独成「起步策略」一节 → 判定信号：逐项核对档位表无创建期参数混入。

**④ 失败分支**：
- 现象：档位表里有开关但切换无任何效果 → 原因：该项是创建期参数 → 处置：按第 3 步移出档位表，不许留假设置。

**⑤ 验收清单**：
- [ ] 档位表逐项核对：全部为运行时可改项
- [ ] 创建期参数集中在起步策略且代价明示
- [ ] 无「存在但不生效」的设置项

**⑥ 禁忌与易错点**：设置项存在、行为不变，是最难自查的假功能——它不会报错，只会让所有人以为调过档了。

**⑦ 参数表**：创建期参数示例：antialias、powerPreference；起步策略：antialias = false（全设备）；代价补偿：升像素比。实测参数：无专用数值——本条以参数分类核对为主，步骤为通用规程。

#### 【特效封顶】

**① 目标与适用场景**：只增不减的特效集合设上限，超限丢最旧，把最坏情况钉死在可承受范围内。适用于粒子、曳光等集合型特效；与【特效池化】配套（池管分配、顶管总量）。

**② 前置条件**：已知正常对局的特效样本量分布；上限的定标方法写明：上限 = 正常对局样本量的高分位（P99 量级）× 安全系数（示意 1.5–2 倍，标定后登记），且必须低于压测定出的雪崩点——本条 48 组 / 30 条是按此法在本项目定标的结果，换项目重定标、不许照搬。

**③ 操作步骤**：
1. 设上限 → 实测口径：粒子上限 48 组、曳光上限 30 条 → 判定信号：上限值写入配置。
2. 超限策略：丢最旧并 dispose → 判定信号：压测叠加到超限时，集合长度恒定、旧对象被正确释放（无泄漏）。
3. 无感验证 → 动作：正常对局回放/实测中观察 → 判定信号：正常样本量远低于上限，玩家无感。

**④ 失败分支**：
- 现象：正常对局频繁触顶 → 原因：上限按旧样本定、玩法已变 → 处置：按新样本分布重定上限，不许直接摘掉封顶。

**⑤ 验收清单**：
- [ ] 上限值与配置一致（对照实测 48 组 / 30 条）
- [ ] 超限压测下集合长度恒定且无泄漏
- [ ] 正常对局不触顶

**⑥ 禁忌与易错点**：无界增长平时不暴露，多人混战叠满就是雪崩帧；封顶不是限制表现，是给最坏情况定价。

**⑦ 参数表**：粒子上限：48 组；曳光上限：30 条；超限策略：丢最旧 + dispose（实测口径）。

#### 【性能根因·寻路全量扫】

**① 目标与适用场景**：寻路碰撞检测逐点全量扫全部碰撞体是逻辑耗时大头，用空间网格宽相治理，且必须过等价性硬验收才许上线。适用于静态碰撞体密集的寻路/碰撞检测。

**② 前置条件**：已用函数级计时探针定位头号耗时（判据形态：单函数被调用数十万次、累计耗时占逻辑大头）；碰撞体集合以静态为主；已从生产代码中登记本项目实际使用的 pad 取值集合（见步骤 3 的 pad 分档来源）；等价性测试的点集文件位置与差异报告格式已约定。

**③ 操作步骤**：
1. 建空间网格宽相：4m 格；碰撞体按 AABB + 最大 pad（记 P_max，取生产 pad 集合的最大值）展开登记到所覆格；格键用数字编码，不用字符串 → 判定信号：登记后每格只含邻近碰撞体。
2. 检测改走宽相并守候选召回条件：查询必须检索「以查询点为中心、按本次查询 pad 展开的区域所覆的全部格」，再在候选集内做原精确判定 → **候选完备条件（硬约束）：检索格半径 r = ceil(P_max ÷ 格尺寸)；本项目格尺寸 4m 且 P_max ≤ 4m，故 r = 1（所在格＋8 邻格）即完备；若某项目 P_max > 格尺寸，r 必须按公式放大，不许照搬九宫格** → 判定信号：代码中的检索半径与登记的 P_max、格尺寸满足公式关系（逐项可核）。
3. 等价性校验（硬验收，不许跳）——按下列可复现规格造点集、逐点比对，规格四要素缺一不可：
   - **种子与点集存档**：用固定种子的伪随机生成器生成点集，种子写进点集文件头；点集文件本身存档入库，复验时直接读文件、不重新生成（换种子 = 换一套题，旧结论作废须重验）。
   - **分层采样（两层分开配额、分开统计）**：总量 60,000 点分两层——均匀层：全图范围内均匀随机撒点，覆盖常规区域；边界层：按碰撞体逐个生成近界点（见下），专测登记边界行为。两层配额在本轮开始前按碰撞体数量与地图面积标定并写入点集文件头（配额比例为标定值，示意形态：均匀层约 2/3、边界层约 1/3）；**边界层必须单列的原因：均匀随机命中几何边界（零测度集合）的概率为零，靠均匀层永远测不到登记展开的边界行为——这正是宽相最容易漏登记的地方**。
   - **边界层生成规则**：逐个碰撞体，在其 AABB 四边与四角的法向偏移点上取样，偏移集合 = {−P_max、−ε、0、+ε、+P_max}（负 = 体内侧、正 = 体外侧，ε 取浮点可分辨小量、量级示意 1e-4m，须在本轮标定后登记），即每个碰撞体覆盖「体内—恰在界上—体外」与「pad 展开边界」两类临界位置；每碰撞体的近界点数下限在本轮标定（示意：每体不少于 8 点），不许只挑几个大碰撞体取样。
   - **pad 三档的取值来源**：三档不许自拟——从生产检测调用实际传入的 pad 参数中取最小、典型、最大三档，逐档登记数值与出处（调用点/配置项）；每个测试点都标注其所属 pad 档，三档各测满本层配额。
   - 逐点比对与差异报告：同一点集分别跑宽相版与原全量扫，逐点比结果；差异报告每行字段 = 点坐标 / 所属层 / pad 档 / 旧结果 / 新结果 / 最近碰撞体 / 所在格键 / 检索到的候选格集合 → 判定信号：**差异 = 0 才许上线**，且差异计数按层、按 pad 档分别给出（边界层差异单独成列，不许被均匀层的零差异稀释）。
   - **结论边界（必须随验收记录一同写明）**：「差异 = 0」只证明**在本已存档点集（含边界层）覆盖的样本内**新旧等价，不是「对所有点等价」的数学证明；未被点集覆盖的构型（如新形状碰撞体、pad 超出登记集合）出现时，必须扩点集重验后才许沿用结论。
4. 耗时对照（在同一点集上测）：用等价性点集作为固定工作负载跑新旧两版总耗时，预热后取多次运行中位数，并记录机器/浏览器/点数/pad 分布 → 实测样本：pointBlocked 总耗时 1,275ms → 405ms（−68%，本项目点集与机器口径）；对照警戒：格键用字符串的实现只到 849ms，键编码方式本身就是性能项 → 判定信号：耗时报告带工作负载定义，他人能按同点集复跑。

**④ 失败分支**：
- 现象：等价性校验出现差异点 → 原因：碰撞体展开登记漏格（pad 取小）或格键冲突或检索半径不足 → 处置：按差异报告字段定位（先看该点 pad 档与候选格集合），修登记/检索逻辑后**全量重验**，不许只修差异点附近、不许删差异点。
- 现象：优化后耗时只降到字符串键版的量级 → 处置：查格键编码，改数字键。

**⑤ 验收清单**：
- [ ] 点集文件存档：种子、两层配额、三档 pad 数值及出处、边界层生成规则齐全可复跑
- [ ] 60,000 点等价性比对差异 = 0，且按层/按 pad 档分别计数（记录留存，含结论边界声明）

- [ ] 总耗时有同工作负载前后对照（对照实测 1,275→405ms、−68%，注明点集与机器口径）
- [ ] 格键为数字编码

**⑥ 禁忌与易错点**：空间索引最容易出「漏登记、错格」的边界 bug——没有零分歧验证的宽相优化，就是用正确性换速度；均匀随机点「含边缘」是自欺，边缘必须靠边界层构造出来；格尺寸（4m）按检测半径与物体密度调，不是常数；把有限样本的零差异说成普遍等价，是验收口径上的越界。

**⑦ 参数表**：碰撞体总量：177 个（实测，本项目样本）；格尺寸：4m；登记展开：AABB + P_max（P_max = 生产 pad 集合最大值，逐项目登记）；检索半径：r = ceil(P_max ÷ 格尺寸)，本项目 = 1（九宫格，前提 P_max ≤ 格尺寸）；等价性样本：60,000 点（均匀层＋边界层分层，配额标定后登记；种子固定、点集存档）；边界偏移集合：{−P_max、−ε、0、+ε、+P_max}（ε 为标定小量，示意 1e-4m 量级）；pad 档位：3 档，取自生产调用实际值（最小/典型/最大，逐档登记数值与出处）；pointBlocked 总耗：1,275ms → 405ms（−68%，本项目点集口径）；字符串键劣化版：849ms。

1. 缓存元素引用：初始化时把 HUD 元素引用存下，更新路径不再 querySelectorAll → 判定信号：热路径无 querySelectorAll 调用。
2. 值未变不写：每处写入前比对旧值，未变跳过 → 实测规模：原每 tick 全量写约 20 处 DOM → 判定信号：静态画面下每 tick 实际写入数 ≈ 0。
3. 量收益并如实汇报 → 实测：updateHUD 单次 32.1µs → 20.4µs（−36%）→ 判定信号：组件级数字有前后对照；整步级收益被 AI/物理方差淹没时，汇报如实说明「组件级成立、整步级未显」，不夸大成整体提速。

**④ 失败分支**：
- 现象：守卫后某 HUD 值不刷新 → 原因：比较用了引用相等而值是新对象 → 处置：该处改值比较或退出守卫，不许为守卫牺牲正确性。

**⑤ 验收清单**：
- [ ] 热路径无 querySelectorAll、无无条件全量写
- [ ] 单次耗时有前后对照（对照实测 32.1→20.4µs）
- [ ] 汇报口径区分组件级与整步级
- [ ] HUD 各项显示正确性复验通过

**⑥ 禁忌与易错点**：DOM 写入的成本不在单次而在频率与强制重排；守卫的收益汇报最容易夸大——组件级数字只能说组件级的话。

**⑦ 参数表**：实测：updateHUD 32.1µs → 20.4µs/次（−36%）；原写入规模：约 20 处 DOM/tick + 1 次 querySelectorAll。

#### 【雷达节流】

**① 目标与适用场景**：低信息更新率的辅助组件（2D 雷达）全量重绘降频。主画面与命中反馈这类即时性组件不可节流。

**② 前置条件**：已确认该组件的信息更新率低（单位位移在小图上亚像素级）；降频定版值要真机肉眼复核。

**③ 操作步骤**：
1. 先降一档试：每 tick 重绘 → 30Hz → 判定信号：肉眼无差、占用下降。
2. 再降一档：30Hz → 20Hz → 实测结论：肉眼无差、恒定占用减半 → 判定信号：真机复核通过后定版 20Hz。
3. 把定版频率写入配置并注明复核结论 → 判定信号：后人不会「顺手」改回每 tick。

**④ 失败分支**：
- 现象：降频后雷达点位明显跳格 → 原因：该组件信息率被低估（高速单位多）→ 处置：回升一档频率再复核，不硬守 20Hz。

**⑤ 验收清单**：
- [ ] 定版频率有真机肉眼复核记录
- [ ] 占用有前后对照：同场景、同单位数、同机位下用探针量节流前后的单帧 CPU 耗时（对照实测：恒定占用减半）；肉眼复核口径：以最高单位速度在雷达上移动、第二人观察有无跳格
- [ ] 即时性组件未被误节流

**⑥ 禁忌与易错点**：节流的判据是信息更新率，不是「看起来不重要」；主画面套此法就是灾难。

**⑦ 参数表**：重绘频率：每 tick → 30Hz → 20Hz（定版，实测口径）；收益：恒定占用减半。

#### 【每帧小额分配治理】

**① 目标与适用场景**：治理热路径上每帧每角色的小额临时分配，积少成多的 GC 压力。低频路径的临时对象可读性优先，不强行复用。

**② 前置条件**：已定位热路径上的临时分配点（形态：每帧给每个角色新建临时对象/临时向量）；改造须保证首帧语义等价。

**③ 操作步骤**：
1. 盘点热路径分配点 → 实测形态：每帧每角色新建 _lp 类临时对象、临时 Vector3 → 判定信号：分配点清单成文。
2. 改对象复用与模块级临时向量 → 约束：复用对象不得跨帧留状态 → 判定信号：改造后行为与改造前一致——验收不止首帧：改造前后各跑一段固定输入回放，逐帧比对多帧状态轨迹（位置、相位等）全程一致，首帧等价证明不了连续帧无串扰。
3. 复验 GC 表现 → 判定信号：帧率曲线上与分配相关的抖动收敛（与【特效池化】是同一病理在逻辑层的形态，验收口径一致）。

**④ 失败分支**：
- 现象：复用后出现状态串扰（A 角色的数据被 B 读到）→ 原因：临时对象里留了跨帧状态 → 处置：该点退出复用、恢复新建，并把「无跨帧状态」复查一遍全部复用点。

**⑤ 验收清单**：
- [ ] 热路径分配点清单与改造一一对应
- [ ] 多帧状态轨迹回放比对通过（固定输入、逐帧一致）
- [ ] 无跨帧状态残留于复用对象

**⑥ 禁忌与易错点**：单个临时对象不值一提，「每帧 × 每角色 × 几十个」的乘积才是稳定的垃圾产生速率；复用最大的坑是把跨帧状态误留在临时对象里。

**⑦ 参数表**：实测参数：无专用数值——本条以分配点盘点与等价核对为主，步骤为通用规程。

#### 【移动子步进积分】

**① 目标与适用场景**：Bot 移动按子步进积分，大 dt 不再瞬移穿墙；步态与步声由实际位移驱动。适用于帧率抖动环境下的移动积分。

**② 前置条件**：移动系统可改积分方式；碰撞判定支持逐步检测。

**③ 操作步骤**：
1. 单步位移按 ≤0.09m 切子步、上限 4 步，逐步积分并逐步判碰撞 → 判定信号：人为制造大 dt（卡帧）时 Bot 不穿薄墙。
2. 步态相位与步声改由实际位移驱动（累计位移推进），不再由时间推 → 判定信号：慢帧下无「脚不动、人滑行」，步声与落步对齐。

**④ 失败分支**：
- 现象：超大 dt 时仍欠步穿墙 → 原因：子步上限 4 步封顶 → 处置：那是帧率已崩的情形，靠降档解决（见【自动画质迟滞重写】），不在积分层硬扛加步数。

**⑤ 验收清单**：
- [ ] 大 dt 注入测试不穿墙
- [ ] 步态/步声与实际位移对齐（慢帧抽查）
- [ ] 子步参数与配置一致（≤0.09m、上限 4 步）

**⑥ 禁忌与易错点**：帧率抖动时 dt 变大，一步跨过薄墙就是穿墙；子步进把位移粒度钉死在碰撞可判的尺度内——但别把子步上限当万能药，帧率崩了先治帧率。

**⑦ 参数表**：子步长：≤0.09m；子步上限：4 步（实测口径）；单帧可覆盖位移上限 = 4 × 0.09m = 0.36m/帧——适用前提：最薄墙厚 > 单子步 0.09m，且单位最大速度 × 最大 dt 不超过 0.36m，超出此包络须先加步数或治帧率，不许以为子步进万能；步态驱动量：实际位移。

#### 【预热渲染】

**① 目标与适用场景**：消除首帧着色器编译的秒级卡顿：加载后预热编译并预渲染模板一帧。适用于 WebGL 项目的首帧卡顿治理。

**② 前置条件**：已确认卡顿来自着色器编译（判据：首帧与稳态帧耗时差出量级，见步骤 1 的实测形态）。

**③ 操作步骤**：
1. 先量证：实测首帧编译 9,005ms vs 稳态 9ms → 判定信号：差出三个量级即锁定编译问题（本项目中它曾是早期「击杀超时」假象的真因之一）。
2. 加载后做 renderer.compile 预热 → 判定信号：编译动作发生在加载阶段而非对局首帧。
3. 各回退链模板临时实例渲染一帧 → 预热清单的生成法：枚举场景实际引用的全部「材质 × 光照」组合逐项入清单（清单随场景/材质变更同步更新，漏一项就漏一次首现卡顿）；首帧计时口径 = 从首个 rAF 回调到首帧呈现完成 → 动作：按清单把各链模板各实例化渲染一帧后清干净 → 判定信号：预热后场景无残影残留、对局首帧耗时回到稳态量级。

**④ 失败分支**：
- 现象：预热后某材质首次出现仍卡一帧 → 原因：该材质/光照组合未被预热覆盖 → 处置：把该组合补进预热清单，不许以「预热过了」结案。

**⑤ 验收清单**：
- [ ] 首帧与稳态耗时有量测记录（对照实测 9,005ms vs 9ms）
- [ ] 预热覆盖实际用到的材质/光照组合
- [ ] 预热残留清理干净、对局首帧无秒级卡顿

**⑥ 禁忌与易错点**：9 秒级编译卡顿发生在开局时刻，极易被误诊为网络或逻辑问题，排障方向全错——先量首帧/稳态差，再谈其他嫌疑。

**⑦ 参数表**：实测：首帧编译 9,005ms vs 稳态 9ms；预热动作：renderer.compile + 各链模板临时实例渲染 1 帧。

#### 【自动化下禁调速器】

**① 目标与适用场景**：自动画质调速器在自动化（webdriver/autotest）环境禁用，保证测试确定性；调速器参数路径与手动画质共用同一函数，另行探针验证落地。适用于自动化测试体系。

**② 前置条件**：能识别自动化环境（webdriver 标志等）；调速器与手动设置共用参数应用函数（先确认此架构，不是则先改成共用）。

**③ 操作步骤**：
1. 自动化环境下关调速器 → 判定信号：同份测试在不同机器跑出同一画质路径（结果可比、失败可复现）。
2. 共用函数核查 → 动作：确认调速器改档与手动改档走同一参数应用函数 → 判定信号：代码核查两路同函数。
3. 探针验证参数落地 → 动作：用探针改档后读回实际渲染参数 → 判定信号：参数真的生效，验证结论留痕。

**④ 失败分支**：
- 现象：正式包误关调速器 → 处置：禁用条件严格限定自动化环境特征，正式包发布前专项核查此开关状态（列入发布清单）。

**⑤ 验收清单**：
- [ ] 自动化环境下调速器关闭且测试结果可复现
- [ ] 调速器与手动路径共用同一参数函数（代码证）
- [ ] 探针验证参数落地且留痕
- [ ] 正式包调速器为开启状态

**⑥ 禁忌与易错点**：调速器开着时测试结果不可比、失败不可复现；但禁用只针对自动化环境——正式包误关是把本条用反了。

**⑦ 参数表**：实测参数：无专用数值——本条以环境判定与路径核查为主，步骤为通用规程。

#### 【单步尖峰留观】

**① 目标与适用场景**：未定位的偶发尖峰列遗留观察项，带频率与候选成因登记，不冒充已修。适用于低频偶发性能尖峰的处置。

**② 前置条件**：尖峰有可测的出现频率与量级；候选成因可枚举。

**③ 操作步骤**：
1. 登记观察项 → 实测样本：约 68ms 的偶发单步尖峰，900 步约 1 次，成因在回合事件/爆炸/GC 三者间未证实 → 判定信号：条目含频率、量级、候选成因三要素。
2. 后续每轮性能工作重新审视该项 → 判定信号：每轮记录中有对该项的复核痕迹（有新采样就更新频率）。
3. 升级判据：频率上升到影响对局 → 升级为正式缺陷专项定位，不再留观 → 判定信号：升级动作有记录。

**④ 失败分支**：
- 现象：有人把留观项在汇报中写成「已优化」 → 处置：当场更正为留观状态——未定位就报已修，是把未知包装成已知。

**⑤ 验收清单**：
- [ ] 留观条目三要素（频率/量级/候选成因）齐全
- [ ] 每轮性能工作有复核痕迹
- [ ] 汇报中无留观项冒充已修

**⑥ 禁忌与易错点**：留观不是遗忘——必须带频率与影响评估，后续每轮都被重新审视；也不是拖延的挡箭牌，达升级判据必须升级。

**⑦ 参数表**：实测样本：尖峰约 68ms、频率约 1 次/900 步；候选成因：回合事件 / 爆炸 / GC（未证实）。
