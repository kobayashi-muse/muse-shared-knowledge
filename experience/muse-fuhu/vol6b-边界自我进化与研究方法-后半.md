# 卷六 边界、自我进化与研究方法（后半）——操作规程版（整卷重写）

本稿对应卷六后半 124 条。每条固定七段：①目标与适用场景 ②前置条件 ③操作步骤（每步带可观测的判定信号）④失败分支（只写本条专属失败形态）⑤验收清单（只列可打勾的核查动作）⑥禁忌与易错点（只写本条专属）⑦参数表（数值带量纲、证据等级与测法；源材料无数值时给测量/标定规程，不编数）。同一要点只出现一次，后段不复述前段。

**证据标注格式（全卷通用）**：结论写成 `[证据等级｜证据载体｜定位]`。五级：官方文档／代码实证／实测报告／博客经验／推测。定位粒度：官方文档写页名或条款号；代码实证写文件与函数/行段；实测报告写输入、输出、时间；博客经验写链接与段落，只作线索不支撑强结论；推测不写定位、直接标「推测」。

## 研究方法与证据分级（13 条）

### 【转述说法默认未验证】

**①目标与适用场景**：经他人转述的事实性说法（证书日期、绑定记录、账号状态之类）在证据上默认「未验证」。触发场景：任何人转告你一个可实查的事实，你正准备把它写进台账、汇报或后续判断。

**②前置条件**：能指出该说法的实查入口（发证机关公示、系统后台记录、证书原件照片，任一即可）；没有实查入口的转述不适用本条，改按【无权威来源列未核实】处理。

**③操作步骤**：
1. 把转述原话逐字记下，标注转述人与时间 → 判定信号：记录里能找到原话与出处，不是你的复述版。
2. 走实查入口核对 → 判定信号：拿到一手记录（页面、原件、后台条目），且关键字段（日期、状态、编号）逐项可比对。
3. 一致 → 在记录上把状态从「未验证」改为「已实查」，注明实查来源；不一致 → 当轮发出纠正，写明转述值、实查值、受影响的后续工作 → 判定信号：纠正消息在发现错误的同一轮次内已发出，不是攒到下轮。

**④失败分支**：
- 实查入口临时不可用（系统维护、权限未到）：说法保持「未验证」标记挂账，写明待查入口与下次触发条件，不先行采信。
- 转述人坚持其说法与实查冲突：以一手记录为准，把冲突双方并列留痕，不私下改记录迁就任何一方。

**⑤验收清单**：
- [ ] 每条被采用的转述说法都有一手实查记录可回指
- [ ] 查出误差的转述已在当轮发出纠正，含转述值与实查值两列
- [ ] 未能实查的说法仍带「未验证」标记，未混入已证事实

**⑥禁忌与易错点**：不要因为转述人可靠就跳过实查——实测中证书有效期、绑定状态都出过转述误差，与转述人无关，是转述环节本身的损耗。

**⑦参数表**：无数值参数。判线：可实查对象（证书日期／绑定记录／账号状态等）一律先查后用；纠正时点＝发现当轮。

### 【政策原文找不到的替代核法】

**①目标与适用场景**：地方性办法原文经多轮、多渠道搜索仍拿不到，但现行口径必须核对时，用上位文件替代核对。触发场景：目标文件在官网、政策库、搜索引擎均无原文，而工作不能停。

**②前置条件**：已穷尽常规渠道并留有搜索记录（见【取证路线记失败形态】）；能确定该地方办法的上位文件（上级部门或中央同主题文件）且其原文可得。

**③操作步骤**：
1. 取上位文件原文，定位与现行口径对应的条款 → 判定信号：条款原文已摘录留存，不是转述。
2. 按构成要件与数字比对，不按措辞比对：把现行口径拆成要件（适用对象、范围、比例/金额、时限、程序）逐项对原文 → 判定信号：每项标「一致／不一致／原文未规定」三态之一；措辞不同但要件相同，判一致。
3. 在工作记录写明「地方原文未得，本次以××文件第×条替代核对」 → 判定信号：记录中原文缺口与替代依据同时可见。

**④失败分支**：
- 比对出要件级不一致：标「冲突待核」，正式材料中该口径停用或降级表述，不拿措辞差异冒充冲突、也不掩盖真冲突。
- 上位文件也拿不到：整项转入未核实清单，本条到此为止，不再降级用博客或问答帖充当依据。

**⑤验收清单**：
- [ ] 比对表按要件逐项有三态结论，无整段「基本一致」式结论
- [ ] 工作记录写明原文未得与替代文件出处
- [ ] 本条产出的结论在引用时最高标为「与上位文件不冲突」，未写成「已核地方原文」

**⑥禁忌与易错点**：找不到不等于不存在，更不等于可以编；替代核法只能证明与上位文件不冲突，证明不了地方原文的细节规定。

**⑦参数表**：启用门槛＝地方原文经二十多轮、多渠道搜索未得（源材料实测口径）；本条结论证据上限＝实测报告级（替代核对），不得标官方文档级。

### 【实证与旁证分开标】

**①目标与适用场景**：研究对象本体（原文、原文件、原始记录）拿不到、只能用同主题旁证材料时，报告中实证与旁证严格分栏。触发场景：成稿引用了任何非本体材料。

**②前置条件**：已逐份判定材料性质：亲见本体＝实证；同主题他人材料、引用、转述＝旁证。分工：本条管「引用时怎么标」，【结论标五级证据】管「结论强度怎么定」，两条不互相替代。

**③操作步骤**：
1. 每处引用后紧跟出处类型标记（本体原文／同主题旁证） → 判定信号：全文抽查任意一处引用，都能一眼看出是实证还是旁证。
2. 旁证内容一律写成「据××材料推断/显示」，动词降格 → 判定信号：旁证段落中不存在引号包裹的「原话」。
3. 结论段按证据来源分栏排：实证支撑的结论与旁证支撑的结论不混排 → 判定信号：读者能逐条指出每个结论靠的是哪一栏。

**④失败分支**：
- 写着写着分不清某份材料算实证还是旁证：按旁证处理（就低不就高），并在材料清单注明存疑点。
- 本体后来拿到、与旁证冲突：以本体为准改稿，旁证结论整段撤下，不做折中拼接。

**⑤验收清单**：
- [ ] 全文引用无一处缺出处类型标记
- [ ] 旁证无一处以原话引用形式出现
- [ ] 结论强度与所在栏匹配，旁证栏无强结论

**⑥禁忌与易错点**：旁证冒充原话是研究报告最常见的注水方式；分开标不降低旁证的参考价值，但旁证支撑的结论必须随之降级使用。

**⑦参数表**：无数值参数。标记两类：本体原文／同主题旁证；旁证结论强度上限见【结论标五级证据】。

### 【取证路线记失败形态】

**①目标与适用场景**：每次取证除记成功路径，还给每条失败路线留一行记录。触发场景：任何一次多渠道查证（找文件、找原文、找数据）结束时。

**②前置条件**：有固定的取证记录载体（台账或工作日志），不是临时便签。

**③操作步骤**：
1. 每条路线记四个字段：入口（站点/库名）、走了几步（到哪一页/哪一步停）、失败形态（空壳页／超时／登录墙／链接失效／版本不符／无此条目）、是否值得重试及条件 → 判定信号：记录行四字段齐全，后来者不用重走就能判断。
2. 成功路径同样记入口与步数 → 判定信号：下次同类取证能按记录直接复现，不靠记忆找路。

**④失败分支**：
- 失败形态判不清（页面打开但内容对不上）：记「形态存疑」并附页面特征一句话，不硬归类。
- 同一路线失败形态与上次记录不同（如上次超时、这次登录墙）：两行都留，注明时点——形态变化本身是通道状态变化的信号。

**⑤验收清单**：
- [ ] 本轮每条走过的路线都有一行记录，无只记成功不记失败的情况
- [ ] 失败形态用词具体（能区分空壳页与链接失效），无「打不开」式笼统记录

**⑥禁忌与易错点**：记失败形态是给后来者省路，不是给「没取到」找台阶；该换路线继续挖的，记完照样继续挖。

**⑦参数表**：每条路线记录字段 4 项：入口／步数／失败形态／重试条件。

### 【登录墙下多关键词检索】

**①目标与适用场景**：目标平台有登录墙或 IP 限制、内容本体打不开时，用外部检索拼合内容全貌。触发场景：正文页进不去，但内容被搬运、存档或引用过。

**②前置条件**：已知内容的至少两个检索锚点（作者名、标题、编号、特征句，任二）。

**③操作步骤**：
1. 用锚点两两组合成多组关键词，分别全网检索 → 判定信号：至少跑完作者+标题、标题+编号、特征句原文三组。
2. 收集搬运页、存档页、引用页，对同一段落找两个以上独立来源互证 → 判定信号：拼合稿中每段都能指出来源数，单源段落单独标出。
3. 成稿注明「检索拼合」及始终未能确认的部分 → 判定信号：未确认部分逐项列名，不用省略号带过。

**④失败分支**：
- 只找到单一来源：该部分按旁证降格（见【实证与旁证分开标】），不写成已拼合确认。
- 各来源互相矛盾：保留冲突双方及出处，不选边、不平均。

**⑤验收清单**：
- [ ] 关键词组数 ≥3，锚点组合有变化，不是同一词重复搜
- [ ] 拼合稿每段有来源数标注，单源段已降格
- [ ] 未确认部分逐项列名

**⑥禁忌与易错点**：不要在登录墙前反复硬闯触发更严的限制；拼合结论的可信度低于亲见原文，引用时不许去掉「拼合」标注。

**⑦参数表**：无数值参数。互证判线：关键段落独立来源 ≥2 才算拼合确认。

### 【评估先切开营销产品】

**①目标与适用场景**：评估某个题材的工具或方案，候选里混有被大量投诉的商业推广产品时，先切开再评。触发场景：候选清单里同时有营销产品与免费/自建路线。

**②前置条件**：候选清单已列全，能逐个判定其属性（营销产品／免费或自建路线）。

**③操作步骤**：
1. 清单按属性分两栏，营销产品栏逐个登记投诉类型与来源（退款、虚假宣传、跑路等） → 判定信号：每条投诉能回指到具体来源，不是「口碑差」三字。
2. 两栏用同一套维度评（功能、成本、风险、可持续性） → 判定信号：评分表维度列完全一致，没有给某一栏单设宽松维度。
3. 结论分栏下：先给自建/免费路线的可行性结论，再给营销产品的处置结论 → 判定信号：结论中不存在「这个题材整体不行」式跨栏总评。

**④失败分支**：
- 某候选属性判不清（半营销半工具）：单列「属性待定」，先查运营主体与收费模式再归栏，不硬塞。
- 自建路线评估后确实不可行：如实写不可行及卡点，不因已切开就预设自建必胜。

**⑤验收清单**：
- [ ] 清单分栏完整，无未归栏候选
- [ ] 两栏评分维度一致
- [ ] 营销产品的差口碑未污染对整个题材的判断

**⑥禁忌与易错点**：切开是为了分别评，不是预设结论；营销产品声量最大、投诉也最多，混评必然得出错误的总判断。

**⑦参数表**：无数值参数。评估维度 4 项：功能／成本／风险／可持续性。

### 【结论标五级证据】

**①目标与适用场景**：研究报告每条结论标注证据等级，供后续决策按强度取舍。触发场景：任何研究报告成稿时。

**②前置条件**：结论已拆成单条（一条结论一个判断），复合结论先拆开再标。

**③操作步骤**：
1. 逐条按格式标注 `[证据等级｜证据载体｜定位]`，定位粒度按卷首格式表写 → 判定信号：抽查任一条标注，按定位能实际打开对应原文、代码位置或实测记录。
2. 按等级定使用方式：官方文档／代码实证／实测报告可支撑强结论与行动；博客经验只支撑「值得一试」；推测只支撑「待验证假设」 → 判定信号：正文中强结论（「应当」「必须」）无一挂在博客经验或推测上。
3. 与【实证与旁证分开标】分工：引用标注看那条，本条只管结论强度 → 判定信号：同一报告两套标注各司其职，无重复打架。

**④失败分支**：
- 某条结论证据跨级（部分实测、部分推测）：按最低一级标，并在括号里注明哪部分未证。
- 定位写不出（说不清证据在哪）：该条降为推测级，不许凭印象标高等级。

**⑤验收清单**：
- [ ] 每条结论有完整三段标注
- [ ] 随机抽 3 条按定位回溯，全部能打开对应证据
- [ ] 强结论无一由博客经验/推测支撑

**⑥禁忌与易错点**：等级标的是证据强度，不是结论对错；低等级结论可以是对的，但使用前要补证或降格，不许因为「我觉得对」就标高。

**⑦参数表**：等级 5 级：官方文档／代码实证／实测报告／博客经验／推测。强结论门槛：前三级。

### 【无权威来源列未核实】

**①目标与适用场景**：字段口径、参数定义类问题找不到权威来源时，列入未核实清单，不用类推填空。触发场景：查遍可及来源仍无权威定义，而交付物正等着这个数。

**②前置条件**：已实际查过权威来源（官方文档、标准原文、发文机关），「没查」不算「查不到」。

**③操作步骤**：
1. 清单条目写四项：问题、已查来源（逐个列名）、类推假设（如有）、验证前禁入范围 → 判定信号：后来者看清单就知道查过哪、还差哪。
2. 类推假设只以「待试假设」身份出现在清单里，正式结论与交付物正文不引用 → 判定信号：全文检索类推值，只在清单出现。
3. 新证据出现时逐项销账：把验证结果与证据定位补进原条目，状态改「已核实」 → 判定信号：清单有进有出，不是只进不出的死账。

**④失败分支**：
- 交付压力要求「先给个值」：给值必须同时交付其「未核实」标记与假设来源，缺一不发；对方仍要无标记版，拒绝并留痕。
- 同一问题被多人重复类推、数值互相打架：全部作废回到清单原点，以先到的实证定案。

**⑤验收清单**：
- [ ] 未核实项全部在清单内，正式结论零引用
- [ ] 每条清单项已查来源逐个列名
- [ ] 已销账项有验证证据定位

**⑥禁忌与易错点**：留白不是放弃；类推填出的口径表面完整实则无据，被下游当定论用时返工成本远高于留白。

**⑦参数表**：无数值参数。清单条目字段 4 项：问题／已查来源／类推假设／禁入范围。

### 【AI产品评估七维清单】

**①目标与适用场景**：评估外部 AI 产品（工具、服务、平台）能不能用，先立七维问题清单再取证。触发场景：任何新 AI 产品进入候选。

**②前置条件**：产品名称、运营主体可查；没有可查主体的产品直接出局，不进七维。

**③操作步骤**：
1. 七维逐维先写问题再取证：背景（主体、存续、融资/营收形态）、机制（技术路线、数据流向）、价格（计费方式与隐藏项）、部署（自托管/云端、迁移成本）、数据隐私（上传什么、留存多久、是否训练）、账号风险（封号条款、申诉通道）、口碑合规（投诉、处罚、监管表态） → 判定信号：每维的问题清单先于答案存在，不是看完演示再补问题。
2. 逐维填答并标证据等级（按【结论标五级证据】） → 判定信号：每维至少有一条一手来源（官网原文、条款、登记信息），只有测评文章的维标「未查实」。
3. 任一维空白，评估结论头部标注「××维未查」 → 判定信号：结论页能一眼看到未查维度名单。

**④失败分支**：
- 数据隐私维查不到留存/训练条款：按最坏情形（上传即留存）评估并写明，这是风险维，不许按「没写就是不留存」处理。
- 价格维只有营销页口径、无计费文档：标未查实，不采信口头价。

**⑤验收清单**：
- [ ] 七维问题清单齐全且先于取证
- [ ] 每维有一手来源或明确标未查实
- [ ] 结论头部列出全部未查维度

**⑥禁忌与易错点**：AI 产品的坑多在机制之外——数据去向、账号风控、合规口碑才是决定能不能用的地方，只看功能演示必然漏项；框架列全但没取证的，按待查交付（见【未取证框架如实标待查】）。

**⑦参数表**：维度 7 项：背景／机制／价格／部署／数据隐私／账号风险／口碑合规。

### 【营销与实证分栏标】

**①目标与适用场景**：评估材料内部把营销文案与实证材料分栏，防止自我宣称被转手当事实。触发场景：整理任何产品的评估摘录时。

**②前置条件**：能接触到至少一类实证来源（工商登记、备案信息、真实用户反馈）；完全没有实证来源时整份材料按营销栏处理。

**③操作步骤**：
1. 摘录时同步打栏标：厂商自述（用户量、准确率、合作方名单）进营销栏；登记、备案、第三方反馈进实证栏 → 判定信号：抽查任一摘录，栏标与来源性质一致。
2. 实证栏内部再看一手程度：登记/备案原文＞当事方截图＞二手转述 → 判定信号：实证栏条目带一手程度注记。
3. 查不到的写「查不到」三字加已查入口，不留空白、不推测 → 判定信号：全文无无声空缺。

**④失败分支**：
- 某说法两栏都有（厂商宣称与用户反馈各执一词）：两栏并列原文呈现，结论处标冲突待核。
- 实证来源本身疑似造假（反馈账号批量新建等）：降格回营销栏并注明降格理由。

**⑤验收清单**：
- [ ] 每条摘录有栏标
- [ ] 营销栏内容无一被结论引用为事实
- [ ] 查不到项有「查不到」加已查入口

**⑥禁忌与易错点**：分栏只解决来源标注，不解决实证本身真伪；厂商把营销内容伪装成「用户故事」投放时，按来源性质仍归营销栏。

**⑦参数表**：无数值参数。分栏 2 类：营销文案／实证材料。

### 【视觉接管先查协议风险】

**①目标与适用场景**：评估「纯视觉方式接管已登录聊天应用」类方案（截图识别＋模拟操作），核查顺序定式：先风险，后功能。触发场景：有人拿这类方案的演示来问能不能用。

**②前置条件**：已知目标平台与接管方式（视觉识别、界面自动化、无障碍接口等）；查不到目标平台用户协议原文的，先停在查协议这一步。

**③操作步骤**：
1. 查平台用户协议：检索「自动化」「脚本」「非官方客户端」相关条款，摘录原文 → 判定信号：有条款原文定位（条款号或页段），不是「好像不让」的印象。
2. 查封号案例：找该平台对同类接管方式的实际处置案例（封号公告、用户实录） → 判定信号：至少区分「有实证案例／仅有传闻／未查到」三态并注明。
3. 查数据出境：确认截图与识别在哪算（本地/云端）、经哪些服务器 → 判定信号：数据流向能画成一条完整路径，无「云端识别但不知是哪家」断点。
4. 三项过关后才看功能演示 → 判定信号：评估记录中风险三项的填写时间早于功能评估段。

**④失败分支**：
- 协议未明文禁止但已有封号实证：按有风险处理，协议沉默不构成安全证明。
- 数据流向查不全：整项标未核实，方案不得进入试用，更不得接业务数据。

**⑤验收清单**：
- [ ] 协议条款有原文摘录与定位
- [ ] 封号案例三态结论明确
- [ ] 数据流向路径完整无断点
- [ ] 功能评估排在风险核查之后

**⑥禁忌与易错点**：这类方案功能上往往真能跑，但代价可能是整号被封、业务数据出境；风险项不过关，功能再好也不能用。

**⑦参数表**：首要核查项 3 项：平台用户协议／封号案例／数据是否出境。

### 【未取证框架如实标待查】

**①目标与适用场景**：调研只立起框架、多维未取证时的交付纪律。触发场景：交付期限到，但取证明显未完成。

**②前置条件**：框架维度已列全，能逐维说清哪些查了、哪些没查。

**③操作步骤**：
1. 交付物封面写完成度声明：框架已立／已取证维度名单／未取证维度名单 → 判定信号：封面三项齐全，读者不翻正文就知道成色。
2. 未取证维度逐个列名并写补证触发条件（等什么材料、谁提供、什么时点复查） → 判定信号：每个未取证维度都有一条可执行的触发条件，不是「以后再查」。
3. 正文结论只许出现在已取证维度内；未取证维度只写问题清单，不写判断句 → 判定信号：全文检索未取证维度名，其后无结论性表述。

**④失败分支**：
- 被要求「先给个大致结论」：只给已取证部分的结论，并把未取证名单随结论同页交付，不单独发结论页。
- 待查长期无人补证：主动提出终止或降级为问题清单归档，不许无限期挂着待查冒充在办。

**⑤验收清单**（本条专属）：
- [ ] 封面完成度声明齐全（框架/已取证/未取证三名单）
- [ ] 未取证维度逐个列名且各有补证触发条件
- [ ] 未取证维度名下无任何结论句

**⑥禁忌与易错点**：不要套用「每个结论都要有证据标注」的通用验收来卡本条——本条交付物恰恰大量内容无证据，验收只看声明是否诚实、名单是否齐全；标待查是诚实不是免责。

**⑦参数表**：无数值参数。本条为规程条目（非原则清单）：完成度声明 3 项＋每未取证维度 1 条触发条件。

### 【引擎验证零业务数据】

**①目标与适用场景**：验证引擎或模型能力时，测试集只用公开样例与自制变体，零业务数据。触发场景：任何引擎/模型选型实测开工前定测试集。

**②前置条件**：模型包自带样例可得；自制变体的制作方法明确（变速、加噪、衰减等，见【自制音频变体测鲁棒性】）。

**③操作步骤**：
1. 动手前把测试集来源写死成清单：官方样例逐个列名、自制变体逐个列派生方式 → 判定信号：清单在第一条实测记录之前已存在。
2. 实测全程只从清单取材；临时想加业务样本验证「真实效果」，当场停手记入待办 → 判定信号：实测目录中文件与清单一一对应，无清单外文件。
3. 报告直接按实测口径成文，无需脱敏裁剪 → 判定信号：报告可整份外发，不含需打码内容。

**④失败分支**：
- 官方样例缺失或损坏：用自制变体补足并在清单注明替代关系，不顺手抓业务数据顶替。
- 业务方坚持要看真实数据效果：另立上线后抽查计划（在生产侧、按生产权限做），不在验证环境里开这个口子。

**⑤验收清单**：
- [ ] 测试集清单先于实测记录存在
- [ ] 实测目录文件与清单一一对应
- [ ] 报告无业务数据内容

**⑥禁忌与易错点**：零业务数据验证的是引擎能力与链路通断，真实业务分布下的表现仍需上线后抽查补验，不许拿验证结论冒充业务效果结论。

**⑦参数表**：无数值参数。测试集来源 2 类：官方公开样例／自制变体；业务数据用量＝0。


## 领域口径、对口关系与报送核查（11 条）

### 【硬截止倒逼清单】

**①目标与适用场景**：政策给出硬截止（如某类项目须年底前完成入库）时，把截止倒逼成逐项必办清单。触发场景：文件出现「×月×日前完成」且涉及多个在办事项。

**②前置条件**：受影响事项能完整枚举（项目库、在办台账）；每项的必备件构成已知（预算、绩效目标、需求留痕等）。

**③操作步骤**：
1. 列全受影响事项，逐项拆必备件并逐件标状态（已备／在备／未启） → 判定信号：清单覆盖率与事项总数对得上，无「其他」兜底行。
2. 未决数字（数量、规格断面之类）单独挂账，每项写待确认人与确认方式 → 判定信号：挂账项无一缺确认人。
3. 按截止倒排跟进节奏，挂账超期未确认的逐级上报 → 判定信号：清单上有每个挂账项的最近跟进日期，上报留痕存在。

**④失败分支**：
- 截止前发现必备件根本备不齐：提前向上报告缺件与原因，争取延期或调整口径，不捂到截止日爆雷。
- 确认人长期不回：升级到其上级或改走书面催办，清单上把状态改「催办中」并留催办记录。

**⑤验收清单**：
- [ ] 事项清单与在办总数一致
- [ ] 每项必备件有状态、每个未决数有确认人
- [ ] 超期挂账项有上报或催办留痕

**⑥禁忌与易错点**：硬截止不会因内部没准备好而延期；不要等截止前一周才发现缺件——清单的价值就在随时可查「还差什么、卡在谁」。

**⑦参数表**：无固定数值。清单字段：事项／必备件及状态／未决数／确认人／最近跟进日期。

### 【领域口径按渠道分】

**①目标与适用场景**：同一类项目能不能申报，答案随资金渠道而变；口径必须带渠道标签使用。（本条只写方法，不写实例。）触发场景：判断任一具体事项适用哪条政策口径时。

**②前置条件**：候选渠道已枚举（本单位可及的全部资金/政策渠道）；各渠道正式文件可查。

**③操作步骤**：
1. 口径入库时强制带两个标签：适用渠道、不适用渠道 → 判定信号：口径库中无无标签条目。
2. 判断具体事项时先定渠道、再套该渠道口径 → 判定信号：判断记录第一行是渠道名，不是口径结论。
3. 同一事项多渠道都可能沾边时，逐渠道各判一遍并列呈现 → 判定信号：结论按渠道分行，无跨渠道合并结论。

**④失败分支**：
- 渠道口径文件查不到：该渠道标「口径未核」，判断只做到其余渠道，不拿相近渠道的口径顶替。
- 两渠道口径冲突：一事一渠道申报，按申报渠道口径为准并记录冲突，不自行调和。

**⑤验收清单**：
- [ ] 口径库条目全部带双标签
- [ ] 每次判断记录先渠道后口径
- [ ] 无跨渠道套用结论的实例

**⑥禁忌与易错点**：渠道间口径宽窄不同，有的覆盖面宽、有的只覆盖特定范围；不带标签的口径在转述中最容易被一刀切用错。经验判断只能提示先查哪个渠道，不能替代文件本身。

**⑦参数表**：无数值参数。每条口径标签 2 项：适用渠道／不适用渠道。

### 【对口关系是耐久知识】

**①目标与适用场景**：上级部门与本单位各办公室的对口关系入册长期保存；发现排错时在送达前全量改对。触发场景：新建一条业务线的通知分工，或发现既有分工对口错误。

**②前置条件**：对口关系有确认来源（分工文件、对方单位通讯录、负责人确认，任一）；仅凭印象的对口先标待确认。

**③操作步骤**：
1. 确认后把「上级部门→本单位对口办」写入知识库对口表，注明确认来源与日期 → 判定信号：对口表每行有来源，不是裸对应关系。
2. 发现排错时，先冻结该线全部未送达件，逐件按正确对口改正（牵头、配合、汇总去向同步改） → 判定信号：改正后全文检索旧对口办名，在该线未送达件中零残留。
3. 已送达的错误版本逐件追回说明：向已收件人发更正，写明哪项分工改归谁 → 判定信号：更正发出清单与已送达清单条数一致。

**④失败分支**：
- 对口关系两方说法不一致：以发文单位的分工文件为准；文件未到的，按【继任分工不猜】冻结归属判断。
- 改正时发现汇总台账已按错对口收了数：台账整表按新对口重收，不在错表上打补丁。

**⑤验收清单**：
- [ ] 对口表每行有确认来源与日期
- [ ] 纠错轮次未送达件旧口径零残留
- [ ] 已送达错误版本全部有追回更正记录

**⑥禁忌与易错点**：排错对口意味着整条线的通知、台账、汇总全部错位；「队列还没发」是原地改对的唯一窗口，一旦送达就只能追回，成本完全不同。

**⑦参数表**：无数值参数。对口表字段：上级部门／对口办／确认来源／日期。

### 【通知没写的不要编】

**①目标与适用场景**：上级通知原文未提及的事项（报送时限、是否需要回报表之类）一律标未定，不自行补全。触发场景：转发或部署任何上级通知时。

**②前置条件**：手上有通知原文；只有转述版时先按转述未验证处理，不进入本条。

**③操作步骤**：
1. 部署文稿分两栏列：通知已明确的（逐项引原文）、通知未提及的（逐项标「未定」） → 判定信号：部署稿中每个执行要求都能回指原文句，未定栏条目无一被写成要求。
2. 未定项并行准备材料但不对外发布口径、不据此催办 → 判定信号：催办记录中无以未定项为依据的条目。
3. 后续口径到达或负责人拍板后，把未定项移入明确栏并注明来源 → 判定信号：未定栏有销账记录。

**④失败分支**：
- 下级按惯例追问「到底要不要报、什么时候报」：只答「通知未提及、已标未定、有口径第一时间转达」，不给经验性时限。
- 已有人按自编口径行动：立即叫停并说明该口径无出处，已产出的材料按未定状态封存待真口径。

**⑤验收清单**：
- [ ] 部署稿明确/未定两栏分明
- [ ] 未定项无一进入对外要求或催办依据
- [ ] 未定项销账有来源记录

**⑥禁忌与易错点**：自编的时限和要求会被下级当正式要求执行，错了整条线返工，还损害通知的严肃性。

**⑦参数表**：无数值参数。未定项状态 2 态：未定／已定（附来源）。

### 【专项部署排兵法】

**①目标与适用场景**：一项专项工作落到单位时的标准分工：对口办牵头收总台账、相关办配合、一线入户摸排、职能办出底数。触发场景：新专项通知到达、需要全员分工时。

**②前置条件**：牵头办已按对口关系定准（见【对口关系是耐久知识】）；专项要点清单已按通知原文拟好（未提及项按【通知没写的不要编】标未定）。

**③操作步骤**：
1. 定四类角色：牵头办（对接上级＋收总台账）、配合办（业务支撑）、入户线（社区与片区人员宣传排查）、底数办（掌握重点人群信息的办公室出名单并与入户挂钩） → 判定信号：分工表四类角色无空缺、无一人身兼牵头与汇总之外的冲突角色。
2. 每位参与者发同一份要点清单（检查要点、处置口径、汇总去向写在同一页） → 判定信号：抽查任意两名参与者手中的清单版本一致。
3. 隐患/问题登记统一汇总到牵头办一个口 → 判定信号：各线上报路径终点都是牵头办台账，无第二汇总点。

**④失败分支**：
- 某片区无人可派：分工表上显性标「空缺片区」并报负责人调配，不默默把该片区从清单删掉装作全覆盖。
- 底数办名单与入户实况对不上（人已搬离等）：入户线当场标注实况回牵头办，底数按实况修订，不按旧名单凑数。

**⑤验收清单**：
- [ ] 四类角色齐全且牵头办唯一
- [ ] 全部参与者清单版本一致
- [ ] 汇总口只有一个，空缺片区显性标注

**⑥禁忌与易错点**：排兵只解决分工与汇总路径，不替代专项本身的技术要求；要点清单要随上级口径更新同步修订，旧版清单要收回。

**⑦参数表**：无数值参数。角色 4 类：牵头／配合／入户／底数。

### 【跟进事项分清两回事】

**①目标与适用场景**：同一个人身上有两件待确认事项时，分开记录、分开询问。触发场景：准备向某人追问，而其名下挂着 ≥2 件未决事项。

**②前置条件**：台账按事项分行（一事一行、各有状态），不是按人合并记。

**③操作步骤**：
1. 沟通时一件事问清、记下结论，再问下一件 → 判定信号：对话记录中两件事的问答段落可分开摘录，无交叉。
2. 对方只答了一件：未答的那件状态保持「未确认」，不把已答件的结论顺手记到它头上 → 判定信号：台账两行状态独立变化。

**④失败分支**：
- 对方把两件事混着答：当场拆开复述确认——「先确认第一件：……；第二件您刚说的是……对吗」，确认完再落账。
- 历史台账已把两件事记混：按原始沟通记录逐件重建，两行都标「曾记混、已重建」留痕。

**⑤验收清单**：
- [ ] 同人多事项台账一事一行
- [ ] 每件结论能回指到独立问答段
- [ ] 无一事的结论记到另一事名下

**⑥禁忌与易错点**：可以在同一次接触里依次问，但问法与记录必须逐件分开；合并追问必然得到含糊答复，落账时还会张冠李戴。

**⑦参数表**：无数值参数。台账粒度：1 事项 1 行 1 状态。

### 【继任分工不猜】

**①目标与适用场景**：领导班子调整后，新任者接哪一摊以正式分工文件为准。触发场景：人事调整已宣布、分工文件未下，而工作需要确定归属时。

**②前置条件**：能区分「宣布了人事」与「下发了分工文件」两个时点；只有前者时本条生效。

**③操作步骤**：
1. 文件未下期间冻结三类归属：分组命名、权限归属、台账归属，全部保持调整前原状 → 判定信号：系统与台账中相关命名、权限、归属与调整前逐项一致，无一处「先按惯例改上」。
2. 有人问起归属，只答「等分工文件」并指向当前临时承办渠道 → 判定信号：答复中无任何猜测性归属表述。
3. 在办事项按原渠道继续推进，不因等文件停摆 → 判定信号：冻结期内在办事项进度记录连续，无以「等分工」为由的停滞项。
4. 文件到达当轮，按文件一次性改齐三类归属并留变更记录 → 判定信号：变更记录日期与文件日期衔接，无拖延跨轮。

**④失败分支**：
- 有人已按猜测归属送错材料：按【对口关系是耐久知识】的追回规程逐件更正。
- 文件迟迟不下而事项必须定归属：请有权负责人临时指定并书面留痕，标注「临时指定、待文件确认」，不把临时指定写成正式分工。

**⑤验收清单**：
- [ ] 冻结期三类归属与调整前一致
- [ ] 对外答复无猜测性归属
- [ ] 文件到达后当轮改齐并留痕

**⑥禁忌与易错点**：猜错分工会把材料、权限、责任连续送错人；冻结的是归属判断，不是工作本身。

**⑦参数表**：无数值参数。冻结对象 3 类：分组命名／权限归属／台账归属。

### 【报送前待定项清单】

**①目标与适用场景**：正式报送发出前的逐项勾选清单。（本条只写方法，不写实例。）触发场景：任何正式报送件点「发送」之前。

**②前置条件**：报送件已成稿；清单四项的核对渠道明确（本人确认走当面/电话/其本人消息，账号核对走第 3 步方法）。

**③操作步骤**：
1. 人选经本人确认：确认凭据落纸——记录确认方式、时间、确认人原话要点，存入报送底稿包 → 判定信号：底稿包里能找到确认记录，口头问过但无记录的按未确认处理。
2. 联系方式就本次用途核对：按【联系方式就用途单独确认】的记录验是否覆盖本次用途与日期 → 判定信号：确认记录的用途栏与本次报送用途逐字对得上。
3. 发件账号核对：打开账号资料页核对登录态账号标识，并与最近一封已成功送达的发件记录比对发件人字段 → 判定信号：两处账号标识一致；不一致立即停发查因。
4. 职务与称谓：逐个与最新任职文件或单位通讯录比对 → 判定信号：无一称谓凭记忆填写。
5. 四项全勾才发出；任一未勾，整件停发并在清单上标卡点 → 判定信号：发出记录时间晚于清单全勾时间。

**④失败分支**：
- 临近截止仍有一项确认不到：按【未核字段留空不凑数】处理该字段或请示延期，不跳过清单硬发。
- 发出后才发现清单有假勾（记录对不上）：立即向收件方发更正，并复盘该项核对方法失效原因。

**⑤验收清单**：
- [ ] 四项各有凭据（确认记录/用途记录/账号双比对/任职出处）
- [ ] 发出时间晚于全勾时间
- [ ] 底稿包完整可回溯

**⑥禁忌与易错点**：清单拦的是「未核实」，不是「写得不好」；内容质量走审稿环节，不与此清单混用。报送件的错误大多不在正文，而在这些边角字段，且发出后无法撤回。

**⑦参数表**：必查项 4 项：人选本人确认／联系方式本次用途核对／职务与称谓／发件账号。

### 【联系方式就用途单独确认】

**①目标与适用场景**：某联系方式在其他材料里出现过，不等于本人确认可用于本次用途。（只写方法。）触发场景：报送、公示、对外提供任何关键联系字段前。

**②前置条件**：能联系到本人或其明确授权的确认渠道；联系不到本人的，该字段按未确认处理。

**③操作步骤**：
1. 就本次用途向本人单独确认该字段可用，确认时说清用途与公开范围 → 判定信号：确认记录含用途、范围、日期三要素。
2. 换用途（哪怕同一字段、同一材料体系）重新确认 → 判定信号：用途变更记录后跟着一条新确认记录。
3. 确认记录与字段绑定存放，引用字段时能顺带调出其确认状态 → 判定信号：抽查任一对外字段，可当场指出其确认用途与日期。

**④失败分支**：
- 本人确认的是另一用途、被误用到本次：立即撤下本次使用，向本人说明并重新确认，不将错就错。
- 字段已变更（本人换号等）：旧确认自动失效，按新字段重走确认。

**⑤验收清单**：
- [ ] 对外关键字段全部有对应用途的确认记录
- [ ] 确认记录三要素齐全
- [ ] 无跨用途沿用确认的实例

**⑥禁忌与易错点**：旧材料里的号码可能已变更、可能他人代收、也可能本人不愿用于新场景，沿用即埋雷。低风险的公开联系方式可按公开口径使用，不必逐次确认——但「公开」要以官方公开渠道为准，不以「别处见过」为准。

**⑦参数表**：确认记录要素 3 项：用途／公开范围／日期。确认粒度：1 字段 × 1 用途 1 次。

### 【未核字段留空不凑数】

**①目标与适用场景**：报送材料中未核实的字段留空待补，绝不拿旧记录凑数发出。（只写方法。）触发场景：成稿时发现个别字段无核实依据。

**②前置条件**：已区分「未核」与「确实没有」：前者留空标待核，后者写「无」并注明依据，两者不混。

**③操作步骤**：
1. 未核字段清空原值，填「待核」并注明核实责任人与预计核实路径 → 判定信号：留空处显性可见，收件方一眼能分清是未核而不是没有。
2. 整件因留空不完整时，宁可延后报送并向收件方说明缺项与补报时间 → 判定信号：延期说明已发出，不存在带未核值悄悄发出的版本。
3. 核实后补填并在版本记录里注明补填来源 → 判定信号：补填值可回指核实记录。

**④失败分支**：
- 旧记录的值看起来「八九不离十」：仍按未核处理；旧值只能作为核实线索写进内部底稿，不进报送件。
- 收件方催要完整版：给带「待核」标记的版本并说明，不给凑数版。

**⑤验收清单**：
- [ ] 报送件无一字段是旧记录凑数
- [ ] 每个留空处有「待核」标记与责任人
- [ ] 补填值全部有核实来源

**⑥禁忌与易错点**：凑数数据一旦进入上级台账，会被当作已核事实层层引用，纠错成本成倍放大；留空必须显性标注，静默空缺会让收件方误读为「没有」。

**⑦参数表**：无数值参数。字段状态 3 态：已核／待核（标责任人）／无（标依据）。

### 【多件报送各走各件】

**①目标与适用场景**：同日多件报送时每件独立成件、独立发送。（只写方法。）触发场景：同一天要发出 ≥2 件、且节点或收件方不同。

**②前置条件**：每件的收件方、节点、依据文件已分别明确；分不清归属的材料先停下分件。

**③操作步骤**：
1. 逐件建件：一件一函、一件一套附件、一件一条发送记录 → 判定信号：发送记录数与报送件数相等，无一函多件。
2. 每件独立走【报送前待定项清单】 → 判定信号：每件有自己的全勾清单，不共用。
3. 同一收件方、同一节点的成套材料可同件，但函内逐件列明件名与各自依据 → 判定信号：函内清单与附件逐件对得上。

**④失败分支**：
- 误把两件并作一件发出：立即向收件方说明并补发独立件，原合并件注明作废，不装作没发生。
- 某件未就绪而其他件到期：就绪的先发，未就绪的单独延期，不捆绑等待也不捆绑硬发。

**⑤验收清单**：
- [ ] 件数＝函数＝发送记录数
- [ ] 每件有独立待定项清单
- [ ] 合并例外（同收件方同节点）函内逐件列明

**⑥禁忌与易错点**：合并打包省的是一次点击，赔的是每件的留痕、回执与责任归属；节点不同、收件不同的材料塞进同一封信，任何一件出问题都会污染其余件的送达认定。

**⑦参数表**：无数值参数。成件粒度：1 事项 1 件。


## 计算与生成管线方法（11 条）

### 【计算归脚本写作归模型】

**①目标与适用场景**：管线分工定式：确定性计算全交脚本与成熟库，语言模型只拿结构化事实写作解读。触发场景：设计任何「算＋写」类生成管线时。

**②前置条件**：任务能明确切出计算部分（有确定输入输出）与生成部分（叙述、解读）；切不出的判断环节先单列，不硬塞任何一层。

**③操作步骤**：
1. 计算层写成纯函数脚本：输入结构化、输出结构化，同一输入重复跑结果逐字节一致 → 判定信号：同输入连跑两次，输出文件哈希相同。
2. 生成层只读计算层输出，不接触原始推算过程 → 判定信号：生成层提示词/输入里只有计算结果，没有原始数据与公式。
3. 生成层文中出现的每个数字回查计算层输出 → 判定信号：抽查 5 个数字，全部能在计算输出中定位，无一为模型自算。

**④失败分支**：
- 两次运行结果不一致：先查计算层（随机源、时间依赖、浮点路径），定位前整条管线停用，不把不一致归咎于「模型波动」。
- 生成层数字与计算输出对不上：以计算输出为准整段重生成，不手工改数字——手改会留下第二处不一致。

**⑤验收清单**：
- [ ] 计算层同输入双跑哈希一致
- [ ] 生成层输入不含原始推算材料
- [ ] 成稿数字抽查与计算输出一致

**⑥禁忌与易错点**：无法形式化的判断不要硬塞给脚本，也不要把模型判断包装成计算结果；分工的前提是计算可形式化。

**⑦参数表**：无数值参数。一致性判线：同输入双跑输出哈希相同。

### 【可代码化计算不交模型】

**①目标与适用场景**：查表型、公式型计算（历法换算、查表推演等）绝不交语言模型心算。触发场景：任何需求里出现「算一下××」且该计算有确定规则。

**②前置条件**：能判断计算类型：查表型（有对照表）、公式型（有明确公式）适用本条；无规则可循的估算不适用。

**③操作步骤**：
1. 识别出查表/公式型计算后，第一动作是找成熟库，无库则写脚本，模型只解释结果 → 判定信号：工作记录里先有库/脚本的验证记录，后有结论引用。
2. 库/脚本先过已知答案用例（见【三类边界案例回归对齐】） → 判定信号：用例全过才进入正式计算。
3. 一次性小计算例外：可由模型做，但结果必须经独立复算（另一路径或人工验算）才交付 → 判定信号：交付物旁有复算记录。

**④失败分支**：
- 同一问题模型给了两个不同结果：立即判定该计算不可由模型承担，转脚本实现，并回查此前已交付的同类结果是否已污染。
- 找不到成熟库且计算规则不完整：规则缺口列未核实，不许让模型「按理解补全规则」继续算。

**⑤验收清单**：
- [ ] 全部查表/公式型计算有库或脚本承担
- [ ] 计算工具先过已知答案用例
- [ ] 模型手算的例外项全部有独立复算记录

**⑥禁忌与易错点**：实测让模型查表手推，同一问题两次能给两个结果，且这类错误无声无息——不报错、不提示，直接以正确答案的面目交付。

**⑦参数表**：无数值参数。判线：同问两次结果不一致即判定模型心算不可用。

### 【解读链写死顺序标依据】

**①目标与适用场景**：专业解读类任务：分析顺序写死、每步不许跳、每条结论标依据。触发场景：搭建或执行任何多步专业解读流程。

**②前置条件**：解读步骤序列已定义且每步的输入事实来源明确；步骤未定稿前不对外出解读。

**③操作步骤**：
1. 按固定步骤序列推进，前一步无产出不进下一步 → 判定信号：解读稿每段能标注所属步骤号，无跳步段落。
2. 每条断语后标依据：出自哪一步、依据哪个事实（指向计算层输出或原始输入） → 判定信号：抽查任一断语，依据可在两步内定位到具体事实。
3. 单一依据支撑的结论标「孤证」并降格表述（「倾向于」代替「就是」） → 判定信号：孤证结论无一使用绝对断语。

**④失败分支**：
- 某步事实缺失：该步标「无依据、跳过声明」，后续依赖该步的结论同步降格或撤下，不许用常识补位。
- 依据指向的事实被推翻：顺链回溯，依赖它的全部结论逐条复核改判。

**⑤验收清单**：
- [ ] 解读稿步骤完整无跳步
- [ ] 每条断语有可定位的依据
- [ ] 孤证结论全部降格表述

**⑥禁忌与易错点**：标依据只保证推理可追溯，不保证结论正确；语气上仍给倾向性判断，不下绝对断语——尤其孤证场合。

**⑦参数表**：无数值参数。标注粒度：每条断语 1 个依据指针。

### 【入口门控与降级声明】

**①目标与适用场景**：生成管线入口写死门控：必填项、口径选择、未知项降级规则。触发场景：设计任何「输入不全也可能被要求出结果」的管线。

**②前置条件**：必填项清单与口径选项已枚举；每个未知项的降级形态（只出部分结果/整单拦截）已预先定义。

**③操作步骤**：
1. 必填缺失 → 拦截并逐项说明缺什么，不启动生成 → 判定信号：拦截输出列出缺失项名单，不是笼统报错。
2. 口径选项必须显式选定，未选不默认 → 判定信号：运行记录里有口径选择值与选择人。
3. 某项未知 → 只输出可得部分，并在交付物正文写降级声明（缺哪项、因此少了什么、结论适用范围收窄到哪） → 判定信号：降级声明在正文可见位置，不只记内部日志。

**④失败分支**：
- 使用方要求「先按假设值出全量版」：拒绝在正式交付物里用假设值填满；可另出标注「假设版」的内部讨论稿，与正式版物理分开存放。
- 门控被绕过（有人直接调生成层）：生成层自身再验一遍必填与口径，缺失即拒绝产出。

**⑤验收清单**：
- [ ] 缺必填时拦截且列明缺项
- [ ] 口径选择有记录、无默认偷跑
- [ ] 降级声明进交付物正文

**⑥禁忌与易错点**：禁止为填满报告编造输入；入口不设门控，错误与编造会顺流而下，最后以「完整报告」的面目出现。

**⑦参数表**：无数值参数。门控三件：必填清单／口径显式选定／降级声明模板。

### 【口径做没做写进交付物】

**①目标与适用场景**：交付物固定设「口径说明」节，逐项写明关键口径做没做、怎么做（时间校正、历史特殊时制处理、边界规则取舍等）。触发场景：一切带口径选择的计算/解读类交付。

**②前置条件**：本单涉及的口径项已枚举；每项能明确回答「采用/未采用」。

**③操作步骤**：
1. 按四列表格写口径说明：口径名／采用与否／理由／出处（文件、条款或实测记录） → 判定信号：表格无空行，每项四格齐全。
2. 有争议的口径同时给出备选口径下的结果差异 → 判定信号：争议项行内有差异数值或差异说明。
3. 未做的口径如实写「未做」及原因，不许用含糊措辞（「已做相应处理」）蒙混 → 判定信号：全文检索「相应处理、适当调整」等模糊词，口径节内零出现。

**④失败分支**：
- 执行中发现某口径实际没做而初稿已写做了：当轮更正交付物并向接收方发更正说明，不等对方发现。
- 口径出处查不到：该项标「出处未核」，按未核口径降格使用，不编造出处。

**⑤验收清单**：
- [ ] 口径说明节四列表格齐全
- [ ] 未做项如实写未做
- [ ] 争议口径有备选结果差异

**⑥禁忌与易错点**：口径说明写事实与选择，不写辩解；未做的声称已做是交付诚信问题，不是文案问题。本条按报告意见已从「通用步骤版」升级为带字段模板的可执行规程。

**⑦参数表**：口径说明表字段 4 列：口径名／采用与否／理由／出处。

### 【周期切换按精确时刻】

**①目标与适用场景**：以时刻而非日期为界的周期划分系统：切换发生在精确时刻，交界附近必须分钟级处理。触发场景：计算涉及周期归属（节气、班次、账期类边界）。

**②前置条件**：底层库能给出精确切换时刻（时分秒级）；只能给日期的库不满足本条，先换库或补算。

**③操作步骤**：
1. 归属判定用时刻比较：输入时刻与切换时刻比大小定归属 → 判定信号：交界日任意抽 3 个时刻（界前、界上、界后）归属正确。
2. 圈定交界窗口：切换时刻前后各取一段（如各 24 小时，具体宽度按业务容错在规格里定死并留痕） → 判定信号：规格文件里有窗口宽度数值，不是「附近」二字。
3. 窗口内输入单列为专项回归用例逐个验证 → 判定信号：用例清单与窗口定义对应，改动管线后全量重跑全过。

**④失败分支**：
- 发现历史结果按日期近似算过：圈出受影响的交界日批次，按精确时刻重算并逐件更正，不只修新数据。
- 底层库给出的切换时刻与权威来源差分钟级以上：以权威来源为准标定库，差异记入口径说明（见【口径做没做写进交付物】）。

**⑤验收清单**：
- [ ] 归属判定基于时刻比较
- [ ] 交界窗口宽度有数值并留痕
- [ ] 窗口用例全量回归通过

**⑥禁忌与易错点**：远离交界的常规输入不必全量按分钟级成本处理，关键是识别并圈定窗口；按日期近似处理，交界日结果会整批翻转——这是这类系统最常见的第一翻车点。

**⑦参数表**：窗口宽度：源材料未给统一值，标定规程＝按业务可接受的归属误差反推（误差容忍越小窗口越宽），定值后写入规格并作为回归基线，不许口头约定。

### 【结构化先转文本再投喂】

**①目标与适用场景**：结构化数据喂给语言模型前，先经一道「转文本」工序，排成带标签的结构化文本。触发场景：管线中模型需要读取计算层输出时。

**②前置条件**：计算层输出字段已定型；转文本模板与字段一一对应。

**③操作步骤**：
1. 按模板把每个字段渲染为「标签：值」行，层级用缩进或分节表达 → 判定信号：文本版与原始结构逐字段可对账，字段数相等。
2. 转换工序自带字段对账：原文有而文本版无的字段当场报错 → 判定信号：故意删一字段做测试，对账环节能报警。
3. 模型只读文本版写作 → 判定信号：成稿引用的字段值与文本版一致（抽查）。

**④失败分支**：
- 字段对账报警：停在转换层修模板，不许把缺字段的文本版先喂给模型「凑合出一稿」。
- 嵌套过深渲染后可读性崩坏：改分节渲染或拆多次投喂，不把原始结构直接甩给模型。

**⑤验收清单**：
- [ ] 文本版与原始结构字段数相等
- [ ] 对账报警经故意缺字段测试有效
- [ ] 成稿字段值与文本版抽查一致

**⑥禁忌与易错点**：转文本不能丢字段——转换工序本身要做对账，原文与文本版逐项可追溯；实测模型读带标签文本的准确率高于读裸 JSON，不要省这道工序。

**⑦参数表**：无数值参数。对账判线：字段数相等且逐项可回指。

### 【输出校验加模板渲染】

**①目标与适用场景**：生成层收口定式：模型只产固定结构数据，校验脚本查结构与引用，最终页面由固定模板渲染。触发场景：任何要交付成页面的生成管线。

**②前置条件**：输出结构（schema）已定义，含分析结论字段与依据字段；模板已定版。

**③操作步骤**：
1. 模型输出按 schema 产数据，不产排版 → 判定信号：输出可被 schema 校验器完整解析。
2. 校验脚本查两项：结构完整（必填字段齐）、引用真实（依据指针能定位到真实事实） → 判定信号：故意构造一条假引用，校验能拦下。
3. 校验通过才进模板渲染 → 判定信号：渲染产物只来自通过校验的数据；未通过的留在校验报告里。

**④失败分支**：
- 校验不通过：回生成层重产，不许人工在渲染结果上直接改字补结构——改字会绕过下一轮校验。
- 模板渲染异常（溢出、乱码）：修模板，不改数据迁就模板。

**⑤验收清单**：
- [ ] 输出全部过 schema 校验
- [ ] 假引用注入测试被拦下
- [ ] 页面只由校验通过的数据渲染

**⑥禁忌与易错点**：模板渲染保证形式稳定，不保证内容质量；校验只查结构与引用存在性，判断对错仍靠【解读链写死顺序标依据】的方法约束。内容与颜值解耦：模型不碰排版。

**⑦参数表**：无数值参数。校验项 2 类：结构完整／引用真实。

### 【三类边界案例回归对齐】

**①目标与适用场景**：计算管线的验证法：三类已知答案的边界案例做回归，与权威工具逐项对齐。触发场景：管线新建、改动或换库后。

**②前置条件**：权威工具（官方实现或公认标准实现）可得；三类案例的权威答案已逐项取得。

**③操作步骤**：
1. 建固定案例集，三类各取若干：跨周期边界的日期、历史特殊时制覆盖的日期、临界时刻 → 判定信号：案例集文件固定存放，含输入与权威答案两列。
2. 管线输出与权威答案逐项对齐，不一致逐条记差异与口径归属 → 判定信号：对齐表无「大致一致」，每项是「一致」或「差异＋原因」。
3. 同一输入连跑两次，结果必须一致 → 判定信号：双跑输出逐字节相同。

**④失败分支**：
- 与权威工具不一致且查明是权威工具口径不同：记录口径归属并在口径说明中声明本管线采用哪一口径，不悄悄选一个当标准。
- 双跑不一致：先定位非确定性来源（见【计算归脚本写作归模型】），回归暂停，不许挑一次「对的」结果交付。

**⑤验收清单**：
- [ ] 案例集三类齐全、答案有权威出处
- [ ] 对齐表逐项有结论
- [ ] 双跑一致性通过

**⑥禁忌与易错点**：常规案例测不出边界错误；这三类恰好覆盖周期切换、历史规则、时刻精度三大翻车点，不许用常规案例充数。

**⑦参数表**：案例类型 3 类：跨周期边界日期／历史特殊时制日期／临界时刻。一致性判线：同输入双跑结果逐字节一致。

### 【非商用许可只借方法】

**①目标与适用场景**：选型许可纪律：功能最全的现成包挂非商用许可时，只借鉴方法论，不搬代码与文案。触发场景：立项选型评估任何第三方包。

**②前置条件**：能取得每个候选包的许可证原文；拿不到原文的按许可未核处理，不进入代码地基候选。

**③操作步骤**：
1. 逐包读许可证原文，判定商用可用性并留摘录 → 判定信号：选型表每包有许可结论与原文出处。
2. 代码地基只选宽松许可（如 MIT 类）的库 → 判定信号：依赖清单中无非商用许可包。
3. 非商用包只读其方法结构（步骤、组织方式），实现另起炉灶 → 判定信号：代码与文案全文检索，无与该包相同的表述段落与独有数据。

**④失败分支**：
- 已误搬非商用代码进项目：立即整段替换重写并留处置记录，不许「改几个变量名」式洗稿。
- 宽松许可替代品功能缺一截：缺口自研补齐或降级需求，不以功能差距为由破例用非商用包。

**⑤验收清单**：
- [ ] 每包许可结论有原文出处
- [ ] 依赖清单无非商用包
- [ ] 借鉴包的代码/文案零搬运

**⑥禁忌与易错点**：借鉴方法论也要保持距离——步骤结构可以学，原文表述与独有数据不能抄；拿非商用代码做收费产品是直接侵权，事后替换成本远高于立项绕开。

**⑦参数表**：无数值参数。代码地基许可白名单：宽松许可（MIT 类）；非商用许可处置＝只读方法。

### 【对象未确认列候选标可信度】

**①目标与适用场景**：研究目标对象无法唯一确认时，列高度吻合的候选并逐个标可信度，不拿相似品冒充本体。触发场景：检索结果出现多个疑似对象、无法定案。

**②前置条件**：候选的吻合点与存疑点可逐项列出；完全无候选时不适用本条，按未核实处理。

**③操作步骤**：
1. 报告头部写明「无法唯一确认」 → 判定信号：该声明在结论之前出现，读者不会先入为主。
2. 候选逐个列：吻合点、存疑点、可信度评级及评级依据（多源印证程度：独立来源数与来源等级） → 判定信号：每个评级能回指具体印证来源，不是印象分。
3. 后续分析如需引用候选，引用处带候选身份与可信度，不在行文中途把候选升格为本体 → 判定信号：全文检索本体名称，无无标记的升格引用。

**④失败分支**：
- 新证据使某候选可定案：更新报告并注明定案证据，原候选列表保留作过程留痕。
- 所有候选可信度都低：结论写「对象未确认」，研究转入待查，不挑最高分的凑数。

**⑤验收清单**：
- [ ] 「无法唯一确认」声明在位
- [ ] 每候选有吻合点、存疑点、带依据的可信度
- [ ] 无候选被冒充本体引用

**⑥禁忌与易错点**：冒充本体得出的后续结论全部建在错误前提上；可信度评级要有依据，不能凭印象打分。

**⑦参数表**：无数值参数。可信度依据：独立印证来源数 × 来源证据等级（按【结论标五级证据】）。


## 共享存储写入规范（8 条）

本章八条是一条完整写入链：写前问格式（36）→照抄成功样本（37）→先整库备份（38）→写后真解析器验字节（39）→引号即格式（40）→消费者回读对数（41）→错误成串扫修（42）→容错只是兜底（43）。按序执行，不跳环。

### 【写前先问消费者格式】

**①目标与适用场景**：往共享存储（配置文件、共享库、台账文件）写数据前，先搞清真正读取它的解析器/程序期望什么格式。触发场景：任何对多方共读存储的写入。

**②前置条件**：能定位至少一个消费者（代码、程序或其现存数据）。消费者有多个时以最严格的为准。

**③操作步骤**：
1. 找到消费者代码或用其现存数据反推格式契约五项：字段、类型、引号、编码、分隔方式 → 判定信号：契约五项逐项有据（代码位置或样本条目），不是「应该是这样」。
2. 找不到消费者代码、也无现存数据（全新存储）：以该格式的官方规范为契约，并把契约文档随数据一同落盘 → 判定信号：存储旁有契约文档，后来写者不用再猜。
3. 契约确认后才动手写，写后走【用真解析器验字节】 → 判定信号：写入时间晚于契约确认记录。

**④失败分支**：
- 定位不到任何消费者：先别写——无人读取的存储写了也是死数据；把「消费者待定位」记入待办。
- 多个消费者格式要求冲突：以最严格者为准并在契约文档注明冲突点，不按最宽松者写完赌其余能忍。

**⑤验收清单**：
- [ ] 格式契约五项逐项有据
- [ ] 全新存储有契约文档随数据落盘
- [ ] 写入发生在契约确认之后

**⑥禁忌与易错点**：格式契约的权威在消费者一侧，不在写作者的编辑器观感里；写方觉得「差不多」的格式，读方可能直接解析失败。

**⑦参数表**：契约项 5 项：字段／类型／引号／编码／分隔方式。

### 【新记录照抄成功样本】

**①目标与适用场景**：新增记录时照抄消费者已成功加载的现存记录结构，只替换值。触发场景：在既有存储里追加记录。

**②前置条件**：存储里有可确认「已被消费者成功加载过」的记录（有加载日志或长期在用且无报错）。

**③操作步骤**：
1. 挑最近一条成功加载的记录作模板，复制其字段顺序、引号风格、分隔与转义 → 判定信号：新记录与模板做结构 diff，除值以外零差异。
2. 只替换值，值内含分隔符/引号时按模板同类值的转义方式处理 → 判定信号：含特殊字符的新值经真解析器回读后与原值逐字相等。
3. 写后走【用真解析器验字节】与【消费者回读对数】 → 判定信号：两环通过才算新增完成。

**④失败分支**：
- 样本疑似历史遗留的错误格式（靠容错兜底才没炸）：先按【容错只是兜底】确认它是标准还是例外，是例外则换标准样本，并把该坏样本登记待修。
- 存储里无任何成功样本（空库首写）：转【写前先问消费者格式】的官方规范路径。

**⑤验收清单**：
- [ ] 新记录与模板结构 diff 仅值不同
- [ ] 特殊字符值回读逐字相等
- [ ] 验字节与回读对数两环通过

**⑥禁忌与易错点**：成功样本是已被消费者验证过的格式，比任何文档描述都可靠；不要按自己理解拼格式——理解偏差恰恰是坏写的来源。

**⑦参数表**：无数值参数。模板选取判线：最近一条已成功加载记录。

### 【写共享存储先整库备份】

**①目标与适用场景**：改共享存储前的固定动作：先整库备份，再动手。触发场景：任何批量写入、结构变更、扫修类操作。

**②前置条件**：备份位置独立于存储本体（不同目录/介质）；备份工具能整库导出。

**③操作步骤**：
1. 整库备份，文件名带时间戳 → 判定信号：备份文件存在且大小与原库量级一致（不是 0 字节空壳）。
2. 验证备份可读：用真解析器打开备份并回读条数 → 判定信号：备份条数与写入前原库条数相等。
3. 写入方案里同时写明回滚路径（用哪份备份、什么命令恢复） → 判定信号：方案文档含回滚段，备份验证通过后才开始写。

**④失败分支**：
- 备份不可读或条数对不上：停写，先修备份链路；无有效备份时任何写入不许开始。
- 写入后发现坏写：按回滚路径整库恢复，不逐条抢修——逐条修会漏掉未被发现的坏记录。

**⑤验收清单**：
- [ ] 备份带时间戳且条数验证通过
- [ ] 回滚路径写进方案
- [ ] 写入开始时间晚于备份验证时间

**⑥禁忌与易错点**：备份只降低事故成本，不降低写前核对的要求；「反正有备份」不是跳过【写前先问消费者格式】的理由。

**⑦参数表**：无数值参数。备份判线：解析可读＋条数与原库相等。

### 【用真解析器验字节】

**①目标与适用场景**：写入后的验证标准：用消费者实际使用的解析器，解析刚写进去的确切字节。触发场景：每次共享存储写入完成时。

**②前置条件**：能调用与消费者同款同版本的解析器（同库、同配置）；只有「类似」解析器时结论降格并注明。

**③操作步骤**：
1. 写完立即以解析器回读刚写入的记录（按确切字节，不是编辑器里的显示文本） → 判定信号：解析无异常且读回字段值与写入值逐项相等。
2. 解析报错时记下报错位置与字符特征 → 判定信号：错误特征（字段、引号型、转义型）明确到可供【格式错误成串扫修】当扫描特征。

**④失败分支**：
- 解析失败：立即停止继续写入，按【写共享存储先整库备份】的备份回滚，保留坏写样本供扫修，不在坏库上接着写。
- 本地解析通过但消费者仍报错：查解析器版本/配置差异，以消费者环境为准复测，本地结论作废。

**⑤验收清单**：
- [ ] 回读用的是消费者同款解析器
- [ ] 读回字段值与写入值逐项相等
- [ ] 失败时有回滚与坏样本留存记录

**⑥禁忌与易错点**：「在编辑器里能打开、肉眼看着没问题」不算数——引号、转义、编码问题肉眼几乎看不出来，只有真解析器能当场判错。解析通过只证明格式合法，不证明内容正确，内容另走【消费者回读对数】与业务核对。

**⑦参数表**：无数值参数。判线：解析零异常＋字段值逐项相等。

### 【引号风格即格式】

**①目标与适用场景**：结构化文本里引号风格本身是格式的一部分，手改引号等于改格式。触发场景：编辑含引号的结构化记录（JSON、CSV、配置文件）时手痒想「统一一下引号」。

**②前置条件**：能区分手工编辑与序列化工具整体重写：前者适用本条，后者允许但须整条重验。

**③操作步骤**：
1. 发现引号风格不顺眼：不改，或改前先确认消费者契约（见【写前先问消费者格式】）是否允许该风格 → 判定信号：无契约依据的引号改动零发生。
2. 确需改风格时，改完对整条记录重新走真解析器验证 → 判定信号：该条记录在改后解析通过且字段值不变。
3. 批量风格调整只许用序列化工具整体重写，逐条解析复验 → 判定信号：全批复验通过率 100%，失败条单独列出处理。

**④失败分支**：
- 手改后解析失败：用备份恢复该条，不手工「再改回去」——手工往返只会叠加错误。
- 发现历史上已有人手改过一批：按错误特征走【格式错误成串扫修】。

**⑤验收清单**：
- [ ] 无无依据的手工引号改动
- [ ] 每次风格变更后整条重验通过
- [ ] 批量调整由工具完成且全量复验

**⑥禁忌与易错点**：单双引号在不同解析器里转义规则不同，手改后常出现整条记录失效，而改动者往往以为只是「美化」。

**⑦参数表**：无数值参数。判线：引号变更＝格式变更，必整条重验。

### 【消费者回读对数】

**①目标与适用场景**：写入成功的判据：通过消费者本身回读，条数与预期对上。触发场景：批量写入或新增记录后。

**②前置条件**：消费者提供回读路径（接口、列表、查询）；预期条数在写入前已算清（写前总数＋本次新增数）。

**③操作步骤**：
1. 写后经消费者回读全量，核对总数 → 判定信号：回读总数＝预期总数，一条不差。
2. 抽查新增条目的字段内容 → 判定信号：抽查条目字段值与写入值一致（条数对只证明可见，内容另抽查）。
3. 对不上立即按备份回滚并查因 → 判定信号：回滚与查因记录在当轮完成，不带病过夜。

**④失败分支**：
- 条数多了：查是否重复写入（重试未判重），删重后重新对数并补判重逻辑。
- 条数少了或新增不可见：优先怀疑格式、缓存、索引三类原因，按此序排查，不先怀疑消费者坏了。

**⑤验收清单**：
- [ ] 回读总数与预期相等
- [ ] 新增条目抽查字段一致
- [ ] 不一致时已回滚查因

**⑥禁忌与易错点**：写接口返回成功不等于消费者读得到——中间的格式、缓存、索引都可能让新记录「写了但不存在」；只看写入返回是假验收。

**⑦参数表**：判线：回读条数＝写前条数＋新增条数（整数相等，无容差）。

### 【格式错误成串扫修】

**①目标与适用场景**：发现一处格式错误时默认它不是孤例，按相同特征扫全库一并修。触发场景：任一坏写被验出时。

**②前置条件**：首条错误的特征可精确描述（字段名＋错误形态，如「某字段单引号未转义」）；特征模糊到会误伤正常记录时先收窄特征。

**③操作步骤**：
1. 从首条错误提炼可机检的特征模式 → 判定信号：用该模式扫全库，命中集里人工抽查 3 条全是真错误，误报为零才继续。
2. 命中记录先整库备份（见【写共享存储先整库备份】），再逐条修复 → 判定信号：修复数与命中数相等。
3. 修完全批走真解析器复验 → 判定信号：全库解析通过、回读条数不变。

**④失败分支**：
- 特征误报率高：停扫，重新提炼特征（加字段、加上下文条件），不用宽特征硬修。
- 修复中发现第二种错误形态：单独立项再扫一轮，不顺手混修——混修后无法归因。

**⑤验收清单**：
- [ ] 特征模式经抽查零误报
- [ ] 命中全部修复且有备份
- [ ] 修后全库解析与对数通过

**⑥禁忌与易错点**：成串错误通常来自同一次批量写入或同一种手工习惯，只修一处等于留着其余的雷；但扫修前必须确认特征可精确匹配，误判正常记录一起「修坏」是另一种事故。

**⑦参数表**：无数值参数。判线：命中集抽查误报＝0 才可批量修。

### 【容错只是兜底】

**①目标与适用场景**：给读取侧加容错（宽松解析、默认值、跳过坏行）只能作兜底，不能代替把记录写对。触发场景：有人提议「读的时候容错一下就行」时。

**②前置条件**：能区分数据源可控性：自家可控写入适用本条严标准；外部不可控数据源容错是主要防线，可加强。

**③操作步骤**：
1. 容错可以加，但每类容错命中必须记日志（记录标识、命中规则、原始字节） → 判定信号：日志里能按周统计各类容错命中次数。
2. 命中日志形成待修清单，坏记录同步修复 → 判定信号：待修清单有进有出，命中数呈下降趋势，不是只涨不消。
3. 定期复查：同一规则命中不降反升，说明写侧在持续产坏数据，转【格式错误成串扫修】处理写侧 → 判定信号：复查记录存在且有处置结论。

**④失败分支**：
- 容错兜不住的坏记录（解析直接崩）：按坏写事故处理，回滚加扫修，不继续加容错层层包裹。
- 外部数据源坏得太多：容错加强的同时向数据提供方反馈，不默默全盘吞下。

**⑤验收清单**：
- [ ] 容错命中全部有日志
- [ ] 待修清单在销账
- [ ] 无「只加容错不修记录」的遗留项

**⑥禁忌与易错点**：容错会掩盖错误积累，等容错也兜不住时，爆出来的是整批历史坏数据；对自家写入，标准永远是写对。

**⑦参数表**：无数值参数。健康判线：容错命中数随修复逐期下降。


## 通道协议研究（19 条）

### 【通道能力分两层评】

**①目标与适用场景**：评估一条消息通道能不能发某种内容，分参数层（参数构造是否正确）与投递层（服务端是否真放行）两层取证。触发场景：为新通道/新内容类型下「支持/不支持」结论前。

**②前置条件**：参数层有类型定义或实现代码可查；投递层有可实发的测试对象与接收端。

**③操作步骤**：
1. 参数层：查类型定义与实现代码，确认该内容类型的参数构造方式存在且可构造 → 判定信号：能构造出一份通过本地校验的完整请求。
2. 投递层：用真实账号实发，以接收端实收为准（记录法见【投递结果双轨记录】） → 判定信号：投递层结论至少有成功与失败各一次的实发记录；只有单次成功时结论标「单次实证、未成定论」。
3. 结论分两层落笔：参数层结论与投递层结论各写一行，互不合并 → 判定信号：结论页两行齐全，无「支持」一词跨层使用。

**④失败分支**：
- 参数全对但投递被拒：结论写「参数层通过、投递层被拒（权限/策略）」，不回头乱改参数。
- 投递层结论只对测试时的账号类型与通道状态成立：账号形态变化后投递层重验，参数层结论可沿用。

**⑤验收清单**（本条专属）：
- [ ] 参数层与投递层分别有结论
- [ ] 投递层样本含成功与失败记录，或已标注单次样本的降格说明
- [ ] 结论未出现跨层合并表述

**⑥禁忌与易错点**：实测出现过参数全部正确、仍被服务端在投递或权限层拒绝的情况——只评参数层会得出「支持」的假结论。

**⑦参数表**：无数值参数。投递层样本量判线：成功＋失败各 ≥1 次实发记录才下定论。

### 【投递结果双轨记录】

**①目标与适用场景**：通道实验每次发送同时记两列：接口返回与终端实收。触发场景：一切通道能力实验。

**②前置条件**：接收端观测手段就位，最低配置三选一：第二台设备登录接收账号蹲守、第二个账号互发、或接收端本地日志可读。三者皆无时只能记接口层，结论按【通道能力分两层评】降格。

**③操作步骤**：
1. 发送时记接口列：成功/失败、消息编号、错误码与错误文案原文 → 判定信号：文案逐字留存，不是转述大意。
2. 记实收列：收到／未收到／形态不对，形态不对再分三类记：样式降级（富形态变纯文本）、被转成文件/链接、延迟到达（超过正常时延后才到） → 判定信号：实收列每条有观测依据（截图、日志时间戳或接收端确认时间）。
3. 两列不一致时以实收为准下结论，接口列只作排障线索 → 判定信号：结论引用的是实收列内容。

**④失败分支**：
- 实收观测中断（接收设备掉线）：该条实验作废重做，不拿接口成功补位。
- 延迟到达与未收到难区分：设观测窗口（按通道正常时延的数倍，在实验方案里预先写明），窗口外到达记延迟，窗口结束未到记未收到。

**⑤验收清单**：
- [ ] 每条实验双列齐全
- [ ] 形态不对已按三类归类
- [ ] 结论以实收列为准

**⑥禁忌与易错点**：接口成功与真收到可以不一致，只记接口返回会把「发出去了」误报成「送达了」。

**⑦参数表**：记录列 2 列：接口返回（成功/消息编号/错误码＋文案）／终端实收（收到/未收到/形态不对三类）。

### 【类型有不等于管线支持】

**①目标与适用场景**：协议类型定义里存在某种媒体类型，不等于官方发送管线支持发送它。触发场景：有人引类型定义主张「协议支持××类型」时。

**②前置条件**：能查到官方能力表与功能请求（feature request/issue）记录；查不到官方材料时只能走到投递实证一步定案。

**③操作步骤**：
1. 先查官方能力表：该类型是否列在官方支持清单 → 判定信号：有官方页面或文档定位。
2. 再查功能请求记录：该类型是否有长期未实现的官方请求 → 判定信号：存在官方未实现请求即强烈提示管线不支持，记录其状态。
3. 最后找投递实证（按【投递结果双轨记录】） → 判定信号：定案只认实证，类型定义只作线索出现在记录的「线索」栏。

**④失败分支**：
- 官方能力表滞后于实现（表上没写但实发能通）：以实证为准定案，并在记录里注明表与实证不一致。
- 实证被拒但类型定义存在：结论写「仅定义存在」，归档供后来者免试。

**⑤验收清单**：
- [ ] 能力表、功能请求、投递实证三路都查过
- [ ] 定案依据是实证而非类型定义
- [ ] 结论措辞与证据等级匹配（见【无投递记录不写支持】）

**⑥禁忌与易错点**：类型定义常含预留、内部或已废弃类型，照定义开发会一路做到投递环节才发现被拒——最晚、最贵的发现方式。

**⑦参数表**：证据优先级：投递实证＞官方能力表＞功能请求记录＞类型定义。

### 【错误码先读文案】

**①目标与适用场景**：通道排障次序纪律：先读错误文案，再对错误码表。触发场景：任何发送失败拿到错误返回时。

**②前置条件**：返回里有错误文案字段可读；文案缺失时本条跳到第 3 步的对照实验。

**③操作步骤**：
1. 逐字读错误文案，按文案语义先分因：令牌过期、配额耗尽、包体过大、限流、类型被拒等 → 判定信号：分因结论能指出文案中的关键词句。
2. 再用错误码交叉验证：同码多因时以文案为准 → 判定信号：记录里同时有文案分因与码值，两者冲突时注明以文案定案。
3. 文案缺失或含糊：回到单变量对照实验定因（见【排障先删字段对照】【最小结构反向试】） → 判定信号：实验每次只动一个变量，定因有实验记录支撑。

**④失败分支**：
- 文案与码指向不同成因：按文案处置一次并观察结果，结果不对再按码的成因处置，全程留痕，不同时改两处。
- 文案是通用兜底话术（「未知错误」类）：按令牌过期类先处置（冷却/刷新令牌）再观察，这是本项目实测的归因顺序，仍无果转对照实验。

**⑤验收清单**：
- [ ] 定因记录含文案原文与关键词句
- [ ] 码值仅作交叉验证，未单独定因
- [ ] 文案不足时有对照实验记录

**⑥禁忌与易错点**：同一错误码有五六种成因，只看数字必然误判——把令牌过期当限流去等、把类型被拒当配额去拆包，都是实测过的弯路。

**⑦参数表**：同码成因量级：五六种（令牌过期／配额耗尽／包体过大／限流／类型被拒等）。定因顺序：文案→码表→对照实验。

### 【回复配额与包体上限】

**①目标与适用场景**：非官方通道的两个未公开上限——每条入站消息可回复条数、单个数据包体积——设计发送逻辑前必须实测出本通道的值。触发场景：接入任何非官方消息通道时。

**②前置条件**：有可反复实发的测试会话（自己的测试对象，不拿真实用户当探测对象）；发送结果按【投递结果双轨记录】记。

**③操作步骤**：
1. 先用本项目实测值作设计起点：回复配额约 10 条/每条入站消息、单包上限约 16KB（本项目通道实测值，证据等级：实测报告；你的通道必须按下两步复测，不许直接套用） → 判定信号：设计文档里两值标明「待复测」状态。
2. 配额二分探测：对一条入站消息连续回复，条数按 1、2、4、8…倍增发，直到出现被拒/静默丢弃，再在最后成功数与首个失败数之间二分收窄 → 停止信号：错误文案出现配额类语义，或接口成功但实收列缺条（静默丢弃）；判线：连续两轮二分结果一致，取较小值为安全配额，设计时再留 20% 余量。
3. 包体二分探测：构造内容长度可控的消息（纯 ASCII 填充，长度按字节计），从 1KB 起倍增：1、2、4、8、16、32KB…，首个被拒点后二分收窄 → 停止信号：错误文案出现包体过大类语义或实收未达；判线同上，安全上限取收窄后较小值并留 20% 余量。注意：纯 ASCII 填充时字节数＝字符数，若通道上限按字符计而实际内容含多字节字符（如中文），按字节测得的上限会偏乐观——分片落地时一律按实际编码后的字节数核算（见【大文件分片传输校验法】）。
4. 设计落地：长内容按安全上限分片，回复合并发送省配额；两值做成可调参数 → 判定信号：代码中两值为配置项，不是写死常数。

**④失败分支**：
- 探测触发限流或会话暂停：立即停探，按【会话过期先冷却】冷却后再继续，不硬顶——探测把账号探封了就本末倒置。
- 上限随账号状态漂移（新号更严）：以最严状态下测得的值为设计值，并在记录里注明账号状态。

**⑤验收清单**：
- [ ] 两值均有本通道复测记录（步长、停止信号、错误文案留存）
- [ ] 设计值带 20% 余量且为可调参数
- [ ] 分片与合并策略按实测值落地

**⑥禁忌与易错点**：上限不写在文档里，撞上时表现为发送被拒或静默失败，事后极难定位到是配额问题；不许拿真实用户的会话做探测。

**⑦参数表**：回复配额参考值 ≈10 条/入站消息、单包上限参考值 ≈16KB（均为本项目通道实测，[实测报告｜本项目通道实验记录｜见【错误码先读文案】的成因分类]；复现条件：普通账号、非限流状态）。探测法：倍增＋二分，安全值取小并留 20% 余量。

### 【会话过期先冷却】

**①目标与适用场景**：会话过期类错误的处置次序：先冷却等待，持续出现再重新扫码登录。触发场景：发送失败且文案指向会话过期/暂停。

**②前置条件**：能读到错误文案；能区分三类相近状态——会话过期（文案含会话过期/暂停语义，且通道行为是整段暂停）、限流（文案含频率/限流语义，只拒高频请求）、令牌过期（文案含令牌/token 语义，刷新凭据可解）。区分不清时按【错误码先读文案】走对照实验。

**③操作步骤**：
1. 认出会话过期：错误码为该通道的会话暂停类专属码（与限流共用码不同），文案样本形态为「会话已过期/暂停」类表述、且后续所有发送均被拒而不只是高频被拒 → 判定信号：低频单发一条仍被拒，且文案与限流样本比对不一致。
2. 立即停发冷却约 1 小时（源材料口径：官方行为即暂停约一小时，[官方口径转述｜源材料记录]，复现条件：过期触发后不做任何重试） → 判定信号：冷却期内发送尝试次数为 0，日志可查。
3. 期满先低频观察：单发一条测试，通了再逐步恢复正常节奏 → 判定信号：测试条实收成功。
4. 冷却后仍持续失败，才走重新扫码登录 → 判定信号：重扫发生在至少一轮完整冷却之后。

**④失败分支**：
- 冷却中有人催发：不破例试发——试发会刷新暂停计时，把一小时拖得更久；给催方看冷却截止时间。
- 文案指向账号异常（封禁类语义）：不走本条傻等，按账号问题另行处置。

**⑤验收清单**：
- [ ] 定因有文案样本与三类状态区分记录
- [ ] 冷却期内零发送尝试
- [ ] 恢复先单发观察、重扫在完整冷却之后

**⑥禁忌与易错点**：过期后立刻盲目重登、反复重试，会把短暂暂停拖成更重的风控处置；「约 1 小时」是官方口径转述，你所在通道的实际暂停时长以一次完整冷却实测为准并回填本条。

**⑦参数表**：冷却时长 ≈1 小时（官方口径转述，待本地实测回填）；处置顺序：停发冷却→低频观察→重扫。

### 【同名异口径字段逐个查】

**①目标与适用场景**：同一字段名在不同接口/结构里口径不同（如某密钥在上传接口要裸十六进制串、在发送结构里要再编码一层），逐个查实不凭直觉套用。触发场景：接入新协议、或同名字段跨接口复用时。

**②前置条件**：能拿到三路材料：类型定义、真实抓包样本、接口文档；缺任何一路先标明，结论相应降格。

**③操作步骤**：
1. 字段枚举三路对照：从类型定义导出全部字段清单，从抓包样本导出实际出现字段，从文档导出声称字段，三份清单对齐成一张总表 → 判定信号：总表每字段有三路出处标记，缺哪路一目了然。
2. 逐字段写判别测试样例：每个字段构造一个「按口径 A 填」与「按口径 B 填」的对照发送，只变这一个字段 → 判定信号：每字段有且仅有一组对照实验记录，结论（裸串/再编码/原样）由实收结果定。
3. 把定案口径写回总表对应行，注明定案方式（实测/文档） → 判定信号：总表无「待定」字段进入正式代码。

**④失败分支**：
- 抓包样本拿不到：只用定义＋文档两路，结论标「未实测」，上线前必须补一组对照实验。
- 对照实验两口径都通：说明该字段服务端宽容，记录「双口径可通」并选与官方样本一致的一种固定下来，不许混用。

**⑤验收清单**：
- [ ] 字段总表三路出处齐全
- [ ] 每字段有对照实验或明确的未实测标记
- [ ] 正式代码字段口径与总表一致

**⑥禁忌与易错点**：字段名相同最容易让人想当然；错一层编码就是整条链路不通，且报错往往不指向编码问题。本条按报告意见已从「通用步骤版」补齐枚举与判别规程。

**⑦参数表**：无数值参数。枚举来源 3 路：类型定义／抓包样本／接口文档；每字段判别实验 1 组（双口径对照）。

### 【参数单位多源交叉】

**①目标与适用场景**：协议参数单位（秒/毫秒、字节/千字节）社区说法冲突时的定案法。触发场景：同一参数查到两种以上单位说法。

**②前置条件**：能找到官方文档与至少两家独立实现；只有转述帖时不定案。

**③操作步骤**：
1. 以官方文档为基准记下单位 → 判定信号：有文档原文定位。
2. 找两家以上独立实现核对它们代码里的换算 → 判定信号：实现来源互相独立（不是同一代码的搬运），换算口径一致。
3. 有条件时做一次受控实测定案：按候选单位各设一个明显可分的值（如超时设 2 与 2000），看实际行为落在哪边 → 判定信号：实测行为与定案单位一致；实测优先于文献一致。

**④失败分支**：
- 多源一致但实测打架：以实测为准，并记录「文献同源抄错」的可能，不回头改实测迁就文献。
- 官方文档本身含糊：标未核实（见【无权威来源列未核实】），代码里把单位换算集中到一处常量，定案后只改一处。

**⑤验收清单**：
- [ ] 定案有官方文档定位＋两家独立实现印证，或有实测记录
- [ ] 单位换算在代码中单点定义
- [ ] 冲突说法与定案依据留痕

**⑥禁忌与易错点**：单位错一位数量级，表现是「偶尔超时」「偶尔超限」这类幽灵问题，极难事后定位；单一转述不作数。

**⑦参数表**：无数值参数。定案优先级：受控实测＞官方文档＋多源实现＞单一转述（不作数）。

### 【排障先删字段对照】

**①目标与适用场景**：请求被判参数无效时的首选排障法：单变量删字段对照。触发场景：完整请求被拒、错误文案指向参数问题。

**②前置条件**：有可反复试发的测试对象（不在生产会话上试）；完整请求样本已保存。

**③操作步骤**：
1. 嫌疑排序：官方类型里没有的额外字段排最前，其余按新近改动排序 → 判定信号：有一张有序嫌疑清单。
2. 每次只删一个字段发一遍，其余字节不动 → 判定信号：每轮实验记录只对应一个变量变化。
3. 删掉某字段后通过 → 该字段即触发源，单独研究它的合法形态；全删完仍不过 → 转【最小结构反向试】 → 判定信号：定因结论有对应轮次的实验记录。

**④失败分支**：
- 删字段改变了业务语义导致另一类报错：记为「该字段必填」，恢复它并换下一个嫌疑，不把它当触发源。
- 试发触发限流：暂停实验，按【会话过期先冷却】的节奏纪律等恢复，不换号硬试。

**⑤验收清单**：
- [ ] 实验单变量、有轮次记录
- [ ] 触发字段已定位或已明确转最小结构法
- [ ] 实验全程在测试对象上进行

**⑥禁忌与易错点**：全量猜测式改参数只会把变量搅浑；多字段同时改，通了也不知道是谁的功劳。

**⑦参数表**：无数值参数。变量纪律：1 轮 1 字段。

### 【最小结构反向试】

**①目标与适用场景**：全字段路线被拒时反向尝试：只留必填字段的最小结构先跑通，再逐个加回。触发场景：【排障先删字段对照】删到最后仍不过，或请求结构复杂无从下手。

**②前置条件**：能判定哪些字段是必填（类型定义中的必填标记）；有测试对象。

**③操作步骤**：
1. 构造最小可用请求（仅必填字段）验证投递 → 判定信号：最小结构实收成功；不成功说明问题不在字段层，转查身份/权限（见【原样重发切分问题】）。
2. 按业务必需程度排序，逐个加回字段，每加一个发一遍 → 判定信号：每个字段有独立的加回实验记录。
3. 加到某字段被拒 → 该字段即嫌疑源，停在上一可用版本研究它 → 判定信号：可用版本与失败版本只差这一个字段。

**④失败分支**：
- 最小结构就被拒且原样重发也失败：定性为身份/权限问题，字段排障到此为止。
- 必需字段加回后必被拒：研究该字段的合法取值形态（编码、单位、枚举层），按【同名异口径字段逐个查】处理。

**⑤验收清单**：
- [ ] 最小结构投递结论明确
- [ ] 每个加回字段有独立记录
- [ ] 最终可用结构与失败点定位留痕

**⑥禁忌与易错点**：最小结构跑通不等于可以上线——加回业务必需字段后要再做完整回归；从最小往上加，每步因果清楚，这正是它优于从全字段往下减的地方。

**⑦参数表**：无数值参数。加回顺序：按业务必需程度升序，1 次 1 字段。

### 【原样重发切分问题】

**①目标与适用场景**：把真实入站消息的字节与参数原样复制重发，一刀切分参数问题与身份权限问题。触发场景：自构造请求失败、两类原因纠缠不清时。

**②前置条件**：通道里有真实入站消息样本可取；重发频次可控（本法消耗配额与限流额度）。

**③操作步骤**：
1. 取一条真实入站消息，不改任何字节与参数，走发送路径重发 → 判定信号：重发内容与原消息逐字节一致（哈希相同）。
2. 重发成功 → 发送侧身份与权限无问题，毛病在自构造参数，转【排障先删字段对照】 → 判定信号：结论有重发实收记录支撑。
3. 重发也失败 → 定性身份/权限问题，停下查账号状态与权限层 → 判定信号：后续动作全部转向账号侧，不再改参数。

**④失败分支**：
- 没有真实入站样本：本法不适用，先用测试对象制造一条入站再做。
- 重发成功但自构造仍失败且删字段无果：查自构造与原样的字节级 diff（编码、前缀、字段顺序），按【编码前缀勿手动重复】类问题逐项比。

**⑤验收清单**：
- [ ] 重发样本逐字节一致有哈希记录
- [ ] 切分结论（参数/身份）二选一明确
- [ ] 后续排障方向与切分结论一致

**⑥禁忌与易错点**：重发本身可能触发配额与限流，频次要克制；不要连发多条样本「求稳」，一条定性足够。

**⑦参数表**：无数值参数。样本量：1 条真实入站即可定性。

### 【枚举跨层编号不同】

**①目标与适用场景**：同一枚举在不同协议层编号不同（应用层与传输层各有一套值）。触发场景：写跨层代码、查跨层文档、引用社区代码时。

**②前置条件**：能列出涉及的协议层与各自的枚举定义出处。

**③操作步骤**：
1. 每个枚举值在代码与文档中强制注明层归属（如「应用层·类型3」「传输层·类型3」） → 判定信号：全文检索枚举数值，无无层标记的裸用。
2. 引用社区代码时重点核对它混用哪套：把它的枚举值逐个回查两层定义 → 判定信号：核对表列出每个值的所属层与是否存在混用。
3. 跨层转换集中写一个映射函数并附两层对照表 → 判定信号：转换只发生在一处，代码他处不出现裸数值互传。

**④失败分支**：
- 某值两层定义都查不到：标未核实，不猜；用实发对照实验定它属于哪层。
- 已上线代码发现混用：按影响面整段替换映射，不逐处打补丁。

**⑤验收清单**：
- [ ] 枚举值全部带层标记
- [ ] 社区代码混用核对表完整
- [ ] 跨层转换单点实现

**⑥禁忌与易错点**：社区代码把两套枚举混用是常见错误来源；照抄时最容易连坑一起抄进来。

**⑦参数表**：无数值参数。标记格式：层名＋枚举值，缺一不可。

### 【音频格式不可互替】

**①目标与适用场景**：个人账号语音与企业官方接口的音频格式不可互替，同一「语音」概念编码与封装各不相同。触发场景：跨通道复用现成音频文件时。

**②前置条件**：目标通道的格式要求可查（编码、封装、采样率）；手头有文件头检测手段。

**③操作步骤**：
1. 判断真实编码看文件头字节，不看扩展名 → 判定信号：检测记录写的是文件头特征，不是文件名后缀。
2. 按目标通道要求单独准备音频，格式不符走转码（见【转码链选对库方向】） → 判定信号：待发文件文件头与目标通道要求逐项一致。
3. 发送前小样实发验证 → 判定信号：接收端能正常播放，形态正确（见【投递结果双轨记录】的形态分类）。

**④失败分支**：
- 文件头与扩展名不符的历史文件：按文件头重新归类登记，不改名迁就扩展名。
- 转码后仍被拒：查目标通道是否还有封装层要求（容器、头信息），不只盯编码。

**⑤验收清单**：
- [ ] 待发音频按文件头核验过
- [ ] 无跨通道直接顶替发送
- [ ] 小样实发播放正常

**⑥禁忌与易错点**：扩展名不代表真实编码，顶替发送轻则播放失败，重则整条消息被拒；转码可以弥合差异，但那是走对转码链的事，不是改扩展名的事。

**⑦参数表**：判据：文件头字节特征（与【SILK语音解码链】的文件头校验同法）。


### 【转码链选对库方向】

**①目标与适用场景**：媒体转码选库的方向性原则：通用转码器只做中间格式转换，专用编码库才产目标格式。触发场景：设计任何源格式→目标格式的转码链时。

**②前置条件**：源格式与目标格式都已按文件头确认（见【音频格式不可互替】）；候选库的解码/编码方向可查（文档或实测）。

**③操作步骤**：
1. 先画链路图：源格式→中间格式（如 PCM）→目标格式，每段标注承担库与方向 → 判定信号：链路图每段都有库名，没有「某库应该能编」式空格。
2. 逐段验方向：产出段的库必须有编码能力，用一条小样实跑产出并查文件头 → 判定信号：产出文件头是目标格式特征，不是中间格式冒充。
3. 能用单一库直达目标格式时不绕链 → 判定信号：链路段数取可行方案中的最少。

**④失败分支**：
- 某库装齐了却产不出目标格式：先查它是否只有解码方向（最常见弯路），是则换专用编码库，不在参数里死磕。
- 多段链音质损耗超标：回头找直达库或更高质量的中间格式（无损 PCM），不用有损格式当中间段。

**⑤验收清单**：
- [ ] 链路图每段库与方向明确
- [ ] 产出文件头为目标格式
- [ ] 段数已取最少可行

**⑥禁忌与易错点**：选只有解码方向的库去做编码，是实测过的常见弯路——链装得再齐也产不出目标格式；链路每多一段就多一次质量损耗与失败点。

**⑦参数表**：链路形态：源→中间（PCM 等无损）→目标，共 2 段为常态。

### 【编码前缀勿手动重复】

**①目标与适用场景**：某些编码库的平台变体参数会自动添加协议前缀字节，手动再加会造成双前缀。触发场景：用带平台变体的编码参数产出待发音频时。

**②前置条件**：已知当前编码路径是否用平台变体参数；有文件头字节检查手段。

**③操作步骤**：
1. 编码前查清前缀由谁负责：变体参数自动加的，手动环节就禁止再加 → 判定信号：管线配置里前缀责任方唯一（库或手动，二选一写明）。
2. 产出后校验文件头：前缀只出现一份、其后紧跟正确的格式头 → 判定信号：字节级检查记录在案（如 SILK 类校验前若干字节与标准头一致，见【SILK语音解码链】）。
3. 走原始编码（不用变体）时，前缀按协议手动加，同样校验 → 判定信号：同上。

**④失败分支**：
- 检出双前缀：定位是哪一环重复加，删掉手动那一环并把整批已产出文件按特征扫回重编，不逐个手工删字节。
- 播放器能播但通道拒收：查前缀形态是否与目标通道变体一致，可能错在变体选错而非有无。

**⑤验收清单**：
- [ ] 前缀责任方在配置中唯一写明
- [ ] 产出文件头字节校验通过
- [ ] 双前缀批次已整批重编

**⑥禁忌与易错点**：双前缀音频在多数播放器上直接异常，听感排查容易跑偏到音质问题上；关键是先确认当前路径谁负责前缀。

**⑦参数表**：判线：前缀份数＝1。

### 【语音条不等于实时通话】

**①目标与适用场景**：概念澄清：聊天机器人宣称的「能语音聊天」，多数是异步语音条快速往返，不是实时通话。触发场景：评估任何宣称支持语音通话的机器人/通道方案时。

**②前置条件**：能查该方案的协议层构成（文档或抓包）；只有演示视频时先标未核实。

**③操作步骤**：
1. 问协议层两件事：有没有通话信令、有没有持续音频流端点 → 判定信号：两问都有可指认的协议实体才算有实时通话的地基。
2. 两者缺一 → 定性为语音条往返，按异步标准评估：测单轮往返延迟（发出到对方语音条可播的时间）与条数限制 → 判定信号：评估表用的是异步指标，没有「通话质量」类目。
3. 把定性结论写进评估头部 → 判定信号：采购/设计方看到的第一行就是形态定性。

**④失败分支**：
- 对方坚称是实时但给不出协议实体：按语音条往返定案，举证责任在宣称方。
- 方案是混合形态（信令模拟＋语音条）：如实写混合形态及每段的真实机制，不许整体包装成实时通话。

**⑤验收清单**：
- [ ] 信令与音频流端点两问有明确答案
- [ ] 评估指标与定性形态匹配
- [ ] 形态定性写在评估头部

**⑥禁忌与易错点**：把语音条往返当实时通话采购或设计产品，交互预期会整体错位；语音条往返在很多场景已经够用，澄清概念是为了预期对齐，不是贬低这条路线。

**⑦参数表**：定性判据 2 项：通话信令有无／音频流端点有无，缺一即非实时。

### 【实时语音两条真路】

**①目标与适用场景**：在聊天应用生态里实现真·实时语音只有两条路：一是客户端界面自动化接听＋虚拟声卡注入，二是跳出聊天改用实时音视频组件。触发场景：评估任何「实时语音」方案，先问清对方走哪条路，再逐路评估。

**②前置条件**：方案方能说清其技术路线；说不清的按未核实处理，不进入评估表。

**③操作步骤**：
1. 先定路线：把方案归入路一（界面自动化＋虚拟声卡）或路二（实时音视频组件），两条都不是的，要求其给出协议实体证据（见【语音条不等于实时通话】） → 判定信号：路线栏有明确归属。
2. 逐路按四项评估并各打结论：设备占用（需不需要独占一台带界面的设备常开）、稳定性（界面改版/弹窗对自动化的破坏面）、合规（平台协议与自动化条款，见【视觉接管先查协议风险】）、账号风险（自动化行为的封号暴露面） → 判定信号：评估表两路各一行、四项各有结论与依据，无整表一句「可行」。
3. 两条路的结论分别呈报，不许合并成一个总分 → 判定信号：决策方能按路线分别取舍。

**④失败分支**：
- 路一评估中发现目标客户端频繁改版：稳定性项直接判不合格，不寄望「跟版维护」——维护成本无上限。
- 两条路都判不合格：如实结论「当前无可行真路」，回退到语音条往返方案，不硬凑第三条路。

**⑤验收清单**：
- [ ] 方案路线已归属（路一/路二）
- [ ] 逐路四项评估齐全（设备占用/稳定性/合规/账号风险）
- [ ] 结论按路线分开呈报

**⑥禁忌与易错点**：两条路的代价结构完全不同，不问清路线就比功能，等于拿演示效果代替可行性判断；两条路都绕开了聊天协议本身，账号与设备风险不默认可长期稳定运行。本条按报告意见已把两条路写进步骤与参数表，不再只出现在目标行。

**⑦参数表**：真路 2 条：①客户端界面自动化接听＋虚拟声卡注入；②跳出聊天、改用实时音视频组件。逐路评估项 4 项：设备占用／稳定性／合规／账号风险。

### 【无投递记录不写支持】

**①目标与适用场景**：通道能力结论的措辞纪律：多家开源库实现了某发送函数、但无一有投递成功记录时，结论写「代码存在、投递未证」。触发场景：写任何通道调研结论时。

**②前置条件**：已按【类型有不等于管线支持】查过代码与记录，能区分证据到了哪一层。

**③操作步骤**：
1. 结论措辞按证据三级对号：有投递实证（双轨记录在案）才写「支持」；只有实现代码写「代码存在、投递未证」；只有类型定义写「仅定义存在」 → 判定信号：结论用词与证据层级逐条对得上。
2. 「未证」项如值得投入，立实验项按协议研究方法逐项验，把未证变实证或证伪 → 判定信号：未证项有去向（已立实验/明确放弃），不长期悬空。

**④失败分支**：
- 被要求「先按支持写进方案」：拒绝，方案里该能力标未证并给出实验计划；按已通设计下去，联调才发现从没通过，返工面最大。
- 后来拿到实证：当轮升级措辞并注明实证出处，原「未证」记录保留作过程留痕。

**⑤验收清单**：
- [ ] 结论措辞与证据层级一致
- [ ] 未证项全部有去向
- [ ] 无一处以代码存在冒充支持

**⑥禁忌与易错点**：「未证」不是「不行」，不要把未证写成否定结论吓退投入；同样不许把未证写成支持放行设计。

**⑦参数表**：措辞 3 级：支持（有投递实证）／代码存在、投递未证／仅定义存在。

### 【先发附件保目标】

**①目标与适用场景**：原生语音条路线不通时的降级交付法：音频按文件附件发出，先达成「对方能听到声音」的产品目标。触发场景：原生形态攻坚未通、但交付期限已到。

**②前置条件**：附件通道已实证可发可收（按【投递结果双轨记录】验过）；使用方知晓并接受形态差异。

**③操作步骤**：
1. 交付先行走附件路线，发出后验实收与可播放 → 判定信号：接收端点开能正常播放，记录在案。
2. 向使用方明说形态差异：点开播放，而非语音条样式 → 判定信号：说明在交付记录里，不是口头带过。
3. 原生形态攻坚并行保留，结论出来后切换并回归验证 → 判定信号：攻坚项有独立状态，不因已交付而自动关闭。

**④失败分支**：
- 附件也被拒或形态被二次转换：按双轨记录定位被拒层级，转其他已证通道，不在同一形态上反复试。
- 使用方明确不接受附件形态：如实报告原生未通的结论与预计攻坚路径，不把附件版包装成原生版交付。

**⑤验收清单**：
- [ ] 附件版实收可播放
- [ ] 形态差异已明示并留痕
- [ ] 原生攻坚项状态独立在册

**⑥禁忌与易错点**：不许把附件形态包装成原生语音条已通；产品目标是对方听到声音，形态是实现细节，死磕形态会让整个交付无限期延后——但降级必须明说。

**⑦参数表**：无数值参数。降级判线：产品目标（对方能听到声音）达成即先行交付。


## 语音转写与语音助手评估（21 条）

### 【平台无转写时本地ASR兜底】

**①目标与适用场景**：平台不给语音消息转写文字时，用本地离线 ASR 搭兜底链，让语音照样按文字处理。触发场景：入站语音到了手里只有音频、没有文字。

**②前置条件**：本链以「已能取得原始语音文件」为前提——取得路径按平台而定（入站消息落盘文件、客户端缓存目录导出等），先在你的平台上确认一条可复现的取得路径并记录；取不到原文件的平台不适用本链。解码环节见【SILK语音解码链】，转写引擎选型与实测见【ASR引擎弱CPU先行实测】。

**③操作步骤**：
1. 取原始语音文件：按已记录的取得路径拿到文件，先验文件头确认是目标语音编码 → 判定信号：文件头特征与该平台语音格式一致（见【音频格式不可互替】）。
2. 解码：按编码走对应解码链转成 ASR 可吃的 wav → 判定信号：产出 wav 可播放、采样率与声道符合引擎要求。
3. 本地转写：全程本机离线运行，不调用任何云端转写 → 判定信号：断网环境下整链仍可跑通。
4. 转写文字进入正常文字处理流程，涉关键字段走【转写结果复述确认兜底】 → 判定信号：关键信息未经复述确认不直接落正式记录。

**④失败分支**：
- 取得路径失效（平台改版、缓存加密）：链停在第一步并记录失效形态，转人工听取或请对方补文字，不找破解缓存的旁门。
- 解码失败：按【SILK语音解码链】的头校验分支定位，不跳过解码直接把原文件喂引擎。

**⑤验收清单**：
- [ ] 原始文件取得路径有记录且可复现
- [ ] 整链断网可跑通
- [ ] 关键字段经复述确认才入正式记录

**⑥禁忌与易错点**：多人业务数据的隔离要求决定了不能把语音甩给云端转写服务；兜底链识别质量有上限，不直接当原文用。

**⑦参数表**：链路 4 步：取原文件→解码→本地转写→按文字处理。数据边界：全程本地，不出本机。

### 【ASR引擎弱CPU先行实测】

**①目标与适用场景**：接入任何 ASR 引擎前，先在目标弱 CPU 环境做小规模实测，达标才写接入方案。触发场景：新 ASR 引擎进入候选时。

**②前置条件**：目标弱机的规格已定（线程数、内存上限）；测试集按【引擎验证零业务数据】备好公开样例与自制变体。

**③操作步骤**：
1. **先定 RTF 的定义与测法（全卷首次出现，在此定死）**：RTF（实时率）＝处理时长 ÷ 音频时长，无量纲；RTF＜1 表示快于实时，0.06 表示处理 1 秒音频耗时 0.06 秒；TTS 语境下 RTF＞1（如 2.8）表示合成慢于实时 2.8 倍。测量规程：样本 ≥10 条、每条 5–15 秒短句；首条为预热不计入；逐条记录处理时长与音频时长，RTF 报均值与最大值两数；内存按【进程级峰值内存测量】取进程级峰值 → 判定信号：报告里 RTF 同时有均值与最大值、样本数与单条时长范围、线程数，三者缺一不可比对。
2. 在目标弱机（如 2 线程）上跑五语种短句样本，逐条记 RTF、峰值内存、可懂语种 → 判定信号：数据表每行一条样本，不许只报总平均掩盖慢样本。
3. **达标线按场景反推，不抄样例值**：先定业务容忍——如「语音消息转写可等音频时长的 1/2」则达标线 RTF≤0.5；「常开监听」则须 RTF≤0.3 量级且内存峰值 ≤ 机器可用内存的 50%（留给其余进程）；把反推过程写进报告 → 判定信号：达标线一行带推导（容忍值→线值），不是孤零零一个数。
4. 达标才写接入方案；不达标换引擎或降场景预期 → 判定信号：接入方案的引用数据全部出自本轮实测表。

**④失败分支**：
- 均值达标但最大值超线（长尾慢样本）：按最大值判不达标或限定输入时长上限，不拿均值放行。
- 内存峰值超限：先试 int8 量化版或降线程复测，仍超则该引擎出局，不靠「加内存」改目标环境迁就引擎。

**⑤验收清单**：
- [ ] RTF 按本条规程测得（样本数、预热、均值＋最大值齐全）
- [ ] 达标线有场景反推推导
- [ ] 报告明示样例值不是达标线

**⑥禁忌与易错点**：源材料样例——一款主流轻量多语种引擎（int8 量化、模型约 228MB）在 2 线程下 RTF 0.06–0.10、峰值内存约 351MB、五语种短句可用——这是单环境实测样例 [实测报告｜源材料实测记录]，**不是验收线**；复现时任选同级引擎按本规程重测，不要直接引用这组数字当自己的结论。短句达标只证明短句可用，长音频、噪声环境另测。

**⑦参数表**：RTF 定义＝处理时长÷音频时长（无量纲，＜1 快于实时）。测量规程：样本 ≥10 条×5–15 秒、首条预热不计、报均值＋最大值、内存取进程级峰值。样例值（仅参照）：RTF 0.06–0.10、峰值内存约 351MB、模型约 228MB（int8）、2 线程、五语种短句。

### 【新工具链import逐个验活】

**①目标与适用场景**：新工具链落地第一步不是写业务代码，而是逐个 import 验活。触发场景：新引擎/新库刚装好时。

**②前置条件**：已列出链上全部包清单（引擎本体、命令行框架、切分库、模型加载器等）。

**③操作步骤**：
1. 按清单逐个执行 import 并记录结果 → 判定信号：每包一行结果（成功/缺失依赖名），无跳过。
2. 缺失依赖当场补装并复验，缺失清单记进实测报告 → 判定信号：报告含「安装后缺失依赖」一节，逐个列名。
3. 全部 import 通过后，再用真实样例跑通全链 → 判定信号：全链样例有端到端产出，import 通过不冒充功能通过。

**④失败分支**：
- 补装后仍 import 失败（版本冲突）：记冲突组合与报错原文，转【新版API与旧文档脱节以实测为准】处理，不反复重装碰运气。
- 某包根本装不上（平台无轮子）：在报告里判该链在本平台不可行，不拖到写业务代码时才发现。

**⑤验收清单**：
- [ ] 清单每包有 import 结果行
- [ ] 缺失依赖清单入报告
- [ ] 全链样例端到端跑通

**⑥禁忌与易错点**：这类引擎的安装包常不声明全部运行依赖，缺失只在 import 时才炸；不先验活，后面每个报错都要回头猜是不是环境问题。

**⑦参数表**：无数值参数。验活粒度：1 包 1 次 import 1 行记录。

### 【进程级峰值内存测量】

**①目标与适用场景**：测工具峰值内存改用进程级测量（如 Python 的 resource.getrusage().ru_maxrss），不靠任务管理器估读。触发场景：任何要写进报告的内存数字。

**②前置条件**：被测工具以独立进程运行（峰值要归属到单个进程）；多环节串行时每环节单独起进程测。

**③操作步骤**：
1. 在测试脚本内、被测环节结束后直接读 ru_maxrss 并写进报告 → 判定信号：报告中的内存值能回指到具体那次进程运行，不是事后估读。
2. 注意单位：ru_maxrss 在 Linux 上为 KB、个别平台为字节，写报告前先核本平台单位并注明 → 判定信号：报告内存值带单位与平台注记。
3. 多环节分进程测：每环节一个进程一个峰值 → 判定信号：各环节峰值分列，无叠加总数。

**④失败分支**：
- 工具只能常驻多环节同进程：改测增量法（环节前后读当前 RSS 差值）并在报告注明口径不同、不可与峰值口径混比。
- 顺手遇到的小环境坑（如解压属主报错加 --no-same-owner 绕过）：当场绕、当场记进报告，不留「下次再说」。

**⑤验收清单**：
- [ ] 内存值为进程级实测、带单位与平台注记
- [ ] 多环节分进程分列
- [ ] 环境坑当场记录

**⑥禁忌与易错点**：ru_maxrss 是进程历史峰值，同进程测多环节会叠成一个总数；弱机部署的内存预算是硬约束，估读误差足以把「能跑」误判成结论。

**⑦参数表**：测量口径：进程级 ru_maxrss 峰值常驻内存；Linux 单位 KB（写报告前核本平台）。

### 【低电平衰减实测与RMS预检】

**①目标与适用场景**：对「录音电平低拖累识别」的实测结论与保留动作：衰减实验定性＋转写前 RMS 预检拦坏输入。触发场景：评估 ASR 对低电平输入的鲁棒性、或给转写链加预检时。

**②前置条件**：有可衰减处理的样本集；RMS 计算口径定死：RMS 以满量程（16 位 PCM 峰值 32767）百分比表示，先把样本统一到 PCM 再量。

**③操作步骤**：
1. 衰减实验：样本按 −20dB 衰减后转写，与原音转写逐字比对 → 判定信号：比对结果逐条有记录；源材料所测引擎（特征提取带归一化）衰减 20dB 后仍全部正确——此结论绑定该引擎，**换引擎必须重跑本实验**。
2. RMS 预检阈值标定：静音线与削波线按下法在你的样本上标定——取一批确认无声的样本量其 RMS，静音线取其最大值上方留一倍余量（源材料锚点：历史问题录音 RMS 约满量程 1.6% 已显著拖累识别，可作「过低」量级参照）；削波线看峰值：样本峰值达到满量程 100% 且连续多点触顶即判削波风险 → 判定信号：预检代码里两条线是写死的数值且各有标定依据记录，不是「适当阈值」。
3. 预检拦截动作分开：判静音→提示重录/查设备（见【识别不准先查设备层】）；判削波→提示降增益重录；低电平但未触静音线→放行转写（有衰减实验背书时） → 判定信号：三类输入各有明确去向。

**④失败分支**：
- 换引擎后衰减实验出现错字：该引擎无归一化背书，低电平样本改走增益归一化预处理后再转写，并把新结论回填本条。
- 预检误拦正常样本（方言轻声等）：回调静音线并记录误拦样本，不取消预检。

**⑤验收清单**：
- [ ] 衰减实验有逐条比对记录且注明所测引擎
- [ ] 静音/削波两条线有数值与标定依据
- [ ] 三类预检结论各有去向

**⑥禁忌与易错点**：担忧要靠实测定性，不靠直觉加处理环节；但没有阈值的预检写不出代码——两条线必须落成满量程百分比数值。不要把「本引擎未复现」平移到所有引擎。

**⑦参数表**：衰减实验量：−20dB（源材料实测，所测引擎转写仍全对）；低电平锚点：RMS 约满量程 1.6%（历史问题录音实测量级）；静音线/削波线：按本条标定规程在本地样本上定值后回填。

### 【自制音频变体测鲁棒性】

**①目标与适用场景**：官方测试短句测不出鲁棒性时，自己造变体：低电平版、加噪版与原音逐字比对。触发场景：ASR/KWS 选型实测的鲁棒性环节。

**②前置条件**：原音样本为公开样例或自录（见【引擎验证零业务数据】）；变体生成工具可控（衰减、加噪参数可设）。

**③操作步骤**：
1. 从同一样本派生两版：−20dB 低电平版、SNR 10dB 白噪声版 → 判定信号：变体参数记录在案，文件可复现生成。
2. 三版（原音/低电平/加噪）分别转写，逐字对齐比对 → 判定信号：比对表逐条列差异字数，无差异才记「一致」。
3. 三版一致才下「未见退化」结论，且结论只覆盖电平与噪声两个维度 → 判定信号：结论句带维度限定词。

**④失败分支**：
- 某版出现退化：记录退化维度与幅度（差几字、错在哪类字），结论改写为「××维度退化」，不整体否定也不整体放行。
- 真实坏输入维度不在变体里（混响、口音）：按真实维度补造变体再测，不拿现有两维结论顶替。

**⑤验收清单**：
- [ ] 变体参数可复现
- [ ] 三版逐字比对表完整
- [ ] 结论带维度限定

**⑥禁忌与易错点**：鲁棒性问题只在偏离理想输入时暴露，官方样例全是理想录音，测一百遍也测不出来；变体维度要贴近真实坏输入。

**⑦参数表**：变体参数：低电平 −20dB；噪声 SNR 10dB 白噪声。判定：三版逐字一致才写未见退化。

### 【未验范围如实写保留项】

**①目标与适用场景**：实测报告收尾纪律：未验范围逐项写进保留项。触发场景：任何实测报告定稿时。

**②前置条件**：能逐项列出本轮实测的实际覆盖范围（语种、时长、环节、存疑点），而不是计划覆盖范围。

**③操作步骤**：
1. 对照实测记录逐项写保留项：未测的时长段、未验的环节、存疑的结果点，逐项列名带量级（如「长句 30–60 秒未测」「真实语音编码转码环节本轮未验」「同音字存疑 1 字」为源材料报告的实际写法） → 判定信号：保留项每项可独立核查，不用「等」字含糊带过。
2. 每项保留项配销账动作：接入初期抽查、专项补测等，并写触发时点 → 判定信号：保留项不是只写不补，每项有去向。
3. 报告结论的适用范围按已验范围收窄表述 → 判定信号：结论句的范围词与保留项不冲突。

**④失败分支**：
- 接收方只想要结论不想要保留项：保留项随结论同页交付，不单独拆走——拆走保留项的结论就是冒充全量验证。
- 保留项长期未销账：下一轮报告里置顶重列并注明已挂账轮次，不许悄悄删掉装作验完。

**⑤验收清单**：
- [ ] 保留项逐项列名带量级
- [ ] 每项有销账动作与触发时点
- [ ] 结论范围未超出已验范围

**⑥禁忌与易错点**：保留项写清，接入方才知道信任边界在哪；不写，等于默认全量验证过。不拿短句成绩冒充全量验证。

**⑦参数表**：源材料保留项写法示例：未测长句 30–60 秒／未验环节＝真实语音编码转码／存疑＝同音字 1 字。

### 【SILK语音解码链】

**①目标与适用场景**：某主流聊天应用语音是 SILK 编码，需专用解码器还原后才能喂 ASR。触发场景：处理该应用的语音文件时。

**②前置条件**：解码器需自编译：源码取 silk-v3 解码器的公开开源仓库（以「silk-v3-decoder」类项目为准，取源码后先核其 README 的构建说明）；构建链（C 编译器、make）可用。构建参考形态：解压源码→进解码器目录→make 编译出 decoder 可执行文件→用一条样例语音试解，能产出 PCM 即构建成功（具体命令以所取仓库 README 为准，源材料未给死命令，不许凭记忆写命令进生产脚本）。

**③操作步骤**：
1. 验文件头：读文件前若干字节，应为 `#!SILK_V3` → 判定信号：字节比对相等；不等走第 4 步分支。
2. 剥变体前缀：该应用变体在数据前带一个 0x02 前缀，解码前剥掉；解码链须兼容有/无前缀两种情况（先判首字节再决定剥不剥） → 判定信号：两种样本各取一条都能解出 PCM。
3. 解码出 24kHz PCM，再转 16kHz 单声道 wav 喂识别引擎 → 判定信号：wav 参数（16kHz、单声道）经文件信息核验无误，ASR 出字正常。
4. 文件头异常分支：头不等于 `#!SILK_V3` 时，先判是不是被二次封装（如外层套了其他容器）——剥外层后重验头；仍不符则判非 SILK 文件，转【音频格式不可互替】按真实编码处理，不硬解 → 判定信号：异常文件有明确归类，不产生「解码失败」笼统记录。

**④失败分支**：
- 编译失败：按报错先查编译链缺失（编译器/库），把失败形态记进报告（见【新版API与旧文档脱节以实测为准】）；不在业务代码里绕过解码环节。
- 解出 PCM 但 ASR 出字全乱：查采样率转换（24k→16k）是否真执行，多半错在把 24kHz 直接喂了 16kHz 引擎。

**⑤验收清单**：
- [ ] 文件头校验在解码前执行
- [ ] 有/无前缀两样本均可解
- [ ] 输出 wav 为 16kHz 单声道且 ASR 出字正常
- [ ] 头异常文件有归类结论

**⑥禁忌与易错点**：前缀不剥解不出、采样率不对识别率暴跌；换应用或换版本时先用一条真实语音验全链，不许平移旧结论。

**⑦参数表**：变体前缀：0x02（须兼容有/无）；文件头：`#!SILK_V3`；解码输出：PCM 24kHz；ASR 输入：16kHz 单声道 wav。

### 【转写脚本接口规范】

**①目标与适用场景**：给转写脚本定的命令行接口规范，让调用方能精确集成与报障。触发场景：把转写能力封装成脚本供其他程序调用时。

**②前置条件**：调用形态定死：`转写脚本 <音频文件路径>`（参数传路径，脚本自行读文件）；输出行以单个换行结尾、多段转写合并为一行输出（段间以空格连接），不输出多行。

**③操作步骤**：
1. 结果与诊断分离：stdout 只出一行转写文本，全部诊断信息走 stderr → 判定信号：调用方只取 stdout 第一行即得纯文本，stderr 非空也不污染结果。
2. 退出码定死并写进脚本头注释：0＝成功；1＝未预期异常（兜底，调用方按「未知失败」处理并保全 stderr）；2＝输入错误（文件不存在/格式不对）；3＝解码失败；4＝转码失败；5＝识别失败 → 判定信号：调用方按码分支报障，能一步定位失败环节。口径：分段原则必守，具体数值可自定，但必须在脚本头注释声明且调用方按声明对接。
3. 每次独立进程、无常驻状态，临时文件自动清理 → 判定信号：连续调用两次无状态串扰，运行后临时目录无残留。

**④失败分支**：
- 调用方反馈「拿到空结果」：先查退出码——非 0 时 stdout 本就无结果，应看 stderr；把「空 stdout＋退出码」当失败处理，不当空转写。
- 某环节失败码不够分（如解码内部分不清）：在该段内用 stderr 文案细分，码段不许挪用其他环节的码。

**⑤验收清单**：
- [ ] stdout 单行纯文本、诊断全走 stderr
- [ ] 退出码 0–5 语义在脚本头注释声明
- [ ] 独立进程无状态、临时文件自清

**⑥禁忌与易错点**：输出通道不纯净，调用方就没法安全地把 stdout 当结果用；退出码不要在正文里一处写「示例」、另一处按固定值收录——口径必须全文统一。

**⑦参数表**：调用形态：`脚本 <音频路径>`，stdout 1 行（换行结尾）。退出码：0 成功／1 未预期异常／2 输入错误／3 解码失败／4 转码失败／5 识别失败（分段必守、数值以脚本头声明为准）。

### 【转写结果复述确认兜底】

**①目标与适用场景**：ASR 结果进入正式处理前的人工兜底：涉关键信息时在回复里复述请对方确认。触发场景：转写文字含人名、地名、数字、日期任一时。

**②前置条件**：转写文本在内部标注「供参考」；该标注只在内部流转，不发给对方。

**③操作步骤**：
1. 扫转写文本的关键字段（人名、地名、数字、日期） → 判定信号：字段清单与原文逐项对得上。
2. 回复中只复述关键字段请对方核对，不整段复述 → 判定信号：复述段落只含关键字段，对方一个「对」或指出某字错即可完成确认。
3. 对方指出错字：按对方版本落正式记录，并把误识样本记下（同音字误识是主要来源） → 判定信号：正式记录与转写原稿的差异处有据可查。
4. 转写彻底失败：回退固定话术请对方补发文字要点 → 判定信号：话术只请补发要点，不让对方重复发语音碰运气。

**④失败分支**：
- 对方不回复确认：关键字段保持「待确认」状态，不进正式台账，不默认转写正确。
- 同一对方反复出现同类误识：把高频误识词对记入词表，供后续转写后处理自动提示。

**⑤验收清单**：
- [ ] 关键字段全部经复述确认或标待确认
- [ ] 内部「供参考」标注未发给对方
- [ ] 转写失败时已发补发话术

**⑥禁忌与易错点**：整段复述会让对方觉得没在听，反而降低配合度；同音字误识靠自动纠错不可靠，复述确认是成本最低、拦截率最高的办法。

**⑦参数表**：必确认字段 4 类：人名／地名／数字／日期。

### 【语音助手四环评估法】

**①目标与适用场景**：评估任何语音助手演示的四环框架：唤醒、识别、大脑（大模型）、工具调用与呈现。触发场景：看厂商演示、测评或自研方案评审时。

**②前置条件**：演示允许逐环追问与实测；只给录播视频的场合，各环结论最高标「未验」。

**③操作步骤**：
1. 逐环验真，每环问三件事：是否真实在跑、用的什么实现、延迟与失败形态如何 → 判定信号：每环有当场实测记录（现场给指令、看真实响应），不是听介绍。
2. 界面效果不计入任何一环的证据 → 判定信号：评估表里没有「界面流畅」类加分项。
3. 任一环被查出是预录或人工伪装，整场演示结论降级为「不可信」并注明哪一环 → 判定信号：降级理由具体到环。

**④失败分支**：
- 演示方拒绝逐环实测：四环全标未验，评估结论写「无法验真」，不给中性评价。
- 四环都真但指标差（误唤醒高、噪声下崩）：转【语音交互分阶段上与唤醒验收线】做专项验收，不在本条下产品可用结论。

**⑤验收清单**：
- [ ] 四环逐环有实测记录
- [ ] 界面效果零计分
- [ ] 伪装环节有降级处理

**⑥禁忌与易错点**：界面最唬人也最不值钱，演示里最容易造假的恰恰是把预录或人工环节伪装成链在跑；四环都真不等于产品可用。

**⑦参数表**：评估环 4 环：唤醒／识别／大脑／工具调用与呈现（合成并入呈现环验）。


### 【中文唤醒用中文KWS模型】

**①目标与适用场景**：唤醒词检测的语种匹配原则：中文唤醒直接选中文 KWS 模型或自训练，不拿英文模型凑。触发场景：中文唤醒词实测唤醒分长期低、疑似模型不对路时。

**②前置条件**：能采集唤醒分：用 KWS 工具的打分输出（流式检测时每帧/每候选段的 score 值，取目标词段的峰值）；采集方法——让工具以调试模式输出候选分数日志，对同一批样本回放，记录每条样本的目标词峰值与当前阈值。没有打分输出的工具先换可观测的工具再谈调参。

**③操作步骤**：
1. 基线测量：同一批中文样本（≥20 条，含目标词与易混词）在现用模型上回放，记目标词峰值分布与阈值 → 判定信号：有峰值清单，不是「感觉分低」。
2. 判定语种不匹配：峰值整体远低于阈值（源材料现象形态：峰值远低于阈值、差距不是调参能补的量级），且降阈值后误触发密集出现 → 判定信号：降阈实验中误触发率随阈值下降陡增，而目标词检出改善有限——两条曲线一起出现才定性为音素不匹配。
3. 排除音质因素：做 DSP 增强（压噪声尖峰）后复测，峰值仍抬不动 → 判定信号：增强前后峰值无显著变化，根因锁定在音素不匹配而非音质。
4. 换中文 KWS 模型（或自训练）后同批样本复测 → 判定信号：换后峰值与阈值的关系写成对照（换前峰值区间/阈值/换后峰值区间），差距一目了然；源材料未留具体对照数值，复测后把你测到的对照值回填本条参数表，不许空着还宣称「已验证换模型有效」。

**④失败分支**：
- 中文模型也达不到可用峰值：查样本与麦克风链路（见【识别不准先查设备层】），再考虑自训练补样本，不回头继续压英文模型阈值。
- 自训练样本不足：优先找现成中文模型，不硬训——样本不足训出的模型只会把问题换个形态。

**⑤验收清单**：
- [ ] 换模型决策有峰值基线与降阈实验数据
- [ ] DSP 增强排除实验已做
- [ ] 换后对照值已实测回填

**⑥禁忌与易错点**：方向错了，再多调参也只是在误触发与漏唤醒之间二选一；不要把「峰值低」当音质问题去堆降噪。

**⑦参数表**：观测方法：KWS 打分日志取目标词段峰值；样本量 ≥20 条。源材料原值：英文模型对中文口音峰值「远低于阈值」（定性记录，无具体数值存档）；对照数值按本条规程实测回填。

### 【KWS先拉差距再动阈值】

**①目标与适用场景**：唤醒检测调参次序：先拉开目标词与易混词的分数差距，再整体动阈值。触发场景：KWS 已选对语种模型、但误触发与漏检难以兼顾时。

**②前置条件**：易混词清单已从真实使用环境收集（方言近音词、日常高频词）；复测样本组固定：目标词样本与易混词样本各一组，调参全程不换样本。

**③操作步骤**：
1. 固定触发阈值在当前值不动，先测基线：目标词检出率与易混词误触率各是多少 → 判定信号：基线两数有记录。
2. 调 boosting 类参数拉差距：在主流 KWS 工具（如 sherpa-onnx 的 KeywordSpotter）里对应参数为关键词条目上的 boost 分数（keywords 文件中每条关键词可带 boosting score，数值越大该词越易被检出）；调整法——只给目标词加 boost，每次 +0.5 一档（在其常用取值带 1.0–3.0 内试），每调一档用固定样本组复测两率 → 判定信号：每档有对应的检出率/误触率记录，能画出「boost—两率」关系。（所用工具若参数名不同，按其文档中「提高特定关键词检出倾向」的参数对应，原理相同。）
3. 差距拉开（目标词分数分布与易混词分布重叠明显变小）后再整体动阈值收尾 → 判定信号：调阈时两率不再是此消彼长的零和。
4. 参考口径校验：源材料实测——默认阈值下长句一次检出、检出延迟约 0.4 秒、KWS 的 RTF 约 0.04（RTF 定义见【ASR引擎弱CPU先行实测】；「长句一次检出」为源材料单场景记录 [实测报告｜源材料实测]，样本量未存档，你的复测须自报样本量） → 判定信号：你的实测报告含样本量与检出率，不直接引此句当统计结论。

**④失败分支**：
- boost 加满仍拉不开差距：说明模型区分度到顶，回【中文唤醒用中文KWS模型】查语种/模型，不继续加压阈值。
- 易混词清单覆盖不全导致上线后新误触：把新误触词回填清单并重跑复测组，清单是活文档。

**⑤验收清单**：
- [ ] 基线两率有记录
- [ ] boost 调整逐档有复测数据
- [ ] 阈值调整在拉差距之后
- [ ] 实测结论带样本量

**⑥禁忌与易错点**：先动阈值只是在误触发与漏检之间平移；易混词必须来自真实环境，实验室自拟的覆盖不全。

**⑦参数表**：调参顺序：固定阈值→boost 拉差距→整体动阈值。boost 步进参考：+0.5/档，常用带 1.0–3.0（sherpa-onnx KeywordSpotter 口径，换工具按其文档对应参数）。参考实测：检出延迟约 0.4 秒、RTF 约 0.04（单环境实测，非达标线）。

### 【TTS回转写验证可懂度】

**①目标与适用场景**：执行端听不了声音时，用 ASR 把 TTS 合成音回转写，算字错率作可懂度客观旁证。触发场景：无声环境验收合成语音时。

**②前置条件**：回转写用的 ASR 引擎必须与 TTS 不同源（不同厂商/不同模型家族），并在报告中注明引擎；原文文本留存备比对。

**③操作步骤**：
1. 字错率计算口径定死四项：按字计（不按词）；标点不计入；繁简差异按错计（除非业务口径预先声明归一）；同音字按错计（可懂度验的是字面还原，同音替换即信息丢失） → 判定信号：报告头部写明这四项口径，换人复算得同值。
2. 合成音喂回转写引擎，逐条算字错率＝错字数÷原文总字数 → 判定信号：每条样本有独立错率，不只报平均。
3. 判定参考线：字错率 ≤1% 判「可懂度有旁证」；1%–5% 判「基本可懂、需抽听复核」；＞5% 判「不可懂」——此线为本规程的执行判线（源材料只给「近零」定性，本线按其量级落成数值，采用时在报告注明线的来源） → 判定信号：结论与错率数值对应，无「近零」式模糊表述。

**④失败分支**：
- 错率集中在某类字（数字、英文、专名）：单列该类错率，可能 TTS 只是该类读法有问题，不整体判死。
- 回转写引擎本身对合成音有系统性偏差（与 TTS 同源时会系统性高估）：换异源引擎复测，以异源结果为准。

**⑤验收清单**：
- [ ] 计算口径四项写明
- [ ] 回转写引擎异源且已注明
- [ ] 结论按数值线判定

**⑥禁忌与易错点**：回转写只证可懂度，不证音质与自然度；主观音质未测就如实写未测，不冒充听过。用同源引擎回转写等于自己判自己，数值再漂亮也不作数。

**⑦参数表**：字错率口径：按字／标点不计／繁简计错／同音计错。参考判线：≤1% 有旁证；1%–5% 抽听复核；＞5% 不可懂（执行判线，源材料定性为「近零」）。

### 【云端弱机只验链路不当服务端】

**①目标与适用场景**：云端弱机的定位纪律：适合验证链路通不通，不适合当语音服务端。触发场景：想拿手头弱机（共享 vCPU 小规格）长期跑语音服务时。

**②前置条件**：已知弱机规格（vCPU、内存）与待跑模型的单环实测数据。

**③操作步骤**：
1. 按实测量级预判：源材料实测一款轻量 TTS 的 int8 版在共享 1.5 vCPU 上 RTF 约 2.8（RTF 定义见【ASR引擎弱CPU先行实测】，此为单环境实测值）——RTF＞1 即合成慢于实时，交互场景直接出局 → 判定信号：预判表里每环写 RTF 与是否满足场景时延。
2. 多模型同载先算内存总账：各环峰值（按【进程级峰值内存测量】测）相加与机器内存比，逼近上限即判 OOM 风险 → 判定信号：总账有数字，不凭「应该够」。
3. 弱机上的正确用法：只验链路（三环串行跑通、接口对齐），正式服务另找落点 → 判定信号：部署结论里弱机的角色写明「验证」而非「服务」。

**④失败分支**：
- 已在弱机上对外服务且出现超时/OOM：立即降级为链路验证角色并迁移，不靠反复重启续命。
- 三环串行仍超时：链路验证也分环单验，先保每环单独可验，不整链死磕。

**⑤验收清单**：
- [ ] 每环 RTF 与场景时延对照过
- [ ] 内存总账算过、OOM 风险有结论
- [ ] 弱机角色定位写明

**⑥禁忌与易错点**：链路验证的结论只覆盖「通不通」，性能与并发结论必须在目标规格的机器上重测；把验证环境当生产环境，首个真实请求就会把延迟与内存问题一起引爆。

**⑦参数表**：样例实测（单环境）：共享 1.5 vCPU；轻量 TTS int8 RTF 约 2.8；运行约束：识别/合成等环节串行，多模型同载有 OOM 风险。

### 【新版API与旧文档脱节以实测为准】

**①目标与适用场景**：工具链常态：新版 API 与旧文档系统性脱节，逐项以实测为准并记成清单。触发场景：照文档写的代码报错、或行为与文档描述不符时。

**②前置条件**：能确认当前安装版本号；每项脱节都以该版本号为前提记录。

**③操作步骤**：
1. 报错先分因：是我写错，还是文档过期——用最小调用逐项试（见【新工具链import逐个验活】） → 判定信号：每项脱节有最小复现与实测结论。
2. 典型脱节形态对照（源材料实测清单）：安装后先后缺 3 个依赖才跑通；新版 Python API 已无旧配置类、改扁平参数构造；某类（重采样）未在 Python API 暴露需自备实现；某 TTS 的 data-dir 参数在 2.0.0 起被废弃忽略、实际走词典（lexicon）路线 → 判定信号：你遇到的现象先在此清单对号，对不上的按新脱节记录。
3. 每项脱节记进实测报告：现象、文档说法、实测真相、版本号 → 判定信号：后来者按报告可直接避坑，不用重踩。

**④失败分支**：
- 实测也定不了（行为不稳定）：标未核实并冻结该功能点，不在脱节 API 上继续堆业务代码。
- 升级版本后：关键脱节项逐项复测，旧版结论不平移到新版，复测结果更新原条目。

**⑤验收清单**：
- [ ] 每项脱节有最小复现与版本号
- [ ] 脱节清单入实测报告
- [ ] 升级后关键项已复测

**⑥禁忌与易错点**：照旧文档写的代码报错时，很难分清是自己写错还是文档过期——实测清单把这笔账一次算清；不要因为文档写得正式就默认它对应当前版本。

**⑦参数表**：源材料脱节实例：缺依赖 3 个；配置类消失改扁平参数；重采样类需自备；data-dir 自 2.0.0 废弃走 lexicon 路线。

### 【识别不准先查设备层】

**①目标与适用场景**：语音识别不准时的排查次序：先查设备层，再动模型。触发场景：「换了大模型还不准」时。

**②前置条件**：能取到问题录音原文件并量其 RMS（口径见【低电平衰减实测与RMS预检】）；能查录音设备的枚举与采样率设置。

**③操作步骤**：
1. 查麦克风枚举：录音实际用的设备是不是选定的那支（系统常默认到别的设备） → 判定信号：录音文件里能听到预期声源特征，且设备名与设置一致。
2. 查采样率匹配：录音采样率与引擎期望是否一致，不一致的重采样后再测 → 判定信号：同一录音重采样前后各跑一次转写，错字数有对比记录。
3. 查录音电平：量问题录音的 RMS（满量程百分比）——源材料锚点：历史问题录音 RMS 仅约满量程 1.6%，已显著拖累识别 → 判定信号：电平值有数字；落在 1%–2% 量级即优先判设备/增益问题。
4. 三项都正常，才轮到模型与声学环境，按【自制音频变体测鲁棒性】继续定位 → 判定信号：排查记录显示设备层三项逐项排除。

**④失败分支**：
- 设备层查出问题但改不了（设备固定、增益不可调）：走预处理增益归一化补救，并在报告注明这是补救不是根治。
- 三项正常但识别仍差且变体测试也正常：查语种/口音与模型匹配，转【中文唤醒用中文KWS模型】的语种匹配思路。

**⑤验收清单**：
- [ ] 设备层三项逐项有排查记录
- [ ] 电平有实测数值
- [ ] 动模型决策在设备层排除之后

**⑥禁忌与易错点**：输入信号本身坏了，再强的模型也只能把噪声识别得很认真；不要跳过设备层直接换模型——换完还不准时你连定位起点都没了。

**⑦参数表**：排查顺序：麦克风枚举→采样率→录音电平→模型。异常电平锚点：RMS 约满量程 1.6%（历史实测量级）。

### 【原生助手抢答调参无解】

**①目标与适用场景**：一类无解问题的定性：不刷机前提下，靠轮询第三方接口拦不住设备原生助手的抢答。触发场景：想在现成智能设备上用自有助手接管语音交互时。

**②前置条件**：已确认设备型号在不在相关接管方案的支持清单内；不在清单内直接出局，不进入调参。

**③操作步骤**：
1. 先小规模实测定性：试轮询拦截方案，记录现象——实测结论形态是「只能做到先答后打断，所谓静音不是真静音」 → 判定信号：定性记录里有试过的档位/方案与各自现象，不是凭印象宣判。
2. 定性无解后立即停调参，把结论与两条真路摆出来：刷机整栈接管，或端侧直接接管麦克风 → 判定信号：后续投入只发生在这两条路之一上。
3. 把无解结论记入死路类记录（见【死路实测否掉不再重试】的记录法） → 判定信号：后来者查得到，不重走调参路。

**④失败分支**：
- 有人提出新的拦截参数组合：先问与已试方案的原理差异，无原理差异不重试；有差异的按新实验立项小试。
- 设备型号不在支持清单：连两条真路都先冻结，等清单覆盖或换设备，不硬改。

**⑤验收清单**：
- [ ] 无解定性有实测现象支撑
- [ ] 调参投入已停、去向明确（两条真路之一或放弃）
- [ ] 结论已入死路记录

**⑥禁忌与易错点**：无解的问题要尽早定性，否则会在调参上无限烧时间，还误以为是自己参数没调对；但定性「调参无解」必须有实测支撑，不许凭印象宣判。

**⑦参数表**：无数值参数。真路 2 条：刷机整栈接管／端侧接管麦克风。前置判线：设备型号在支持清单内。

### 【语音交互分阶段上与唤醒验收线】

**①目标与适用场景**：语音交互按「按键说话→VAD 端点检测→唤醒词→自由对话」分阶段上线，每阶段稳定再进下一阶段；唤醒上线前做误触发专项并按验收线实测。触发场景：语音交互功能立项与上线评审时。

**②前置条件**：每阶段的「稳定」判据已预先写明（如按键阶段连续一周无链路故障）；唤醒测试的样本与环境按第 3 步规程备好。

**③操作步骤**：
1. 分阶段推进：当前阶段达稳定判据才开下一阶段，问题定位到阶段为止 → 判定信号：每阶段有上线与稳定记录，跳阶段的决定有书面理由。
2. 唤醒验收实测规程（最小版）：唤醒率——每个距离档（1 米/3 米/5 米）至少 3 人 × 每人 10 次，正常室内噪声环境（非消声室、非刻意安静），唤醒成功定义为「说出唤醒词后 3 秒内设备进入监听态」；误唤醒——设备在真实生活声环境（含电视/人声闲聊）挂测满 24 小时，计自动进入监听态的次数 → 判定信号：实测表含人数、次数、距离、环境四要素，缺一不可比。
3. 实测值与参考线逐项比大小后下结论：参考线为唤醒率 1 米 >95%、3 米 >92%、5 米 >90%，误唤醒 <1 次/24 小时 → 判定信号：结论表是「实测值 vs 参考线」的数值对照，不是把参考线抄一遍当结果。
4. 专项注意：只开降噪不开回声消除时，设备播报会自唤醒——误唤醒挂测须包含设备自身播报场景 → 判定信号：挂测记录里有播报时段及其自唤醒次数。

**④失败分支**：
- 某距离档不达线：先查设备层与模型语种（见【识别不准先查设备层】【中文唤醒用中文KWS模型】），不直接降线放行。
- 场景与参考线环境差异大（噪声、方言、距离分布）：按场景加测并另立场景线，参考线只作对照，不许只测安静近场就宣布达标。

**⑤验收清单**：
- [ ] 分阶段上线记录完整、无无理由跳阶段
- [ ] 唤醒实测四要素齐全（人数/次数/距离/环境）
- [ ] 结论为实测值与参考线的数值对照
- [ ] 误唤醒挂测含设备播报场景

**⑥禁忌与易错点**：验收线是行业参考值 [博客经验级｜行业通行口径，源材料未给官方出处]，不是官方标准——引用时带此等级标注；不许把参考线当执行动作抄进步骤交差，执行动作永远是「测出你的值再比」。

**⑦参数表**：上线阶段 4 级：按键说话→VAD 端点检测→唤醒词→自由对话。唤醒率参考线：1 米 >95%／3 米 >92%／5 米 >90%；误唤醒参考线：<1 次/24 小时（均行业参考值）。最小测试规程：每距离 ≥3 人×10 次；误唤醒挂测 ≥24 小时真实声环境。

### 【高频命令短语映射优先】

**①目标与适用场景**：高频固定命令做「短语→动作」映射持久化，匹配优先于大模型推理。触发场景：语音助手命令执行链设计时。

**②前置条件**：高频命令清单可枚举（来自真实使用频次统计，不是拍脑袋列）；每个动作有固定执行入口。

**③操作步骤**：
1. 把高频命令短语与动作的对应表落盘持久化 → 判定信号：映射表是文件/配置，不是写在提示词里的临时约定。
2. 识别结果先查表：命中即直执对应动作，不经大模型推理 → 判定信号：命中路径的日志显示「查表直执」，延迟近零。
3. 识别结果一律当不可信输入：只走固定白名单映射，绝不拼接成 shell 命令执行 → 判定信号：代码中不存在「识别文本→命令字符串」的拼接路径，全文可检索验证。
4. 未命中才走大模型理解，但执行入口同样过白名单与权限闸 → 判定信号：长尾请求与高频命令共用同一执行闸。

**④失败分支**：
- 高频命令出现近音误命中：把误命中样本回填映射表的排除项或加确认环节，不靠调识别模型解决一切。
- 命令频次分布变化（新命令变高频）：定期按频次统计更新映射表，表的新陈代谢有记录。

**⑤验收清单**：
- [ ] 映射表已持久化落盘
- [ ] 命中路径查表直执、无模型介入
- [ ] 无识别文本拼 shell 的代码路径
- [ ] 长尾请求同过白名单闸

**⑥禁忌与易错点**：映射表只覆盖高频固定命令，不要把长尾请求也硬塞进表里撑大误命中面；查表近零延迟且行为确定，白名单同时封住识别错误与恶意注入两类风险。

**⑦参数表**：无数值参数。执行优先级：映射表命中＞大模型理解；安全判线：识别输入 100% 经白名单。

### 【大脑档位先算单问成本】

**①目标与适用场景**：给语音助手选大模型档位时，先算单问成本再定默认档。触发场景：语音助手选型或换档评审时。

**②前置条件**：「全套工具」的构成已列清（本系统实际挂载的工具清单）；能从 API 返回的 usage 字段读到每问的输入/输出 token。

**③操作步骤**：
1. 测单问成本：采样 ≥30 个真实问句（分普通问与需取数据问两类），逐问读 usage 字段的输入＋输出 token，分类取均值 → 判定信号：成本表有样本量与分类均值，不是单个印象数。源材料参考值：带全套工具后普通单问约 1600 token、需取数据时约 3000 token [实测报告｜源材料单环境实测]——只作量级对照，你的值按本步测。
2. 算总账：总账＝Σ（各档日均问数 × 单问 token × 该档单价），单价分输入/输出两列、取服务商当期价目（本条不给死数，价目以查询当日为准并注明日期） → 判定信号：总账表算到钱，不停在 token 层。
3. 定默认档与升级档：默认倾向低 effort 小档（快、稳、便宜），同时写明升级档触发条件（哪类任务自动升档） → 判定信号：档位表含触发条件列，不是只有默认档一个名字。

**④失败分支**：
- usage 字段拿不到（中转接口不透传）：用分词器对采样问句离线估算并在报告注明「估算口径」，结论降格。
- 小档在关键任务上答错率高：按任务类拆分档位（关键任务留升级档通道），不整体升档烧钱、也不整体降档赌正确率。

**⑤验收清单**：
- [ ] 单问成本有采样测量（≥30 问、分类均值）
- [ ] 总账算到金额、单价带查询日期
- [ ] 默认档与升级触发条件成文

**⑥禁忌与易错点**：成本不是唯一维度——复杂任务答错一次的代价可能远超 token 账；语音助手是高频低单值场景，单问成本差一倍、全年总账差一个量级，不算账就选大档等于默认烧钱换不必要的聪明。

**⑦参数表**：参考单问成本（源材料单环境实测）：普通约 1600 token／取数据约 3000 token。测量法：读 usage 字段、采样 ≥30 问分类取均值。总账公式：Σ（日均问数×单问 token×当期单价，输入输出分列）。


## 多人桥接安全与生产改动（4 条）

### 【生产改动只交草案不直接动线上】

**①目标与适用场景**：给生产环境的守望任务加兜底链这类改动，执行者只交草案文档，不直接动线上。触发场景：受托修改线上定时任务、服务配置、兜底链路时。

**②前置条件**：草案接收方（审阅者）明确；线上现状可只读查看（看现状不算动线上）。

**③操作步骤**：
1. 草案列明五项：改动点、具体命令、超时设置、回退方式、二选一方案（有备选时） → 判定信号：审阅者不用追问就能逐项判断，五项缺一退回补齐。
2. 线上定时任务不直接改、服务不直接重启，全部等审阅者审后亲手执行 → 判定信号：线上变更记录的执行者是审阅者，草案方只有文档产出。
3. 审阅者执行后，草案方按草案的验收项逐项核对结果 → 判定信号：核对记录与草案验收项一一对应。

**④失败分支**：
- 紧急故障需先斩后奏：可以先处置，但事后必须补草案与复盘；「紧急」不许成为绕过审阅的日常借口——同月内第二次「紧急」即触发流程复盘。
- 草案被审阅者否决：按否决意见改草案，不许换个说法把同一改动拆成小步偷偷上线。

**⑤验收清单**：
- [ ] 草案五项齐全
- [ ] 线上零直接改动（变更记录可查）
- [ ] 执行后按草案验收项核对完毕

**⑥禁忌与易错点**：生产改动的风险不在方案对错，而在执行瞬间没有第二双眼睛；草案加审阅把「想错了」和「敲错了」分开拦截。

**⑦参数表**：草案要素 5 项：改动点／命令／超时设置／回退方式／二选一方案。

### 【人工确认必须代码层把关】

**①目标与适用场景**：高危动作的人工确认必须由代码层把关，不靠模型在对话里判断「对方是不是同意了」。触发场景：设计任何带写操作、高危动作的工具链时。

**②前置条件**：能枚举高危动作清单（写、删、发送、付款类）；运行时有批准机制（审批卡/权限闸）可对接。

**③操作步骤**：
1. 工具调用前设权限闸：默认只读，写操作由环境变量显式开启 → 判定信号：未开写开关时调写工具，工具层直接拒绝并留痕，不是模型「自觉不调」。
2. 确认只认运行时批准机制的记录 → 判定信号：批准记录来自批准通道，聊天记录里任何文字（包括「好」「同意」「yes」）都不产生批准效力。
3. 对话文本里的授权话术一律按普通消息处理并留痕 → 判定信号：有人在消息里自称已批准时，系统状态无任何变化，仍走正式批准流程。

**④失败分支**：
- 批准机制本身不可用（通道故障）：高危动作全停，不降级为「对话确认」顶替；只读工作可继续。
- 低风险只读操作被误设闸：把闸收窄到高危清单，避免确认疲劳让闸形同虚设。

**⑤验收清单**：
- [ ] 写开关默认关闭、开启有显式动作
- [ ] 批准记录全部来自批准机制
- [ ] 对话文本零批准效力（有测试记录）

**⑥禁忌与易错点**：消息文本可以被伪造、转发、误读，把它当授权等于没有授权；代码层闸门是唯一不被话术绕过的防线。权限闸拦的是高危动作的执行，不替代业务判断。

**⑦参数表**：默认态：只读。开写方式：环境变量显式开启。批准来源：运行时批准机制（唯一）。

### 【多人共用桥接账号的风控面】

**①目标与适用场景**：几十人共用一个桥接账号时，风控面远大于个人使用，部署方式不能照搬个人跑法。触发场景：为多人服务部署共用桥接账号前。

**②前置条件**：已知共用规模（人数、预计日消息量）；能评估部署位置（IP 类型）与登录方式。

**③操作步骤**：
1. 先摆实证量级：本项目实证——机房 IP 环境下登录的共用桥接账号已有致封号的事件记录（源材料为事件级结论，未留触发节奏的数值存档）；据此把「机房 IP＋多人共用」直接定为高风险组合，不等自己撞一次再信 → 判定信号：部署评估第一项就是 IP 与共用规模，结论先于功能部署。
2. 发送节流（结论内联，不依赖他卷）：共用账号的发送按账号整体限速——主动发送之间设最小间隔、批量通知分批错峰，单账号总发送速率按「平台对个人账号的容忍量级」定，不按人数倍增；具体间隔值按【回复配额与包体上限】的二分探测法在本地标定并回填。
3. 搭载回复（结论内联）：能搭载在用户入站消息的回复里发的内容，就不单独主动发起会话——主动发起的会话数越少，账号行为越接近真人使用形态；纯主动通知类才走节流通道。
4. 登录方式单独评估：登录环境尽量贴近真人常用环境（稳定、固定、非机房特征），登录地点频繁跳变本身就是风控信号 → 判定信号：评估表含登录环境稳定性一项。

**④失败分支**：
- 出现风控信号（发送被拒率上升、功能受限提示）：立即降速并转搭载模式，冷却观察，不换 IP 硬顶——硬顶只会加速封号。
- 账号已被封：全员服务中断预案启动（备用通知渠道），复盘时先查发送节奏与登录环境两项，不先怪功能代码。

**⑤验收清单**：
- [ ] 部署评估含 IP 类型与共用规模两项且结论在部署前
- [ ] 节流参数已本地标定并回填
- [ ] 可搭载内容已改走搭载通道
- [ ] 登录环境稳定性有评估结论

**⑥禁忌与易错点**：平台风控看的是账号整体行为，几十人的量叠加在一个账号上，触发阈值的速度是个人使用的几十倍，一次封号全员断线；个人自用账号的跑法经验不能平移过来，反之亦然。

**⑦参数表**：规模口径：几十人共用 1 个账号（源材料量级）。实证：机房 IP 共用账号有致封号事件记录（事件级，无节奏数值存档；本地节奏按二分探测标定）。核心处置 2 条：发送节流（整体限速、错峰分批）／搭载回复（优先随入站回复发出）。

### 【分布式终端心跳加遗嘱】

**①目标与适用场景**：分布式终端状态管理：心跳＋遗嘱（last will）——服务停掉或断线，状态立即标 unavailable。触发场景：多端协同、任一端行动前要判断对端死活时。

**②前置条件**：各端能周期发心跳并预设遗嘱消息（连接层支持 last will 或等效机制）；状态读取方能拿到最近心跳时间。

**③操作步骤**：
1. 每端按固定周期发心跳并预设遗嘱：异常断线由系统自动发布离线状态 → 判定信号：强杀一端进程做演练，其状态在遗嘱机制下自动变 unavailable，不靠人工标注。
2. 任一端行动前先看状态新鲜度：最近心跳距今超过约定时限即按离线/未知处理 → 判定信号：行动日志里有新鲜度判断记录，不是只看「进程在不在」。
3. 时限这样定：取心跳周期的 3 倍为过期线（漏两拍即判过期），把周期与过期线成对写进配置 → 判定信号：配置中两数成对出现，改周期同步改过期线。

**④失败分支**：
- 状态新鲜度无法确认（状态服务本身无响应）：按离线处理，不依据旧状态继续派活。
- 心跳正常但业务无响应（假活）：在心跳里带业务自检结果字段，自检不过的状态标 degraded，不只看心跳存活。

**⑤验收清单**：
- [ ] 强杀演练后状态自动转 unavailable
- [ ] 行动前有新鲜度判断记录
- [ ] 心跳周期与过期线成对配置

**⑥禁忌与易错点**：分布式系统最危险的不是节点宕机，而是其他节点以为它还活着、继续按旧状态派活；进程在不等于状态新，判断依据永远是最近一次心跳时间——这与服务健康巡查「看状态新鲜度、不看进程存活」同理。

**⑦参数表**：过期线标定法：心跳周期 ×3（漏两拍判过期）；源材料未给绝对周期值，按端的重要性定周期后成对回填。

## 看板机制（5 条）

### 【刷新不覆盖人工订正】

**①目标与适用场景**：自动刷新与人工维护共存的数据表，保证自动刷新永不覆盖人工订正。触发场景：设计或修改任何「机器刷新＋人工可改」的数据表时。

**②前置条件**：每行能落两个字段：来源标记（manual/refresh）与 userTouched 标记位。

**③操作步骤**：
1. 建行时写来源：人工建行标 manual，刷新建行标 refresh → 判定信号：全表每行来源非空。
2. 用户编辑任何一行时置 userTouched＝真 → 判定信号：编辑动作与标记位变化在同一次保存里发生。
3. 刷新只替换「来源为 refresh 且 userTouched 为假」的行，其余一律跳过并记录跳过原因 → 判定信号：刷新日志含跳过行清单及原因（人工行/已订正）。

**④失败分支**：
- 发现人工订正被覆盖：立即从订正记录/备份恢复该行，并查标记位为何没生效——这是机制 bug，不是操作失误，修好前暂停自动刷新。
- 自动行本身写错：靠刷新源头的数据质量解决，不靠人工去逐行改自动行（改了就变订正行、再也不刷新）。

**⑤验收清单**：
- [ ] 每行来源标记齐全
- [ ] 编辑即置 userTouched 有验证记录
- [ ] 刷新跳过清单含人工行与订正行

**⑥禁忌与易错点**：保护的是「用户编辑过」这个事实，不是行的内容对错；用户改过的数据被下一次刷新冲掉，发生一次就会摧毁对整个看板的信任，且订正往往含系统里没有的线下信息，丢了找不回。

**⑦参数表**：字段 2 个：source（manual/refresh）／userTouched（布尔）。刷新替换条件：source＝refresh 且 userTouched＝假。

### 【刷新只提取不编造】

**①目标与适用场景**：负责刷新的代理职责边界：只从记录原文提取，不生产新信息。触发场景：任何自动刷新看板/台账的任务运行时。

**②前置条件**：源记录（记忆、台账原文）可读；每条提取结果能挂出处注记（sourceNote）。

**③操作步骤**：
1. 逐条从原文提取：不补日期、不猜进度、不编造条目 → 判定信号：看板任一条目按 sourceNote 回指原文，能找到逐字对应段落。
2. 状态只能按记录写：记录没说完成就写未完成 → 判定信号：标「完成」的条目，其原文有完成表述；抽查无一例外。
3. 同一事项多处记录时取最新口径，只报一条，旧口径不并列 → 判定信号：同事项在看板上唯一，注记指向最新记录。

**④失败分支**：
- 原文口径互相冲突：取最新口径并保留出处，不自行调和出第三种说法。
- 原文信息不足以成条：不成条，在刷新报告里列「原文不足」清单，不用推测补齐。

**⑤验收清单**：
- [ ] 每条目有 sourceNote 且可回指原文
- [ ] 完成状态全部有原文依据
- [ ] 同事项唯一、取最新口径

**⑥禁忌与易错点**：刷新环节一旦开始「合理推测」，看板就会混进无源信息，且这类信息最像真的、最难事后筛出；提取允许归并与去重，不允许推断。

**⑦参数表**：无数值参数。每条目必带：sourceNote 出处注记。

### 【看板日期用纯日历日】

**①目标与适用场景**：看板日期一律用户时区的纯日历日（YYYY-MM-DD），不用时刻换算。触发场景：设计看板日期字段、或刷新代理写入到期日时。

**②前置条件**：用户时区已定；能区分「到某天为止」的事项与「精确到时刻」的事项。

**③操作步骤**：
1. 到期日、节点日按日历日落盘，不带时分秒 → 判定信号：日期字段全文匹配 YYYY-MM-DD 格式，无一带时刻。
2. 「只有星期说法」的事项，由刷新代理按当天日期换算成实际日期再写入 → 判定信号：写入值是具体日期，不是「周五」字样。
3. 精确到时刻的会议类信息保留时刻，但与日历日字段分开存 → 判定信号：两类字段物理分离，排序分组只用日历日字段。

**④失败分支**：
- 历史数据已带时刻：一次性归一化为日历日（按用户时区取日期部分）并留转换记录，不新旧混存。
- 跨时区协作方给的日期带时区偏移：先换算到用户时区的日期再落盘，不直接截字符串。

**⑤验收清单**：
- [ ] 日期字段格式全量合规
- [ ] 星期说法已换算为实际日期
- [ ] 时刻信息与日历日分开存

**⑥禁忌与易错点**：带时刻的日期在时区换算中会漂移，把到期日错位一天——看板错一天就是提醒晚一天。

**⑦参数表**：日期格式：用户时区 YYYY-MM-DD；时刻换算：不用。

### 【数据只经声明动作读写】

**①目标与适用场景**：看板数据访问纪律：任何一方都不直连应用数据库，只经应用声明的动作读写。触发场景：给看板接刷新任务、维护工具或新展示方时。

**②前置条件**：应用已声明覆盖刷新所需全部读写的动作（scheduled action 触发、保存动作回写）；缺动作时先补动作。

**③操作步骤**：
1. 每日刷新由定时任务调用应用声明的计划动作触发，后台代理再经保存动作回写 → 判定信号：刷新链路上每一步都是声明动作调用，日志可查。
2. 刷新方、展示方、维护方走同一套声明动作 → 判定信号：三方调用的动作清单一致，无一方持有数据库直连凭据。
3. 发现直连需求（某动作缺失）：先给应用补声明动作再继续 → 判定信号：补动作记录在案，直连次数为零。

**④失败分支**：
- 已有人直连写过库：按【写共享存储先整库备份】思路先备份核查数据完整性，再收编其写法规程到声明动作。
- 声明动作与应用层校验冲突导致刷新失败：修动作定义，不绕过校验直连「就这一次」。

**⑤验收清单**：
- [ ] 全部读写经声明动作
- [ ] 无数据库直连凭据在外
- [ ] 缺失动作已补齐

**⑥禁忌与易错点**：直连数据库绕过了应用层的校验与来源标记机制，一次裸写就可能破坏【刷新不覆盖人工订正】的保护逻辑；图省事直连一次，后面所有保护都不可信。

**⑦参数表**：无数值参数。访问路径：声明动作（唯一）。

### 【看板内容两类与刷新时间戳】

**①目标与适用场景**：工作看板内容结构定式：只装两类内容，刷新时间戳单独展示。触发场景：新建或改版工作看板时。

**②前置条件**：两类内容的来源数据齐备（待办记录、项目进度记录）；时间戳存元数据（meta），不混进内容行。

**③操作步骤**：
1. 第一类：按到期日分组的待办——逾期／本周／下周／无日期四组，每条带责任人与卡点 → 判定信号：每条待办四要素（事项、到期日、责任人、卡点）齐全，分组与到期日一致。
2. 第二类：按申报阶段排序的项目进度 → 判定信号：排序键是阶段序，不是更新时间。
3. 刷新时间戳单独存 meta 并显示在看板上 → 判定信号：用户打开看板第一眼能看到「数据新到哪天」。

**④失败分支**：
- 新需求想加第三类内容：先评估是否真需要上板，能并入两类的并入；确需新增的，单独立项改版，不顺手塞。
- 刷新失败时时间戳保持旧值不许伪装新值：用户据旧时间戳判断数据可信度，这正是时间戳外显的意义。

**⑤验收清单**：
- [ ] 内容只有两类、待办四要素齐全
- [ ] 项目按阶段排序
- [ ] 时间戳在 meta 且看板可见

**⑥禁忌与易错点**：内容收敛到两类，看板才扫得动；无限加类的看板最后没人看。

**⑦参数表**：内容 2 类：分组待办（4 组）／阶段排序项目进度。时间戳：存 meta、看板展示。

## 主动投递机制（5 条）

### 【预备稿投递前复核时效】

**①目标与适用场景**：后台预备好的投递稿（条目＋草稿＋来源）在真正投递前必须复核时效。触发场景：投递轮次启动、准备发送任何预备条目时。

**②前置条件**：预备条目带来源与制备时间；有记忆检索与实时来源可供核对。

**③操作步骤**：
1. 逐项核对三件事：事实仍成立、未过时、未被后续进展覆盖 → 判定信号：每项有复核结论（成立/已变/已过时），不是整批一句「已复核」。
2. 过期快照宁可丢弃，不发旧闻 → 判定信号：丢弃条目有记录与理由（见【投递决策逐条给理由】的跳过理由）。
3. 队列里的草稿不等于已投递：投递状态以真实发送记录为准 → 判定信号：状态字段与发送日志对得上。

**④失败分支**：
- 复核发现条目部分失效：失效部分删改后重核，或整条跳过，不许「大体还对」照发。
- 实时来源暂时核不到：该条本轮跳过标「无法确认」，不赌它还成立。

**⑤验收清单**：
- [ ] 每条发送前有逐项复核结论
- [ ] 过期条目已丢弃并留理由
- [ ] 投递状态与发送记录一致

**⑥禁忌与易错点**：预备稿是过去时点的快照，躺得越久与现实脱节概率越大；把已解决的事当新提醒发出去，比不发更伤信任。复核只核事实与时效，不重写条目。

**⑦参数表**：复核项 3 项：仍成立／未过时／未被后续进展覆盖。

### 【预备条目标注证据与工作键】

**①目标与适用场景**：每个预备条目标注证据出处（grounds）与工作键（work key），投递决策可回溯。触发场景：制备任何预备条目时。

**②前置条件**：条目来源是可定位的记忆主张或原话；对应工作有唯一工作键。

**③操作步骤**：
1. 条目上注明 grounds：源自哪条记忆主张、哪句原话（给定位，不复制全文） → 判定信号：按标注能实际打开对应证据。
2. 挂上对应工作的 work key → 判定信号：按 key 能调出该工作的当前状态，投递前据此复核（见【预备稿投递前复核时效】）。
3. 无 grounds 或无 key 的条目不进投递候选 → 判定信号：候选池抽查无裸条目。

**④失败分支**：
- 证据已失效（主张被更新）：条目随证据一同失效，按跳过处理，不把旧 grounds 换个新条目继续用。
- 工作键指向的工作已关闭：条目自动失去投递资格，留记录供复盘。

**⑤验收清单**：
- [ ] 每条 grounds 可打开、key 可调状态
- [ ] 候选池无裸条目
- [ ] 失效证据的条目已同步失效

**⑥禁忌与易错点**：标注指向证据即可，不必把全部上下文塞进条目；没有出处的条目，投递时无法复核、出错时无法溯源，最后变成凭印象推送。

**⑦参数表**：标注 2 项：grounds（证据定位）／work key（工作键）。

### 【投递决策逐条给理由】

**①目标与适用场景**：主动投递每个条目发送或跳过，都必须落一个标准理由代码。触发场景：每轮投递决策时。

**②前置条件**：投递历史可查（判「已告知」靠它）；条目带过期时刻（见【预备条目设过期时刻】）。

**③操作步骤**：
1. 发送的逐条标发送理由（五选一）：time_sensitive（时效紧迫）／changed（事项有变）／requested（用户索要）／ready_for_decision（备好待决）／new_opportunity（新机会） → 判定信号：每条发送记录有且仅有一个主理由。
2. 跳过的逐条标跳过理由（五选一）：moot（已失效）／already_handled（已处理或已告知）／unconfirmed（无法确认）／preferences（偏好排除）／not_useful_now（此刻不值得发） → 判定信号：同上。
3. already_handled 靠投递历史比对判定：查该条是否已实际送达并告知过 → 判定信号：判定依据是发送历史记录，不是印象。

**④失败分支**：
- 拿不准属于哪类理由：先按跳过处理并标最接近的跳过理由，不硬凑发送。
- 发现已发条目理由标错：当轮更正记录，理由是事前决策依据，不许事后补写说辞。

**⑤验收清单**：
- [ ] 本轮每条有且仅有一个理由代码
- [ ] already_handled 判定有历史比对依据
- [ ] 无「已说过的事当新事再发」

**⑥禁忌与易错点**：逐条给理由让投递从「感觉该发」变成可审计的决策；重复打扰与陈旧提醒这两类最伤信任的错误，都被理由环节拦住。

**⑦参数表**：发送理由 5 个：time_sensitive／changed／requested／ready_for_decision／new_opportunity。跳过理由 5 个：moot／already_handled／unconfirmed／preferences／not_useful_now。

### 【预备条目设过期时刻】

**①目标与适用场景**：每个预备条目带「过期时刻」（useful until），到期未投递自动失效。触发场景：制备预备条目时。

**②前置条件**：能判断事项性质：事件型、提醒型、常青型，过期点设法各不同。

**③操作步骤**：
1. 制备时按性质设过期点：事件型到事件结束、提醒型到截止日、常青型给一个复审日 → 判定信号：每条有具体过期时刻，无「长期有效」裸奔条目。
2. 投递轮次先筛掉已过期条目再做其余决策 → 判定信号：过期条目不进入本轮候选，其跳过理由自动记 moot（见【投递决策逐条给理由】）。
3. 过期是自动失效不是删除：失效条目保留记录供复盘 → 判定信号：失效记录可查、不可再被选回候选。

**④失败分支**：
- 事项延期导致过期点失效：由制备方显性改过期时刻并留变更记录，不许投递方私自展期。
- 大批条目同时过期：复盘制备节奏——备得太早或投递太慢，二选一改，不把过期当常态。

**⑤验收清单**：
- [ ] 每条有过期时刻
- [ ] 投递前已筛过期
- [ ] 失效记录保留且不可回选

**⑥禁忌与易错点**：没有过期机制的队列会积累陈旧提醒，在错误的时间落地，比错过提醒更糟。

**⑦参数表**：过期点设法 3 类：事件型＝事件结束／提醒型＝截止日／常青型＝复审日。

### 【缺失事实收敛成确认问题】

**①目标与适用场景**：备稿复核时发现唯一缺失的事实只能由用户本人回答时，把整条备稿收敛成一句确认问题。触发场景：复核卡在「只有他知道」的一个事实上。

**②前置条件**：已确认只缺这一件事实，且该事实经其他渠道核实不到（能查的先查完，不许偷懒全推给用户）。

**③操作步骤**：
1. 把备稿收敛成一句确认问题，只问这一件事 → 判定信号：问题单义、无复合问句，用户一句话能答完。
2. 预先写好两个分支的后续动作：答「办了」如何收尾、答「没办」如何推进 → 判定信号：分支动作具体到可直接执行，用户一答即可动。
3. 用户答后当轮执行对应分支并回告结果 → 判定信号：执行记录与所答分支对应。

**④失败分支**：
- 用户答复含糊（既非办了也非没办）：只就含糊点再收敛问一句，不把整条备稿重新摊开。
- 复核中发现缺的不止一件事实：不适用本条，先把可查的查完，剩余再逐件收敛。

**⑤验收清单**：
- [ ] 确认问题单义一句
- [ ] 两分支动作预先写好
- [ ] 答后当轮执行并回告

**⑥禁忌与易错点**：这类事实猜不得、查不到，替用户猜等于替用户撒谎；收敛成一个问题，是对用户注意力最省的推进方式。

**⑦参数表**：无数值参数。收敛判线：缺失事实＝1 件且仅用户可答。


## 定时与守望任务（5 条）

### 【定时任务文件化与退役归档】

**①目标与适用场景**：每个定时任务都是一份带元数据的文件；退役任务移入归档区留档，不直接删除。触发场景：新建、修改、退役任何定时任务时。

**②前置条件**：任务定义有统一存放位置与归档区（_archive）；元数据字段定死。

**③操作步骤**：
1. 任务定义文件带全元数据：id、计划（schedule）、时区、投递目标、归属目标 → 判定信号：任一任务文件五项齐全，可据此重建任务。
2. 新建、修改、退役都走文件变更并留变更痕迹 → 判定信号：任务现状与文件一致，无「只在调度器里改了、文件没跟上」的漂移。
3. 退役时把定义文件移入 _archive 并注明退役原因与日期 → 判定信号：归档区能回答「这个提醒为什么停了」。

**④失败分支**：
- 发现调度器里有无文件的野任务：立即补文件或停用，不许长期无档运行。
- 归档文件与调度器残留冲突（已归档但还在跑）：以停用为准先停，再查残留来源。

**⑤验收清单**：
- [ ] 全部在跑任务有定义文件、元数据五项齐全
- [ ] 文件与调度现状一致
- [ ] 退役任务在归档区且有原因

**⑥禁忌与易错点**：直接删除退役任务等于销毁审计线索；调度面貌要可审计、可回溯，靠文件不靠谁记得。任务的运行日志另行留存，不混进定义文件。

**⑦参数表**：元数据 5 项：id／计划／时区／投递目标／归属目标。退役方式：移入 _archive，不删除。

### 【守候任务有始有终】

**①目标与适用场景**：等待外部审批或事件的守候任务自带完整生命周期，不变僵尸任务。触发场景：为「等某件外部结果」建任何轮询守候时。

**②前置条件**：等待对象与查询渠道明确（如自有邮箱查审批邮件）；总时限在建任务时就定死。

**③操作步骤**：
1. 每轮查指定渠道，无消息静默结束、不打扰 → 判定信号：无消息轮次零通知，有运行记录可查。
2. 收到拒绝 → 报告一次并自删任务 → 判定信号：报告发出与任务删除在同一轮完成，只报一次。
3. 收到通过 → 接续完成后续部署（部署动作仍走正常审阅流程） → 判定信号：后续动作有独立记录，不因守候通过而跳过审阅。
4. 到总时限仍无结果 → 报告一次超时并自删 → 判定信号：超时报告含等待时长与渠道核查结论（如「审核超时未批」），任务已删除。

**④失败分支**：
- 渠道本身故障（查不了）：该轮记故障形态，连续多轮故障升级报告，不把「查不了」当「没消息」静默到底。
- 通过与拒绝同时出现矛盾信号：暂停接续，先人工核清哪份为准，不抢跑部署。

**⑤验收清单**：
- [ ] 任务带总时限
- [ ] 三种结局（通过/拒绝/超时）各有且仅有一次报告
- [ ] 结局后任务已自删

**⑥禁忌与易错点**：守候任务最容易被遗忘，长年空转既耗资源又会在某天突然误触发；自删前必须把结局报告到位，报告没发成就删任务等于白等。

**⑦参数表**：生命周期 4 态：静默等待／拒绝→报告＋自删／通过→接续部署／超时→报告＋自删。总时限：建任务时按等待对象定死并写进任务定义。

### 【守望任务令牌保密与正文即规程】

**①目标与适用场景**：无人值守答复任务两条铁律：令牌保密、任务正文即完整作业规程。触发场景：建任何无人值守、要调内部接口的守望任务时。

**②前置条件**：令牌有受控存放文件，任务运行时可读；正文篇幅足以写全流程。

**③操作步骤**：
1. 令牌每轮从受控文件现读现用，绝不写进任务正文、日志、回复或给用户的消息 → 判定信号：全文检索正文与近期日志，令牌值零出现；正文只引用令牌存放位置。
2. 任务正文写全规程：拉取、处理、回执、失败口径都在正文里 → 判定信号：换一个没见过此任务的执行者，只读正文即可完整跑一轮（可抽测）。
3. 正文变更走审阅（见【生产改动只交草案不直接动线上】的草案纪律） → 判定信号：正文变更有审阅记录。

**④失败分支**：
- 令牌疑似已进日志/消息：按泄露处理——立即轮换令牌并排查扩散范围，不只删那一条记录。
- 正文规程与实际执行漂移（执行者靠记忆补步骤）：以正文为准纠正执行，并把缺的步骤补进正文。

**⑤验收清单**：
- [ ] 令牌值在正文与日志中零出现
- [ ] 正文规程完整可独立执行
- [ ] 正文变更有审阅记录

**⑥禁忌与易错点**：令牌一旦进日志或消息就等于公开；正文可以写全流程，但不许把令牌本身写进正文。正文即规程保证任务不依赖某个执行者的记忆，换人不断档。

**⑦参数表**：令牌存放：受控文件（正文只写位置）。规程四段：拉取／处理／回执／失败口径。

### 【心跳清单与调度分离】

**①目标与适用场景**：心跳类任务的结构：正文只写一句「执行清单文件」，检查项全在独立清单里，清单与调度分离维护。触发场景：建任何周期性巡检/心跳任务时。

**②前置条件**：清单文件有独立存放位置与版本说明；调度只负责触发时机。

**③操作步骤**：
1. 任务正文只保留一句指向清单文件的指令 → 判定信号：正文无具体检查项，检查项只存在于清单文件一处。
2. 改检查项只改清单文件，不动调度；改调度不动清单 → 判定信号：变更记录显示两类变更互不牵连。
3. 清单带版本号与生效说明 → 判定信号：每轮执行记录注明所用清单版本。

**④失败分支**：
- 清单为空或读取失败：心跳报错留痕，不许静默跳过装作正常——静默跳过的心跳比没有心跳更危险。
- 清单项与实际系统漂移（检查对象已下线）：当轮标注失效项并修订清单，不照单全收地跑假检查。

**⑤验收清单**：
- [ ] 正文只有清单指针
- [ ] 清单有版本、执行记录注明版本
- [ ] 清单读取失败会报错留痕

**⑥禁忌与易错点**：检查项的变更频率远高于调度，绑在一起每次改清单都要动任务定义，风险与成本都不成比例。

**⑦参数表**：无数值参数。分离判线：检查项唯一存放处＝清单文件。

### 【目标线索推断的证据格式】

**①目标与适用场景**：从已核实的对话证据推断耐久目标线索时，每条线索的固定五要素写法。触发场景：把推断出的潜在目标记入线索库时。

**②前置条件**：推断依据是已核实的对话证据（有原话可引）；线索库与正式目标分开存放。

**③操作步骤**：
1. 每条线索写全五要素：依据原话引用、置信度、什么能确认它、什么能推翻它、只在自然时机轻轻提出的下一步 → 判定信号：五要素逐项非空，确认/推翻条件是可观察事件，不是感觉。
2. 推断线索只存线索库，绝不混入正式目标 → 判定信号：正式目标列表中每条都有用户明示依据，无推断混入。
3. 自然时机轻提确认：确认了才转正式目标，被推翻当轮销账 → 判定信号：线索状态变化有记录（已确认/已推翻/待时机）。

**④失败分支**：
- 推翻条件先发生：直接销账，不保留「也许以后还成立」的僵尸线索。
- 原话引用定位失效（记录被删改）：该线索降为无据，撤下待重新取证。

**⑤验收清单**：
- [ ] 每条线索五要素齐全
- [ ] 线索库与正式目标物理分开
- [ ] 状态变化有记录

**⑥禁忌与易错点**：推断只用于在自然时机轻提确认，不许据此直接立项、花资源或对外承诺；写全可证伪条件，才不会随时间被误当成用户亲口定下的目标。

**⑦参数表**：固定要素 5 项：原话引用／置信度／确认条件／推翻条件／自然时机下一步。

## 美术资产工程（6 条）

### 【美术资产先样张后量产】

**①目标与适用场景**：成套美术资产先做一个完整样张给用户认画风，认可后才量产。触发场景：任何成套新画风资产开工时。

**②前置条件**：规格已数字化（见【资产规格先数字化】）；样张按最终规格做全套动作与状态，不做缩水版。

**③操作步骤**：
1. 只做一个样张（一个角色/一套物件的全套状态） → 判定信号：样张帧数与状态数与规格一致，不是抽帧的简化版。
2. 样张交用户认画风，认可信号以用户明确表态为准 → 判定信号：认可记录在案，未认可前量产帧数为零。
3. 不认可就只迭代样张，改到认可为止 → 判定信号：每轮迭代只有样张在变，量产未启动。

**④失败分支**：
- 多轮迭代仍不认可：回规格层重谈画风方向（参考图、风格关键词），不在样张细节里无限磨。
- 量产中发现画风漂移：以样张为基准逐帧比对，漂移帧隔离重做，不拿「整体差不多」放行。

**⑤验收清单**：
- [ ] 样张按最终规格全套完成
- [ ] 认可记录在量产启动之前
- [ ] 量产帧与样张基准一致

**⑥禁忌与易错点**：样张认可的是画风与规格，不是每一帧的细节质量；量产仍需逐帧质检，不能拿样张背书全批。不许先量产再指望整体返工——样张成本是一套资产的几十分之一，这道关最划算。

**⑦参数表**：无数值参数。关口判线：认可前量产帧数＝0。

### 【长期工程规格加清单】

**①目标与适用场景**：长期资产工程的管理方式：一份规格文件加一份进度清单，进度不靠记忆。触发场景：跨多轮、多执行者的资产工程立项时。

**②前置条件**：规格与清单合为一个工程文件；「一格」的粒度已定义（一个角色或一组动作）。

**③操作步骤**：
1. 工程文件同时含规格（见【资产规格先数字化】）与进度清单（每格一行：内容、状态、完成日期） → 判定信号：任一执行者打开文件就能指出「完成到哪、下一格是什么」。
2. 闲时轮次每轮推进一格，推进完当轮立即回写清单 → 判定信号：回写时间与推进工作在同一轮，无攒着补记。
3. 规格变更走文件修订并留痕，清单状态随规格变更同步复核 → 判定信号：规格版本号与清单备注对得上。

**④失败分支**：
- 清单与实际产物对不上（标完成但文件缺失）：以产物为准回退状态并查因，清单从此只认产物验证后的状态。
- 工程长期停滞：清单头部标注停滞与原因，不许让清单看起来像在正常推进。

**⑤验收清单**：
- [ ] 工程文件规格＋清单齐全
- [ ] 每格状态与产物实存一致
- [ ] 回写当轮完成

**⑥禁忌与易错点**：靠记忆接续必然重复劳动或漏项，清单是唯一的进度真相；攒记出来的清单和记忆没有区别。

**⑦参数表**：推进粒度：1 轮 1 格（1 角色或 1 组动作）。

### 【资产规格先数字化】

**①目标与适用场景**：开工前先把资产规格写成数字：帧数、画布尺寸、状态清单、显示尺寸下的可辨识度要求。触发场景：任何美术资产工程开工前。

**②前置条件**：显示尺寸已定（资产在产品里的实际呈现大小）；状态清单可枚举。

**③操作步骤**：
1. 逐角色列状态与每状态帧数，算全套总量 → 判定信号：规格表有总量数，排期与工作量据此算得出。
2. 先定显示尺寸，再反推源图分辨率与细节密度 → 判定信号：规格里分辨率数值有反推依据（显示尺寸×倍率），不是随手写的整数。
3. 可辨识度要求落成可测标准：在最终显示尺寸下，关键特征（武器、职业标识等）须可辨认 → 判定信号：样张按显示尺寸缩小验过（与【美术资产先样张后量产】衔接）。

**④失败分支**：
- 样张阶段发现规格不合理：正式改规格并留痕（改哪项、为什么），不许私下放水照旧规格交差。
- 总量算出后超出工期：砍状态或分期交付，规格表上显性标注，不许靠「做快点」硬撑。

**⑤验收清单**：
- [ ] 规格表含帧数、画布、状态清单、总量
- [ ] 分辨率有反推依据
- [ ] 可辨识度在显示尺寸下验过

**⑥禁忌与易错点**：数字规格是开工基线；可辨识度按最终显示尺寸定，避免源图精细却在产品里糊成一团。

**⑦参数表**：规格字段：状态清单／每状态帧数／画布尺寸／显示尺寸／源图分辨率／总量。

### 【新资产复用现行图集】

**①目标与适用场景**：新资产按现行图集格式与加载、回退逻辑打包，复用既有构建脚本口径。触发场景：给现役产品新增/替换成套帧资产时。

**②前置条件**：现行图集的帧布局、命名、元数据格式可查；构建脚本可用。

**③操作步骤**：
1. 新图集的帧布局、命名、元数据与现行图集逐项对齐 → 判定信号：用现行构建脚本打包新资产，无需改脚本即产出合格图集。
2. 引擎侧不为新资产开特例：加载走既有路径，失败走既有回退 → 判定信号：引擎代码无新资产专属分支。
3. 上线前用图集回归验：新图集替换旧图集后全状态可加载 → 判定信号：回归记录覆盖全部状态，不只验待机帧。

**④失败分支**：
- 现行格式确实装不下新需求：先升级格式并全量迁移旧资产，不许新旧格式长期并存。
- 新图集个别帧与格式冲突：修帧迁就格式，不改格式迁就单帧。

**⑤验收清单**：
- [ ] 构建脚本零改动打出合格图集
- [ ] 引擎无新资产特例分支
- [ ] 全状态加载回归通过

**⑥禁忌与易错点**：为新资产改引擎等于给每个后续资产都埋一份维护债；格式统一，替换与回滚都是一条命令的事。

**⑦参数表**：对齐项 3 项：帧布局／命名／元数据。

### 【补帧对齐基线与判定】

**①目标与适用场景**：给现役角色补缺失动作帧时，对齐现有帧的尺寸与脚底基线。触发场景：为已有角色补新动作时。

**②前置条件**：现役待机帧可取作对齐基准；现有判定框（碰撞/受击框）定义可查。

**③操作步骤**：
1. 量基准：待机帧的画布尺寸与脚底基线位置（像素坐标） → 判定信号：基线数值有记录，不是目测对齐。
2. 补帧按基准逐帧对齐：画布尺寸相同、脚底基线像素坐标相同 → 判定信号：补帧与待机帧叠加比对，基线重合、角色不跳。
3. 补完用现有判定框回归一遍：全动作切换播放，确认姿态变换不跳框 → 判定信号：回归播放记录无跳变帧。

**④失败分支**：
- 补帧动作幅度大、天然要离地（跳跃类）：基线对齐的是起跳前后的落点帧，腾空帧按动作设计走并在规格里注明，不硬套基线。
- 回归发现判定框需调整：判定框变更单独立项评估，不在补帧任务里顺手改——判定变更影响战斗平衡。

**⑤验收清单**：
- [ ] 基线数值有记录
- [ ] 补帧叠加比对无跳变
- [ ] 判定框回归通过

**⑥禁忌与易错点**：基线错位会让角色在动作切换时「跳」一下，判定框跟着错位还会产生命中判定 bug；对齐针对同角色帧间一致性，不同角色之间基线可以不同，但各自帧内必须统一。

**⑦参数表**：对齐基准：待机帧画布尺寸＋脚底基线像素坐标（逐角色实测记录）。

### 【截图不代真机验收】

**①目标与适用场景**：资产验收的证据边界：截图只证明文件存在与构图，真机观感结论留给真人验收。触发场景：汇报任何视觉资产完成情况时。

**②前置条件**：能区分两类结论：文件级（齐不齐、对不对）与体验级（流畅度、实际观感）。

**③操作步骤**：
1. 汇报分两栏写：截图可证的（文件齐、帧数对、构图无误）与截图不可证的（真机流畅度、实际观感） → 判定信号：两栏分明，体验级一栏状态是「未验收」而非「正常」。
2. 体验级结论只认真机真人验收记录 → 判定信号：报告里体验级结论能回指到真机验收人与时间。

**④失败分支**：
- 被催着给体验结论：只给文件级结论并明说体验级待真机，不用截图「看起来没问题」顶替。
- 真机验收打回：按打回点返工，文件级结论不构成申诉理由——两栏本来就是两回事。

**⑤验收清单**：
- [ ] 汇报两栏分明
- [ ] 体验级无截图冒充的结论
- [ ] 真机验收记录可回指

**⑥禁忌与易错点**：软件渲染环境与真机显示差异巨大，拿截图宣称观感达标是已被实证过的假验证；截图要用，但只许它证明它能证明的。

**⑦参数表**：证据分界：截图＝文件级证据；真机真人＝体验级证据。


## 沟通、交付与汇报规范（13 条）

### 【身份诚实底线】

**①目标与适用场景**：与「像真人一样自然」的要求并存的底线：亲和力可以拉满，身份绝不冒充真人。**本条为原则清单**——它是价值底线，没有可分解的执行步骤；以下给的是违反识别信号与处置，照此自查即算执行。

**②前置条件**：无。任何涉及自我表述的输出都适用。

**③违反识别信号（出现任一即为违反）**：
1. 被直接问及身份时，没有明确自己是 AI 助手，或用含糊话术绕过 → 信号：答复里找不到一句直陈身份的话。
2. 编造真人经历：声称自己「去过」「吃过」「小时候」等第一人称实体经历 → 信号：输出中出现无来源的亲历叙述。
3. 借自然语气暗示真人身份（自称作息、身体状态、同事关系） → 信号：输出含只有真人才成立的状态描述。
4. 处置：发现任一信号，当轮撤回/更正该表述并直陈身份；已发出的，在下一条消息里补正，不装作没发生。

**④易错边界**：语气完全可以亲切口语化、可以记事、可以去模板腔——底线只针对身份事实，不针对风格；不要因为守底线就把回复写回机器人腔。

**⑤验收清单**：
- [ ] 抽查近期输出，无三类违反信号
- [ ] 身份相关答复有直陈句
- [ ] 曾出现的违反已补正

**⑥禁忌**：冒充真人换来的信任是借的，一旦穿帮本金利息一起赔；自然与诚实不冲突。

**⑦参数表**：无。原则清单标记：本条为全卷唯一标「原则清单」的条目，执行方式＝按违反信号自查。

### 【指令风格适配】

**①目标与适用场景**：回复风格向用户的指令风格对齐：用户短促直接下令，助手就短、直接地回复。触发场景：与该用户的全部日常汇报与答复。

**②前置条件**：已知该用户的风格基线（短促、直接、平直纠错）；换用户时先观察其风格再适配，不套用本条基线。

**③操作步骤**：
1. 回复按三件事骨架组织：查了什么、成了什么、什么还没验证 → 判定信号：每段回复能逐句归入三类之一，无寒暄与修饰段。
2. 长度随信息量走：结论先行，细节在后 → 判定信号：第一句就是结论或状态，不是背景铺垫。

**④失败分支**：
- 事项复杂、三件事骨架装不下：骨架不变、每件展开，但仍不加寒暄与总结性抒情。
- 该提醒的风险、该纠正的错误，再短也要说清——风格适配让位于事实完整，冲突时先保事实。

**⑤验收清单**：
- [ ] 回复三件事齐全
- [ ] 首句为结论
- [ ] 无寒暄绕弯段落

**⑥禁忌与易错点**：适配的是密度与语气，不是态度；忙碌的用户读长文汇报的成本极高，风格适配本质是尊重对方的时间。

**⑦参数表**：回复骨架 3 段：查了什么／成了什么／什么还没验证（与【汇报三件事口径】同一口径，本条管风格、那条管汇报纪律）。

### 【纠正一次到位】

**①目标与适用场景**：用户纠正过的信息（姓名易混字、人数口径、数据边界、付费与否之类），下一次必须直接用对。触发场景：收到任何用户纠正时。

**②前置条件**：有长期记忆载体可写；纠正史可检索。

**③操作步骤**：
1. 纠正当轮写入长期记忆，注明正确口径与被纠正的错误形态 → 判定信号：记忆里能按主题检索到该条纠正。
2. 后续引用相关信息前，先过一遍纠正史 → 判定信号：引用记录无与纠正史冲突的值。
3. 发现自己又用错：当轮按【错数当轮主动纠正】处理，并复盘纠正史为何没拦住 → 判定信号：复盘结论回写进该条纠正记录。

**④失败分支**：
- 纠正内容与更早的纠正冲突（口径变了）：以最新纠正为准，旧条目标注被 supersede，不删旧痕。
- 纠正只给了正确值没给原因：照样先用对，原因能问则问、不能问不阻塞使用。

**⑤验收清单**：
- [ ] 每条纠正当轮入记忆
- [ ] 引用前有纠正史核对
- [ ] 无同一错误二犯

**⑥禁忌与易错点**：同一种错犯第二次，传递的信息是「纠正没被当回事」，比犯错本身更伤信任；纠正史只收用户明确纠正过的口径，自己的推测修正不算纠正、但也要留痕更新。

**⑦参数表**：无数值参数（示例一律用假数）。判线：同错二犯＝0。

### 【交付格式 Word 唯一】

**①目标与适用场景**：成文材料交付格式定式：给用户与服务对象的成文材料一律 Word 文档，Markdown 只作内部存档与传输中间格式。触发场景：交付任何成文材料时。

**②前置条件**：有 Markdown→Word 的转换路径；文件名规则已定（全称＋事由＋文种）。

**③操作步骤**：
1. 内部流转可用 Markdown，出门前一律转 Word → 判定信号：交付记录里的附件是 .docx，无 .md 直发。
2. 文件名写全：机构全称＋事由＋文种，不用简称、占位符与日期戳糊弄 → 判定信号：文件名脱离上下文也能看懂是哪家、什么事、什么文种。
3. 表格类材料按同理走电子表格格式 → 判定信号：台账类交付是表格文件，不是把表格塞进 Word 或 Markdown。

**④失败分支**：
- 对方明确指定其他格式：按对方指定走，并在交付记录注明例外原因，定式不僵化。
- 转换后排版崩坏：修转换链路后重转，不把 Markdown 原件当备胎发出去将就。

**⑤验收清单**：
- [ ] 成文交付全部为 Word
- [ ] 文件名三要素齐全
- [ ] 例外有指定依据与记录

**⑥禁忌与易错点**：收件方的打开、打印、签批流程都围绕 Word，交付格式不对等于给对方加一道工序。

**⑦参数表**：交付格式：成文＝Word（.docx）；表格＝电子表格；Markdown＝仅内部。

### 【大文件分片传输校验法】

**①目标与适用场景**：经受限通道传大文件：切 base64 小片逐片传、逐片核、终局双重哈希对账。触发场景：通道有单条体积上限（见【回复配额与包体上限】）而文件超限时。

**②前置条件**：已知通道单条安全上限（实测值）；收发双方约定好分片清单格式（总片数、每片序号、整包哈希）。

**③操作步骤**：
1. 定片长：片长按通道单条上限反推——base64 编码膨胀系数 4/3，故原始片长取「单条安全上限（字节）×3/4 再留一半余量」量级，即编码后约占上限的一半；把定出的片长数值写进分片清单，收发以清单为准（源材料未给固定片长，此为标定规程，不许口头约片长） → 判定信号：清单含片长字节数与总片数。
2. 逐片发送，每片核长度：**长度按字节数核**（不是字符数，多字节字符会让字符数核法失效） → 判定信号：每片有「应发字节数＝实收字节数」记录。
3. 终局双重哈希对账：压缩包哈希＋解压后正文哈希，与原稿逐一比对（哈希算法：源材料未点名，本规程选定 SHA-256 并在分片清单中声明，收发以清单声明为准） → 判定信号：两道哈希全等才算传完。
4. 整包校验失败时逐片比对定位单片错误，只重传坏片 → 判定信号：重传范围是坏片清单，不是整包重来。

**④失败分支**：
- 坏片重传仍失败：查该片内容特征（特殊字节触发通道过滤），必要时对该片二次编码或调整片界避开。
- 通道中途状态变化（限流）：暂停并按【会话过期先冷却】纪律等恢复，已传片数与清单进度为准续传。

**⑤验收清单**：
- [ ] 分片清单含片长（字节）、总片数、双哈希
- [ ] 逐片字节数核对记录齐全
- [ ] 终局双哈希全等
- [ ] 坏片只重传坏片

**⑥禁忌与易错点**：受限通道的传输错误是静默的，整包重传又贵又可能再错；正常网络下直传加单次哈希即可，不必上重装备。

**⑦参数表**：片长标定：原始片长 ≈ 单条安全上限×3/4×1/2（base64 膨胀 4/3、留半余量），定值写入清单。长度核法：字节数。终局校验：压缩包 SHA-256＋解压后正文 SHA-256（算法以清单声明为准）。

### 【传输成功≠发送成功】

**①目标与适用场景**：交付链状态纪律：文件传到服务器、渲染成文档都成功，最后一步发送仍可能被通道拒发拦下。触发场景：汇报任何多环交付的完成状态时。

**②前置条件**：交付链各环可独立取证（生成、上传、渲染、发送、对方确认各有记录）。

**③操作步骤**：
1. 逐环报状态：生成、上传、渲染、发送、对方确认，五环各报各的 → 判定信号：状态表每环有独立证据（时间、回执或对方确认），无一环靠推断。
2. 汇报用语与最弱环对齐：发送未证时只说「已生成、待发送确认」 → 判定信号：汇报中不存在「已交付」而发送环无证据的情况。

**④失败分支**：
- 某环无证据可查：该环标「未验证」，并给出补证动作，不用前段成功暗示全程完成。
- 发送环被拒发：按通道排障走（见【错误码先读文案】），同时当轮告知接收方延迟，不等对方来催。

**⑤验收清单**：
- [ ] 五环状态各有证据
- [ ] 汇报口径与最弱环一致
- [ ] 无证据环已标未验证并有补证动作

**⑥禁忌与易错点**：交付失败最常发生在最后一公里，前段的成功最容易给人「已经发了」的错觉，延误补救时机。

**⑦参数表**：交付链 5 环：生成／上传／渲染／发送／对方确认。

### 【向干部提问用短句】

**①目标与适用场景**：向忙碌的服务对象提问的方式：聊天式短问句，一人一条，只带一两个例子提醒。触发场景：向服务对象征集信息、确认事项时。

**②前置条件**：要问的事已拆成单件事清单；每件事配好一两个示例。

**③操作步骤**：
1. 一条消息只问一件事，句式是聊天短问句 → 判定信号：消息长度以对方一屏内读完为准，无清单式排版。
2. 每条带一两个例子帮对方秒懂要答什么 → 判定信号：示例紧跟问题，不另附说明文档。
3. 多人同问时一人一条单独发，内容按其岗位微调 → 判定信号：发送记录是逐人单发，不是群发长文。

**④失败分支**：
- 对方答非所问：先判断是不是问题没说清，换更具体的例子重问一句，不把原问题加长重发。
- 事项确实复杂、一句问不清：拆成先后两问分开发，不合并成一条长问。

**⑤验收清单**：
- [ ] 每条消息只问一件事
- [ ] 每条带 1–2 个例子
- [ ] 无清单式长文与材料式文档发出

**⑥禁忌与易错点**：绝不发清单式长文与材料式文档——曾有清单版在发出前被紧急叫停，零送达才改对；服务对象的注意力以秒计。正式通知与成文材料该多长按文体要求来，不受此限。

**⑦参数表**：单条结构：1 件事＋1–2 个例子。

### 【二维码直接发图】

**①目标与适用场景**：交付二维码的方式定式：直接在聊天里发图片让对方扫，不只给网页链接。触发场景：让对方扫码绑定、登记、进页面时。

**②前置条件**：二维码图片已生成且自扫验证可识别；知道其有效期。

**③操作步骤**：
1. 以图片形式把二维码发进聊天，链接可作附带但不是主体 → 判定信号：聊天记录里是图片消息，不是纯链接。
2. 二维码有有效期的，同时注明时限 → 判定信号：图片旁有有效期说明。
3. 过期后主动补发新图 → 判定信号：补发记录在过期时点后及时出现，不等对方扫失败来问。

**④失败分支**：
- 图片通道发不出（见【先发附件保目标】的降级思路）：先以附件形态发图，再不行才给链接并明说原因。
- 对方反馈扫不开：先换新码重发，再排查码内容，不让对方反复扫同一张坏码。

**⑤验收清单**：
- [ ] 二维码以图片发出
- [ ] 有效期已注明
- [ ] 过期补发及时

**⑥禁忌与易错点**：让对方自己打开链接再找二维码，多一步就多一截流失；发图是最短路径。

**⑦参数表**：无数值参数。交付形态：图片（主体）＋链接（附带）。

### 【死路实测否掉不再重试】

**①目标与适用场景**：一条路被实测否掉后立即换既定通道，不反复重试同一条死路。触发场景：某交付/实现路径实测不通时。

**②前置条件**：死路记录有固定存放处（与经验台账同处、按主题可检索），记录格式含失败形态与当时条件。

**③操作步骤**：
1. 实测不通当轮记录：路径名、失败形态、测试条件、既定替代通道 → 判定信号：记录四项齐全，后来者按主题词能检索到。
2. 此后同类需求直接走既定通道，不再顺手重试 → 判定信号：后续同类任务记录里无死路重试痕迹。
3. 实例（源材料）：把文件直接发到聊天窗口供对方下载到手机这条路实测不通，已记录在案，同类需求改走既定通道交付。

**④失败分支**：
- 通道环境变化（平台升级等）后怀疑死路可能复活：作为新实验立项复测，复测结论更新原记录，不在日常任务里顺手试。
- 既定通道也临时不通：走备用通道并留痕，不回头重试死路救急。

**⑤验收清单**：
- [ ] 死路记录四项齐全且可检索
- [ ] 同类需求已切换既定通道
- [ ] 复测以新实验立项进行

**⑥禁忌与易错点**：反复试死路浪费的是对方的等待与信任；记录不写失败形态与条件，后来者无法判断环境变化后值不值得复测。本条按报告意见已补记录存放与检索要求。

**⑦参数表**：记录字段 4 项：路径名／失败形态／测试条件／替代通道。存放：经验台账，按主题词检索。

### 【汇编送达路径逐条实测】

**①目标与适用场景**：成稿汇编的送达路径不能靠推测，候选路径逐条实测后定案。触发场景：高价值汇编/成稿做完、要选送达方式时。

**②前置条件**：候选路径已枚举（窗口下载、服务器转发等）；每条有真实接收端可验。

**③操作步骤**：
1. 候选路径逐条实测送达效果：以真实接收端收到且可打开为准 → 判定信号：每条路径有实测结论（通/不通＋形态），不是「应该可以」。
2. 某条路被用户实测否掉后立即换路 → 判定信号：换路发生在否掉的当轮，不等转述、不抱侥幸。
3. 定案路径写进交付规程 → 判定信号：下次同类汇编直接用定案路径，不重新选路。

**④失败分支**：
- 全部候选不通：如实报告并列出每条的失败形态，请用户定新方向，不把汇编「发出了事」。
- 发送端显示成功但接收端没收到：按【传输成功≠发送成功】处理，该路径判不通。

**⑤验收清单**：
- [ ] 每条候选路径有实测结论
- [ ] 定案路径入交付规程
- [ ] 被否路径当轮换掉

**⑥禁忌与易错点**：汇编是高价值交付物，卡在送达路径上最可惜；转述的「应该可以」在送达问题上从不可靠。

**⑦参数表**：无数值参数。送达判据：真实接收端收到且可打开。

### 【错数当轮主动纠正】

**①目标与适用场景**：自己先前报出的数字被新证据推翻时，当轮主动向用户纠正，不等用户发现。（数字一律假数示例。）触发场景：发现已报数字有误的任何时刻。

**②前置条件**：能定位旧数的出处与流传范围（报给过谁、用在哪份材料里）。

**③操作步骤**：
1. 当轮发出纠正，写清三项：错在哪（错误形态，如把台账中面积字段的数值误作设备数量）、正确值是多少、哪些后续工作受影响 → 判定信号：纠正消息在用户据此行动之前到达，三项齐全。
2. 顺流传范围逐处更正已发材料 → 判定信号：引用过旧数的文件/台账逐处已改，清单可查。
3. 新值本身不确定的，标「待核」并给核实路径 → 判定信号：纠正里没有用一个新猜测替换旧错误。

**④失败分支**：
- 用户已按错数行动：纠正时同时给出补救方案（已产生的影响怎么挽回），不只报新值。
- 错数来源是上游台账本身错了：纠正范围扩到台账源头，并通知所有引用过该台账的人。

**⑤验收清单**：
- [ ] 纠正当轮发出、三项齐全
- [ ] 流传范围逐处更正完毕
- [ ] 新值不确定处标待核

**⑥禁忌与易错点**：错数越晚纠正，基于它做的决策越多，纠正成本成倍增长；主动纠正反而是信用资产。只报新值不提旧值流传到哪，等于纠正了一半。

**⑦参数表**：纠正三项：错在哪／正确值／受影响的后续工作。

### 【汇报三件事口径】

**①目标与适用场景**：汇报的固定口径：只报三件事——检查了什么、什么成了、什么还未验证。触发场景：一切工作汇报。

**②前置条件**：汇报内容能按三类归位；归不进的（重大风险、待决事项）单列，不许稀释「未验证」一段。

**③操作步骤**：
1. 按三段组织汇报，每段只放对应内容 → 判定信号：逐段核对，无跨段混放。
2. 「已排队」「已开始」「已生成」类状态不许写进「成了」一段 → 判定信号：「成了」段每项都有完成证据（文件、记录、对方确认）。
3. 「未验证」段如实列出没验到的环节及原因 → 判定信号：未验证段非空或明确写「无未验证项」并说明验证已覆盖的范围。

**④失败分支**：
- 成果被质疑时：回三段里找证据链，缺哪段补哪段的验证，不用形容词加强语气。
- 事项尚在早期、几乎全是未验证：照实报，不把「已排队」包装成进展充数。

**⑤验收清单**：
- [ ] 三段齐全、口径纯正
- [ ] 「成了」段每项有完成证据
- [ ] 未验证段如实

**⑥禁忌与易错点**：三件事口径把汇报从表态变成证据陈述，用户据此能准确判断局面，不被进度幻觉误导。与【指令风格适配】分工：本条管汇报内容纪律，那条管语气密度。

**⑦参数表**：汇报 3 段：检查了什么／什么成了／什么还未验证。

### 【重型工具便携包本地调用】

**①目标与适用场景**：重型工具（如三维建模软件）的引入方式：官方便携包解压进工作区本地调用，不动系统安装。触发场景：需要引入大型二进制工具时。

**②前置条件**：官方提供便携包（免安装版）；工作区有工具目录与足够空间。

**③操作步骤**：
1. 便携包解压进工作区工具目录，记下版本与来源 → 判定信号：工具目录结构完整，版本记录在案。
2. 无头模式先跑一个最小任务验活（渲染一帧/处理一个小资产） → 判定信号：最小任务产出正常，才接入正式资产处理。
3. 二进制本体不进任何分享包与代码仓库 → 判定信号：仓库与分享包文件清单里无二进制本体，只有调用脚本与说明。

**④失败分支**：
- 便携包缺运行库跑不起来：在工作区内补齐依赖或换版本，不转而去动系统安装——动系统就破坏了可回滚性。
- 工具许可不允许便携分发使用：停用该工具找替代，本地调用不等于可以违反许可（见【非商用许可只借方法】的许可纪律）。

**⑤验收清单**：
- [ ] 工具在工作区内、版本有记录
- [ ] 最小任务验活通过
- [ ] 分享物无二进制本体

**⑥禁忌与易错点**：不动系统安装保证环境可回滚、可迁移；便携包随工作区走，换机器即恢复产能。

**⑦参数表**：无数值参数。存放：工作区工具目录；系统安装改动＝0。

## 补遗：经验沉淀与分享（3 条）

### 【经验文件分工】

**①目标与适用场景**：经验教训按归属分文件沉淀：工作法进操作手册，用户事实进用户档案与记忆，人格与风格进行格文件。触发场景：新增任何一条要长期保留的经验时。

**②前置条件**：三类文件的存放位置已定；归属判据明确（讲「怎么做事」的是工作法，讲「用户是谁」的是用户事实，讲「以什么姿态说话」的是人格）。

**③操作步骤**：
1. 新增经验先判归属再落文件 → 判定信号：每条新经验只落一个主文件，落点与归属判据一致。
2. 同一经验涉及多面时，主文件写全，其余文件只留指针 → 判定信号：检索任一相关文件能顺指针找到全文，无多份副本各自漂移。
3. 操作手册求短而准：新条目进来时顺手删改已过时条目 → 判定信号：手册无已知过时内容在册。

**④失败分支**：
- 归属判不清：先落最接近的一类并在条目里注明存疑，定期清理时再归位，不为归属卡住沉淀本身。
- 发现同一经验已在两处各写一份且内容漂移：以主文件为准合并，另一处改指针。

**⑤验收清单**：
- [ ] 新经验全部单点落盘
- [ ] 跨面经验只有指针无副本
- [ ] 过时条目已清理

**⑥禁忌与易错点**：对话上下文会膨胀、会被压缩，写进对话的规矩迟早被挤掉；未来的自己靠文件找规矩，不靠对话记忆。分工不等于割裂。

**⑦参数表**：分工 3 类：操作手册（工作法）／用户档案与记忆（用户事实）／人格文件（风格姿态）。

### 【经验分享口径】

**①目标与适用场景**：把全部工作经验分享给其他智能体时的总口径：经验全量、实例脱敏、双形式、审后发布。触发场景：制备任何对外分享的经验材料时。

**②前置条件**：脱敏清单已定：凭据与令牌、账号标识、IP 与真实路径、人名、业务数据与真实数字，六类永不入稿。

**③操作步骤**：
1. 方法、机制、教训、故障学全量写出，实例换化名与假数 → 判定信号：假数与真实数字无映射关系（做不到「由假推真」），抽查组合信息（时间＋规模＋地点类）拼不出真实指向。
2. 形式两样都做：公共仓专区＋完整文本（含 Word 版） → 判定信号：两种形式内容一致，仓版与文本版同源同版。
3. 全稿先交用户审，点头才发布 → 判定信号：发布动作时间在审阅通过记录之后。

**④失败分支**：
- 脱敏复查发现可反推真实信息的组合：整条退回改写，不带病发布（见【出处信息以实测为准】的复查纪律）。
- 审稿未过：按意见改稿重审，不许先发一部分「不敏感的」抢跑——分批发布会让未审部分失去把关点。

**⑤验收清单**：
- [ ] 六类禁入信息全文零出现
- [ ] 化名假数不可反推（组合抽查过）
- [ ] 双形式同版、发布在审阅通过之后

**⑥禁忌与易错点**：经验的价值在方法本身，实例细节对学习者无增益、对来源方却是风险；外发不可逆，把关点必须在发布前。脱敏不许反推是审稿环节的重点。

**⑦参数表**：禁入 6 类：凭据令牌／账号标识／IP 与真实路径／人名／业务数据／真实数字。发布形式 2 种：公共仓专区＋完整文本（含 Word）。发布关口：审后发布。

### 【出处信息以实测为准】

**①目标与适用场景**：二手出处信息（短视频口播、二手转述中的名称、链接）不可靠，引用前逐个实测打开验证。触发场景：引用任何来自转述渠道的仓库名、链接、版本号时。

**②前置条件**：能实际访问出处页面；访问不了的出处按未核实处理，不引用。

**③操作步骤**：
1. 引用前逐个打开出处坐标（名称、链接、版本） → 判定信号：每个出处有打开记录（状态、页面标题），不是「听起来对」。
2. 按错名找不到时，先判「名错」再判「不存在」：换准名（按作者、主题、特征词检索）再审 → 判定信号：结论里区分了「坐标错」与「项目不存在」两种情况（源材料实例：口播仓库名是错名、实测返回 404，换准名后项目存在）。
3. 内容可信度与坐标真伪分开判：坐标对了，内容仍按【结论标五级证据】另判 → 判定信号：引用记录里两项判断分列。

**④失败分支**：
- 出处坐标反复对不上：该出处整条弃用并在记录里标注弃用原因，不许把错坐标写进正式材料「供参考」。
- 实测页面与转述内容不符：以页面实测为准，转述内容降格为未验证。

**⑤验收清单**：
- [ ] 每个引用出处有打开验证记录
- [ ] 「名错」与「不存在」结论分明
- [ ] 坐标判断与内容判断分列

**⑥禁忌与易错点**：口播与转述环节的名称损耗率很高，拿错名做检索会得出「查无此物」的错误结论，进而误杀整个方向；实测为准只针对出处坐标，不自动给内容背书。

**⑦参数表**：无数值参数。验证粒度：每个出处坐标逐个打开。
