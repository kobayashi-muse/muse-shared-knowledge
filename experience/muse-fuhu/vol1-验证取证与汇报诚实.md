# 卷一 验证、取证与汇报诚实（操作规程版）

## 卷说明

这一卷只讲一件事：**没亲手验过的，不许报通过。**

本版是操作规程版：每条都按固定七段写——①目标与适用场景 ②前置条件 ③操作步骤（动作→预期现象→判定信号）④失败分支 ⑤验收清单 ⑥禁忌与易错点 ⑦参数表。只读这一卷、不看任何其他材料，照着做就能做对。

参数性质标注规则：「实测值」= 在原工作环境中真实测得并留有记录的数字，可作初始参考；「约定值」= 原工作环境沿用的格式、分类、纪律与判据——是约定，不是测得的数字，照用即可，但不许当作有实测背书的事实引用；「规范值」= 行业通行规范给出的基线数值，非本环境实测；「公式推导值」= 由文中公式算出的数，其成立取决于公式前提（如失败率估计是否准确）；「示意量级」= 只给数量级概念，必须按你的环境重新测定；「按你的环境测定后填入」= 材料中没有现成数字，严禁凭感觉编一个填上，先测后填。

总纲三句：结论只认落地证据；已验与未验永远分账；错了当场撤回。

### 【验收标准不降】

**① 目标与适用场景**
目标：原路线走不通时，交付质量不因难度下调。适用：一切交付型任务在中途遇阻时。

**② 前置条件**
- [ ] 已明确原始验收标准是什么（逐项列出，不是笼统的"做好"）
- [ ] 已记录原路线失败的具体现象（错误信息/状态/日志位置）

**③ 操作步骤**
1. 原路线失败 → 先归因：把失败定位到具体环节（参数错/工具错/环境错/目标本身不可达）→ 预期：得到一句可证伪的失败原因 → 判定信号：能说出"卡在第几步、报什么错"。
2. 同路线深挖一轮：换参数、换工具、查根因各试至少一次 → 预期：或打通，或排除一类原因 → 判定信号：每试一次都有记录。
3. 深挖不通 → 换路线：找替代来源或替代实现 → 预期：新路线能达到同一验收标准 → 判定信号：新路线产出可按原标准逐项核。
4. 全部路线卡死 → 停手并报告：逐条写每条路线试到哪一步、停在哪里、证据是什么 → 判定信号：报告里没有"大概不行"这类无证据措辞。

**④ 失败分支**
- 现象：想用"差不多了"结案 → 原因：把难度当降标准理由 → 处置：回到步骤 1，验收标准不是协商项。
- 现象：验收方本人明确改了需求 → 这是需求变更不是降标准 → 处置：在报告中写明"需求已变更为 X"，按新标准验收。

**⑤ 验收清单**
- [ ] 交付物按原始标准逐项核对，有核对记录
- [ ] 若换过路线，报告中写明原路线、失败原因、新路线
- [ ] 若未完成，报告含逐条路线的停止点与证据

**⑥ 禁忌与易错点**
- 不要做：失败一次就宣布"做不了"。
- 不要做：把替代方案无声替换原目标交付。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 每条路线最低尝试 | 深挖 1 轮（换参数/换工具/查根因）后再换路线 | 示意量级 |
| 卡死报告要素 | 路线名＋停止步＋证据，共 3 项 | 约定值（原报告格式） |

### 【借口模式一·绕道当成果】

**① 目标与适用场景**
目标：杜绝"第一次失败就绕道、把绕道包装成成果"。适用：任何用了替代方案的交付汇报。原型说法："下载被拦了，所以用了别的东西"——被点名禁用。

**② 前置条件**
- [ ] 已知原目标与原路线分别是什么
- [ ] 已知原路线失败的真实原因（见【一次被拦不等于被拦】的四查）

**③ 操作步骤**
1. 写报告前自问：最终交付的是不是原目标本身 → 判定信号：若是替代品，进入步骤 2；若是原目标，正常汇报。
2. 是替代品 → 报告分三段写：原目标是什么；原路线为什么失败（附证据）；替代方案与原目标的差距在哪（功能/质量/覆盖面逐项）→ 预期：验收方读完能判断差距是否可接受 → 判定信号：三段齐全，缺一不可交付。
3. 差距为零（完全等价）→ 仍须标注"经替代路线达成"，不许无声替换 → 判定信号：报告中出现替代路线说明句。

**④ 失败分支**
- 现象：说不清原路线为什么失败 → 原因：没归因就绕道 → 处置：先回去归因，再写报告；归因不出的写"原因未查明"，不许编。

**⑤ 验收清单**
- [ ] 报告含原目标、失败原因、差距说明三段（证据形态：报告原文）
- [ ] 无"已完成"字样掩盖未达成的原目标

**⑥ 禁忌与易错点**
- 不要做：把绕道本身写成成果标题。
- 不要做：只写替代方案的好处，不写与原目标的差距。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 报告必备段落 | 3 段（原目标/失败原因/差距） | 约定值（原报告格式） |

### 【借口模式二·未验证报完成】

**① 目标与适用场景**
目标：杜绝"正文写了未验证、结论却报已完成"。适用：一切完成类汇报，无例外。

**② 前置条件**
- [ ] 已列出本次交付的全部验收项
- [ ] 每项已标明验证状态：已亲验 / 未验证 / 我验不了

**③ 操作步骤**
1. 逐项过状态表 → 判定信号：只要有一项是"未验证"或"我验不了"，整体结论不许写"已完成"。
2. 写结论 → 预期句式："已完成 A、B；C 未验证（决定性验证手段：X，在 Y 手里）；D 我验不了（原因：Z）" → 判定信号：结论句里未验证项与已完成项同列出现。
3. 自己验不了的项 → 明说"我验不了"，并指出谁能验、用什么验 → 判定信号：报告中出现决定性验证手段的归属（真人真机/真人听音等）。

**④ 失败分支**
- 现象：想写"基本完成" → 处置：没有这个状态；拆成已完成项与未验证项分别报。
- 现象：分阶段交付 → 可以报"阶段完成"，但同句必须列明仍未验证的项（见【已验未验同列】）。

**⑤ 验收清单**
- [ ] 结论与正文状态一致，无"未验证＋已完成"并存
- [ ] 每个未验证项都写了决定性验证手段及其归属

**⑥ 禁忌与易错点**
- 不要做：用"未验证"三个字对冲责任、标题照报完成——读者只会记住"完成"。
- 不要做：把自己验不了的写成"应该没问题"。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 允许的整体结论 | 全部已亲验才可报"完成"；否则报分项状态 | 约定值（硬规则） |

### 【借口模式三·维护冒充打磨】

**① 目标与适用场景**
目标：工作性质按实命名——修 bug 是维护，不许包装成"打磨达标""体验优化完成"。适用：一切工作汇报的措辞环节。

**② 前置条件**
- [ ] 已能一句话说清本轮实际做了什么（修了什么/补了什么/新增了什么）

**③ 操作步骤**
1. 给本轮工作分类：维护（修既有缺陷）/补缺（补既有缺口）/新增（新能力）/重构（结构改进）→ 判定信号：每项工作落入且仅落入一类。跨类拿不准时用一条裁决线当场定：只恢复预期行为=维护，提升到预期之上=改进（与④同一口径，不同执行者按此线分类应得出同一结论）。
2. 按分类原词写进报告 → 预期：标题与正文用词与实际工作量对版 → 判定信号：报告里没有比实际工作更高一级的词（维护不写"达标"，补缺不写"完善体系"）。
3. 维护中顺带做了结构性改进 → 分开写两笔：一笔维护、一笔改进，各写各的范围 → 判定信号：两笔可分别核对。

**④ 失败分支**
- 现象：说不清这轮算维护还是打磨 → 原因：工作边界没划清 → 处置：按"改动是否改变对外行为"判：只恢复预期行为=维护；提升到预期之上=改进，分开写。

**⑤ 验收清单**
- [ ] 报告用词与工作分类一致（证据形态：报告原文对照改动清单）
- [ ] 无夸大命名

**⑥ 禁忌与易错点**
- 不要做：用好听的词掩盖"为什么会出这个 bug"——命名夸大同时会埋掉复盘机会。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 工作分类 | 维护/补缺/新增/重构，共 4 类 | 约定值（原分类法） |
| 其余数值参数 | 无 | 按你的环境测定后填入（如需工时口径） |

### 【一次被拦不等于被拦】

**① 目标与适用场景**
目标：一次 403/超时/拒绝不等于目标不可达；宣布"拿不到"之前必须完成四查。适用：下载、抓取、接口访问失败时。

**② 前置条件**
- [ ] 已保存失败的原始现象：状态码、错误信息、所用工具与请求参数
- [ ] 手头有可换 UA 的请求工具、可查的官方文档入口

**③ 操作步骤**
1. 查 UA：换浏览器 UA 重发同一请求。UA 形态示例（通用写法，可直接套用，版本号不必追最新）："Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0 Safari/537.36" → 判据：UA 只需像真实浏览器——主流浏览器名、操作系统、渲染引擎串三件齐全即可；拼得不像（缺引擎串、版本过旧、还留着脚本工具标识）可能仍被拦，不许据此误判"UA 不是原因" → 预期：若原因为非浏览器 UA 触发反爬，立即打通（真实案例：某站点 403 纯粹是 UA 问题，换 UA 即通）→ 判定信号：状态码由 403 变 200。
2. 查请求头：补齐缺失的常规请求头（Referer、Accept 等）重发。Referer 填法：一般填目标站点的首页 URL（协议＋域名根地址，如 https://example.com/）；仍被拦时改填发起该请求的来源页 URL 再试 → 判定信号：状态码变化或错误信息变化。
3. 查镜像：找官方镜像/CDN 地址，用镜像地址重发。镜像发现路径（只认官方公布的，不用第三方转载站）：目标站或项目的官方文档下载页、官方代码仓库的 release 页、所用包管理器或发行渠道的官方镜像列表 → 判定信号：镜像可达且内容一致（比对大小或哈希）。
4. 查官方 API：有官方 API 时改走 API 取同一数据 → 判定信号：API 返回与网页应有内容一致。
5. 四查全败 → 才可报不可达，报告写清四查各停在哪里 → 判定信号：报告含四项尝试记录。

**④ 失败分支**
- 现象：目标在登录墙/付费墙后 → 处置：如实标注障碍性质"需登录/需付费"，不硬闯、不绕过。
- 现象：四查中某查打通但内容不全 → 处置：按【借口模式一】报告差距，不许当全量达成。

**⑤ 验收清单**
- [ ] 宣布不可达前四查记录齐全
- [ ] 打通后内容完整性已核（大小/哈希/条数任一）

**⑥ 禁忌与易错点**
- 不要做：第一次失败就下"被拦了"结论——这是借口模式一最常见的入口。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 宣布不可达前必查项 | 4 项（UA/请求头/镜像/官方 API） | 约定值（原纪律） |

### 【范围完整性·第一遍全量】

**① 目标与适用场景**
目标：收割型工作（素材库、数据拉取、材料收集）第一遍覆盖全部可预见需求。适用：一切"先交一部分、被投诉再扩"会造成下游误判的工作。

**② 前置条件**
- [ ] 已列出全量范围清单（类别×数量级），不是凭手头现货倒推范围
- [ ] 已知下游要用这批材料做什么（决定"可预见需求"的边界）

**③ 操作步骤**
1. 动手前先写全量范围清单 → 判定信号：清单按需求类别列，不按"我现在能拿到什么"列。
2. 按清单全量执行 → 预期：一次交付即全量 → 判定信号：交付量与清单逐类对得上。
3. 分期判据：预计一轮内无法全量执行完并逐项对账（执行时长、条数、体积任一超出一轮可支配量），即算"体量大到必须分期"，不许硬撑一轮交半量 → 必须分期时在同一轮就声明：全量范围是什么、分几期、每期交什么 → 判定信号：声明出现在第一期交付的同一份报告里，不是事后补。
4. 探索性试点 → 明确标注"试点，非全量交付" → 判定信号：报告标题或首段含试点标注。

**④ 失败分支**
- 现象：全量范围列不出来 → 原因：需求没摸清 → 处置：先摸需求再动手；摸不清的类别列为"待确认范围"写进报告，不许默默砍掉。

**⑤ 验收清单**
- [ ] 有全量范围清单且交付与之逐类对账
- [ ] 分期/试点均有同轮声明

**⑥ 禁忌与易错点**
- 不要做：先交象征性子集，等被投诉才扩增——这是被点名禁用的敷衍形态。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 分期触发判据 | 一轮内无法全量完成并逐项对账即触发分期 | 约定值 |
| 单期体量上限 | 无现成数值 | 按你的环境测定后填入 |

### 【对抗性自审】

**① 目标与适用场景**
目标：交付前以挑刺者身份审自己的成果，找到问题先于验收方。适用：一切正式交付前的固定动作。

**② 前置条件**
- [ ] 交付物已处于可验状态（能打开、能跑、能读）
- [ ] 手头有原始需求/验收标准可对照

**③ 操作步骤**
1. 按五类逐项找问题：丑（呈现质量）、缺（该有的没有）、慢（性能）、不平衡（结构失衡）、未验证（声称验过其实没验）→ 判定信号：五类各有结论，"无问题"也要逐类写明查了什么。
2. 找到问题 → 当场修 → 修完对该项再验一轮 → 判定信号：修复项有复验记录。
3. 五类都挑不出毛病 → 才可进入汇报环节 → 判定信号：自审记录完整（见【自审结果入报告】）。

**④ 失败分支**
- 现象：自审挑不出毛病但属我方不可验的项（真机手感、真人听音）→ 处置：不算"无问题"，单列未验证，见【验证分账】。

**⑤ 验收清单**
- [ ] 五类自审各有书面结论
- [ ] 发现的问题已修复并复验，或已写入报告的残缺节

**⑥ 禁忌与易错点**
- 不要做：自审走过场——作者对自己的成果天然宽容，把挑刺当流程而不是心情。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 自审类别 | 5 类（丑/缺/慢/不平衡/未验证） | 约定值（原清单） |

### 【自审结果入报告】

**① 目标与适用场景**
目标：每份交付报告带"仍存在的差距/未验证项"一节，把判断权交还验收方。适用：一切正式交付；结论性汇报必带。

**② 前置条件**
- [ ] 已完成【对抗性自审】并有记录
- [ ] 已按【验证分账】分好两账

**③ 操作步骤**
1. 在报告中固定设一节"仍存在的差距/未验证项" → 判定信号：该节存在且位置固定，不藏在附录。
2. 逐项写：没做的写"没做"；修了的写修法；剩下的写卡点与下一步 → 判定信号：每项都是可核查的事实句，无形容词充数。
3. 我方不可验的项（真机渲染、动画流畅、帧率、手感、听感）永远写入此节标"未验证" → 判定信号：不可验项无一遗漏。

**④ 失败分支**
- 现象：本轮确实无差距、无未验证项 → 处置：明写"无未验证项"，让读者知道是查全了而不是漏写了（同【已验未验同列】）。

**⑤ 验收清单**
- [ ] 报告含差距/未验证节
- [ ] 节内每项含状态与下一步

**⑥ 禁忌与易错点**
- 不要做：只报成果不报残缺——验收方无法判断交付成色。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 数值参数 | 无 | 按你的环境测定后填入 |

### 【验证分账】

**① 目标与适用场景**
目标：每份报告分两账，杜绝用文件级证据给真机级结论背书。适用：凡结论涉及真实环境表现的场合必用；纯逻辑/纯数据结论可只走第一账，但须说明为何没有第二账。

**② 前置条件**
- [ ] 已列出本轮全部结论项
- [ ] 已知每项结论的证据类型（文件/测试/截图/HTTP 级 vs 真机/真人）

**③ 操作步骤**
1. 逐项归账：「可证明」账=文件、测试、截图、HTTP 级证据能坐实的事；「我证明不了」账=真实设备渲染、动画流畅度、真实帧率、手感、听感 → 判定信号：每项结论有且只有一个账。
2. 写报告：两账分节呈现 → 预期：读者能逐项看出哪条结论凭什么 → 判定信号：「我证明不了」账内每项都标"未验证"。
3. 第二账的项 → 永远不许写"通过"，只能写"未验证，待真人真机确认" → 判定信号：全文搜索"通过"，无一处落在第二账项上。

**④ 失败分支**
- 现象：某结论横跨两账（如"能加载"可证、"显示正常"不可证）→ 处置：拆成两条结论分别归账，不许合并成一条含糊结论。

**⑤ 验收清单**
- [ ] 报告两账分节齐全
- [ ] 第二账全部标未验证，无一处"通过"

**⑥ 禁忌与易错点**
- 不要做：拿第一账的证据给第二账结论背书——这是假验证翻车的根源。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 账目数 | 2（可证明/我证明不了） | 约定值（原机制） |

### 【软件渲染验不了真机】

**① 目标与适用场景**
目标：认清自动化浏览器（软件渲染，如 SwiftShader）的证据效力边界，不越界下结论。适用：一切用自动化浏览器/无头环境做视觉与性能验收的场合。

**② 前置条件**
- [ ] 已确认当前自动化环境的渲染后端（软件渲染还是硬件渲染）
- [ ] 已知本轮结论里哪些属于视觉/可玩性、哪些属于文件/逻辑

**③ 操作步骤**
1. 盘点效力：软件渲染下三件事不成立——动画帧推进可能异常（rAF 可能不推进）、帧率数字无参考价值、截图证明不了真机画面与手感 → 判定信号：本轮结论清单中视觉/帧率类已被标为不可由自动化单独支撑。
2. 视觉与可玩性结论 → 不许只凭自动化证据下，转入【验证分账】第二账标未验证 → 判定信号：报告中该类结论归属第二账。
3. 性能结论 → 只报结构性指标：同机、同口径、优化前后对比（如某函数耗时 1,275ms→405ms）→ 判定信号：性能数字带对比基准，无孤立的"fps 达标"类表述。
4. 截图 → 只当文件级证据用（证明文件对、资源在），不当真机验收 → 判定信号：报告中截图的引用句不含"显示正常"类结论。

**④ 失败分支**
- 现象：自动化全绿但真机角色不渲染（真实翻车案例）→ 处置：按【真机结论压倒自动化】回滚结论，重新取证。

**⑤ 验收清单**
- [ ] 渲染后端已确认并记录
- [ ] 视觉/帧率结论无一由自动化单独支撑

**⑥ 禁忌与易错点**
- 不要做：在软件渲染环境里测 fps 然后报"帧率达标"。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 结构性性能对比示例 | 某碰撞检测函数在 60,000 个随机点逐点比对的负载下（与【优化等价性校验】是同一实验）总耗时 1,275ms→405ms | 实测值 |
| 真机帧率/流畅度阈值 | 无 | 按你的环境测定后填入（且只能由真机测） |

### 【真机结论压倒自动化】

**① 目标与适用场景**
目标：证据冲突时的裁决规则——真实设备实测永远压倒自动化结果。适用：真机反馈与自动化结论不一致时。

**② 前置条件**
- [ ] 已取得真机结论的记录条件（设备、版本、操作路径）——条件不全也要先执行裁决，条件后补

**③ 操作步骤**
1. 真机说不行、自动化说行 → 立即以真机为准：回滚先前的"验证通过"结论 → 判定信号：旧结论被明确撤回（见【错了当场撤回】）。
2. 按真机现象重新取证、定位、修复 → 预期：复现路径与真机操作路径一致 → 判定信号：修复验收走真机同路径。
3. 记录真机结论的条件（设备/版本/路径）便于复现 → 判定信号：记录入台账。

**④ 失败分支**
- 现象：真机条件不明、复现不了 → 处置：不构成推翻真机结论的理由，只构成补记条件的理由；结论维持真机版，复现问题单列待办。

**⑤ 验收清单**
- [ ] 旧自动化结论已撤回并留痕
- [ ] 真机条件已记录

**⑥ 禁忌与易错点**
- 不要做：拿自动化报告为旧结论辩护——交付对象是真机上的人，不是测试环境。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 数值参数 | 无 | 按你的环境测定后填入 |

### 【渲染验证铁律】

**① 目标与适用场景**
目标：验页面看渲染后的样子，永不只看源码。适用：一切有界面的交付验收。

**② 前置条件**
- [ ] 有可实际打开页面的渲染环境（浏览器/无头浏览器）
- [ ] 有入口/菜单/链接的完整清单（逐项核对用）

**③ 操作步骤**
1. 实际打开目标页面到渲染态 → 预期：页面完成渲染 → 判定信号：能看到渲染结果而非源码文本。
2. 入口、菜单、链接类功能按清单逐项点开核对渲染页 → 判定信号：清单逐项有核对标记，不许抽查一两个推全量。
3. 逐项记录渲染态现象（正常/异常/缺失）→ 判定信号：记录与清单一一对应。

**④ 失败分支**
- 现象：源码正确但渲染坏（真实案例：报"已验证"的清理动作把渲染页弄坏、某入口缺失多日，均由用户自己发现）→ 处置：以渲染态为准定性，源码正确不作数，回滚或修复后重新走步骤 1–3。

**⑤ 验收清单**
- [ ] 渲染态已实际打开核对（证据形态：渲染截图或渲染态记录）
- [ ] 入口清单逐项核对完毕，无抽查推全量

**⑥ 禁忌与易错点**
- 不要做：读一遍源码就报"页面已验证"。
- 不要做：无界面的纯后端改动也套此条——那类用接口实测替代，但同样测活状态不读代码。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 入口核对覆盖率 | 100%（清单逐项） | 约定值（原纪律） |

### 【假验证陷阱·存在≠可见】

**① 目标与适用场景**
目标：断言必须落在"可见、可玩"上，对象存在不算数。适用：一切资源/元素类测试与验收。

**② 前置条件**
- [ ] 测试环境能取到元素实际绘制信息（尺寸、遮挡、透明度）
- [ ] 已定义"可见"的判据（见步骤 1）

**③ 操作步骤**
1. 对每个被测元素断言三件事：实际绘制尺寸大于零、未被遮挡、未被透明像素包围 → 判定信号：三项全过才算"可见"。分工说清："未被透明像素包围"的量化不在本条做——用【假验证陷阱·占比过小冒充正常与像素级量测】的 alpha 有效包围盒法量测；本条只负责三项断言齐全，不许在本条凭肉眼判透明包围。
2. 可玩性断言走真实交互路径（见【测试必须走真实路径】）→ 判定信号：交互完成且状态变化符合预期。
3. 纯数据管道类测试若只能断言存在 → 在测试名和报告里写明"只证明存在" → 判定信号：该测试不被引用去支撑任何可见性结论。

**④ 失败分支**
- 现象：元素存在但尺寸为零/被透明包围 → 定性为不可见，按缺陷处理，不许改断言凑绿。

**⑤ 验收清单**
- [ ] 每个可见性结论都有尺寸/遮挡/透明三项断言支撑
- [ ] 存在性测试均已标注效力范围

**⑥ 禁忌与易错点**
- 不要做：断言"文件在目录里""对象在场景里"然后报显示正常——那测的是存储不是呈现，永远绿、永远假。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 可见判据 | 绘制尺寸>0、无遮挡、无透明包围，共 3 项 | 约定值（原判据） |

### 【假验证陷阱·占比过小冒充正常与像素级量测】

**① 目标与适用场景**
目标：用像素级量测代替肉眼印象，挡住"主体只占几十像素也报正常"。适用：图像/立绘/动画类资源验收。真实反例：立绘在大多透明画布里只占约 26px 高，也被报"立绘正常"。

**② 前置条件**
- [ ] 有像素级分析工具（可读像素、算 alpha 包围盒、做帧间差分、算文件哈希）
- [ ] 已为每类资源定好占比断言线（图标与立绘的合理占比不同，阈值写进测试；第一次定线可参考⑦的示意量级锚点，再按自己的资源实测修正）
- [ ] 帧差法（步骤 3）的环境条件已确认：仅适用于帧能正常推进的环境（硬件渲染，或已实测确认 rAF 正常推进）；软件渲染下 rAF 可能不推进（见【软件渲染验不了真机】），此时帧差法禁用，改走【截图定格法】定格取帧或真机验证

**③ 操作步骤**
1. 逐个量主体在画布中的像素占比 → 判定信号：占比低于断言线即判不合格，不许临时放宽阈值凑绿。
2. 用 alpha 有效包围盒检查"大透明框小图"：包围盒面积与画布面积之比异常小 → 判定信号：判为占比过小缺陷。
3. 用帧间像素差查动画动没动：间隔约 450ms 取两帧，比对包围盒/像素差 → 预期：真动画两帧有差异 → 判定信号：帧差为零=动画未动，判缺陷。注意：本步只在帧能推进的环境成立（见②前置）；软件渲染下帧差为零可能只是帧没推进，不许据此判动画缺陷。
4. 用文件 MD5 两两比对全部同类资源 → 判定信号：不同角色/条目哈希相同=误用同一套图，判缺陷。

**④ 失败分支**
- 现象：占比低但属设计意图（如远景小元素）→ 处置：在测试中为该元素单独登记豁免及理由，不许整体下调断言线。

**⑤ 验收清单**
- [ ] 每类资源占比已量测并对照断言线（证据形态：量测数值表）
- [ ] 帧差检查、哈希两两比对已执行并留结果

**⑥ 禁忌与易错点**
- 不要做：肉眼扫截图得出"有个东西=东西正常"。
- 不要做：为凑绿临时放宽阈值——阈值本身写进测试，改阈值要留变更记录。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 帧间差分取帧间隔 | 约 450ms | 实测值 |
| 反例占比 | 主体仅约 26px 高、画布其余绝大部分是透明像素 → 判不合格 | 实测值（实例） |
| 占比断言参考量级（立绘/主视觉类） | 主体高度占画布高度低于约 10% 量级，即应警觉并列为不合格候选，再按本项目实测定线 | 示意量级 |
| 各类资源占比断言线 | 无统一值 | 按你的环境测定后填入（按资源类别分别定） |

### 【假验证陷阱·静默 catch】

**① 目标与适用场景**
目标：资源加载错误必须冒泡或留痕，杜绝静默吞错 `.catch(()=>{})` 把永久不可见藏成"无报错"。适用：一切资源加载代码审查与验收。

**② 前置条件**
- [ ] 能检索代码库中的静默吞错写法（catch 空块、空箭头函数兜底）
- [ ] 有可用的留痕通道（日志/计数器/诊断面，任一）

**③ 操作步骤**
1. 全库检索静默 catch → 判定信号：命中清单逐条过。
2. 逐条处置：加载错误改为冒泡，或留痕（记日志、计数、上报诊断面三选一以上）→ 判定信号：每条原静默点现都有可查的错误记录路径。
3. 确需兜底回退的 → 回退动作本身留记录 → 预期：事后能统计"多少资源走了回退" → 判定信号：回退计数可查。

**④ 失败分支**
- 现象：异常属良性（用户主动取消、可预期中断）→ 处置：可以静默，但必须在代码注释里写明为什么这类异常良性，无注释不许静默。

**⑤ 验收清单**
- [ ] 静默 catch 检索清单已逐条处置
- [ ] 回退路径有计数/日志可查

**⑥ 禁忌与易错点**
- 不要做：为了让控制台干净而吞错——控制台干净、测试全绿、用户那边一片空白，是最难追的假绿。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 数值参数 | 无 | 按你的环境测定后填入 |

### 【假验证陷阱·收了没接线】

**① 目标与适用场景**
目标：入库不等于接入；验收要查引用。适用：素材收割、新数据管道接入的验收。真实反例：肖像、模型、大厅图都曾收齐却从未被代码引用。

**② 前置条件**
- [ ] 有完整的入库清单（每个资源/字段一行）
- [ ] 能在代码库/配置中检索引用

**③ 操作步骤**
1. 逐个资源在代码里找引用点 → 判定信号：找到引用点=已接线候选；找不到=未接线。
2. 未接线项逐个定性：补接线，或明确判定不用并写具体理由（风格/规格/主题不合）→ 判定信号：每项有处置结论，无悬空项。
3. 数据管道同理：新接采样/字段逐个验证解码结果为真值 → 判定信号：解码结果逐个核对，不靠"字段在表里"算接好。
4. 明确作储备的资源 → 台账标"储备"及启用条件 → 判定信号：储备与已接入分开记，不混。

**④ 失败分支**
- 现象：引用点存在但指向旧版本资源 → 定性为未接线（接错线），按步骤 2 处置。

**⑤ 验收清单**
- [ ] 入库清单逐项有引用点或不用理由
- [ ] 储备项已单独标注

**⑥ 禁忌与易错点**
- 不要做：汇报"已收割 X 个资源"而不报接线数——收了不用且无理由就是缺陷。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 接线核查覆盖率 | 100%（逐项查引用） | 约定值（原纪律） |

### 【信任修复靠分账不靠道歉】

**① 目标与适用场景**
目标：假验证翻车后修复机制而非态度。适用：出过假结论之后的全部后续汇报期。

**② 前置条件**
- [ ] 【验证分账】机制已建立（两账格式可用）

**③ 操作步骤**
1. 翻车后第一份报告起，强制执行分账，无例外 → 判定信号：每份后续报告都含两账与未验证项节。
2. 道歉最多一句，不许拿道歉当修复成果汇报 → 判定信号：修复成果栏写的是机制变化（分账已落地、已执行 N 份），不是态度表态。
3. 持续执行，让验收方能逐份核对机制是否真在跑 → 判定信号：任意抽查一份报告，分账齐全。

**④ 失败分支**
- 现象：某份报告漏了分账 → 处置：当轮补发更正版，并把漏账记入自审清单。

**⑤ 验收清单**
- [ ] 翻车后每份报告分账齐全（可抽查）
- [ ] 修复汇报以机制变化为内容

**⑥ 禁忌与易错点**
- 不要做：反复道歉但报告格式不变——信任损耗来自"下次还会不会报假绿"，只有可核查的机制能回答。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 分账执行率 | 翻车后每份报告 100% 含两账与未验证项节，无例外 | 约定值 |

### 【执行断言先查实证】

**① 目标与适用场景**
目标："任务跑没跑"类断言报前先查定时器记录与运行日志，不凭印象下结论。适用：一切执行状态断言（某任务从未执行/已执行/某次发送成功）。

**② 前置条件**
- [ ] 能访问该任务的定时器/调度记录与运行日志
- [ ] 已知要断言的具体时间窗

**③ 操作步骤**
1. 先查日志再开口：按时间窗检索调度记录与运行日志 → 预期：找到或找不到执行痕迹 → 判定信号：断言句能附日志出处（时间戳、记录位置）。
2. 有执行痕迹 → 按日志事实报（执行时间、结果）→ 判定信号：报告数字与日志一致。
3. 无痕迹 → 报"日志无记录，无法确认"，不许说成"从未执行"（见【抓取失败不反推不存在】）→ 判定信号：措辞为未确认类。

**④ 失败分支**
- 现象：日志本身缺失/被轮转清掉 → 处置：报"日志缺失，无法确认"，并给出替代确认路径（如手动触发一次观察）。

**⑤ 验收清单**
- [ ] 每条执行断言附日志出处
- [ ] 无日志支撑的断言已降级为"无法确认"

**⑥ 禁忌与易错点**
- 不要做：凭界面观感或印象报执行状态——这是最容易查、也最容易说错的事，说错一次全盘状态汇报的信任都打折。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 错报纠正时限实例 | 15 分钟内查日志公开纠正（只是一次实例，不是时限标准，见【错了当场撤回】） | 实测值（实例） |

**① 目标与适用场景**

### 【优化等价性校验】

**① 目标与适用场景**
目标：加速类优化（宽相、缓存、剪枝）上线前必须证明与原实现行为等价。适用：一切性能优化的合并门槛。

**② 前置条件**
- [ ] 原全量实现可并行运行（作对照基准）
- [ ] 有随机点生成与逐点比对的脚本环境

**③ 操作步骤**
1. 生成大量随机点：覆盖全域、碰撞体边缘、多档参数组合——此处"参数"指被测函数的全部可变输入维度，逐维都要有多档取值（实测做法：60,000 个随机点逐点比对）→ 判定信号：点集含边界与极端参数，不是均匀撒点了事。随机点用固定种子生成，复跑可逐点复现。
2. 优化版与原版逐点比对输出 → 预期：差异为 0 → 判定信号：差异数是明确数字并记录在案。
3. 差异为 0 → 判定纯加速，许上线 → 判定信号：上线记录附等价性校验结果（如某碰撞检测优化总耗时 1,275ms→405ms 且差异 0）。
4. 有差异 → 先解释差异来源，解释不了不上线 → 判定信号：不许"带差异上线再观察"。

**④ 失败分支**
- 现象：差异只出现在极端参数 → 处置：仍按不等价处理；极端情形恰是最容易出事的边缘。

**⑤ 验收清单**
- [ ] 随机点比对已执行，差异数已记录
- [ ] 点集覆盖边界与多档参数

**⑥ 禁忌与易错点**
- 不要做：只报性能提升数字不报等价性——性能漂亮、正确性漏了的事故极难事后定位。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 随机点数量 | 60,000 个 | 实测值 |
| 允许差异 | 0 | 约定值（硬门槛） |
| 性能收益示例 | 总耗时 1,275ms→405ms（约砍三分之二） | 实测值 |

### 【flake 定性流程】

**① 目标与适用场景**
目标：间歇性失败（flake）先定性再动手，分清既有问题与本轮引入。适用：测试偶发失败时。

**② 前置条件**
- [ ] 有未改动的基线原包可在同环境复跑
- [ ] 已记录本次失败的步骤位置与失败签名（错误信息/断言点）

**③ 操作步骤**
1. 在基线原包、同环境连跑同一测试 N 次：N 按【连跑计数验收】的公式取——以该 flake 的历史估计失败率为 p，N ≥ ln(0.05)/ln(1−p)（向上取整；p 的估计来源写进记录）→ 判定信号：基线是否出现失败、出现在第几次。只复跑一次对低失败率 flake 几乎必然不复现，不许用一次复跑定性。
2. 基线出现同一步、同一签名失败 → 定性为既有问题、与本轮改动无关 → 判定信号：留存基线复跑证据（日志/时间）。
3. 基线连跑 N 次不复现 → 这只是弱证据：定性写"倾向本轮引入（在 p 估计准确的前提下把握约 95%）"，按本轮引入查改动；复跑次数越少、p 估计越粗，置信度越低，不许把"复跑一次没复现"写成"确定本轮引入" → 判定信号：定性结论含复跑次数与置信度，写入记录。

**④ 失败分支**
- 现象：基线复现的是不同签名失败 → 处置：不算定性完成，新签名重新走本流程。

**⑤ 验收清单**
- [ ] 定性结论有基线复跑证据支撑
- [ ] 定性只覆盖"同一步同签名"的失败

**⑥ 禁忌与易错点**
- 不要做：不复跑就改代码——大概率在修一个不存在的问题，还会掩盖真问题。
- 不要做：把本轮引入的问题甩锅给 flake。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 定性判据 | 同一步＋同签名，共 2 项同时成立 | 约定值（原判据） |
| 基线复跑次数 | 按【连跑计数验收】公式取 N，p 取历史估计失败率 | 公式推导值 |

### 【连跑计数验收】

**① 目标与适用场景**
目标：flake 修复的验收线是连跑次数，不是单次通过。适用：低失败率间歇问题的修复验收。

**② 前置条件**
- [ ] 已估计该 flake 的历史失败率 p，并按步骤 1 的公式算出连跑门槛、写进修复记录
- [ ] 测试环境可连续多轮运行

**③ 操作步骤**
1. 先算门槛再连跑：要以约 95% 把握排除"失败率仍为 p 的 flake 其实没修好"，需连续全绿 N 次，N ≥ ln(0.05)/ln(1−p)，向上取整。对照（公式推导值）：p=20%→14 次；p=10%→29 次；p=5%→59 次；p=1%→299 次。然后执行连跑：全套件与目标套件分别按各自 p 算出的 N 连跑全绿 → 判定信号：每轮结果逐轮记录。原先"全套 5 次、单套 10 次"只是示意量级：按公式反推，5 次全绿只能排除失败率约 45% 以上的 flake、10 次约 26% 以上；失败率 5% 的 flake 连跑 10 次全绿的概率约 60%——低失败率 flake 照 5/10 次验，等于大概率把没修好的报成已修复。
2. 中途出现一次失败 → 计数清零，从头重来 → 判定信号：记录中可见清零点。
3. 达门槛 → 才可报"已修复" → 判定信号：报告附连跑计数。

**④ 失败分支**
- 现象：环境资源不足跑不满次数 → 处置：报"已连跑 N 次，未达门槛"，不许报修好。

**⑤ 验收清单**
- [ ] 门槛已预先写进修复记录
- [ ] 连跑计数达标且逐轮有记录

**⑥ 禁忌与易错点**
- 不要做：单次通过就宣布 flake 修好——失败率百分之几的 flake，单次通过什么都证明不了。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 连跑门槛公式 | N ≥ ln(0.05)/ln(1−p)，向上取整（p=历史失败率，把握约 95%） | 公式推导值 |
| 门槛对照表 | p=20%→14 次；p=10%→29 次；p=5%→59 次；p=1%→299 次 | 公式推导值 |
| 旧经验量级 | 全套 5 次、单套 10 次（仅够排除 p≳45%/p≳26% 的 flake，不许当通用门槛） | 示意量级 |
| 失败处置 | 出现 1 次失败即清零重来 | 约定值（原规则） |

### 【测试抖动如实记录】

**① 目标与适用场景**
目标：环境抖动导致的测试失败如实记录、准确定性，不隐瞒也不误报回归。适用：长时负载下时序敏感断言偶发失败时。

**② 前置条件**
- [ ] 有独立探针可复测同一断言
- [ ] 已保存首跑失败的完整日志

**③ 操作步骤**
1. 首跑失败 → 不删日志、不改结论，先留证据 → 判定信号：失败日志完整保存。
2. 用独立探针复测同一断言，并复跑全套 → 预期：探针与复跑结果出来 → 判定信号：两者全过且失败签名与当时负载条件吻合，才可进入步骤 3。
3. 定性为环境抖动 → 报告写明"首跑失败、复跑通过、判抖动"及证据 → 判定信号：报告含三段事实，不是一句"后来好了"。

**④ 失败分支**
- 现象：探针或复跑也失败 → 处置：不是抖动，按真实失败/回归处理（见【flake 定性流程】）。

**⑤ 验收清单**
- [ ] 首跑失败记录未被隐瞒
- [ ] 抖动定性有探针或复跑证据

**⑥ 禁忌与易错点**
- 不要做：隐瞒首跑失败——下一个人遇到同样失败将无从判断。
- 不要做：凭"感觉是抖动"定性——无证据不定性。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 数值参数 | 无 | 按你的环境测定后填入 |

### 【环境超时≠用例失败】

**① 目标与适用场景**
目标：官方测试脚本超时无产出时，定性为环境问题，不记失败也不冒充绿灯。适用：固定轮询窗口脚本在多任务争抢下超时。

**② 前置条件**
- [ ] 已确认超时时的环境状态（并发任务、资源占用）
- [ ] 有同一测试流程的可驱动版本（可加宽等待）

**③ 操作步骤**
1. 脚本超时无产出 → 先查超时原因是否为资源争抢 → 判定信号：有争抢证据（同期任务/资源占用记录）。
2. 用加宽等待的同流程驱动复跑（只改等待时限，不动断言，见【测试环境适配留痕】）→ 判定信号：复跑得出明确过/不过。
3. 结论分两句写："官方脚本环境超时、非用例失败；同流程加宽等待复跑结果为 X" → 判定信号：两个事实分开陈述，无一句含糊的"通过"。

**④ 失败分支**
- 现象：复跑不过 → 处置：按用例失败处理，超时定性不成立。

**⑤ 验收清单**
- [ ] 超时原因有争抢证据
- [ ] 复跑只改了等待类参数，断言未动且留痕

**⑥ 禁忌与易错点**
- 不要做：把超时记成通过（假绿）或记成失败（冤枉用例）。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 加宽后的等待时限 | 无统一值 | 按你的环境测定后填入（并留痕记录原值与新值） |

### 【零输出诊断法】

**① 目标与适用场景**
目标：长测试"长时间零输出"先诊断，不凭零输出下"卡死"结论。适用：一切长时批处理/长测试。

**② 前置条件**
- [ ] 能查看进程状态与 CPU 占用
- [ ] 能读到被测脚本的源码（看输出设计用）

**③ 操作步骤**
1. 先看脚本输出设计：很多脚本只在跑完才打印最后一行 → 判定信号：若脚本属"末行输出型"，任何阶段未跑完都是字面零输出，零输出不构成卡死证据。
2. 看 CPU 占用判断进程是否在干活：连续采样观察约 30 秒，多点看而不是瞥一眼 → 判定信号：CPU 持续占用=在推进；CPU 为零且无 IO=疑似真卡死，进入步骤 3。必须做单核折算：多核机器上一个单线程满载的进程只占总 CPU 的约 1/核数（如 8 核约 12.5%），不许把"总占用百分之十几"误读成没干活——按"单核占用≈总占用×核数"折算，接近 100% 单核即在满负荷推进；多线程进程则按其线程数同理折算。
3. 疑似卡死 → 结合阶段打点/日志最后位置定位停在哪一步 → 判定信号：能说出最后推进到的阶段才可下卡死结论。
4. 结论：长脚本必须带阶段打点；没有打点的，先补打点再重跑 → 判定信号：重跑的脚本每阶段有输出。

**④ 失败分支**
- 现象：短任务零输出 → 处置：另查——先查进程存活与日志文件，不套长任务结论。

**⑤ 验收清单**
- [ ] 卡死/未卡死结论有输出设计＋CPU 两项依据
- [ ] 长脚本已带阶段打点

**⑥ 禁忌与易错点**
- 不要做：凭零输出杀掉其实在正常推进的长任务——浪费的恰是最贵的长跑时间。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| CPU 采样窗口 | 连续约 30 秒多点采样 | 示意量级 |
| 单核折算 | 单核占用≈总占用×核数（8 核机单线程满载≈总占用 12.5%） | 公式推导值 |
| 阶段打点间隔 | 无 | 按你的环境测定后填入 |

### 【截图定格法】

**① 目标与适用场景**
目标：软件渲染帧饥饿、截不到动态帧时，用定格手段取得真证据帧。适用：无头/软件渲染环境下的视觉取证。

**② 前置条件**
- [ ] 自动化环境支持小视口、对象传送（直接设置位置）、暂停时序/固定帧位

**③ 操作步骤**
1. 改用小视口降低渲染负担 → 预期：帧推进恢复可控 → 判定信号：能稳定停在目标帧位。
2. 用传送把对象直接送到目标位置（不靠走过去）→ 判定信号：对象出现在目标位置。
3. 用定格手段（暂停时序、固定帧位）拍证据帧 → 判定信号：帧可判读（对象、位置、可见性清楚）。
4. 失败的尝试留档说明 → 判定信号：报告中失败尝试有记录。

**④ 失败分支**
- 现象：环境根本不支持对象传送/暂停时序（②前置不成立）→ 处置：不强求定格，直接按【截不到/未采到要明说】披露该项证据未采到、结论标未验证，不要在不支持的环境里反复试到超时。
- 现象：定格也拍不到 → 处置：按【截不到/未采到要明说】披露缺口，不许拿探针数据冒充截图——那是证据造假。

**⑤ 验收清单**
- [ ] 证据帧为真实渲染帧，非数据顶替
- [ ] 引用时已按【验证分账】归账：定格帧只证明该帧状态（位置、可见性），不证明动画流畅度

**⑥ 禁忌与易错点**
- 不要做：拿别的数据顶替截不到的图。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 定格视口尺寸 | 无统一值 | 按你的环境测定后填入（以帧可控为准逐步缩小） |

### 【截不到/未采到要明说】

**① 目标与适用场景**
目标：单项证据没采到就明说没采到，不让缺口被整体通过盖住。适用：一切多项证据的验收。

**② 前置条件**
- [ ] 已列出本轮应采的证据清单（逐项）

**③ 操作步骤**
1. 逐项核对证据清单：采到的标已采，未采到的逐项标注原因（如"无头截图不合成某些图层""因超时未采到"）→ 判定信号：每项状态明确。
2. 报告中对未采项写"数据已证、截图未拍到/未采到"（或对应形态）→ 判定信号：缺口在报告正文可见，不藏附录。
3. 复测时优先补采缺口项 → 判定信号：补采列入复测清单第一项。

**④ 失败分支**
- 现象：单项任务整体没采到证据 → 处置：直接按未验证汇报（见【借口模式二】），不走本条的"部分缺口"口径。

**⑤ 验收清单**
- [ ] 证据清单逐项有状态
- [ ] 未采项已在报告中明说并列入复测优先项

**⑥ 禁忌与易错点**
- 不要做：用场景图或"整体通过"盖住单项缺口——缺口被盖住就会永久沉底，所有人默认它验过了。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 数值参数 | 无 | 按你的环境测定后填入 |

### 【测试环境适配留痕】

**① 目标与适用场景**
目标：为迁就测试环境所做的改动逐项留痕，断言一字不动。适用：一切测试侧改动（等待时限、探针写法等）。

**② 前置条件**
- [ ] 有变更记录的位置（测试记录/提交说明）
- [ ] 已分清哪些是断言、哪些是环境适配项

**③ 操作步骤**
1. 改适配项前先登记：改什么、为什么改、原值与新值 → 判定信号：记录在改动发生前或同时产生，不是事后补。
2. 断言一字不动 → 判定信号：改动 diff 中无断言行变化。
3. 为软件渲染放宽的超时变量 → 只用于验证轮次，生产代码明确不带 → 判定信号：生产代码中检索不到该放宽变量。

**④ 失败分支**
- 现象：适配项与断言界限不清（如改了等待又改了判定窗口）→ 处置：拆开两次改动分别留痕；判定窗口属断言，按断言变更流程走，不许混在适配里。

**⑤ 验收清单**
- [ ] 每项适配改动有原值/新值/原因记录
- [ ] 断言零改动

**⑥ 禁忌与易错点**
- 不要做：适配不留痕——时间一长分不清"标准本来如此"还是"当时为环境放宽过"，验收尺度无声漂移。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 数值参数 | 无（逐项记录原值/新值即可） | 按你的环境测定后填入 |

### 【端口占用假失败】

**① 目标与适用场景**
目标：识别"测试连错页面"造成的假通过/假失败。适用：一切本地起服务的测试。典型症状：日志为空、零错误地"通过"或"失败"。

**② 前置条件**
- [ ] 能查端口归属（哪个进程在监听目标端口）
- [ ] 测试脚手架可改启动等待逻辑

**③ 操作步骤**
1. 见"日志为空＋零错误"的结果先怀疑连错页面 → 查目标端口归属 → 判定信号：监听进程不是被测服务=连错。
2. 释放被占端口（先确认占用方是谁，不许误杀正在运行的正经服务）→ 复跑测试 → 判定信号：复跑结果才作数，首跑结果作废。
3. 脚手架加固，二选一：(a) 被测服务会打印监听行 → 等子进程打印出监听行再放行测试；(b) 被测服务不打印监听行 → 用替代就绪判据：轮询目标端口直到可连接，且健康检查端点（或任一能返回本服务标识的端点，如服务名/版本接口）返回的确实是本服务而非占用方 → 判定信号：健康检查不会被别的服务误答。

**④ 失败分支**
- 现象：端口占用方是正经服务不能杀 → 处置：给被测服务换端口并同步改测试配置，留痕（见【测试环境适配留痕】）。
- 现象：服务不打印监听行，监听行等待永远等不到 → 处置：走步骤 3 的 (b) 替代就绪判据，不许把等待超时当成服务故障。

**⑤ 验收清单**
- [ ] 假失败/假通过的首跑结果已作废并复跑
- [ ] 脚手架有就绪等待逻辑（监听行等待，或端口轮询＋服务标识核验）

**⑥ 禁忌与易错点**
- 不要做：据连错页面的结果下任何结论——它与被测对象毫无关系，而零错误的表象最容易骗过粗看的人。

|---|---|---|
| 数值参数 | 无 | 按你的环境测定后填入 |

### 【200不等于能渲染】

**① 目标与适用场景**
目标：【渲染验证铁律】的操作面——HTTP 200 加源码吻合不等于页面能用。适用：一切 Web 页面与接口验收。

**② 前置条件**
- [ ] 能发 HTTP 请求、能看渲染态、能查关键数据接口回数

**③ 操作步骤**
1. 请求目标页面 → 判定信号：返回 200（只证明服务器给了文件）。
2. 查关键数据接口 → 判定信号：接口有回数且回数与预期量级相符。
3. 实际打开渲染态核对 → 判定信号：渲染内容与数据一致。
4. 三步全过才可下"页面正常"；缺一，结论只能到"已取到文件" → 判定信号：报告措辞与完成步数匹配。

**④ 失败分支**
- 现象：200 但渲染崩坏/数据加载失败 → 处置：按渲染态定性，不许用 200 给结论背书。

**⑤ 验收清单**
- [ ] 三步（状态码/接口回数/渲染态）逐项有记录
- [ ] 结论措辞未越过完成步数

**⑥ 禁忌与易错点**
- 不要做：只看状态码与源码就报页面正常——脚本报错、数据失败、渲染崩坏全都可以在 200 之下发生。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 验收步数 | 3 步（200/接口回数/渲染态） | 约定值（原流程） |

### 【计数对不上报未验证】

### 【抓取失败不反推不存在】

**① 目标与适用场景**
目标：取证失败只说明这次没读到，不反推对象不存在。适用：抓取失败、页面被挡、超时、本地缺文件导致 404 等场合。

**② 前置条件**
- [ ] 已记录失败形态（状态码/超时/被挡/本地缺失）

**③ 操作步骤**
1. 失败后先分形态：是取证通道的问题（被挡、超时）还是对象的问题 → 判定信号：形态定性有依据。
2. 本地文件树缺失导致的 404 → 先分清本地缺文件还是线上真故障 → 判定信号：线上直查结果出来前不下故障结论。
3. 结论只写"未读到/未证实" → 判定信号：报告无"不存在""已损坏"类反推措辞。

**④ 失败分支**
- 现象：多次、多通道都读不到且有旁证 → 可以报"多方未证实存在"，但保留此措辞，不许简化成"不存在"。

**⑤ 验收清单**
- [ ] 失败结论措辞为未读到/未证实
- [ ] 本地 404 已与线上状态分开定性

**⑥ 禁忌与易错点**
- 不要做：从"我没看到"反推"它不存在"——那是把取证能力的边界冒充成世界的边界。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 数值参数 | 无 | 按你的环境测定后填入 |

### 【错了当场撤回】

**① 目标与适用场景**
目标：错误结论在同一回复/同一轮内撤回，不留旧说法过夜。适用：实测或对方指出错误后。

**② 前置条件**
- [ ] 已确认旧说法错了（或至少已确认旧说法不可靠）

**③ 操作步骤**
1. 在同一回复或同一轮工作内撤回：明确指出错的是哪一句 → 判定信号：撤回指向具体句子，含糊的"之前可能不太准"不算撤回。
2. 给出正确事实；正确事实还没查清 → 先撤回，再说"正确值待查" → 判定信号：错误说法不继续挂着等查完。
3. 赶在对方据旧说法行动之前完成撤回 → 判定信号：撤回时效以对方行动为界。

**④ 失败分支**
- 现象：旧说法已被多处引用 → 处置：逐处追改（见【纠正写入必读记录】），对话里的撤回只是第一步。

**⑤ 验收清单**
- [ ] 撤回已发出且指向具体旧句
- [ ] 正确事实已给出或已标待查

**⑥ 禁忌与易错点**
- 不要做：让错误说法继续挂着——旧说法多挂一会儿，对方就可能多做一步基于错误的操作。

**⑦ 参数表**
| 参数 | 值 | 性质 |
|---|---|---|
| 撤回时限 | 同一回复/同一轮内 | 约定值（原纪律） |
| 与实例的关系 | 【执行断言先查实证】里的"15 分钟内纠正"只是一次实例，不是时限标准；本条时限以"赶在对方据旧说法行动之前"为准 | 约定值 |

### 【结论标五级证据】

**① 目标与适用场景**
目标：调研与审计类产出中，每条结论标出证据强度。适用：调研、审计、选型类产出；日常执行汇报用【说法先标来源】的三级标注即可。

**⑥ 禁忌与易错点**

|---|---|---|
